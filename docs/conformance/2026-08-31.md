### Разбивка провалов по причинам (512 всего)

| Причина | Штук | Пример |
|---|---|---|
| too-permissive: парсим то, что спека отвергает | 199 | `http://[1::2]:3:4`, `http://2001::1` (не отличаем IPv6 без скобок / с мусором после) |
| field-mismatch: host (прочее) | 101 | `http://example\t.\norg` (нет удаления forbidden host code points), `http:foo.com` (не заполняем host для схемы `http` без `//`) |
| field-mismatch: pathname (прочее) | 84 | `\t   :foo.com   \n` (нет preprocessing — обрезка control/пробелов) |
| unexpected-failure: пустой host отвергнут | 40 | `foo://`, `foo://///////` — неизвестная схема с пустым host у нас всегда ошибка, спека для non-special схем host не требует |
| field-mismatch: host — IDN / non-ASCII (нет IDNA) | 14 | `http://é@é`, `http://GOO​⁠﻿goo.com` (zero-width не схлопываются), `http://www.foo。bar.com` (ideographic full stop не мапится в `.`) |
| field-mismatch: dot-segment normalization | 15 | `h://.`, `about:/../`, `data:/../` — у нас dot-segments схлопываются только при `has_authority`, у не-special схем — нет |
| field-mismatch: hash (прочее) | 20 | `lolscheme:x x#x x`, `:#` |
| field-mismatch: search (прочее) | 15 | `https://localhost?q=🔥`, `http://host/?'` (нет percent-encoding query по UTF-8 set) |
| field-mismatch: percent-encoding not normalized | 10 | `http://example.com/foo/%2e` (`%2e` не распознаётся как `.` в dot-segments) |
| unexpected-failure: port | 10 | `http://f:\n/c`, `http://[2001::1]` (нет разбора IPv6-адресов в `[...]` вовсе — `parse_authority` ищет `:` как разделитель порта и ломается на IPv6) |
| field-mismatch: empty query | 2 | `?`, `C\|?` |
| unexpected-failure: missing scheme | 2 | управляющие символы в начале строки, не удаляемые preprocessing-ом |

**Читать для LIB-6:** самый крупный класс (199, too-permissive — в основном
IPv6-хосты без `[...]`) и «нет IPv6-адресов в скобках вовсе» (10) — это
одна и та же дыра: `parse_authority` не парсит IPv6 литералы как отдельный
случай, поэтому `[...]` либо не даёт распарсить порт, либо кусок до первого
`:` внутри скобок молча становится host. Второй по размеру класс —
forbidden/control code points в host (101+84 вместе бьют оба) — preprocessing
шаг (обрезка tab/LF/CR, control chars) отсутствует целиком. Оба — не про
IDNA/percent-encoding сложность, а про целые ветки алгоритма WHATWG §4,
которых в `url.rs` просто нет. Решение «чинить точечно vs заменить» —
задача `LIB-6`, эта таблица — входные данные для неё, не сам выбор.

## 2. Текст (шейпинг)

Метод — §3.2. Проба — [`probes/text-shaping.html`](probes/text-shaping.html).
Свидетельство — [`2026-08-31-evidence/text-shaping.dump-display-list.txt`](2026-08-31-evidence/text-shaping.dump-display-list.txt)
+ [`2026-08-31-evidence/text-shaping.png`](2026-08-31-evidence/text-shaping.png).

**Методологическая находка (добавлена в `conformance-method.md` §4):**
ни один headless/MCP путь снимка (`--screenshot`, `--dump-display-list`-рендер,
MCP `resource://screenshot` живого окна) не подключает `SystemFontIndex` —
все они строят `Renderer::new_headless(INTER_FONT.to_vec(), …)`
(`crates/driver/src/winit_session.rs::screenshot`, тот же приём в
`crates/engine/paint/src/cpu_raster.rs`), поэтому любой текст рисуется
ТОЛЬКО bundled Inter, класс BUG-221. Проверено: `lumen_font::cmap` для
Tahoma верно находит `U+0639`→969, `U+05E9`→697 (юнит-проба поверх
`lumen-font` напрямую) — то есть системные шрифты индексируются и парсятся
правильно, дыра именно в том, что рендер-пути снимка их не запрашивают.
Единственный путь с реальным `SystemFontIndex` — видимое окно, снятое
`gdigrab` (как `graphic_tests/run.py`) или просмотренное человеком; в рамках
этой сессии не поднимался (тяжелее по времени, чем оправдано для одной
пробы). Отсюда — пункты 05–08 помечены «не проверено», а не FAIL.

| № | Проверка | Шрифт | Результат |
|---|---|---|---|
| 01 | Лигатура fi/ffi | Inter (bundled) | **Не проверено машиной**: рисуется, но глиф-уровневых данных (glyph ID) дамп не даёт, а скриншот на этом масштабе неразличим. Визуально правдоподобно |
| 02 | Кернинг AV/To | Inter (bundled) | **Не проверено машиной** — та же причина: нет per-glyph advance в дампе |
| 03a | `e` + U+0301 (decomposed) | Inter (bundled) | **PASS** — ширина в дампе (220.10) и вид на скриншоте идентичны 03b |
| 03b | `é` (precomposed) | Inter (bundled) | **PASS** (контроль для 03a) |
| 04 | Вьетнамский (2 диакритика на букве) | Inter (bundled) | **PASS** — рендерится корректно, диакритики на месте (precomposed-кодпоинты, не проверяет GPOS-стекинг двух комбинирующих знаков) |
| 05 | Арабское соединение (4 формы) | системный (Tahoma/Segoe UI/…) | **Не проверено** — headless-путь не грузит систему шрифты (см. находку выше) |
| 06 | Деванагари (переупорядочение) | системный (Nirmala UI/…) | **Не проверено**, та же причина |
| 07 | Иврит с огласовками | системный | **Не проверено**, та же причина |
| 08 | RTL + смешанные числа | системный | **Не проверено**, та же причина |
| — | Контроль (magenta box) | — | PASS — страница загрузилась целиком |

**Итог:** 3 из 9 содержательных проверок дают числовой PASS (03a/03b/04),
2 неразличимы этим инструментарием (01/02 — нужен per-glyph дамп, которого
нет), 4 не проверены вовсе (05–08 — блокированы находкой про headless-путь).
Знаменатель здесь **сознательно не сведён к проценту** — метод (§2) требует
фиксировать знаменатель один раз, а с текущим инструментарием честный
знаменатель «доказуемых» проверок — 4 из 9, что не отражает конформность
шейпера, а отражает дыру в тулинге. Прежде чем повторять этот замер после
LIB-1, нужно закрыть эту дыру (снимок через видимое окно + `gdigrab`,
или добавить per-glyph ID в `--dump-display-list`).

## 3. SVG

[`probes/svg-inline.html`](probes/svg-inline.html) (inline `<svg>` в
разметке) и [`probes/svg-external.html`](probes/svg-external.html)

[`2026-08-31-evidence/`](2026-08-31-evidence/). В отличие от текста, SVG-путь
не зависит от `SystemFontIndex` — снимок здесь достоверен для обоих путей.

| 02 | Радиальный градиент, fill | **FAIL** — `FillRoundedRect … #000000ff` | **FAIL** |
| 03 | Градиент `url(#)` на stroke | **FAIL** — команда не эмитится вовсе (пусто) | **FAIL** — пусто на скриншоте |

**Знаменатель — 9 содержательных проверок × 2 пути = 18. Пройдено — 2 (оба
контроля). Доля — 11.1 %.** Это ожидаемо: LIB task прямо называет «ноль
градиентов, масок, фильтров в пути отрисовки» — перепись подтверждает это
числом, а не оценкой на глаз, и даёт byte-level свидетельство (дамп) для
сравнения после LIB-4/LIB-5.

Оговорка по проверке 09: провал вызван тем, что headless-путь не фетчит
`data:` URI внутри `<image>` вообще (сетевой уровень, не рендер-путь) —
это ДРУГОЙ дефект от «нет градиентов/масок» (см. `docs/automation.md`'s
"fetch()/XMLHttpRequest do nothing in headless dump modes"-класс готчи).
Проверка сама по себе (умеет ли SVG-рендерер рисовать вложенный `<image>`)
этим прогоном не закрыта; повторить с внешним `href` на реальном сервере
перед тем, как читать эту строку как «LIB-5 закрыла nested image».
