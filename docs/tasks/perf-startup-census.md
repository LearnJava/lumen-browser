# Census стоимости старта — брифы PERF-9 / PERF-11 / PERF-12

Бриф для ROADMAP.md-задач `PERF-9`, `PERF-11`, `PERF-12` (Фаза 3, дорожка `PERF`).
Владелец движковых правок — **P1**. Все числа этого файла получены 2026-08-18 в слоте
`p1-work`, профиль `dev-release`, Windows 10, машина пользователя.

**Числа этого файла — не догадки, каждое воспроизводится командой из раздела «Как перемерить».**
Перед тем как править что-либо по этим задачам, перемеряй на своей машине: абсолютные величины
машинозависимы, значим только их порядок и соотношение.

---

## 1. Откуда взялись эти задачи

Отправная точка — не найденный баг и не жалоба на скорость, а вопрос пользователя (2026-08-18) про
[lightpanda-io/browser](https://github.com/lightpanda-io/browser): headless-браузер на Zig,
заявляющий 9× по времени и 16× по памяти против headless Chrome. Разбор показал, что их выигрыш
почти целиком берётся из **отсутствия рендеринга** (нет layout, paint, композитора, шрифтов,
декодирования картинок) — то есть скопировать его, оставаясь рендерящим браузером, нельзя.

Переносимой оказалась одна их техника: они embed-ят **стартовый снапшот V8**, чтобы не собирать
окружение заново. Отсюда PERF-9. Задача PERF-10 (прогон тестов без растеризации) — ослабленный
вариант их «хирургического вычитания»: layout мы сохраняем, отключаем только paint и живое окно.

PERF-11 и PERF-12 **не планировались** — они выпали из census, который делался ради PERF-9 по
требованию [`docs/perf-method.md`](../perf-method.md) («census before the fix»). Оказалось, что обе
крупнее той задачи, ради которой измерялись.

## 2. Что намерено

### 2.1. Разложение процесса по режимам дампа

`samples/page.html`, min из 3 прогонов:

| Режим | мс | дельта | что добавляет |
|---|---|---|---|
| `--dump-source` | 114 | — | старт процесса + чтение + парсинг HTML |
| `--dump-layout` | 209 | **+95** | стили и layout |
| `--dump-display-list` | 219 | +10 | построение display list |
| `--screenshot` | 247 | +28 | CPU-растеризация + PNG |

### 2.2. +95 мс — это не текст

Синтетические страницы:

| Страница | `--dump-source` | `--dump-layout` | дельта |
|---|---|---|---|
| один `<div>`, **ни одного символа** | 111 | 217 | **+106** |
| `<p>a</p>` | 134 | 231 | +97 |

Страница, в которой нечего верстать, платит те же ~100 мс. Значит это фиксированная
инициализация при первом layout, а не работа с содержимым.

### 2.3. Источник: индекс системных шрифтов (PERF-11)

Census-тест [`crates/engine/font/src/system_fonts.rs`](../../crates/engine/font/src/system_fonts.rs)
`perf_census::census_system_font_index_build_cost`:

```
shared_system_index() handle:  26.6 µs
first index build:            124.4 ms   (174 семейства)
second call (cached):          0.13 ms
```

`shared_system_index()` строит индекс лениво через `OnceLock`; `build_index` → `scan_dir` читают и
парсят имена/OS-2 у **сотен файлов** в системных директориях шрифтов. Комментарий в самом файле это
признаёт («в системных директориях это сотни файлов»), но плата берётся с **каждого запуска
процесса**.

### 2.4. Разложение JS-инициализации (PERF-9)

Census-тесты в [`crates/js/src/v8_runtime.rs`](../../crates/js/src/v8_runtime.rs) (`perf9_*`),
стационар:

| Фаза | мс | доля `install_dom` |
|---|---|---|
| `V8JsRuntime::new` (изолят + контекст) | 2.5 | — |
| регистрация 184 нативов + setup | 1.2 | 1 % |
| eval `WEB_API_SHIM` (732 991 байт) | 30.3 | 35 % |
| батч ~68 JS-модулей + `seal_internal_globals` | 53.6 | 63 % |
| **`install_dom` итого** | **85.8** | 100 % |

95 % стоимости — исполнение JS, то есть ровно то, что снапшот заменяет десериализацией.

### 2.5. Итоговая карта рычагов

| Что | мс | когда платится |
|---|---|---|
| скан шрифтов (**PERF-11**) | 124 | **всегда**, любая страница |
| фиксированный старт процесса (**PERF-12**) | 111 | **всегда** |
| JS-инициализация (**PERF-9**) | 86 | только страницы со скриптами |
| собственно layout + display list + paint простой страницы | ~30 | — |

Для простой страницы ~220 из 247 мс — накладные, не зависящие от содержимого.

## 4. PERF-11 — кэш индекса системных шрифтов

**Статус `ready`, размер S, рекомендуется брать первой** — выигрыш больше, чем у PERF-9,
платится всегда, риск минимальный.

### Что делать

Сериализовать построенный индекс на диск и читать его вместо скана.

1. Место хранения — `<exe_dir>/data/fonts/` через `browser_data_dir()`. **Не** `%APPDATA%`,
   не `lumen_cache_dir()`, не `config_path()` — портируемая конвенция проекта, см. CLAUDE.md
   Known gotchas (решение пользователя 2026-06-16).
2. Инвалидация — по mtime + размеру каждой сканируемой директории. Промах кэша → строить как
   сейчас и перезаписать.
3. Формат — свой, без новых зависимостей (политика §5 tech-stack). Индекс это
   `HashMap<String, Vec<FaceRecord>>`, `FaceRecord` плоский.
4. Битый/устаревший/нечитаемый кэш обязан деградировать в полный скан, а не в панику и не в
   пустой индекс: пустой список семейств — это страница без шрифтов, то есть тихая порча
   рендера вместо честной задержки.

### Ловушки

- Гонка: несколько процессов Lumen (graphic_tests гоняет их пачками) пишут кэш одновременно →
  писать во временный файл рядом и переименовывать.
- `assets/fonts/Inter-Regular.ttf` (бандленный) обязан оставаться доступен и при промахе кэша —
  `rasterizer.rs:538` читает его напрямую, мимо индекса.
- Проверять надо не только «стало быстрее», но и что `list_families()` даёт **тот же** набор:
  сравнение с холодным сканом должно быть точным, иначе кэш молча теряет шрифты.

### Гейт

`cargo test -p lumen-font census_system_font -- --nocapture` до и после — первое построение должно
упасть со 124 мс до единиц. Плюс процессный A/B: `--dump-layout` на странице без текста должен
потерять ~100 мс. Порядок сравнения — по min из ≥3 прогонов ([`docs/perf-method.md`](../perf-method.md)),
не по одному замеру.

Изменение не может двигать пиксели (набор шрифтов тот же) → гейт `scripts/scoped-test.sh` +
пустой diff `python graphic_tests/dump_golden.py`, полный 20-минутный прогон не нужен. Но если
`dump_golden.py` покажет **любой** diff — значит кэш отдаёт не тот набор шрифтов, и это баг кэша,
а не «ожидаемое расхождение».

## 5. PERF-12 — фиксированный старт процесса

**Статус `planned`, размер M. Первый шаг — не оптимизация, а инструментация.**

111 мс уходят до всякой полезной работы (`--dump-source` на странице из одного `<div>`). Сейчас это
чёрный ящик: спанов `lumen_core::trace` на участке «`main()` → первая полезная работа» нет вовсе.
Для сравнения, у PERF-1 (`--trace-nav`) спаны покрывают лишь 52 мс из 266 мс спана `navigation` на
`samples/page.html` — остальное не инструментировано, и именно дыры в waterfall и есть предмет
задачи.

### Порядок

1. Расставить спаны от входа в `main()` до первой полезной работы и внутри `navigation` — закрыть
   214 мс безымянных. Инструментация уже устроена как no-op вне трейса (один relaxed atomic), так
   что висит на общем пути даром.
2. Только после этого решать, что резать.

### Кандидаты в источники, по убыванию правдоподобия

- загрузка ~70-МБ бинаря загрузчиком ОС — PERF-4 отделил `cold − warm = 43 мс`, но остаток warm не
  разложен;
- инициализация V8-платформы (`ensure_v8_platform`);
- прочие статики/`OnceLock` на общем пути — PERF-11 показала, что такое здесь водится.

## 6. PERF-9 — состояние и поправка к методике

Задача остаётся `active`, ветка `p1-v8-snapshot` существует. Осуществимость подтверждена, но
дороже, чем казалось.

### Хорошее

- `web_api_shim()` ([`dom.rs:15791`](../../crates/js/src/dom.rs)) — чистая конкатенация констант
  **без единого параметра страницы**, текст побайтово одинаков для любого URL → снапшот строится
  один раз на сборку.
- rusty_v8 150.1.0 даёт всё нужное: `Isolate::snapshot_creator`, `set_default_context`,
  `create_blob`, `CreateParams::snapshot_blob`, `Context::from_snapshot`.
- Регистрация нативов, которая в снапшот принципиально не попадает, стоит 1.2 мс — то есть
  неоптимизируемая часть ничего и не весит.

### Препятствие

Шим вызывает нативы **на верхнем уровне**, то есть снапшот нельзя снять «как есть». Тест
`perf9_census_top_level_native_deps` перечисляет их, следуя за ошибками интерпретатора — **19 штук**:

- 7 DOM: `_lumen_get_document_root`, `_lumen_append_child`, `_lumen_insert_before`,
  `_lumen_set_attr`, `_lumen_set_inner_html`, `_lumen_remove_child`, `_lumen_set_text_content`;
- 12 storage: `_lumen_ls_*`, `_lumen_ss_*` (по 6);
- плюс глобальная константа `_LUMEN_CROSS_ORIGIN_ISOLATED`.

Каждый — per-document Rust-замыкание, то есть сайт, который придётся сделать ленивым до снятия
снапшота.

### Рекомендуемый порядок срезов

Батч из ~68 модулей даёт 63 % выигрыша и, в отличие от `WEB_API_SHIM`, документа скорее всего не
касается («plain JS-shim installs» по комментарию на месте) — брать его первым, `WEB_API_SHIM` с
его 19 ленивыми сайтами вторым.

### Более дешёвая альтернатива, ещё не пробованная

**V8 code cache** вместо снапшота: `ScriptCompiler::create_code_cache` /
`Source::new_with_cached_data` / `cached_data_version_tag` в rusty_v8 150.1.0 есть (проверено).
Кэш байткода убирает парсинг 716 КБ, **не требуя ленивых сайтов вообще**, потому что исполнение
остаётся на месте. Выигрыш меньше снапшота (парсинг, но не исполнение), зато цена реализации
несопоставимо ниже, и одно другому не мешает. Перед выбором стоит померить, какая доля из 30 мс
eval-а — парсинг.

### Методическая поправка — важно

`run_scripts_with_dom` ([`crates/shell/src/main.rs:7171`](../../crates/shell/src/main.rs)) содержит
ранний возврат:

```rust
if scripts.is_empty() && module_scripts.is_empty() && extra_scripts.is_empty() {
    return (doc_arc, None, None);
}
```

Страница без скриптов V8 не создаёт вовсе. Следовательно `samples/page.html` за JS **не платит**, и
базлайн `cargo run -p lumen-bench -- --startup`, который гоняет именно её, **путь PERF-9 не меряет**.
Гейт PERF-9 обязан строиться на странице со скриптами — иначе изменение покажет ноль независимо от
того, работает оно или нет.

## 7. Как перемерить

```bash
# JS-инициализация: три census-теста (печатают, не ассертят)
cargo test -p lumen-js --features v8-backend --profile dev-release perf9 -- --nocapture --test-threads=1

# индекс шрифтов
cargo test -p lumen-font --profile dev-release census_system_font -- --nocapture

# пофазный процессный замер (min из 3 — один прогон ничего не значит)
for mode in --dump-source --dump-layout --dump-display-list; do
  for i in 1 2 3; do /usr/bin/time -f "$mode %e" ./target/dev-release/lumen.exe $mode samples/page.html >/dev/null; done
done

# waterfall навигации
./target/dev-release/lumen.exe --trace-nav .tmp/nav.json samples/page.html

# базлайн старта процесса (внимание: samples/page.html не содержит скриптов, см. §6)
cargo run -p lumen-bench --profile dev-release -- --startup --iters 7
```

## 8. Чего из lightpanda сознательно НЕ берём

- **libcurl** — у нас свой сетевой слой с политикой приватности, HSTS, cookie-jar; менять на curl
  значит терять контроль над тем, ради чего браузер писался.
- **html5ever через FFI** — у них это осмысленно (Zig, писать парсер HTML5 не хочется), у нас свой
  парсер, и census показал, что `parse-html` на samples-масштабе — 0.07 мс, то есть не предмет.
- **их бенчмарк как ориентир** — 933 страницы в краулинг-режиме без рендера; с нашими числами
  несопоставим, сравнение будет ложным.
