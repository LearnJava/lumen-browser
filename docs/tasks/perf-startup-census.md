# Census стоимости старта — брифы PERF-9 / PERF-11 / PERF-12

Бриф для ROADMAP.md-задач `PERF-9`, `PERF-11`, `PERF-12` (Фаза 3, дорожка `PERF`).
Владелец движковых правок — **P1**. Все числа этого файла получены 2026-08-18 в слоте
`p1-work`, профиль `dev-release`, Windows 10, машина пользователя.

**Числа этого файла — не догадки, каждое воспроизводится командой из раздела «Как перемерить».**
Перед тем как править что-либо по этим задачам, перемеряй на своей машине: абсолютные величины
машинозависимы, значим только их порядок и соотношение.

---

## 1. Откуда взялись эти задачи

Отправная точка — не найденный баг и не жалоба на скорость, а вопрос пользователя (2026-08-18) про
[lightpanda-io/browser](https://github.com/lightpanda-io/browser): headless-браузер на Zig,
заявляющий 9× по времени и 16× по памяти против headless Chrome. Разбор показал, что их выигрыш
почти целиком берётся из **отсутствия рендеринга** (нет layout, paint, композитора, шрифтов,
декодирования картинок) — то есть скопировать его, оставаясь рендерящим браузером, нельзя.

Переносимой оказалась одна их техника: они embed-ят **стартовый снапшот V8**, чтобы не собирать
окружение заново. Отсюда PERF-9. Задача PERF-10 (прогон тестов без растеризации) — ослабленный
вариант их «хирургического вычитания»: layout мы сохраняем, отключаем только paint и живое окно.

PERF-11 и PERF-12 **не планировались** — они выпали из census, который делался ради PERF-9 по
требованию [`docs/perf-method.md`](../perf-method.md) («census before the fix»). Оказалось, что обе
крупнее той задачи, ради которой измерялись.

### 2.2. +95 мс — это не текст

Синтетические страницы:

| Страница | `--dump-source` | `--dump-layout` | дельта |
|---|---|---|---|
| один `<div>`, **ни одного символа** | 111 | 217 | **+106** |
| `<p>a</p>` | 134 | 231 | +97 |

Страница, в которой нечего верстать, платит те же ~100 мс. Значит это фиксированная
инициализация при первом layout, а не работа с содержимым.

### 2.3. Источник: индекс системных шрифтов (PERF-11)

Census-тест [`crates/engine/font/src/system_fonts.rs`](../../crates/engine/font/src/system_fonts.rs)
`perf_census::census_system_font_index_build_cost`:

```
shared_system_index() handle:  26.6 µs
first index build:            124.4 ms   (174 семейства)
second call (cached):          0.13 ms
```

`shared_system_index()` строит индекс лениво через `OnceLock`; `build_index` → `scan_dir` читают и
парсят имена/OS-2 у **сотен файлов** в системных директориях шрифтов. Комментарий в самом файле это
признаёт («в системных директориях это сотни файлов»), но плата берётся с **каждого запуска
процесса**.

### 2.4. Разложение JS-инициализации (PERF-9)

Census-тесты в [`crates/js/src/v8_runtime.rs`](../../crates/js/src/v8_runtime.rs) (`perf9_*`),
стационар:

| Фаза | мс | доля `install_dom` |
|---|---|---|
| `V8JsRuntime::new` (изолят + контекст) | 2.5 | — |
| регистрация 184 нативов + setup | 1.2 | 1 % |
| eval `WEB_API_SHIM` (732 991 байт) | 30.3 | 35 % |
| батч ~68 JS-модулей + `seal_internal_globals` | 53.6 | 63 % |

95 % стоимости — исполнение JS, то есть ровно то, что снапшот заменяет десериализацией.

## 4. PERF-11 — кэш индекса системных шрифтов

**Статус `ready`, размер S, рекомендуется брать первой** — выигрыш больше, чем у PERF-9,
платится всегда, риск минимальный.

### Что делать

Сериализовать построенный индекс на диск и читать его вместо скана.

1. Место хранения — `<exe_dir>/data/fonts/` через `browser_data_dir()`. **Не** `%APPDATA%`,
   не `lumen_cache_dir()`, не `config_path()` — портируемая конвенция проекта, см. CLAUDE.md
   Known gotchas (решение пользователя 2026-06-16).
2. Инвалидация — по mtime + размеру каждой сканируемой директории. Промах кэша → строить как
   сейчас и перезаписать.
3. Формат — свой, без новых зависимостей (политика §5 tech-stack). Индекс это
   `HashMap<String, Vec<FaceRecord>>`, `FaceRecord` плоский.
4. Битый/устаревший/нечитаемый кэш обязан деградировать в полный скан, а не в панику и не в
   пустой индекс: пустой список семейств — это страница без шрифтов, то есть тихая порча
   рендера вместо честной задержки.

### Ловушки

- Гонка: несколько процессов Lumen (graphic_tests гоняет их пачками) пишут кэш одновременно →
  писать во временный файл рядом и переименовывать.
- `assets/fonts/Inter-Regular.ttf` (бандленный) обязан оставаться доступен и при промахе кэша —
  `rasterizer.rs:538` читает его напрямую, мимо индекса.
- Проверять надо не только «стало быстрее», но и что `list_families()` даёт **тот же** набор:
  сравнение с холодным сканом должно быть точным, иначе кэш молча теряет шрифты.

### Гейт

`cargo test -p lumen-font census_system_font -- --nocapture` до и после — первое построение должно
упасть со 124 мс до единиц. Плюс процессный A/B: `--dump-layout` на странице без текста должен
потерять ~100 мс. Порядок сравнения — по min из ≥3 прогонов ([`docs/perf-method.md`](../perf-method.md)),
не по одному замеру.

Изменение не может двигать пиксели (набор шрифтов тот же) → гейт `scripts/scoped-test.sh` +
пустой diff `python graphic_tests/dump_golden.py`, полный 20-минутный прогон не нужен. Но если
`dump_golden.py` покажет **любой** diff — значит кэш отдаёт не тот набор шрифтов, и это баг кэша,
а не «ожидаемое расхождение».

## 5. PERF-12 — фиксированный старт процесса

**Шаг 1 (инструментация) сделан 2026-08-18, ветка `p1-perf-12`. Его результат опроверг постановку
задачи — читать раздел целиком, прежде чем что-либо оптимизировать.**

### 5.1. Что было заявлено

> 111 мс уходят до всякой полезной работы (`--dump-source` на странице из одного `<div>`), это
> чёрный ящик, кандидаты — загрузчик ОС, `ensure_v8_platform`, статики/`OnceLock` на общем пути.

### 5.2. Что построено

- [`crates/shell/src/startup_trace.rs`](../../crates/shell/src/startup_trace.rs) — секундомер
  фиксированного старта. Спаны `pre-main` / `config-load` / `arg-parse` / `services-init` и
  охватывающая полоса `startup (<режим>)`.
- `lumen_core::trace::enable_at(origin)` + `record_span(name, cat, begin, end)` — трейсер теперь
  можно завести с началом отсчёта **в прошлом** и досыпать в таймлайн уже завершившийся отрезок.
  Без этого участок до `main()` не выразим в принципе: `enable()` ставит origin «сейчас».
- Трейсер включается на первой строке `run_cli` (сырой скан argv на `--trace-nav`), а не в
  `run_trace_nav`. **`run_trace_nav` больше не зовёт `enable()`** — повторный вызов сбросил бы
  origin и потерял все стартовые спаны.
- `LUMEN_STARTUP_LOG=1` — та же раскладка на stderr. Нужна потому, что trace-файл пишет только
  режим `--trace-nav`: `--dump-*` его не пишет, а выход по ошибке аргументов случается задолго до.
- Время создания процесса берётся у ОС (`GetProcessTimes`, Windows; на прочих ОС — `None` и
  деградация к отсчёту от входа в `main`). Никакой `Instant` внутри процесса участок до `main`
  увидеть не может, а `std` времени создания процесса не отдаёт.

### 5.3. Раскладка

Тёплый прогон, `--dump-source` на странице из одного `<div>`:

| Участок | мс |
|---|---|
| `pre-main` (загрузчик ОС + CRT) | **26** |
| `config-load` | 0.1 |
| `arg-parse` | 0.1 |
| `services-init` | 0.0 |
| весь процесс от создания до конца `main` | **30** |

Холодный прогон (бинарь только что перезаписан, не в файловом кэше): `pre-main` = 145 мс.

### 5.4. Постановка задачи опровергнута в двух местах

**Во-первых, наш собственный код до диспетча стоит 0.7 мс.** Ни `config::load`, ни разбор
аргументов, ни спавн сервисов не являются предметом. `ensure_v8_platform` на этом пути **не
вызывается вовсе** — V8 создаётся только на страницах со скриптами (см. §6), так что кандидат №2
из заявки к `--dump-source` не относится.

**Во-вторых, самих «111 мс» у процесса нет.** Это артефакт внешнего секундомера. Контроль
(min из 5, чередование, одинаковый харнесс):

| exe | размер | мс |
|---|---|---|
| `hostname.exe` | 15 КБ | 83 |
| `where.exe` | 43 КБ | 83 |
| `git.exe --version` | 4 МБ | 81 |
| `lumen.exe` (выход по ошибке аргументов) | **80 МБ** | **133** |

Стоимость спавна **плоская ~82 мс** от 15 КБ до 4 МБ — это константа `bash`+ОС, которую платит
любой процесс, и она к Lumen не относится. Собственная надбавка Lumen = 133 − 82 ≈ **51 мс**, из
которых 26 мс видны изнутри как `pre-main`, а остальные ~25 мс приходятся на exec 80-МБ образа и
teardown процесса — то есть лежат вне `main` и изнутри неизмеримы.

**Единственный рычаг PERF-12 — размер бинаря (80 МБ).** Он же управляет и `pre-main`, и
exec/teardown, и холодным штрафом (145 мс). Это вопрос конфигурации сборки —
[`docs/build-speed.md`](../build-speed.md), — а не кода старта. Резать в `run_cli` нечего.

### 5.5. Побочная находка: 114 мс безымянных внутри `navigation`

Заявка обещала «дыры в waterfall» — они нашлись, но не там, где искали. На `samples/page.html`
спан `navigation` = 128 мс, детские спаны покрывали 13.8 мс, **дыра 114.7 мс** — и она лежала
между `parse-css` и `layout`, при том что сам `layout` = 0.6 мс.

Виновник назван двумя новыми спанами (`font-faces`, `system-fonts` в `parse_and_layout`):
это `system_font_faces()` — ленивое построение индекса системных шрифтов, то есть **PERF-11**.
После инструментации дыра 114.7 мс → **0.9 мс**, а `system-fonts` стал доминирующим спаном
таймлайна.

Практическое следствие: у PERF-11 теперь есть точный гейт — спан `system-fonts` в
`--trace-nav`-таймлайне, а не только процессный A/B.

### 5.6. Что осталось от PERF-12

1. Размер бинаря — единственный оставшийся рычаг, отдельная задача в терминах
   `docs/build-speed.md` (LTO, `opt-level`, состав зависимостей). Заводить её имеет смысл
   **после PERF-11**: 124 мс шрифтов больше, чем 51 мс образа.
2. Инструментация — сделана и висит на общем пути даром (один relaxed atomic вне трейса).

### 5.7. Оговорка о числах этого раздела

Часть замеров снята, когда на машине параллельно шла сборка (3 × `rustc.exe`) — абсолютные
величины в такие моменты завышены вдвое-втрое (`pre-main` 26 мс → 77 мс на том же бинаре).
Доверять здесь следует **соотношениям и чередующимся сравнениям** (контрольная таблица §5.4
снята одним прогоном, все exe в одинаковых условиях), а не абсолютным миллисекундам.
Перед любой оптимизацией перемерить на незанятой машине — §7.

## 6. PERF-9 — состояние и поправка к методике

**ЗАКРЫТА 2026-08-21 (ветка `p1-perf-9`), но не тем путём, что здесь намечен.** Полный V8-снапшот
(§ ниже) не реализован — вместо него взята альтернатива из «Более дешёвая альтернатива» (§ ниже),
применённая к рекомендованному первому срезу («батч ~68 модулей», без `WEB_API_SHIM`). Подробности
результата — § 9. Ветка `p1-v8-snapshot` была пуста (только этот бриф-коммит, слит напрямую в main
2026-08-18) и с тех пор удалена как исчерпанная. Разделы ниже оставлены как есть — историческая
запись рассуждения, приведшего к § 9, не переписывается задним числом.

### Хорошее

- `web_api_shim()` ([`dom.rs:15791`](../../crates/js/src/dom.rs)) — чистая конкатенация констант
  **без единого параметра страницы**, текст побайтово одинаков для любого URL → снапшот строится
  один раз на сборку.
- rusty_v8 150.1.0 даёт всё нужное: `Isolate::snapshot_creator`, `set_default_context`,
  `create_blob`, `CreateParams::snapshot_blob`, `Context::from_snapshot`.
- Регистрация нативов, которая в снапшот принципиально не попадает, стоит 1.2 мс — то есть
  неоптимизируемая часть ничего и не весит.

### Препятствие

Шим вызывает нативы **на верхнем уровне**, то есть снапшот нельзя снять «как есть». Тест
`perf9_census_top_level_native_deps` перечисляет их, следуя за ошибками интерпретатора — **19 штук**:

- 7 DOM: `_lumen_get_document_root`, `_lumen_append_child`, `_lumen_insert_before`,
  `_lumen_set_attr`, `_lumen_set_inner_html`, `_lumen_remove_child`, `_lumen_set_text_content`;
- 12 storage: `_lumen_ls_*`, `_lumen_ss_*` (по 6);
- плюс глобальная константа `_LUMEN_CROSS_ORIGIN_ISOLATED`.

Каждый — per-document Rust-замыкание, то есть сайт, который придётся сделать ленивым до снятия
снапшота.

### Рекомендуемый порядок срезов

Батч из ~68 модулей даёт 63 % выигрыша и, в отличие от `WEB_API_SHIM`, документа скорее всего не
касается («plain JS-shim installs» по комментарию на месте) — брать его первым, `WEB_API_SHIM` с
его 19 ленивыми сайтами вторым.

### Более дешёвая альтернатива, ещё не пробованная

**V8 code cache** вместо снапшота: `ScriptCompiler::create_code_cache` /
`Source::new_with_cached_data` / `cached_data_version_tag` в rusty_v8 150.1.0 есть (проверено).
Кэш байткода убирает парсинг 716 КБ, **не требуя ленивых сайтов вообще**, потому что исполнение
остаётся на месте. Выигрыш меньше снапшота (парсинг, но не исполнение), зато цена реализации
несопоставимо ниже, и одно другому не мешает. Перед выбором стоит померить, какая доля из 30 мс
eval-а — парсинг.

### Методическая поправка — важно

`run_scripts_with_dom` ([`crates/shell/src/main.rs:7171`](../../crates/shell/src/main.rs)) содержит
ранний возврат:

```rust
if scripts.is_empty() && module_scripts.is_empty() && extra_scripts.is_empty() {
    return (doc_arc, None, None);
}
```

Страница без скриптов V8 не создаёт вовсе. Следовательно `samples/page.html` за JS **не платит**, и
базлайн `cargo run -p lumen-bench -- --startup`, который гоняет именно её, **путь PERF-9 не меряет**.
Гейт PERF-9 обязан строиться на странице со скриптами — иначе изменение покажет ноль независимо от
того, работает оно или нет.

## 7. Как перемерить

```bash
# JS-инициализация: три census-теста (печатают, не ассертят)
cargo test -p lumen-js --features v8-backend --profile dev-release perf9 -- --nocapture --test-threads=1

# индекс шрифтов
cargo test -p lumen-font --profile dev-release census_system_font -- --nocapture

# пофазный процессный замер (min из 3 — один прогон ничего не значит)
for mode in --dump-source --dump-layout --dump-display-list; do
  for i in 1 2 3; do /usr/bin/time -f "$mode %e" ./target/dev-release/lumen.exe $mode samples/page.html >/dev/null; done
done

# waterfall навигации
./target/dev-release/lumen.exe --trace-nav .tmp/nav.json samples/page.html

# базлайн старта процесса (внимание: samples/page.html не содержит скриптов, см. §6)
cargo run -p lumen-bench --profile dev-release -- --startup --iters 7

# раскладка фиксированного старта изнутри процесса (PERF-12, §5) — работает
# в ЛЮБОМ режиме, включая те, что не пишут trace-файл и выходят по ошибке аргументов
LUMEN_STARTUP_LOG=1 ./target/dev-release/lumen.exe --dump-source .tmp/onediv.html 2>&1 >/dev/null

# waterfall теперь начинается от создания процесса, а не от навигации
./target/dev-release/lumen.exe --trace-nav .tmp/nav.json samples/page.html

# КОНТРОЛЬ, без которого числа выше читаются неверно: сколько стоит спавн любого
```

## 9. PERF-9 — что реально landed (2026-08-21, ветка `p1-perf-9`)

Взят не снапшот, а «более дешёвая альтернатива» из §6, и не на весь `install_dom`, а только на
рекомендованный первый срез — батч модульных JS-шимов, **`WEB_API_SHIM` исключён сознательно**.

### Механизм

Процесс-локальный кэш V8-байткода: `CODE_CACHE` (`LazyLock<Mutex<HashMap<u64, Vec<u8>>>>`, ключ —
`DefaultHasher` от исходного текста) + макрос `compile_cached!`, оба в
[`crates/js/src/v8_runtime.rs`](../../crates/js/src/v8_runtime.rs) рядом с `with_tc!`. `eval()`
( `impl JsRuntime for V8JsRuntime`) прозрачно заменяет прямой `v8::Script::compile` на
`compile_cached!`: ниже `CODE_CACHE_MIN_LEN` (512 байт) — то же самое, что раньше; на/выше —
промах компилирует через `v8::script_compiler::compile_unbound_script` (`NoCompileOptions`),
зовёт `UnboundScript::create_code_cache()` и кладёт байты в `CODE_CACHE`; попадание пересобирает
`Source` через `Source::new_with_cached_data` + `ConsumeCodeCache` и **не** перепарсивает текст —
если V8 всё же отверг кэш (`CachedData::rejected()`), код самовосстанавливается обычной
компиляцией и перезаписывает запись. Скрипт в обоих случаях **исполняется как обычно** — кэш
экономит только фазу разбора, поэтому ни один нативный вызов не нужно делать ленивым (в отличие от
снапшота, который сериализует уже выполненное состояние).

Почему это безопасно для ~94/98 констант `*_SHIM` (`install_v8!` в `install_dom`, каждая — чистая
конкатенация без параметра страницы) и **не тронуло** `WEB_API_SHIM`: `WEB_API_SHIM` идёт не как
`v8::Script`, а как **строковый аргумент косвенного `eval()`** (BUG-378-комментарий на месте
вызова, `v8_runtime.rs` рядом с `install_dom`) — это даёт top-level `var`/`function`-биндингам
`configurable: true`, без чего `internal_globals::seal_internal_globals_v8` не может дать им
`enumerable: false` (см. `internal_globals.rs` docs — не-configurable уже допускается для module-
шимов, но там это осознанно принятая более слабая защита, а для `WEB_API_SHIM` это ухудшение
статус-кво). Перевод `WEB_API_SHIM` на `v8::Script`+код-кэш дал бы тот же 247-имённый
`for (k in window)`-протечку, что BUG-378 закрыл. Переписать `WEB_API_SHIM` так, чтобы он сам
явно объявлял свои top-level имена через `Object.defineProperty(..., {configurable: false,
enumerable: false})` вместо голых `var`/`function` — это и есть BUG-753, отдельная, более крупная
задача; код-кэш для `WEB_API_SHIM` имеет смысл заводить заново уже поверх неё.

### Порог `CODE_CACHE_MIN_LEN`

512 байт, подобран измерением всех 98 констант `*_SHIM` в `crates/js/src/*.rs`: ловит 96 из 98,
608 из 710 КБ их суммарного размера при пороге 4 КБ (изначальная прикидка) — понижен до 512,
теряя всего 637 байт (2 шима: `BATTERY_SHIM` 188 Б, `GPC_SHIM` 449 Б). Пороговое значение — не
магическое: любой одноразовый динамический скрипт (`_lumen_focus_update(3)` ~23 Б,
deterministic-seed/UA/timezone-override) на порядки меньше 512 байт, так что кэш не разбавляется
ими. `CODE_CACHE_MAX_ENTRIES` (512 записей) — защитный потолок на случай, если какой-то будущий
`eval()`-вызов начнёт гонять большой не повторяющийся текст; сегодня такого нет.

### Измерение (`docs/perf-method.md`: min из 3×3 прогонов, A/B на той же машине в тот же день)

Census-тест `perf9_census_install_dom_cost` (`cargo test -p lumen-js --features v8-backend
perf9_census_install_dom_cost -- --nocapture`), стационарные раунды (2-й/3-й — 1-й греет
процесс-локальный кэш):

| | до (стэш без кода) | после | дельта |
|---|---|---|---|
| `install_dom`, min стационара | 59.0 мс | 39.9 мс | **-32 %** |
| `install_dom`, типичный разброс | 59–67 мс | 40–50 мс | — |

Совпадает с прогнозом §2.4/§6: батч модульных шимов — 53.6 из 85.8 мс (63 %) полной цены
`install_dom`; код-кэш забирает почти весь этот кусок (не полностью — hash+lookup+bind не
бесплатны, и 2 шима вне порога), `WEB_API_SHIM` (732 991 Б, 30.3 мс, 35 %) остаётся нетронутым —
отсюда наблюдаемые ~62% сокращение JS-доли, а не полные 63%. Первая навигация процесса (round 1,
промах) не замедлилась — 82–92 мс что до, что после, в пределах шума.

### Тесты

`perf9_code_cache_hit_preserves_semantics` (три `eval()` одного и того же скрипта ≥512 байт в
разных изолятах — идентичный результат; попадание не портит и не дублирует запись под тем же
ключом — сверяется по байтам, не по `len()` карты: `CODE_CACHE` общий на процесс, и `len()` гуляет
от параллельных тестов), `perf9_code_cache_skips_small_scripts` (короткий скрипт никогда не
попадает в кэш). `cargo test -p lumen-js --features v8-backend` — 2898/2898, 3 прогона подряд без
флейка.

### Что осталось

`WEB_API_SHIM` (35 % JS-доли, 30.3 мс) — за BUG-753 (переписать без голых top-level
`var`/`function`), отдельная задача не заводится, чтобы не дублировать её. Полный V8-снапшот
(§1–§6 этого файла) остаётся нереализованным путём — если он понадобится, придётся отдельно
решать проблему 19 top-level нативов (§6 «Препятствие»), код-кэш её не решает и не пытался.
