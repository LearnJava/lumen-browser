# WEBCRYPTO-SYM — срезы

Сейчас `crates/js/src/subtle_crypto.rs` (2637 строк) поддерживает AES только с ключом 16/32 байта, три режима AES разнесены по вариантам `KeyMaterial::AesGcm/AesCbc/AesCtr(Vec<u8>)`, хеши — SHA-1/256/384/512 только в `digest` (`web_crypto_natives.rs:34`); в HMAC/PBKDF2/HKDF/RSA стоят ручные `match` на три хеша с молчаливым откатом на SHA-256 (`hmac_hash` `:1793`, `pbkdf2_derive` `:1824`, `hkdf_derive` `:1866`, `rsa_sign` `:1243`), так что SHA-1 там сейчас считается как SHA-256. `wrapKey`/`unwrapKey` — заглушки `NotSupportedError` (`crypto_shim.js:311-317`). Конвенция natives: пустой `Vec<u8>` = ошибка (шим превращает в `OperationError`, `crypto_shim.js:212`).

Цифры потолка — `docs/wpt-vendor-notes/WebCryptoAPI.md` (кластер C2) и число ожидаемых FAIL в `tests/wpt/metadata/WebCryptoAPI/**.ini`: `wrapKey_unwrapKey` 205, `digest/sha3` 48, `digest/digest` 48, `digest/cshake` 88, `encrypt_decrypt/aes_ocb` 276, `chacha20_poly1305` 28, `generateKey/successes_AES-KW` 72, `successes_AES-OCB` 288, `successes_chacha20_poly1305` 192, `successes_kmac` 144, `sign_verify/kmac` 102, `import_export/KMAC_importKey` 144, `AES-OCB_importKey` 72, `Argon2_importKey` 45, `ChaCha20-Poly1305_importKey` 24, `argon2.tentative` 2. Часть FAIL ещё держат BUG-1734 (форма `CryptoKey`), BUG-1736 (нормализация, usages, порядок ошибок) и BUG-1739 (`tagLength` GCM и др.), поэтому критерии — «нет `NotSupportedError` + unit-тесты на векторах + PASS векторных тестов», а не точное число PASS; исполнитель записывает в коммит фактические «было/стало» по каждому префиксу.

**Решения, принятые планировщиком.** (1) Все новые RustCrypto-крейты берутся из поколения `digest 0.10`/`aead 0.5`/`cipher 0.4` — того же, что у уже подключённых `sha2 0.10`, `hmac 0.12`, `rsa 0.9`, `aes 0.8`, `aes-gcm 0.10`: `sha3 = "0.10"` (0.10.8 содержит SHA-3, cSHAKE и TurboSHAKE, feature `oid` нужна для RSA PKCS#1), `aes-kw = "0.2"`, `chacha20poly1305 = "0.10"`, `ocb3 = "0.1"`, `argon2 = "0.5"`. Версии 0.11/0.12 (`sha3 0.12`, `chacha20poly1305 0.11`, `argon2 0.6`) тянут `digest 0.11`/`aead 0.6`, их трейты несовместимы с остальным стеком — не использовать. Каждая зависимость — комментарий в `crates/js/Cargo.toml` рядом с `aes-gcm` (`:81-93`) и `**Why this dependency:** Permanent (crypto exception #3), RustCrypto-семья того же поколения, граф зависимостей общий с aes-gcm/sha2; нет альтернативы в дереве` в тело коммита (ADR-027). (2) Для AES-OCB в этой задаче поддерживается только nonce длиной 15 байт (в `encrypt_decrypt/aes_ocb_vectors.js` nonce 120 бит, плохие длины 0 и 16 → `OperationError`); `ocb3` параметризуется типами `NonceSize`/`TagSize`, 3 размера ключа x 3 размера тега раскрываются одним макросом, nonce 12-14 байт остаются `OperationError` (остаток отметить в `CAPABILITIES.md`, отдельной строкой не заводить). (3) Новые natives, где пустой результат — законный (расшифровка пустого сообщения ChaCha/OCB), возвращают `Vec<u8>` с первым байтом-статусом (`0` = успех, дальше данные; `1` = сбой), шим снимает байт; существующие natives не трогать (пустой plaintext у GCM/CBC/CTR — отдельный дефект BUG-1739). (4) Каждый срез, меняющий `crypto_shim.js`, читает актуальный контракт шима: BUG-1736/1734/1739 переписывают нормализацию алгоритма параллельно (`git log --oneline -n 10 -- crates/js/src/shim/crypto_shim.js`); если имя уже каноническое, `hash` строка — использовать, иначе сравнивать имя через `to_ascii_uppercase()`, как сейчас. (5) SHA-3 в ECDSA: если к S3 влит WEBCRYPTO-CURVES-S2, заменить в его `ecdsa_prehash` (grep по имени) четырёхветочный `match` на `HashAlg::digest`; если нет — ECDSA не трогать (в WPT SHA-3 встречается только в `digest/sha3`).

Unit-тесты — в `subtle_crypto::tests` и в новых модулях под `#[cfg(test)]`; запуск `cargo test -p lumen-js --lib subtle_` (собирается без V8). WPT-команда: `python tests/wpt/run_corpus.py --prefixes <префиксы> --processes 4` на `dev-release` с `--features v8-backend` (`docs/commands.md`, `docs/wpt/pass-rate.md`).

## WEBCRYPTO-SYM-S1: AES-192 и ключи AES-KW
- **Точка входа:** `crates/js/src/subtle_crypto.rs`: `generate_key` `:239` (ветки `"AES-GCM"` `:307`, `"AES-CBC"` `:322`, `"AES-CTR"` `:338`, проверка `byte_len != 16 && != 32`), `import_key` `:445` (ветки `:608`, `:634`, `:660`, проверка `raw.len() != 16 && != 32`), `export_key` `:982` (`:1004-1020`, JWK `alg` выбирается `if raw.len()==16`), `aes_gcm_encrypt/decrypt` `:1443`/`:1485`, `aes_cbc_*` `:1527`/`:1560`, `aes_ctr_crypt` `:1598`; `web_crypto_natives.rs:25`.
- **Сделать:** (a) 192-битные ключи: допустить 24 байта в трёх `generate_key`, трёх `import_key`; в `export_key` выбирать JWK `alg` по длине (`A192GCM`, `A192CBC`, `A192CTR`); в шифрах добавить ветку `aes::Aes192` (GCM: `aes_gcm::AesGcm<aes::Aes192, aes_gcm::aead::consts::U12>`; CBC/CTR — `cbc::Encryptor::<aes::Aes192>`, `ctr::Ctr128BE::<aes::Aes192>`); `match raw.len()` вместо `if == 16 else`. (c) Функции `aes_kw_wrap(key_id, data) -> Vec<u8>` и `aes_kw_unwrap(key_id, data) -> Vec<u8>` (RFC 3394, `KekAes128/192/256`; длина данных кратна 8 и ≥ 16 для wrap, кратна 8 и ≥ 24 для unwrap, иначе пустой результат = `OperationError`; ошибка целостности unwrap — тоже пустой) и natives `_lumen_subtle_aes_kw_wrap/_unwrap` в `web_crypto_natives.rs`.
