# Очередь SPLIT — разрезание монолитных файлов (P1)

**Developer:** P1 (батчи `crates/shell` может брать P2 — код механический)
**Крейты:** `lumen-shell`, `lumen-layout`, `lumen-paint`, `lumen-network`, `lumen-css-parser`, `lumen-dom`, `lumen-js` (добавлен 2026-08-26, см. пересчёт в §1)
**Родитель:** `SPLIT` в [`ROADMAP.md`](../../ROADMAP.md)
**Ветки:** `p1-split-<id>` (например `p1-split-sh1`)
**Заведена:** 2026-08-23, по итогам аудита здоровья кода
**Назначена P1:** 2026-08-26 — все 19 оставшихся батчей заведены строками в
`ROADMAP.md` (id `SPLIT-SH2`…`SPLIT-DM1`) и указателями в `STATUS-P1.md`; порядок
там сверху вниз и есть порядок работы. Группа SH идёт с хвоста файла к голове,
чтобы вырезка не сдвигала анкеры ещё не взятых батчей.

Один батч = одна строка в `STATUS-P1.md` = одна сессия. Каждый батч — чисто
механический перенос кода между модулями: ноль изменений поведения, ноль правок
сигнатур. Это НЕ рефакторинг API — публичная поверхность каждого крейта не меняется.

## 1. Контекст

Аудит 2026-08-23: workspace ≈ 545 тыс. строк, при этом 15 файлов >2000 строк,
шесть из них >19 000. Монолиты тормозят ревью, мержи и работу агентных сессий
(контекст не помещается). Цель дорожки: **ни одного файла >8000 строк**; гиганты
свести к набору файлов ≤2000 строк. Поведенческие фиксы и новые фичи в эти файлы
в этот период НЕ заводить — иначе разрез гонится за движущейся целью.

### Перепись на 2026-08-23 (метод воспроизводим)

Крупнейшие непрерывные регионы файла (границы по top-level item'ам):

```bash
python scripts/split_census.py <file>                  # карта top-level item'ов
python scripts/split_census.py <file> --inner LO HI    # карта тем внутри модуля
```

Скрипт заведён ST-0 (2026-08-27) и **заменяет однострочник `rg "^pub struct |…"`,
которым эта перепись пользовалась раньше** — тот врёт в трёх местах, и каждое
стоило дорожке отдельной осечки. Он не отличает код от строкового литерала (в
`crates/js/src/dom.rs` 45 531 строка почти целиком лежит внутри `const
WEB_API_SHIM: &str = r#"…"#`, и JS внутри начинается теми же словами); он не знает
границ item'а, а без них нельзя измерить регион — числа переписи 2026-08-23
поэтому и промахивались на 600–1 000 строк; и он не поднимает начало item'а над
его атрибутами и `///`, из-за чего вырезка по такому числу отрывает
доккомментарий от функции (осечка SH-4b, повторённая на SH-5 и трижды на SH-6).
Скрипт считает глубину скобок вне строк, raw-строк, символьных литералов и
вложенных `/* */`, проверяет себя итоговой глубиной (обязана быть 0) и печатает
счётчик item'ов без `///` над ними — машинный признак отклеившегося
доккомментария из SH-3c. Проверен на четырёх монолитах очереди (`style.rs`,
`box_tree.rs`, `js/dom.rs`, `paint/renderer.rs`): глубина сходится на всех.

## 2. Железные правила каждого батча

1. **Только перенос.** Запрещено менять поведение, сигнатуры `pub`/`pub(crate)`
   функций, имена типов и полей. Меняются только пути модулей; для внешних
   потребителей крейта — `pub use` реэкспорт со старого пути.
2. **Тесты едут вместе с кодом.** Счётчик `#[test]` крейта до и после батча —
   в теле коммита. Тест-модуль разрешено перенести в файл рядом с кодом либо в
   `tests/<name>.rs`; удалять тесты запрещено.
3. **serde/bincode (ADR-008 hibernation-snapshots):** структуры с
   `derive(Serialize, Deserialize)` переносить целиком, поля и атрибуты serde не
   трогать. Переименование типа = запрет даже внутри крейта (snapshot-совместимость
   и grep-аемость истории).
4. **#[allow]-реестр.** Файловый `#![allow(missing_docs)]` при дроблении НЕ
   копировать в новые файлы автоматически: если долг реально остаётся за
   переносимым кодом — оставить allow в новом файле И обновить счётчик в
   `docs/lint-policy.md §10` тем же коммитом. Точечные `#[allow]` переносятся
   вместе с кодом как есть.
5. **Пиксели не двигаются,** но snapshot/CPU-тесты (`graphic_tests/run.py`,
   snapshot-наборы layout/paint) прогнать перед мержем — страховка от случайной
   семантической правки при вырезке.
6. **Размер батча:** один регион одного файла за сессию. Если регион >4000
   перемещённых строк — резать на подбатчи по внутренним секциям, а не тащить
   одним коммитом.
7. Правило CLAUDE.md сохраняется: clippy `-D warnings` чист по каждому крейту
   каждой ветки перед мержем.

## 3. Процедура батча (шаблон)

```bash
export PATH="/c/Users/konstantin/.cargo/bin:$PATH"
git worktree add .claude/worktrees/split-<id> -b p1-split-<id>
cd .claude/worktrees/split-<id>
```

1. Замер ДО: `(Get-Content <file> | Measure-Object -Line).Lines`,
   `rg -c "#\[test\]" <файлы>` — записать в черновик коммита.
2. Создать целевой модуль (`src/<name>.rs` или каталог с `mod.rs`), добавить
   `mod <name>;` туда, где жил код.
3. Вырезать регион по анкерам из таблицы ниже (границы — top-level item'ы),
   вставить как есть; поправить `use`-блоки обоих файлов. Внутрикрейтовые
   вызыватели переводить на новый путь напрямую; `pub use` со старого пути —
   только если путь используется другим крейтом.
4. Прогнать: `cargo check -p <crate>` → `cargo test -p <crate>` →
   `cargo clippy -p <crate> --all-targets -- -D warnings`. Для paint/layout —
   плюс snapshot-прогон (правило §2.5).
5. Коммит: `P1/SPLIT-<id>: <что перенесено> (<N> строк, тестов было X — стало X)`.
   Merge `--no-ff` в main, удалить указатель батча из `STATUS-P1.md`, отметить
   DONE в таблице этого файла тем же коммитом.

### Группа SH — `crates/shell/src/main.rs` (10 334 строки после SH-3d)

Приоритет сверху вниз: сначала самодостаточные регионы, ядро (`impl Lumen`) — последним.

**Анкеры в этой таблице дрейфуют — пересчитывать в начале батча, не верить числу.**
Числа переписи 2026-08-23 были сняты с ещё более старого снимка (файл на дату аудита
уже был 32 088 строк, а не 29 823), из-за чего каждый анкер группы промахивался на
~600–1 000 строк. Пересчёт — одной командой:
`rg -n "^(pub )?(struct|enum|impl|fn|mod|trait|const|static|type) " crates/shell/src/main.rs`.

Вторая ловушка переписи: регион в ней **назван по первому item'у**, а не по содержимому.

только потому, что регион открывался `struct ViewTransitionState`; на деле три типа занимали
29 строк, а остальные 3 845 были одним блоком `impl Lumen` с релейаутом, chrome и загрузкой
страницы. Всё, что относится к view transitions, — 25 упоминаний, разбросанных по циклу
событий, отдельным файлом стать не может. Перед батчем читать карту методов региона, а не
его первую строку.

**ST-8 (`apply_declaration`, 3 045 строк) — почему он не решается чистым
переносом и что с ним делать.** Это одна функция: преамбула на 70 строк
(пропуск `--*`, подстановка `var()`) и один `match prop` (14940…17911) из **343
веток** с `_ => {}` в конце. Потолок нового файла — 2 000 строк (`CAP` в
`scripts/check_file_sizes.py`, правило №1: «новый монолит завести нельзя
вообще»), и он жёсткий, в отличие от храповика для уже существующих файлов.
Значит функция целиком в новый файл не помещается, а поделить её — это правка
кода, которую §2.1 у батча отбирает.

Прецедент, разрешающий такой батч, на дорожке уже есть: SH-2 превратил методы
трейта в однострочные переходники, потому что это была «единственная форма, в
которой регион вообще помещается в правило размера файла». Здесь измерены три
вещи, которые делают аналогичный приём механическим, и одна, которая делает его
опасным.

* Ветки переносятся **побайтово**: внутри `match` нет ни одного `return`
  (проверено), а три вхождения `?` — все в комментариях. Форма помощника,
  сохраняющая тела веток байт в байт, такая: `fn apply_decl_<тема>(…) -> bool {
  match prop { <ветки как есть>, _ => return false, } true }`, а
  `apply_declaration` после преамбулы выстраивает их цепочкой
  `if apply_decl_layout(…) { return; }`. Новыми в файле оказываются только
  заголовок функции, строка `_ => return false,` и завершающее `true` — тела
  веток не редактируются вовсе. Приём проходит по типам, потому что каждая ветка
  вычисляется в `()`.
* Ветки можно **перегруппировать по смыслу**, а не резать подряд: все 351 метка
  (343 ветки, часть многометочных) уникальны, дублей нет, так что порядок веток
  в `match` по строковым литералам семантики не несёт.
* **И ровно это последнее — ловушка батча.** Компилятор поймает дубль метки
  (недостижимый паттерн), но НЕ поймает потерянную ветку: она молча проваливается
  в `_ => {}`, то есть свойство перестаёт применяться, и ни один тип, ни один
  тест сборки этого не заметит. Поэтому механическая проверка батча — не сверка
  тел (её тоже делать), а **сверка мультимножества меток до и после: 351 метка,
  тот же состав**. Скрипт на пять строк, и без него батч брать нельзя.
* Швы измерены по именам веток, шесть отрезков почти равного веса:
  14941…15430 (490) `display`…`max-block-size` — раскладка, flex, grid, размеры;
  15431…15935 (505) `font-style`…`offset-anchor` — шрифт, текст, тени, обводка,
  счётчики, трансформы, фильтры; 15936…16425 (490) `row-gap`…`place-self` —
  колонки, разрывы страниц, выравнивание; 16426…16966 (541)
  `will-change`…`container` — фон-слои, позиционирование, inset, contain,
  контейнеры; 16967…17537 (571) `writing-mode`…`mask-*` — режим письма, скролл,
  переносы, transitions/animations/таймлайны, маски; 17538…17909 (372)
  `line-height`…`box-sizing` — SVG-краска, отступы, text-decoration, границы.
  Собираются в четыре файла `style/apply/{layout,text,paint,motion}.rs` плюс
  `mod.rs` с преамбулой и цепочкой вызовов; конкретная развесовка — за батчем,
  потолок 2 000 строк выдерживают любые две соседние пары.

**Запасной вариант, если приём выше сочтут выходом за устав батча:**
`apply_declaration` остаётся в самом `style.rs`. Цель дорожки («ни одного файла
>8000 строк», §1) при этом достигается — после ST-1…ST-18 в файле останутся
`use`-блок, преамбула, эта функция и реэкспорты, ≈ 3 200 строк, а `style.rs`
числится в базовой линии, где действует храповик, а не потолок. Цена: критерий
§5 «целевой файл ≤2000 строк» на этом батче не выполняется, и `style.rs`
остаётся крупнейшим файлом крейта.

**Постановка строки ROADMAP частично отвечена самим замером.** Она предупреждает
«`WEB_API_SHIM` — строковый литерал, резать по границам шимов (`WEB_API_SHIM_MID`
и соседи), а не по строкам Rust». Границы шимов резать не нужно: **шимы уже
разрезаны** — это 14 отдельных `const`, и `web_api_shim()` склеивает 13 из них
`format!`-строкой **ровно в порядке следования по файлу** (проверено: порядок
конкатенации совпадает с порядком объявлений посимвольно). Доккомментарий самой
`web_api_shim` объясняет, почему разрез безопасен: куски идут в исходном порядке,
поэтому V8 компилирует одну программу с одной областью подъёма, и разрез невидим
коду шима. Настоящий вопрос батча другой — **где вообще лежит этот JS**.

**Ответ: в `.js`-файлах через `include_str!`.** Три измерения делают это
дешёвым и проверяемым, а одно — опасным.

* Приём в workspace **прецедентен**: `include_str!` уже держит четыре ресурса,
  включая целый HTML-документ (`shell/src/chrome_preview.rs`).
* Гейт размера читает **только `.rs`** (`git ls-files "*.rs"` в
  `scripts/check_file_sizes.py`), так что 19 968 строк уходят из учёта целиком,
  а не переезжают в другой `.rs`.
* Публичная поверхность **не меняется вовсе**: `const` остаётся на месте и с тем
  же именем, меняется только правая часть (`= "` … `"` → `= include_str!(…)`).
  `worker.rs`/`sw_worker.rs`, читающие `EVENT_TARGET_SHIM`/`PERFORMANCE_SHIM`/
  `MESSAGE_CHANNEL_SHIM`, не правятся.
* **Опасное:** все 14 констант объявлены обычной строкой `"`, а не raw-строкой
  (`r#"`), то есть текст JS в файле **экранирован**, и перенос в `.js` — это
  снятие экранирования, а не побайтовая вырезка. Объём экранирования измерен и
  мал: на 19 968 строк приходится **81 строка** с обратной косой (80 `\"`,
  147 `\\`, 28 `\n`), продолжений строки нет ни одного. Ошибка здесь молчалива —
  `\\d` в регулярном выражении, ставшее `\d`, меняет семантику JS и не роняет
  сборку. Поэтому **механическая проверка батча обязательна и она полная**:
  сверить байты `web_api_shim()` и `worker_exposed_shim()` до и после (тест на
  пять строк, печатающий длину и SHA обеих строк). Это ровно тот же приём, что
  «сверка мультимножества меток» в ST-8: замена читаемости кода машинным
  тождеством.

**Правила группы JS — те же, что у ST (библиотечный крейт), кроме третьего.**
`lib.rs` объявляет `pub mod dom;` и `pub mod v8_runtime;`, так что реэкспорт
обязан быть `pub use`, а `SYMBOLS.md` двинется на каждом батче. Но `pub`-item'ов
здесь мало (7 в `dom.rs`, 8 в `v8_runtime.rs`), а снаружи крейта по полному пути
берут **шесть имён и все из `v8_runtime`** (`V8JsRuntime`, `ensure_v8_platform`,
`set_global_{user_agent,timezone}_override`, `{user_agent,timezone}_override_script`,

уходят наружу реэкспортом `lumen_js::NavigateRequest` из `lib.rs`. Третье правило
ST (**`#![allow(missing_docs)]` едет с кодом**) здесь **не применяется**: allow
стоит на уровне крейта (`lib.rs:4`), новые файлы наследуют его сами, править §10
lint-policy не нужно. Пиксельный гейт (§2.5) группе не нужен — `crates/js` не

**JS-6 (`install_dom`, 3 925 строк) — почему он не решается чистым переносом.**
Это **одна функция**: `pub fn install_dom(…)` с одиннадцатью параметрами,
преамбулой и телом внутри замыкания `self.run(move |inner| { … })`. Внутри
замыкания создаются `scope`/`ctx`/`store`, затем объявляется **локальный
`macro_rules! reg!`** (16 ветвей, арности 0–7 в двух формах возврата), и дальше
идут **42 секции-баннера** с **231** площадкой вызова `reg!`.

Измерено три вещи, и первая из них закрывает самый привлекательный вариант.

* **Макрос нельзя вынести на уровень модуля «как есть».** `reg!` ссылается на
  `scope`, `ctx`, `store` как на *свободные* идентификаторы, и работает это
  только потому, что объявлен он внутри той же функции. Очевидный обход —
  модульный макрос, ПОРОЖДАЮЩИЙ локальный `reg!` (с передачей доллара через
  `$d:tt`, единственная форма вложенного `macro_rules!` на stable), — **проверен
  компилятором и не собирается**: `error[E0425]: cannot find value 'scope' in
  this scope` … `an identifier with the same name exists, but is not accessible
  due to macro hygiene`. Гигиена `macro_rules!` привязывает такой идентификатор
  к контексту определения макроса, а не вызова. Не тратить на это время повторно.
* **Работающая форма — контекст параметрами макроса** (проверена компиляцией на
  той же пробе): `macro_rules! reg { ($s:expr, $c:expr, $st:expr, $name:expr, …) }`
  на уровне модуля, и площадка вызова получает приставку `scope, ctx, store,`.
  Правка механическая, greppable и считаемая (231 площадка), а **тела веток не
  редактируются вовсе** — это тот же класс, что превращение методов трейта в
  переходники (SH-2) и вынос веток `match` в помощники (ST-8). Сигнатура
  помощника известна заранее и совпадает с тем, что уже принимает
  `register_v8_native` (`v8_compat.rs:980`): `scope: &mut v8::PinScope<'_, '_>`,
  `ctx: v8::Local<'_, v8::Context>`, `store: &mut Vec<OwnedNativeFn>`.
* **Секции самодостаточны.** Для каждой из 42 секций посчитано, сколько имён
  преамбулы (48 `let`-привязок) она читает: **41 секция читает не больше шести**

**`render_impl` — риск группы, крупнее любого индивидуального item'а всей
дорожки SPLIT** (JS-6's `install_dom` — 3 925 строк, BT-10's `lay_out_inner` —

состоит из последовательных стадий с общим локальным состоянием — но превращение
каждой стадии в отдельный метод (параметризация захваченными `let`-привязками,
приём JS-6/SH-2) здесь рискованнее: JS-6 такой трансформацией не касался
заимствований (`macro_rules!` не подчиняется borrow checker), а шесть
`&mut self`-хелперов, вызванных подряд из одного `&mut self`-метода, ГОРАЗДО
вероятнее столкнутся с конфликтом заимствований на общих полях `Renderer`
(текстуры/буферы, которые несколько фаз держат разом). Это отдельное,
самостоятельное расследование, не входящее в объём переписи. **Запасной
вариант — тот же, что JS-7 принял для `install_dom` в `v8_runtime.rs`:**
функция остаётся в базовом файле как есть; после переноса остальных тем

render-точек входа) ≈ 5 600…6 000 строк — цель §1 «ни одного файла >8000 строк»
достигается, критерий §5 «≤2000 на новый файл» — нет (тот же компромисс, что
принят для `v8_runtime.rs`).
