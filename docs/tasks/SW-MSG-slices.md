# SW-MSG — срезы
Сейчас воркер сервис-воркера — отдельный поток с изолятом V8 (`crates/js/src/sw_worker.rs`, `run_sw_thread_v8` `:548`) и циклом `rx.recv()` без задач: `setTimeout` — синхронная заглушка (`:434`), события `install`/`activate`/`fetch`/`push` — литералы-объекты без `ExtendableEvent`, `waitUntil` — пустая функция, `clients` — заглушки (`:93`), `registration.active` — фиктивный объект. Страничная сторона: `ServiceWorker.postMessage` — no-op (`web_api_shim_mid_b.js:475`), `navigator.serviceWorker.onmessage` — просто поле (`:691`), хэндл воркера лежит в `SwWorkerStore` по ключу `(origin, scope)` и создаётся в `_lumen_sw_activate_script` (`v8_runtime/install/net.rs:145`) после фиктивной активации. Готовые кирпичи, на которые опираются срезы: конверт `{__lumen_msg__, data, ports}` и `MessagePort` через границу потоков (`worker_shims.rs:723`, `worker.rs:1305`, `message_channel_shim.js`), `WORKER_TIMERS_SHIM` + `run_worker_tasks` (`worker.rs:1143`), шаблон теста «сообщение, затем fetch читает результат» (`sw_worker.rs:1302`) и интеграционный шаблон страница + хранилище (`dom/tests/v8_events_cache.rs:1500`, `runtime_on_shared_cache`).

Решения, принятые в брифе (исполнитель их не пересматривает). (1) Данные сообщений едут JSON-строкой, как у `Worker` (структурное клонирование через `structuredClone`+`JSON.stringify`, тот же компромисс, что в `Worker.prototype.postMessage`). (2) Канал воркер → страница и реестр клиентов — процесс-глобальный `static HUB: OnceLock<SwHub>` в новом `crates/js/src/sw_clients.rs`, а не поле `SwWorkerStore`: так не меняется ни `lumen-core` (кроме нового варианта сообщения), ни `lumen-shell`; оболочка уже вызывает `pump_workers` на каждом тике, доставку подключаем внутрь него. Хаб ключуется `client_id` (число из `AtomicU64`, поле `sw_client_id` у `V8JsRuntime` рядом с `sw_worker_store`, `runtime.rs:369`); тесты берут уникальные origin. (3) Клиенты-iframe (`iframe.contentWindow.navigator.serviceWorker`) не входят: это BUG-1743, а `Client.navigate`/`clients.openWindow` требуют навигации оболочки — вне срезов. (4) Тесты WPT, которые шлют сообщение в `registration.installing`, заработают только после BUG-1742 (изолят должен существовать в состоянии installing); срезы его не ждут и проверяются Rust-тестами на активном воркере.

Цифры: кластер B разведки — 79 id, 24/498 сабтестов, потолок 74.6 балла (22.5 п.п. `service-workers`), `docs/wpt-vendor-notes/service-workers.md`. Прирост WPT появится только вместе с BUG-1742 и BUG-1743 (тесты строят окружение в iframe и ждут install в изоляте); поэтому критерии срезов — Rust-тесты, а прогон `run_corpus.py --prefixes service-workers/service-worker --processes 6` выполняется один раз после S6 информационно (записать числа в отчёт, без порога).
