# Дорожка WPT-RUN — пропускная способность WPT-раннера

Бриф для ROADMAP.md-задач `WPT-RUN` / `WPT-RUN-1`…`WPT-RUN-3` (Фаза 3).
Владелец тулинга — **P2**; движковые баги по находкам уходят **P3/P1** по обычной
методологии группировки.

**Приоритет:** решением пользователя 2026-07-30 три указателя `WPT-RUN` подняты в
**начало** `STATUS-P2.md`, выше 184 строк `WPT-VENDOR`. Это сделано намеренно, а не
случайно: вендоринг категории №104 даёт меньше, чем довендоренный хелпер, после
которого начинают отчитываться тысячи layout-тестов. Не «исправлять» этот порядок
обратно.

Параллельная и независимая дорожка — `DEVX-7…16`,
[`p1-introspection-track.md`](p1-introspection-track.md). Общих файлов нет
(здесь Python в `tests/wpt/`, там Rust в `layout`/`paint`/`driver`), поэтому
дорожки идут одновременно.

---

## Зачем

Задача дорожки — превратить **уже вендоренный** корпус в измеряемый. Не вендорить
новое (это `WPT-VENDOR`), не писать новые тесты (это `TEST`), а снять три
ограничения исполнителя, из-за которых крупнейшая категория корпуса не прогоняется.

Факты из [`docs/wpt-status.md`](../wpt-status.md), строка `css`:

- Категория `css/` вендорена целиком 2026-07-26: **54350 файлов, ~209 МБ**,
  манифест отбирает **34607 тестовых id** — рекорд корпуса (следующая по размеру,
  `content-security-policy`, даёт 865).
- `run_report.py --all --root css --recursive` **не завершился**. При наблюдаемом
  темпе полный последовательный прогон занял бы порядка **суток**, а не часов.
- Ограниченная проба (~11:30, остановлена вручную) обработала **382 из 34607 id
  (~1.1%)**, покрыв `CSS1`/`CSS2` box-model/floats/normal-flow и начало
  `compositing`. Из них: **267 SKIP** («Executor does not support testdriver.js»),
  **62 голых TIMEOUT**, **53 harness OK**, и по добежавшим —
  **1294 из 2594 сабтестов passed**.
- Замечены 404 на `/resources/check-layout-th.js` (**56 попаданий**) и
  `/fonts/ahem.css` (3).

Отсюда вывод, определяющий приоритет дорожки: **половина сабтестов базовой
блочной модели CSS1/CSS2 падает, и мы не знаем, сколько там багов** — потому что
измерено 1.1%. В `BUGS.md` при этом на `css-parser` числится 13 багов из 429, то
есть счёт багов отражает, где мы искали, а не где они есть.

### Почему это дешевле кросс-движкового сравнения

Отдельно рассматривался вариант «открыть страницу в Chromium и в Lumen и
сравнивать стадии конвейера». Он отклонён (см.
[`p1-introspection-track.md`](p1-introspection-track.md) §Отложено): даёт «две
реализации расходятся, кто прав — неизвестно», тогда как WPT содержит **ожидаемый
ответ из спеки**.

`check-layout-th.js` — это ровно тот механизм: хелпер самопроверяющихся
layout-тестов, выдающий «expected width = 342, actual = 318, node = `<div>`»
нативно, для тысяч тестов, без эталонного браузера. Мы на нём отдаём 404. Один
довендоренный JS-файл даёт то, ради чего предлагалось строить дифер с Chromium.

### Что уже есть и не надо изобретать

- `tests/wpt/run_report.py` + `run_suite.py` (гейт), плагин `tools/wptrunner`,
  вендоренный офлайн-снапшот (`tests/wpt/VENDOR.md`).
- **Система ожиданий**: `.ini`-файлы + группировка провалов в `BUG-NNN` по
  первопричине (методология описана в `docs/wpt-status.md`, поставлена в P2-wpt
  S5) + храповик `KNOWN_DEBTORS`. Поэтому «тысячи красных» после массового
  прогона — не проблема: они ратчетятся, а не разбираются по одному.
- Гочи вызова `run_report.py` (нужен `LUMEN_PROFILE=dev-release`, `REPO_ROOT`
  от `__file__`, гонка `MANIFEST.json`, расширение `.htm`) — уже известны, см.
  `docs/wpt-status.md` §«Как обновить» и README в `tests/wpt/`.

## WPT-RUN-3: шардирование и массовый прогон `css/` (M)

**Зависит от:** `WPT-RUN-1`, `WPT-RUN-2` — иначе прогон измеряет не движок, а
пробелы исполнителя.

**Состав:** параллельный/шардированный прогон (34607 id последовательно ≈ сутки),
затем массовый прогон `css/` с записью ожиданий в `.ini` по существующей
методологии и группировкой провалов в `BUG-NNN` по первопричине.

**DoD:**
- `css/` прогнана целиком, результат зафиксирован в `docs/wpt-status.md`
  (строка `css` + при необходимости отдельная детальная таблица, как у `dom/nodes`).
- Ожидания закоммичены, гейт зелёный при нулевых unexpected.
- Провалы сгруппированы в `BUG-NNN` по первопричине — **не по одному тесту на баг**.
- В журнале зафиксировано, сколько id не добежало и почему (правило «no silent
  caps»: молча урезанное покрытие читается как полное).

**Порядок относительно дорожки DEVX:** массовый прогон полезнее делать **после**
того, как доехал инвариантный слой (`DEVX-8a`), — тогда часть падений приезжает
уже локализованной (сработавший инвариант называет место), а не в виде
«expected 342, actual 318». Это не блокирующая зависимость: прогон возможен и без
инвариантов, ратчет ожиданий его удержит. Речь только о стоимости **разбора**,
и поскольку дорожки идут параллельно, соблюдение этого порядка ничего не стоит.

**Ловушка:** не ослаблять вендоренные тесты. Движковый пробел = `expected:FAIL` +
`BUG-NNN`, ровно как в P2-wpt.

**Срез 1 (2026-08-02) — сделан только шардинг/параллелизм, не массовый прогон.**
`run_report.py` получил `--processes` (проброс в `wptrunner`'s `--processes`),
`--offset`/`--limit` (резать `--all`-выборку на воспроизводимые куски между
сессиями — id отсортированы, так что фиксированная пара всегда даёт один и тот
же срез, пока корпус не меняется).

Почему `--processes` вообще масштабируется: `wptrunner` группирует тесты по
каталогу (`testloader.py::PathGroupedSource`) и ограничивает число процессов
числом групп (`process_count = max(1, min(requested, num_groups))`) — на одном
каталоге (`css/CSS2/floats`, 12 id) `--processes=4` реально поднял только 2
процесса, но на разнородном срезе `css/` (много каталогов) поднялись все 6
запрошенных. Корректность проверена на `css/CSS2/floats`: `--processes=1` и
`--processes=4` дали побитово одинаковый результат (3/3 harness OK, 54/68
сабтестов) — параллелизм не портит исход.

Замер пропускной способности: `--root css --recursive --offset 0 --limit 600`
(353 отобранных id, начало `CSS1`/`CSS2`) — `--processes=6` прогнал их за ~48с
(~7.7 id/с) против ~0.55 id/с прежней последовательной пробы — **~14× быстрее**.
Это пересматривает оценку «сутки» вниз до порядка **~75 минут** чистого времени
`wptrunner` на весь корпус 34607 id при сопоставимом темпе. Не гарантия — начало
`CSS1`/`CSS2` может быть легче среднего по корпусу (директории с `testdriver`/
`.https.` дороже, см. `reference_wpt_run_report_invocation_recipe` в памяти
Claude) — реальную цифру даст только сам массовый прогон. Даже при 75 минутах
он не помещается в один интерактивный вызов (лимит Bash-таймаута), поэтому
`--offset`/`--limit` остаются нужны для нарезки на куски по сессиям, даже когда
`--processes` уже даёт параллелизм внутри куска.

Не сделано этим срезом (задел на срез 2+): собственно массовый прогон всего
`css/`, запись `.ini`-ожиданий, группировка провалов в `BUG-NNN`, обновление
строки `css` в `docs/wpt-status.md` с итоговым покрытием.

**Срез 2 (2026-08-02) — массовый прогон + `.ini` + группировка на `css/CSS2`
(816 файловых id, одна поддиректория, не весь `css/`).**

Первая находка среза меняет саму оценку задачи: `--root css/CSS2 --recursive`
отбирает 805 id по файловой системе (`all_vendored_test_ids()` просто
глобит `.html`/`.htm`), но фактический манифест `wptrunner` признаёт
`testharness`-тестами только **63** — остальные 742 суть reftest/crashtest-пары
(историческая CSS WG практика: `CSS2` в основном визуальные reftest'ы, не
JS-ассерты), для которых у `browsers/lumen.py` нет исполнителя вовсе (`TEST-4`,
warning `Unsupported test type reftest for product lumen` в логе). Это не
недосчёт этого среза — это структурный состав категории; наивный
файлово-глобовый счётчик `all_vendored_test_ids()` систематически завышает
«сколько реально прогонится» для любой reftest-тяжёлой директории. Оценку
среза 1 «~75 минут на весь `css/`» на основе этого стоит читать как верхнюю
оценку темпа wptrunner per-testharness-id, не как оценку покрытия — реальный
прогоняемый объём `css/` меньше файлового счётчика на неизвестную (но,
вероятно, немаленькую) долю.

Из 63 `testharness`-тестов: 53 harness OK, 10 TIMEOUT, 1206/2454 сабтестов
passed. Полная поимённая триаж (не оценка по частоте строк в логе, как в пробе
WPT-RUN-1, а чтение каждого непройденного файла и, где нужно, соответствующего
куска `dom.rs`/хелпера) дала 8 новых кластеров (BUG-463…470) и объяснила ещё 13
файлов уже открытыми находками (BUG-360 мёртвый `onload=`, BUG-384 named
access on Window) — детали и полный список файлов на баг см.
[`docs/wpt-status.md`](../wpt-status.md) → строка `css`, там же 5 файлов,
намеренно оставленных некластеризованными (единичные наблюдения, не решился
формулировать первопричину по одному данному).

`.ini` для всех 58 классифицированных файлов лежат под
`tests/wpt/metadata/css/CSS2/` (структура зеркалит id теста), с шапкой-ссылкой
на `BUG-NNN`; повторный прогон подтверждает 0 unexpected на них (5
некластеризованных остаются красными намеренно — не подтянуты в `.ini` без
приписанной первопричины).

Технический гоча: subtest-имена вида `... at (0) should be [initial]`
(WAAPI-интерполяционные тесты) содержат буквальные `[`/`]` — секция `.ini`
`[name]` парсится `tools/wptrunner/wptrunner/wptmanifest`, и незаэкранированный
`]` внутри имени рвёт парсер (`ParseError: Junk before EOL`). Экранировать
только `]` (и сам `\`) через `\]` — `[` внутри имени экранировать не нужно
(сериализатор апстрима, `wptmanifest/serializer.py::escape(name, extras="]")`,
делает ровно так же).

Не сделано этим срезом (задел на срез 3): та же процедура (массовый прогон +
триаж + `.ini` + `BUG-NNN`) на оставшихся ~34500 id `css/` за пределами
`CSS2` — `CSS1` (пусто в текущем вендоре), все `css-*`-модули, `cssom`,
`compositing`, и т.д.

## WPT-RUN-4: честная сводная цифра pass-rate по всему корпусу (M)

**Отличие от `WPT-RUN-3`.** `WPT-RUN-3` прогоняет и **триажит** категории по
одной, наращивая `.ini` и заводя `BUG-NNN` — это работа по улучшению движка.
`WPT-RUN-4` отвечает на другой вопрос: **какова цифра целиком**, за один
прогон, в форме, сопоставимой с wpt.fyi/Servo/Ladybird. Первый проход —
измерение, не гейт: `.ini` эта задача не пишет вовсе.

Повод — вопрос «как попасть на wpt.fyi»: туда загружают не HTML-отчёты, а
`wptreport.json` по всему корпусу, и первым делом нужна собственная честная
цифра.

**Решения пользователя (2026-08-18), не пересматривать по ходу:**

1. Сначала testharness-цифра (этапы «знаменатель → оркестратор → прогон»),
   reftest-исполнитель (`TEST-4`/`TEST-5`) — следующим шагом.
2. Знаменатель — **весь манифест без изъятий**: reftest-ы, которые мы не
   исполняем, и 🚫-категории остаются внутри; неисполненное = непройденное.
3. Первый прогон — пилот из 10 разнородных категорий, затем всё.
4. `.ini` не трогаем.
5. Трекинг — эта дорожка, ветка `p2-wpt-run-4`, слот `p2-work`.
6. Результат — `docs/wpt/runs/<дата>.json` + журнал `docs/wpt/pass-rate.md`.

**Почему знаменатель нельзя брать из файлов.** `run_report.py::all_vendored_test_ids()`
глобит `*.html`, и такой счёт ошибается в обе стороны сразу: завышает
(`foo-ref.html` — файл, но не исполняемый id) и занижает (`?variant`,
развёртка `.any.js`). Ни с чьим дашбордом такое число не сопоставимо.
Считает манифест `tests/wpt/corpus_stats.py`.

**Срез 1 (2026-08-18) — знаменатель.** 273 категории, 73495 id; из них 67735
автоматизируемых (знаменатель), 5760 `manual`/`visual` (их не исполняет ни
один раннер, включая апстримный — вынесены отдельной строкой), 37319
`testharness`. Отсюда главный факт задачи: **потолок сегодняшней цифры —
55.1%**, потому что зарегистрирован единственный исполнитель `testharness`;
в одной только `css/` 24552 reftest против 7447 testharness. Публиковать
цифру без этой оговорки нельзя — иначе она читается как приговор движку.

**Срез 2 (2026-08-18) — оркестратор.** `tests/wpt/run_corpus.py`: отбор из
манифеста, шард = единица работы и чекпойнта, `run_smoke.py` вызывается
подпроцессом на шард. Три вынужденных решения задокументированы в самом
файле: подпроцесс (зависший `wptrunner` внутри своего интерпретатора не
убить, а прогон обязан пережить один плохой шард), убийство по дереву
процессов (`Popen.kill()` снял бы только Python, осиротевший `lumen.exe`
держал бы BiDi-порт и ломал следующий шард; по имени образа не убиваем
никогда), обновление `MANIFEST.json` один раз за прогон (дефолт `wptrunner` —
пересканировать 72k файлов на каждом из ~480 шардов).

Скоринг повторяет форму wpt.fyi: тест с сабтестами — доля пройденных, без
сабтестов — 1 при `PASS`, **id без результата — 0**. Последнее и есть суть:
считаем по манифесту, а не по отчётам, поэтому неисполнимые reftest-ы и
потерянные шарды честно тянут цифру вниз. Методика — `docs/wpt/pass-rate.md`.

**Срез 3 (2026-08-18) — пилот и его находки.** Пилот отработал по назначению:
поймал три дефекта до ночного прогона.

- *Фиксированный таймаут шарда негоден.* 1200с убили `encoding` (1343 id) на
  середине и были десятикратно избыточны для `FileAPI` (125 id). Бюджет стал
  пропорциональным (`600с + 2с/id` при измеренных ~0.8с/id на `--processes=6`).
- *Сплит на один уровень недостаточен.* `css/CSS2` — 9228 id, шард на 5.3
  часа, смерть которого уносит весь бюджет. Сплит стал рекурсивным: 479
  шардов, крупнейший 1991 id, сумма id ровно 73495 (сходится с манифестом).
  Побочный случай, который сплит обязан различать: файлы, лежащие прямо в
  директории с подкаталогами — префиксом их не выбрать, `/css/CSS2/` заново
  захватил бы отделённые подкаталоги. По корпусу таких узлов 5 на ~100 id,
  они передаются явным списком id.
- *[BUG-785](../../bugs/BUG-785-OPEN.md)* — доверенные корни собираются только
  из `webpki_roots` в пяти местах `lumen-network`, добавить свой CA нечем.
  Самоподписанный CA WPT отвергается: каждый `.https.`-тест умирает как
  `UnknownIssuer`, не начавшись. **7190 из 67735 id (10.6% корпуса)** прибиты
  инфраструктурой, а не движком. Не путать с `WPT-RUN-2`, где чинился
  отсутствующий https-**порт** — другой слой, и он действительно починен.

**DoD:**
- Прогнан весь корпус за один прогон; цифра и снимок лежат в

**Ловушка (проверить перед публикацией цифры):** в пилоте `dom` дал 90
`TIMEOUT` на 320 исполненных. В срезах 40/42 `WPT-RUN-3` уже описан случай,
когда тест финиширует верно, а `wptrunner` всё равно пишет `TIMEOUT`, потому
что результат пришёл после внешнего дедлайна. При шести параллельных
браузерах это правдоподобно, и тогда цифра занижена **параллелизмом, а не
движком**. Контроль — тот же шард на `--processes=1` со сравнением числа
`TIMEOUT`.

**Ловушка снята (2026-08-18).** Контроль проведён на `dom`: `--processes=1`
и `--processes=6` дали **побитово одинаковый результат** — 320 тестов,
229 OK / 90 TIMEOUT / 1 ERROR, 2030/5616 сабтестов, ноль расхождений по
статусам, при этом параллельный прогон быстрее в 4.4× (267 с против 1170 с).
Параллелизм на цифру не влияет; полный прогон идёт с `--processes=6` без
оговорок. Сами таймауты `dom` разобраны: 48 из 90 висят на сабтестах,
требующих второго глобала (`<iframe>` без browsing context —
[BUG-480](../../bugs/BUG-480-OPEN.md), уже открыт), 42 не отчитываются вовсе
и остаются незакрытым вопросом для P3.

### Срезы 5–7 (2026-08-18)

- **Срез 5.** Убитый по бюджету шард терял всё, что успел прогнать
  (`--log-wptreport` пишется один раз, в конце): пилот так потерял 1656 id,

  Тогда же исправлен охват: частичный прогон считался по всему манифесту
  (10 категорий давали 0.58 % вместо 7.52 %).

- **Срез 7.** `--skip-https`. Замер: выборка 200 https-id из 65 категорий —

  экстраполяция на 6874 id — **≈14 часов** ради заранее известного нуля

  всё исключено» и «шард восстановлен из raw-лога» — раньше первое
  рапортовалось как второе.
