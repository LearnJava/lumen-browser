# Дорожка WPT-RUN — пропускная способность WPT-раннера

Бриф для ROADMAP.md-задач `WPT-RUN` / `WPT-RUN-1`…`WPT-RUN-3` (Фаза 3).
Владелец тулинга — **P2**; движковые баги по находкам уходят **P3/P1** по обычной
методологии группировки.

**Приоритет:** решением пользователя 2026-07-30 три указателя `WPT-RUN` подняты в
**начало** `STATUS-P2.md`, выше 184 строк `WPT-VENDOR`. Это сделано намеренно, а не
случайно: вендоринг категории №104 даёт меньше, чем довендоренный хелпер, после
которого начинают отчитываться тысячи layout-тестов. Не «исправлять» этот порядок
обратно.

Параллельная и независимая дорожка — `DEVX-7…16`,
[`p1-introspection-track.md`](p1-introspection-track.md). Общих файлов нет
(здесь Python в `tests/wpt/`, там Rust в `layout`/`paint`/`driver`), поэтому
дорожки идут одновременно.

---

## Зачем

Задача дорожки — превратить **уже вендоренный** корпус в измеряемый. Не вендорить
новое (это `WPT-VENDOR`), не писать новые тесты (это `TEST`), а снять три
ограничения исполнителя, из-за которых крупнейшая категория корпуса не прогоняется.

Факты из [`docs/wpt-status.md`](../wpt-status.md), строка `css`:

- Категория `css/` вендорена целиком 2026-07-26: **54350 файлов, ~209 МБ**,
  манифест отбирает **34607 тестовых id** — рекорд корпуса (следующая по размеру,
  `content-security-policy`, даёт 865).
- `run_report.py --all --root css --recursive` **не завершился**. При наблюдаемом
  темпе полный последовательный прогон занял бы порядка **суток**, а не часов.
- Ограниченная проба (~11:30, остановлена вручную) обработала **382 из 34607 id
  (~1.1%)**, покрыв `CSS1`/`CSS2` box-model/floats/normal-flow и начало
  `compositing`. Из них: **267 SKIP** («Executor does not support testdriver.js»),
  **62 голых TIMEOUT**, **53 harness OK**, и по добежавшим —
  **1294 из 2594 сабтестов passed**.
- Замечены 404 на `/resources/check-layout-th.js` (**56 попаданий**) и
  `/fonts/ahem.css` (3).

Отсюда вывод, определяющий приоритет дорожки: **половина сабтестов базовой
блочной модели CSS1/CSS2 падает, и мы не знаем, сколько там багов** — потому что
измерено 1.1%. В `BUGS.md` при этом на `css-parser` числится 13 багов из 429, то
есть счёт багов отражает, где мы искали, а не где они есть.

### Почему это дешевле кросс-движкового сравнения

Отдельно рассматривался вариант «открыть страницу в Chromium и в Lumen и
сравнивать стадии конвейера». Он отклонён (см.
[`p1-introspection-track.md`](p1-introspection-track.md) §Отложено): даёт «две
реализации расходятся, кто прав — неизвестно», тогда как WPT содержит **ожидаемый
ответ из спеки**.

`check-layout-th.js` — это ровно тот механизм: хелпер самопроверяющихся
layout-тестов, выдающий «expected width = 342, actual = 318, node = `<div>`»
нативно, для тысяч тестов, без эталонного браузера. Мы на нём отдаём 404. Один
довендоренный JS-файл даёт то, ради чего предлагалось строить дифер с Chromium.

### Что уже есть и не надо изобретать

- `tests/wpt/run_report.py` + `run_suite.py` (гейт), плагин `tools/wptrunner`,
  вендоренный офлайн-снапшот (`tests/wpt/VENDOR.md`).
- **Система ожиданий**: `.ini`-файлы + группировка провалов в `BUG-NNN` по
  первопричине (методология описана в `docs/wpt-status.md`, поставлена в P2-wpt
  S5) + храповик `KNOWN_DEBTORS`. Поэтому «тысячи красных» после массового
  прогона — не проблема: они ратчетятся, а не разбираются по одному.
- Гочи вызова `run_report.py` (нужен `LUMEN_PROFILE=dev-release`, `REPO_ROOT`
  от `__file__`, гонка `MANIFEST.json`, расширение `.htm`) — уже известны, см.
  `docs/wpt-status.md` §«Как обновить» и README в `tests/wpt/`.

## WPT-RUN-3: шардирование и массовый прогон `css/` (M)

**Зависит от:** `WPT-RUN-1`, `WPT-RUN-2` — иначе прогон измеряет не движок, а
пробелы исполнителя.

**Состав:** параллельный/шардированный прогон (34607 id последовательно ≈ сутки),
затем массовый прогон `css/` с записью ожиданий в `.ini` по существующей
методологии и группировкой провалов в `BUG-NNN` по первопричине.

**DoD:**
- `css/` прогнана целиком, результат зафиксирован в `docs/wpt-status.md`
  (строка `css` + при необходимости отдельная детальная таблица, как у `dom/nodes`).
- Ожидания закоммичены, гейт зелёный при нулевых unexpected.
- Провалы сгруппированы в `BUG-NNN` по первопричине — **не по одному тесту на баг**.
- В журнале зафиксировано, сколько id не добежало и почему (правило «no silent
  caps»: молча урезанное покрытие читается как полное).

**Порядок относительно дорожки DEVX:** массовый прогон полезнее делать **после**
того, как доехал инвариантный слой (`DEVX-8a`), — тогда часть падений приезжает
уже локализованной (сработавший инвариант называет место), а не в виде
«expected 342, actual 318». Это не блокирующая зависимость: прогон возможен и без
инвариантов, ратчет ожиданий его удержит. Речь только о стоимости **разбора**,
и поскольку дорожки идут параллельно, соблюдение этого порядка ничего не стоит.

**Ловушка:** не ослаблять вендоренные тесты. Движковый пробел = `expected:FAIL` +
`BUG-NNN`, ровно как в P2-wpt.

**Срез 1 (2026-08-02) — сделан только шардинг/параллелизм, не массовый прогон.**
`run_report.py` получил `--processes` (проброс в `wptrunner`'s `--processes`),
`--offset`/`--limit` (резать `--all`-выборку на воспроизводимые куски между
сессиями — id отсортированы, так что фиксированная пара всегда даёт один и тот
же срез, пока корпус не меняется).

Почему `--processes` вообще масштабируется: `wptrunner` группирует тесты по
каталогу (`testloader.py::PathGroupedSource`) и ограничивает число процессов
числом групп (`process_count = max(1, min(requested, num_groups))`) — на одном
каталоге (`css/CSS2/floats`, 12 id) `--processes=4` реально поднял только 2
процесса, но на разнородном срезе `css/` (много каталогов) поднялись все 6
запрошенных. Корректность проверена на `css/CSS2/floats`: `--processes=1` и
`--processes=4` дали побитово одинаковый результат (3/3 harness OK, 54/68
сабтестов) — параллелизм не портит исход.

Замер пропускной способности: `--root css --recursive --offset 0 --limit 600`
(353 отобранных id, начало `CSS1`/`CSS2`) — `--processes=6` прогнал их за ~48с
(~7.7 id/с) против ~0.55 id/с прежней последовательной пробы — **~14× быстрее**.
Это пересматривает оценку «сутки» вниз до порядка **~75 минут** чистого времени
`wptrunner` на весь корпус 34607 id при сопоставимом темпе. Не гарантия — начало
`CSS1`/`CSS2` может быть легче среднего по корпусу (директории с `testdriver`/
`.https.` дороже, см. `reference_wpt_run_report_invocation_recipe` в памяти
Claude) — реальную цифру даст только сам массовый прогон. Даже при 75 минутах
он не помещается в один интерактивный вызов (лимит Bash-таймаута), поэтому
`--offset`/`--limit` остаются нужны для нарезки на куски по сессиям, даже когда
`--processes` уже даёт параллелизм внутри куска.

Не сделано этим срезом (задел на срез 2+): собственно массовый прогон всего
`css/`, запись `.ini`-ожиданий, группировка провалов в `BUG-NNN`, обновление
строки `css` в `docs/wpt-status.md` с итоговым покрытием.

**Срез 2 (2026-08-02) — массовый прогон + `.ini` + группировка на `css/CSS2`
(816 файловых id, одна поддиректория, не весь `css/`).**

Первая находка среза меняет саму оценку задачи: `--root css/CSS2 --recursive`
отбирает 805 id по файловой системе (`all_vendored_test_ids()` просто
глобит `.html`/`.htm`), но фактический манифест `wptrunner` признаёт
`testharness`-тестами только **63** — остальные 742 суть reftest/crashtest-пары
(историческая CSS WG практика: `CSS2` в основном визуальные reftest'ы, не
JS-ассерты), для которых у `browsers/lumen.py` нет исполнителя вовсе (`TEST-4`,
warning `Unsupported test type reftest for product lumen` в логе). Это не
недосчёт этого среза — это структурный состав категории; наивный
файлово-глобовый счётчик `all_vendored_test_ids()` систематически завышает
«сколько реально прогонится» для любой reftest-тяжёлой директории. Оценку
среза 1 «~75 минут на весь `css/`» на основе этого стоит читать как верхнюю
оценку темпа wptrunner per-testharness-id, не как оценку покрытия — реальный
прогоняемый объём `css/` меньше файлового счётчика на неизвестную (но,
вероятно, немаленькую) долю.

Из 63 `testharness`-тестов: 53 harness OK, 10 TIMEOUT, 1206/2454 сабтестов
passed. Полная поимённая триаж (не оценка по частоте строк в логе, как в пробе
WPT-RUN-1, а чтение каждого непройденного файла и, где нужно, соответствующего
куска `dom.rs`/хелпера) дала 8 новых кластеров (BUG-463…470) и объяснила ещё 13
файлов уже открытыми находками (BUG-360 мёртвый `onload=`, BUG-384 named
access on Window) — детали и полный список файлов на баг см.
[`docs/wpt-status.md`](../wpt-status.md) → строка `css`, там же 5 файлов,
намеренно оставленных некластеризованными (единичные наблюдения, не решился
формулировать первопричину по одному данному).

`.ini` для всех 58 классифицированных файлов лежат под
`tests/wpt/metadata/css/CSS2/` (структура зеркалит id теста), с шапкой-ссылкой
на `BUG-NNN`; повторный прогон подтверждает 0 unexpected на них (5
некластеризованных остаются красными намеренно — не подтянуты в `.ini` без
приписанной первопричины).

Технический гоча: subtest-имена вида `... at (0) should be [initial]`
(WAAPI-интерполяционные тесты) содержат буквальные `[`/`]` — секция `.ini`
`[name]` парсится `tools/wptrunner/wptrunner/wptmanifest`, и незаэкранированный
`]` внутри имени рвёт парсер (`ParseError: Junk before EOL`). Экранировать
только `]` (и сам `\`) через `\]` — `[` внутри имени экранировать не нужно
(сериализатор апстрима, `wptmanifest/serializer.py::escape(name, extras="]")`,
делает ровно так же).

Не сделано этим срезом (задел на срез 3): та же процедура (массовый прогон +
триаж + `.ini` + `BUG-NNN`) на оставшихся ~34500 id `css/` за пределами
`CSS2` — `CSS1` (пусто в текущем вендоре), все `css-*`-модули, `cssom`,
`compositing`, и т.д.

## WPT-RUN-4: честная сводная цифра pass-rate по всему корпусу (M)

**Отличие от `WPT-RUN-3`.** `WPT-RUN-3` прогоняет и **триажит** категории по
одной, наращивая `.ini` и заводя `BUG-NNN` — это работа по улучшению движка.
`WPT-RUN-4` отвечает на другой вопрос: **какова цифра целиком**, за один
прогон, в форме, сопоставимой с wpt.fyi/Servo/Ladybird. Первый проход —
измерение, не гейт: `.ini` эта задача не пишет вовсе.

Повод — вопрос «как попасть на wpt.fyi»: туда загружают не HTML-отчёты, а
`wptreport.json` по всему корпусу, и первым делом нужна собственная честная
цифра.

**Решения пользователя (2026-08-18), не пересматривать по ходу:**

1. Сначала testharness-цифра (этапы «знаменатель → оркестратор → прогон»),
   reftest-исполнитель (`TEST-4`/`TEST-5`) — следующим шагом.
2. Знаменатель — **весь манифест без изъятий**: reftest-ы, которые мы не
   исполняем, и 🚫-категории остаются внутри; неисполненное = непройденное.
3. Первый прогон — пилот из 10 разнородных категорий, затем всё.
4. `.ini` не трогаем.
5. Трекинг — эта дорожка, ветка `p2-wpt-run-4`, слот `p2-work`.
6. Результат — `docs/wpt/runs/<дата>.json` + журнал `docs/wpt/pass-rate.md`.

**Почему знаменатель нельзя брать из файлов.** `run_report.py::all_vendored_test_ids()`
глобит `*.html`, и такой счёт ошибается в обе стороны сразу: завышает
(`foo-ref.html` — файл, но не исполняемый id) и занижает (`?variant`,
развёртка `.any.js`). Ни с чьим дашбордом такое число не сопоставимо.
Считает манифест `tests/wpt/corpus_stats.py`.

**Срез 1 (2026-08-18) — знаменатель.** 273 категории, 73495 id; из них 67735
автоматизируемых (знаменатель), 5760 `manual`/`visual` (их не исполняет ни
один раннер, включая апстримный — вынесены отдельной строкой), 37319
`testharness`. Отсюда главный факт задачи: **потолок сегодняшней цифры —
55.1%**, потому что зарегистрирован единственный исполнитель `testharness`;
в одной только `css/` 24552 reftest против 7447 testharness. Публиковать
цифру без этой оговорки нельзя — иначе она читается как приговор движку.

**Срез 2 (2026-08-18) — оркестратор.** `tests/wpt/run_corpus.py`: отбор из
манифеста, шард = единица работы и чекпойнта, `run_smoke.py` вызывается
подпроцессом на шард. Три вынужденных решения задокументированы в самом
файле: подпроцесс (зависший `wptrunner` внутри своего интерпретатора не
убить, а прогон обязан пережить один плохой шард), убийство по дереву
процессов (`Popen.kill()` снял бы только Python, осиротевший `lumen.exe`
держал бы BiDi-порт и ломал следующий шард; по имени образа не убиваем
никогда), обновление `MANIFEST.json` один раз за прогон (дефолт `wptrunner` —
пересканировать 72k файлов на каждом из ~480 шардов).

Скоринг повторяет форму wpt.fyi: тест с сабтестами — доля пройденных, без
сабтестов — 1 при `PASS`, **id без результата — 0**. Последнее и есть суть:
считаем по манифесту, а не по отчётам, поэтому неисполнимые reftest-ы и
потерянные шарды честно тянут цифру вниз. Методика — `docs/wpt/pass-rate.md`.

**Срез 3 (2026-08-18) — пилот и его находки.** Пилот отработал по назначению:
поймал три дефекта до ночного прогона.

- *Фиксированный таймаут шарда негоден.* 1200с убили `encoding` (1343 id) на
  середине и были десятикратно избыточны для `FileAPI` (125 id). Бюджет стал
  пропорциональным (`600с + 2с/id` при измеренных ~0.8с/id на `--processes=6`).
- *Сплит на один уровень недостаточен.* `css/CSS2` — 9228 id, шард на 5.3
  часа, смерть которого уносит весь бюджет. Сплит стал рекурсивным: 479
  шардов, крупнейший 1991 id, сумма id ровно 73495 (сходится с манифестом).
  Побочный случай, который сплит обязан различать: файлы, лежащие прямо в
  директории с подкаталогами — префиксом их не выбрать, `/css/CSS2/` заново
  захватил бы отделённые подкаталоги. По корпусу таких узлов 5 на ~100 id,
  они передаются явным списком id.
- *[BUG-785](../../bugs/BUG-785-FIXED.md)* — доверенные корни собираются только
  из `webpki_roots` в пяти местах `lumen-network`, добавить свой CA нечем.
  Самоподписанный CA WPT отвергается: каждый `.https.`-тест умирает как
  `UnknownIssuer`, не начавшись. **7190 из 67735 id (10.6% корпуса)** прибиты
  инфраструктурой, а не движком. Не путать с `WPT-RUN-2`, где чинился
  отсутствующий https-**порт** — другой слой, и он действительно починен.

**DoD:**

### Профиль бюджетных убийств (2026-08-20 18:40): темп задаёт доля TIMEOUT, а не размер шарда

Снимок на 49 из 273 категорий, 3894 automatable id, частичная цифра по своему
охвату **9.11 %** (`ran` 3378, `never ran` 516, `TIMEOUT` 2090). Три шарда
убиты по бюджету — `WebCryptoAPI`, `ai`, `bluetooth`; их результаты спасены из
raw-логов (129, 85 и 83 записи, срез 8).

Бюджет шарда — `600 + 2.0·N` секунд, значит шард гибнет, когда его темп
превышает `2 + 600/N` c/id: для `N = 2000` это 2.30 c/id, для `N = 155` — 5.87.
Средний темп по 48 отработанным шардам — **2.48 c/id** (2.98 ч на 4327 id), то
есть формально на грани. Но разложение по шардам показывает, что средним тут
пользоваться нельзя — разброс полтора порядка, и определяет его **не размер**:

| шард | id | c/id | состав |
|---|---|---|---|
| `core-aam` | 275 | 0.02 | почти всё отсеяно фильтром |
| `dom` | 343 | 0.75 | 320 testharness, движок отвечает |
| `content-security-policy` | 896 | 1.41 | 894 testharness |
| `compat` | 38 | 0.48 | 25 reftest |
| `IndexedDB` | 813 | 2.21 | 813 testharness, много TIMEOUT |
| `bluetooth` | 155 | ≥5.87 | убит; API не реализован — каждый тест выстаивает свой настенный таймаут |
| `attribution-reporting` | 24 | 16.73 | то же, но шард мал и уложился в базу 600 с |
| `background-sync` | 2 | 35.75 | фиксированный старт браузера на два теста |

Отсюда два вывода для хвоста прогона (осталось **433 шарда / 69 804 id**):

1. **Крупные `css/*` не в зоне риска, вопреки арифметике порога.** 12 135
   оставшихся id лежат в шардах с порогом 2.3–2.5 c/id (`css/css-text` 1991,
   `svg` 1740, `html/canvas/element` 1517, `css/css-flexbox` 1432), и по
   среднему 2.48 они читались бы как обречённые. Но это ровно
   reftest-тяжёлые директории, а reftest в замере 18:20 дал ноль TIMEOUT при
   9 PASS / 44 FAIL — то есть доходит до вердикта быстро. Плюс крупный шард
   амортизирует старт браузера. Ожидаемый темп там — ниже 2 c/id.
2. **Риск — категории нереализованных API**, где таймаутит всё подряд: они
   дороги на id, и убивает их бюджет ровно в среднем диапазоне размеров
   (100–400 id), где база 600 с уже не спасает, а `2·N` ещё мало.

**Что делать с этим в `WPT-RUN-9`:** поднять `--shard-timeout-per-id` (значение
8 покрывает наблюдаемый максимум по шардам ≥100 id с запасом). **Отменено
срезом 15:** значение 8 подобрано по наблюдению и покрывает убитые шарды с
запасом 2–4 %, то есть случайно; бюджет теперь выводится из объявленных в
манифесте таймаутов, а флаг остался только для воспроизведения старого
прогона. Это ничего не
стоит на здоровых шардах — бюджет есть таймаут, а не пауза, и здоровый шард
завершается раньше; платят только те шарды, которые иначе были бы убиты.
Поднимать на **живом** прогоне бесполезно: процесс держит аргументы со старта,
а перезапуск ради этого переиграет убитые шарды заново (`--resume` пропускает
только `outcome == "ran"`) — на текущей тройке это ~50 минут.

### Срез 9 (2026-08-20 18:55): `--resume` больше не переигрывает убитые шарды

### Срез 13 (2026-08-20 23:00): второго пути потери стиля нет — зато BUG-786 работает иначе, чем записано, и рядом нашёлся BUG-793

Срез 12 оставил открытым вопрос «есть ли у XHTML второй путь потери стиля
помимо CDATA» и оставил 22 не-CDATA `inert`-PASS неразобранными. Отвечает
новый режим `tests/wpt/inert_style_audit.py --explain <json-прошлого-прогона>`:
он не вырезает CSS, а **добавляет** в каждый авторский `<style>` одно заведомо
наблюдаемое объявление (`html{margin-left:37px}`) — в начало блока и, отдельным
прогоном, в конец, внутрь `<![CDATA[ … ]]>`, если он есть. Вырезание отвечает
на вопрос «сработало ли хоть одно авторское объявление», добавление — на
следующий вопрос вниз: «дошёл ли блок до CSS-парсера вообще», а разделение
начало/конец локализует потерю внутри блока.

Прогон по всем 29 `inert`-PASS среза 12 (`--explain .tmp/inert-sample-400.json`):

| механизм | сколько | что значит |
|---|---|---|
| `sheet_live` | **18 (62 %)** | блок дошёл до парсера, инертны сами авторские объявления |
| `no_style_block` | 7 (24 %) | авторский CSS — `<link>`/`style="…"`, зонд до него не достаёт |
| `first_rule_eaten` | 2 | блок парсится, но его первое правило — нет |
| `tail_eaten` | 1 | наоборот: начало живо, хвост потерян |
| `sheet_lost` | 1 | артефакт зонда, см. ниже |

**Ответ на вопрос среза 12: второго пути потери стиля у XHTML нет.** Пять из
шести CDATA-класса стоят `sheet_live`, все `.xht` из не-CDATA — тоже. То, что
осталось в `inert`, — не потерянные таблицы стилей, а объявления, которые
ничего не двигают на этом движке: непопавшая медиа-выборка
(`media-dependency-010/016` — `@media braille`), объявление, перекрытое собой
же (`floats-022`: `float:left; float:none`), нереализованное свойство
(`outline-style-001`/`outline-width-071`), негативные тесты CSS2.1. Искать
«второй XML-баг» не надо — его нет.

**Зато сам BUG-786 описан неверно, и это выяснилось тем же зондом.** Маркер,
вставленный **внутрь** CDATA, применяется — значит блок до парсера доходит,
вопреки формулировке «всё содержимое отброшено». Прямое репро с тремя
правилами внутри CDATA: первое теряется, второе и третье применяются. Механизм
ровно тот, что в самом баге описан наполовину: `<![CDATA[` — невалидный старт
правила, и парсер съедает его как prelude плохого правила вместе с первым же
блоком `{…}`; дальше поток снова валиден, закрывающий `]]>` последнее правило
не уносит. По корпусу: в `.xht`/`.xhtml` вендоренного WPT 4 327 CDATA-блоков,
из них ровно одно правило (то есть полная потеря) — **736 (17 %)**; в
остальных 83 % пропадает одно правило из нескольких. Это независимо
подтверждает прямой замер среза 12 (7 из 35 CDATA-PASS вакуумны, 20 % — тот же
порядок) и объясняет его: вакуумны ровно блоки с единственным правилом.
[BUG-786](../../bugs/BUG-786-OPEN.md) и его строка в `BUGS.md` исправлены —
заголовок, раздел «Симптом», новый раздел «Уточнение механизма».

**Побочная находка — [BUG-793](../../bugs/BUG-793-OPEN.md).** Единственный
`tail_eaten` — `css/CSS2/cascade/at-import-009.xht`, чей `<style>` начинается с

положен блок, но закрытое `;`, съедает **весь остаток таблицы стилей**.

другим не прерывается, поэтому телом «медиа-правила» становится следующее

обрабатывает правильно), `@charset;`, `@import`, `@page;`, `@font-face;`,
`@layer;`. По WPT это почти ничего не стоит (89 grep-совпадений, почти все —
строки в JS), ценность — устойчивость живых сайтов.

То есть **потолок исполнителей объясняет 3 030 из 27 117**, а остальные 24 087
(35.6 % корпуса, 46 % всего, для чего исполнитель есть) — это не «движок не
смог», а «до этих id никто не дошёл». Для сравнения тот же разбор на
Linux-половине: 1 828 потолок + 341 убитые по бюджету шарды + **ноль** остального.

**2. Почему это не видно ни в отчёте прогона, ни в `--resume`.** Оба режима
отказа записываются в `state.json` как `outcome: "ran"`:

* wptrunner открывает файл `--log-wptreport` **в начале** и пишет его один раз в
  конце, поэтому шард, умерший до первого теста, оставляет нулевой файл — ровно
  такой же, какой оставляет категория, где нечего запускать. `run_corpus.py`
  проверял только «файла нет» (`no-report`) и обе эти ситуации считал `ran`;
* шард, завершившийся кодом `143`, тоже `ran` — `proc.wait()` вернул код, а не
  бросил `TimeoutExpired`, значит убил его не бюджет, а что-то на той машине.

`ran` — это ровно тот признак, по которому `--resume` считает шард сделанным, так
что 199 шардов (30 819 id) были потеряны **навсегда**, а сводка прогона при этом
честно печатала «479/479 шардов, outcome == ran».

**3. Природа отказа.** Прямых логов Windows-машины у этой сессии нет, но профиль
однозначен: 132 из 158 пустых шардов — `rc=1` при медиане 11 с, тогда как
здоровый шард той же величины идёт минуты. `rc=1` у wptrunner означает «прогон
дал неожиданные результаты», `rc=64` — «что-то залогировало CRITICAL»
(`wptrunner.py::start`), а исключение, вылетевшее из старта окружения, даёт
именно `1` от самого интерпретатора. 11 с — это цена старта wptserve. На
Linux-половине те же строки `wptserve CRITICAL ... Address already in use` /
`No sockets activated` встречаются **в 226 логах из 242** и переживаются, то есть
механизм общий (порт предыдущего шарда ещё занят), а фатальным он становится на
Windows. Это ровно та готча про `Servers failed to start`, что записана в
CLAUDE.md, — но с последствием, которого там не было: она не роняет прогон, она
молча вычитает из него шард.

**4. Правка.** Три изменения в `run_corpus.py`, все — про «называть вещи своими
именами», а не про новую логику:

* шард без единого вердикта больше не `ran`. Различаются по собственным словам
  wptrunner в логе шарда: `Unable to find any tests` / `No tests ran` →
  `no-tests` (терминально, повтор ничего не даст), иначе → `empty-report`;
* `empty-report` повторяется **сразу**, один раз, с паузой 10 с (стоит секунды,
  а лечит именно транзиторную занятость порта) и ещё раз на следующем
  `--resume`;
* код возврата вне `(0, 1, 64)` означает, что процесс завершили извне →
  `signalled`; такой шард виден в сводке как проблемный и достаётся
  `--retry-timeouts`.

`--resume` вдобавок **перечитывает диск, а не верит записанному outcome**: шард,
записанный как `ran`, но не давший вердиктов и не сказавший «нечего запускать»,
запускается снова. Это то, что лечит уже существующий `state.json`
Windows-половины: одна команда `--resume` возвращает 158 пустых шардов, а
`--retry-timeouts` — ещё 41 убитый. Проверено: на живом Linux-каталоге (242
шарда) фильтр не трогает **ни одного** шарда, а на синтетическом наборе из
четырёх случаев (нет тестов / всё отфильтровано / упал старт / здоровый) в
повтор уходит ровно упавший.

Цена лечения посчитана по тем же категориям, где Linux их уже прогнал: 36 из 199
шардов дают **1.13 с/id**, отсюда все 30 819 id — **≈9.7 ч**. Это не «лишние
часы»: сейчас эти id стоят в знаменателе как нули.

**5. Что теперь можно сказать про две половины.** `--compare` сравнивает снимки
на пересечении охвата, и картина ровно обратная той, что читается из головных
цифр:

* из 74 общих категорий **48 совпадают до последнего счётчика** — движок
  детерминирован, и там, где обе машины прогнали одно и то же, они дают одно и
  то же;
* расхождения в оставшихся 26 почти целиком — разница **охвата**, а не вердиктов:
  на исполненный id Windows даёт 0.1959 против 0.1828 у Linux (разница 6.7 %
  относительных, и та объясняется тем, что Linux дошёл до тяжёлых категорий вроде
  `encoding`, где почти нечего набирать), тогда как по знаменателю манифеста

* **слитая цифра** (по категории берётся тот прогон, что исполнил больше) на

Отсюда практический вывод к публикации: **головную цифру Windows-половины
публиковать нельзя без указания охвата** — 11.22 % посчитаны там, где 40 %

Честная пара — «11.22 % от манифеста при 60.0 % охвата» либо «18.72 % на
исполненных id»; первая цифра сравнима с wpt.fyi по методике, вторая — нет, но
она показывает, чего стоит дыра. Правильный порядок: сначала `--resume`

**Состояние прогона на момент среза:** Linux 242 из 479 шардов, процесс жив
8 ч 13 мин; правка `run_corpus.py` его не затрагивает (интерпретатор прочитал
скрипт на старте), эффект — на первом `--resume`.

### Срез 17 (2026-08-21): в `accounting()` тот же класс бага, что срез 16 чинил в `run_shard()` — сравнение имён шардов вместо кода завершения

Независимо от разбора среза 16 (снимок Windows-половины, `--snapshot`/`--compare`),
на свободной Windows-машине прогнан старый путь `score_audit.py --out-dir` — тот,
что читает каталог `.tmp/wpt-corpus` напрямую, а не опубликованный снимок. Он
до сих пор даёт `LEAK` (`lost-in-ran-shard` в районе 10-11 тыс. id), хотя срез 16
уже объяснил ту же дыру через `outcome`/`returncode`. Причина — второй,
независимый баг в самом `accounting()` (не в `run_shard()`, его срез 16 не
трогал): `empty_set` строится из имён файлов на диске (`css__css-fonts`, `/` →
`__`, как и путь отчёта в `run_corpus.py`), а сравнивается с `name` — именем
шарда из `state.json`, которое хранится с `/` (`css/css-fonts`). Для любой
многоуровневой категории `"css/css-fonts" in {"css__css-fonts", ...}` — всегда
`False`, и легитимно пустой шард ошибочно засчитывается утечкой. Показательно,
что новый `snapshot_accounting()` того же среза 16 сравнивает верно
(`shard["name"].replace("/", "__") in empty`) — баг остался только в старой
функции, на новый путь не перешёл.

Правка — `name.replace("/", "__") in empty_set`, как уже делает `kill_cost()` и
как теперь делает `snapshot_accounting()`. Проверено A/B на завершённом
Windows-прогоне (479/479, 11.22 %): `shard-empty` 13227→15369,
`lost-in-ran-shard` 10860→8718 — сдвиг ровно на 2142 id, ни одна другая причина
не шевельнулась. Остаток `lost-in-ran-shard` (8718 id) — это ровно то, что срез
16 уже объяснил и лечит через `--resume`+перечитывание диска
(`empty-report`/`no-tests`/`signalled`), отдельного действия не требует.
### Срез 18 (2026-08-21): ни один шард Linux-половины не поднял собственные серверы

Срез 16 объяснил дыру Windows-половины двумя режимами отказа шарда, один из
которых — «шард вернулся за медианные 11 с с пустым отчётом» (158 шардов,
15 753 id). Починка среза 16 замечает такой шард и переигрывает его, но она
лечит симптом: причина пустого отчёта в том, что шард **не смог занять порты**,
и повтор упирается в того же держателя.

Держатель — не гипотеза. `tests/wpt/config.json` фиксирует все семь портов
(18300/18301 http, 18443/18444 https, 18888/18889 ws/wss, 19000 h2), а
`wptserve` запускает каждый сервер отдельным `multiprocessing`-потомком: убийство
раннера над ними (Ctrl-C, конец сессии, OOM) до них не доходит, они
переподчиняются init и живут вечно. Замер на живой Linux-половине 2026-08-21:

- все семь портов держат сироты (pid 136911–136917, по одному на порт),
  стартовавшие **16:10:27 — за 4.5 минуты до самого прогона** (16:15:00), то
  есть это остатки прогона, умершего прямо перед ним;
- из 342 завершённых шардов **328 несут `Address already in use`**, остальные
  14 до старта серверов не доходили вовсе (`Unable to find any tests`). То есть
  собственный сервер не поднял **ни один** шард, дошедший до необходимости в
  нём — 100 %, а не «часть»;
- на Windows тот же захват не отвечает, и шард умирает пустым отчётом. Это
  ровно дыра среза 16, увиденная с той стороны, с которой она чинится.

**Что это делает с цифрой.** Не «портит вердикты», но и не ничего. Проверено
зондами на живом прогоне: сирота отдаёт дерево с диска в текущем виде (файл,
созданный за секунду до запроса, вернулся `200`), то есть тесты исполняются
именно те; `/resources/testharnessreport.js` он отдаёт **ломеновский**, а не
дефолтный wptrunner-овский (BUG-301) — расхождение с файлом в
`tests/wpt/resources/` ровно в четырёх подстановках `%(...)s`. Но подставляет
их `TestEnvironment.get_routes` **в момент старта сервера**, и в этом опасность:
до страницы доходят `output`, `debug`, `timeout_multiplier`, `explicit_timeout`
**мёртвого** прогона, а не живого, и то же верно для любого статического
маршрута из `browsers/lumen.py::env_options`. Linux-половина достоверна лишь
потому, что умерший прогон запускался той же командой; в отчёте об этом ничего
нет, и никто этого не проверял. Второй риск того же порядка: сирота из **чужого
worktree** отдавал бы файлы чужой ветки — цифра описывала бы не тот код, и
опять молча.

**Починка** — `tests/wpt/port_guard.py` (новый модуль) + вызов из
`run_corpus.py` перед каждым шардом. Политика намеренно узкая, потому что на
машине живут сессии других разработчиков (пять слотов пула): убивается только
держатель одного из настроенных портов и только если это осиротевший
`wptserve`-потомок; держатель, над которым **жив** чужой `run_corpus.py` /
`run_smoke.py` / `wptrunner`, не трогается — прогон останавливается и называет
его. Отдельный случай — держатель, над которым жив **сам вызывающий**
(`own_pid`): это ещё не доехавший сервер предыдущего шарда, и его надо забирать,
иначе правило «над ним жив корпусный прогон» отменяло бы прогон на его
собственных остатках. Проверка стоит семь `connect_ex` по refused-порту, то есть
микросекунды, и не порождает ни одного подпроцесса, пока порты свободны;
`--no-port-guard` — аварийный выход.

Проверено `--selftest` (синтетический сквоттер на эфемерном порту:
обнаружение → классификация `orphan`/`live`/`stale` → убийство → порт свободен),
трижды подряд PASS, и `--reclaim --dry-run` против настоящих семи сирот — они
опознаны как `orphan`, живой прогон при этом не тронут.

**Идущий прогон это не чинит**: его процесс держит код на 16:15. Останавливать
его ради порт-гарда не стали — тесты берутся с живого диска, а опции умершего
прогона совпадают с его собственными. Следующий запуск (в том числе `WPT-RUN-9`)
получает гарду автоматически; перед ним стоит один раз выполнить
`.venv-wpt/bin/python tests/wpt/port_guard.py --report` и убедиться, что семь
портов свободны.

### Срез 19 (2026-08-21): «never ran: N» — это четыре разные причины в одном числе

Срез 16 нашёл дыру Windows-половины не из сводки прогона, а отдельным аудитом
(`score_audit.py`, срез 15). Сводка при этом печатала ровно одну строку:

```
  never ran:  27117  (scored 0 — no executor, skipped, or lost shard)
```

Все четыре причины — тип без исполнителя, шард убитый по бюджету, шард с пустым
отчётом и id, потерянный внутри шарда, который отчитался успехом — попадали в
это число неразличимо. Классификатор, умеющий их разделять, существовал с среза
15, но он в отдельном скрипте: чтобы дыра стала видна, её надо было пойти и
поискать. Windows-половина пришла к финишу с `479/479 shards ran` и 36 %
знаменателя без вердикта именно поэтому.

**Что сделано.** Сводка прогона и снимок `--run-json` теперь несут разбор
нулевого ведра, и считает его **тот же** `score_audit.accounting`, а не вторая
копия правил: `run_corpus.score_reports` вызывает его локальным импортом
(`score_audit` импортирует `run_corpus` на верхнем уровне, поэтому только
локальным). Классификация обогащена привязкой к шарду — `lost_by_shard`
возвращает `{shard, outcome, cause, ids}`, и это используют оба печатника:
теперь видно не «потеряно 503», а какие шесть шардов их потеряли и по какой
причине. `print_snapshot_audit` при наличии точного блока печатает его рядом со
своей покатегорийной оценкой — сверять их на одном снимке полезнее, чем
заменять одну другой.

Как это читается на живой Linux-половине (142 из 266 категорий, 04:09):

```
  never ran:        2672  (scored 0)
    no executor:  2169  (crashtest=1670, print-reftest=403, aamtest=96) — a runner gap (WPT-RUN-8), not an engine result
    lost:         503  in 6 shard(s): WebCryptoAPI(shard-killed)=184, fledge(shard-killed)=96, ...
```

и это же — независимая проверка двух вещей, которые до сих пор принимались на
слово:

- **у reftest'ов дыры нет вообще**: 0 из 26 481 id без вердикта. Исполнители
  TEST-4/TEST-5 отрабатывают на всём охвате половины, а не только на выборке;
- **вся потеря testharness — 503 id из 25 288 (2.0 %)** и вся она лежит в шести
  шардах, убитых по бюджету. `lost-in-ran-shard` — ноль. То есть кроме
  известной статьи «шард не уложился в бюджет» Linux-половина ничего не теряет.

Для сравнения, завершённая Windows-половина по своему же снимку: 27 117 id без
вердикта при `479/479 ran`, из них 15 753 в шардах, не давших ни одного
вердикта, 6 474 в шардах, убитых сигналом, 3 030 без исполнителя и 1 860 не
объяснены ничем. Новая сводка напечатала бы это на месте, а не через сутки.

**Проверка** — `tests/wpt/run_corpus.py --selftest`: синтетический манифест из
четырёх категорий, четыре шарда с назначенными исходами и один вердикт; восемь
утверждений (тип без исполнителя не приписывается шарду, убитый шард назван со
своей причиной, пустой отчёт **не** считается тихой дырой, id с вердиктом не
попадает в потери). Утверждения проверены на чувствительность мутациями входа:
смена исхода шарда с `ran` на `timeout` обнуляет тихую дыру, изъятие шарда из
списка пустых поднимает её до 2, появление вердикта — опускает до 0.

Оговорка про идущий прогон прежняя и теперь важнее: он держит код на 16:15, его
собственная финальная сводка блока охвата не напечатает. Финальный снимок
обязательно пересчитать `--aggregate-only` — только тогда в
`docs/wpt/runs/…json` появится `scored.coverage`.

### Срез 20 (2026-08-21): 2 550 id корпуса адресованы хосту, которого на этой машине не существует

Срез 18 закончился признанием: прогон обслуживают серверы-сироты, и «цифра при
этом не сломана» — но проверено это было одним `http`-портом, а сама фраза
опиралась на то, что у мёртвого прогона были те же опции. Первым делом закрыт
именно этот долг: **все семь настроенных серверов живы и отвечают правильно** —
`http` 18300/18301 и `https` 18443/18444 отдают `/resources/testharness.js`
(200, 198 291 байт, тот же размер, что на диске), `h2` 19000 отвечает по HTTP/2,
`ws` 18888 и `wss` 18889 отдают `101 Switching Protocols` на рукопожатие.
Гипотеза «массовый TIMEOUT — артефакт полумёртвой обвязки» закрыта: обвязка
целая.

Зато та же проба нашла другое, и покрупнее. Вот что живой сервер отдаёт
браузеру в `/common/get-host-info.sub.js` — файле, из которого тесты берут
«другой origin»:

```
var ORIGINAL_HOST = '127.0.0.1';
var REMOTE_HOST = (ORIGINAL_HOST === 'localhost') ? '127.0.0.1' : ('www1.' + ORIGINAL_HOST);
var OTHER_HOST = 'www2.127.0.0.1';
var NOTSAMESITE_HOST = (ORIGINAL_HOST === 'localhost') ? '127.0.0.1' : ('not-web-platform.test');
var OTHER_NOTSAMESITE_HOST = 'www2.not-web-platform.test';
```

`www1.127.0.0.1` — не адрес и не имя: `getaddrinfo` на него отвечает
NXDOMAIN, как и на `not-web-platform.test`, для которого нужна запись в
`/etc/hosts`. Из **66** имён, которые `wptserve` публикует по своей же
конфигурации, на этой машине разрешается **одно** — сам `127.0.0.1`.

**Откуда это взялось.** WPT — многооригинный набор: сервер раздаёт одно дерево
под основным хостом, пятью поддоменами (`www`, `www1`, `www2` и два IDN) и
отдельным доменом `not-web-platform.test`, чтобы тест мог проверить поведение
через границу origin. Апстрим это работает после штатного шага установки
(`wpt make-hosts-file` → `/etc/hosts`). Наш раннер этот шаг сознательно
пропускает: `browsers/lumen.py::env_options` фиксирует `browser_host` в
литерал `127.0.0.1`, и в комментарии там прямо написано почему — «BiDi-автоматизация
кросс-origin-поддомены всё равно не гоняет, скоуп S4/S5 — однооригинные
`dom/`-тесты». Для пилота это было правдой и стоило ноль. На корпусе — не
правда и не ноль: `wptserve` строит семейство поддоменов **префиксом** к
`browser_host`, то есть из IP получается `www1.127.0.0.1`.

**Сколько это стоит цифре** (`tests/wpt/host_audit.py`, сканирование исходников
+ соединение с вердиктами живого прогона):

```
exposure: 2550 of 67735 automatable ids (3.8%) name a foreign host, in 2009 of 60536 source files
  testharness      2473 of 37319
  reftest            72 of 27386
  top categories: html=650/9981, fetch=310/921, speculation-rules=212/530,
                  service-workers=107/331, xhr=85/425, resource-timing=77/159

cost: of the 1509 marked ids with a verdict, 69.4% TIMEOUT and they score 5.38%;
      the other 50518 ids 18.1% / 18.12%
```

Разбор по механизму: 1 892 id называют только поддомен собственного хоста,
305 — только альтернативный домен, 256 — оба.

**Контроль.** Помеченные id — это ровно кросс-origin-тесты, они и без того
тяжелее среднего, поэтому разрыв 69.4 % против 18.1 % сам по себе ничего не
доказывает. Смотреть надо внутри категории, где сравниваются соседи:

| категория | помечено | TIMEOUT | score | остальные | TIMEOUT | score |
|---|---|---|---|---|---|---|
| `html` | 583 | 80.1 % | 2.7 % | 9 132 | 27.9 % | 18.3 % |
| `fetch` | 310 | 68.1 % | 8.6 % | 607 | 66.9 % | 12.9 % |
| `content-security-policy` | 74 | 66.2 % | 10.0 % | 822 | 57.1 % | 10.1 % |
| `fenced-frame` | 73 | 80.8 % | 0.0 % | 126 | 65.1 % | 0.4 % |
| `client-hints` | 64 | 54.7 % | 0.0 % | 68 | 36.8 % | 4.4 % |
| `css` | 62 | 8.1 % | 18.6 % | 31 937 | 5.6 % | 20.5 % |

Читается это так: в `html` неразрешимое имя добавляет 52 п.п. таймаутов к
соседям по категории — там эффект настоящий и крупный; в `fetch` разрыва нет
вообще (68.1 против 66.9), то есть там тесты висят по своим причинам и хост
ничего не добавляет. Значит 2 550 id — это **верхняя** граница ущерба, а не
измеренный ущерб, и списывать весь их ноль на неразрешимый хост нельзя.

**Сколько это стоит часам.** 1 047 таймаутов среди помеченных id — на 774
больше, чем дала бы средняя по корпусу доля; по подогнанной ставке 2.69 с за
TIMEOUT (срез 15) это 0.6 ч уже потраченного времени и ≈1.0 ч на весь корпус.
На фоне 4–6 ч общего счёта за таймауты — мелочь. **Это дефект качества цифры, а
не пропускной способности**, и в `WPT-RUN-6` он не входит.

**Что с этим делать — три пути, ни один не бесплатный.**

1. **Как делает апстрим:** `/etc/hosts` (одна строка от `wpt make-hosts-file`)
   и `browser_host` обратно в `web-platform.test`. Чинит всё, включая
   альтернативный домен; требует `sudo` **на обеих машинах** — то есть выходит
   за рабочую границу проекта и решается пользователем, а не сессией.
2. **`browser_host: "localhost"`** — правка одной строки в `env_options`, целиком
   в нашей власти. На этой машине `*.localhost` разрешается (RFC 6761 +
   `systemd-resolved`: `www1.localhost` → `::1`), то есть семейство поддоменов
   (1 892 id) оживает без изменения системы, а `get-host-info` для `localhost`
   отдаёт `NOTSAMESITE_HOST = '127.0.0.1'` — другой origin, чем `localhost`, так
   что часть «оба» тоже начинает работать. Два подвоха: Windows-половина
   `*.localhost` не резолвит (халвы перестанут быть сопоставимы), и имя
   разрешается в `::1`, а сервер слушает IPv4 — надо проверять, что клиент
   перебирает адреса, иначе «висело» превратится в «отказ в соединении».
3. **Переопределение резолва в самом браузере** — `LUMEN_RESOLVE=host=ip,…` по
   образцу `curl --resolve`, точка вставки готовая: `lumen_core::ext::DnsResolver`,
   рядом с `SystemDnsResolver` в [`crates/network/src/dns.rs`](../../crates/network/src/dns.rs).
   Раннер передаёт переменную так же, как уже передаёт `LUMEN_EXTRA_CA_CERT`
   (фикс BUG-785). Портируемо, не трогает машину, полезно за пределами WPT —
   но это правка движка, то есть отдельная задача, а не строка в конфиге.

Заведено как `WPT-RUN-10` (ROADMAP.md); выбор пути — за пользователем, потому
что путь 1 меняет его машину, а путь 3 расширяет публичную поверхность движка.
До того как путь выбран, **оговорка едет вместе с обеими цифрами**: у
Windows-половины ровно тот же `env_options`, так что её опубликованные 11.22 %
несут её в той же мере.

**Инструмент.** `tests/wpt/host_audit.py` — три независимые части: `exposure`
(скан исходников по маркерам `get-host-info`/`{{domains[`/`{{hosts[`/литералы
доменов, один читаемый файл на N id), `cost` (соединение с вердиктами прогона,
общее и внутри категории, плюс цена в часах через `score_audit.wall_clock`),

`--selftest` — синтетическое дерево из четырёх файлов и манифест с фан-аутом
`.any.js`: проверяется, что помечается файл, а не id (2 id с одного источника),

Утверждения проверены мутациями: изъятие маркера, скоринг без сабтестов,

### Срез 23 (2026-08-21): `nohup … & disown` не переживает конец Claude-сессии на Windows — перезапуск через `schtasks`

Новая сессия застала процесс среза 21 **мёртвым**: `wmic`/`Get-CimInstance`
не находят ни `run_corpus.py`, ни одного `lumen.exe`, порты свободны
(`port_guard.py --report` — все семь). При этом `.tmp/wpt-corpus/*.log` и
`*.raw.jsonl` шарда `html/canvas/offscreen/text` дописывались до 04:38:56 —
буквально за минуты до старта этой сессии, лог обрывается посреди
`TEST_START` без единой строки об ошибке (не краш, а внешнее убийство).
`state.json`: 341 из 465 шардов учтены (300 `ran`, 41 `signalled`).

**Вывод: `nohup <cmd> & disown` в git-bash на Windows не даёт настоящей
независимости от родительского процесса.** Срез 21 полагался на этот приём
именно потому, что процесс пережил несколько смен сессий подряд (несколько
часов между 00:48 и 04:38) — то есть приём работал долго, но не абсолютно:
как только Claude-сессия, из-под которой был запущен `nohup`-процесс,
закрылась (конец предыдущего хода), процесс погиб вместе с ней. Похоже на
Windows Job Object с `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, который
терминал/харнесс вешает на всё дерево процессов сессии: `disown` отвязывает
процесс от job control самого bash, но не от Job Object, если ОС всё равно
считает его потомком того же дерева. Для задач короче одной сессии это не
проявляется (потому что сессия жива, пока команда не отработает) — риск
чисто для многочасовых фоновых прогонов, переживающих конец хода.

**Починка на этот раз — `schtasks /Create ... /SC ONCE`.** Задача Планировщика
запускается службой `Task Scheduler`, которая физически не является потомком
ни bash, ни Claude Code, поэтому не входит ни в один Job Object сессии.
`.bat`-обёртка (`.tmp/resume_wpt_run5.bat`, не коммитится — рядом с
чекпойнтами) делает `cd /d`, `set LUMEN_PROFILE=dev-release` и вызывает тот же
`--resume` (тот же бинарь `e6d5e73c5`, чтобы не портить сравнимость уже
набранных вердиктов), лог — `.tmp/wpt-corpus/resume_srez22.log`. Проверено:
через ~2 минуты после `/ST` в процессах появились 6 `lumen.exe` и воркеры
`wptrunner`, лог показывает корректный резюм («cached» для всех 341 уже
учтённых шардов, затем реальный старт `[250/465] html/canvas/offscreen/text:
254 ids` — ровно то, на чём умер прошлый процесс).

**Правило для любого будущего многочасового фонового прогона на Windows:**
не полагаться на `nohup`/`disown` как на способ пережить конец сессии — он
работает по наблюдению много часов, но не гарантированно и не документирован
как такой. Использовать `schtasks /Create /SC ONCE /ST <through +1..2 min>`
(или `wmic process call create`, если нужен полностью detached процесс без
задержки) — оба физически вне дерева процессов сессии. Стоит добавить в
[`docs/automation.md`](../automation.md), если приём понадобится ещё раз вне
этой дорожки.

**Следующая сессия:** тот же протокол среза 21 — проверить живость (`Get-CimInstance
Win32_Process | Where-Object { $_.CommandLine -match 'run_corpus' }` работает
надёжнее, чем `wmic`, у которого кириллица в выводе бьётся кодировкой) и не
запускать второй экземпляр. Задача Планировщика называется
`LumenWptRun5Resume` — `schtasks //Query //TN LumenWptRun5Resume //V` покажет
код завершения, когда прогон закончится.

### Срез 26 (2026-08-21 05:10): вторая машина не добавила охвата — но доказала, что цифра не зависит от платформы

**Обстановка.** Linux-половина жива (PID 143091, 12 ч 54 мин, 375 из 479 шардов
в `state.json`), Windows-половина идёт своим `--resume` среза 21/23 и на
04:56 отдала чекпойнт в 345 шардов. Живой `--out-dir` не трогали:
`--aggregate-only` с *другим* `--run-json` (`.tmp/slice26-linux.json`) — путь,
проверенный срезом 23, — дал текущую Linux-цифру **16.66 %** (9 268 из 55 614
id, 169 из 266 категорий, исполнено 94.9 % знаменателя, ноль
`shard-produced-nothing`, ноль `unexplained`).

**Головные цифры по-прежнему сравнивать нельзя, и теперь видно, во что это
обходится.** У чекпойнта Windows headline 14.80 %, но исполнено лишь 79.5 %
знаменателя, а нулевое ведро несёт `shard-killed` 6 848, `unexplained` 1 870
(из них `html` 1 807), `shard-produced-nothing` 168 и **2 889 id, потерянных
внутри шардов, отчитавшихся успехом**. У Linux-половины эти три ведра пусты.
То есть разрыв 16.66 / 14.80 — это разница в охвате и потерях, а не в
поведении движка, и публиковать надо Linux-половину, а Windows-половину
использовать как сверку.

**Сверка нужна честная, а её нечем было снять.** `--compare` печатал «на общем
охвате: left 17.98 %, right 18.61 %», но общий охват — это категории, которые
обе половины *затронули*, а не прошли на одну глубину: `html` там стоит 9 715
исполненных id против 6 009. Такой разрыв на категории — снова охват, и
«per-executed-id 0.173 против 0.143» ничего про платформу не говорит. Поэтому
в `score_audit.py::compare_snapshots` добавлен блок **like-for-like** —
только те категории, где `ran` совпал у обеих сторон: единственная выборка, в
которой расхождение балла не может быть охватом.

**Результат like-for-like: 98 категорий, 2 523 исполненных id, left 306.2
против right 307.2 — дельта −0.040 п.п.** Расходятся ровно две категории, и
ни одна не про платформу:

* `console` — 1.75 против 2.75 (Windows: +1 `harness_ok`, +1 сабтест из +1
  добавившегося). На Linux единственный не-worker тест категории с нулём
  сабтестов — `/console/console-log-large-array.any.html`, и он несёт
  `TestRunner hit external timeout (this may indicate a hang)`, а в исходнике
  объявлен ровно один `test()`. Отчёта Windows на этой машине нет, так что
  это вывод из счётчиков, а не прямой diff, но сходится он однозначно:
  расхождение стоит 1.00 балла и создано таймаутом тяжёлого теста, то есть
  скоростью/загрузкой машины.
* `input-events` — `harness_ok` 28 против 25 при **одинаковых** `score` (0.62),
  `subtests_passed` (120) и `subtests_total` (1 749). Полезная сторона: дрейф
  статуса гарнесса на трёх тестах в цифру не протекает.

**Вторая машина не купила охвата.** Множество категорий Windows-половины —
строгое подмножество Linux-половины (категорий, до которых дошла только
Windows: **0**), исполнить больше id она смогла ровно в одной категории
(`WebCryptoAPI`, 313 против 129 — это шард, убитый по бюджету на Linux).
Отсюда fused-цифра 16.67 % против 16.66 % у одной Linux-половины: слияние
добавляет один балл. Причина структурная, а не случайная: обе половины
запущены одним и тем же `--all`, то есть идут по одному и тому же порядку
шардов, и вторая машина даёт не параллельный охват, а повтор. Что она
действительно дала — независимую сверку: 97 категорий из 132 общих совпали во
всех счётчиках, а на равной глубине расхождение 0.04 п.п.

**Практический вывод для закрывающей сессии.** Публиковать Linux-половину как
вторую полную цифру; Windows-половину — как строку сверки (like-for-like
дельта, а не headline). Если охват двух машин когда-нибудь понадобится
складывать по-настоящему, половинам нужно раздать **непересекающиеся списки
категорий** (`--categories`), иначе вторая машина стоит своего времени только
как контроль.

**Инструмент.** `score_audit.py --compare` печатает теперь строку
`like-for-like (same ran on both sides): N categories, M executed ids — left …,
right …, delta ±X pp`, список расходящихся на равной глубине категорий и
`of them reached only by it: K` рядом с числом категорий, взятых слиянием у
второй стороны. `--selftest` вырос на пять проверок: блок берёт только
равноглубокие категории, суммирует их исполненные id, считает дельту на
исполненный id, называет расхождение и отдельно — категорию, до которой дошла
только вторая сторона.
