# WEBCRYPTO-CURVES — срезы

Сейчас `crates/js/src/subtle_crypto.rs` (2637 строк) знает только P-256: `KeyMaterial` хранит `p256::ecdsa::SigningKey` и пр., `ECDSA` подписывает всегда SHA-256 (параметр `hash` игнорируется, `sign_data` `:1227`), `generate_key` для пары жёстко пишет usages `["sign"]`/`["verify"]` (`:285`, `:293`). Остальные кривые дают `err:NotSupportedError`. Крейты `p384 0.13.1`, `p521 0.13.3`, `ed25519-dalek 2.2.0`, `x25519-dalek 2.0.1` уже в `Cargo.lock` (тянет `crates/network`, зависимости на уровне `crates/network/Cargo.toml:35-71`), то есть в `lumen-js` добавляются без новых записей в lock-файле; commit-body обязан содержать `**Why this dependency:**` (ADR-027), формулировка — как у `p256` в `crates/js/Cargo.toml:66-69` (Permanent, crypto exception #3, та же семья RustCrypto, граф уже в дереве).

Цифры потолка — из `docs/wpt-vendor-notes/WebCryptoAPI.md` (кластер C1) и `tests/wpt/metadata/WebCryptoAPI/**.ini` (число ожидаемых FAIL: `generateKey/successes_ECDSA` 54, `successes_ECDH` 72, `successes_Ed25519` 36, `successes_X25519` 32, `ec_importKey` 264, `okp_importKey_Ed25519` 72, `okp_importKey_X25519` 54, `sign_verify/ecdsa` 289, `eddsa_curve25519` 19, `eddsa_small_order_points` 14, `ecdh_bits` 32, `ecdh_keys` 25, `cfrg_curves_bits_curve25519` 17, `cfrg_curves_keys_curve25519` 15, `getPublicKey.tentative` 74). Часть этих FAIL ещё держат BUG-1734 (форма `CryptoKey`) и BUG-1736 (нормализация, порядок ошибок) — поэтому критерии готовности сформулированы как «нет `NotSupportedError`» + unit-тесты на векторах, а не как точное число PASS. Исполнитель записывает в сообщение коммита фактические «было/стало» по каждому префиксу.

**Решения, принятые планировщиком.** (1) Ключи EC хранятся как сырые байты (`curve`, `d: Option<Vec<u8>>`, `point` — несжатая SEC1-точка) и пересобираются в типы крейта на каждой операции; один макрос `ec_curve!(p256|p384|p521)` порождает единый набор функций — так три кривые не множат код. (2) Для X25519 и Ed25519 spki/pkcs8 кодируются константными префиксами DER (RFC 8410: `302a300506032b6570032100`+32 байта и `302e020100300506032b657004220420`+32 байта для Ed25519, OID `2b656e` вместо `2b6570` для X25519), крейты `pkcs8`/`spki` для OKP не подключаются. (3) Ed448/X448 в срезы НЕ входят: единственный стабильный `ed448-goldilocks 0.9.0` содержит только арифметику кривой и Decaf (нет подписи Ed448, нет X448), а `0.14.0-pre.15` — предрелиз на digest 0.11, несовместимом с `sha2 0.10`/`rsa 0.9` стека; собственную реализацию без решения пользователя не писать. Остаток — отдельная строка ROADMAP `WEBCRYPTO-CURVES-448` с этой причиной (потолок: `successes_Ed448` 36, `successes_X448` 32, `okp_importKey_Ed448/X448` 72+54, `eddsa_curve448` 19, `cfrg_curves_*_curve448` 30 FAIL, `getPublicKey` — по 2 сабтеста).

Общий порядок работы в каждом срезе: перед началом `git log --oneline -n 10 -- crates/js/src/shim/crypto_shim.js crates/js/src/subtle_crypto.rs` и прочитать актуальный контракт шима с Rust (BUG-1736/1734/1739 переписывают нормализацию алгоритма и форму `CryptoKey` параллельно): если алгоритм приходит уже нормализованным (каноничное имя, `hash` строкой), использовать это; пока `hash` может быть и строкой, и `{name}`, читать его через общий помощник `hash_name(alg_json)` (создаётся в S2, до этого — только P-256 без hash). Unit-тесты запускать `cargo test -p lumen-js --lib subtle_` (модуль собирается под `cfg(test)` и без V8).

## WEBCRYPTO-CURVES-S1: EC-слой на три кривые (generate/import/export)
- **Точка входа:** `crates/js/src/subtle_crypto.rs:57-89` (варианты `KeyMaterial`), `generate_key` `:239` (ветки `"ECDSA"` `:266`, `"ECDH"` `:403`), `import_key` `:445` (ветки `:481`, `:859`), `export_key` `:982` (ветки `:1022-1060`, `:1117-1150`), `sign_data` `:1227`, `verify_signature` `:1355`, `ecdh_derive_bits` `:1749`; зависимости — `crates/js/Cargo.toml:66-69`.
- **Сделать:** (a) в `Cargo.toml` добавить `p384 = { version = "0.13", features = ["ecdsa","pkcs8","ecdh"] }` и `p521` с теми же features (версии те же, что в `crates/network`; для p521 при необходимости ещё `arithmetic`) с комментарием `Permanent … Why this dependency`. (b) Новый файл `crates/js/src/subtle_ec.rs` (`mod` в `lib.rs` рядом с `:68`, под тем же `cfg(any(feature="v8-backend", test))`): `enum EcCurve {P256,P384,P521}` с `name()`/`from_name()`/`field_len()` (32/48/66), структура `EcKey {curve, d: Option<Vec<u8>>, point: Vec<u8>}`, макрос, порождающий для каждой кривой: `generate() -> EcKey` (случайный скаляр через `getrandom`, как сейчас `:274`), `public_from_d`, `validate_point` (отклонять точки вне кривой и бесконечность), `spki_encode/decode`, `pkcs8_encode/decode`, и функции JWK (`x`,`y`,`d` — base64url фиксированной длины поля, `crv`). (c) Заменить 4 варианта `KeyMaterial` на `Ec(EcKey)` + признак назначения (`EcPurpose::Ecdsa|Ecdh`) для `algorithm_json`; перенести ветки generate/import/export на `subtle_ec`, убрав `if curve != "P-256" { NotSupportedError }`. Неизвестная кривая — по-прежнему `err:NotSupportedError`. (d) `generate_key` для пары: usages приватного ключа = пересечение запрошенных с допустимыми (`sign` для ECDSA; `deriveKey`/`deriveBits` для ECDH), публичного = `verify` для ECDSA и `[]` для ECDH; сейчас пишется константа. (e) `sign_data`/`verify_signature`/`ecdh_derive_bits` — только переписать на `KeyMaterial::Ec` с поведением P-256 как было (сигнатуры `fn` не менять; расширение — в S2).
- **Не трогать:** RSA/AES/HMAC-ветки, `crypto_shim.js`, нормализацию алгоритма (BUG-1736), форму `CryptoKey` (BUG-1734).
- **Готово, когда:** ≥ 12 новых unit-тестов в `subtle_ec` (для каждой из 3 кривых: generate → export `raw`/`spki`/`pkcs8`/`jwk` → import → export совпадает побайтно; импорт точки вне кривой и `raw` неверной длины → ошибка `DataError`); известный `spki` P-256 из `tests/wpt/WebCryptoAPI/derive_bits_keys/ecdh_bits.js:14` импортируется и экспортируется в те же байты, для P-384 и P-521 — `:15`, `:13`; все прежние тесты `subtle_crypto::tests` зелёные. WPT: `run_corpus.py --prefixes WebCryptoAPI/generateKey/successes_ECDSA WebCryptoAPI/generateKey/successes_ECDH WebCryptoAPI/import_export/ec_importKey` — у сабтестов с `P-384`/`P-521` в названии исчезает `NotSupportedError`; число PASS по трём префиксам записать в коммит.
- **Гейт:** `cargo clippy -p lumen-js --all-targets -- -D warnings`; `cargo test -p lumen-js --lib subtle_`; WPT-команда выше (dev-release, `--features v8-backend`).
- **Зависит от:** BUG-1736 (исходная зависимость задачи; на сами правки не влияет, но шим меняется там же).

## WEBCRYPTO-CURVES-S2: ECDSA с hash и ECDH на трёх кривых
- **Точка входа:** `sign_data` `crates/js/src/subtle_crypto.rs:1196` (ветка `KeyMaterial::Ec`), `verify_signature` `:1317`, `ecdh_derive_bits` `:1749`, `derive_bits` `:1915` (ветка `"ECDH"` `:1922`), `crypto_shim.js:255-288` (`deriveBits`: для ECDH сейчас `length || 256`, из-за чего `null` даёт 256 бит вместо полного секрета), `crypto_shim.js:153-184` (`sign`/`verify`).
- **Сделать:** (a) помощник `hash_name(alg_json) -> Option<&str>`, понимающий `"hash":"SHA-256"` и `"hash":{"name":"SHA-256"}`; ECDSA: `digest = sha1|sha2::<H>(data)` для SHA-1/256/384/512, дополнить нулями слева до `field_len` кривой (`ecdsa 0.16` отклоняет prehash короче половины поля — SHA-1 при P-521 — а дополнение нулями даёт то же целое по SEC1 §4.1.3) и подписать через `signature::hazmat::PrehashSigner` / проверить через `PrehashVerifier` (в `p521 0.13.3` оба реализованы, `src/ecdsa.rs:132`); подпись — P1363 `r||s` длиной `2*field_len`; `verify` с подписью неверной длины → `false`, без паники. (b) ECDH: общий секрет — X-координата длиной `field_len`; `length` в битах: `null`/отсутствует = весь секрет, `length > 8*field_len` → `OperationError`, `length` не кратная 8 → первые `ceil(length/8)` байт со старшими `length%8` битами последнего байта (остальные обнулить). Ключи разных кривых (`namedCurve`) → `InvalidAccessError` (`err:InvalidAccessError`), как сейчас обрабатываются коды `err:` в `_dom_err` (`crypto_shim.js:58`). (c) шим: ECDH-ветка `deriveBits` передаёт `length` как есть (`null` → 0 → «весь секрет»); добавить в `deriveKey` расчёт длины для ECDH → AES (`derivedKeyAlgorithm.length`) и HMAC (по hash; по умолчанию длина блока).
- **Не трогать:** RSA, HKDF/PBKDF2 (`hmac_hash` `:1793` — это срез SYM-S3), Ed25519.
- **Готово, когда:** unit-тесты на векторах `tests/wpt/WebCryptoAPI/sign_verify/ecdsa_vectors.js` (по одному вектору verify на кривую × hash, включая SHA-1 для P-521 и «подпись с изменённым байтом → false») и `derive_bits_keys/ecdh_bits.js` (P-256/384/521, известный секрет, `length` 8·k и нецелый байт); `run_corpus.py --prefixes WebCryptoAPI/sign_verify/ecdsa WebCryptoAPI/derive_bits_keys/ecdh_bits WebCryptoAPI/derive_bits_keys/ecdh_keys` — в отчёте нет `NotSupportedError` и нет «Signature verified expected true got false»; число PASS записать в коммит.
- **Гейт:** `cargo clippy -p lumen-js --all-targets -- -D warnings`; `cargo test -p lumen-js --lib subtle_`; WPT-команда выше.
- **Зависит от:** WEBCRYPTO-CURVES-S1.
