# Как измерять конформность подсистемы до и после замены на готовую библиотеку

Дорожка `LIB` ([ADR-027](decisions/ADR-027-own-vs-vendored-boundary.md)) заменяет
три подсистемы внешними крейтами. Этот файл отвечает на один вопрос: **чем
доказать, что стало лучше** — и, что важнее, что именно измерено, а что нет.
Числа конкретных прогонов лежат в `docs/conformance/<дата>.md`, здесь — метод.

Тот же принцип, что в [`perf-method.md`](perf-method.md): перепись «до» делается
**до** правки, гейт — счётчик, а не впечатление.

---

## 1. Правило приёмки

Замена принимается, только если выполнены оба условия:

1. **цифра выросла** — доля пройденного по разделу 3 строго больше, чем «до»;
2. **ни один эталон не сдвинулся необъяснённо** — расхождения графтестов
   разобраны поимённо и каждое либо ожидаемо, либо заведено багом.

Если цифра не выросла — замена откатывается, а в задаче записывается, почему
ожидание не подтвердилось. «Библиотека полнее» — это гипотеза, а не результат.

## 2. Знаменатель

Урок [`wpt/pass-rate.md`](wpt/pass-rate.md): доля бессмысленна, пока не назван
знаменатель, и «сколько файлов на диске» ошибается сразу в обе стороны.

Для этой дорожки знаменатель фиксируется так:

| Подсистема | Знаменатель | Откуда |
|---|---|---|
| URL | все записи `urltestdata.json`, кроме помеченных как относящиеся к API-сеттерам, которых у нас нет | `tests/wpt/url/resources/urltestdata.json` (уже вендорено) |
| Текст | число проверок на странице-пробе (раздел 3.2), каждая — независимый бинарный признак | сама проба |
| SVG | то же для страницы-пробы SVG (раздел 3.3) | сама проба |

Знаменатель фиксируется **один раз**, в `LIB-0`, и не меняется между «до» и
«после». Иначе сравнивать нечего.

## 3. Что и чем меряется

### 3.1 URL

Прогнать `lumen_core::url::Url::parse`/`resolve` по официальному корпусу и
сравнить `scheme`/`host`/`port`/`path`/`query`/`fragment` с ожидаемыми.

Записать: сколько записей прошло, сколько провалилось, и **распределение
провалов по причинам** — процент-энкодинг, IDN, схемы без хоста, `..`-сегменты,
пустой query. Без разбивки цифра не отвечает на вопрос «чинить точечно или
заменять».

### 3.2 Текст

Страница-проба со следующими независимыми проверками, каждая — своя строка:

- лигатура `fi`/`ffi` в шрифте, где она есть;
- кернинг пары `AV`/`To`;
- **комбинирующая диакритика** — `e` + U+0301 против готовой `é` (это GPOS 4,
  которого у своего шейпера нет: две формы обязаны совпасть по ширине и по виду);
- вьетнамский (два диакритических знака на одной букве);
- арабское соединение (изолированная, начальная, срединная, конечная формы);
- деванагари (переупорядочение гласного знака);
- иврит с огласовками;
- RTL-строка со смешанными числами.

Снять скриншот и `--dump-display-list`. **Список команд отрисовки — основное
свидетельство**, скриншот вторичен: он не отличает «глиф не тот» от «глиф не на
том месте», а дамп отличает.

### 3.3 SVG

Страница-проба, где каждый элемент проверяется отдельно и *виден* по отдельности:

- линейный градиент в `fill`, радиальный в `fill`;
- градиент через `url(#…)` на `stroke`;
- `clipPath`, `mask`;
- `filter` с `feGaussianBlur`;
- `pattern`;
- `marker` на концах пути;
- `<image>` внутри SVG;
- контрольная фигура без всего перечисленного (доказывает, что проба вообще
  отрисовалась).

Прогнать **дважды**: как inline-SVG в разметке и как внешний файл через
`<img src=*.svg>` — это два разных пути в движке (второй идёт через
`lumen_image::is_svg` + `shell/svg_image.rs`), и заменяются они разными задачами.

## 4. Ловушки, стоившие времени в этом репозитории

- **Скриншот на Windows и на Linux несравним.** Эталоны `dump-golden/`
  сняты на Windows; на Linux шесть из двенадцати проверок расходятся на
  неизменённом `main` из-за метрик шрифта. Сравнивать «до/после» можно только
  на одной машине, и лучше по дампам, а не по пикселям.
- **Замена шейпера сдвигает эталоны, и это не регресс.** Три независимых
  набора: `graphic_tests/` (gdigrab), `graphic_tests/snapshots/cpu/` (PNG),
  `crates/engine/paint/tests/snapshots/*.snap` (текстовые списки команд).
  Пересъёмка — отдельная задача `LIB-2`, в том же коммите, иначе гейт красный
  у следующей роли.
- **Любое переключение фокуса ОС во время прогона графтестов портит все
  последующие снимки** — `gdigrab` снимает весь рабочий стол. Стена
  одновременных FAIL с большим diff — почти всегда это, а не движок.
- **Проба не должна называть то, что сама определяет.** Страница, которая
  проверяет градиент, не должна для этого использовать `clipPath` — иначе
  провал одного пункта скроет другой.
- **Контрольный пункт обязателен.** Без фигуры, которая обязана отрисоваться
  при любом состоянии движка, «ничего не видно» неотличимо от «страница не
  загрузилась».
- **Каждый headless/MCP путь снимка рисует текст ТОЛЬКО bundled Inter,
  независимо от `font-family` в CSS — системные шрифты в снимке не участвуют
  вообще.** Обнаружено 2026-08-31 при LIB-0: страница с `font-family: Tahoma`
  (или Segoe UI / Nirmala UI / Arial Unicode MS) для арабского/иврита/
  деванагари даёт на снимке сплошной `.notdef`-«тофу», хотя `SystemFontIndex`
  находит шрифт (174 семейства в индексе на тестовой машине) и его `cmap`
  парсится верно (`lumen_font::cmap::Cmap::glyph_index` для Tahoma:
  U+0639→969, U+05E9→697 — проверено юнит-пробой поверх `lumen-font` напрямую,
  минуя рендер). Причина — не в шейпере и не в `cmap`, а в том, что
  ВСЕ пути получения PNG строят `Renderer::new_headless(INTER_FONT.to_vec(), …)`
  (`crates/driver/src/winit_session.rs::screenshot`, тот же приём в
  `crates/engine/paint/src/cpu_raster.rs`) — по конструктору у рендерера нет
  `FontProvider` вообще, поэтому codepoint-cascade (§3.1 `pick_face_for_codepoint`)
  видит только Inter. Это тот же класс, что и уже задокументированный BUG-221
  (CPU-путь не при паритете с окном), но конкретно для текста он покрывает и
  `--screenshot`, и `--dump-display-list`-рендер (сам дамп текста ОК — там
  просто нет глифов), и MCP/BiDi `resource://screenshot` живого окна тоже
  (тот же `WinitSession::screenshot`) — то есть НИ ОДИН автоматизируемый путь
  снимка не подтверждает и не опровергает работу шейпинга нелатинских
  скриптов. Единственный путь с реальным GPU-рендером и `SystemFontIndex` —
  видимое окно, снятое `gdigrab` (как `graphic_tests/run.py`), либо ручной
  просмотр глазами. **Последствие для §3.2:** проверки 05–08 (Arabic/
  Devanagari/Hebrew/RTL) нельзя закрыть числом через `--screenshot`/MCP — в
  переписи они помечаются «не проверено доступным инструментарием», а не
  FAIL; заводить как FAIL по снимку — значит измерять BUG-221, а не шейпер.
- **Живое окно + `gdigrab` НЕ закрывает дыру предыдущего пункта для
  `lumen_font`'s переключаемого шейпера — это отдельная, несвязанная
  находка.** Обнаружено на повторном замере LIB-2→LIB-3
  (`docs/conformance/2026-08-31-post-lib2.md`): обычное окно рисует текст
  через `crates/engine/paint/src/varied_text.rs`'s путь в бэкенд femtovg,
  который использует femtovg's СОБСТВЕННЫЙ встроенный `rustybuzz`
  (безусловная зависимость femtovg, не связанная с `LUMEN_OWN_TEXT_SHAPING`)
  — `lumen_font::active_text_shaper()` живым окном не вызывается вообще.
  Доказано напрямую: тот же пробник, снятый `gdigrab` дважды (дефолтный
  rustybuzz vs форсированный `LUMEN_OWN_TEXT_SHAPING=1`), даёт побайтово
  идентичные PNG. **Единственный путь, где переключение флага действительно
  меняет пиксели — headless `--screenshot`/`WinitSession::screenshot`**
  (`Renderer::new_headless` → `cpu_raster.rs` → `active_text_shaper()`), тот
  самый путь без `SystemFontIndex` из предыдущего пункта. Значит для
  нелатиницы (05–08) чистого замера ИМЕННО НАШЕГО шейпера сейчас нет вообще
  ни одним доступным путём — либо чинить `FontProvider` в headless-раст-пути,
  либо принимать только точечные юнит-тесты на сырых шрифтах (как сделал
  LIB-1) как единственное свидетельство.

## 5. Куда писать результат

`docs/conformance/<ГГГГ-ММ-ДД>.md` — одна таблица на подсистему: знаменатель,
пройдено, доля, разбивка провалов по причинам, версия движка (`git rev-parse
--short HEAD`) и машина. Файл «до» не переписывается никогда: он база для всех
последующих сравнений.
