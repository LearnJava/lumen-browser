# Live engine gaps a probe will walk into

**Read this before writing a probe.** These are open defects, not history: a probe that depends on one of them measures the bug instead of its subject, and a page that goes silent because of one reads exactly like a page whose feature you were testing does not work.

Scope and lifecycle:

- The authoritative list of defects is [`BUGS.md`](../BUGS.md); this page is the subset that **changes how you write a probe**, phrased as "do this instead".
- A line dies here when its bug moves to `BUGS-FIXED.md` — delete it, do not annotate it as fixed.
- Method (what counts as evidence, how to launch a probe, how to read a WPT failure) — [`probe-method.md`](probe-method.md). Engine-side implementation traps — `subsystems/<crate>.md`.

Moved out of `CLAUDE.md` on 2026-09-03: the list is only relevant to probe/triage work, and it was being loaded in full at the start of every session regardless of the task.

## Harness limits — the probe cannot see what you think it sees

- **`fetch()`/`XMLHttpRequest` do nothing in the headless dump modes and on a `file://` page** — the runtime is handed `fetch_provider = None` and answers `false` without logging, so the failure is indistinguishable from a blocked request. A probe that needs real network must drive a live window (`--mcp-live-port`) and be served over http from the same origin.
- **A `file://` URL passed as the initial CLI page argument does not load** ([BUG-651](../bugs/BUG-651-OPEN.md)) — `PageSource::from_arg` never strips the scheme (the sibling used by JS/BiDi navigation does). Start on `about:blank` and navigate.
- **`AutomationCommand::Screenshot` (`resource://screenshot` over `--mcp-live-port`) cannot see ANY per-frame overlay.** `render_current_page_to_png` rasterizes `self.display_list`, but the caret bar, spellcheck squiggles, validation tooltips and the DS-15 anonymous-profile border are built fresh every frame as local `page_buf`/`anim_dl`/`overlay_buf` values inside `on_redraw_requested` and handed straight to `r.render(…)` — never written back into `self.display_list`. Measured on the page's own already-shipped `<input>` caret (FRAME-7 slice 1): click + `type` through MCP updates the value, but the automation screenshot shows no caret at all. A probe needing to *see* one of these overlays has no automation surface today — the absence is not evidence that the overlay is missing.
- **A headless dump mode is a good JS probe harness, but only for synchronous script** — `lumen --dump-layout <page>` runs the page's scripts and `console.log` lands on stderr prefixed `[JS] `, which makes it the cheapest way to read a DOM-level result without a window. What it will not give you is anything behind a timer: a `setTimeout(…, 0)` callback simply never logs, because the one-shot run finishes first. Silent, so an absent line reads as «the API returned nothing» rather than «the callback never ran» — measured 2026-09-09 while probing [BUG-982](../bugs/BUG-982-FIXED.md). Anything asynchronous needs a live window.
- **A spacer that paints nothing gives the page no scroll** — `content_height` comes from the display list, so `<div style="height:4000px">` leaves `max_scroll()` at 0 and `scrollTo` genuinely does nothing. Give it a background.

## Events and dispatch

- **There is no `navigation` global at all** — `'onnavigate' in navigation` and every other Navigation API feature-detect throws `ReferenceError` before it even gets to answer `false` ([BUG-881](../bugs/BUG-881-OPEN.md)). `'onX' in Y` on `window`/`document` is reliable again since 2026-09-12 ([BUG-874](../bugs/BUG-874-FIXED.md)). Event propagation itself is no longer a gap — the full capture/target/bubble path with `window` as the last hop landed 2026-09-10 ([BUG-873](../bugs/BUG-873-FIXED.md)), and so did `composedPath()` ([BUG-577](../bugs/BUG-577-FIXED.md)); what a probe should still not expect is shadow-tree retargeting, which is unmodelled, so a path crossing a shadow boundary lists the real nodes.
- **`window.postMessage` accepts only the legacy string `targetOrigin`** — `'*'`, the exact origin and `'/'` work; both dictionary forms, the one-argument form and a trailing slash drop the message silently ([BUG-717](../bugs/BUG-717-OPEN.md)). The cheapest way to sequence a probe page therefore needs the literal `'*'`.

## Navigation, frames and documents

- **`window.open()` and `<a target=_blank>` replace the *calling* document** ([BUG-883](../bugs/BUG-883-OPEN.md)) — the opener's timers never fire again.
- **A frame inserted after the shell's single sub-document pass** (from a `load` handler, a timer, rAF), or a `src` assigned to an already-inserted frame, produces no request at all ([BUG-885](../bugs/BUG-885-FIXED.md)); a frame built by a top-level inline script loads fine. Write frames into the markup with their final URL.
- **`document.open()`/`close()` do not exist** ([BUG-888](../bugs/BUG-888-OPEN.md)); an entry made by `history.pushState(state, "")` (no URL argument) fires no `popstate` on traversal ([BUG-886](../bugs/BUG-886-OPEN.md)).
- **An `.xhtml`/`.xht`/`.svg` page still has no real XML path** — it is HTML-parsed with point-fixes, not a conforming XML parser ([BUG-786](../bugs/BUG-786-OPEN.md)/[BUG-685](../bugs/BUG-685-OPEN.md)). All three measured `<script>` shapes now work (GAP-XMLDOC срезы 1/2/5): CDATA-wrapped inline bodies, a self-closing `<script src="…"/>`, and a prefixed `<h:script src>` (namespace resolved, request fires). The tokenizer's RAWTEXT/RCDATA state was also namespace-blind (срез 12) — fixed. A foreign `<script>` now also tracks HTML LS §13.2.6.5 execution eligibility: it runs only if closed by a literal `</script>` end tag while it was still the current node, or by a self-closing start tag (which also now resolves SVG's `href`/`xlink:href` as the external source, not just `src`) — anything else (an ancestor's end tag implicitly popping it, a foreign-content breakout tag) leaves its parsed text in the tree but never executes it (GAP-XMLDOC срез 13, BUG-685). `tests/wpt/html/syntax/parsing/unclosed-svg-script.html` is now fully green (5/5 subtests, `.ini` expectations removed). `parse_fragment` (the `Element.innerHTML=` entry point) now also honours a real §13.4 context element — `parse_fragment_with_context`, GAP-XMLDOC срез 14 — so CDATA sections (a mechanism that didn't exist in the tokenizer at all before this срез) are namespace-correctly allowed/disallowed, and a bare `</p>`/`</br>` breakout end tag with nothing open to close still exits foreign content like its start-tag counterpart (`cdata-in-integration-point-fragment.html` and `html_content_in_foreign_context.html` are both fully green now). `PushTokenizer` (the real network/streaming path, `IncrementalTreeBuilder::feed`/`feed_bytes`) now also arms `cdata_allowed` per-token, mirroring pull's `run_pull` (GAP-XMLDOC срез 15, BUG-685) — `<svg>`/`<math>` opening and its CDATA section can arrive over the wire in arbitrary chunk boundaries, including a chunk boundary landing right after a bare `>` inside the section's content (before the real `]]>` terminator), and still match what `parse` (pull) would build. Self-closing `<table>`/`<select>`/`<button>` in `xml_mode` also work now (GAP-XMLDOC срез 16, BUG-786) — those three were the only non-RAWTEXT `mode_in_body` start-tag arms still pushing straight onto `open_elements` without threading `self_closing` through `push_open_element`, a live defect (self-closing `<table/>` nested forever) rather than the "unmeasured, 0 corpus hits" status срез 11 had recorded it as. Self-closing `<a>`, the §13.2.4.3 formatting elements (b/big/code/em/font/i/s/small/strike/strong/tt/u) and `<nobr>` in `xml_mode` also work now (GAP-XMLDOC срез 17, BUG-786) — the same push-site class, now fully closed across `mode_in_body`. `push_active_formatting` was left untouched on purpose: a self-closed formatting element still sits on the active formatting list afterwards, so trailing content that triggers `reconstruct_active_formatting` (more formatting starts, text) still wraps a *new* clone around it, exactly as an implicitly (not explicitly) closed formatting element would per spec — that reconstruction is correct behavior, not a residual bug. Self-closing `<th>`/`<td>` in `xml_mode` also work now (GAP-XMLDOC срез 18, BUG-786) — `mode_in_row`'s cell arm had the same push-straight-onto-`open_elements`, ignore-`self_closing` shape, measured live on `css/CSS2/syntax/colors-006-ref.xht` (32 self-closing `<td/>`, a reftest reference fixture whose table rendering broke on nested cells). Self-closing `<caption>`/`<colgroup>`/`<tbody>`/`<thead>`/`<tfoot>`/`<tr>` in `xml_mode` also work now (GAP-XMLDOC срез 19, BUG-786) — the same push-site class in `mode_in_table`/`mode_in_table_body`, fixed on the strength of the same proven mechanism (not fresh corpus hits — the grep found 0 for all six tags, same as `<table>`/`<select>`/`<button>` before срез 16 proved it live). Self-closing `<option>`/`<optgroup>` in `xml_mode` also work now (GAP-XMLDOC срез 20, BUG-786) — the last unconverted push site of this class, in `mode_in_select`; also 0 corpus hits, fixed the same way. `<!DOCTYPE html [ ... ]>` (an internal subset holding a `<?PI?>` or `<!--comment-->`) also parses correctly now in `xml_mode` (GAP-XMLDOC срез 21, BUG-786) — a different class of defect, in the tokenizer's DOCTYPE state itself, not a tree-builder push site: HTML5's bogus-DOCTYPE state stops at the first `>`, which used to land inside the subset's own `<?x y?>`/`<!--x-->`, leaving `]>` as stray markup at the document root (measured on `dom/nodes/ProcessingInstruction-in-doctype.xhtml`/`Comment-in-doctype.xhtml`/`css/cssom/xml-stylesheet-pi-in-doctype.xhtml`). A leading `<?xml version="1.0"?>` declaration also no longer leaks into the tree as a visible text node (GAP-XMLDOC срез 22, BUG-786/BUG-685) — the tokenizer's tag-open-state catch-all used to hand the already-consumed `<` back as `Token::Text` and re-enter data state on `?xml...`, so every `.xhtml`/`.xht`/`.svg` document opening with the standard XML declaration (1253 corpus files, 239 testharness) surfaced stray text ahead of `<html>`; now `?` reconsumes into bogus-comment state per HTML LS §13.2.5.6, same as any real browser — not gated behind `xml_mode`, this is a generic tokenizer correction, not an XML-specific one. In `xml_mode` a `<?target data?>` with `target` other than `"xml"` is now a real `ProcessingInstruction` node (`instanceof ProcessingInstruction`, `.target`/`.data`), not a bogus comment (GAP-XMLDOC срез 23, BUG-786) — the target-"xml" case stays a bogus comment (срез 22's XML-declaration behavior). `document.createProcessingInstruction` now also exists on detached documents (`DOMImplementation.createDocument`/`createHTMLDocument`), and the PI object itself now has `cloneNode`/`getRootNode` (GAP-XMLDOC срез 25, BUG-786) — it previously only existed on the live `document` and lacked both methods entirely, unlike arena-backed Comment/Text. `DOMParser().parseFromString(...)` output still lacks `createProcessingInstruction` (a separate virtual-node system, `dom_parser.rs`, not this code path) and inserting a detached PI/Comment/Text into a live element via `appendChild` is silently a no-op rather than a real insertion ([BUG-1055](../bugs/BUG-1055-OPEN.md)) — neither is XML-specific. A `<![CDATA[` section inside an ordinary, non-foreign HTML-namespace element (e.g. `<div><![CDATA[E]]></div>`, XML §2.7) now also works in `xml_mode` (GAP-XMLDOC срез 26, BUG-786) — `cdata_sections_allowed()` used to gate real CDATA sections on the current node being foreign (SVG/MathML), correct for plain HTML5's §13.2.5.5 "cdata-in-html-content" parse error but wrong for a real XML document, where CDATA is legal wherever character data is.  `<?xml-stylesheet type="text/css" href="…"?>` now also loads and applies the referenced sheet (GAP-XMLDOC срез 27, BUG-786) — the PI parsed into a real node by срез 23 had no consumer wiring it into the cascade; `collect_link_hrefs` (`crates/shell/src/stylesheets.rs`) now also matches `target == "xml-stylesheet"`, decodes its pseudo-attributes (`type`/`href`/`media`/`alternate`) with the same XML `Name="value"` grammar as a tag attribute, and gates it through the same `text/css`/`alternate`/`media` rules as an ordinary `<link>`. Script-blocking (the WPT test's actual assertion) falls out of the pipeline's existing full-parse-before-scripts ordering for free — nothing new to implement there. A DOCTYPE internal subset's `<!ENTITY name "value">` declarations are now also expanded — `&name;` references elsewhere in the document splice in that literal replacement text (which may itself be markup, e.g. `<!ENTITY tree "<span id='x'>…</span>">`) before tokenization, matching `Element-firstElementChild-entity{.svg,-xhtml.xhtml}` (GAP-XMLDOC срез 28, BUG-786) — implemented as a textual pre-pass over the whole document string in `parse_xml_flavoured` (pull mode only; the real streaming/`PushTokenizer` path, like CDATA before срез 15 fixed it there too, does not see declared entities yet). `xml_mode` itself is now also armed on the shell's streaming/progressive-paint builder for `.xhtml`/`.xht`/`.svg` documents (GAP-XMLDOC срез 29, BUG-786/BUG-685) — before this срез, `IncrementalTreeBuilder::new_xml_flavoured()` (the constructor `parse_xml_flavoured` itself now uses) had no push-mode caller at all outside tests, so none of срезes 1–28's fixes applied to the DOM painted while an XML-flavoured page was still loading, only to the final document `parse_and_layout` rebuilds from scratch (pull, `parse_xml_flavoured`) at load completion; the streaming builder now gets the same `xml_mode` from the document's URL/path extension (Content-Type isn't known that early in the stream). Wiring this up also surfaced and fixed two `find_safe_split` bugs specific to chunked `xml_mode` input that no prior срез's tests exercised: (1) a DOCTYPE internal subset's own `<?PI?>`/`<!--comment-->` is a nested `<...>` construct the old "only check the buffer's LAST `<`" scan could miss entirely (fixed the same way срез 15 fixed CDATA's nesting — a dedicated pre-check, `last_unterminated_doctype_subset_start`); (2) the RAWTEXT/RCDATA-close branch judged a tail "safe" by byte length alone ("enough room for a `</tag>`-shaped pattern"), not by whether it was actually closed — so a still-unterminated `<?target d` sitting right after an already-complete `</style>` could satisfy the length check and get truncated at the chunk boundary instead of waiting for more bytes (now reuses `is_tag_closed`, the same real check the plain Data-state branch already used). Not covered by срез 29: entity expansion still doesn't work in this streaming builder either (same textual-pre-pass limitation срез 28 documented). That pre-pass was also lexically blind, and срез 30 (BUG-786) fixed four consequences of that in one function: it used to rewrite `&name;` inside a CDATA section (XML §2.7 — so `<![CDATA[&t;]]>` built the very element the author had escaped, undoing срез 26 on any document that also declares entities), inside a comment (XML §2.5 — and a replacement text carrying `-->` closed the comment early, landing a **live executing `<script>`** in the tree), inside a processing instruction (XML §2.6 — not harmless since срез 27 feeds `<?xml-stylesheet href=…?>` to the cascade, so the engine fetched a URL the document never literally contained) and inside the DOCTYPE's own `<!ENTITY …>` value literal (XML §4.4.7 "Bypassed"); conversely it did *not* resolve a reference nested in another entity's replacement text (XML §4.4.2), so `&a;` → `&b;` → `<b/>` stopped at literal `&b;`. Expansion now walks the input left to right, copies those four constructs verbatim, and recurses into replacement text under a depth cap of 8 plus a 100 000-expansion budget (the "billion laughs" shape is exponential in depth alone). A probe measured every case; the nine vendored corpus files that declare entities parse to byte-identical trees before and after, and none of them contains any of the four shapes. The streaming/`PushTokenizer` path now also expands declared entities (GAP-XMLDOC срез 31, BUG-786) — but only by falling back to whole-document buffering for the (rare) document that declares any: splicing an expanded replacement text into an already-tokenized prefix has no well-defined byte offset to resume the buffer drain from, so a document whose DOCTYPE declares entities cannot stream progressively any more — its DOM stays empty while loading and populates in one shot at `finish()`/EOF, same trade-off `parse_xml_flavoured` (pull) already made. A document with no declared entities (the overwhelming majority) streams exactly as срез 29 left it, at zero extra cost — the prolog scan (`PushTokenizer`'s `EntityGate`) resolves to "no entities" the moment a non-Misc, non-DOCTYPE byte is seen, typically the very first chunk. What is still genuinely unhandled: parameter entities (`<!ENTITY % …>`), an external DTD subset and `SYSTEM` entities — a missing subsystem rather than a point defect — and the underlying "no real XML parser" scope itself. A page whose XML flavour is only announced by its `Content-Type` response header, not its URL extension, now also gets `xml_mode` on any network load (GAP-XMLDOC срез 32, BUG-786/BUG-685) — both `PageSource::load_bytes`/`load_bytes_streaming` used to hardcode `RawPage.content_type` to `Some("text/html")` regardless of what the server actually sent, so `is_xml_flavoured_document`'s MIME-type branch was dead code for every network response; `svg/struct/reftests/support/html-resource-with-symbol-and-content-type-svg.html` (a `.html`-named file served as `image/svg+xml`) is the corpus fixture that exercises exactly this. `RawPage.content_type` is now an owned `Option<String>` read from the response's real `Content-Type` header via the new `page_source::response_content_type`; `File`/`Snapshot`/`Static`/`AboutBlank` sources are unaffected (no HTTP response to read). The same header now also reaches `lumen_encoding::detect`, so a charset declared only in the HTTP header (no `<meta charset>`) is picked up too — same root, not separately measured. A `<svg:svg>`/`<math:math>` element bound to its namespace by an explicit prefix (`xmlns:svg="…/2000/svg"`, `xmlns:math="…/1998/Math/MathML"`) now also resolves to the SVG/MathML namespace (GAP-XMLDOC срез 33, BUG-685) — the always-foreign check for a bare `<svg>`/`<math>` start tag compared the tag name whole, so `"svg:svg"` never matched `"svg"` and 54 corpus `.xht` files (CSS2 replaced-element reftests) plus 18 MathML crashtests rendered as inert unknown HTML elements; `foreign_content::strip_known_svg_prefix`/`strip_known_mathml_prefix` strip the one prefix each actually seen in the corpus, same hardcoded-pair boundary as `html:`/`h:` (срез 5), but — unlike that case — without forcing a namespace: the bare name is left to resolve normally, which the existing `<svg>`/`<math>`-is-always-foreign path and namespace-inheritance already handle. `mathml:`/`m:`/`xhtml:` — three more corpus-measured prefix aliases for the same two namespaces plus a third for HTML (GAP-XMLDOC срез 34, BUG-685) — same hardcoded-pair, no-resolver treatment as срез 33. An arbitrary, user-declared prefix bound to neither HTML/SVG/MathML (`xmlns:pickle="…"`) now also gets a correct `.localName` (GAP-XMLDOC срез 35, BUG-685) — `foreign_content::strip_unknown_prefix` is the generic fallback after all hardcoded pairs fail: it recovers only the local-name half of XML's `Name ::= (Prefix ':')? LocalPart` grammar, not namespace resolution (`.prefix` stays `null`, same documented limit as `web_api_shim_mid.js`'s `get prefix()`), measured on `dom/nodes/Element-firstElementChild-namespace-{xhtml.xhtml,svg.svg}` (`<pickle:dill/>.localName` used to read back `"pickle:dill"` instead of `"dill"`). Still genuinely unhandled: parameter entities (`<!ENTITY % …>`), an external DTD subset and `SYSTEM` entities — a missing subsystem, re-confirmed at 0 corpus hits across срезы 30–35; and real `xmlns:*` namespace-binding resolution into `.prefix`/`.namespaceURI` for an arbitrary prefix.

## Resource loading

- **`<img>` fires neither `load` nor `error` on any insertion path, and `img.complete` is `undefined`** ([BUG-630](../bugs/BUG-630-OPEN.md)). Never sequence a probe on an image arriving, and never read a silent `<img>` as evidence that a policy blocked it.
- **`<object data>` and `<embed src>` never fetch** ([BUG-798](../bugs/BUG-798-OPEN.md)); `<input type=image>` and SVG `<image>` fetch but fire no `load`/`error`. A probe needing a subresource should use `<link rel=stylesheet>`, `<script src>` or `fetch()`.
- **A script-side resource path is dead where the parser's works.** An `<img>` created by script (or a parser one given a new `src`) draws nothing through `drawImage` and rejects `createImageBitmap` with «image not yet decoded» — the bitmap store is filled once, by the parse pass ([BUG-938](../bugs/BUG-938-OPEN.md)); a `background-image` assigned from JS is never requested although the cascade shows it ([BUG-939](../bugs/BUG-939-OPEN.md)). Both fetch fine from markup, so a probe that builds its image or its background in JS measures this instead of its subject.
- **No outgoing request carries `Referer` or `Origin`** — not a subresource, not `fetch()`, not a same-origin POST ([BUG-859](../bugs/BUG-859-OPEN.md)), although `docs/plan/privacy.md` promises `strict-origin-when-cross-origin`.

## Media

- **Only an animated GIF decodes as a media resource**, so `canPlayType` answers `""` for mp4/webm/ogg and resource selection ends in `MEDIA_ERR_SRC_NOT_SUPPORTED` **without issuing a request at all** — the server never sees the file (`GAP-MEDIADECODE`, measured 2026-09-01). A probe that waits for `loadstart`/`loadedmetadata`/`canplay`/`play` can only hang; only the `error` half arrives.
- **An `<audio>` `src` is not resolved against the document base**, so a relative URL dies as `MEDIA_ERR_SRC_NOT_SUPPORTED` with no request on the server ([BUG-924](../bugs/BUG-924-OPEN.md)). `<audio>` and `<video>` are two different models — `<audio>` still dispatches synchronously — so run a media probe against both.
- **`<video src="">`/`<audio src="">` never fire `loadstart`** — `<video>` still fires `error`; `<audio>` fires neither event at all ([BUG-955](../bugs/BUG-955-OPEN.md)). A probe arming `loadstart` before its assertions hangs on an empty-string `src`, not just on a missing one.

## DOM / CSSOM surface that is simply absent

- **The CSSOM is read-only**: `document.styleSheets`/`<style>`/`<link>.sheet`/`CSSStyleSheet`/the `CSSRule` hierarchy exist since CSSOM-1 (2026-09-03), but `new CSSStyleSheet()` throws, `insertRule`/`deleteRule` don't exist, and `adoptedStyleSheets` is a plain expando ([BUG-897](../bugs/BUG-897-OPEN.md) / CSSOM-5). Also missing as globals: `StaticRange`, `XSLTProcessor`/`document.evaluate`, `document.forms`/`scripts`/`links`, `document.defaultView` ([BUG-622](../bugs/BUG-622-OPEN.md)). `DOMRect`/`DOMPoint`/`DOMMatrix`/`DOMQuad`/`getClientRects` shipped 2026-09-05 (GAP-GEOM).
- **A `TreeWalker`/`NodeIterator` rooted at `document` traverses nothing** — `nextNode()` returns `null` on the first call for every `whatToShow`, `SHOW_ALL` included, because the walker reads `root.__nid__` and the `document` singleton is a literal that has none ([BUG-1046](../bugs/BUG-1046-OPEN.md)). Silent, and half the object still works (`firstChild`/`nextSibling`/`lastChild` answer correctly), so `while (w.nextNode())` reads as «this document contains no such nodes». Root a probe's walker at `document.documentElement` — that path is measured good — and never read an empty document-rooted walk as evidence about the nodes.
- **An MCP `click` that misses its target now *fails*, it no longer answers `success`** ([BUG-1044](../bugs/BUG-1044-FIXED.md), 2026-09-11): when the hit test at the resolved point returns a node that is neither the target nor its descendant, `click`/`type` answer `Element click intercepted: point (x, y) hits <tag>#id (node N) instead of the target element (node M)` and dispatch nothing. A probe no longer has to assert on the event *target* to notice a miss — but it does have to expect an error where it used to read `success`, and an element that is covered (overlay, `position:absolute` sibling) is now a hard failure rather than a silent one. (The `<button>`-shaped instance — a control with no CSS width laying out zero-wide, so every click fell through to the parent — is gone since [BUG-926](../bugs/BUG-926-FIXED.md), 2026-09-10.)
- **`slotchange` never fires** — no dispatch point exists anywhere in the codebase, even though `assignedNodes()` itself now resolves correctly ([BUG-876](../bugs/BUG-876-OPEN.md)) — and `host.shadowRoot` returns a fresh wrapper per read ([BUG-877](../bugs/BUG-877-OPEN.md)).

## Networking, storage, policy

- **CSP is parsed and never enforced**, and `securitypolicyviolation` is dispatched nowhere ([BUG-811](../bugs/BUG-811-OPEN.md)) — a wait on it can only hang.
- **`new WebSocket(url)` blocks the whole document until the handshake settles** ([BUG-856](../bugs/BUG-856-OPEN.md)), and `send()` throws on anything that is neither string nor buffer ([BUG-862](../bugs/BUG-862-OPEN.md)). Open one only against a server you control.
- **`sessionStorage` has no quota**, so a `while (true)` filling it hangs the page ([BUG-870](../bugs/BUG-870-OPEN.md)).
- **A leaked IndexedDB connection stalls every later upgrade and delete on that name** — correct per spec, but it means a probe must close its connections or the next test waits forever.

## WPT-specific

- **Any element-targeted `test_driver.*` call can still die before it reaches the executor**: `testdriver-extra.js::get_context` reads `element.ownerDocument.defaultView`, which doesn't exist at all ([BUG-622](../bugs/BUG-622-OPEN.md)) — a probe using `click`/`send_keys`/`action_sequence` on an element sees "Browsing context for element was detached" from the page side, not from Lumen. `click`, `action_sequence`, `send_keys`, `delete_all_cookies` and `generate_test_report` are implemented in the executor now (WPT-RUN-12); `set_permission`/`get_computed_role`/`get_computed_label` are not ([BUG-1014](../bugs/BUG-1014-OPEN.md)) and still reject with `ActionError`.
- **`PerformanceObserver.supportedEntryTypes` lists `layout-shift` and never delivers one** ([BUG-809](../bugs/BUG-809-OPEN.md)) — the advertisement is why such tests TIMEOUT instead of failing. The list is a promise about the *type*, not about delivery: check for a call site before believing it.
