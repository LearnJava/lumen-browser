# Уроки малых движков и стратегии совместимости: Opera Presto, EdgeHTML, Firefox, Ladybird, Servo, Pale Moon, Flow

Приложение к исследованию уровня 0. В основе 30 находок (CMP-01…CMP-30), прошедших проверку фактов: 21 подтверждена, 9 исправлены (в тексте только исправленные версии), опровергнутых нет. Пометка «(не проверено)» стоит у деталей, которые исследователь привёл по памяти и проверка первоисточником не подтвердила. Дубли слиты: CMP-08 с CMP-29 (Chrome-измы и правило bug-compat), CMP-11 с CMP-30 (сервисы Google). Состояние Lumen сверено с `CAPABILITIES.md` и кодом на 2026-10-12.

## Главное в области

1. **Самый крупный и дешёвый рычаг — идентичность, а не рендеринг. Она должна быть согласованной во всех слоях.** У Firefox 52% меток issue в интервенциях — отсечение по идентификации: firefox-blocked-completely 187 и unsupported-warning 48 из 450. Крупнейшие узлы его базы знаний — «Unsupported Browser» (341 связанный отчёт) и «Unsupported browser warning» (234), тогда как ни один узел о CSS или API не набирает больше 47. Ladybird открыл современные Gmail и Google Search одной сменой UA. **У Lumen сейчас пять слоёв отвечают по-разному.** HTTP — Chrome 153, `navigator.userAgent` — `Lumen/0.5.0`, `navigator.vendor` — `Google Inc.`, `navigator.userAgentData` — «Google Chrome 114», заголовков `Sec-CH-UA` нет вовсе. Свести эти слои к одному источнику — первая и самая дешёвая задача области.
2. **Назваться Chrome — значит подписаться на совместимость с его багами.** Получив Chrome-UA, сайт сразу отдаёт Chrome-ветки кода. YouTube Music рассчитывает на `::-webkit-scrollbar`, Google Docs по номеру версии выбирает keypress-логику, GitHub в Safari работает только на «Chrome-подобном» пути. Подмена UA и bug-compat идут парой; сомнительные Chrome-измы стоит включать флагом по доменам, как делает Firefox.
3. **Совместимость — постоянная операционная служба с данными, а не проект с концом.** У Firefox 405 файлов и 423 интервенции, у WebKit 179 записей квирков. Сайты не стали тестировать ни под Presto, ни под EdgeHTML, хотя у EdgeHTML был статус браузера по умолчанию в Windows, телеметрия от 3+ млн инсайдеров и краулер Bing. Safari держится только за счёт обязательности iOS. У Lumen системы интервенций нет совсем. Её нужно заложить до широкого релиза в виде подписанного пакета данных, который обновляется вне релиза.
4. **Процент WPT насыщается и не показывает готовность, а производительность входит в совместимость.** Ladybird проходит 93,8% подтестов (Safari — 94,4%) и при этом остаётся пре-альфой: css 76% против 88% у Safari, webrtc 1%, webcodecs 0%. Pale Moon выпустил `:has()`, который встречается на 54,43% загрузок в Chrome, и через три недели выключил его из-за тормозов. KPI должен опираться на корпус реальных сайтов и сценарии с логином, а не на общий процент.
5. **Привратники переехали в инфраструктуру, а приватность сама производит поломки.** В KB Mozilla есть отдельные узлы по Akamai (36 связей), Imperva (13), OneTrust (9) и DataDome. По словам Ladybird, Cloudflare Turnstile «kept us out of a lot of sites» до мая 2026. 28% webcompat-багов Firefox, заведённых с 2023 года (1859 из 6599), вызваны защитой от трекинга. Один контакт с вендором антибота стоит сотни писем владельцам сайтов. Шимы для заблокированных трекеров и раздельный учёт поломок «движок / защита» нужны с первого дня.
6. **Отчёты пользователей сами по себе почти ничего не чинят.** Из ≈235 тыс. отчётов webcompat.com исправлено 3081 (≈1,3%), а 92,9 тыс. закрыты как invalid. Цикл замыкают самопомощь (лестница «режим совместимости → ослабить защиту → открыть в Edge/Chrome»), автодиагностика и агрегированный сигнал. Встроенный запасной Chromium (WebView2) противоречит позиционированию «приватный и прозрачный» и снимает мотивацию чинить собственный движок.

**Главная причина поломок — отсечение по UA, а не баги рендеринга (CMP-02)** · массово · критично
- Что видит пользователь / что ломается: заглушку «ваш браузер не поддерживается», урезанную выдачу Google или ответ 403. Движок справился бы со страницей, но сайт его не пускает.
- Механизм: в Bugzilla Mozilla есть компонент Web Compatibility → Knowledge Base, где отчёты сведены к корневым причинам. «Unsupported Browser» (1886128) блокирует 341 отчёт, «Unsupported browser warning» (1886129) — 234. Узел «google.com — Firefox Android doesn't receive the tier1 sent to Chrome Android» (975444) набирает 118 связей: 5 зависимостей, 9 блоков и 104 see also. Среди 194 узлов KB ни один про CSS или API не набирает больше 47; максимум у SpeechRecognition. Ladybird в январе 2026 сменил UA и этим открыл современные Google Search и Gmail. Vivaldi 10.12.2019 убрал своё имя из UA везде, кроме собственных сайтов и DuckDuckGo, Ecosia, Qwant и Startpage. Причины: WhatsApp Web не пускал браузер, Teams блокировал, Google Docs показывал предупреждение, Netflix требовал Silverlight.
- Как решают другие: Vivaldi и Brave отдают UA, неотличимый от Chrome (Brave можно опознать через `navigator.brave`). Ladybird дописывает к своему токену `Chrome/153.0.0.0 AppleWebKit/537.36 Safari/537.36` — в исходнике это макрос `SAD_COMPATIBILITY_HACK`. Servo отдаёт `Firefox/153.0`, Edge с 2015 года шлёт токены Chrome и Safari.
- Что делать нам: HTTP-слой уже совпадает с UA стабильного Chrome для Windows. Не совпадает `navigator.userAgent`: сниффер на сервере видит Chrome, а JS-сниффер — неизвестный `Lumen/0.5.0`. Именно сценарий «JS-проверка → заглушка „не поддерживается“» KB Mozilla называет главной причиной поломок. Нужно брать `navigator.userAgent` (страница и воркеры) из того же источника, что и HTTP-UA. Собственное имя показывать в About, в отчётах и на своих доменах (подход Vivaldi). Мажорную версию Chrome перевести с ручного макроса на удалённый подписанный конфиг. Отказы уже видны в статусе `SITE_REFUSED` (401/403) в `scripts/perf_audit.py --mode compat` — им удобно мерить эффект.
- Источники: https://bugzilla.mozilla.org/show_bug.cgi?id=1886128 (341 отчёт) · https://ladybird.org/newsletter/2026-01-31/ (Gmail и Search после смены UA) · https://vivaldi.com/blog/user-agent-changes/ (WhatsApp, Teams, Docs, Netflix)

**UA Client Hints: `navigator.userAgentData` вызывают на 67,65% загрузок в Chrome (CMP-05)** · массово · высокая
- Что видит пользователь / что ломается: «Chrome по UA», у которого нет `userAgentData` и `Sec-CH-UA` или они говорят другое, — противоречивый отпечаток. Скрипты аналитики и антибота понижают доверие или отдают другую ветку кода.
- Механизм: use counters Chrome (10.10.2026): `NavigatorUAData_GetHighEntropyValues` — 67,65% загрузок, `Brands` — 47,49%, `Mobile` — 34,06%. Сайты запрашивают подсказки: `Sec-CH-UA-Platform-Version` — 35,53%, `Model` — 34,65%, `Full-Version-List` — 34,14%. Firefox и Safari этот API не реализуют, поэтому у сайтов есть для них резервные ветки. Для «Chrome по UA» такой ветки нет: сайт ждёт полный Chromium-набор.
- Как решают другие: Edge, Opera и Brave отдают `Sec-CH-UA` с собственным брендом, «Chromium» и GREASE-брендом. Vivaldi собственный бренд не отдаёт: только «Chromium» и GREASE-бренд «Not A Brand», то есть на уровне Client Hints выглядит как Chromium без бренда (блог Vivaldi, 13.01.2023). Firefox и Safari не отдают ни API, ни заголовков, и для них это нормально, потому что их UA честный.
- Что делать нам: сейчас в Lumen три несовместимых ответа (таблица выше), а сочетание «Chrome в UA, другое имя или версия в `userAgentData`» исследование прямо называет маркером бота. Минимум — брать версию во всех слоях из `chrome_major!`. Дальше выбор по данным: (А) UA-CH согласованно с UA, с брендами по образцу Vivaldi или с собственным брендом «Lumen» и GREASE, но без ложного «Google Chrome»; (Б) не реализовывать UA-CH, как Firefox, но тогда противоречие с Chrome-UA остаётся. Оба варианта прогнать на корпусе и на антибот-стенах (CMP-06). Варианты и их цена — в разделе «Решения».
- Источники: https://chromestatus.com/data/featurepopularity (GetHighEntropyValues 67,65%; Brands 47,49%) · https://vivaldi.com/blog/technology/client-hints-or-client-lies/

**Мало назваться Chrome: серверы разбирают платформенный токен и номер версии (CMP-03)** · часто · высокая
- Что видит пользователь / что ломается: даже с токеном Chrome сайт отдаёт кривую страницу входа, если в скобках UA указана реальная ОС или нестандартная архитектура или если номер версии выглядит непривычно.
- Механизм: Ladybird зафиксировал платформенный токен для каждой ОС (для Windows — `Windows NT 10.0; Win64; x64`) и отвязал его от реальной платформы. В комментарии в `UserAgent.h` сказано, что настоящие ОС и CPU приводили к «degraded or broken content (e.g. the Instagram login page)». Opera 10 (Andreas Bovens, 27.05.2009) оставила в UA `Opera/9.80`, а настоящую версию унесла в хвост `Version/10.00`: снифферы читали «10» как «1». У Firefox до сих пор есть 2 интервенции `cap_Version_to_99` — наследие трёхзначных версий 2022 года.
- Как решают другие: Chrome сам заморозил платформенный токен (UA reduction), и Chromium-браузеры получают это даром. Ladybird и Servo держат готовые строки для каждой платформы.
- Что делать нам: не показывать собственную версию вроде 0.5 или 1.0 там, где снифферы ищут версию браузера; платформенный токен брать только в замороженном варианте Chrome. HTTP-слой Lumen так и делает (`crates/network/src/http/mod.rs:55`), а `navigator.userAgent = 'Lumen/0.5.0'` — ровно «своя версия на месте версии браузера». Версию движка показывать отдельно: в About и в отчётах.
- Источники: https://github.com/LadybirdBrowser/ladybird/blob/master/Libraries/LibWebCommon/Loader/UserAgent.h (Instagram login) · https://web.archive.org/web/2010/http://dev.opera.com/articles/view/opera-ua-string-changes/ · интервенции Firefox (`cap_Version_to_99` ×2)

**Назвался Chrome — получил код, написанный под Chrome, вместе с его особенностями (CMP-04)** · часто · высокая
- Что видит пользователь / что ломается: после подмены UA часть сайтов ломается по-новому. Сайт перестаёт обходить браузер стороной и включает Chrome-only ветки: `::-webkit-scrollbar`, keypress-логику, скролл к якорю.
- Механизм: bug 2008579 — YouTube Music показывает горизонтальные полосы прокрутки «on browsers with Chrome in the UA string», потому что ветка для Chrome рассчитывает на `::-webkit-scrollbar`. Поэтому Firefox включает поддельный `::-webkit-scrollbar` только по белому списку `layout.css.fake-webkit-scrollbar.enabled-domains`: mail.google.com, docs.google.com, play.google.com, polymarket.com, www.beterbed.nl, www.shazam.com, www.tiktok.com. Обратный случай — WebKit: в `QuirkTable.cpp` для github.com стоит `needsChromeCompatibilityUserAgentQuirk("151")` с комментарием «A Chrome-like UA takes the working code path». Ekioh Flow: Google Docs вставлял буквы p–z дважды, когда Flow представлялся Firefox 62. Docs выполняет для Firefox ≤65 отдельную keypress-ветку, и UA «Firefox 68» это вылечил.
- Как решают другие: Firefox включает Chrome-измы точечно (префы со списком доменов, интервенции). Safari точечно отдаёт «like Chrome/NNN». Ladybird и Servo выбрали один режим и чинят движок под него.
- Что делать нам: UA Chrome означает обязательство bug-compat с Chrome: `::-webkit-scrollbar`, `-webkit-line-clamp`, `overflow: overlay`, `-webkit-fill-available`, `zoom` (состояние Lumen — в блоке CMP-08/29). Сомнительные Chrome-измы включать флагом на домен. Каждый новый режим идентификации гонять на корпусе: подмена может починить один сайт и сломать другой. Сайты с серверным сниффингом уже присылают Lumen Chrome-ветки, а несогласованный JS-слой даёт на одной странице смесь Chrome- и не-Chrome-веток.
- Источники: https://bugzilla.mozilla.org/show_bug.cgi?id=2008579 · https://github.com/mozilla-firefox/firefox/blob/main/modules/libpref/init/StaticPrefList.yaml (7 доменов) · https://www.ekioh.com/devblog/google-docs-in-a-clean-room-browser/ (Firefox 62 → 68)

**Firefox OS: новый токен в UA вызвал волну серверного сниффинга, в том числе на российских сайтах (CMP-24)** · часто · высокая
- Что видит пользователь / что ломается: не тот вариант сайта — десктоп вместо мобильного, страница «скачайте приложение», голая выдача.
- Механизм: в Web Compatibility 2528 багов созданы в 2013–2016 годах (по годам 796 / 933 / 569 / 230). Из них 1004 (39,7%) помечены serversniff, clientsniff или uaoverride, тогда как в другие периоды таких 0–10%. Пик пришёлся на запуск Firefox OS и рост Firefox Android. Российские примеры: «maps.yandex.ru sends Firefox Mobile to an apps download page» (1099105), «odnoklassniki.ru sends desktop site to Firefox Android» (1099553), «hh.ru sends desktop site to Firefox OS» (1099115), «yandex.ru doesn't recognize B2G UA as mobile» (878286). В ноябре 2014 года Mozilla завела серию 1099108–1099181 по RU-топу: rambler, auto.ru, love.mail.ru, gazeta.ru, beeline.ru, sports.ru и другие.
- Как решают другие: Mozilla отвечала UA-интервенциями и письмами владельцам сайтов (теги contactready, sitewait). Многие баги закрылись только через годы.
- Что делать нам: новое имя в UA означает волну поломок на крупных национальных сайтах. Для русскоязычной аудитории сразу проверять Яндекс (поиск, карты, почта, диск), VK, OK, Mail.ru, hh.ru, Avito, Ozon, Wildberries, банки и Госуслуги. Сейчас в корпусе `docs/perf/corpus.txt` 14 сайтов, из них российских 5 (ya.ru, lenta, ria, rbc, habr). Ни одного из перечисленных сервисов в нём нет.
- Источники: https://bugzilla.mozilla.org/show_bug.cgi?id=1099105 · https://bugzilla.mozilla.org/show_bug.cgi?id=878286 · Bugzilla REST, Web Compatibility 2013–2016 (1004 из 2528 с тегами сниффинга)

**Servo называет себя Firefox, Ladybird — Chrome: от имени зависит, какие ветки сайтов получит движок (CMP-17)** · часто · средняя
- Что видит пользователь / что ломается: какие поломки станут типичными, зависит от того, кем назвался движок.
- Механизм: Servo по умолчанию отдаёт `Mozilla/5.0 (Windows NT 10.0; Win64; {ARCH}; rv:153.0) Servo/{SERVO_VERSION} Firefox/153.0` (`components/config/prefs.rs`), и сайты отправляют его по Gecko-веткам. Ladybird работает в режиме `NavigatorCompatibilityMode::Chrome`: `navigator.vendor` — «Google Inc.», `productSub` — «20030107». Servo с 13.04.2026 публикуется на crates.io (0.1.0, затем LTS-ветка 0.1.x). Пост «June in Servo» о «real world compat» (lichess, Zulip, Speedtest) вышел 31.07.2026 и описывает изменения июня (Servo 0.4.0). Успехи Servo собирает в тред Zulip, провалы — в GitHub issues. Как выбираются сайты, не описано.
- Как решают другие: Firefox-UA разумен для движка, чьё поведение ближе к Gecko. Движку с эталоном Chrome он приносит Gecko-специфичный код: префиксы `-moz-` и обходы для Firefox.
- Что делать нам: эталон Lumen — Chrome (графтесты сверяются с Edge), поэтому и идентичность должна быть Chrome-совместимой целиком, в режиме Chrome из HTML: UA, vendor, productSub, appVersion. `vendor` и `productSub` в Lumen уже такие, `appVersion` Chrome-подобный, выбивается только `navigator.userAgent`. Канал «сайт заработал / не заработал» сделать двусторонним, как у Servo, но встроить его в браузер (CMP-26).
- Источники: https://github.com/servo/servo/blob/main/components/config/prefs.rs · https://github.com/LadybirdBrowser/ladybird/blob/master/Libraries/LibWeb/HTML/NavigatorID.cpp · https://servo.org/blog/2026/07/31/june-in-servo/

### 2. Система интервенций: заплатки под сайты как данные

**Firefox держит ≈420 сайт-специфичных заплаток, и больше половины из них — подмена UA (CMP-01)** · массово · критично
- Что видит пользователь / что ломается: без заплатки сайт пишет «браузер не поддерживается» или ломается, с заплаткой пользователь ничего не замечает. Даже третий по величине движок с выделенной командой не обходится без ручных заплаток.
- Механизм: каталог `browser/extensions/webcompat/data/interventions` в mozilla-firefox/firefox на 12.10.2026 — 405 файлов, 423 блока. По типам: `ua_string` — 235, CSS — 104, JS — 79, `hide_messages` — 6, `alter_request_headers` — 6, `hide_alerts` — 4, `replace_string_in_request` — 2, `modify_meta_viewport` — 1. Поле issue встречается 450 раз: firefox-blocked-completely — 187, unsupported-warning — 48, вместе 52%. За ними идут broken-interactive-elements, broken-layout, desktop-layout-not-mobile, page-fails-to-load, broken-scrolling, broken-meetings — по нескольку десятков. Подмены под Chrome: add_Chrome — 99, Chrome — 60, Chrome_with_FxQuantum — 54. По платформам: all — 214, android — 104, desktop — 83.
- Как решают другие: у Firefox это системное расширение webcompat и страница about:compat, у Safari — `QuirkTable.cpp` (CMP-14), у Presto был `browser.js` (CMP-12). Chrome почти обходится без этого, потому что тестируют под него.
- Что делать нам: заложить систему интервенций в архитектуру до широкого релиза и рассчитывать на сотни записей. Формат — декларативный файл на сайт: matches, platforms, issue, тип, ссылка на баг. Порядок предпочтения брать по правилам Firefox (CMP-22): CSS или скрытие сообщения, затем подмена UA на домене, затем JS. Блокировки по UA лечить идентичностью (CMP-02), а не правкой движка. Сейчас в Lumen нет ни механизма, ни формата: «квирки» в `CAPABILITIES.md` — это только режим документа HTML. Инфраструктура подписи уже есть: манифест самообновления подписан ed25519 (`crates/update-manifest/src/lib.rs`), её можно переиспользовать для пакета интервенций.
- Источники: https://github.com/mozilla-firefox/firefox/tree/main/browser/extensions/webcompat/data/interventions (405 файлов, 423 интервенции, 235 подмен UA) · https://github.com/mozilla-firefox/firefox/blob/main/browser/extensions/webcompat/intervention_schema.json

**Жизненный цикл интервенции у Firefox: узкий matches, парные тесты на живом сайте, обновление вне релиза (CMP-22)** · часто · высокая
- Что видит пользователь / что ломается: заплатки копятся, устаревают и ломают сайт уже после того, как он сам исправился. Пользователь не знает, что на сайте работает заплатка.
- Механизм: правила записаны в `AGENTS.md` в `browser/extensions/webcompat`. На каждый сайт — отдельный файл `{bug_id}-{domain}.json` с самым узким matches. CSS и `hide_messages` идут раньше `ua_string`, потому что подмена UA меняет поведение всего сайта. Готовые скрипты переиспользуются. Наблюдаемое изменение один раз логируется через `console.info` со ссылкой на баг. На каждую интервенцию — два pytest-теста через WebDriver на живом сайте: `test_disabled` (поломка воспроизводится) и `test_enabled` (фикс работает); запуск — `./mach test-interventions`. Без теста можно обойтись в нескольких случаях: нужен логин, капча, 2FA или VPN; сайт детектирует WebDriver; поломка нестабильна; тест вышел бы хрупким или слишком сложным. Обновления приходят через Remote Settings (`onRemoteSettingsUpdate` в `lib/interventions.js` и `lib/shims.js`) без релиза браузера; manifest.json версии 160.1.0 использует experiment API `remoteSettings`.
- Как решают другие: WebKit пишет в комментарии к квирку условие удаления. Presto обновлял `browser.js` отдельно от браузера (не проверено).
- Что делать нам: перенять целиком. Подписанный пакет скачивается целиком, без запросов по домену (так не теряется приватность), и обновляется вне релиза. Парные тесты гонять по ночам через собственный WebDriver BiDi Lumen (`crates/bidi-server`, `crates/driver`). Если `test_disabled` перестал воспроизводить поломку, интервенция идёт на удаление. Нужна страница `lumen://compat` со списком и переключателями, а на сайте с активной интервенцией пользователь должен это видеть (CMP-26).
- Источники: https://github.com/mozilla-firefox/firefox/blob/main/browser/extensions/webcompat/AGENTS.md · https://github.com/mozilla-firefox/firefox/blob/main/browser/extensions/webcompat/lib/interventions.js · https://github.com/mozilla-firefox/firefox/blob/main/browser/extensions/webcompat/manifest.json

**Даже Safari держит 179 записей квирков и 25 подмен UA; рычаг WebKit — обязательность iOS (CMP-14)** · часто · средняя
- Что видит пользователь / что ломается: пользователи Safari на macOS тоже получают «сломано, а в Chrome работает». Без iOS Safari оказался бы в положении Firefox.
- Механизм: WebKit перевёл квирки на данные — `QuirkTable.cpp` и `QuirksData.h`. У каждой записи есть `RuntimeQuirkBehavior` с полями script, userAgent, chromeCompatibilityVersion, cookieNames, elementSelector. На 12.10.2026 в `QuirkTable.cpp` 179 вхождений `.matches`. `needsUserAgentStringOverrideQuirk` встречается 25 раз, `needsChromeCompatibilityUserAgentQuirk` — 3: github.com (Chrome 151), mms.pinduoduo.com (149), tiktok.com (136); `Quirks.cpp` дописывает к UA «like Gecko, like Chrome/NNN». Больше всего записей у google.com (8), live.com (7), icloud.com (6) и youtube.com (5). Компенсирующий рычаг — монополия WebKit на iOS: сайт обязан работать в Safari, иначе потеряет iPhone.
- Как решают другие: ни у Firefox, ни у новых движков такого рычага нет, и у Lumen на Windows его не будет.
- Что делать нам: рассчитывать только на себя. Перенять формат записи: условие по домену, вторичное условие по URL, селектор элемента, параметризованная версия Chrome, ссылка на баг и условие удаления.
- Источники: https://github.com/WebKit/WebKit/blob/main/Source/WebCore/page/QuirkTable.cpp (179 записей, 25 подмен UA, 3 «like Chrome») · https://github.com/WebKit/WebKit/blob/main/Source/WebCore/page/QuirksData.h

**Pale Moon/Goanna: полифилы в каждую страницу и UA «режима Firefox» (CMP-19)** · редко · средняя
- Что видит пользователь / что ломается: форк, отставший от актуального движка, ломается на GitHub, Google и за антиботами, а пользователям приходится вручную переключать префы.
- Механизм: Pale Moon 35.0.0 (сентябрь 2026) встраивает в страницы и заранее загружает шимы и полифилы: `Intl.DisplayNames`, `ListFormat`, `RelativeTimeFormat`, `Segmenter`, Streams `pipeTo`/`pipeThrough`, `TransformStream`, `image.decode()`, `getAnimations`. Авторы сами оговаривают, что строгая CSP может помешать и что это «not the most performant solution imaginable». UA «Firefox compatibility mode» поднят до версии 140 и переопределяется глобально и по сайтам. Проблемы с челленджем Cloudflare подтверждаются тредом форума Pale Moon и обсуждением на HN. Поломки на GitHub после перехода на custom elements в 2019–2021 годах (не проверено).
- Как решают другие: Firefox ESR и форки Chromium получают совместимость от апстрима, Pale Moon тратит силы на догонялки.
- Что делать нам: полифил допустим только как временная интервенция на домен с условием удаления, но не как стратегия: он медленный, ломается от CSP и маскирует пробелы движка. Любой откат поведения делать удалённо по доменам, а не префом пользователя. У Lumen JS-builtins (Intl и т. п.) закрывает V8, так что полифилы могут понадобиться разве что для Web API.
- Источники: https://www.palemoon.org/releasenotes.shtml (35.0.0: полифилы, Firefox compatibility mode 140)

### 3. Bug-compat с Chrome: префиксы, Chrome-измы, производительность

**-webkit- префиксы — стандарт де-факто: 88 префиксных свойств на >1% страниц, 51 — на >10% (CMP-07)** · массово · высокая
- Что видит пользователь / что ломается: многоточие не обрезает текст, старый flexbox (`-webkit-box`) не выстраивает элементы, пропадают маски и градиенты, не запускаются анимации.
- Механизм: CSS use counters Chrome (10.10.2026) отслеживают 202 webkit-свойства и алиаса. 88 из них встречаются более чем на 1% загрузок, 51 — более чем на 10%. Топ: `-webkit-user-select` — 64,65%, `-webkit-appearance` — 63,65%, `-webkit-tap-highlight-color` — 62,97%, `-webkit-font-smoothing` — 61,47%, `-webkit-text-size-adjust` — 58,53%, `-webkit-box-orient` — 52,54%, `-webkit-line-clamp` — 46,15%, `-webkit-box-pack` — 40,28%, `-webkit-mask-image` — 30,09%. WHATWG Compatibility Standard (обновлён 15.03.2026) требует ~80 алиасов, `@-webkit-keyframes`, функции `-webkit-linear/radial/repeating-*-gradient()`, медиапризнак `-webkit-device-pixel-ratio`, сопоставление `-webkit-box-*` и `window.orientation`. По словам Edge (2015), поддержка `-webkit-` (добавлена в 2014-м) дала «improvement on more than 40% of mobile web sites». Ladybird в январе 2026 вернул к жизни diagrams.net одним алиасом `@-webkit-keyframes`.
- Как решают другие: Presto ввёл `-webkit-` в 2012 году (статья dev.opera «opera-mobile-emulator-webkit-prefix-support»), EdgeHTML — в 2014-м, затем Firefox.
- Что делать нам: Compatibility Standard реализовать целиком как базовый уровень, а не как хвост; приоритеты расставлять по chromestatus csspopularity. `-webkit-tap-highlight-color` и `-webkit-font-smoothing` на десктопе Windows видимого эффекта не дают и в приоритет не входят. Что уже есть в Lumen: `-webkit-line-clamp` с `display: -webkit-box`, `-webkit-box` / `-webkit-inline-box` / `-webkit-flex`, `-webkit-appearance`, `-webkit-user-select`, `-webkit-text-size-adjust`, `-webkit-box-orient`, `-webkit-background-clip`, `-webkit-fill-available`, `-webkit-image-set()`, `@-webkit-keyframes` (`crates/engine/css-parser/src/parser/at_rules.rs:566`). В коде не найдены (пробой не подтверждено): `-webkit-linear-gradient()` и родственные функции — `is_gradient_function` знает только беспрефиксные имена (`crates/engine/layout/src/style/parse/image.rs:35`); `-webkit-box-pack` (40%); `-webkit-mask-image` (30%); медиапризнак `-webkit-device-pixel-ratio`; `window.orientation`. Первый шаг — механически сверить список Compat Standard с кодом и проверить каждый пункт пробой. Поведение `-webkit-box` и `-webkit-line-clamp` спецификация строго не описывает, его надо сверять с Chrome. Префиксы `-moz-` и `-o-` не трогать.
- Источники: https://chromestatus.com/data/csspopularity (88 > 1%, 51 > 10%) · https://compat.spec.whatwg.org/ · https://blogs.windows.com/msedgedev/2015/06/17/building-a-more-interoperable-web-with-microsoft-edge/ (более 40% мобильных сайтов)

**Нестандартные Chrome-измы и правило bug-compat: когда следовать спецификации, а когда Chrome (CMP-08, CMP-29)** · часто · высокая
- Что видит пользователь / что ломается: другой масштаб, лишние полосы прокрутки, пропавшие иконки в полях, не срабатывающая ссылка. Пользователь делает вывод «браузер кривой», даже если формально браузер прав.
- Механизм: узлы KB Mozilla и число связанных с ними отчётов: `zoom` — 33 (Firefox в итоге его реализовал), `-webkit-scrollbar` — 28, «Different font-weight on websites compared to Chrome» — 19, `overflow: overlay` — 18, другой UI скроллбаров — 12, `-webkit-fill-available` — 11, «Sites depending on Chrome's href="javascript:..." behavior» — 10. Отдельный узел — `::before/::after` у `input` (1956529). Use counters: `zoom` — 29,41% загрузок, `chrome.loadTimes*` — 1,53–1,68%, `WebKitCSSMatrix` — 2,13%. В Firefox по умолчанию включены только `zoom`, `-webkit-fill-available` для width/height и поддельный `::-webkit-scrollbar` по белому списку. `-webkit-line-clamp` на обычных блоках реализован, но выключен (`layout.css.webkit-line-clamp.block.enabled = false`). EdgeHTML грузил кросс-доменные шрифты без CORS «как WebKit» и принимал кривой charset «utf8». В HTML такое поведение уже закреплено как navigator compatibility mode (Chrome, Gecko, WebKit). Узел 1935259 описывает некорректные функции сравнения: SpiderMonkey вызывает compareFn на других парах элементов, чем V8 и JSC, и сломанный компаратор даёт другой порядок. Сайты зависят даже от этого. Узел закрыт как дубликат 1973866.
- Как решают другие: Firefox сначала копит отчёты, потом реализует за префом, нередко по доменам. Chrome и Safari договариваются через Interop.
- Что делать нам: правило из трёх уровней. (а) Если Chrome и Safari совпадают, делать как они, а расхождение со спецификацией выносить в issue или Interop. (б) Только Chrome, use counter больше 1% — реализовать. (в) Только Chrome, редкое или сомнительное — за флагом, который включается по доменам из пакета интервенций. Состояние Lumen:
  - `zoom` (с 2026-08-10), `-webkit-fill-available` и `line-clamp` уже есть.
  - `overflow: overlay` не разбирается: `parse_overflow_kw` знает только visible/hidden/clip/scroll/auto (`crates/engine/layout/src/style.rs:581`). Декларация отбрасывается, и если сайт не задал раньше запасное `overflow: auto`, блок остаётся без прокрутки. В Chrome это алиас `auto`, правка размера S.
  - `::-webkit-scrollbar` транслируется в `scrollbar-width`/`scrollbar-color` для всех доменов, но учитывается только `width` (`crates/engine/layout/src/style/adjust.rs:94`). Частые способы спрятать полосу — `display: none` и `height: 0` для горизонтальной — по коду не учитываются (пробой не проверено).
  - V8 бесплатно снимает целый класс JS-расхождений: порядок при некорректном компараторе сортировки, `Error.stack`, Intl, разбор Date. Не патчить поведение V8 «под спецификацию».
  - `window.chrome` на обычных страницах в Lumen нет. Минимальную заглушку (`loadTimes`/`csi`) рассматривать только по данным корпуса и антибот-стен.
  - Разницу в font-weight и выборе гарнитуры на Windows проверить отдельно: её видно глазом на любом сайте.
- Источники: https://bugzilla.mozilla.org/show_bug.cgi?id=1835345 (zoom, 33) · https://github.com/mozilla-firefox/firefox/blob/main/modules/libpref/init/StaticPrefList.yaml (что включено по умолчанию) · https://chromestatus.com/data/csspopularity (zoom 29,41%)

**Pale Moon выпустил `:has()` и через три недели выключил: производительность тоже входит в совместимость (CMP-09)** · часто · высокая
- Что видит пользователь / что ломается: селектор реализован по спецификации, но страницы с ним подвисают. Пользователь видит тормоза, а не отсутствие фичи.
- Механизм: Pale Moon 35.0.0 (17.09.2026) добавил `:has()`. В 35.0.1 (22.09.2026) исправили «major performance bug», а 35.0.2 (06.10.2026) выключил селектор по умолчанию «for causing additional severe performance issues on websites»; вернуть его можно префом `layout.css.has-pseudo.enabled`. В Chrome `:has()` встречается на 54,43% загрузок (`OBSOLETE_CSSSelectorPseudoHasInLiveProfile` — 40,95%), и при таком охвате наивная инвалидация превращается в массовую регрессию. Похожая история с формами в той же ветке: разбор форм внутри таблиц ужесточили ещё в 35.0.0, а преф отката `html5.forms.standards_compliant` добавили только в 35.0.2.
- Как решают другие: Chrome, Firefox и Safari выпускали `:has()` сразу с оптимизированной инвалидацией.
- Что делать нам: для массовых селекторов и API (`:has()`, container queries, `content-visibility`) готовность определять не по «прошёл WPT», а по отсутствию регрессии времени рестайла на корпусе. В Lumen `:has()` уже включён (`CAPABILITIES.md`), а серия BUG-935 показывает, что стоимость каскада на тяжёлых страницах — живой риск. Стоит добавить в перф-аудит время рестайла на страницах с `:has()`. Откатывать удалённо по доменам, а не через конфиг пользователя. Ужесточение разбора выпускать вместе с откатом в том же релизе.
- Источники: https://www.palemoon.org/releasenotes.shtml (35.0.0 / 35.0.1 / 35.0.2) · https://chromestatus.com/data/featurepopularity (CSSSelectorPseudoHas 54,43%)

**Chrome-only API для устройств статистически ничтожны, но больно бьют по узким сценариям (CMP-10)** · редко · средняя
- Что видит пользователь / что ломается: прошить клавиатуру, 3D-принтер или ESP32, выбрать папку для бэкапа в Google Photos нельзя — сайт отправляет в Chrome.
- Механизм: use counters: `SerialRequestPort` — 0,00127% загрузок, `showOpenFilePicker` — 0,00246%, `showDirectoryPicker` — 0,00036%. При этом `WebBluetoothGetAvailability` встречается на 1,615% — вероятно, это фингерпринтинг. В KB Mozilla: WebUSB — 28 связей, Web Serial — 16 (узел закрыт), Web Bluetooth — 12, SpeechRecognition — 47; последний зависит от облачного распознавания Google. Примеры: в Photos нет «Back up folders» (2038123), в Gmail нет «Voice message» (1988130), в Поиске нет «Spoken answers» (1989531).
- Как решают другие: позиция Mozilla по WebUSB и WebHID — negative. Web Serial вышел в Firefox 151 (2026) на Mac, Windows и Linux, доступ даётся через site-permission add-on, позиция — neutral (add-on gated). WebKit эти API не реализует, Ladybird и Servo не планируют.
- Что делать нам: не тратить ресурсы движка на WebUSB, WebHID и Web Bluetooth. Сейчас Lumen выставляет `navigator.usb`, `navigator.serial`, `navigator.hid`, `navigator.bluetooth`, `SpeechRecognition` и `webkitSpeechRecognition` как заглушки, которые всегда отклоняют вызов (`crates/js/src/webusb.rs`, `serial.rs`, `webhid.rs`, `bluetooth.rs`, `speech.rs`). Проверка `'usb' in navigator` проходит, сайт показывает кнопку «подключить», и она падает с `NotSupportedError` вместо понятного сообщения «используйте Chrome». Вариантов два (см. «Решения»): убрать заглушки и честно не иметь API или оставить их ради сходства с отпечатком Chrome, но тогда распознавать отказ и предлагать «Открыть в Edge/Chrome» (CMP-26). File System Access в Lumen реализован (`crates/js/src/filesystem_access.rs`). SpeechRecognition делать только локально или с явным предупреждением, что аудио уйдёт в облако.
- Источники: https://chromestatus.com/data/featurepopularity (SerialRequestPort 0,00127%) · https://bugzilla.mozilla.org/show_bug.cgi?id=1835416 (WebUSB, 28) · https://github.com/mozilla/standards-positions/blob/main/activities.yml

### 4. Привратники: антибот, защита от трекинга, сертификаты

**Привратники сместились с сайтов в инфраструктуру: Akamai, Cloudflare, DataDome, Imperva, reCAPTCHA (CMP-06)** · массово · критично
- Что видит пользователь / что ломается: бесконечную капчу, страницу «проверка браузера» или молчаливый 403 на тысячах сайтов, за которыми стоит один антибот-вендор.
- Механизм: в KB Mozilla есть узлы «Sites blocked by Akamai» (1903597) — 36 связей, «Sites blocked by Datadome» (2052868, сейчас RESOLVED FIXED), «[meta] breakage caused by imperva/incapsula» (2011267) — 13, «[meta] breakage caused by onetrust» (1987919) — 9. Cloudflare Turnstile не пропускал Ladybird до мая 2026 и, по словам команды, «kept us out of a lot of sites». Ladybird прошёл после нескольких месяцев закрытия мелких пробелов совместимости и изменения на стороне Cloudflare; что именно помогло, команда не знает. reCAPTCHA заработала в Ladybird в июле 2025 года после исправления postMessage между realm'ами, тогда только на google.com. Форум Pale Moon сам закрыт Anubis — PoW-челленджем с cookie `techaro.lol-anubis`. Бот-менеджеры сверяют TLS ClientHello (JA3/JA4) и параметры HTTP/2 SETTINGS с заявленным UA (не проверено; как общее знание правдоподобно).
- Как решают другие: Ladybird точечно чинит API, нужные челленджам, и выходит на контакт с Cloudflare. Firefox ведёт узлы KB по каждому вендору и связывается с ними. Chromium-браузеры проходят по умолчанию.
- Что делать нам:
  - Завести отдельный трек «антибот-стены» с тестовыми страницами Turnstile, reCAPTCHA v2/v3, hCaptcha, DataDome, Akamai, Imperva и российских сервисов — DDoS-Guard, Qrator, Yandex SmartCaptcha (список не проверен).
  - С вендорами работать напрямую.
  - Челленджи не обходить: это совпадает с ADR-007, где решатели капч прямо исключены.
  - Сетевой слой Lumen уже подогнан под Chrome: порядок заголовков, `Accept` навигации, HTTP/2 SETTINGS. Но ClientHello на rustls идёт без CBC-наборов Chrome, и ADR-007 сам признаёт, что JA3 отличается. В комментарии корпуса `docs/perf/corpus.txt` команда уже относит часть 403 на «TLS-фингерпринт rustls» (w3.org — с 2026-09-23). Сверху JS-слой называет себя `Lumen/0.5.0` (раздел 1).
  - Порядок: сначала дёшево снять противоречие JS-слоя, затем замерить, сколько стен по-прежнему падает, и только после этого решать вопрос с ClientHello.
- Источники: https://bugzilla.mozilla.org/show_bug.cgi?id=1903597 (Akamai, 36) · https://ladybird.org/newsletter/2026-05-31/ (Turnstile) · https://ladybird.org/newsletter/2025-07-31/ (reCAPTCHA)

**Приватность сама по себе стоит совместимости: 28% webcompat-багов Firefox с 2023 года вызваны защитой от трекинга (CMP-20)** · массово · высокая
- Что видит пользователь / что ломается: в приватном браузере чаще, чем в обычном, ломаются логины через соцсети, встроенные видео, комментарии, оплата и капчи.
- Механизм: компонент «Privacy: Site Reports» — 2243 из 12 300 багов Web Compatibility (18%). Среди созданных с 2023-01-01 — 1859 из 6599 (28%), ключевое слово `webcompat:tracker-blocking` — у 1125. Firefox SmartBlock держит 64 шима на месте заблокированных скриптов: GA/GTM, Google IMA, Facebook SDK, Doubleclick, Criteo, Rambler Authenticator, Optimizely, эмбеды Disqus, TikTok, Instagram и Spotify, логины Microsoft, StackOverflow и Messenger. Без шима страница падает на обращении к `ga()` или `FB.init()`.
- Как решают другие: у Firefox — шимы и кнопка «отключить защиту для сайта». У Brave и uBlock Origin — redirect-ресурсы и scriptlets со списками исключений.
- Что делать нам: делать шимы вместе с блокировщиком, а не после него. Каждый шим — минимальный объект API без сетевых вызовов. Нужны отдельный тип отчёта «сломалось из-за защиты» и кнопка «временно ослабить защиту на сайте» с таймером. Метрики поломок движка и поломок от защиты вести раздельно, у них разные владельцы. В Lumen переключатель защиты на сайт уже есть (`crates/shell/src/panels/shields_panel.rs`), но исключения живут только в пределах сессии (`CAPABILITIES.md`). Подробности — в приложении 05.
- Источники: https://bugzilla.mozilla.org/rest/bug?product=Web%20Compatibility&component=Privacy:%20Site%20Reports&count_only=1 (2243; 28% с 2023) · https://github.com/mozilla-firefox/firefox/blob/main/browser/extensions/webcompat/data/shims.js (64 шима)

**Российская специфика: сертификаты НУЦ Минцифры и сайты, которые советуют «российский браузер» (CMP-27)** · часто · высокая
- Что видит пользователь / что ломается: веб-версия СберБанк Онлайн и другие сайты, переведённые на сертификаты Минцифры, показывают ошибку безопасности. Банк прямо рекомендует сменить браузер.
- Механизм: Сбер пишет, что веб-версии СберБанк Онлайн и СберБизнес «уже переведены на сертификаты Минцифры России». Про Opera, Firefox и Mi Браузер там же сказано: «после установки сертификатов сайты всё равно могут открываться с ошибкой» и «рекомендуем использовать российский браузер». Корня Russian Trusted Root CA нет в стандартных хранилищах Chrome, Firefox и Apple. Яндекс Браузер и Атом доверяют ему из коробки, Яндекс — с ограничением списком доменов (не проверено).
- Как решают другие: Firefox умеет брать корни из хранилища Windows через `security.enterprise_roots` (не проверено). Chrome на Windows пользуется собственным Chrome Root Store и учитывает локально добавленные корни (не проверено).
- Что делать нам: нужна явная политика. Сейчас Lumen доверяет только вкомпилированному набору webpki-roots (`crates/network/Cargo.toml:20`) и PEM-файлу из переменной `LUMEN_EXTRA_CA_CERT` (`crates/network/src/tls/mod.rs`). Хранилище Windows не читается, поэтому корень, поставленный пользователем по инструкции банка, Lumen не увидит. Варианты — в «Решениях» и в приложениях 05 и 06. Государственный корень не встраивать молча. Ошибку на таких сайтах показывать с объяснением и выбором, а не голым кодом.
- Источники: https://www.sberbank.ru/ru/certificates

### 5. Сервисы Google и флагманы

**Сервисы Google — главный источник поломок для не-Chrome движков: урезанные «тиры», баннеры и молча скрытые функции (CMP-11, CMP-30)** · массово · критично
- Что видит пользователь / что ломается: Gmail, Docs, Meet, YouTube, Поиск и Календарь работают хуже. Иногда висит баннер «browser not supported» или отдаётся упрощённая выдача, но чаще просто нет пункта меню или кнопки. Пользователь узнаёт об этом от знакомых с Chrome и решает, что браузер «урезанный».
- Механизм: из 12 300 багов Web Compatibility больше всего приходится на google.com — 399 (87 открыты), дальше facebook.com — 97, youtube.com — 88 (19 открыты), github.com — 86. Мета-узел «Google UA sniffing, resulting in degraded experience for Firefox users» (1985678) собирает 16 случаев 2014–2026 годов; последний — «calendar.google.com — Browser not supported banner» (02.02.2026). Скрытые функции: на YouTube нет «Download» (1852943, заведён в 2023), в Photos нет «Back up folders» (2038123), в Gmail нет «Voice message» (1988130), в Поиске нет watchlist (1945744). Баги про макросы Sheets (1996535) и выбор даты в Docs (1908648) уже закрыты как исправленные. В user story Mozilla такое помечено impact: feature-broken (519) и unsupported-feature (58). Бывший сотрудник Edge рассказал на HN (17.12.2018), что пустой div поверх видео YouTube выключал аппаратный путь воспроизведения в EdgeHTML, а убрать его YouTube отказался. Ekioh для Gmail воспользовался служебным URL поддержки Google, который не проверяет браузер.
- Как решают другие: Firefox ведёт отдельную мета-ветку по Google. UA-интервенция для Google у него только одна — для meet.google.com (1896424); для docs.google.com (1836872, 1845299) и play.google.com (1779908) интервенции чисто CSS (меню, лишние полосы прокрутки). В WebKit 8 квирков для google.com и 5 для youtube.com. Vivaldi и Brave выдают себя за Chrome. У Ladybird Gmail ожил после смены UA.
- Что делать нам: вести «Google suite» как отдельный регрессионный набор с логином и прогонять на каждом релизе: Gmail (чтение, ответ, вложения), Docs (ввод, IME, правка), Meet (камера, экран), YouTube (воспроизведение, полноэкранный режим, комментарии), Поиск, Карты, Календарь. При сравнении с Chrome в корпусе проверять не только пиксели, но и набор интерактивных элементов по дереву доступности — так видны скрытые функции. Для флагманов вести чек-лист функций. Видеозвонки (Meet, Teams) — отдельный класс, у Mozilla для них есть диагностическая группа video-conferencing.
- Источники: https://bugzilla.mozilla.org/rest/bug?product=Web%20Compatibility&count_only=1 (google.com — 399 из 12 300) · https://bugzilla.mozilla.org/show_bug.cgi?id=1985678 (16 случаев) · https://news.ycombinator.com/item?id=18697824

**Flow (Ekioh): clean-room движок довёл до работы полный Gmail и Google Docs, выбрав их флагманами (CMP-18)** · часто · средняя
- Что видит пользователь / что ломается: задача — как маленькой команде добиться работы самых тяжёлых веб-приложений без исходников и при обфусцированном JS.
- Механизм: Gmail (28.11.2019) показывал белый экран из-за отсутствующего `window.postMessage`. Дальше понадобились порядок исполнения скриптов, порядок mouseover/out, `MouseEvent.relatedTarget`, табличные DOM API, живой `getElementsByClassName` (иначе бесконечный цикл), MutationObserver и contenteditable. Добавление `template` и TreeWalker/NodeIterator, по словам автора, дало «no difference», а отправку письма починила заглушка XMLSerializer. `innerHTML` со строкой в несколько мегабайт разбирался больше минуты, потому что буфер строки рос по одному байту. Когда шаг роста сделали 1024 байта, разбор стал почти мгновенным. Google Docs (17.09.2021): «over 30 distinct issues» за «a couple of months»; например, `getClientRects()` игнорировал inline-элементы, и пропадал перенос строк. Отлаживали брейкпоинтами в чужом инспекторе и поиском имён API в обфусцированном коде. В посте «Can we fix it?» (11.09.2020) Ekioh чинил раскладку по скриншотам The Guardian, eBay, YouTube (`calc()` с процентами в padding), Outlook и Twitter. Flow работает на SpiderMonkey, раскладка многопоточная.
- Как решают другие: Ladybird идёт от тех же флагманов — Gmail, Instagram, Slack.
- Что делать нам: выбрать 10–15 флагманов, которые вытягивают широкий набор API: Gmail, Docs, YouTube, VK, Яндекс Почта, Госуслуги, Ozon, Wildberries, онлайн-банки. Доводить их до 100% сценариев — это покрывает длинный хвост. Отдельно мерить разбор и вставку больших строк (`innerHTML` на мегабайты).
- Источники: https://www.ekioh.com/devblog/full-google-mail-in-a-clean-room-browser/ · https://www.ekioh.com/devblog/google-docs-in-a-clean-room-browser/ (30+ проблем за пару месяцев) · https://www.ekioh.com/devblog/can-we-fix-it/

### 6. Измерение и приоритизация

**Как измерять: корпус против Chrome, критические сценарии с логином и антибот-стены (CMP-28)** · массово · критично
- Что видит пользователь / что ломается: без объективной метрики «как в Chrome» команда не знает, стало ли лучше, и пропускает регрессии на реальных сайтах.
- Механизм: у Mozilla есть Sightline — фокус на топ-сайтах, 1334 бага — и autowebcompat — автоматическое воспроизведение, 1331 баг, из них 673 в 2026 году. Edge в 2015 году использовал краулер Bing с подсчётом использования 7000 API. Ekioh чинил раскладку по скриншотам известных сайтов. Use counters Chrome служат картой обязательных фич. WPT насыщается (CMP-15).
- Как решают другие: Firefox сочетает ручной Sightline с ML-триажем, Ladybird и Servo каждый месяц вручную проверяют сайты.
- Что делать нам: три слоя.
  1. Корпус ≈1000 сайтов: глобальный топ и RU-топ, главная и вторая страница. Метрики: доля сайтов без видимых отличий от эталонного Chrome (пиксельный и структурный дифф с допуском на рекламу и даты), доля сайтов с JS-ошибками, которых нет в Chrome, время до интерактивности.
  2. 50–100 критических сценариев с тестовыми аккаунтами: вход, поиск, оплата в песочнице, видео, загрузка файла, видеозвонок. Метрика — доля сценариев, пройденных до конца.
  3. Антибот-стены (CMP-06).

  Регрессия любой метрики блокирует релиз. Результаты публиковать — это и есть «прозрачный». Заготовки в Lumen уже есть. `scripts/perf_audit.py --mode compat` запускает свежий процесс на сайт и собирает время, память, JS-ошибки, CPU-скриншот и статусы, включая `SITE_REFUSED` для 401/403. Корпуса: `docs/perf/corpus.txt` (14 сайтов) и `docs/perf/corpus-top100-foreign.txt` (100 сайтов). Графтесты сравнивают с Edge, но только синтетические страницы. Не хватает эталона Chrome на тех же реальных сайтах и диффа по пикселям, DOM и дереву доступности.
- Источники: https://bugzilla.mozilla.org/rest/bug?product=Web%20Compatibility (webcompat:sightline 1334, autowebcompat 1331) · https://blogs.windows.com/msedgedev/2015/06/17/building-a-more-interoperable-web-with-microsoft-edge/ (7000 API) · https://www.ekioh.com/devblog/can-we-fix-it/

**Процент WPT — плохой прокси совместимости: Ladybird по подтестам на уровне Safari, но всё ещё пре-альфа (CMP-15)** · массово · высокая
- Что видит пользователь / что ломается: команда видит «94% WPT» и считает, что всё почти готово, а пользователь открывает пять любимых сайтов, и два не работают.
- Механизм: последние прогоны wpt.fyi (11–12.10.2026), общий набор — 123 962 теста. Доля пройденных подтестов: Chrome — 97,7%, Firefox — 96,0%, Safari — 94,4%, Ladybird — 93,8%, Servo — 90,5%. Доля полностью пройденных тестов: Chrome — 70,7%, Firefox — 66,1%, Ladybird — 59,5%, Safari — 58,1%, Servo — 57,7%. Ladybird по областям: css — 76% (у Safari 88%), svg — 65%, service-workers — 34%, webrtc — 1%, webcodecs — 0%. Servo: css — 55%, web-animations — 8%, service-workers — 7%. Большие наборы подтестов (кодировки, IDL) накачивают процент, а дыры в целых подсистемах почти не видны. Ladybird в январе 2026 года сместил фокус на «real websites and daily-driver usability».
- Как решают другие: Ladybird и Servo публикуют графики WPT, но отчитываются конкретными сайтами. Interop следит за выбранными областями, а не за общим процентом.
- Что делать нам: главный KPI — корпус и сценарии (CMP-28). WPT — регрессионная сеть, и смотреть в нём стоит покрытие по подсистемам (WebRTC, Service Workers, медиа), а не общий процент. Lumen ведёт WPT по категориям (`docs/wpt-status.md`); долю по подсистемам держать там же, а общий процент не выносить в публичные метрики готовности.
- Источники: https://wpt.fyi/api/runs?product=servo&product=ladybird&product=chrome&product=firefox&product=safari&label=master&max-count=1 (пересчёт на 123 962 тестах) · https://ladybird.org/newsletter/2026-01-31/

**Канал «сообщить о поломке» очень шумный: из ≈235 тыс. отчётов webcompat.com исправлено ≈1,3% (CMP-21)** · массово · высокая
- Что видит пользователь / что ломается: после отчёта ничего не меняется, и пользователь перестаёт сообщать. Команда тонет в сортировке.
- Механизм: вехи github.com/webcompat/web-bugs: invalid — 92 926, worksforme — 51 912, incomplete — 21 746, duplicate — 18 229, non-compat — 16 921, wontfix — 1865, moved (передано в Bugzilla) — 4588, fixed — 3081. Ждут триажа 22 170, в sitewait — 248; всего ≈235,3 тыс. Поток по годам: 2024 — 14 020, 2025 — 51 253 (скачок после появления встроенного отчёта в Firefox), 2026 — 39 221. В Bugzilla метка autowebcompat (ML и автоматическое воспроизведение) выросла с 76 багов в 2023 году до 673 в 2026-м; repro-failed — 931, repro-success — 388.
- Как решают другие: у Mozilla — модерация, ML-триаж, автоматическое воспроизведение и затем ручная диагностика. Edge в 2015 году опирался на телеметрию инсайдеров, а не на текстовые отчёты.
- Что делать нам: отчёт сам собирает диагностику с согласия пользователя: URL без query, версию, включённые интервенции, что заблокировано, ошибки консоли, скриншот, помог ли режим совместимости. Отчёты по одному домену агрегируются автоматически, а пользователь видит статус («уже знаем, сообщили 37 человек»). Не обещать починку каждого отчёта. Ценнее агрегированный сигнал «сколько людей переключили режим совместимости на домене», но это телеметрия, и её модель — решение команды.
- Источники: https://api.github.com/repos/webcompat/web-bugs/milestones?state=all (invalid 92 926, fixed 3081) · https://github.com/webcompat/web-bugs

**Ladybird: от WPT к реальным сайтам; фиксы обычно мелкие, а дорогая часть — диагностика (CMP-16)** · часто · средняя
- Что видит пользователь / что ломается: новый движок долго не годится как основной браузер, хотя формально покрывает большую часть платформы.
- Механизм: цель — альфа в 2026 году для Linux и macOS, Windows «at a later stage». В январе 2026 года команда переключилась на реальные сайты. Instagram ожил после `ServiceWorkerContainer.ready`, TripAdvisor — после исправления закрытия MessagePort, Street View — после `Canvas.measureText()`, diagrams.net — после `@-webkit-keyframes`, Slack — после процентного max-width. После смены UA Gmail открылся в настоящем интерфейсе, а профилирование сократило загрузку входящих «roughly a second». Скоупированная инвалидация псевдоклассов при наведении на ящики занимала «over 10% of runtime». 05.06.2026 проект перестал принимать публичные PR, но отчёты о багах, редукции и тестирование сайтов по-прежнему приветствует.
- Как решают другие: Servo тоже публикует ежемесячные списки сайтов, Flow выбрал флагманами Gmail и Docs (CMP-18).
- Что делать нам: наращивать совместимость петлёй «корпус → автоматический дифф → самые массовые расхождения → минимальная репродукция → фикс». Обычно фикс — одно недостающее API или один крайний случай раскладки, поэтому вкладываться стоит в сведение поломки к тесткейсу: бисекцию DOM/CSS, запись и повтор сессии. Методику проб Lumen (`docs/probe-method.md`) достроить до автоматической редукции страницы.
- Источники: https://ladybird.org/ (Alpha 2026, Windows позже) · https://ladybird.org/newsletter/2026-01-31/ · https://ladybird.org/posts/changing-how-we-develop-ladybird/

**Приоритизация у Mozilla: оценка влияния, программа топ-сайтов, база корневых причин; аутрич медленный (CMP-23)** · часто · средняя
- Что видит пользователь / что ломается: сломанных сайтов больше, чем рук. Без формулы приоритета команда чинит то, что громче, а не то, что массовее.
- Механизм: в user story багов Bugzilla есть разметка. Impact: site-broken 801, workflow-broken 684, feature-broken 519, content-missing 378, blocked 331, unsupported-warning 229. Кроме того, поля affects, configuration и platform. Diagnosis-team: webcompat 922, layout 551, dom 498, media 197, privacy 146, networking 116, video-conferencing 60. user-impact-score стоит у 3472 багов. Whiteboard webcompat:sightline — 1334 бага; по годам 2023 — 208, 2024 — 381, 2025 — 277, 2026 — 255, то есть ≈1121 за 2023–2026. Knowledge Base — 194 узла корневых причин. Аутрич медленный: webcompat:needs-contact — 701, webcompat:site-wait — 274, на webcompat.com в sitewait висит 248 открытых.
- Как решают другие: Edge в 2015 году — телеметрия и краулер с подсчётом API. Chrome — use counters, по которым решает и что можно удалять.
- Что делать нам: формула «влияние × охват × частота конфигурации × вес сайта в корпусе», вес — из локального топа (RU + глобальный). Вести базу корневых причин: один фикс движка закрывает десятки сайтов. Аутрич — вторая линия после интервенции, а не первая. В Lumen есть `docs/bug-priority.md` — дополнить его полями влияния и веса сайта, а не заводить параллельную схему.
- Источники: https://bugzilla.mozilla.org/rest/bug?product=Web%20Compatibility (user story: user-impact-score 3472) · https://bugzilla.mozilla.org/buglist.cgi?product=Web%20Compatibility&component=Knowledge%20Base (194 узла)

### 7. Аварийный выход для пользователя

**Лестница действий для пользователя, когда «сайт работает не так» (CMP-26)** · массово · критично
- Что видит пользователь / что ломается: сейчас у него два пути — терпеть или уйти в Chrome насовсем. Каждый такой уход — вероятная потеря пользователя.
- Механизм: что уже есть у других. Firefox: about:compat с переключателями интервенций (`aboutCompat.html/js`), «Report broken site», отключение защиты для сайта. Edge: «Reload in IE mode» с индикатором. Vivaldi: свой UA только на белом списке доменов. Pale Moon: переопределение UA глобально или по сайтам, но через конфиг. Opera Presto: «Identify as / Mask as» по сайтам (не проверено). Konqueror: «Browser Identification» по доменам (не проверено).
- Как решают другие: ни один браузер не собирает эти шаги в одну лестницу; у Firefox они разнесены по разным местам интерфейса.
- Что делать нам: одна кнопка в адресной строке «Сайт работает неправильно?» открывает лестницу.
  1. «Перезагрузить в режиме совместимости» — перебирает идентичности Chrome, Firefox и Safari, снимает защиту от трекинга, выключает тяжёлые оптимизации и в конце спрашивает «так лучше?».
  2. «Ослабить защиту на этом сайте» — с таймером.
  3. «Открыть в другом браузере» — Edge, Chrome или браузер по умолчанию, URL без лишних параметров.
  4. «Сообщить» — с автодиагностикой (CMP-21).

  Выбор в пунктах 1–2 запоминается для домена, видимо и обратимо. Если домен уже есть в пакете интервенций, показывать «мы знаем об этой проблеме, применено исправление». Ничего не прятать в about:config и не требовать от пользователя понимать слово «UA». Для пункта 1 в Lumen пока нет основы: `http_profile` (chrome/firefox/safari/edge/…) глобальный (`crates/shell/src/config.rs:228`) и меняет только HTTP-слой, а `navigator.userAgent`, `vendor` и `userAgentData` от него не зависят. Нужна идентичность на домен, согласованная во всех слоях, и запоминание исключений защиты дольше сессии.
- Источники: https://github.com/mozilla-firefox/firefox/tree/main/browser/extensions/webcompat/about-compat · https://learn.microsoft.com/en-us/deployedge/edge-ie-mode · https://vivaldi.com/blog/user-agent-changes/

**Гибридный запасной движок (WebView2, «IE mode наоборот»): чем поможет и чем навредит лёгкому приватному браузеру (CMP-25)** · часто · высокая
- Что видит пользователь / что ломается: банк или Госуслуги нужны сейчас, а не после фикса движка. Возникает соблазн открыть сломанный сайт во встроенном Chromium.
- Механизм: прецеденты.
  - Режим IE в Edge: два движка в одном окне, логотип IE слева в адресной строке. Сайты попадают в режим через Enterprise Mode Site List или политику «Send all intranet sites to IE».
  - WebView2 Evergreen входит в Windows 11 и стоит на «the vast majority» машин с Windows 10. Fixed Version весит больше 250 МБ.
  - Китайские «двухъядерные» браузеры (360, QQ, Sogou); Lunascape с тремя движками; Konqueror с выбором между KHTML и QtWebEngine — после этого KHTML перестал развиваться и был удалён в KDE Frameworks 6 (всё — не проверено).

  Минусы для Lumen:
  - отдельное хранилище cookies и сессий, то есть вход заново;
  - компонент Microsoft со своей телеметрией и обновлением — против «приватного и прозрачного»;
  - расход памяти;
  - блокировщик и интервенции туда не распространяются;
  - путаница «какой движок сейчас работает»;
  - пользователи переключаются по привычке, и мотивация чинить собственный движок падает.
- Как решают другие: Edge держит второй движок только для старого IE и под корпоративной политикой. Firefox, Safari, Ladybird и Servo запасного движка не держат.
- Что делать нам: по умолчанию не встраивать. Если всё же делать, то только как явное действие пользователя на конкретном сайте: постоянный индикатор, отдельный очищаемый профиль, предупреждение о том, что данные уйдут компоненту Microsoft. Каждое переключение логировать локально как сигнал о пробеле движка. Дешевле и честнее кнопка «Открыть в Edge/Chrome» с передачей URL (CMP-26).
- Источники: https://learn.microsoft.com/en-us/deployedge/edge-ie-mode · https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution (Fixed Version > 250 МБ)

### 8. Почему проиграли Presto и EdgeHTML

**Opera Presto: browser.js, маски «Identify as» и уход на WebKit (CMP-12)** · часто · высокая
- Что видит пользователь / что ломается: пользователи Opera годами видели сайты, сломанные снифферами и вёрсткой «только под WebKit», особенно на мобильных.
- Механизм: пресс-релиз Opera о переходе на WebKit известен по пересказу PPK (quirksmode.org, февраль 2013). Первая выгода, которую там называют, — «better site compatibility, especially with mobile-facing sites», потому что многие такие сайты «have only been tested in WebKit browsers». PPK добавляет две причины: растущую стоимость гонки за WebKit и невозможность портировать Presto на iOS. Ещё в 2009 году Opera 10 сохранила в UA `Opera/9.80` из-за снифферов (CMP-03). В 2012 году Presto ввёл поддержку `-webkit-` (статья в репозитории operasoftware/devopera). По памяти (не проверено): `browser.js` — автоматически обновляемый файл JS-патчей под сайты, независимый от релиза; в настройках сайта было «Identify as Opera / Mask as Firefox / Mask as IE»; команда Open the Web писала владельцам сайтов; о переходе объявили 13.02.2013, когда у Opera было ≈300 млн пользователей.
- Как решают другие: Firefox и Safari сегодня повторяют модель `browser.js` — интервенции и квирки с обновлением вне релиза. Модель Opera проиграла по экономике, а не по технике: заплаток требовалось больше, чем команда успевала писать.
- Что делать нам: перенять механику — удалённо обновляемый пакет патчей, маски по сайтам в UI, работу с владельцами сайтов. Маленькая команда гонку «чинить быстрее, чем ломают» не выиграет, поэтому нужны автоматическое обнаружение поломок (CMP-28) и аварийный выход (CMP-25/26). Не рассчитывать на то, что сайты начнут тестировать под новый движок.
- Источники: https://www.quirksmode.org/blog/archives/2013/02/opera_switching.html · https://github.com/operasoftware/devopera/tree/master/src/articles

**EdgeHTML: 3 млн инсайдеров, краулер Bing на 7000 API, -webkit- для 40% мобильных сайтов — и всё равно уход на Chromium (CMP-13)** · часто · высокая
- Что видит пользователь / что ломается: даже браузер по умолчанию в Windows не смог добиться, чтобы сайты тестировали под него.
- Механизм: блог Edge, 17.06.2015. Приоритеты строили по отчётам о сайтах от более чем 3 млн участников Windows Insider и по краулеру Bing: 33 трлн страниц, 44 млрд сайтов, учёт использования 7000 API. Edge убрал ActiveX, добавил `-webkit-`, принял кривые meta refresh и charset «utf8», грузил кросс-доменные шрифты без CORS — «change to WebKit behavior». UA в посте назван «an ever-growing pack of lies». VBScript и attachEvent в этом посте не упоминаются; их удаление из EdgeHTML известно по другим постам блога Edge (не проверено). 06.12.2018 Joe Belfiore объявил переход на Chromium «to create better web compatibility for our customers and less fragmentation of the web for all web developers», не приведя ни одной цифры. Экс-сотрудник на HN рассказал, как изменения на YouTube били по EdgeHTML (CMP-11).
- Как решают другие: Edge на Chromium сохранил режим IE — два движка в одном окне с индикатором (CMP-25).
- Что делать нам: совместимость — бюджет навсегда, а не проект с концом. Краулер реальных страниц и отчёты пользователей работают, но малая доля рынка не заставит сайты тестировать под вас. Значит, стратегия держится на идентичности «как Chrome», bug-compat и интервенциях, а не на просвещении веб-разработчиков. Перенять у Edge краулер с подсчётом использования API и «нестрогое» поведение там, где так делают WebKit и Chromium.
- Источники: https://blogs.windows.com/msedgedev/2015/06/17/building-a-more-interoperable-web-with-microsoft-edge/ · https://blogs.windows.com/windowsexperience/2018/12/06/microsoft-edge-making-the-web-better-through-more-open-source-collaboration/ · https://news.ycombinator.com/item?id=18697824

## Решения, которые должна принять команда

1. **Идентичность по умолчанию (UA, `navigator.*`, UA-CH).** В любом варианте убрать нынешнее расхождение «Chrome 153 / `Lumen/0.5.0` / Chrome 114 / нет заголовков».
   - (а) Полная Chrome-идентичность: `navigator.userAgent` совпадает с HTTP-UA, `userAgentData` и `Sec-CH-UA` берут версию из `chrome_major!`, бренды — «Chromium» и GREASE, как у Vivaldi. Максимум совместимости. Цена: обязательство bug-compat с Chrome и бренд «Chromium» у движка, который не Chromium.
   - (б) Chrome-UA плюс собственный бренд в UA-CH: «Lumen» и GREASE, без «Google Chrome» и «Chromium». Честнее, но сайты, которые ищут в brands «Chromium» или «Google Chrome», пойдут по не-Chrome-ветке. Масштаб неизвестен, его надо мерить на корпусе.
   - (в) Chrome-UA без UA-CH. Дёшево, но для антибот-скриптов «Chrome без client hints» выглядит подозрительно, а `getHighEntropyValues` вызывают на 67,65% загрузок.
   - (г) Честный `Lumen/x.y` во всех слоях. Цена — сотни ручных заплаток и волна сниффинга на RU-сайтах (CMP-01, CMP-02, CMP-24).
   - При (а) и (б) литерал `navigator.userAgent`, который `CLAUDE.md` называет единственным ручным местом версии, станет производным от `chrome_major!`, и правило в `CLAUDE.md` придётся обновить.
2. **Откуда брать мажорную версию Chrome.** Сейчас это макрос в сборке, который сверяют вручную перед аудитами.
   - (а) Удалённый подписанный конфиг, тот же канал, что у интервенций. Версия не отстаёт между релизами, но канал придётся сделать.
   - (б) Только в сборке. Отставание от Chrome растёт между релизами Lumen.
3. **Канал интервенций.**
   - (а) Подписанный пакет данных, который скачивается целиком и обновляется вне релиза (подпись ed25519 переиспользуется из `crates/update-manifest`). Нужны хостинг, ревью записей и ночные парные тесты через BiDi.
   - (б) Только вместе с релизами. Поломки будут висеть неделями.
   - Отдельно решить: допустимые типы (CSS, скрытие сообщений, UA на домене, JS), кто сопровождает пакет, публиковать ли список.
4. **Отпечаток TLS ClientHello.**
   - (а) Подогнать под Chrome: CBC-наборы, порядок расширений, GREASE. Возможно, понадобится форк rustls или другая TLS-библиотека, а значит обоснование по ADR-027 и постоянная поддержка вслед за Chrome.
   - (б) Оставить rustls как есть, работать с вендорами антибота и сначала убрать дешёвые расхождения (JS-слой).
   - Решать после замера: сколько стен ещё падает, когда JS-слой согласован.
5. **Заглушки device-API (WebUSB, Serial, HID, Bluetooth, SpeechRecognition).**
   - (а) Удалить. Сайт честно видит «API нет» и показывает свою подсказку, а Lumen предлагает «Открыть в Edge/Chrome». Минус — расхождение с отпечатком Chrome, где эти объекты есть.
   - (б) Оставить. Отпечаток ближе к Chrome, но кнопка на сайте молча падает, поэтому минимум нужны распознавание отказа и подсказка.
6. **Запасной движок.**
   - (а) Не встраивать, ограничиться кнопкой «Открыть в Edge/Chrome». Дёшево (S) и честно.
   - (б) WebView2 по явному действию на сайте, с индикатором и отдельным профилем. Это L–XL работы, телеметрия Microsoft, риск для позиционирования и для мотивации чинить свой движок.
7. **Главный KPI и релизный гейт.** Предлагаемая основа: корпус против Chrome (пиксели, DOM, дерево доступности), сценарии с логином, антибот-стены. Нужно решить:
   - размер корпуса (сейчас 14 + 100 сайтов, российских 5);
   - где взять тестовые аккаунты (для банков и Госуслуг тестовых аккаунтов нет);
   - блокирует ли регрессия релиз;
   - публиковать ли результаты.
8. **Политика bug-compat.** Принять ли правило трёх уровней (CMP-08/29). Кто относит Chrome-изм к уровню (в). Флаги по доменам хранить в пакете интервенций или в коде.
9. **Отчёты и агрегированный сигнал.** Куда уходит отчёт, кто его триажит, сколько хранится. Собирать ли счётчик «переключили режим совместимости на домене»:
   - (а) opt-in, без идентификаторов;
   - (б) не собирать — тогда приоритеты только по корпусу.
10. **Доверие к корням НУЦ и хранилищу Windows.**
    - (а) Только webpki-roots, как сейчас, плюс объясняющий экран.
    - (б) Учитывать корни, которые пользователь сам добавил в хранилище Windows, с заметным индикатором.
    - (в) Встроить государственный корень. Это противоречит позиционированию.
    - Связано с приложениями 05 и 06.
11. **Список флагманов.** Какие 10–15 сайтов доводить до 100% сценариев: российские (Госуслуги, Сбер, VK, сервисы Яндекса, Ozon, Wildberries) и глобальные (Gmail, Docs, YouTube).

## Анти-цели области

- Не мерить готовность общим процентом WPT и не публиковать его как метрику совместимости.
- Не ставить в UA уникальный токен Lumen и не показывать собственную версию там, где снифферы ищут версию браузера.
- Не отдавать противоречивую идентичность: Chrome в одном слое и другое имя или версия в `navigator.userAgent`, `userAgentData`, `Sec-CH-UA`.
- Не зашивать квирки под сайты в код движка: только данные с удалённым обновлением, парными тестами и условием удаления.
- Не держать полифилы в каждой странице как постоянную стратегию.
- Не реализовывать WebUSB, WebHID и Web Bluetooth ради паритета. Не держать заглушки API, которые проходят feature detection и всегда отказывают, если отказ никак не обработан. Не делать облачный SpeechRecognition без явного предупреждения.
- Не встраивать по умолчанию запасной движок (WebView2).
- Не обходить капчи и антибот-челленджи и не строить для этого инструменты (ADR-007).
- Не строить стратегию на том, что владельцы сайтов начнут тестировать под Lumen; аутрич — вторая линия после интервенции.
- Не прятать переключатели совместимости в about:config и не требовать от пользователя понимать слово «UA».
- Не выпускать массовые селекторы и API (`:has()`, container queries) без замера времени рестайла на корпусе. Не ужесточать разбор без удалённого отката по доменам.
- Не патчить поведение V8 «под спецификацию» там, где V8 совпадает с Chrome.
- Не встраивать государственный корень молча.
- Не обещать починку каждого отчёта и не привязывать отчёт к общей телеметрии.
