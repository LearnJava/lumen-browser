# Прокрутка, масштаб, чтение, отрисовка текста, тёмная тема

Легенда. Массовость: массово / часто / редко. Тяжесть: высокая / средняя / низкая. «У ChatGPT» — насколько пункт раскрыт в документе ChatGPT. Пометка «(не проверено)» стоит у деталей, которые взяты по памяти или источник которых не открылся при проверке фактов. Звёзды Chromium (★) взяты из поля vote count во внутреннем JSON issues.chromium.org; то, что это именно звёзды, не подтверждено. Reddit, 4PDA, Pikabu и NN/g напрямую не читались: кончился лимит веб-поиска. Поэтому печать, клик по треку, щипок и переносы опираются в основном на код браузеров и общие знания.

## Главное в области

1. **Правильное поведение браузеры находили через годы и после жалоб, а потом оно регрессировало.** Учёт шапок при Page Down в Firefox: эвристика 2012 года (Fx17), доработка в Fx45, позже sticky и предел 1/3. Белую вспышку Firefox закрывал пятью отдельными фиксами за 2019–2022 (Fx68, Fx75, Fx95, Fx108), а баг «новая вкладка рисуется до применения темы» открыт с 2018. Chromium на Windows до сих пор вспыхивает при создании окна: патч Microsoft с cloak был брошен в январе 2025, влит только фикс вспышки при разворачивании. «Прыгающий Facebook» из-за scroll anchoring чинили 15 месяцев, в баге 183 комментария. Пользователь замечает такие вещи, только когда они сломаны, поэтому каждую сразу закрывать регрессионным тестом.
2. **Рецепт зрелых браузеров: сначала подсказка автора страницы, потом эвристика с жёсткими порогами.** scroll-padding, затем поиск шапки (≥50% ширины или ≥800 px, ≤1/3 высоты). overflow-anchor, затем anchoring с самоотключением при петле. color-scheme, затем цвет полосы по светимости фона. В исходниках Gecko и Chromium есть готовые продуктовые решения с числами: пороги, длительности, цвета, тайминги. Брать их как спецификацию по умолчанию, а отклонения обосновывать.
3. **Явная настройка ОС побеждает дизайн браузера.** Шаблон Firefox: значение подстраивается, только пока пользователь его не трогал (колесо ×2 действует лишь при системной скорости по умолчанию). Что читать и перечитывать по `WM_SETTINGCHANGE`: число строк колеса, «Всегда показывать полосы прокрутки», «Анимация элементов управления», «Размер текста», ClearType Tuner, выключенное сглаживание. Контрпример — Fluent-полосы Chrome 146. Жалобу «OS scrollbar not respected» закрыли как Won't Fix, а через полгода в Canary 154 вернули флаг, который переопределяет настройку ОС «в обе стороны».
4. **Белая вспышка — это цепочка слоёв, а не один баг.** Окно DWM, контейнер вкладок, about:blank, новая вкладка, переход между документами, canvas до загрузки CSS, JS сайта. Каждый слой закрывается отдельно, иначе получается «half-fixed and broken again». Самое дешёвое для своего движка: с самого начала поддержать `<meta name="color-scheme">` и держать предыдущий кадр до первого содержательного кадра нового документа.
5. **Свой рендер текста — преимущество перед Chromium на Skia.** С первого дня можно читать параметры DirectWrite для каждого монитора (gamma, контраст, уровень ClearType, структура пикселей) и по умолчанию выбирать grayscale на OLED и HiDPI. В Chrome и Firefox это доступно только через флаги и about:config. Для русскоязычной аудитории сюда же относится кириллица: serif (Times New Roman) по умолчанию на страницах без стилей, веб-шрифты без кириллического подмножества, старые локально установленные Roboto, жалобы на мутный UI при 125%. Корпус тестов должен включать русские сайты.
6. **Пользователи путают три разных «масштаба».** Страничный: с reflow, запоминается для хоста. Визуальный щипок: без reflow, не запоминается. Масштаб только текста: в десктопном Chrome его нет. Нужны постоянный индикатор нестандартного масштаба и сброс к масштабу по умолчанию, а не к 100%. Модель запоминания (хост или вкладка) надо выбрать явно: Chrome отклонил просьбу о масштабе по вкладке, и пользователи живут на расширениях.

## Находки

### Прокрутка: шаг, плавность, отзывчивость

**Шаг колеса мыши: системное число строк, 100 px на щелчок, точные колёса** · массово · тяжесть высокая · у ChatGPT: вскользь
- Боль: «колесо крутит слишком мало» — классика Chromium на Linux и жалобы новичков в Firefox. «Поменял в Windows число строк — браузеру всё равно». В Edge с percent-based scrolling маленькие панели (например, боковая в Gmail) прокручиваются по чуть-чуть.
- Как должно быть: на Windows число строк брать из `SPI_GETWHEELSCROLLLINES` (по умолчанию 3) и перечитывать по `WM_SETTINGCHANGE`; `WHEEL_PAGESCROLL` означает экран за щелчок. Базовый шаг как в Chromium: строки × 100/3 px, то есть 100 CSS px при значении по умолчанию. Firefox считает строку по высоте шрифта скроллера (не меньше 5 px, `mousewheel.min_line_scroll_amount`) и умножает на 2, только если системная скорость не тронута (`mousewheel.system_scroll_override.*.factor=200`, Windows и Linux), — получается примерно 110–120 px. У высокоточных колёс (delta < 120) и тачпада дробные доли копить, а не округлять до строк. Shift+колесо и `WM_MOUSEHWHEEL` — горизонтальная прокрутка, Ctrl+колесо — масштаб. `WheelEvent.deltaY` для сайтов остаётся «100 на щелчок», даже если фактическое расстояние другое (так сделал и Edge). Шаг на коротком скроллере не меньше одной строки.
- Кто делает лучше / хуже: лучше Firefox — соблюдает явный выбор пользователя и меняет только значение по умолчанию. Chromium на Windows жёстко привязан к 33,3 px на системную строку, на Linux годами прокручивает слишком медленно. Edge с percent-based на коротких скроллерах даёт шаг меньше строки (об этом предупреждал Tab Atkins).
- Источники: https://issues.chromium.org/issues/41195115 («Linux scroll speed is too low», 37★, с 2015); https://github.com/chromium/chromium/blob/main/ui/events/blink/web_input_event_builders_win.cc ; https://qna.habr.com/q/503495

**Плавная прокрутка: 100–200 мс, перенацеливание, выключатель и связь с системными анимациями** · массово · тяжесть высокая · у ChatGPT: вскользь
- Боль: одни пишут «Firefox прокручивает вязко и рывками по сравнению с Chrome», и самый частый совет — включить msdPhysics. Другие — «плавная прокрутка в Chrome желейная, как отключить» (Хабр, Pikabu, Ответы Mail.ru).
- Как должно быть: кривая ease-in-out. В Chromium анимация колеса длится 6–12 кадров по 1/60 с, то есть 100–200 мс, и чем больше дельта, тем она короче: 200 мс при 120 px, 100 мс при 480 px. Постоянная длительность — 9 кадров (150 мс). В Firefox колесо 50–200 мс (`general.smoothScroll.mouseWheel.durationMin/MaxMS`), стрелки и Page — 150 мс; msdPhysics по умолчанию включён только в Nightly. Новый щелчок во время анимации перенацеливает её с текущей скоростью, а не запускает заново: без этого прокрутка кажется вязкой. Первый сдвиг виден в ближайшем vsync после ввода, анимация идёт по vsync реальной частоты монитора (см. пункт про отзывчивость). Если в Windows снято «Анимация элементов управления и элементов внутри окна» (`SPI_GETCLIENTAREAANIMATION`), плавность отключать — Chromium так и делает. Флажок «Плавная прокрутка» держать в обычных настройках, а не во флагах. Пиксельные дельты тачпада и инерцию ОС повторно не анимировать.
- Кто делает лучше / хуже: у Firefox флажок есть в настройках, но поведение по умолчанию считают вязким, и в сообществе ходят пресеты (AveYo, «Windows scrolling personality»). Chrome и Яндекс прячут настройку в `chrome://flags/#smooth-scrolling` (`browser://flags`), на macOS флага нет; системную настройку анимаций Chromium учитывает. Edge в 2020 перенёс кривую из старого Edge.
- Источники: https://github.com/chromium/chromium/blob/main/cc/animation/scroll_offset_animation_curve.cc ; https://www.resetera.com/threads/just-switched-to-firefox-and-scrolling-feels-so-sluggish-on-websites-including-resetera.445204/ ; https://connect.mozilla.org/t5/ideas/implement-smoother-scrolling/idi-p/8035

**Page Down / Space вычитают высоту fixed- и sticky-шапок** · часто · тяжесть высокая · у ChatGPT: нет
- Боль: «после каждого Page Down или пробела первые строки уходят под приклеенную шапку, жму стрелку вверх 2–3 раза». Жалуются на форумы, LinkedIn, NYTimes, ArsTechnica.
- Как должно быть: шаг = (высота scrollport − шапка − подвал) − перекрытие. Шапка — fixed-элемент или залипший sticky-элемент у верхнего края, подвал — у нижнего; элементы стопкой и с перекрытием объединяются. Пороги Firefox: видимая ширина ≥50% scrollport или ≥800 CSS px, высота ≤1/3 высоты окна. Более высокие элементы игнорируются, чтобы шаг не схлопнулся. Перекрытие = min(10% высоты, 2 строки шрифта) (`toolkit.scrollbox.pagescroll.maxOverlapPercent=10`, `maxOverlapLines=2`). Вычитать max(scroll-padding-top, найденная шапка). Те же правила для Shift+Space и Page Up. При прокрутке к якорю и к совпадению Ctrl+F не ставить цель под шапку. Тест: fixed-шапка 80 px; после Page Down последняя видимая строка остаётся видимой.
- Кто делает лучше / хуже: лучше всех Firefox. Эвристика появилась в 2012 году (Fx17: полная ширина, ≤1/4 высоты), в Fx45 добавились шапки с transform и порог 50%/800 px, позже — sticky и предел 1/3. Chromium шапки не ищет: шаг = 87,5% от (высота окна − scroll-padding), на macOS — max(87,5%, высота − 40 px). При scroll-padding: 0 шапка закрывает текст; в 2022 менять это отказались из соображений совместимости. WebKit учитывает scroll-padding (r271788).
- Источники: https://bugzilla.mozilla.org/show_bug.cgi?id=780345 ; https://github.com/mozilla/gecko-dev/blob/master/layout/generic/ScrollContainerFrame.cpp ; https://news.ycombinator.com/item?id=4654002

**Прокрутка не ждёт JavaScript и идёт с частотой монитора** · часто · тяжесть высокая · у ChatGPT: вскользь
- Боль: «страница тормозит при прокрутке», «на 165 Гц прокрутка как на 30», рывки Chromium на 144/165 Гц, «sticky-шапка дрожит при прокрутке» (Firefox bug 1585378).
- Как должно быть: прокрутка в потоке композитора, без ожидания главного потока. Слушатели wheel, touchstart и touchmove на window, document и body по умолчанию passive (интервенции Chrome: touch — версия 56, wheel — 73, не проверено). Если на цели есть непассивный слушатель, ждать JS не дольше 400 мс (Firefox `apz.content_response_timeout`), потом прокручивать. Неотрисованные области заливать цветом canvas страницы, а не белым. fixed- и sticky-элементы сдвигаются в том же кадре, что и контент. Кадры идут по vsync реального монитора (60/120/144/165/240 Гц), без пропусков при переносе окна между мониторами с разной частотой.
- Кто делает лучше / хуже: Chrome и Firefox (APZ) прокручивают асинхронно. На рывки при высокой частоте жалуются у Chromium на Windows; на Wayland с NVIDIA — у всех браузеров (монитор 170 Гц, прокрутка 90–100 fps).
- Источники: https://learn.microsoft.com/en-us/answers/questions/3876914/chrome-based-browser-stutter-when-scrolling ; https://bugzilla.mozilla.org/show_bug.cgi?id=1585378 ; https://forums.developer.nvidia.com/t/stutering-and-low-fps-scrolling-in-browsers-on-wayland-when-gsp-firmware-is-enabled/311127

**Клавиатурная прокрутка: шаги, цель, Space на кнопках** · часто · тяжесть средняя · у ChatGPT: нет
- Боль: «нажимаю пробел, чтобы листать, а нажимается кнопка или видео встаёт на паузу». «Стрелки не прокручивают блок, по которому я кликнул». «Стрелки перестали прокручивать» — случайно включился каретный режим F7.
- Как должно быть: стрелка — 40 px (Chromium `kPixelsPerLineStep`); при удержании — непрерывная плавная прокрутка, а не дёрганые шаги автоповтора. Page Up/Down и Space/Shift+Space — шаг из пункта про шапки, Home/End — к началу и концу. Если фокус на кнопке, чекбоксе или в поле, Space действует на этот элемент, иначе листает. Цель клавиш: скроллер с фокусом, иначе последний кликнутый скроллер, иначе корень (порядок не проверен по коду). Скроллер без фокусируемых потомков попадает в Tab-порядок (keyboard-focusable scroll containers), чтобы его можно было прокрутить без мыши. Включённый каретный режим F7 меняет смысл стрелок, и это должно быть видно.
- Кто делает лучше / хуже: Chrome — 40 px на стрелку и 87,5% на страницу. Фокусируемые скроллеры там окончательно включены в 132 (январь 2025); раскатки в 127 и 130 откатывали из-за проблем совместимости с сайтами и регрессии доступности. Firefox — шаг стрелки в строках шрифта, страница минус min(10%, 2 строки).
- Источники: https://github.com/chromium/chromium/blob/main/cc/input/scroll_utils.h ; https://chromestatus.com/feature/5231964663578624 ; https://www.askvg.com/fix-arrow-keys-not-scrolling-webpages-navigating-through-text-in-google-chrome/

**Автопрокрутка средней кнопкой (autoscroll)** · часто · тяжесть средняя · у ChatGPT: нет
- Боль: «в Chrome на Linux и Mac нет прокрутки средней кнопкой» — запросы с 2015 года, флаги Brave, расширения. Новички: «курсор стал кружком со стрелками, как убрать» (Яндекс Кью).
- Как должно быть: средний клик вне ссылки и поля ставит значок-якорь с доступными направлениями (только вертикаль, если горизонтально прокручивать нечего). Скорость растёт с расстоянием от якоря, вокруг якоря мёртвая зона в несколько px (размер зоны и кривая скорости не проверены, ориентир — Firefox на Windows). Режимов два. Если кликнуть и отпустить, режим держится до следующего клика. Если зажать и тащить, он заканчивается при отпускании. Выход по любой клавише, Esc или клику. Прокручивается ближайший скроллер под якорем. Средний клик по ссылке открывает фоновую вкладку и автопрокрутку не включает. На Linux средний клик вставляет PRIMARY selection, поэтому там автопрокрутка по умолчанию выключена и включается в настройках.
- Кто делает лучше / хуже: Firefox — включено на Windows и macOS, выключено на Linux (`general.autoScroll`). Chrome — код есть на всех платформах, но включено только на Windows (MiddleClickAutoscroll). Brave — флаг `middle-button-autoscroll`.
- Источники: https://issues.chromium.org/issues/41195637 («Implement middle-click autoscroll on all platforms», 20★, с 2015); https://andreer.no/blog/autoscroll-in-chrome-on-macos ; https://yandex.ru/q/question/kak_otkliuchit_avtomaticheskuiu_prokrutku_b083da2f/

### Прокрутка: удержание места чтения

**Восстановление позиции при Назад/Вперёд и перезагрузке** · массово · тяжесть высокая · у ChatGPT: вскользь
- Боль: «нажимаю Назад и оказываюсь в начале списка, хотя был на 120-м товаре». «Позиция держится миллисекунду и прыгает наверх» (bug 518181). Хуже всего с бесконечными лентами, eBay и Reddit.
- Как должно быть: (1) bfcache — мгновенно и точно; без нужды страницу из него не выбрасывать (поводы: unload, no-store, открытые соединения). (2) Без bfcache восстанавливать сохранённую позицию и повторять попытки по мере подгрузки контента, пока пользователь сам не прокрутит (Gecko `ScrollToRestoredPosition`). (3) Сохранять не только пиксели, но и якорь: элемент и смещение от него. Иначе позиция ломается при `content-visibility: auto` и поздних картинках над точкой чтения. (4) Соблюдать `history.scrollRestoration = 'manual'`: SPA восстанавливают позицию сами. (5) При перезагрузке позицию тоже восстанавливать, как делают Chrome и Firefox (спор в whatwg/html#10597). Вложенные скроллеры — по тем же правилам, что корень.
- Кто делает лучше / хуже: Chrome массово включил bfcache с версии 96. У Firefox многолетний хвост багов: 217120, 258133, 518181, 1123161, 1173474 (eBay), 1723282 (bfcache при Fission). Часть таких «багов» — сайты без bfcache, с бесконечной лентой или ручным scrollRestoration.
- Источники: https://bugzilla.mozilla.org/show_bug.cgi?id=518181 ; https://bugzilla.mozilla.org/show_bug.cgi?id=1106280 («на reddit.com восстановление не работает никогда»); https://github.com/w3c/csswg-drafts/issues/6225 (Facebook: якорь-элемент вместо пикселей)

**Scroll anchoring: защита от скачков при догрузке и от самого anchoring** · часто · тяжесть высокая · у ChatGPT: вскользь
- Боль: «читаю, сверху догрузилась реклама или картинка — текст уехал». Обратная беда: «лента Facebook прыгает туда-сюда, не могу вернуться к посту» (Firefox bug 1779404: 183 комментария, 15 месяцев; пользователи отключали `layout.css.scroll-anchoring.enabled`).
- Как должно быть: по CSS Scroll Anchoring якорь — первый видимый in-flow элемент в scrollport, после reflow позиция прокрутки сдвигается вслед за якорем. Корректировку подавлять при изменении position/top/left/transform/размеров на пути к якорю и при `overflow-anchor: none`. Защита от петли как в Firefox: после 10 подряд корректировок без пользовательской прокрутки (окно 500 мс) проверить среднюю корректировку и отключить anchoring для этого скроллера, если она меньше 2 CSS px (`max-consecutive-adjustments=10`, `max-consecutive-adjustments-timeout-ms=500`, `min-average-adjustment-threshold=2`). Если содержимое укоротилось, сначала заново ограничить последнюю асинхронную позицию новым диапазоном прокрутки, иначе страница скачет на экран назад. Это и был корень бага 1779404, исправленного в Fx120. Корректировки из обработчиков scroll браузеры обрабатывают по-разному, отсюда расхождения с Chrome. Прогнать WPT css-scroll-anchoring, включая after-scrollable-range-shrinkage.html.
- Кто делает лучше / хуже: Chrome — с версии 56 (2017); по данным Chromium Blog, anchoring предотвращает около трёх скачков на один просмотр страницы. Firefox — с версии 66, Safari — с Safari 27 (14.09.2026). На «прыгающий Facebook» жаловались и в Chrome (1346847), и в Firefox.
- Источники: https://bugzilla.mozilla.org/show_bug.cgi?id=1779404 (183 комментария); https://blog.chromium.org/2017/04/scroll-anchoring-for-web-developers.html ; https://lists.w3.org/Archives/Public/public-css-archive/2022Sep/0754.html

### Прокрутка: вложенные скроллеры и жесты тачпада

**Вложенные скроллеры: куда идёт колесо и когда прокрутка передаётся родителю** · часто · тяжесть высокая · у ChatGPT: вскользь
- Боль: «докрутил список в модальном окне до конца — поехала страница под ним». «Кручу страницу, курсор наехал на карту или iframe — прокрутка застряла там».
- Как должно быть: цель колеса — самый внутренний скроллер под курсором, который может прокрутиться в этом направлении. Цель закрепляется на всю серию щелчков (wheel transaction): в Firefox `mousewheel.transaction.timeout=1500` мс со сбросом при движении мыши. Если серия началась у края внутреннего скроллера, она уходит родителю. Если серия началась внутри, она не перескакивает на родителя, даже когда скроллер упёрся в край, — так страница не «утекает» из модального окна. `overscroll-behavior: contain | none` обрывает цепочку. Это работает и на scroll container без переполнения (overflow: hidden или auto без лишнего контента; пример в Chrome — `::backdrop` с overflow: hidden), но не на элементах, которые не являются scroll container. Выбор цели для клавиатуры — в пункте про клавиатурную прокрутку.
- Кто делает лучше / хуже: в основном поведение браузеров совпадает, различаются таймауты закрепления. Chrome соблюдает overscroll-behavior на scroll container без переполнения с версии 144 (stable 13.01.2026). Без contain модальные окна пропускают прокрутку на страницу — частый баг сайтов, которые пытаются закрыть его через `body { overflow: hidden }`.
- Источники: https://ishadeed.com/article/prevent-scroll-chaining-overscroll-behavior/ ; https://blog.openreplay.com/stop-page-scrolling-dialog-open/ ; https://github.com/Moistbobo/vrc-world-dashboard/issues/332

## Анти-цели области

- Ни одного белого кадра в тёмной теме: ни при создании окна, ни при ресайзе и разворачивании, ни на about:blank, новой вкладке или при навигации.
- Не переопределять явные настройки ОС «ради дизайна»: число строк колеса, «Всегда показывать полосы прокрутки», «Анимация элементов управления», «Размер текста», ClearType Tuner, выключенное сглаживание. Подстраивать можно только значения по умолчанию.
- Не делать полосы прокрутки тоньше системных и не сужать зону попадания до видимой части; не гасить полосу, если в ОС включено «Всегда показывать».
- Не запускать анимацию плавной прокрутки заново на каждом щелчке колеса и не анимировать повторно инерцию тачпада. Выключатель плавности не прятать во флаги.
- Не блокировать прокрутку ожиданием JS дольше таймаута и не показывать на месте неотрисованного контента белое.
- Не давать scroll anchoring бороться с пользователем: при петле корректировок anchoring для скроллера выключается.
- Не менять сайтам `WheelEvent.deltaY` при изменении фактического шага прокрутки.
- Не уводить страницу Назад горизонтальным свайпом посреди прокрутки и не терять при этом введённые в форму данные.
- Не сбрасывать Ctrl+0 к 100% вместо масштаба по умолчанию, не скрывать нестандартный масштаб и не превращать щипок тачпада в скачки 100 → 110 → 125%.
- Не включать субпиксельное сглаживание на OLED, при неизвестной структуре пикселей, на прозрачных и анимируемых слоях.
- Не рисовать стандартную ссылку #0000EE на тёмном canvas и не оставлять белые полосы прокрутки и поля на тёмных страницах.
- Не инвертировать фото и не затемнять принудительно сайты, объявившие `color-scheme: dark`; не терять индикатор фокуса в принудительной тёмной теме.
- Не прятать доступность (масштаб только текста, минимальный размер шрифта, шрифты по письменности, сглаживание текста) в about:config и флагах.
- Не печатать в тёмной схеме и с текущей позиции прокрутки по умолчанию.
