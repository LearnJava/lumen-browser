# Ввод текста: каретка, куда печатаются символы, раскладки, IME

## Главное в области

1. **Почти все болезненные дефекты ввода относятся к одному классу: фокус рассинхронизирован между ОС, интерфейсом браузера и DOM страницы.** Сюда входят потерянные первые символы после Ctrl+T, autofocus, который перехватывает ввод, каретка, пропавшая после диалога или Alt+Tab, и две мигающие каретки на двух мониторах. Точечные исправления этот класс не закрывают. Нужен единый арбитр фокуса: через него проходит любой запрос фокуса, и от страницы, и от интерфейса браузера. У арбитра есть флаг «пользователь сейчас печатает здесь», аналог `user_input_in_progress` в адресной строке Chromium.
2. **Собственный движок рисует каретку сам и поэтому теряет всё, что ОС бесплатно даёт нативным полям.** Это толщина каретки, ритм и таймаут мигания, слежение Лупы, индикатор текстового курсора Windows 11, позиция окна кандидатов IME, индикаторы раскладки и Caps Lock в macOS. Каждую вещь нужно подключить явно: `SPI_GETCARETWIDTH`, `SPI_GETCARETTIMEOUT`, `GetCaretBlinkTime`, перечитывание по `WM_SETTINGCHANGE`, невидимая системная каретка (`CreateCaret`/`SetCaretPos`), UIA TextPattern, TSF `GetTextExt`. В Chromium для этого есть отдельный класс `AXSystemCaretWin`.
3. **Для русскоязычной аудитории главное отличие — работа с раскладкой, а не IME.** Что нужно:
   - горячие клавиши по физической клавише, но с приоритетом латинского символа, иначе ломаются Dvorak и AZERTY;
   - accesskey, работающий в ЙЦУКЕН: в Chrome 153 не работает, в Firefox работает;
   - переключение раскладки по Alt+Shift и Ctrl+Shift не трогает меню и команды;
   - подсказка «Исправлена раскладка» в адресной строке и в Ctrl+F (сейчас есть только в Яндекс Браузере);
   - индикатор RU и ⇪ в поле пароля.
4. **Есть дешёвые места, где можно сразу обойти Chrome и Firefox.**
   - Системную толщину каретки не учитывает ни один крупный браузер.
   - Chrome и Edge мигают кареткой бесконечно.
   - Индикатора Caps Lock в поле пароля нет в Chrome на Windows (crbug 6403), а запрос в Firefox открыт с 2004 года (46 голосов).
   - Принудительной вставки при заблокированном paste нет ни у кого.

   Это мелочи, но пользователь их заметит и запомнит.
5. **Два правила обработки клавиш нужно заложить в архитектуру, а не делать отдельными фичами.**
   - (а) Любой обработчик клавиш в интерфейсе браузера сначала проверяет, идёт ли IME-композиция. Это касается Enter в адресной строке, Esc в диалогах и fullscreen, F7, Tab для принятия подсказки и горячих клавиш.
   - (б) Одиночная клавиша без модификаторов вне поля ничего не стирает и никуда не уводит: фокус выпадает из поля чаще, чем кажется.

   К правильным решениям браузеры приходили после многолетних жалоб. Backspace-назад убран в Chrome 52 (2016) и в Firefox 86. Проверка орфографии на нескольких языках сразу появилась в Firefox только в версии 100 (2022). Остановка мигания — в Firefox 93 (2021). Новому браузеру стоит брать эти решения сразу.
6. **Приватность ввода незаметна пользователю, но обязательна для браузера, который называет себя приватным.** В приватных окнах и в полях паролей IME и сенсорная клавиатура не должны обучаться на вводе. Для этого есть флаги: `IS_PRIVATE` (TSF), `IBUS_INPUT_HINT_PRIVATE`, `IME_FLAG_NO_PERSONALIZED_LEARNING`. Облачное предсказание текста и «улучшенная» проверка орфографии включаются только по явному согласию и никогда в приватном режиме.

Числовые ориентиры области:

| Параметр | Значение |
|---|---|
| Ритм мигания, Windows | `GetCaretBlinkTime()`, по умолчанию 530 мс на фазу (не проверено); 0 или `INFINITE` — не мигать |
| Остановка мигания | Windows `CaretTimeout` 5000 мс; GTK `gtk-cursor-blink-timeout` 10 с; в macOS таймаута нет |
| WCAG F50 | мигание дольше 5 с без способа остановить — нарушение |
| Толщина каретки | `CaretWidth` (1–20) × масштаб DPI монитора, не меньше 1 физического пикселя |
| Эхо символа | в том же кадре: ≤ 16 мс при 60 Гц, p99 < 50 мс (целевое значение исследования) |
| Задержка Enter/↓/Tab до прихода подсказок | ≤ 200–300 мс (Firefox: 300 мс, `browser.urlbar.eventBufferer.deferringTimeoutMs`) |
| Контраст каретки с фоном | ≥ 3:1 (WCAG 1.4.11; рекомендация) |
| Ввод с машинной скоростью | 1000 символов/с без потерь при занятом main thread (задачи по 200 мс) |

В документе ChatGPT эта область покрыта строками M01–M03 и сценарием J02. Нет раскладок, орфографии, блокировки вставки, Backspace-навигации, потери первых символов, Caps Lock, приватности IME, подстановок macOS, перемещения по словам и колеса в поле number.

## Находки

### Куда уходят символы: фокус и доставка ввода

**Кража фокуса при загрузке: страница вызвала autofocus или focus() и перехватила ввод** · массово · тяжесть: высокая · у ChatGPT: вскользь
- Боль: половина URL остаётся в адресной строке, остальное уходит в поиск стартовой страницы. Другой случай: пользователь начал заполнять форму, пока страница грузится, скрипт перевёл фокус, и пробел открыл автокомплит вместо прокрутки. На медленной сети это происходит постоянно; ради этого существует отдельное расширение Stop Autofocus.
- Как должно быть:
  - Правило 1. Фокус, запрошенный страницей (`autofocus`, `element.focus()`, `window.focus()`), никогда не забирает клавиатурный фокус у интерфейса браузера: адресной строки, поиска по странице, диалогов. Если страница не в фокусе, меняется только `document.activeElement` внутри неё.
  - Правило 2. Если с начала навигации уже был пользовательский ввод (keydown в любом поле, клик, прокрутка), `autofocus` и программный `focus()` во время загрузки игнорируются. Это расширение правила HTML, по которому autofocus блокируется, если в документе уже есть элемент в фокусе или в URL есть фрагмент.
  - Правило 3. После Enter в адресной строке фокус переходит в страницу. Если пользователь снова начал печатать в адресной строке, коммит навигации и загрузка не забирают фокус и не сбрасывают набранный текст.
  - Приёмка: страница со `setTimeout(focus, 300…3000 мс)`, в адресную строку автоматически вводится 10 символов/с. В страницу не должно уйти ни одного символа.
- Кто делает лучше / хуже:
  - Chrome: новая вкладка отдаёт клавиатурный фокус сначала адресной строке, и расширение, подменяющее страницу новой вкладки, его не забирает. Регрессия 40313398 в dev-версии 28 исправлена с приоритетом P1. Blink блокирует autofocus при фрагменте в URL (40670785, Chrome 79). Отдаёт ли Chrome фокус странице при `focus()` во время набора в адресной строке — не проверено.
  - Firefox: bug 1270677 открыт с 2016 года. Там предложено не переводить фокус в страницу, если в адресной строке есть набранный пользователем текст и это первая смена фокуса из-за загрузки. Отдельная ошибка, когда фоновая вкладка забирала фокус через `textbox.focus()` (124750), исправлена в 2009 году.
- Источники: https://bugzilla.mozilla.org/show_bug.cgi?id=1270677 · https://developer.chrome.com/docs/extensions/develop/ui/override-chrome-pages · https://chromewebstore.google.com/detail/stop-autofocus-%E2%80%93-prevent/gdlpfppedknpakeenimmcoiccohhlccm (спрос на блокировку autofocus)

**Первые символы теряются, если печатать сразу после Ctrl+T, Ctrl+L или открытия окна** · часто · тяжесть: высокая · у ChatGPT: нет
- Боль: нажал Ctrl+T, сразу печатаешь, а первые 1–3 буквы исчезают. Либо адресная строка очищается, когда догружается страница новой вкладки, либо всё набранное вдруг выделяется и затирается следующим символом. Обход «подождать секунду» идёт против мышечной памяти.
- Как должно быть:
  - Адресная строка принимает ввод сразу после keydown Ctrl+T. Нажатия, пришедшие до готовности интерфейса, сохраняются в буфер и воспроизводятся по порядку.
  - Пока в адресной строке пользовательский текст, её текст и выделение не меняются: ни при загрузке страницы новой вкладки (своей или из расширения), ни при появлении значков.
  - Выделить всё можно только в момент получения фокуса, никогда посреди набора.
  - Когда вкладку перетаскивают в новое окно, фокус и текст адресной строки сохраняются.
  - Приёмка: SendInput «Ctrl+T, затем 20 символов с интервалом 30 мс» × 100 прогонов, холодный и тёплый старт, с расширением для новой вкладки и без. Строка совпадает в 100% прогонов.
- Кто делает лучше / хуже:
  - Firefox 1427535 (заведён в 2018 году на Fx57, в 2020 году проявился снова, около Fx80; 10 голосов, NEW, P5): адресная строка очищается, когда в ней появляется значок «Extension». То же описано в Tridactyl #2840.
  - Brave #3756: адрес целиком выделялся посреди набора. Приоритет P1, исправлено в 0.63.x.
  - Vivaldi на Android с внешней клавиатурой: команда воспроизвела ошибку, обход — дождаться иконки поисковика и курсора.
  - Firefox iOS #10054: всё, набранное за первые ~0,5 с, стирается. Закрыто как not planned.
  - Firefox 1602396 (фокус терялся при перетаскивании вкладки в новое окно) исправлен в Fx91.
- Источники: https://bugzilla.mozilla.org/show_bug.cgi?id=1427535 (10 голосов) · https://github.com/brave/brave-browser/issues/3756 · https://forum.vivaldi.net/topic/113212/first-character-in-new-tab-search-bar-disappears

**Ввод с машинной скоростью: сканеры штрихкодов, YubiKey, переключатели раскладки — без потерь и без склейки повторов** · редко · тяжесть: высокая · у ChatGPT: нет
- Боль: сканер или YubiKey «печатает» с интервалом в несколько миллисекунд. Браузер теряет символы или пропускает повторяющиеся, поэтому OTP не проходит, а артикул искажается.
- Как должно быть:
  - Клавиатурные события не объединяются и не отбрасываются, даже когда main thread занят. Очередь ввода сохраняет порядок.
  - Одинаковые символы подряд с интервалом от 1 мс доставляются все. OTP YubiKey начинаются с серии одинаковых букв вроде «cccc» (не проверено).
  - Синтетический ввод через `SendInput` обрабатывается так же, как реальный, в том числе на фоне inline-дополнения в адресной строке. Пример — Punto Switcher, менеджеры паролей и AutoHotKey, которые шлют Backspace×N и печатают текст заново.
  - Приёмка: 1000 символов/с в textarea, input и адресную строку при искусственно занятом main thread (задачи по 200 мс). Результат совпадает побайтно.
- Кто делает лучше / хуже:
  - Firefox 1098981 [GTK] (символы сканеров терялись) исправлен в 2026 году, ветка 154. Firefox 1237708 (YubiKey, пропуск повторяющихся символов) в статусе UNCONFIRMED.
  - По Chrome есть только косвенные данные: тормоза при переключении вкладок вместе с Punto Switcher (Habr Q&A, ответ не принят автором).
- Источники: https://bugzilla.mozilla.org/show_bug.cgi?id=1098981 · https://bugzilla.mozilla.org/show_bug.cgi?id=1237708 · https://qna.habr.com/q/757505

### Сохранность набранного текста

**Одиночная клавиша вне поля не уничтожает введённое: Backspace ≠ «Назад»** · массово · тяжесть: критично · у ChatGPT: нет
- Боль: фокус выпал из поля (клик мимо, скрипт снял фокус), пользователь нажал Backspace, браузер ушёл на предыдущую страницу, и заполненная форма потерялась. Годами одна из самых злых жалоб.
- Как должно быть:
  - Backspace вне редактируемого элемента ничего не делает: ни навигации, ни прокрутки.
  - «Назад» — это Alt+←, в macOS Cmd+[ или Cmd+←, кнопка мыши X1, жест.
  - Общее правило: одиночная клавиша без модификаторов вне поля не запускает разрушительных или навигационных действий без подтверждения.
  - Если навигация всё-таки уводит со страницы с изменённой формой, срабатывает `beforeunload` сайта. Состояние формы при этом сохраняется в истории (см. «Набранный текст переживает перезагрузку…»), и «Вперёд» возвращает текст.
- Кто делает лучше / хуже:
  - Chrome 52 (июль 2016) убрал Backspace-назад. По данным UseCounter, назад по Backspace уходили 0,04% просмотров страниц, а 0,005% — сразу после работы с формой. То есть больше 10% таких переходов случались после ввода в форму.
  - Firefox сделал то же в Fx86 (bug 1041377, `browser.backspace_action=2`) на основе тех же цифр.
- Источники: https://9to5google.com/2016/05/20/chrome-52-backspace-shortcut-gone/ · https://bugzilla.mozilla.org/show_bug.cgi?id=1041377 (3 дубля) · https://news.ycombinator.com/item?id=11729287

**Набранный текст переживает перезагрузку, закрытие вкладки, «Назад/Вперёд» и падение** · массово · тяжесть: высокая · у ChatGPT: вскользь
- Боль: человек писал длинный комментарий или заявку, нажал F5, Ctrl+W или «Назад», либо вкладка упала, и текст пропал. Именно потеря данных была главным мотивом Chrome, когда он отказывался от Backspace-назад.
- Как должно быть:
  - Состояние полей хранится в записи истории и в сессии. Это значения input и textarea, кроме password, hidden, полей с `autocomplete=off` и полей OTP или номера карты.
  - Состояние восстанавливается при «Назад/Вперёд» (с bfcache и без него), при Ctrl+Shift+T, при восстановлении после падения и, если включено, при F5. При Ctrl+F5 не восстанавливается.
  - Пользователь закрывает вкладку или окно, а в поле изменённый им текст длиннее порога (например, 200 символов — рекомендация), и у сайта нет `beforeunload`. Тогда браузер тихо сохраняет черновик и возвращает его по Ctrl+Shift+T, без диалога.
  - contenteditable восстанавливается, только если сайт явно не против (дополнительная функция, настраивается по сайтам). Документы в `designMode` (rich-text iframe) восстанавливаются так же, как в Firefox.
- Кто делает лучше / хуже:
  - Chrome после F5 поля не восстанавливает: Blink применяет сохранённое состояние формы только при `IsBackForwardOrRestore`. При «Назад/Вперёд» восстанавливает, в том числе без bfcache (document state хранится в HistoryItem), и при восстановлении сессии.
  - Firefox: хранилище сессии сохраняет поля и `innerHTML` body документов в `designMode`. Отдельные элементы contenteditable не сохраняет. Что Firefox восстанавливает поля после F5 — по памяти, не проверено.
- Источники: https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/loader/document_loader.cc · https://raw.githubusercontent.com/mozilla-firefox/firefox/main/toolkit/components/sessionstore/SessionStoreUtils.cpp · https://www.ghacks.net/2016/05/21/chrome-52-blocks-backspace-back-navigation/

**Колесо мыши над полем number не меняет значение незаметно для пользователя** · часто (массовость жалоб не подтверждена источником) · тяжесть: средняя · у ChatGPT: нет
- Боль: пользователь ввёл количество или сумму, прокручивает страницу колесом, курсор оказывается над полем, и число тихо меняется.
- Как должно быть:
  - По умолчанию колесо над `input[type=number]` и `range` прокручивает страницу и не меняет значение.
  - Колесо меняет значение, только если поле в фокусе и пользователь после этого явно навёл на него курсор, либо если это включено в настройках.
  - ↑/↓ в поле с фокусом меняют значение на `step`.
  - У полей с `inputmode=numeric` без `type=number` кнопки прокрутки значения не появляются.
- Кто делает лучше / хуже:
  - Лучше Firefox: `dom.input.number_and_range_modified_by_mousewheel=false`, колесо над number или range в фокусе прокручивает страницу.
  - Хуже Chrome: колесо меняет значение поля в фокусе. В Blink условие `ShouldSpinButtonRespondToWheelEvents` требует `IsFocused()`, шаг берётся по `wheelDeltaY`.
- Источники: https://raw.githubusercontent.com/mozilla-firefox/firefox/main/modules/libpref/init/StaticPrefList.yaml · https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/html/forms/text_field_input_type.cc

### Раскладки и горячие клавиши

**Горячие клавиши в нелатинской раскладке: по физической клавише, но без поломки Dvorak и AZERTY** · массово · тяжесть: высокая · у ChatGPT: нет
- Боль:
  - В веб-клиентах Ctrl+C/V/F не срабатывают, пока не переключишь раскладку.
  - В Chrome 153 на Windows с русской раскладкой не работает ни один accesskey Alt+буква, кроме Alt+=.
  - В Linux с раскладкой Russian Phonetic Ctrl+A закрывал Firefox, как Ctrl+Q (1500834). Баг закрыт как WORKSFORME в 2021 году, причина не установлена.
  - До Firefox 3 нелатинская раскладка в Linux ломала все сочетания с Ctrl (69230).
- Как должно быть:
  - Горячие клавиши браузера (Ctrl+T, W, L, F, Shift+T, D, H…) сопоставляются так. Если текущая раскладка даёт для клавиши латинский символ, берётся он: так сохраняются Dvorak и AZERTY. Если символ нелатинский (кириллица, греческий, иврит, арабский), берётся символ той же скан-клавиши в US QWERTY или в первой установленной латинской раскладке.
  - Платформы: Windows — по VK-коду; macOS — `charactersIgnoringModifiers` ASCII-совместимой раскладки; Linux — первая латинская группа XKB.
  - То же правило действует для accesskey страницы (Alt+буква / Alt+Shift+буква) и для команд редактирования Ctrl+A/C/V/X/Z/Y в полях.
  - В `KeyboardEvent` передаём `key` = «с» (кириллица) и `code` = «KeyC», чтобы сайт выбирал сам.
  - Приёмка: все сочетания из справки работают в раскладках RU, UA, BY, KZ (ЙЦУКЕН), Russian Phonetic, Dvorak и AZERTY, и ни одно не вызывает другую команду.
- Кто делает лучше / хуже:

**Переключение раскладки не вызывает меню и команды, раскладка не «прыгает» между вкладками** · часто · тяжесть: средняя · у ChatGPT: нет

**Мигание каретки: ритм из ОС, остановка после бездействия, после остановки каретка остаётся видимой** · часто · тяжесть: средняя · у ChatGPT: вскользь
- Боль: каретка мигает бесконечно. Это отвлекает, а на ноутбуке тратит батарею: каждая смена фазы будит main thread, renderer и compositor. В VS Code мигающая каретка в простое давала 13% CPU. Утверждение, что пользователи Firefox 110 приняли остановку мигания за баг, не проверено: тред SUMO не открылся.
- Как должно быть:
  - Ритм мигания берём из ОС:
    - Windows: `GetCaretBlinkTime()`. По умолчанию 530 мс на фазу (не проверено); 0 или `INFINITE` — не мигать, рисовать сплошной;
    - macOS: `NSTextInsertionPointBlinkPeriodOn/Off`;
    - GTK: `gtk-cursor-blink`, `gtk-cursor-blink-time`.
  - Остановка мигания после бездействия:
    - Windows: `SPI_GETCARETTIMEOUT` (реестр `HKCU\Control Panel\Desktop\CaretTimeout`, по умолчанию 5000 мс);
    - GTK: `gtk-cursor-blink-timeout` (10 с);
    - в macOS системного таймаута нет.
  - После таймаута каретка остаётся видимой, а не гаснет.
  - Любое нажатие клавиши, движение каретки, клик или вставка сразу показывают каретку, начинают видимую фазу заново и сбрасывают таймер. Пока пользователь непрерывно печатает, каретка не мигает.
  - Настройки перечитываются по `WM_SETTINGCHANGE` без перезапуска.
  - Мигание делается анимацией прозрачности на композиторе, без перерисовки в main thread.
  - CSS `caret-animation: manual` (Chrome 140) отключает мигание браузера для конкретного элемента.
  - По WCAG F50 мигание дольше 5 с без способа его остановить — нарушение.
- Кто делает лучше / хуже:
  - Лучше всех Firefox. С Fx93 (bug 1724405, 2021) он останавливает мигание по `CaretTimeout` на Windows и по настройке GTK, и каретка остаётся видимой. Pref `ui.caretBlinkCount` появился в Fx40 после отзывов партнёров о расходе энергии; значение по умолчанию задано только для Android.
  - Хуже всех Chrome и Edge. Ритм они берут из Windows (с M31, 2013) и из macOS (с 2016 года), но по таймауту не останавливаются: по наблюдению Igalia, каретка мигает с постоянной частотой без конца.
- Источники: https://bugzilla.mozilla.org/show_bug.cgi?id=1724405 · https://codereview.chromium.org/24288004 · https://news.ycombinator.com/item?id=13940014

**Каретка на границе мягкого переноса (affinity), Home/End и движение вверх-вниз** · редко · тяжесть: средняя · у ChatGPT: нет
- Боль: на перенесённой строке нажимаешь End, а каретка оказывается в начале следующей строки. Стрелки ↑/↓ сдвигают каретку на символ, на коротких строках теряется колонка. После программной установки выделения каретка прыгает на следующую строку.
- Как должно быть:
  - У каретки есть affinity: upstream (привязка к концу строки) или downstream (к началу следующей). End и клик правее конца визуальной строки дают upstream, и каретка рисуется в конце этой строки. Ввод символа и горизонтальные стрелки дают downstream.
  - Home и End работают по визуальной строке, а не по абзацу, в textarea тоже.
  - ↑/↓ сохраняют целевую позицию по x (goal column) при проходе через короткие и пустые строки. Любое горизонтальное движение или клик её сбрасывают.
  - Высота и позиция каретки на стыке шрифтов берутся по символу с той стороны, к которой привязана каретка.
  - `Selection.collapse` и `addRange` со смещением, равным точке переноса, дают downstream, как в Chrome, чтобы не ломать сайты. Внутренний affinity при перерисовке при этом не теряется.
- Кто делает лучше / хуже:
  - В нативных textarea и contenteditable Chrome и Firefox ставят каретку в конец перенесённой строки правильно.
  - Chrome хранит affinity внутри, но через веб-API его не отдаёт (w3c/editing#189). Поэтому редакторы, которые ставят каретку программным Range (CodeMirror 5 #6274), не могут поставить её в конец такой строки.
  - Firefox 1475232 (↑/↓ в contenteditable с flex/grid) исправлен в Fx103. Баги 813040 (`addRange` переносит каретку) и 968518 в статусе UNCONFIRMED.
  - Без affinity при движении вверх-вниз в CJK теряется колонка (rinch #941).
- Источники: https://github.com/w3c/editing/issues/189 · https://github.com/codemirror/codemirror5/issues/6274 · https://bugzilla.mozilla.org/show_bug.cgi?id=813040

### Адресная строка как поле ввода

**Автодополнение в строке и «призрачный текст»: не перебивать быстрого пользователя** · массово · тяжесть: средняя · у ChatGPT: вскользь
- Боль: набираешь gist.g…, а из истории дописывается опечатка gist.gihub.com, и Enter ведёт туда. В Chrome автодополнение прямо в строке отключить нельзя. В Edge серые подсказки text prediction в полях страниц принимаются по Tab и мешают переходить по форме.
- Как должно быть:
  - Адрес дописывается прямо в строке только для хостов, которые пользователь сам набирал или открывал не меньше N раз, и только до конца хоста или сегмента пути. Порог N — рекомендация.
  - Дописанная часть выделена. Если следующий набранный символ совпадает с ней, он её «съедает», если не совпадает — заменяет.
  - Backspace или Delete убирают дописанную часть одним нажатием.
  - Shift+Delete или крестик в подсказке удаляют запись навсегда, и она не появляется снова.
  - Есть настройка «не дописывать адрес в строке».

**Задержка появления символов в адресной строке и предсказуемый Enter после быстрого набора** · часто · тяжесть: высокая · у ChatGPT: вскользь

  - Если Enter, ↓ или Tab нажаты раньше, чем обновились подсказки, нажатие ждёт результатов, но не дольше 200–300 мс. Так «↓ Enter» по мышечной памяти выбирает ожидаемую строку.

Баги 1530012 (тормоза в адресной строке) закрыт как INVALID, 1065499 (около 0,5 с задержки в полях, 2014) в статусе UNCONFIRMED.

### Редактирование и буфер обмена

**Сайты запрещают вставку (и копирование): у пользователя должен быть способ вставить** · часто · тяжесть: высокая · у ChatGPT: нет
- Боль: поля «повторите пароль», номер карты, ИНН или e-mail не дают нажать Ctrl+V, и менеджер паролей с генератором становятся бесполезны. Пользователи ставят расширения вроде «Don't F*** With Paste» или в Firefox глобально отключают события буфера обмена, из-за чего ломаются редакторы.
- Как должно быть:
  - Обычная вставка работает по спецификации: срабатывает событие `paste`, и сайт может вызвать `preventDefault`.
  - Отдельная команда браузера «Вставить принудительно» в контекстном меню поля и на сочетании клавиш (например, Ctrl+Shift+Alt+V). Она вставляет текст как обычный ввод пользователя: генерирует `beforeinput`/`input`, но не `paste`, поэтому запрет через `onpaste` её не видит.
  - Команда работает только в поле, куда пользователь сам поставил фокус.
  - Автозаполнение из менеджера паролей браузера не зависит от `onpaste`.
  - Для текста с `user-select:none` и запретом через `oncopy` — команда «Копировать выделенное принудительно».
  - Это включается для отдельных сайтов, а не общим выключателем событий буфера обмена.
- Кто делает лучше / хуже:
  - Хорошего решения нет ни у кого, здесь можно выделиться.
  - Chrome и Edge — только расширения. Одну из версий «Don't F*** With Paste» удалили из Chrome Web Store; дата 24.09.2025 не проверена. Расширение не помогает, если сайт перехватывает и keydown Ctrl+V.
  - Firefox — `dom.event.clipboardevents.enabled=false` в about:config. Это выключает события буфера для всех сайтов и ломает редакторы.
  - Safari — ничего.
  - Британский NCSC выступал против запрета вставки паролей. Статья сейчас снята с сайта, но есть в веб-архиве.
- Источники: https://addons.mozilla.org/en-US/firefox/addon/don-t-fuck-with-paste/ · https://www.ncsc.gov.uk/blog-post/let-them-paste-passwords · https://www.stationx.net/i-fcking-hate-this-blocking-password-pasting/

**Перемещение и удаление по словам: Ctrl+←/→, Ctrl+Backspace/Delete (Option в macOS) с учётом URL и пунктуации** · часто · тяжесть: средняя · у ChatGPT: нет
- Боль:
  - Ctrl+Backspace в адресной строке стирает не тот кусок. В Firefox на Windows в 2024 году «google.com» превращался в «gcom/» (не проверено: тред Connect не открылся).
  - Ctrl+→ останавливается не там, где в Word.
  - В Firefox Ctrl+Backspace при выделенном тексте только двигает каретку (не проверено).
- Как должно быть:
  - Границы слов определяются по UAX #29, для URL есть свои правила. В адресной строке и в полях `type=url`/`email` каретка останавливается на `/ . : ? = & # @ - _`, по одному сегменту за шаг, как в Chrome.
  - В обычном тексте:
    - знак препинания считается отдельным «словом»;
    - подчёркивание — часть слова (snake_case);
    - дефис внутри кириллического слова («кто-то») — граница для Ctrl+→, как в Word.
  - Windows: Ctrl+→ ставит каретку в начало следующего слова, пропуская пробел. Linux: Ctrl+→ ставит каретку в конец текущего слова. На обеих платформах Ctrl+← ставит каретку в начало слова.
  - macOS: Option+→ — в конец текущего слова; Cmd+← и Cmd+→ — в начало и конец видимой строки; Cmd+Backspace удаляет текст до начала строки.
  - Если есть выделение, Ctrl+Backspace и Ctrl+Delete удаляют только его.
  - Двойной клик выделяет слово по тем же границам: в Windows вместе с пробелом после слова (настраивается), в macOS без него.
- Кто делает лучше / хуже:
  - Ближе всех к ожиданиям Chrome: в адресной строке Ctrl+Backspace стирает по одному сегменту. Пробел после слова Blink пропускает только в режиме Windows.
  - Firefox:
    - `layout.word_select.stop_at_punctuation=true` на всех платформах. На unix так с 2007 года (bug 190615); старые жалобы 245708 и 257922 на стирание всего URL закрыты как его дубли;
    - `layout.word_select.eat_space_to_next_word=true` только в Windows;
    - подчёркивание считается частью слова с Fx59 (196175).
- Источники: https://bugzilla.mozilla.org/show_bug.cgi?id=190615 (дубли 245708, 257922) · https://support.mozilla.org/en-US/questions/1266046 · https://support.mozilla.org/en-US/questions/1095090

**Отмена и повтор в полях: понятный шаг отмены и сохранность истории** · часто · тяжесть: средняя · у ChatGPT: вскользь
- Боль: Ctrl+Z в поле ничего не делает или стирает целый абзац. Если сайт сам поправил значение (маска телефона, React), откатить уже нельзя. Отмена вставки не возвращает выделение.
- Как должно быть:
  - У каждого поля своя история: Ctrl+Z, Ctrl+Y и Ctrl+Shift+Z (в macOS Cmd+Z и Cmd+Shift+Z) плюс пункты контекстного меню.
  - Непрерывный набор отменяется одним шагом. Шаг заканчивается, когда случается одно из событий:
    - пауза около 1 с (по памяти о нативных полях, не проверено, нужно замерить);
    - перемещение каретки;
    - смена ввода на удаление или наоборот;
    - вставка;
    - конец слова.
  - Вставка, вырезание, перетаскивание, автозамена и подтверждение IME — отдельные шаги.
  - Отмена восстанавливает и текст, и выделение, какими они были до операции.
  - Программное присваивание `.value` очищает историю; так делают все браузеры.
  - `execCommand('insertText')` и `setRangeText` с флагом пользовательского ввода (если он поддержан) попадают в историю и отправляют `input` с `inputType`.
  - В адресной строке Ctrl+Z после правки возвращает прежний текст, а Esc — исходный URL.
- Кто делает лучше / хуже:
  - Chrome и Safari поддерживают `execCommand('insertText')` в input и textarea с 2017 года, Firefox — с Fx89 (2021, bug 1220696).
  - Firefox 1523270: после присваивания `value` история теряется. Это сделано намеренно ради производительности (bug 1346723).
  - React #28369 и #5807: в управляемом поле отмена ломается при асинхронном `setState`.
  - Сайты пишут собственные истории правок (TextStack, text-field-edit). Discourse перешёл на `execCommand`, чтобы работала отмена.
- Источники: https://bugzilla.mozilla.org/show_bug.cgi?id=1523270 · https://github.com/fregante/text-field-edit · https://github.com/facebook/react/issues/28369

**Вставка без форматирования и вставка многострочного текста в однострочное поле** · часто · тяжесть: средняя · у ChatGPT: вскользь
- Боль:
  - В contenteditable (почта, CMS) вместе с текстом вставляются чужие шрифты и фон.
  - В Firefox Ctrl+Shift+V до 2022 года не работал.
  - В Safari на Mac работает только Opt+Shift+Cmd+V.
  - Если вставить в input адрес или номер с переводами строк, слова склеиваются.
- Как должно быть:
  - Windows и Linux: Ctrl+Shift+V вставляет обычный текст в input, textarea и contenteditable (`inputType=insertFromPaste`, только `text/plain`).
  - macOS: Cmd+Shift+V и Opt+Shift+Cmd+V (Paste and Match Style) делают одно и то же. Команда есть в меню Edit и в контекстном меню.
  - Обычный Ctrl+V в contenteditable вставляет очищенный HTML: структура сохраняется, скрипты и обработчики событий удаляются.
  - Вставка в однострочный input: переводы строк (CR/LF) заменяются пробелом, а не удаляются, чтобы слова не склеивались. Табуляция тоже заменяется пробелом.
  - В адресной строке и в полях `type=email`/`url`/`tel` пробелы в начале и в конце обрезаются.
  - Если у поля есть `maxlength`, вставка обрезается до лимита и поле подсвечивается, чтобы хвост не пропадал молча (рекомендация).
- Кто делает лучше / хуже:
  - Chrome, Edge и Firefox поддерживают Ctrl+Shift+V; Firefox — с версии 104 (2022, bug 968104).
  - Chrome на Mac принимает оба сочетания, Safari — только Opt+Shift+Cmd+V (проверка 2021 года).
  - Firefox в однострочном поле заменяет переводы строк пробелами: `editor.singleLine.pasteNewlines=2`, это значение по умолчанию.

### Проверка орфографии и автозамены

**Проверка орфографии: русский и английский одновременно, без ручного переключения** · массово · тяжесть: средняя · у ChatGPT: нет
- Боль: пишешь «открой pull request в main», и половина слов подчёркнута, потому что проверка идёт на одном языке. В Firefox до версии 100 (2022) словарь переключали вручную. Пользователи не находят, где включить язык, и не понимают, почему на конкретном сайте нет подчёркиваний.
- Как должно быть:
  - По умолчанию включены словари всех языков раскладок ОС, например RU и EN. Слово помечается ошибочным, только если его нет ни в одном активном словаре.
  - Рекомендации исследования (не сверены с поведением браузеров):
    - Ё и Е взаимозаменяемы;
    - не проверяются слова с цифрами, URL, e-mail, CamelCase и слова В ВЕРХНЕМ РЕГИСТРЕ.

  - Волнистая линия рисуется цветом ОС под базовой линией и не перекрывает нижние выносные элементы букв.
  - Контекстное меню: варианты исправления, «Добавить в словарь» и переключатели языков. Выбор языков сохраняется в настройках.
  - Проверка только локальная. Облачная («улучшенная») включается лишь по явному согласию и выключена в приватном режиме.
  - В macOS используется `NSSpellChecker` с языками и режимом «Автоматически» из системных настроек.
- Кто делает лучше / хуже:
  - Chrome проверяет несколько языков одновременно с 2015 года, сначала в Canary. Правило «ошибка, только если слова нет во всех языках» взято из дизайн-документа Chromium. На Mac Chrome использует системную проверку орфографии, а режим Enhanced отправляет текст в Google.
  - Firefox проверяет несколько языков сразу только с Fx100 (май 2022, bug 1402822, 36 голосов, 7 дублей). Языки выбираются в контекстном меню. Жалобы на то, что выбор теряется, не проверены: страница Connect не открылась.
  - Яндекс Браузер, Edge и Vivaldi работают как Chromium.
- Источники: https://bugzilla.mozilla.org/show_bug.cgi?id=1402822 (36 голосов, 7 дублей) · https://www.chromium.org/developers/design-documents/advancedspellchecker/ · https://thenextweb.com/news/chrome-can-now-spellcheck-multiple-languages-simultaneously

### IME и системные службы ввода

**Окно кандидатов IME — у каретки, а не в левом верхнем углу экрана** · редко · тяжесть: высокая · у ChatGPT: вскользь
- Боль: японский или китайский IME показывает варианты в левом верхнем углу экрана или окна, окно мерцает. При масштабе страницы не 100%, в iframe и во всплывающих окнах расширений оно оказывается не на месте. На каждый иероглиф приходится переводить взгляд через весь экран.
- Как должно быть:
  - На каждый запрос IME отдаём прямоугольник композиции и каретки в физических пикселях экрана: TSF `ITfContextView::GetTextExt`/`GetScreenExt`, IMM `ImmSetCandidateWindow`/`ImmSetCompositionWindow`, в macOS `firstRectForCharacterRange`.
  - Учитываем iframe, масштаб страницы, CSS transform, прокрутку, DPI монитора и всплывающие окна (у них свой owner HWND).
  - Если раскладка страницы ещё не готова, не отвечаем `TS_E_NOLAYOUT`: после него MS-IME ставит окно в (0,0). Вместо этого отдаём последний известный прямоугольник каретки, а потом отправляем `OnLayoutChange` (рекомендация исследования).
  - Подсказки адресной строки и автозаполнения не перекрывают окно кандидатов: во время композиции их список скрыт или сдвинут.
- Кто делает лучше / хуже:
  - Firefox прошёл весь путь по багам:
    - 1609675: окно MS-IME мерцает в левом верхнем углу из-за `TS_E_NOLAYOUT`, исправлено в Fx75 обходом, сделанным специально для MS-IME;
    - 1081993: ATOK и Japanist, Fx36;
    - 1419285: всплывающее окно Hatena Bookmark, Fx59;
    - 1564639: всплывающие окна расширений, Fx70;
    - 1261671: масштаб не 100%, Fx48, только без e10s.
  - WebKit 61023 (координаты в iframe) исправлен в 2011 году.
  - CEF #3313 (режим отрисовки вне экрана, OSR) открыт.
- Источники: https://bugzilla.mozilla.org/show_bug.cgi?id=1609675 · https://bugzilla.mozilla.org/show_bug.cgi?id=1564639 · https://bugs.webkit.org/show_bug.cgi?id=61023

**Enter, Esc и Tab во время IME-композиции принадлежат IME, а не браузеру и не сайту** · редко · тяжесть: высокая · у ChatGPT: вскользь
- Боль: японский или корейский пользователь нажимает Enter, чтобы подтвердить преобразование, а сообщение уходит недописанным или адресная строка открывает половину слова. В Chrome на macOS с корейским IME один Enter даёт два keydown: сообщение отправляется, последний слог остаётся в поле и уходит вторым сообщением.
- Как должно быть:
  - Порядок событий по UI Events: keydown (`key`=«Process», `keyCode`=229, `isComposing`=true) → `compositionstart`, `compositionupdate` → `beforeinput` и `input` (`isComposing`=true) → `compositionend` → keyup.
  - Нажатие, которое завершает композицию, приходит одним keydown с `isComposing`=true. Второй keydown Enter с `keyCode` 13 не генерируется.
  - Интерфейс браузера игнорирует Enter, Esc, Tab и стрелки, пока идёт композиция. Это касается адресной строки, поиска по странице, диалогов и отправки по Enter в собственных панелях браузера.
  - Esc во время композиции только отменяет её: не закрывает диалог, не выходит из полноэкранного режима, не откатывает адресную строку.
  - Адрес не дописывается в строке, пока идёт композиция.
- Кто делает лучше / хуже:
  - Chrome и Edge отдают `keyCode` 229 и `isComposing`=true, но на macOS с корейским IME бывает лишний keydown (OpenSearch Dashboards PR 12826).
  - Safari раньше отправлял `compositionend` до keydown, и `isComposing` был false. Поэтому сайты проверяют `keyCode===229`. В 2026 году правильный порядок включили по умолчанию (WebKit 165004 закрыт как дубль 311717). Safari 27 ошибки не имеет, но в веб-приложениях macOS исправление пока не действует.
  - Как ведёт себя адресная строка Firefox во время композиции — не проверено.
- Источники: https://bugs.webkit.org/show_bug.cgi?id=165004 · https://github.com/opensearch-project/OpenSearch-Dashboards/pull/12826 · https://github.com/assistant-ui/assistant-ui/issues/8319

**Приватный режим и поля паролей: IME и клавиатура не учатся на вводе** · редко · тяжесть: средняя · у ChatGPT: нет
- Боль: адреса, имена и запросы, набранные в инкогнито-окне, попадают в подсказки IME и сенсорной клавиатуры и потом всплывают в обычных приложениях. Пользователь замечает утечку, когда подсказка выдаёт его при посторонних.
- Как должно быть:
  - В приватных и гостевых окнах все поля, адресная строка и поиск получают флаг «не обучаться»: TSF InputScope `IS_PRIVATE` (Windows), `IBUS_INPUT_HINT_PRIVATE` (Linux), `IME_FLAG_NO_PERSONALIZED_LEARNING` (Android).
  - Поля `type=password` получают `IS_PRIVATE` во всех окнах.
  - Смысл флага: IME не запоминает новый ввод, но может показывать уже накопленные подсказки.
  - Флаг `IS_DEFAULT` в обычных окнах явно не ставим: в Chromium это изменило результат `window.getSelection()`, и изменение откатили.
  - Облачные функции ввода (предсказание текста, «улучшенная» проверка орфографии) в приватном режиме выключены.
- Кто делает лучше / хуже:
  - Chromium ставит флаг приватного ввода в окнах инкогнито, а также в InPrivate и гостевом режиме Edge. Поля паролей, по разбору авторов azooKey, сообщают `IS_PRIVATE`; в модульном тесте Chromium при включённом обучении пароль получает `IS_PASSWORD`. `IS_DEFAULT` для обычных окон откатили в июне 2024 года (коммит a0bed883).
  - IME подстраиваются: изменения Mozkey #303 и azooKey #466 влиты в октябре 2026 года, Mozc PR #1564 ещё открыт.
  - Что Edge выключает предсказание текста в InPrivate и в гостевом режиме — не проверено.
- Источники: https://chromium.googlesource.com/chromium/src/+/a0bed883c074617e8e8ddfa379ab5d563e6ed2da%5E!/ · https://github.com/koyasi777/mozkey/pull/303 · https://github.com/dolquis/azooKey-Desktop/pull/466

### Каретка и специальные возможности ОС

**Положение каретки для ОС: Лупа, индикатор текстового курсора, экранные лупы** · редко · тяжесть: высокая · у ChatGPT: нет
- Боль: собственный движок рисует каретку сам, и ОС не знает, где она. Лупа Windows не следует за набором, цветной индикатор текстового курсора Windows 11 не появляется, ZoomText теряет место ввода. Пользователь с лупой на 300% печатает вслепую.
- Как должно быть:
  - Параллельно с отрисовкой держим невидимую системную каретку (Win32 `CreateCaret`/`SetCaretPos`) и сообщаем позицию каретки через UIA TextPattern и IAccessible2 в физических пикселях экрана.
  - Позицию обновляем при каждом движении каретки, прокрутке, смене масштаба, перемещении окна и смене DPI.
  - В macOS используем NSAccessibility и `firstRectForCharacterRange`.
  - Приёмка:
    - Лупа Windows на 300% с включённым «Следовать за текстовым курсором» движется за кареткой в textarea и в адресной строке;
    - индикатор текстового курсора Windows 11 стоит на каретке;
    - индикаторы раскладки и Caps Lock macOS Sonoma появляются под кареткой в поле на странице.
- Кто делает лучше / хуже:
  - В Chromium для этого есть класс `AXSystemCaretWin`. В комментарии к нему объяснено: Chrome не использует стандартную системную каретку, а часть вспомогательных программ узнаёт позицию каретки только через определённые API.
  - Индикатор текстового курсора Windows работает в Chrome, Edge и Firefox, то есть все три сообщают позицию.
  - Для Lumen это не преимущество, а обязательный минимум: без него специальные возможности ОС не видят, где каретка.
- Источники: https://chromium.googlesource.com/chromium/src/+/main/ui/accessibility/platform/ax_system_caret_win.h · https://adrianroselli.com/2025/09/custom-carets-and-users-when-the-caret-is-no-longer-a-stick-yes-thats-a-poor-attempt-at-a-pun.html · https://macmost.com/turning-off-the-caps-lock-and-other-text-cursor-indicators-on-your-mac.html

**Толщина каретки: системная настройка Windows и масштаб DPI** · редко · тяжесть: средняя · у ChatGPT: нет
- Боль: слабовидящие ставят в Windows толщину текстового курсора на максимум, а в браузерах каретка остаётся толщиной в волос. По жалобам на AskWoody (2024), настройка не действует в Chrome, Firefox и Edge; на форуме Vivaldi такой запрос набрал 4 голоса.
- Как должно быть:
  - Читаем `SPI_GETCARETWIDTH` (значения 1–20, реестр `CaretWidth`; «Параметры > Специальные возможности > Текстовый курсор > Толщина»).
  - Ширина в физических пикселях = max(1, round(`CaretWidth` × масштаб DPI монитора)).
  - Масштаб страницы и CSS transform не делают каретку тоньше 1 физического пикселя. При масштабе 33–50% и при `scale()` каретка не пропадает (Firefox 226301).
  - Значение обновляется по `WM_SETTINGCHANGE`.
  - Высота каретки равна ascent + descent шрифта текста рядом с ней, а не line-height. В пустом поле высота берётся по метрикам шрифта поля, на стыке шрифтов — по символу перед кареткой.
  - Та же толщина в адресной строке и в полях интерфейса браузера.
- Кто делает лучше / хуже:
  - Chrome, Edge и Firefox системную толщину игнорируют. В Firefox значение `IntID::CaretWidth` равно 1, а `SPI_GETCARETWIDTH` не читается. Есть скрытый параметр `ui.caretWidth`, и его имя чувствительно к регистру.
  - Индикатор текстового курсора Windows работает во всех трёх браузерах.
  - Это готовое преимущество: никто из крупных браузеров системную толщину не учитывает.
- Источники: https://adrianroselli.com/2025/09/custom-carets-and-users-when-the-caret-is-no-longer-a-stick-yes-thats-a-poor-attempt-at-a-pun.html · https://devblogs.microsoft.com/oldnewthing/20240916-00/?p=110272 · https://bugzilla.mozilla.org/show_bug.cgi?id=226301 (21 голос)

**Отключение мигания как настройка специальных возможностей, которую видит и страница** · редко · тяжесть: средняя · у ChatGPT: вскользь
- Боль: людям со светочувствительностью, мигренью или СДВГ мигание физически мешает. Firefox bug 271785 так и называется: мигающий курсор, который нельзя выключить, вызывает неврологические проблемы. В Chrome на Windows и macOS отключить мигание можно только средствами ОС или через `defaults write`. В редакторах со своей кареткой (CodeMirror, VS Code, Google Docs) системная настройка не действует.
- Как должно быть:
  - В настройках браузера, в разделе «Специальные возможности», есть переключатель «Мигание текстового курсора: как в системе / не мигать».
  - По умолчанию значение берётся из ОС:
    - Windows: частота мигания `INFINITE`;
    - macOS Sequoia: Accessibility > Display > Prefer non-blinking cursor; в macOS Tahoe эта настройка переехала в раздел Motion;
    - ChromeOS и Android: собственные настройки ОС.
  - Значение действует в полях страниц, в адресной строке, в поиске и во всех полях интерфейса браузера.
  - Сайтам со своей кареткой настройка передаётся через `prefers-reduced-motion`, а когда появится — и через `prefers-caret-blink-rate` (предложение в CSSWG).
  - Пользовательская таблица стилей с `caret-animation: manual` должна работать.
- Кто делает лучше / хуже:
  - Лучше всех ChromeOS: там есть системная настройка «не мигать».
  - В заметках к выпуску Chrome 140 тем, кому мешает мигание, советуют отключить его пользовательской таблицей стилей с `caret-animation`.
  - Встроенного переключателя нет ни в Chrome, ни в Edge, ни в Firefox; в Firefox есть только `ui.caretBlinkTime=0` в about:config.
  - По наблюдению Roselli (2025), настройка macOS в Chrome не влияет на каретки, анимированные через CSS.
- Источники: https://bugzilla.mozilla.org/show_bug.cgi?id=271785 (1 дубль) · https://developer.chrome.com/release-notes/140 · https://lists.w3.org/Archives/Public/public-css-archive/2024Apr/0426.html

## Анти-цели области

- Не назначать одиночные клавиши без модификаторов на переходы и разрушительные действия вне полей: никакого Backspace-назад и модального диалога по F7.
- Не отдавать клавиатурный фокус странице в ущерб интерфейсу браузера. Не позволять `autofocus` или `focus()` перехватывать ввод, если пользователь уже начал печатать, кликнул или прокрутил страницу.
- Не выделять всё и не менять текст адресной строки посреди набора, в том числе при загрузке страницы новой вкладки или при появлении значков.
- Не объединять и не отбрасывать клавиатурные события, когда main thread занят. Синтетический ввод не считается «подозрительным».
- Не мигать бесконечно и не гасить каретку после остановки мигания: она остаётся видимой.
- Не зашивать в код частоту мигания, таймаут и толщину каретки: всё это берётся из ОС и перечитывается по `WM_SETTINGCHANGE`.
- Не трогать явно заданный автором `caret-color`, кроме `transparent` в режиме просмотра с кареткой.
- Не заменять набранный текст без спроса. Исправление раскладки — только подсказкой, в Ctrl+F — только при 0 совпадений. Поля паролей и поля страниц не трогать никогда.
- Не занимать сочетания из одних модификаторов (Ctrl+Shift, Alt+Shift, Win+Space, Ctrl+Space) и не открывать меню по Alt, если вместе с ним нажимали другие клавиши.
- Не «помнить раскладку для каждой вкладки» по своей инициативе: пользователи воспринимают такое угадывание как сюрприз.
- Не перехватывать Enter, Esc, Tab, стрелки и F7 во время IME-композиции и не генерировать второй keydown Enter после её завершения.
- Не отвечать IME `TS_E_NOLAYOUT`: окно кандидатов улетает в (0,0).
- Не ставить `IS_DEFAULT` в обычных окнах (опыт Chromium: ломает `window.getSelection()`). Не давать IME обучаться в приватных окнах и в полях паролей.
- Не отправлять набранный текст в облако по умолчанию: предсказание текста и «улучшенная» проверка орфографии только по явному согласию, в приватном режиме — никогда.
- Не принимать призрачный текст по Tab: Tab остаётся переходом по полям формы.
- Не дописывать в адресной строке опечатки и домены с одним визитом. Удалённые подсказки не должны появляться снова.
- Не делать общий выключатель событий буфера обмена (как в Firefox): он ломает редакторы. Принудительная вставка — отдельной командой и только в поле, куда фокус поставил сам пользователь.
- Не менять значение `number`/`range` колесом мыши при прокрутке страницы.
- Не склеивать слова при вставке многострочного текста в однострочное поле: перевод строки заменяется пробелом.
