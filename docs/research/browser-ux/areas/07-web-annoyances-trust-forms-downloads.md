# Защита от назойливости сайтов, разрешения, формы, пароли, загрузки, PDF, печать

Оговорка о данных. На этапе сбора закончился лимит веб-поиска, поэтому голоса и апвоуты с Reddit, HN, crbug и Mozilla Connect не собраны. Механику проверяли по первоисточникам, открытым по прямым URL: исходники Chromium, prefs Firefox (`firefox.js`, `all.js`, `StaticPrefList.yaml`), pdf.js, release notes Firefox, спецификация HTML, MDN. Строки «Боль» в большинстве находок написаны по опыту исследователя, без подсчёта. Меры массовости (звёзды, голоса) указаны там, где их удалось найти. Утверждения, которые не подтвердил ни один источник, помечены «(не проверено)».

## Главное в области

1. **Почти вся защита от назойливости держится на одном примитиве движка — user activation. Его нужно воспроизвести точно.** Примитив состоит из нескольких частей:
   - transient-окно (в Chrome `kActivationLifespan` = 5 с, с комментарием «long enough to allow network round trips»; спецификация говорит «не более нескольких секунд»);
   - sticky-бит;
   - отдельный бит history-action для API истории;
   - потребление активации: один жест даёт одно окно;
   - распространение активации по фреймам.

   По спецификации активацию дают keydown (кроме Esc и зарезервированных браузером сочетаний), mousedown, pointerdown от мыши, pointerup от остальных устройств и touchend. На этом примитиве стоят блокировщик всплывающих окон, запросы уведомлений и разрешений, beforeunload (sticky), чтение буфера обмена (transient), полноэкранный режим и обход ловушки «Назад». Для собственного движка это инфраструктура уровня P0. Ошибка в любую сторону даёт либо дырявые политики, либо сломанные окна OAuth и 3-D Secure, которые сайт открывает после медленного `fetch`.
2. **Правильные числа браузеры уже подобрали за годы проб и жалоб, их можно брать готовыми.**
   - Эмбарго разрешения: 3 закрытия или 4 игнора дают 7 дней тишины, в тихом режиме хватает 1 и 2.
   - Кнопки запроса разрешения неактивны первые 1000 мс.
   - Повторно использовать камеру без вопроса можно 1 час на той же вкладке, origin и устройстве, даже после навигации.
   - Разрешения сайтов, которые не открывали 60 дней, отзываются автоматически.
   - Пузырь загрузок закрывается сам через 5 с, но не закрывается под курсором и при включённых средствах доступности.
   - Плашка полноэкранного режима висит 3 с и появляется снова, если курсор задержался у края дольше 0,5 с. При Keyboard Lock Esc нужно удерживать 1,5 с.
   - Обработчику beforeunload даётся 1 с.
   - Докачка после выхода из сна начинается через 10 с.
   - Сессия пишется каждые 15 с, закрытых вкладок хранится 25, история форм — 180 дней.
   - Дубликаты имён файлов нумеруются до 100, затем к имени добавляется ISO-время.
3. **Главным источником жалоб становятся сами защитные механизмы.**
   - Блокировщик всплывающих окон ломает вход через OAuth.
   - Новая блокировка загрузок в Firefox 125 «работала не как задумано»: её откатили в 125.0.2 и выключили удалённо.
   - Chrome заменил полку загрузок пузырём.
   - Firefox 98 сбросил выбор «Всегда спрашивать»; release notes признают это ошибкой.

   Правило для Lumen: у каждой блокировки должен быть видимый индикатор, который не сдвигает контент, и обход в одно-два действия там, где его ищут (адресная строка, панель сайта). У каждой новой эвристики должен быть удалённый выключатель.
4. **Встроенная функция выигрывает у расширения доверием, а не возможностями.** «I don't care about cookies» после покупки Avast пришлось форкать: у форка 4,3k звёзд, в README причиной названо недоверие к Avast. Для приватного браузера встроенное скрытие cookie-баннеров, кнопка «Разрешить копирование» (расширение DontF-WithPaste — 914 звёзд) и восстановление набранного текста дают прямое преимущество, а не повторяют расширения.
5. **Рунет и Windows добавляют требования, которые зарубежные браузеры не закрывают.**
   - Cookie-баннеры почти всегда без кнопки отказа, поэтому нужен режим скрытия со снятием scroll-lock.
   - Автозаполнению нужны отчество и маски вида «+7 (___)».
   - Имена файлов в `Content-Disposition` приходят в CP1251 или в сыром UTF-8.
   - Одноразовые SMS-коды используются везде (Госуслуги, банки, маркетплейсы). На Windows встроенного решения для них нет: Chrome получает код, только если есть Android-телефон с тем же Google-аккаунтом.
   - Билеты печатают из PDF, а растр 150 dpi в pdf.js для этого опасен.
   - Разрешения работают в два слоя: приватность ОС и занятость камеры другим приложением. К этому добавляются Mark of the Web (от него зависят SmartScreen и защищённый просмотр Office), ограничения имён файлов Windows и Windows Hello.

   Пользователь не отличает «запретил сайт» от «запретила ОС». Выигрывает браузер, который называет точную причину и даёт кнопку в `ms-settings:`.
6. **В документе ChatGPT нет целого класса тем.** Там есть только общие пункты J09, J10, J18 и M17–M19: диалог разрешения с origin и сроком, докачка при поддержке сервера, дубликаты и опасные типы файлов, «не хранить CVV». Отсутствуют:
   - защита от назойливости: cookie-баннеры, уведомления, всплывающие окна, редиректы, beforeunload, scareware, запрет вставки;
   - PDF и печать;
   - момент предложения сохранить пароль и генерация паролей;
   - OTP на десктопе;
   - восстановление текста из contenteditable.

   Пункт M18 «не хранить CVV» к тому же расходится с практикой: Chrome предлагает хранить CVC с подтверждением через Windows Hello (не проверено). Требование лучше сформулировать так: хранить только с явного согласия и подставлять после биометрии.

## Находки

### Запросы и спам уведомлений

**Запрос на уведомления только после жеста, тихий режим, эмбарго** · массово · тяжесть: высокая · у ChatGPT: вскользь
- Боль: сайт спрашивает про уведомления с порога. Пузырь закрывает часть страницы, и его приходится закрывать до начала чтения. Почти никто не нажимает «Разрешить». По статистике Mozilla для Firefox 63, за месяц было 1,45 млрд запросов, из них принято 23,66 млн (около 1,6%), а 48% отклонены явно (не проверено: при проверке блог Mozilla не открылся).
- Как должно быть:
  1. Полный пузырь показывается только при transient activation: не позже 5 с после клика, нажатия клавиши или касания на странице. Esc и зарезервированные браузером сочетания активацией не считаются. Без жеста запрос автоматически отклоняется, а в адресной строке остаётся маленькая иконка; по клику на неё можно разрешить.
  2. Эмбарго считается по паре «origin × тип разрешения». 3 закрытия (крестик или Esc) или 4 игнора (запрос исчез без ответа из-за навигации или закрытия вкладки) дают 7 дней без повторного вопроса. В тихом режиме хватает 1 закрытия или 2 игноров.
  3. Тихий режим (иконка или чип вместо пузыря) включается вручную в настройках, а также автоматически: для пользователя, который систематически отклоняет запросы, и для сайтов с низкой долей согласий.
  4. Из фоновой вкладки запрос не показывается, при навигации он снимается.
  5. Глобальный переключатель «Сайты могут запрашивать отправку уведомлений» доступен в один клик прямо из запроса.
- Кто делает лучше / хуже: Firefox с версии 72 вообще не показывает запрос без жеста: вместо него в адресной строке появляется значок-«облачко» (speech bubble). У Chrome есть quieter messaging с адаптивным включением и перечёркнутый колокольчик в адресной строке, эмбарго 3/4 → 7 дней. Safari 12.1 на macOS требует жест для push-запроса. Edge по умолчанию показывает тихие запросы (не проверено). Хуже всех Chromium-клоны, которые не включили тихий режим по умолчанию.
- Источники: https://chromium.googlesource.com/chromium/src/+/main/components/permissions/permission_decision_auto_blocker.cc (`kDefaultDismissalsBeforeBlock=3`, `kDefaultIgnoresBeforeBlock=4`, тихий UI 1/2, `kDefaultEmbargoDays=7`) · https://www.firefox.com/en-US/firefox/72.0/releasenotes/ · https://blog.mozilla.org/futurereleases/2019/11/04/restricting-notification-permission-prompts-in-firefox/ (статистика запросов)

**Спам уведомлениями после случайного «Разрешить», автоматический отзыв разрешений** · часто · тяжесть: высокая · у ChatGPT: нет
- Боль: в углу экрана всплывает «Обнаружен вирус!», реклама казино и знакомств, даже когда сайт закрыт. Это частый запрос в техподдержку. Пользователь не понимает, откуда приходят уведомления и как их выключить, и считает, что компьютер заражён.
- Как должно быть:
  1. Каждое уведомление (toast Windows) крупно показывает источник (eTLD+1) и кнопки «Отписаться» и «Настройки сайта». Отключить уведомления можно одним кликом прямо из уведомления.
  2. Разрешения сайтов, которые не открывали 60 дней, отзываются автоматически (как `kUnusedSitePermissionsRevocationThreshold` в Chromium). После отзыва показывается отчёт «Разрешения удалены у: …» с кнопкой «Вернуть».
  3. «Шумный» сайт определяется по двум признакам: engagement низкий, а среднее число уведомлений в день выше порога. Сначала он помечается как кандидат (proposed), после периода ожидания разрешение сбрасывается в «Спрашивать».
  4. Сайты из списка злоупотреблений блокируются, даже если разрешение выдано, и должны спросить заново. В Chrome это работает при включённом Safe Browsing.
  5. В приватном режиме уведомления не приходят.
  6. Список разрешённых сайтов открывается из меню уведомления, а не только через Настройки → Конфиденциальность → Настройки сайтов.
- Кто делает лучше / хуже: Chrome — Safety Hub и раздел «Permissions removed». Он автоматически отзывает разрешения неиспользуемых сайтов (60 дней) и disruptive-уведомления. Второе спрятано за фичей `kSafetyHubDisruptiveNotificationRevocation`, пороги задаются её параметрами. В Firefox автоотзыва нет, чистить приходится вручную (не проверено). В Safari уведомления сайтов идут через центр уведомлений macOS, там их легко отключить.
- Источники: https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/ui/safety_hub/unused_site_permissions_manager.cc · https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/ui/safety_hub/disruptive_notification_permissions_manager.cc · https://support.google.com/chrome/answer/3220216

### Разрешения: камера, микрофон, геолокация, буфер обмена

**Анатомия запроса разрешения: привязка к адресной строке, origin верхнего уровня, «в этот раз», задержка кнопок** · массово · тяжесть: высокая · у ChatGPT: вскользь
- Боль: «Нажал "Разрешить" случайно, кнопка появилась прямо под курсором». Непонятно, кто просит камеру: сам сайт или встроенный виджет. Пользователь хочет дать доступ один раз, а не навсегда.
- Как должно быть:
  1. Пузырь привязан к иконке сайта в адресной строке и показывает origin верхнего уровня, eTLD+1 выделен жирным. Если просит iframe, текст такой: «<встроенный> на <сайт> хочет…» (формулировка не проверена).
  2. Три кнопки: «Разрешить при посещении», «Разрешить в этот раз», «Не разрешать». Разовое разрешение действует, пока открыта вкладка сайта.
  3. Первые 1000 мс после появления кнопки неактивны (Firefox `security.dialog_enable_delay=1000`; в Chrome около 500 мс — не проверено). Так двойной клик или приём «кликни быстро» не превращается в согласие.
  4. Из фоновой вкладки запрос невозможен. При навигации он снимается и засчитывается в эмбарго как игнор.
  5. Камера, микрофон и геолокация доступны только в secure context, после жеста и в верхнем фрейме либо по Permissions-Policy.
  6. Браузер не придумывает за сайт причину запроса.
- Кто делает лучше / хуже: у Chrome кнопки «в этот раз» и «при посещении» (с версии 116 — не проверено) и одинаковый UI для всех типов разрешений. Firefox показывает doorhanger с флажком «Запомнить это решение»; без флажка решение временное. Safari часто спрашивает заново (см. следующую находку).
- Источники: https://chromium.googlesource.com/chromium/src/+/main/docs/security/permissions-for-powerful-web-platform-features.md (secure, top-level, жест; запрет из фоновой вкладки; сессионный доступ; одно место для отзыва) · https://raw.githubusercontent.com/mozilla-firefox/firefox/main/modules/libpref/init/all.js (`security.dialog_enable_delay`)

**Индикаторы камеры, микрофона и показа экрана; заглушение уведомлений во время показа** · часто · тяжесть: высокая · у ChatGPT: вскользь
- Боль: «Не понимаю, слушает ли меня сейчас сайт». «Плавающий индикатор Firefox висит посреди экрана». «Во время демонстрации экрана всплыло личное уведомление».
- Как должно быть:
  1. Пока идёт захват, видны три индикатора: значок записи на вкладке, иконка в адресной строке с меню «Остановить / сменить устройство» и глобальный индикатор (окно при показе экрана, иконка в трее для камеры и микрофона).
  2. Индикатор гаснет только после реальной остановки трека, а не когда страница скрыла видео.
  3. При показе экрана браузер предлагает «Заглушить уведомления до конца показа». В Firefox это включено по умолчанию (`privacy.webrtc.allowSilencingNotifications=true`).
  4. Предупреждение при переключении вкладок в окне, которое показывается, и глобальные переключатели «выключить камеру/микрофон для всех сайтов» прямо в индикаторе. В Firefox они есть только как скрытые настройки, выключенные по умолчанию (`sharedTabWarning=false`, `globalMuteToggles=false`). Lumen имеет смысл включить их сразу.
  5. На macOS 14+ системный индикатор дублирует браузерный. Firefox по умолчанию показывает свой (`showIndicatorsOnMacos14AndAbove=true`), настройка позволяет его скрыть. На Windows такого дублирования нет: трей Windows 11 показывает, что камера или микрофон заняты, но не говорит, каким сайтом (не проверено). Поэтому собственный индикатор с именем сайта обязателен.
- Кто делает лучше / хуже: в Chrome красная точка на вкладке и полоса «Остановить показ». Firefox показывает глобальный индикатор и умеет глушить уведомления. На macOS есть системная оранжевая или зелёная точка.
- Источники: https://raw.githubusercontent.com/mozilla-firefox/firefox/main/browser/app/profile/firefox.js (`privacy.webrtc.*`)

**«Сайт спрашивает снова и снова»: запоминание решений и выбранного устройства** · часто · тяжесть: средняя · у ChatGPT: вскользь
- Боль: Safari заново спрашивает доступ к камере на каждом созвоне Meet или Zoom (жалобы в Apple Community, не проверено). Обратная жалоба: один раз нажал «Запретить» и не можешь найти, где это отменить.
- Как должно быть:
  1. После выдачи доступа то же устройство на той же вкладке и origin используется повторно без вопроса в течение 1 часа, в том числе после навигации (Firefox `privacy.webrtc.deviceGracePeriodTimeoutMs=3600000`).
  2. Если пользователь 2–3 раза подряд выбрал «в этот раз» на одном сайте, браузер предлагает «Запомнить для этого сайта».
  3. Для каждого сайта запоминается выбранная камера и микрофон.
  4. После запрета иконка «заблокировано» остаётся в адресной строке, пока сайт пытается использовать устройство. По клику открываются переключатель и подсказка «перезагрузите страницу».
  5. Эмбарго работает так же, как для уведомлений (3/4 → 7 дней), поэтому вызвать запрос в цикле сайт не может.
- Кто делает лучше / хуже: в Firefox льготный час и флажок «Запомнить». В Chrome постоянное или разовое разрешение плюс эмбарго. В Safari по умолчанию «Спросить», а постоянный доступ включается только в Настройки → Веб-сайты → Камера (не проверено).
- Источники: https://raw.githubusercontent.com/mozilla-firefox/firefox/main/browser/app/profile/firefox.js (`deviceGracePeriodTimeoutMs`, действует для tab + origin + device «even past navigation») · https://chromium.googlesource.com/chromium/src/+/main/components/permissions/permission_decision_auto_blocker.cc

**Два слоя разрешений на Windows: запретил сайт, запретила ОС или устройство занято** · часто · тяжесть: средняя · у ChatGPT: нет
- Боль: «Разрешил сайту камеру, а видео чёрное». Причина в том, что доступ выключен в настройках конфиденциальности Windows или камеру держит Zoom. Пользователь винит сайт или браузер.
- Как должно быть:
  1. Различать три причины и показывать их разными текстами:
     - запрещено сайту;
     - запрещено ОС (Параметры → Конфиденциальность → Камера, Микрофон или Расположение, включая доступ для классических приложений) — с кнопкой, которая открывает `ms-settings:privacy-webcam`, `privacy-microphone` или `privacy-location` (URI не проверены);
     - устройство занято: `getUserMedia` отклоняется с `NotReadableError` («Could not start video source»), текст — «Камера используется другим приложением».
  2. Геолокация: если служба расположения Windows выключена, сказать об этом прямо. При определении по IP честно показывать точность. Отдельно предлагать «приблизительное местоположение».
  3. На macOS то же самое: «нужно разрешение macOS» и кнопка, ведущая в Системные настройки.
- Кто делает лучше / хуже: Chromium разрабатывает приблизительную геолокацию (`kApproximateGeolocationPermission`; зависимая `kPermissionPredictionsGeolocationAccuracy` выключена по умолчанию, начальная точность берётся из CPSS). Chrome на macOS подсказывает про системное разрешение (не проверено). Firefox и большинство клонов показывают голое «не удалось» (не проверено).
- Источники: https://chromium.googlesource.com/chromium/src/+/main/components/permissions/features.cc

**Чтение буфера обмена: подтверждение «Вставить» вместо постоянного разрешения** · редко · тяжесть: средняя · у ChatGPT: вскользь
- Боль: «Зачем сайту доступ к буферу обмена?» Обратная ситуация: в веб-редакторе не работает кнопка «Вставить». Адресная строка подтормаживает из-за подсказки «вставить URL из буфера».
- Как должно быть:
  1. `navigator.clipboard.readText()` и `read()` работают только при transient activation.
  2. Если данные скопированы на другом origin, у курсора появляется мини-меню «Вставить». Пользователь подтверждает кликом, постоянного разрешения не возникает.
  3. Данные, скопированные на том же origin, отдаются без подтверждения.
  4. Подсказка «перейти по URL из буфера» в адресной строке читает буфер асинхронно и только при необходимости.
- Кто делает лучше / хуже: Firefox 125 и Safari показывают меню подтверждения. Chrome выдаёт постоянное разрешение (не проверено). У Firefox 125 есть известная проблема: адресная строка подвисает из-за Clipboard Suggestion; обходной путь — снять флажок «Clipboard» в `about:preferences#search`.

### Cookie-баннеры, оверлеи, запрет копирования, автозапуск

**Cookie-баннеры: сначала отказ, иначе скрытие; прокрутка возвращается, баннер не мигает** · массово · тяжесть: высокая · у ChatGPT: нет
- Боль: баннер «Мы используем cookie» есть на каждом сайте и на десктопе закрывает до трети экрана. Пользователи ставят «I don't care about cookies», а после покупки расширения Avast переходят на форк (4,3k звёзд). Частая поломка: баннер скрыт, а страница не прокручивается.
- Как должно быть:
  1. Порядок действий:
     - для известных CMP (OneTrust, Didomi, Cookiebot, Quantcast, TrustArc) по правилу нажать «Отклонить всё» или «Только необходимые»;
     - если кнопки отказа нет, скрыть баннер CSS-правилом и не нажимать «Принять». Режим «принять, если отказаться нельзя» включается только отдельной опцией.
  2. После скрытия вернуть странице прокрутку: снять `overflow:hidden` и `position:fixed` с `html`/`body` и убрать затемняющий backdrop. Без этого скрытие хуже самого баннера: пользователь считает, что «браузер сломал сайт».
  3. Косметические правила применяются при старте документа, до первой отрисовки. Иначе баннер успевает мигнуть на 100–500 мс.
  4. В панели сайта (замок) есть переключатель «Не трогать баннеры на этом сайте» на случай поломки.
  5. Рунет: баннеры почти всегда только с кнопкой «ОК», без отказа, поэтому режим скрытия обязателен.
- Кто делает лучше / хуже: Firefox 120 включил Cookie Banner Blocker по умолчанию только в приватных окнах и только в Германии; он автоматически отказывается от cookie на поддерживаемых сайтах. В Vivaldi баннеры скрывают два списка блокировщика: «Remove cookie warnings (Easylist Cookie List)» и «Remove cookie warnings (I don't care about cookies)». Их надо включить вручную в Sources, и это косметическое скрытие, а не отказ. У Brave и Opera встроенные блокировщики (не проверено). У Chrome, Edge и Safari встроенного решения нет.
- Источники: https://www.firefox.com/en-US/firefox/120.0/releasenotes/ · https://github.com/OhMyGuus/I-Still-Dont-Care-About-Cookies (4,3k звёзд; форк из-за покупки оригинала Avast) · https://help.vivaldi.com/desktop/privacy/tracker-and-ad-blocker/

**Сайт запрещает вставку, копирование, правый клик и выделение, перехватывает сочетания, прячет текст за оверлеями** · часто · тяжесть: средняя · у ChatGPT: нет
- Боль: «Банк не даёт вставить пароль из менеджера». «Нельзя скопировать текст статьи». «Ctrl+F открывает поиск сайта, а не браузера». «Модалка подписки закрывает статью». Люди ставят расширения Don't F*** With Paste и Allow Right-Click.
- Как должно быть:
  1. Shift+правый клик всегда открывает нативное контекстное меню в обход обработчика `contextmenu` сайта (Firefox `dom.event.contextmenu.shift_suppresses_event=true`).

  5. Против оверлеев и paywall-модалок помогают режим чтения и пункт «Скрыть этот элемент на сайте», который запоминается для домена.
  6. Scroll-hijacking браузер без поломок не исправит; спасает режим чтения.
- Кто делает лучше / хуже: у Firefox больше всего встроенных средств: Shift+ПКМ, разрешение на сочетания, `dom.event.contextmenu.enabled` и `dom.event.clipboardevents.enabled` в about:config. В Safari 18 есть «Hide distracting items» (не проверено). В Chrome и Edge штатных средств нет, только расширения.
- Источники: https://github.com/jswanner/DontF-WithPaste (914 звёзд; capture-слушатели copy/cut/paste со `stopImmediatePropagation`; README оговаривает, что контекстное меню и сочетания расширение не трогает) · https://raw.githubusercontent.com/mozilla-firefox/firefox/main/modules/libpref/init/StaticPrefList.yaml · https://raw.githubusercontent.com/mozilla-firefox/firefox/main/browser/app/profile/firefox.js

**Автозапуск медиа со звуком: правило по умолчанию и три уровня** · часто · тяжесть: средняя · у ChatGPT: вскользь
- Боль: «Открыл новость, где-то заорало видео, ищу вкладку». Пользователи просят глобальное «никогда не запускать видео само»: беззвучный автозапуск тоже тратит трафик и CPU и отвлекает.
- Как должно быть:
  1. Беззвучный autoplay разрешён всегда, со звуком по умолчанию запрещён. Звук разрешается в трёх случаях:
     - пользователь взаимодействовал с доменом (клик, касание);
     - сайт установлен как PWA;
     - (вариант Chrome) MEI выше порога. MEI учитывает воспроизведения дольше 7 с со звуком в активной вкладке, видео больше 200×140.
  2. Три уровня, глобально и для сайта: «Разрешить аудио и видео», «Блокировать звук» (по умолчанию), «Блокировать аудио и видео» (до клика по плееру не стартует даже беззвучное видео).
  3. Если autoplay заблокирован, в адресной строке появляется иконка: разрешить для этого сайта можно одним кликом.
  4. Cross-origin iframe получает autoplay только через `allow="autoplay"`, иначе `play()` отклоняется с `NotAllowedError`. Same-origin iframe наследует разрешение.
  5. В фоновой вкладке воспроизведение не начинается, пока вкладку хотя бы раз не покажут (не проверено).
- Кто делает лучше / хуже: Firefox 66 блокирует звук и поддерживает список исключений; блокировать и беззвучное видео стало можно в Firefox 69. У Safari настройка для сайта «Всегда / Остановить медиа со звуком / Никогда» (не проверено). Chrome применяет политику с версии 66 (для Web Audio — с 71) и использует MEI, но глобального «блокировать всё» в интерфейсе нет (не проверено).
- Источники: https://developer.chrome.com/blog/autoplay · https://www.firefox.com/en-US/firefox/66.0/releasenotes/ · https://www.firefox.com/en-US/firefox/69.0/releasenotes/

### Всплывающие окна, редиректы, ловушки навигации, диалоги

**Блокировщик всплывающих окон: 5 секунд, один жест — одно окно, OAuth и 3-D Secure не ломать** · часто · тяжесть: высокая · у ChatGPT: нет
- Боль: жалобы противоположные. Одни: «Сайт открыл три вкладки с рекламой». Другие: «Не открывается окно входа через Google или VK, окно банка для подтверждения платежа». При этом пользователь не видит, что окно заблокировано.
- Как должно быть:
  1. `window.open` разрешён только при transient activation: в Chrome 5 с после жеста, в спецификации «не более нескольких секунд». Вызов потребляет активацию, поэтому один жест даёт одно окно.
  2. Право открыть окно дают события из списка Firefox (`dom.popup_allowed_events`): change, click, dblclick, auxclick, mousedown, mouseup, pointerdown, pointerup, notificationclick, reset, submit, touchend, contextmenu.
  3. Легитимные сценарии (OAuth, 3-D Secure, «Оплатить») ломаются, когда сайт открывает окно после `await fetch()`, который длился больше 5 с. Поэтому индикатор блокировки заметен и одним кликом открывает именно заблокированный URL; рядом есть «Всегда разрешать для сайта».
  4. Индикатор не сдвигает контент: никаких плашек над страницей, только иконка или чип в адресной строке со списком заблокированных URL.
  5. Pop-under (окно открылось, а opener забрал фокус обратно) запрещён: `window.focus()` от opener игнорируется (не проверено).
- Кто делает лучше / хуже: в Chrome иконка в омнибоксе со списком заблокированных окон, каждое можно открыть по ссылке. Firefox показывает жёлтую полосу над страницей, которая сдвигает layout (не проверено). Неочевидно, что в списке событий Firefox есть contextmenu.
- Источники: https://raw.githubusercontent.com/mozilla-firefox/firefox/main/modules/libpref/init/all.js (`dom.popup_allowed_events`) · https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/public/common/frame/user_activation_state.h (`kActivationLifespan`) · https://developer.mozilla.org/en-US/docs/Web/Security/User_activation

**Ловушка «Назад», tab-under, редиректы из рекламных iframe, серийные и скрытые загрузки** · часто · тяжесть: высокая · у ChatGPT: нет
- Боль: «Жму "Назад", а сайт возвращает меня на себя же». «Кликнул по статье, а в исходной вкладке открылся рекламный сайт». «Сайт сам начал качать файлы». Фальшивые кнопки «Скачать» на файлообменниках.
- Как должно быть:
  1. Кнопка «Назад» пропускает записи истории, созданные `pushState` или редиректом на странице, которая ни разу не получала user activation. Долгое нажатие на «Назад» показывает полный список. На `history.back()` и `forward()` из JS правило не действует. В спецификации для этого есть отдельный бит history-action activation.
  2. Навигация верхнего окна из cross-origin iframe без жеста блокируется. Вместо неё показывается инфобар с кнопкой «Перейти» (Chrome 64 — не проверено).
  3. Tab-under (открыть новую вкладку и тут же увести исходную на другой URL) блокируется (Chrome 65 — не проверено).
  4. Вторая и следующие загрузки без жеста вызывают запрос «Сайт пытается скачать несколько файлов» (разрешение Automatic downloads, не проверено).
  5. Загрузки из sandbox-iframe без `allow-downloads` блокируются (не проверено).
  6. Сайты с abusive experiences (фальшивые кнопки, прозрачные оверлеи) определяются по списку Safe Browsing (Chrome 71, не проверено).
- Кто делает лучше / хуже: здесь первопроходец Chrome: History Manipulation Intervention, блокировка редиректов из iframe и tab-under; BackToAdIntervention выключена по умолчанию. Firefox делает это частично, Safari — через ITP и собственные эвристики (не проверено).
- Источники: https://chromium.googlesource.com/chromium/src/+/main/docs/history_manipulation_intervention.md · https://blog.chromium.org/2017/11/expanding-user-protections-on-web.html · https://html.spec.whatwg.org/multipage/interaction.html

**«Покинуть сайт?» (beforeunload): только после взаимодействия, текст браузера, лимит времени** · часто · тяжесть: средняя · у ChatGPT: нет
- Боль: вкладку не закрыть: сайт спрашивает «Вы уверены?», хотя пользователь ничего не делал. При этом на настоящих формах это предупреждение нужно, иначе набранный текст теряется.
- Как должно быть:
  1. Диалог показывается только при sticky activation, то есть если пользователь хоть раз взаимодействовал с документом или его фреймами.
  2. Текст задаёт браузер, свою строку сайт подставить не может.
  3. На обработчик даётся 1 с (Firefox `dom.beforeunload_timeout_ms=1000`). Если он не уложился, закрытие продолжается.
  4. На одно действие показывается не больше одного диалога. Если закрывается окно с несколькими такими вкладками, пользователь получает один сводный вопрос, а не цепочку.
  5. Кнопки «Покинуть» и «Остаться». Какая из них срабатывает по Enter, нужно решить сознательно (Chrome выделяет «Покинуть» — не проверено).
  6. Подписка на beforeunload мешает bfcache: в Firefox такие страницы туда не попадают, и возврат «Назад» становится медленным. Эту цену нужно учитывать.
- Кто делает лучше / хуже: sticky activation требуют все современные браузеры. Chrome убрал пользовательский текст в версии 51, Firefox — в 44 (не проверено).

**Петли alert(), полноэкранные ловушки и scareware «техподдержки»** · редко · тяжесть: высокая · у ChatGPT: нет
- Боль: мошенническая страница «Ваш компьютер заблокирован, позвоните…» разворачивается на весь экран, непрерывно сыплет alert-ами, мешает закрыть вкладку и пищит. Пожилые пользователи в панике перезагружают компьютер или звонят мошенникам.
- Как должно быть:
  1. `alert`, `confirm` и `prompt` модальны только для своей вкладки: они не блокируют другие вкладки и не мешают закрыть эту. Диалог из фоновой вкладки её не активирует (не проверено).
  2. Начиная со второго диалога подряд показывается флажок «Запретить этой странице создавать диалоги». После этого `alert` сразу возвращает управление, `confirm` возвращает `false`, `prompt` — `null`. Спецификация это разрешает: UA «may optionally return true at any time».
  3. Длинный текст диалога усекается без кнопки «показать ещё». Так требует спецификация, чтобы страница не могла подделать интерфейс.
  4. При входе в полноэкранный режим показывается плашка «<домен> в полноэкранном режиме — Esc для выхода». Она держится 3000 мс и появляется снова, если курсор задержался у верхнего края дольше 500 мс (Firefox `full-screen-api.warning.timeout`/`warning.delay`).
  5. Esc не даёт user activation, поэтому по Esc сайт не может снова войти в полноэкранный режим. При активном Keyboard Lock Esc нужно удерживать 1,5 с (Chrome `kHoldEscapeTime` = 1500 мс). Три нажатия Esc за 1 с снова показывают подсказку о выходе. Firefox показывает предупреждение keyboardlock 4000 мс.
  6. Дополнительный слой — локальный детектор scareware: он выводит страницу из полноэкранного режима и глушит звук (Edge Scareware blocker на локальной ML-модели, не проверено).
- Кто делает лучше / хуже: флажок подавления диалогов есть в Chrome и Firefox. Chrome 92 пытался запретить `alert()` в cross-origin iframe и откатил изменение после протестов разработчиков (не проверено). Вывод: ломать совместимость с вебом опасно даже ради защиты.
- Источники: https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html · https://raw.githubusercontent.com/mozilla-firefox/firefox/main/modules/libpref/init/all.js (`full-screen-api.warning.timeout=3000`, `warning.delay=500`, `keyboardlock-warning.timeout=4000`) · https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/ui/exclusive_access/keyboard_lock_controller.cc

### Формы и автозаполнение

**Автозаполнение не в те поля, autocomplete=off, события для фреймворков, российские адреса и телефоны** · массово · тяжесть: высокая · у ChatGPT: нет
- Боль: «Имя попало в поле "Город"». «Маска сайта задвоила семёрку: +7 (791) 612-34-56…». «В профиле адреса нет отчества». «Кнопка "Войти" неактивна, пока не кликнешь куда-нибудь, хотя логин и пароль подставлены». «autocomplete=off игнорируется».
- Как должно быть:
  1. Поля распознаются сначала по `autocomplete`, затем по `name`/`id`, `label` и `placeholder`, с русскими словарями: Фамилия, Имя, Отчество (отдельным полем или ФИО одной строкой), Индекс, Область/Край, Населённый пункт.
  2. Телефон вставляется так, чтобы маска «+7 (___) ___-__-__» не задвоила код. Варианты: проверить, есть ли префикс в маске; вставлять 10 цифр без +7; эмулировать посимвольный ввод.
  3. Каждое заполненное поле получает `input` и `change` (React, Vue и Angular слушают `input`). `:autofill` выставляется до событий.
  4. Пароль, подставленный при загрузке, Chrome не отдаёт JS до первого взаимодействия со страницей (не проверено). Отсюда «неактивная кнопка "Войти"». Баланс между безопасностью и совместимостью нужно выбрать сознательно.
  5. Для логинов `autocomplete=off` игнорируется ради менеджеров паролей. Firefox игнорирует его и для адресов (`extensions.formautofill.addresses.ignoreAutocompleteOff=true`). Для `one-time-code` и CAPTCHA флаг соблюдается.
  6. Ctrl+Z после автозаполнения откатывает всё заполнение, Shift+Delete на подсказке удаляет её из истории форм (оба пункта не проверены). История форм хранится 180 дней (Firefox `browser.formfill.expire_days=180`).
- Кто делает лучше / хуже: Chrome самый агрессивный и точный, но чаще промахивается на нестандартных формах (не проверено). Firefox консервативнее, отчества в его формате адреса нет (не проверено). Яндекс Браузер построен на Chromium.
- Источники: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/autocomplete · https://raw.githubusercontent.com/mozilla-firefox/firefox/main/modules/libpref/init/all.js

**Восстановление набранного текста после краха, закрытия вкладки или ухода со страницы** · часто · тяжесть: высокая · у ChatGPT: вскользь
- Боль: классика: «Писал длинный комментарий или отзыв, вкладка упала или я её случайно закрыл, всё пропало». Ради этого существуют расширения Typio Form Recovery и Form History Control; закрытый Lazarus вспоминают до сих пор.

  1. Сессия хранит текст обычных полей формы на всех сайтах. Так делает Firefox:
     - `browser.sessionstore.privacy_level=0`: 0 — везде, 1 — только на незашифрованных сайтах, 2 — нигде;
     - до 25 закрытых вкладок на окно (`max_tabs_undo=25`);

  4. Предложение для Lumen: локальный зашифрованный журнал текста из `textarea` и contenteditable длиннее ~50 символов, хранится 24–72 ч. Восстанавливается через контекстное меню поля «Восстановить набранный текст…» со списком версий по времени.
  5. Исключения: `type=password`, `autocomplete=cc-*`, `one-time-code`, `new-password`, приватный режим, сайты из списка исключений.
  6. Если закрывается вкладка, где в поле набрано больше N символов, показывается тост «Вкладка закрыта — вернуть?» с кнопкой отмены, а не модальный вопрос.

**Предупреждения об опасных и небезопасных загрузках: ложные срабатывания, спрятанное «Сохранить всё равно»** · часто · тяжесть: высокая · у ChatGPT: вскользь

  1. Предупреждать только по реальному сигналу: репутация файла или хоста, тип в сочетании с источником, вердикт Safe Browsing. Не предупреждать о каждом `.zip` или `.exe` от известного издателя, иначе предупреждения перестают читать.

У Chrome сильная защита (deep scanning, состояние «Content check pending»), но обход спрятан, а предупреждения вызывают привыкание (не проверено). **Имена скачанных файлов: дубликаты, кириллица, ограничения Windows, Mark of the Web** · часто · тяжесть: средняя · у ChatGPT: вскользь
- Боль: «Скачал отчёт, а он называется `Ð¾Ñ‚Ñ‡Ñ‘Ñ‚.pdf`» — кракозябры на российских сайтах. «Файл назвался `download` или `view.php`». «`report (7).pdf` — где теперь нужный?» Windows: «Не удаётся открыть файл с таким именем».
- Как должно быть:
  1. Дубликат получает имя «report (1).pdf»: номер с пробелом ставится перед расширением, попытки идут от 1 до 100 (Chrome `kMaxUniqueFiles=100`). Дальше добавляется суффикс « - 2026-10-11T153012» (ISO-время без двоеточий).
  2. Временный файл имеет отдельное расширение (`.crdownload` у Chrome, `.part` у Firefox). На Windows из лимита длины имени заранее вычитается бо́льшая из двух длин: `.crdownload` (11) или `:Zone.Identifier` (16). Если места не хватает, базовое имя усекается, расширение сохраняется.

     - `filename*` в UTF-8 (RFC 5987/6266);
     - `filename=`: сырые байты UTF-8 или CP1251 распознаются эвристикой, иначе получаются кракозябры;
     - имя из URL;
     - расширение по MIME.

**Прерванные загрузки: докачка, сон ПК, закрытие браузера, истёкшие ссылки** · часто · тяжесть: средняя · у ChatGPT: вскользь
- Боль: «Качал 4 ГБ, на 90% "Ошибка сети", и всё заново». «Закрыл браузер и потерял загрузку, он даже не спросил». «Нажал "Возобновить", а пришла ошибка 403».
- Как должно быть:
  1. При обрыве показывается статус «Ошибка сети — Возобновить». Докачка идёт Range-запросом, если сервер отдал `Accept-Ranges` и `ETag` или `Last-Modified` и они не изменились. Иначе пользователь видит вопрос: «Сервер не поддерживает докачку — начать заново?».
  2. После выхода ПК из сна прерванные загрузки возобновляются сами через 10 с (Firefox `browser.download.manager.resumeOnWakeDelay=10000`).
  3. При закрытии браузера во время загрузок появляется вопрос «Идёт N загрузок — отменить и выйти?» (так делают Chrome и Firefox — не проверено).
  4. Подписанная ссылка (S3, CDN) истекает, и докачка получает 403. Тогда браузер предлагает «Скачать заново со страницы-источника» и открывает сохранённый referrer.
  5. Недокачанный файл не выглядит готовым: суффикс `.part`/`.crdownload` остаётся до конца загрузки.
- Кто делает лучше / хуже: Firefox сам возобновляет загрузки после сна. Chrome возобновляет только при поддержке Range (не проверено).
- Источники: https://raw.githubusercontent.com/mozilla-firefox/firefox/main/browser/app/profile/firefox.js

  1. По умолчанию файлы сохраняются в «Загрузки» без вопроса (Chrome `prompt_for_download=false`, Firefox с версии 98).

**PDF-формы: AcroForm, XFA (госбланки), сохранение заполненного, предупреждение о несохранённом** · часто · тяжесть: высокая · у ChatGPT: нет

- Как должно быть:
  1. AcroForm: заполнение полей, переход по Tab и Shift+Tab в порядке документа, флажки, выпадающие списки. Ctrl+S сохраняет файл с данными. Если были правки, браузер спрашивает: «С изменениями / Оригинал».
  2. XFA: поддерживать хотя бы статические формы (Firefox с версии 93; по release notes, такие формы «used by multiple governments and banks»). Если поддержки нет, честно сказать «Форма требует Adobe Reader» и дать кнопку «Скачать», а не показывать заглушку XFA.
  3. При закрытии вкладки с несохранёнными данными в форме или аннотациях браузер просит подтверждения.
  4. JavaScript внутри PDF: в pdf.js он включён во всех сборках, кроме сборки для Chrome (`enableScripting=true`, кроме CHROME). Выбор между безопасностью и работой вычисляемых полей нужно сделать сознательно.
- Кто делает лучше / хуже: с XFA лучше всех справляется Firefox (93+). Chrome и Edge XFA не поддерживают (не проверено). Edge сильнее в аннотациях и рукописном вводе (не проверено).

**PDF: открыть во вкладке или скачать, octet-stream, имя файла при сохранении** · часто · тяжесть: средняя · у ChatGPT: нет
- Боль: «Хочу, чтобы PDF сразу скачивался, а он открывается во вкладке», и наоборот. «Нажал "Сохранить", получил `document.pdf` или `view.pdf` вместо нормального имени». «Сервер отдал PDF как octet-stream, и он скачался, а не открылся».
- Как должно быть:
  1. Настройка «Открывать PDF в браузере / Скачивать» есть и в настройках, и в самом просмотрщике.
  2. PDF, отданный как `application/octet-stream`, распознаётся по сигнатуре `%PDF` и открывается во встроенном просмотрщике (Firefox `pdfjs.handleOctetStream=true`). `Content-Disposition: attachment` обрабатывается согласно настройке.
  3. «Скачать» в просмотрщике (Ctrl+S) сохраняет исходный PDF с именем из `Content-Disposition` или URL, а не HTML-обёртку и не `document.pdf`.

Firefox задаёт действие для типа PDF, обрабатывает octet-stream и помнит прежний обработчик (`pdfjs.previousHandler.*`). Edge и Firefox навязываются PDF-просмотрщиком по умолчанию в Windows, и это раздражает (не проверено).

### Печать страниц

**Точность печати и «Сохранить как PDF»: фрагментация, «только первая страница», ссылки** · часто · тяжесть: высокая · у ChatGPT: нет
- Боль: «Печатается только первая страница, остальное обрезано» (flex, grid, `overflow:hidden`). «Строки таблицы разрезаны пополам». «Шапка сайта на каждой странице». «В PDF через "Microsoft Print to PDF" ссылки не кликаются».
- Как должно быть:
  1. Превью совпадает с результатом. `beforeprint` срабатывает до построения превью, `afterprint` — после. Раскладка строится по состоянию документа на момент печати. В iframe без `allow-modals` вызов `print()` просто возвращает управление, и ни `beforeprint`, ни `afterprint` не срабатывают.
  2. Flex, grid, multicol и таблицы корректно разбиваются на страницы. Контейнер с overflow не обрезает печать до одной страницы. Поддерживаются `break-inside: avoid`, повтор `thead`/`tfoot` на каждой странице, `@page` (`size`, `margin`) и `@media print`.
  3. Элементы `position: fixed` повторяются на каждой странице. Так ведёт себя Chrome (не проверено), это нужно учитывать.
  4. Встроенное «Сохранить как PDF» сохраняет текстовый слой, кликабельные ссылки и теги для доступности. Это аргумент против системного «Microsoft Print to PDF», который теряет ссылки (не проверено).
  5. Имя PDF по умолчанию — заголовок страницы, очищенный от запрещённых символов.
- Кто делает лучше / хуже: Chrome лучше всех разбивает страницы (LayoutNG) и сохраняет ссылки в PDF. У Firefox исторически были баги печати flex-контейнеров (не проверено). Для собственного движка это самый трудоёмкий пункт области: печать — отдельный режим раскладки с фрагментацией.
- Источники: https://html.spec.whatwg.org/multipage/timers-and-user-prompts.html (шаги печати, sandboxed modals flag)

**Колонтитулы с URL и датой, фоновая графика, поля, «только выделенное»** · часто · тяжесть: средняя · у ChatGPT: нет
- Боль: «Как убрать адрес сайта и дату из распечатки?» — один из самых частых вопросов о печати. «Таблица с цветными ячейками напечаталась белой». «Хочу напечатать только выделенный абзац».
- Как должно быть:
  1. Колонтитулы по умолчанию (как в Firefox): сверху слева заголовок (`&T`), сверху справа URL (`&U`), снизу слева «1 из 5» (`&PT`), снизу справа дата и время (`&D`). Галочка «Колонтитулы» хорошо видна в превью. Колонтитулы печатаются в полях страницы, поэтому при полях «Нет» они исчезают; это стоит объяснить прямо в интерфейсе.
  2. «Фоновая графика» по умолчанию выключена ради экономии тонера. Если на странице есть цветные фоны, превью подсказывает: «Напечатать фоны?».
  3. Пункт «Только выделенное» появляется, если на странице что-то выделено.
  4. Настройки сохраняются между печатями (`print.save_print_settings=true`). «Уместить по ширине» не уменьшает страницу мельче 20% (`print.shrink-to-fit.scale-limit-percent=20`).
  5. Длинный URL в колонтитуле усекается посередине.
  6. Превью открывается мгновенно и обновляется, не закрывая диалог. Системный диалог печати вызывается отдельным сочетанием. В Chrome это Ctrl+Shift+P, но в Firefox то же сочетание открывает приватное окно, поэтому для Lumen конфликт нужно решить до релиза.
- Кто делает лучше / хуже: у Firefox гибко настраиваемые колонтитулы, у Chrome одна галочка. Фон по умолчанию выключен у обоих (не проверено).
- Источники: https://raw.githubusercontent.com/mozilla-firefox/firefox/main/modules/libpref/init/all.js (`print.print_headerleft` и др., `print.shrink-to-fit.scale-limit-percent`, `print.save_print_settings`)

## Анти-цели области

- Не показывать запрос разрешения или уведомлений без жеста пользователя и из фоновой вкладки. Не давать сайту повторять запрос после отказов в обход эмбарго.
- Не делать кнопки запроса разрешения активными сразу после появления под курсором.
- Не выводить индикаторы блокировок (всплывающие окна, autoplay, загрузки, баннеры) плашками над страницей, сдвигающими контент. Не прятать обход блокировки глубоко в настройках.
- Не выкатывать новую блокирующую эвристику без удалённого выключателя и не ломать совместимость с вебом ради защиты.
- Не нажимать «Принять» в cookie-баннерах за пользователя по умолчанию. Не скрывать баннер, оставляя заблокированной прокрутку. Не применять косметические правила после первой отрисовки.
- Не позволять сайту подставлять свой текст в диалог beforeunload и показывать его без sticky activation. Не выстраивать цепочку таких диалогов при закрытии окна.
- Не давать `alert`/`confirm`/`prompt` блокировать другие вкладки или закрытие вкладки. Не добавлять «показать ещё» для усечённого текста диалога.
- Не считать Esc пользовательской активацией. Не отдавать сайту Ctrl+T, Ctrl+W, Ctrl+N, Ctrl+Shift+T и Ctrl+Tab.
- Не говорить «не удалось», если камеру запретила ОС или её держит другое приложение, а называть причину.
- Не предлагать сохранить пароль, подставленный автозаполнением, и не предлагать его после неудачного входа. Не показывать модальное окно сохранения поверх страницы.
- Не отдавать странице значения предпросмотра автозаполнения до выбора. Не сохранять `one-time-code`, пароли и `cc-*` в историю форм и в журнал восстановления текста.
- Не вызывать системный диалог Windows Hello или passkey при загрузке страницы без выбора пользователя.
- Не показывать недокачанный файл как готовый. Не удалять заблокированный файл молча. Не предупреждать о каждом `.exe` или `.zip` без реального сигнала. Не блокировать HTTP-загрузки с локальных адресов.
- Не сбрасывать при обновлении выбор пользователя: «Всегда спрашивать», действия по типам файлов.
- Не складывать в «Загрузки» файлы, которые пользователь только открыл.
- Не создавать имена файлов, недопустимые в Windows, и не терять Mark of the Web.
- Не печатать PDF растром 150 dpi и не масштабировать билеты и бланки «по размеру страницы» по умолчанию.
- Не показывать заглушку XFA без объяснения и кнопки «Скачать». Не навязываться PDF-просмотрщиком по умолчанию повторно.
- Не обрезать печать до одной страницы из-за контейнера с overflow. Не допускать расхождения превью и результата печати.
