### 1.2 Три примера пользователя — дословно

| Пример | Что сказано в документе | Чего нет |
|---|---|---|
| **Мигание курсора** | M01 (стр. 44): «При фокусе каретка видима и позиционируется по текстовым метрикам; мигание учитывает настройки ОС». §5 (стр. 493): «не фиксировать частоту мигания caret». Больше ничего. | Не сказано, откуда брать параметр (Windows `GetCaretBlinkTime()`, по умолчанию 530 мс; `INFINITE` означает «не мигать»). Нет системной толщины курсора (Windows, «Специальные возможности → Текстовый курсор»), таймаута мигания там, где ОС его задаёт (GTK). Нет требования к движку: мигание не должно перерисовывать страницу. |
| **Где печатаются символы** | Документ этот пример даже не интерпретирует. Прокрутка к каретке в длинном `input` или `textarea`. Окно кандидатов IME должно стоять у каретки, а не просто «не перекрываться». Положение каретки на мягком переносе (конец строки или начало следующей). Шорткаты в русской раскладке (Ctrl+С должен работать по физической клавише) — частая жалоба русскоязычных пользователей на нестандартные приложения. |
| **Подсветка ссылок** | M05 (стр. 48): «Status URL появляется без закрытия содержимого; браузер не подменяет CSS сайта». UX-01-001 (стр. 78). §5 (стр. 493): «не навязывать стили ссылок сайтам». J04 (стр. 22): hover → статус URL → middle click. | «Подсветка» сведена к пузырю с URL и запрету трогать CSS. Нет курсора-руки над `a[href]` из UA-стиля. Нет стилей ссылок по умолчанию для страниц без CSS и `:visited` с ограничениями приватности. Не сказано, что `:hover` обновляется после прокрутки колесом без движения мыши и снимается, когда указатель уходит из окна. Нет видимого фокуса ссылки при Tab, когда сайт поставил `outline:none` (браузер обязан решить это явно). Не сказано, что URL показывается и при фокусе с клавиатуры. Нет IDN/punycode для кириллических доменов и гомоглифов. Нет ни одного тайминга. Для ориентира, в Chrome (`status_bubble_views.cc`): появление через 80 мс, скрытие через 250 мс, ширина — треть окна, при приближении мыши ближе 20 px пузырь уезжает. |

**Вывод.** Каждый пример получил одну фразу-цель («учитывает настройки ОС», «без закрытия содержимого»). Мелочи, о которых просил пользователь, — это как раз числа, краевые состояния и источники значений. Именно их в документе нет.

## 3. Разделы 1–3 и 5–8

### Что ценно

- **Разделение слоёв (стр. 11): ENGINE / CHROME / PLATFORM / SITE** и правило «Не обещать средствами браузера то, что определяется кодом сайта». Лучшая идея документа. Для браузера на своём движке это ещё и карта владельцев: движок, оболочка, интеграция с ОС.
- **Карточка требования.** Статусы draft/specified/implemented/tested/blocked (стр. 13) и поля §6 (стр. 497): `standard_ref`, `preconditions`, `expected`, `negative_cases`, `evidence`. Шаблон правильный, но ни одно требование документа по нему не заполнено.
- **Сценарии J01–J20** — хороший каркас: ввод, выделение, ссылки, история, сеть, вкладки, формы, загрузки, разрешения, крах, доступность, DPI, обновление. Особенно удачны сценарии, о которых обычно забывают:
  - J06 — нестабильная сеть;
  - J12 — крах вкладки;
  - J14 — перенос окна между мониторами с разным DPI;
  - J20 — обновление браузера.
- **Честные анти-обещания:**
  - J05: «без ложных обещаний для динамических сайтов»;
  - J09: «resume только при поддержке сервера»;
  - M20: «не обещать восстановление произвольного JS-состояния»;
  - §5 (стр. 493): «не придумывать причину запроса геолокации», «не предполагать, что browser контролирует все ошибки сайтов».
- **Точные инженерные формулировки для своего движка:** M02 (графемы, ZWJ, RTL), M03 (события composition), M06 (hit testing при transform/zoom/scroll), M11 (scroll anchoring), M12 (дробный DPR).
- **§8** честно называет ограничения.

### Что пусто или неверно

- **Принципы (стр. 9)** — общие эвристики, которые не разрешают ни одного спора.
- **Критерии приёмки без измерения.** В разделах 1–3 и 5–8 «предсказуем*» встречается 6 раз, «корректн*» — 3, «понятн*/ясн*» — 4. Ещё 7 оговорок: «по возможности», «когда применимо», «без нужды», «необоснованных», «чрезмерной», «минимальна».
  - J03 (стр. 21): «Выделение предсказуемо; буфер обмена содержит ожидаемый текст». Ожидаемый кем?
  - J12 (стр. 30): «потеря состояния минимальна».
  - J16 (стр. 34): «без … чрезмерной фоновой нагрузки».
  - M10 (стр. 53): «Предсказуемая прокрутка, инерция».
  - M11 (стр. 54): «необоснованных скачков».
- **Числа.** Вне реестра есть только «20 вкладок», «100+ вкладок» и «Zoom 200–400%». Ни одной величины в мс, px, Гц или кадрах.
  - M07 «Drag threshold» (стр. 50) — порог без значения. Для сравнения, в Blink: 4 px; на macOS 3 px и задержка 150 мс перед перетаскиванием текста; правильно — брать системные `SM_CXDRAG`/`SM_CYDRAG`.
  - M10 — нет числа строк на щелчок колеса (`SPI_GETWHEELSCROLLLINES`, по умолчанию 3).
  - Метрики §6 (стр. 501) — только названия, без целевых значений и методики. «Плавность прокрутки» — сколько и чем мерить?
- **Инфляция приоритетов.** P0 стоит у 16 из 20 сценариев J, у 21 из 24 пунктов M и у 15 из 15 осмысленных строк реестра: 52 из 59 (88%). Определение P0 (стр. 13) — «без этого сценарий ненадёжен или опасен» — не соблюдается: например, M09 «меню отличается для … медиа» опасным не назовёшь. Очередь §7 (стр. 505–509) сортирует по P0, а при 88% P0 она ничего не упорядочивает.
- **Смешение уровней.**
  - M15 (стр. 58): горячие клавиши, mute, drag, pin и overflow — в одной строке.
  - M13 (стр. 56): шорткат, Esc и классификатор «URL или поиск» вместе.
  - J18 (стр. 36): пароль, passkey, OTP и ошибка сведены к одному критерию «поток не ломается».
  - Колонка в M называется «Проверяемое поведение» (стр. 42), но проверки в ней нет.
- **Спорные формулировки.**
  - M05 «браузер не подменяет CSS сайта» — слишком широко. У браузера обязаны быть UA-стили, он сам решает про `:focus-visible`, а forced colors (высокий контраст Windows) по стандарту перекрашивает сайт. Формулировка конфликтует с шаблонным аспектом «высокий контраст».
  - M21 «не принуждать сайты к анимациям» — оговорка ни о чём. Суть в другом: передавать сайту `prefers-reduced-motion`.
  - M18 «Не хранить CVV» — это продуктовое решение, а не UX-норма. При этом про главный сценарий паролей — автозаполнение логина — не сказано ничего.
- **Нет приоритетов глазами пользователя.**
  - «Аудитория: универсальный браузер для всех» (стр. 3), но ни одного сегмента или персонажа.
  - Позиционирование Lumen (приватный, лёгкий, прозрачный) в требованиях не отражено.
  - J01 — нет импорта закладок и паролей из прежнего браузера (первое действие человека, который меняет браузер) и выбора поисковика по умолчанию.
- **§5 «по материалу Qwen» (стр. 491)** — 13 заголовков тем без единого требования.

## 4. Чего не хватает в методе

1. **Источники данных.** Ни одного. Нужны источники с метрикой массовости:
   - русскоязычные: подсказки и частоты поисковых запросов («как вернуть закрытую вкладку», «пропал курсор в браузере», «не работает ctrl+c»), ответы mail.ru, Хабр, 4PDA, отзывы о браузерах в RuStore и Google Play;
   - глобальные: Chromium issue tracker по звёздам, Bugzilla по голосам, Mozilla Connect, feature requests Vivaldi с голосами, r/chrome, r/firefox, r/browsers, сообщества поддержки.

   Без этого «мелочи» берутся из общих знаний модели и не отражают реальные жалобы.
2. **Массовость.** Нет оценки «частота × тяжесть × доля пользователей». Набор текста, прокрутка, клик по ссылке и Back случаются сотни раз в день, и их дефект стоит дороже, чем PiP или печать. Приоритет должен считаться из этой матрицы, а не из номера строки.
3. **Совместимость с сайтами — пропущена.** Для не-Chromium движка это пользовательская проблема номер один. Нет сценария «сайт выглядит или работает не так»: как пользователь это заметит и что сможет сделать — перезагрузить без кэша, отключить блокировщик для сайта, отправить отчёт со снимком, открыть сайт в другом браузере. Восприятие скорости (первый кадр, отклик на ввод) сведено к «UI остаётся отзывчивым».
4. **Анти-цели.** Нет явного списка того, чего Lumen не делает: не перерисовывает сайты, не вставляет свои сервисы на новую вкладку, не переопределяет платформенные шорткаты и т. п. Обрывки есть в §5 и J05/J09/M20 — их надо собрать в норму.
5. **Платформенные конвенции.** «Согласно соглашениям платформы» (J04, M08) написано, но сами соглашения не перечислены. Целевые ОС не названы, а от них зависят Ctrl или Cmd и вставка средней кнопкой из PRIMARY-выделения в Linux. Нужен реестр системных параметров, которые браузер **читает, а не хардкодит**:
   - период мигания и толщина каретки;
   - время и зона двойного клика (`GetDoubleClickTime`, по умолчанию 500 мс; `SM_CXDOUBLECLK`);
   - порог drag;
   - строки прокрутки на щелчок колеса;
   - задержка hover;
   - масштаб текста ОС, forced colors, reduce motion, акцентный цвет, раскладки.
6. **Конфликт «браузер против сайта».** Принцип есть (стр. 11), правил разрешения нет. Нужна таблица «что сайт может переопределить, а что нет». Именно здесь пользователь видит разницу между браузерами. Минимум:
   - зарезервированные шорткаты (Ctrl+T/W/N/Shift+T/L);
   - `outline:none` и видимость фокуса;
   - `user-select:none` и копирование;
   - запрет вставки в поле пароля;
   - собственное контекстное меню сайта (Shift+ПКМ — браузерное);
   - перехват колеса (scroll-jacking);
   - `beforeunload`;
   - `autofocus` во время набора в адресной строке;
   - `cursor:none`.
7. **Измеримость и оракулы.** Ожидаемого результата нет нигде. Самый дешёвый оракул для собственного движка — дифференциальный: «ведёт себя как Chrome/Firefox на той же ОС, если отличие не задокументировано». К нему добавляются стандарты (UI Events, Selection API, CSS Scroll Anchoring, WCAG 2.2) и WPT. Каждое требование должно иметь число, метод замера и эталон. Пример метрик: задержка «ввод → кадр» (p95), доля кадров дольше 16,7 мс при прокрутке на 60 Гц, время возврата по Back.
8. **Русскоязычная специфика — целый класс требований:**
   - шорткаты в русской раскладке;
   - кириллические домены (.рф) и защита от гомоглифов;
   - кодировки windows-1251/KOI8-R на старых сайтах;
   - кириллица в именах загружаемых файлов (`Content-Disposition`);
   - орфография, «ё», типографские кавычки.

   В документе русский язык упомянут один раз (J02, стр. 20, «русский/латиница»), плюс шаблонная проверка «кириллица».
9. **Нет привязки к состоянию продукта** (стр. 3: «не аудит текущей реализации»). Требования без статуса «есть / нет / частично» не превращаются в бэклог.

### Пример 1. Мигание каретки

**Было** — M01 (стр. 44), P0: «При фокусе каретка видима и позиционируется по текстовым метрикам; мигание учитывает настройки ОС».

**Стало** — пять атомарных требований:
- **CARET-01. Период из ОС** — PLATFORM + ENGINE, **P1**. Значение не хардкодится, изменение настройки применяется без перезапуска:
  - Windows — `GetCaretBlinkTime()`, по умолчанию 530 мс на фазу; `INFINITE` — не мигать;
  - macOS — `NSTextInsertionPointBlinkPeriodOn/Off`;
  - GTK — `gtk-cursor-blink`, `-time`, `-timeout`.
- **CARET-02. Сброс при вводе** — ENGINE, **P0** (каждое нажатие, видно всем). После символа, Backspace, стрелки или клика каретка видна **в том же кадре**, что и результат, и цикл мигания начинается заново. При наборе с интервалом короче фазы каретка не гаснет.
- **CARET-03. Скрытие** — ENGINE, **P0**. Каретка не рисуется в неактивном окне, в скрытой вкладке и при непустом выделении. При возврате фокуса начинается с фазы «видна».
- **CARET-04. Толщина и цвет** — ENGINE + PLATFORM, **P1**. Толщина — максимум из 1 CSS px (с округлением до целого device px) и системной толщины Windows (`SPI_GETCARETWIDTH`). Цвет — `caret-color`; `auto` = `currentColor`.
- **CARET-05. Цена мигания** — ENGINE, **P1** (батарея). Мигание инвалидирует только прямоугольник каретки: при фокусе в поле на неподвижной странице за 10 с — 0 рестайлов и раскладок, около 2 инвалидаций в секунду.

**Проверка.** Автоматизация фокусирует `<input>` и снимает кадры 3 с.
- Каретка видна примерно в 50% кадров; длина фазы — 530 мс ± 1 кадр.
- Символ, введённый на фазе «скрыта», виден в следующем кадре.
- При отключённом мигании в ОС каретка видна в 100% кадров.
- Негатив: окно в фоне — 0% кадров с кареткой.
- Оракул: Chrome/Edge на той же машине.

### Пример 2. Подсветка ссылки и пузырь URL

**Было** — M05 (стр. 48): «Status URL появляется без закрытия содержимого; браузер не подменяет CSS сайта». UX-01-001 (стр. 78): «Проверить ссылку с длинным URL и выход указателя».

**Стало:**
- **LINK-01 (ENGINE, P0).** Над `a[href]`, `area[href]` и их потомками курсор — рука (UA-стиль `cursor:pointer`), если сайт не задал иное. Смена курсора — в том же кадре, что и `:hover`.
- **LINK-02 (ENGINE, P1).** `:hover` пересчитывается не позже 100 мс после остановки прокрутки, даже без движения мыши, и снимается, когда указатель уходит из окна.
- **LINK-03 (CHROME, P0).** Пузырь стоит в нижнем левом углу области содержимого (в RTL-интерфейсе — в правом). Появляется не позже 100 мс после наведения **или фокуса ссылки с клавиатуры**. Скрывается с задержкой около 250 мс, чтобы не мигать при переходе между соседними ссылками. Ориентир — Chrome: 80 и 250 мс.
- **LINK-04 (CHROME, P1).** Ширина пузыря — не больше трети окна. Схема и хост видны целиком, многоточие ставится в пути. При продолжении наведения пузырь разворачивается до полного URL.
- **LINK-05 (CHROME, P0).** Если указатель подходит к пузырю ближе 20 px, пузырь уходит (за нижний край или в противоположный угол) и не закрывает то, на что наведён указатель.
- **LINK-06 (CHROME, P0, безопасность).** Показывается абсолютный URL после разрешения относительного. Хост выводится в Unicode только если проходит проверку на смешение письменностей: `пример.рф` читаемо, `аpple.com` с кириллической «а» — показывается в punycode.
- **Вместо «не подменяет CSS».** UA-стиль ссылок действует там, где сайт не задал свой. Исключения — forced colors и видимость фокуса.

**Проверка.** Тестовая страница: короткая ссылка, ссылка на 400 символов, IDN-ссылка, ссылка у нижнего левого угла.
- Наведение → через 100 мс пузырь виден, текст совпадает с ожидаемым.
- Движение к пузырю → его рамка не попадает в 20 px вокруг указателя.
- Уход указателя → через 300 мс пузыря нет.
- Оракул: Chrome/Firefox.

### Пример 3. «Где печатаются символы»

**Было** — UX-03-011 (стр. 147), P0: «Текст и IME: предсказуемость фокуса — caret, выделение, Unicode, композиция ввода» | «Проверить фокус до и после действия».

**Стало** — **INPUT-TARGET: символы попадают туда, где пользователь начал печатать.** ENGINE + CHROME, **P0**. Обоснование приоритета: увод ввода означает потерю данных, а пароль, ушедший в адресную строку, утекает в поисковик и историю.
- **01.** Пока у адресной строки есть несохранённая правка, `focus()` и `autofocus` страницы не забирают фокус. После завершения загрузки текст в строке и положение каретки сохраняются. `autofocus` не срабатывает, если пользователь уже сфокусировал другой элемент (так требует HTML).
- **02.** Если главный поток страницы занят до 1 с, ни один символ не теряется и порядок сохраняется. `keydown`, `beforeinput` и `input` доставляются по порядку после разблокировки. UI браузера (вкладки, адресная строка) всё это время отвечает быстрее 100 мс.
- **03.** Первый символ в поле, которое пользователь прокрутил за экран, возвращает поле в видимую область. В однострочном поле, где текст шире поля, каретка всегда видна.
- **04.** Окно кандидатов IME стоит у каретки (TSF/IMM), а не в углу окна.
- **05.** Ctrl+C/V/X/A/Z/T/W/L работают в русской раскладке — по виртуальному коду клавиши, а не по символу.

**Проверка.**
- Страница с `setInterval` на 500 мс busy-loop и с отложенным `input.focus()`.
- Системным вводом (SendInput, 10 символов в секунду) набрать «привет мир» сначала в адресной строке, потом в поле.
- Ожидается: в адресной строке ровно «привет мир», поле страницы пустое; во втором прогоне — «привет мир» в поле, каретка в конце.
- Негатив: IME-композиция во время блокировки потока не обрывается.
- Оракул: Chrome/Firefox, UI Events, Input Events Level 2.
