# WPT vendor notes — `fedcm`

## Vendoring (`tests/wpt/VENDOR.md`)

Test category, added 2026-07-28 by the WPT-VENDOR backlog (`ROADMAP.md` `WPT-VENDOR-fedcm`, `docs/wpt-status.md`), included despite its 🚫 scope note (Federated Credential Management — no IdP integration layer) by the same standing user decision as `accelerometer`/`acid`/`ai`/…/`eyedropper`. Same pinned commit, `git sparse-checkout` at the same commit hash, 192 files (`META.yml`, `WEB_FEATURES.yml`, 39 root `.https.` tests plus their `.headers` files, 12 subdirectories, and a large `support/` tree of 60+ Python `wptserve` IdP endpoints, IdP JSON manifests and `fedcm-helper.sub.js`). Out-of-category helpers not vendored: `/resources/testdriver.js`+`testdriver-vendor.js` (85 files), `/common/get-host-info.sub.js` (4), `/storage-access-api/helpers.js` (1), `/service-workers/service-worker/resources/test-helpers.sub.js` (1), same documented survey gap as `accname`/`audio-session`. `run_report.py --all --root fedcm --recursive` completed in 44 s (81 selected ids, matching wptrunner's own count — no `manual/` directory here, so the `-manual`-substring miscount seen on `eyedropper` does not apply): **all 81 ids SKIP with one and the same reason** (`Executor does not support testdriver.js`) — the first category in this backlog with a perfectly uniform outcome and no TIMEOUT/ERROR/FAIL at all. That is structural, not incidental: FedCM is specified to run through a browser-mediated account chooser, so every test synthesises the user's choice via `test_driver`; as a side effect the HTTPS-port gap that dominates comparable runs (84 of 103 files are `.https.`) never even gets a chance to fire, SKIP happens first. 0/81 harness OK, 0/0 subtests. As with `eyedropper`, the finding came from a `--dump-layout` probe outside WPT — but here the FedCM stub itself turned out to be *correct* (Phase 0, documented in `crates/js/src/credentials.rs:17-19`, really does reject with `NotSupportedError`); the defect is one level up, in the shared `CredentialsContainer` object that the in-scope WebAuthn branch uses too — BUG-366 (methods on the instance instead of the prototype, the internal `_get_original` monkey-patch guard leaked as an enumerable writable web-visible property, interface objects callable without `new`, no `Symbol.toStringTag`, clobbered `constructor`). See `docs/wpt-status.md` for details.

## Прогон и находки (`docs/wpt-status.md`)

Вендорена целиком 2026-07-28 (коммит `35be3b44`, `tests/wpt/fedcm/`, 192 файла: `META.yml`/`WEB_FEATURES.yml`, 39 корневых `.https.`-тестов плюс их `.headers`-файлы, 12 подкатегорий (`alternative-identifiers`, `fedcm-accounts-push`, `fedcm-authz`, `fedcm-button-and-other-account`, `fedcm-error-attribute`, `fedcm-flexible-token`, `fedcm-login-status`, `fedcm-multi-idp`, `fedcm-navigation-interception`, `fedcm-register`, `fedcm-well-known-validation`, `third-party-iframe`), `support/` — 60+ `wptserve`-обработчиков IdP на Python, JSON-манифесты IdP, `fedcm-helper.sub.js` и вспомогательные страницы, плюс `LICENSE-WPT.md`), включена несмотря на скоуп 🚫 (Federated Credential Management) по тому же постоянному решению пользователя, что и `accelerometer`/`acid`/`ai`/…/`eyedropper`. Невендоренные внекатегорийные зависимости: `/resources/testdriver.js`+`testdriver-vendor.js` (85 файлов), `/common/get-host-info.sub.js` (4), `/storage-access-api/helpers.js` (1), `/service-workers/service-worker/resources/test-helpers.sub.js` (1) — тот же survey-gap, что `accname`/`audio-session`. `<meta name=variant>` не используется, каталога `manual/` нет, поэтому счётчик `run_report.py` и счётчик wptrunner сошлись (81 и 81 — контраст с завышением на `eyedropper`). `run_report.py --all --root fedcm --recursive` — **44 с, 0/81 harness OK, 0/0 сабтестов**, и это **первая категория бэклога со стопроцентно однородным исходом: все 81 id — SKIP по одной и той же причине** (`Executor does not support testdriver.js`), без единого TIMEOUT/ERROR/FAIL. Причина не случайна и не чинится вендорингом: FedCM по спеке обязателен к прохождению через браузерный диалог выбора аккаунта, поэтому каждый тест категории синтезирует пользовательский выбор через `test_driver`; заодно это значит, что HTTPS-порт-гэп (84 из 103 файлов — `.https.`), обычно доминирующий в таких прогонах, здесь до срабатывания вообще не доходит — SKIP наступает раньше. Самый дешёвый прогон бэклога по времени на файл. Обследование, как и на `eyedropper`, сделано пробой `--dump-layout` вне WPT. **Сам FedCM-стаб оказался исправен**: `crates/js/src/credentials.rs:17-19` документирует Phase 0 («always rejects with `NotSupportedError`»), и проба это подтверждает — `navigator.credentials.get({identity:…})` и `IdentityProvider.getUserInfo()` отклоняются именно `NotSupportedError`, `new IdentityCredential()` бросает `TypeError`, `IdentityCredential.prototype instanceof Credential`; то есть в отличие от `eyedropper`/[BUG-365](../../bugs/BUG-365-FIXED.md) стаб не расходится с собственной документацией. Не заведено багом и намеренно зафиксировано как ожидаемое: `IdentityCredential.disconnect` (20 обращений в тестах), `IdentityProvider.resolve` (18), `IdentityProvider.close` (3) — `undefined`, а FedCM Login Status API (`navigator.login`/`NavigatorLogin`, 12 обращений к `setStatus`) отсутствует в `crates/` целиком; отсутствие нереализованного API — честный feature detection, тот же класс, что `delegated-ink`/`bluetooth`. Единственная реальная находка лежит **не** в 🚫-скоупном FedCM, а в общем для всей категории объекте `CredentialsContainer`, то есть задевает и в-скоупную ветку WebAuthn/passkeys — [BUG-366](../../bugs/BUG-366-FIXED.md): `navigator.credentials` расходится с WebIDL по пяти пунктам. Главный из них — утечка внутренней детали реализации в веб: `crates/js/src/digital_credentials.rs:44` монки-патчит `get` ради перехвата `options.digital` и кладёт оригинал прямо на публичный объект (`navigator.credentials._get_original`, `enumerable=true writable=true configurable=true`), так что любой скрипт страницы его видит в `Object.keys`, может прочитать (ссылка на необёрнутый `get` в обход перехвата) и перезаписать — а поскольку то же свойство служит флагом идемпотентности установки, страница, присвоившая его заранее, подавляет установку шима; для браузера, который позиционируется как приватный, это ещё и однозначный фингерпринт-маркер. Остальные четыре пункта: методы `create`/`get`/`preventSilentAccess`/`store` присвоены инстансу (`credentials.rs:360,390,417,418`), а не `CredentialsContainer.prototype` (где только `constructor`), отчего все четыре перечислимы в `Object.keys`/`for...in` при пустом `Object.keys` у настоящего `CredentialsContainer` (тот же класс, что пункт про обработчики событий в [BUG-363](../../bugs/BUG-363-FIXED.md)); `CredentialsContainer()` и `IdentityProvider()` вызываются без `new` вместо `TypeError` — причём соседние `PublicKeyCredential`/`OTPCredential`/`IdentityCredential` в том же файле бросают его правильно; нет `Symbol.toStringTag` (`[object Object]`, тот же пункт, что в BUG-365); `IdentityCredential.prototype.constructor === Credential` — замена прототипа целиком не восстанавливает `constructor` (тот же паттерн в строках 295, 297, 300). Профильный WPT-тест для фикса существует и уже вендорен (`credential-management/idlharness.https.window.js`), но `.https.`-only и упирается в HTTPS-порт-гэп, поэтому автоматической верификации фикса сегодня нет ни в одной категории
