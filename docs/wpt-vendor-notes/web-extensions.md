# WPT vendor notes — `web-extensions`

## Vendoring (`tests/wpt/VENDOR.md`)

Test category, added 2026-08-09 by the WPT-VENDOR backlog (`ROADMAP.md` `WPT-VENDOR-web-extensions`, `docs/wpt-status.md`), scope 🚫 (out of scope — extension model is a separate architecture Lumen does not implement at all). Same pinned commit, `git sparse-checkout add` at the same commit hash, `LICENSE-WPT.md` copied from the sibling `web-based-payment-handler` category, 13 upstream files (`META.yml`, 6 `browser.<api>.extension.js` test files — `alarms`/`bookmarks`/`browsingData`/`idle`/`runtime`/`storage` — + matching `resources/<api>/{background.js,manifest.json}` pairs). `run_report.py --all --root web-extensions --recursive` selected **0 ids** ("no tests selected") — not a run-time gap but a selector limit: `all_vendored_test_ids()` only recognizes `.any.js`/`.window.js`/`.html`/`.htm`, and this category's entire corpus is the one upstream-specific `.extension.js` type (`tools/manifest/sourcefile.py` classifies it as `TestharnessTest`; `tools/serve/serve.py::ExtensionHandler` serves it as `.extension.html` wrapped with `testdriver.js?feature=extensions` + `web-extensions-helper.js`, which needs the browser to actually load a WebExtension). Lumen has no such capability whatsoever (no `--load-extension`, no manifest loader, `grep -rn 'browser\.runtime\|WebExtension' crates/` — zero hits outside an unrelated BiDi `"browser"` event-category string) — extending `run_report.py` to select this single test type would not be worth it without the loading capability itself, and the gap matches the 🚫 scope literally rather than being a tooling shortfall. Live probe (`--mcp-live-port`, a page with an inline `<script>` — `about:blank` never gets a JS context) confirmed `typeof browser === 'undefined'`, `typeof chrome === 'undefined'`, and zero `window` keys matching `/browser\|extension\|webext/i` — expected, not a bug. No new bug filed this pass. See `docs/wpt-status.md` for the full breakdown.
