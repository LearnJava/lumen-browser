# WPT vendor notes — `mediacapture-streams`

## Vendoring (`tests/wpt/VENDOR.md`)

Test category, added 2026-08-05 by the WPT-VENDOR backlog (`ROADMAP.md` `WPT-VENDOR-mediacapture-streams`, `docs/wpt-status.md`), included despite its 🚫 scope note (media capture — no pipeline) by the same standing user decision as `mediacapture-region`/`mediacapture-record`/`mediacapture-insertable-streams`/`mediacapture-image`/`mediacapture-handle`/`mediacapture-fromelement`. Same pinned commit, `git sparse-checkout add` at the same commit hash, 73 files (`META.yml`, `WEB_FEATURES.yml`, `LICENSE-WPT.md`, 39 root test files including `idlharness.https.window.js`, `crashtests/enumerateDevices-after-discard-1.https.html`, `support/`). No `variant` hits, no out-of-category deps; 59 of 65 selectable files are `.https.`; 46 files reference `testdriver.js`. `run_report.py --all --root mediacapture-streams --recursive` completed in ~18 min (58 ids from the glob; 57 actually selected by wptrunner — the 58th, `crashtests/enumerateDevices-after-discard-1.https.html`, is an unsupported `crashtest` type for product `lumen`, same exclusion as `mediacapture-image`'s `ImageCapture-grabFrame-crash.https.html`): **2/57 harness OK, 0/3 subtests passed**. 53 `.https.` tests TIMEOUT on the standard TLS `UnknownIssuer` gap (same class as every prior category in this backlog). 2 tests ERROR instantly instead of timing out — reconfirmation of the already-filed BUG-380 (executor doesn't check `browsingContext.navigate`'s outcome after a failed TLS navigation and reuses the browsing context, so the next poll returns the previous test's stale results). The 2 harness-OK tests are both non-`.https.` and both FAIL their sole/only subtests, neither indicating a new engine defect: `MediaDevices-SecureContext.html` expects `isSecureContext` to read `false` when served over plain `http://127.0.0.1`, but per the Secure Contexts spec `127.0.0.1`/`localhost` are always potentially-trustworthy origins regardless of scheme — the test can only pass on a genuinely non-loopback insecure host, which this wptrunner setup never serves from (a test-infra ceiling, not a Lumen bug, distinct from the TLS-cert gap). `MediaStream-supported-by-permissions-policy.html` asserts `document.permissionsPolicy.features()` advertises `"camera"`/`"microphone"`; both FAIL because Lumen's Permissions Policy feature list doesn't include either — consistent with the category being 🚫-scope (no capture pipeline, so no policy-gated capture features to advertise). Live grep of `crates/js/src/media_devices.rs` confirmed `getUserMedia`/`MediaStream`/`MediaStreamTrack` themselves are implemented (Phase 1), matching every other `mediacapture-*` category's finding that the API exists but almost every test is blocked before reaching it by the TLS gap. No bug filed — the TLS gap and BUG-380 are already tracked, and the two harness-OK failures are infra/scope ceilings, not engine defects. See `docs/wpt-status.md` for the full breakdown.

Ни variant-ов, ни вне-категорийных зависимостей; 59 из 65 файлов `.https.`; 46 тянут `testdriver.js`. Прогон `run_report.py --all --root mediacapture-streams --recursive` (~18 мин): глоб даёт 58 id, wptrunner реально отобрал 57 (58-й, `crashtests/enumerateDevices-after-discard-1.https.html`, — неподдерживаемый тип `crashtest`, тот же класс исключения, что `ImageCapture-grabFrame-crash.https.html` у `mediacapture-image`): **2/57 harness OK, 0/3 сабтестов passed**. 53 `.https.`-теста TIMEOUT на стандартном TLS-гэпе (`UnknownIssuer`, тот же класс, что весь бэклог `mediacapture-*`). 2 теста дали мгновенный ERROR вместо TIMEOUT — переподтверждение уже заведённого BUG-380 (исполнитель не проверяет исход `browsingContext.navigate` после провала TLS-навигации и переиспользует browsing context, отдавая результаты предыдущего теста). Живой грep `crates/js/src/media_devices.rs` подтвердил `getUserMedia`/`MediaStream`/`MediaStreamTrack` реализованы (Phase 1), тот же вывод, что у всего бэклога `mediacapture-*`: API есть, но почти все тесты блокируются TLS-гэпом раньше, чем до него доходят. Не заведён отдельный баг — TLS-гэп и BUG-380 уже отслеживаются, а оба harness-OK-провала — потолки инфраструктуры/скоупа, не дефекты движка
