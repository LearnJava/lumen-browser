# WPT vendor notes — `compression`

## Vendoring (`tests/wpt/VENDOR.md`)

Test category, added 2026-07-25 by the WPT-VENDOR backlog (`ROADMAP.md` `WPT-VENDOR-compression`, `docs/wpt-status.md`), in-scope (⬜, Compression Streams API — WICG spec, `CompressionStream`/`DecompressionStream` already implemented in Lumen, `crates/js/src/dom.rs`). Same pinned commit, `git sparse-checkout` at the same commit hash, 28 files (`META.yml`, `WEB_FEATURES.yml`, 18 `.any.js` compress/decompress tests, `idlharness.https.any.js`, `resources/` — 4 JS helpers, `third_party/pako/` — reference inflate library the tests use to cross-check our compressed output independent of our own `DecompressionStream`). Two tests reference un-vendored `/media/foo.vtt`+`/media/test-av-384k-…webm`, same documented survey gap as `FileAPI`/`ai`. `run_report.py --all --root compression --recursive` completed fully (19 selected ids, ~2:12): 14/19 harness OK, 20/317 subtests passed; 2 ERROR (session/URL-reuse artifact, same class as `accelerometer`/`beacon`/`client-hints`), 3 TIMEOUT. Unlike most first-pass entries, most of the FAIL volume isn't a missing API — it's a genuine **V8-specific engine bug**: a live `script.evaluate` diagnostic (bypassing the Streams API) showed `_lumen_compress_bytes`/`_lumen_sha_digest` always receive an **empty** `Vec<u8>` argument under V8 regardless of what's actually passed from JS, root-caused to `v8_to_jsvalue` (`crates/js/src/v8_compat.rs`) silently mapping any Array/Object argument to `JsValue::Null` instead of converting it (unlike the parallel `from_v8` in `v8_runtime.rs`, which handles arrays correctly). `cargo test -p lumen-js`'s existing coverage didn't catch this — those unit tests run through `QuickJsRuntime` (rquickjs), never the non-default `v8-backend` feature. Filed as [BUG-342](../../bugs/BUG-342-FIXED.md) (broad impact: any `_lumen_*` native taking a `Vec<u8>`/`Vec<u32>`/`Vec<String>`/`Vec<f64>` argument under V8, including `WebCryptoAPI`'s `crypto.subtle.digest` — not separately re-verified there). See `docs/wpt-status.md` for details.

## Прогон и находки (`docs/wpt-status.md`)

Вендорена целиком 2026-07-25 (`tests/wpt/compression/`, 28 файлов: `META.yml`, `WEB_FEATURES.yml`, 18 `.any.js` compression/decompression тестов, `idlharness.https.any.js`, `resources/` — `concatenate-stream.js`+`decompress.js`+`decompression-input.js`+`formats.js`, `third_party/pako/` — reference inflate for cross-checking our compressed output). Два теста ссылаются на невендоренные `/media/foo.vtt`+`/media/test-av-384k-…webm` (та же методология survey-gap, что `FileAPI`/`ai`). `run_report.py --all --root compression --recursive` прошёл полностью (19 отобранных id, ~2:12): 14/19 harness OK, 20/317 сабтестов passed; 2 ERROR (session/URL-reuse артефакт, тот же класс, что `accelerometer`/`beacon`/`client-hints` — `compression-with-detach.any.html`, `idlharness.https.any.html`), 3 TIMEOUT (`decompression-correct-input.any.html`/`decompression-extra-input.any.html`/`decompression-uint8array-output.any.html`, гэп с `/media/*` внутри `formats.js`-независимых тестов не объясняет — отдельно не диагностировано). Основная масса FAIL — не отсутствие API (`CompressionStream`/`DecompressionStream` реально реализованы, `crates/js/src/dom.rs`), а **реальный V8-специфичный движковый баг**: живая диагностика через `script.evaluate` (bypass Streams API) показала, что `_lumen_compress_bytes`/`_lumen_sha_digest` под V8 всегда получают **пустой** `Vec<u8>`-аргумент независимо от того, что реально передано из JS (array literal / `Array.from` / `Uint8Array`) — root-caused до `v8_to_jsvalue` (`crates/js/src/v8_compat.rs`), которая для Array/Object аргументов молча возвращает `JsValue::Null` вместо рекурсивной конвертации (в отличие от параллельной `from_v8` в `v8_runtime.rs`, которая Array обрабатывает верно). Существующий `cargo test -p lumen-js` не ловит баг — юнит-тесты идут через `QuickJsRuntime` (rquickjs), не через V8 (`v8-backend` не дефолтная фича). Заведён [BUG-342](../../bugs/BUG-342-FIXED.md) — широкий охват (любой `_lumen_*`-нативный биндинг с `Vec<u8>`/`Vec<u32>`/`Vec<String>`/`Vec<f64>`-аргументом под V8), затрагивает и `WebCryptoAPI` (`crypto.subtle.digest`), не перепроверено там отдельно
