# WPT vendor notes — `mimesniff`

## Vendoring (`tests/wpt/VENDOR.md`)

Test category, added 2026-08-05 by the WPT-VENDOR backlog (`ROADMAP.md` `WPT-VENDOR-mimesniff`, `docs/wpt-status.md`), scope ⬜ (candidate — MIME-sniffing itself is in-scope, unlike the surrounding 🚫-heavy `mediacapture-*`/`mediasession`/`merchant-validation` run). Same pinned commit, `git sparse-checkout add` at the same commit hash, `LICENSE-WPT.md` copied from the sibling `mediasession` category, 34 files total (`META.yml`, `README.md`, `media/`, `mime-types/`, `sniffing/`). No `variant` hits, no `.https.` files, no `testdriver.js` references — the cheapest predictor profile possible; 6 selectable ids (`media/media-sniff.window.html`, `mime-types/charset-parameter.window.html`, `mime-types/parsing.any.html`, `sniffing/html-comment.tentative.window.html`, `sniffing/html.window.html`, `sniffing/mislabeled-binary-resource.tentative.window.html`). `run_report.py --all --root mimesniff --recursive` completed in 1 min 17 s: **4/6 harness OK, 2/7 subtests passed**. Four files hit the already-filed BUG-347 (`fetch()` doesn't resolve relative URLs against the document base) — `charset-parameter.window.html`/`parsing.any.html` (`fetch: network error for resources/mime-types.json`), `html-comment.tentative.window.html` (`fetch: network error for support/html-comment?pipe=...`), and one of `mislabeled-binary-resource.tentative.window.html`'s two subtests (`fetch: network error for resources/binary-data.bin`; its other subtest FAILs for an unrelated reason — an `<iframe>` navigated to a `text/plain`-served HTML resource has a non-null `contentDocument`, i.e. it gets rendered as HTML instead of blocked, but this could not be isolated from the missing-iframe-browsing-context gap (BUG-359's sibling) in the time available and is not filed separately). `html.window.html` (`window.open("support/atom.html")` / `.../rss.html`) hits the already-filed BUG-359 (`window.open` doesn't resolve relative URLs) — reconfirmation, not new. `media/media-sniff.window.html` surfaced a new, more serious defect: setting `<audio>.src` to a relative/unresolvable URL permanently deadlocks the JS engine — confirmed live via `--mcp-live-port` on two independent fresh processes, where the very `eval` call executing `el.src = 'resources/x.mp3'` itself never returns, and every later `eval` on the same process (even the trivial `window.__ready`) times out identically from then on; the `lumen.exe` process stays alive (visible in `tasklist`), so this is a true JS-thread/automation-channel deadlock, not a crash. Filed as [BUG-638](../../bugs/BUG-638-OPEN.md). See `docs/wpt-status.md` for the full breakdown.
