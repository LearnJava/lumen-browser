# WPT vendor notes — `close-watcher`

## Vendoring (`tests/wpt/VENDOR.md`)

Test category, added 2026-07-25 by the WPT-VENDOR backlog (`ROADMAP.md` `WPT-VENDOR-close-watcher`, `docs/wpt-status.md`), in-scope (⬜, CloseWatcher API — WICG spec, already implemented in Lumen as an engine-agnostic JS shim, `crates/js/src/close_watcher.rs`). Same pinned commit, `git sparse-checkout` at the same commit hash, 54 files (`META.yml`, `WEB_FEATURES.yml`, root-level tests, `esc-key/`+`iframes/`+`user-activation/` subcategories, `resources/helpers.js`). Out-of-category helpers not vendored: `/common/top-layer.js`, `/resources/testdriver.js`+`testdriver-vendor.js`+`testdriver-actions.js`, same documented survey gap as `FileAPI`/`clipboard-apis`. Manifest selects 65 ids (49 files, several with `?dialog`/`?CloseWatcher` query variants) — `run_report.py --all --root close-watcher --recursive` completed fully (~19s): 63 SKIP (`Executor does not support testdriver.js`, all of `user-activation/`+`esc-key/`); `frame-removal.html` TIMEOUT (detaching an iframe during the `cancel` event hangs the harness, 0/6 unexpected); `inside-event-listeners.html` harness OK but 8/12 subtests, 4 FAIL — surfaced a genuine engine bug rather than an unimplemented-API gap: `CloseWatcher.requestClose()`, called re-entrantly from its own `oncancel` handler, recurses without bound (`this._closed` is only set inside `_fireClose()`, i.e. after `cancel` has already dispatched, so the re-entrant call re-enters the same guard and fires another `cancel`) — recorded event arrays of length 9497/5520 instead of 2. Filed as [BUG-340](../../bugs/BUG-340-OPEN.md) (unlike most first-pass vendor entries, this one *is* filed — it's a functional defect in an implemented feature, not a missing API). 1/65 harness OK, 8/18 subtests. See `docs/wpt-status.md` for details.
