# WPT vendor notes — `gamepad`

## Vendoring (`tests/wpt/VENDOR.md`)

Test category, added 2026-07-28 by the WPT-VENDOR backlog (`ROADMAP.md` `WPT-VENDOR-gamepad`, `docs/wpt-status.md`), included despite its 🚫 scope note (hardware API — gamepad controllers) by the same standing user decision as `accelerometer`/`fledge`/`eyedropper`. Same pinned commit, `git sparse-checkout` at the same commit hash, 15 files (`META.yml`, `WEB_FEATURES.yml`, 6 `*-manual(.https).html`, 7 non-manual test files, `LICENSE-WPT.md`). No testdriver.js anywhere in the category (zero SKIP), 4 `.https.` files (2 of them manual, excluded). Two out-of-category dependencies not vendored: `idlharness.window.js` → `/resources/WebIDLParser.js`+`idlharness.js` (same documented survey gap as `FileAPI`/`fullscreen`), `permissions-policy-gamepad.html` → `/permissions-policy/resources/permissions-policy.js`. `run_report.py --all --root gamepad --recursive` completed in **1 min 7 s**: the glob found 7 non-manual ids, but wptrunner's manifest selected only 6 — `permissions-policy-gamepad.html` is a bare `<script>` fixture with no `testharness.js` include (a `postMessage` target for other tests' iframes), correctly classified `support` and excluded, not a gap. **1/6 harness OK, 0/3 subtests passed**: `gamepad-default-permissions-policy.https.sub.html` TIMEOUT (ordinary HTTPS-port gap); `idlharness.window.html` TIMEOUT (the un-vendored idlharness deps, not a Lumen bug); `idlharness-extensions.https.window.html` ERROR (session-reuse artifact, same class as BUG-380 — result tagged with the previous test's URL); `gamepad-supported-by-permissions-policy.html` ran (harness OK) but its subtest FAILs on the already-filed BUG-361 (`permissionsPolicy.features()` → `[]`); `gamepad-permissions-policy-event-listener.html` and `not-fully-active.html` both TIMEOUT on the same root cause, confirmed by a live `--mcp-live-port`/`eval` probe: a `srcdoc` `<iframe>`'s `onload` never fires and a `postMessage` posted from inside it never arrives at the parent, because `contentWindow`/`contentDocument` are genuinely `null` (a `typeof` check reports `"object"` because `typeof null === "object"` — verified by chaining a property access, which throws `Cannot read properties of null`) — the already-documented `<iframe>`-has-no-browsing-context gap (BUG-381/BUG-383, category `focus`), not a new finding. The same live probe, run against the Gamepad API itself (implemented, Phase 0, `crates/js/src/gamepad.rs`) on a page with no test scaffolding at all, found a genuine new bug: BUG-392 — `navigator.getGamepads()` always returns 4 `null` slots instead of the spec-required 0 before any device has connected, and `ongamepadconnected`/`ongamepaddisconnected` are missing as `Window` event-handler IDL attributes even though `addEventListener` for the same event types works. See `docs/wpt-status.md` for details.

## Прогон и находки (`docs/wpt-status.md`)

Вендорена целиком 2026-07-28 (коммит `35be3b44`, `tests/wpt/gamepad/`, 15 файлов: `META.yml`, `WEB_FEATURES.yml`, 6 `*-manual(.https).html`, 7 не-manual тестовых файлов, `LICENSE-WPT.md`), включена вопреки скоупу 🚫 (аппаратный API) тем же постоянным решением пользователя, что `accelerometer`/`fledge`/`eyedropper`. Ни одного `testdriver.js`-файла во всей категории (SKIP = 0), 4 `.https.` файла (2 из них manual, исключены). Два внекатегорийных хелпера не довендорены: `idlharness.window.js` → `/resources/WebIDLParser.js`+`idlharness.js` (тот же пробел, что `FileAPI`/`fullscreen`), `permissions-policy-gamepad.html` → `/permissions-policy/resources/permissions-policy.js`. `run_report.py --all --root gamepad --recursive` — **1 мин 7 с**: глоб дал 7 не-manual id, wptrunner отобрал только 6 — `permissions-policy-gamepad.html` не тест, а голая `<script>`-фикстура без `testharness.js` (postMessage-цель для iframe других тестов), манифест верно классифицирует её как `support` и не запускает, это не разрыв. **1/6 harness OK, 0/3 сабтестов**: `gamepad-default-permissions-policy.https.sub.html` — TIMEOUT, обычный HTTPS-порт-гэп; `idlharness.window.html` — TIMEOUT на невендоренных idlharness-зависимостях, не Lumen-баг; `idlharness-extensions.https.window.html` — ERROR, сессионный артефакт класса [BUG-380](../bugs/BUG-380-FIXED.md) (результат помечен URL-ом предыдущего теста); `gamepad-supported-by-permissions-policy.html` исполнился (harness OK), но сабтест падает на уже заведённый [BUG-361](../bugs/BUG-361-FIXED.md) (`permissionsPolicy.features()` → `[]`); `gamepad-permissions-policy-event-listener.html` и `not-fully-active.html` — оба TIMEOUT по одной причине, подтверждённой прямой пробой `--mcp-live-port`/`eval`: у `srcdoc`-`<iframe>` никогда не срабатывает `onload`, а `postMessage` изнутри него не доходит до родителя, потому что `contentWindow`/`contentDocument` — настоящий `null` (`typeof` вводит в заблуждение, отдавая `"object"`, потому что `typeof null === "object"`; обращение к свойству бросает `Cannot read properties of null`) — уже задокументированный пробел «`<iframe>` без browsing context» ([BUG-381](../bugs/BUG-381-OPEN.md)/[BUG-383](../bugs/BUG-383-OPEN.md), категория `focus`), не новая находка. Та же живая проба, направленная на саму Gamepad API (реализована, Phase 0, `crates/js/src/gamepad.rs`) на пустой странице без тестового каркаса, дала настоящую новую находку: [BUG-392](../bugs/BUG-392-OPEN.md) — `navigator.getGamepads()` всегда возвращает 4 слота `null` вместо требуемых спекой 0 до первого подключения устройства, а `ongamepadconnected`/`ongamepaddisconnected` отсутствуют как event-handler IDL-атрибуты на `Window`, хотя `addEventListener` для тех же событий работает.
