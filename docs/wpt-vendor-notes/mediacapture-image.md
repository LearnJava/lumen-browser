## Vendoring (`tests/wpt/VENDOR.md`)

Test category, added 2026-08-05 by the WPT-VENDOR backlog (`ROADMAP.md` `WPT-VENDOR-mediacapture-image`, `docs/wpt-status.md`), included despite its 🚫 scope note (media capture — no pipeline) by the same standing user decision as `mediacapture-handle`/`mediacapture-fromelement`/`mediacapture-extensions`/`media-source`. Same pinned commit, `git sparse-checkout add` at the same commit hash, 24 files (`META.yml`, `LICENSE-WPT.md` copied from the sibling `mediacapture-handle` category, 21 root test files including `idlharness.https.window.js`, `resources/imagecapture-helpers.js`). No `variant` hits; sole out-of-category dep is `../mediacapture-streams/permission-helper.js` (unvendored); 20 of 24 files are `.https.`; 8 files reference `testdriver.js`. `run_report.py --all --root mediacapture-image --recursive` completed in ~5:27 (24 selected ids, 1 — `ImageCapture-grabFrame-crash.https.html` — never runs, `crashtest` is an unsupported test type for product `lumen`, 23 actually executed): **3/23 harness OK, 0/6 subtests passed**. Dominant signal matches `mediacapture-fromelement`: every `MediaStreamTrack-*` test fails with `canvas.captureStream is not a function` — `HTMLCanvasElement.captureStream()` remains entirely absent. The remaining 15 `.https.` tests TIMEOUT on the standard TLS `UnknownIssuer` gap (same class as `mediacapture-handle`/`keyboard-lock`/`magnetometer`). 4 `.https.` tests errored instantly instead of timing out: `AssertionError: Got results from <previous test>, expected <this test>` — a reproduction of the already-filed BUG-380 (the executor doesn't check `browsingContext.navigate`'s outcome after a failed TLS navigation and reuses the browsing context, so the next poll returns the previous test's stale results). No bug filed — reconfirmation of the absent API (`mediacapture-fromelement`) and the already-known BUG-380. See `docs/wpt-status.md` for the full breakdown.
