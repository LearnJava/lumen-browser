# Политики как проверки: перевод правил CLAUDE.md в машинные линты

План перевода проектных правил из прозы в проверки, которые роняют сборку. Составлен 2026-08-17 по итогам разбора «нужен ли отдельный язык/форк компилятора для работы с ИИ» — вывод разбора в §8.

Статусы: ⬜ не внедрено · 🧪 внедрить и замерить · ✅ внедрено · 🚫 отвергнуто.

---

## 1. Задача

Значительная часть правил проекта записана в [CLAUDE.md](../CLAUDE.md) и [REVIEW.md](../REVIEW.md) текстом: «no `panic!`/`unwrap()` в проде», «каждый `unsafe` требует `// SAFETY:`», «`///` на всех публичных элементах — обязательно». Проверяет их только ревью — то есть человек или ассистент, по памяти, глазами. Это худший вид требования: невидимое в сигнатуре, не воспроизводимое и нарушаемое молча.

Цель — перевести каждое такое правило в одну из трёх форм, по убыванию предпочтения:

1. **готовое правило clippy**, включённое в конфиге (кода писать не надо);
2. **своё правило** через `dylint` — отдельный проход, не участвующий в сборке;
3. **скрипт проверки** там, где линт неуместен (например, содержимое `Cargo.toml`).

Правило, которое не удалось перевести ни в одну из форм, остаётся прозой — но это должно быть осознанным исключением, а не умолчанием.

## 2. Текущее состояние (замер 2026-08-17)

| Что | Значение |
|---|---|
| `[workspace.lints]` в корневом `Cargo.toml` | отсутствует |
| `clippy.toml` | отсутствует |
| `#![deny(...)]` во всём workspace | один: `clippy::rc_buffer` в `crates/engine/dom/src/lib.rs:11` |
| Гейт | `cargo clippy -p <crate> --all-targets -- -D warnings` |

**Главное следствие:** гейт `-D warnings` поднимает до ошибки только те правила, что включены **по умолчанию**. Правила, закрывающие три политики выше, по умолчанию выключены (группы `restriction` и `pedantic`, а `missing_docs` — allow-by-default в rustc). То есть сборка зелёная, а политики не проверяются вообще.

Черновая перепись (`grep` по `crates`, исключены только каталоги `tests/`; внутрифайловые `mod tests` **включены**, поэтому числа завышены и годятся лишь для порядка величины):

| Узор | Вхождений |
|---|---|
| `.unwrap()` | ~9 600 в 400 файлах |
| `.expect(` | ~1 900 |
| `panic!(` | ~650 |
| `unsafe {` | 63 |
| `// SAFETY:` | 68 |

Из этого сразу видно две вещи. `unsafe` уже почти в порядке — комментариев больше, чем блоков, значит `undocumented_unsafe_blocks` включается дёшево и должен идти первым. А `unwrap` включить разом невозможно: даже с поправкой на тесты остаток будет большим, и это работа не на один заход.

Точные числа снимать не грепом, а самим clippy — см. протокол в §6.

## 3. Ярус 0 — готовые правила clippy (кода писать не надо)

Механика: секция `[workspace.lints]` в корневом `Cargo.toml` (стабильно с Rust 1.74) плюс строка `lints.workspace = true` в каждом крейте-члене.

```toml
# Cargo.toml (корень)
[workspace.lints.clippy]
unwrap_used                = "warn"
expect_used                = "warn"
panic                      = "warn"
undocumented_unsafe_blocks = "warn"

[workspace.lints.rust]
missing_docs = "warn"
```

```toml
# crates/<любой>/Cargo.toml
[lints]
workspace = true
```

Соответствие политикам:

| Политика (источник) | Правило | Оценка стоимости внедрения |
|---|---|---|
| «каждый `unsafe` требует `// SAFETY:`» (CLAUDE.md §Code conventions) | `clippy::undocumented_unsafe_blocks` | низкая — 63 блока, комментарии в основном есть |
| «`///` на всех публичных структурах, полях и функциях» | `missing_docs` (rustc) | средняя — включать по одному крейту |
| «no `panic!` в проде» | `clippy::panic` | средняя |
| «no `unwrap()` в проде» | `clippy::unwrap_used` | **высокая** — самая массовая правка |
| «no `expect()` в проде» (следует из той же строки) | `clippy::expect_used` | высокая |
| молчаливое проглатывание ошибок | `clippy::let_underscore_must_use`, `clippy::let_underscore_untyped` | не замерено |

Порядок внедрения — строго по возрастанию стоимости: `undocumented_unsafe_blocks` → `missing_docs` (по крейтам) → `panic` → `expect_used` → `unwrap_used`.

## 4. Ярус 1 — `clippy.toml`: настройка и свой чёрный список

Файл `clippy.toml` в корне репозитория. Две функции.

**Первая — исключения, без которых правила яруса 0 неприменимы.** Политика проекта разрешает `unwrap()` в тестах; clippy умеет это ровно так:

```toml
allow-unwrap-in-tests = true
allow-expect-in-tests = true
allow-panic-in-tests  = true
```

Исключение распространяется на `#[cfg(test)]`, то есть покрывает и внутрифайловые `mod tests`, и `tests/`.

**Вторая — собственные запреты без единой строки кода:**

```toml
disallowed-methods = [
  # { path = "std::env::set_var", reason = "гонки в многопоточном шелле" },
]
disallowed-types = [
  # { path = "std::sync::Mutex", reason = "в горячем пути paint использовать <...>" },
]
```

Это уже «свой линт»: перечисляете запрещённый вызов или тип и текст, который увидит нарушитель. Кандидатов надо набирать из реальных разборов багов, а не выдумывать заранее.

## 5. Ярус 2 — `dylint`: свои правила

`dylint` — механизм запуска собственных линтов: правило пишется как небольшая библиотека и вызывается отдельной командой (`cargo dylint --all`). **В сборку проекта не входит** — это второй проход, как clippy. Ломается или отстаёт от компилятора — сборка не страдает.

Сюда идёт то, чего в готовых наборах быть не может, потому что это про наш движок. Кандидаты (не проверены на реализуемость, список для обсуждения):

- вызов layout из фазы paint;
- изменение display list после сборки;
- аллокации в горячем пути растеризации;
- `#[touches(self.field, ...)]` — аннотация «функция трогает только эти поля», проверяемая по MIR. Языковой мощи не даёт (borrowck по-прежнему считает занятым весь `self`), но даёт заявленное намерение, проверенное машиной, и локальность в сигнатуре. Дешёвый заменитель отсутствующих в Rust view types.

Цена: около недели на обвязку (крейт линтов, пиннутый nightly **только для драйвера линтов**, вызов в CI) и 1–3 дня на правило. Заходить сюда стоит только после того, как ярус 0 внедрён и оказался недостаточным.

## 6. Протокол внедрения (одно правило — один заход)

Ровно как в [build-speed.md](build-speed.md) §2: не «на глаз», а числом.

```bash
export PATH="/c/Users/konstantin/.cargo/bin:$PATH"

# 1. Сколько срабатываний даст правило ДО включения
cargo clippy -p <crate> --all-targets --message-format=short -- -W clippy::<lint> 2>&1 \
  | grep -c "clippy::<lint>"

# 2. Включить как "warn" в [workspace.lints], разгрести, снова посчитать (должно быть 0)
# 3. Перевести в "deny" тем же коммитом, что и последняя правка
```

Правила:
- одно правило за коммит; смешивать включение двух — терять возможность откатить одно;
- `warn` → правки → `deny`; не включать `deny` до нуля срабатываний;
- крейты, где остаток велик, гасить локальным `#![allow(...)]` **с комментарием и ссылкой на задачу**, а не откатывать правило целиком;
- результат заносить в журнал §9.

## 7. Что линтом делать не надо

**Границы крейтов** («layout не тянет wgpu», «paint не тянет сеть») уже гарантирует Cargo: чего нет в `[dependencies]` крейта, того нельзя использовать физически. Проверять надо не код, а сами `Cargo.toml` — скриптом в CI, а не линтом. Ставить сюда `dylint` — это платить неделю за то, что уже работает.

**Правила про документацию и процесс** («обновить `CAPABILITIES.md` в том же коммите», «STATUS-PN.md — только строки-указатели») линтом не выражаются: они про содержание, а не про форму. Их место — [REVIEW.md](../REVIEW.md).

## 8. Почему не форк компилятора (разбор 2026-08-17)

Исходный вопрос был шире: не сделать ли форк rustc и не пилить ли в нём то, что нужно именно для работы с ИИ. Отвергнуто:

- **Цена.** rustc — порядка 1.5–2 млн строк; полная bootstrap-сборка идёт часами на каждой машине и в CI. Релиз апстрима каждые 6 недель, перебазирование — от часов (диагностика) до дней (typeck/borrowck). Фича уровня системы типов — работа на месяцы-годы: view types не приняты в апстриме годами именно поэтому.
- **Экосистема.** Наши зависимости (сотни крейтов, включая wgpu и rusty_v8) собираются стандартным компилятором. Новый синтаксис доступен только в нашем коде, rust-analyzer его не понимает, публикация отпадает.
- **Контрпродуктивность для самой цели.** Расширение, полезное ассистенту, должно быть в форме **атрибута или линта, а не грамматики**: атрибуты уже внутри корпуса, на котором обучена модель, и обобщаются с первого взгляда; новое ключевое слово — вне корпуса, и модель систематически про него забывает, скатываясь в обычный Rust. Форк «под ИИ», добавляющий синтаксис, делает ИИ хуже.

**Отложено, не отвергнуто** (ярус 3 в [build-speed.md](build-speed.md) §5, разобрано там же):

- `-Zthreads` (параллельный фронтенд) — плохо сочетается с sccache, а sccache у нас несущий;
- Cranelift для dev — на Windows только `panic = "abort"`, а `catch_unwind` используется в обвязке V8 (`crates/js/src/v8_compat.rs`) и обработчике крашей (`crates/core/src/crash.rs`).

Оба требуют перевода проекта на nightly ради выигрыша, который на нашей базе (инкремент S1 = 4.2 с) невелик. Настоящая цена сейчас — чистые сборки и V8, а их эти меры не трогают.
