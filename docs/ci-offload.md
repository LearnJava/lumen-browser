# Перенос гейта в CI (GitHub Actions)

План выноса части сборочно-тестового гейта с рабочей машины на GitHub Actions: что уезжает, что остаётся, как настроить и как ассистент забирает результат. Составлен 2026-08-18 после проверки лимитов трёх бесплатных CI (GitHub / GitLab / Bitbucket) и аудита существующих workflow.

**Статус: план, ничего из §4–§8 ещё не внедрено.** Оценки времени прогонов помечены как оценки — реальных прогонов в этом репозитории не наблюдалось (`gh` на машине не установлен, историю Actions прочитать нечем). Первый же прогон после §11.1 заменяет оценки замерами в журнале §12.

Смежные документы: [build-speed.md](build-speed.md) (локальная сборка и её замеры), [graphic-tests.md](graphic-tests.md) (почему пиксельный гейт локальный), [perf-method.md](perf-method.md) (почему перф нельзя гейтить по wall-clock), [git-workflow.md](git-workflow.md) (7-шаговый чеклист, который §8 меняет).

---

## 1. Исходная посылка

Репозиторий `LearnJava/lumen-browser` **публичный**, поэтому стандартные раннеры GitHub Actions бесплатны и без лимита минут на всех трёх ОС. Минуты перестают быть ограничением, и вопрос сводится к тому, что физически имеет смысл выполнять на чужой машине.

Ключевое разделение, из которого растёт весь документ:

- **Цикл разработки** (правка → `cargo check -p` = 4–6 с, `dev-release` инкремент = 3.8 с) в CI не переносится ни при каких условиях: раунд-трип до сервера на три порядка дороже. Локальный `target/` и процессорное время на `check` остаются.
- **Гейт задачи** (`clippy --workspace`, тесты крейтов, кросс-платформенная сборка) — один прогон на задачу, десятки минут CPU. Вот он и уезжает.
- **Прогон браузера** (живое окно, MCP-пробы, перф, graphic tests) привязан к локальному GPU, фокусу окна и сравнению с Edge — не уезжает.

Ожидаемый выигрыш формулируется честно: «минус один долгий гейт на задачу», а не разгрузка машины вообще. Дисковые 38 ГиБ корневого `target/` и слоты пула CI не освобождает.

## 2. Лимиты, которые продолжают действовать (проверено 2026-08-18)

| Лимит | Значение | Влияние на нас |
|---|---|---|
| Минуты, публичный репо, стандартные раннеры | безлимитно, $0 | нет |
| Larger runners | тарифицируются всегда, даже для публичных | **не использовать** |
| Кэш | 10 ГБ на репозиторий, вытеснение после 7 дней без обращения | **главный ограничитель, см. §5** |
| Скоуп кэша | прогон читает кэш своей ветки и базовой/дефолтной; соседние ветки — нет | §5: единый кэш на `main` |
| Время джоба | 6 ч (self-hosted — 5 дней) | влезаем с запасом |
| Время всего workflow | 35 дней | нет |
| Конкурентные джобы (Free) | 20 | 5 ролей × 3 ОС = 15, впритык — см. §5 про `concurrency` |
| Артефакты (Free) | 500 МБ, ретенция по умолчанию 90 дней | `lumen.exe` = 77 МБ, см. §6 |
| `GITHUB_TOKEN` | 1000 запросов/час на репозиторий | комментарии в PR — не задевает |
| Размер файла | предупреждение 50 MiB, жёсткий блок 100 MiB | проверять при вендоринге корпусов |
| Размер репозитория | рекомендация <1 ГБ, «настоятельно» <5 ГБ | `.git` = 495 МБ, 108 534 файла — см. §5 про checkout |

GitLab Free (400 мин/мес на namespace, обязательная верификация картой для shared runners, не более трёх top-level групп для аккаунтов после 27.01.2026) и Bitbucket Free (50 мин на весь workspace) при публичном репозитории на GitHub не дают ничего — рассматривались и отклонены.

### 3.1. Почему CI был мёртв два месяца (найдено и починено 2026-08-18)

Аудит выше писался по содержимому workflow, без чтения истории прогонов, и поэтому описывал
`ci.yml` как работающий с дефектом кэша. На деле он не проходил **ни разу с 2026-06-17**: 1187
прогонов на `main`, из 800 просмотренных подряд успешных ноль. Причин было две, вложенные.

**Первая — sccache.** Закоммиченный `.cargo/config.toml` задаёт `build.rustc-wrapper = "sccache"`
(влит `2ffbee511`). На раннерах sccache нет, поэтому любая команда cargo умирала за две секунды,
до компиляции: `error: could not execute process 'sccache …/rustc -vV' (never executed)`.
Починка — `RUSTC_WRAPPER: ""` в `env:` у `ci.yml`/`release.yml`/`bench-gate.yml`.

**Вторая — ALSA, только Linux.** Сразу после снятия первой windows и macos стали зелёными, а
ubuntu упал на `failed to run custom build command for alsa-sys v0.3.1`: `crates/shell` тянет
`cpal`/`rodio`, на Linux они мапятся на ALSA, а шаг установки зависимостей ставил только
X11/Wayland/EGL. Добавлен `libasound2-dev` в `ci.yml` и `release.yml`.

Два вывода для этого документа:

- **`gh` не нужен для диагностики.** Репозиторий публичный, поэтому статусы прогонов, джобы, шаги
  и тайминги читаются анонимным `curl` к `api.github.com`; авторизация нужна **только** для
  логов (`/logs` → 403 «Must have admin rights»). Предусловие §11.1 снимается для всего, кроме
  чтения логов. Анонимный лимит — 60 запросов/час, на постраничном обходе ловится как `curl: (56)`.
- **Аудит workflow по их тексту недостаточен.** Оба дефекта не видны в YAML: первый живёт в
  `.cargo/config.toml`, второй — в списке apt-пакетов против дерева зависимостей. Проверять
  состояние CI надо по истории прогонов, а не по конфигу.

## 4. Целевая раскладка джобов

Оценки — для холодного кэша, до первых реальных замеров.

| Джоб | ОС | Триггер | Оценка | Блокирует мерж |
|---|---|---|---|---|
| `lint` — `clippy --workspace --all-targets -- -D warnings` | ubuntu | PR, push main | 30–45 мин | да |
| `test` — тесты 16 крейтов (как сейчас в `ci.yml`) | ubuntu | PR, push main | 25–40 мин | да |
| `snapshot-cpu` — `cargo test -p lumen-driver --features cpu-render` | ubuntu | PR, push main | 30–45 мин | да |
| `cross` — `cargo check -p lumen-shell` | macos, windows | push main, nightly | 25–45 мин | нет |
| `doc-drift` — `wpt_expectations --check`, `gen_roadmap.py`, `gen_symbols.py`, `cargo hakari verify`, `cargo machete` | ubuntu | PR, push main | 2–5 мин | да |
| `red-lines` — как есть | ubuntu | PR, push main | <1 мин | да |
| `release` — как есть | 4 таргета | тег | 40–60 мин | — |

Обоснование трёх неочевидных пунктов:

**`snapshot-cpu` — главное приобретение.** [snapshot_cpu.rs](../crates/driver/tests/cases/snapshot_cpu.rs) явно спроектирован кросс-платформенным: растеризация идёт через tiny-skia (чистый Rust, программный растр), шрифт бандленный (Inter Regular через `lumen_font::Rasterizer`), подгрузки сабресурсов в headless-пути нет. Комментарий в шапке файла прямо утверждает идентичность вывода на Windows/macOS/Linux. 81 эталонный PNG в `graphic_tests/snapshots/cpu/`. Это единственная часть пиксельного гейта, не требующая GPU и фокуса окна, и именно её протухание рецидивирует (BUG-118 / 149 / 297 / 316) — сейчас его ловит посторонний человек своим красным гейтом, а не автор правки. **Перед внедрением проверить утверждение о кросс-платформенности эмпирически**: первый прогон на ubuntu против закоммиченных эталонов, снятых на Windows; расхождение хотя бы в одном пикселе означает, что джоб надо ставить на `windows-latest` (тоже бесплатно, просто медленнее по очереди).

**`lint` дублирует локальный `clippy --workspace`.** Это самый дорогой шаг `/lumen-task-finish` (компилирует весь workspace, 32 члена). При бесплатных минутах его дублирование в CI бесплатно, а локально он после этого становится необязательным (§8).

**`cross` вынесен с PR на push/nightly.** Кросс-платформенная поломка ловится сейчас только редким `release.yml`, но чинить её в момент мержа некому и незачем — это не блокер задачи. Плюс это снимает 10 из 15 конкурентных джобов при пяти параллельных ролях.

## 5. Кэш, checkout и конкурентность

Три настройки, без которых прогоны будут стабильно холодными и по 45 минут.

**Кэш `target` кэшировать целиком нельзя.** Локальный корневой `target/` = 38 ГиБ при бюджете 10 ГБ на весь репозиторий, а текущий `ci.yml` заводит по отдельному ключу на каждую из трёх ОС. Итог — постоянное взаимное вытеснение и нулевой hit rate. Правильная схема:

- кэшировать не `target` целиком, а только артефакты зависимостей — этим занимается `Swatinem/rust-cache` (вычищает артефакты крейтов workspace, оставляет внешние). Стороннее действие, поэтому пинить по SHA, а не по тегу;
- дополнительно кэшировать `~/.cargo/registry`, `~/.cargo/git` и `$CARGO_HOME/.rusty_v8/` — последнее убирает повторную загрузку ~220 МБ статической библиотеки V8 (механизм описан в [build-speed.md §3.7](build-speed.md));
- писать кэш **только на `main`**, а в PR-прогонах восстанавливать из базовой ветки (правило скоупа это разрешает). Иначе пять ролевых веток разделят 10 ГБ на пять бесполезных долей;
- `sccache` в CI не заводить: он решает ту же задачу, что и кэш зависимостей, но требует внешнего хранилища и на холодной машине выигрыша не даёт.

Даже при идеальном кэше первая сборка после смены `Cargo.lock` останется холодной. Это приемлемо: при бесплатных минутах холодная сборка — только задержка, не стоимость.

**Checkout.** 108 534 файла в индексе, из них 105 702 — вендоренный WPT под `tests/`, `.git` = 495 МБ. Джобам сборки WPT не нужен, поэтому:

```yaml
- uses: actions/checkout@v4
  with:
    fetch-depth: 1
    sparse-checkout: |
      /*
      !/tests/wpt
    sparse-checkout-cone-mode: false
```

Джобу `doc-drift` (он проверяет `wpt_expectations`) — обычный полный checkout.

**Конкурентность.** Лимит 20 джобов на Free, а суперсёданные прогоны при активном push-цикле съедают очередь. В каждый workflow:

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

## 6. Артефакт: как забрать экзешник

`target/dev-release/lumen.exe` = **77 МБ**, в zip-артефакте примерно вдвое меньше; лимит артефактов Free-плана 500 МБ, ретенция по умолчанию 90 дней. Влезает.

Но применение у этого узкое, и это надо держать в голове: **скачивание артефакта не заменяет локальную сборку**. Инкрементальная пересборка shell в `dev-release` после правки — 3.8 с, каскад layout→shell — 8.6 с ([build-speed.md §7](build-speed.md)); CI-прогон это 25–45 мин плюс выгрузка и загрузка 77 МБ. Артефакт оправдан ровно в трёх случаях:

1. бинарь под Linux/macOS — локально не собрать вообще;
2. проверка «собирается на чистой машине» перед релизом;
3. если рабочая машина занята длинным прогоном и нужен бинарь параллельно.

Для повседневной итерации — собирать локально.

Джоб выгрузки (только на `push` в main, чтобы не плодить артефакты на каждый PR):

```yaml
- name: Build dev-release shell
  run: cargo build -p lumen-shell --profile dev-release
- uses: actions/upload-artifact@v4
  with:
    name: lumen-${{ runner.os }}-dev-release
    path: target/dev-release/lumen*
    retention-days: 14
```

## 7. Как ассистент пользуется результатами

**Предусловие, требует действия пользователя:** на машине нет `gh` (`bash: gh: command not found`). Без него ассистент не может ни прочитать статус прогона, ни забрать логи, ни скачать артефакт — установка лежит вне рабочего каталога, поэтому её выполняет пользователь:

```bash
winget install --id GitHub.cli
```

После установки — однократная авторизация `gh auth login` (тоже пользователем, ассистент не вводит учётные данные).

Дальше протокол ассистента. Все команды read-only, кроме явно оговорённых.

```bash
# статус последних прогонов
gh run list -L 10

# прогоны конкретной ветки
gh run list --branch p3-bug-405 -L 5

# что именно упало: логи только упавших шагов
gh run view <run-id> --log-failed

# дождаться завершения (для скрипта/фонового ожидания)
gh run watch <run-id>

# забрать артефакт
gh run download <run-id> -n lumen-Linux-dev-release -D .tmp/artifacts/
```

Правила потребления результата:

- **Один прогон — один лог-файл**, как и для локального cargo: `gh run view <id> --log-failed > .tmp/ci-<id>.log 2>&1`, дальше грепать файл. Не дёргать `gh` повторно ради другого фильтра.
- **Ожидание прогона — фоновая задача** (`run_in_background: true`), не `sleep` в цикле. 30–45 минут блокирующего ожидания — то же самое выгорание времени, что описано в CLAUDE.md про 76 минут из 188.
- **Красный CI не диагностировать по названию джоба.** Сначала `--log-failed`, потом вывод. Отдельно держать в голове, что `snapshot-cpu` краснеет от протухших эталонов чаще, чем от реальной регрессии.
- **`gh run rerun` — только по просьбе пользователя.** Это не read-only и не бесплатно по времени очереди.
- **Push ветки для запуска CI требует явной просьбы пользователя** — правило CLAUDE.md «`git push` без явного запроса запрещён» никак не отменяется появлением CI.

## 8. Что меняется в протоколе задачи

Сейчас гейт локальный и синхронный: `/lumen-task-finish` прогоняет `clippy --workspace` + `scoped-test.sh`, затем сразу `merge --no-ff` и push. С переносом гейта в CI появляется разрыв в 30–45 минут между «код готов» и «можно мержить».

Предлагаемая раскладка (внедрять только после §11.3, когда CI подтверждён зелёным на нескольких задачах):

| Шаг | Было | Стало |
|---|---|---|
| Перед коммитом | `clippy -p <crate> -- -D warnings` + `cargo test -p <crate>` | без изменений (быстрый локальный отсев) |
| Гейт | `clippy --workspace` + `scoped-test.sh` локально, 10–40 мин | push ветки → джобы `lint`/`test`/`snapshot-cpu`/`doc-drift` |
| Пиксельный гейт | `graphic_tests/run.py` при правках, двигающих пиксели | без изменений, локально (§9) |
| Мерж | сразу после локального гейта | после зелёного CI на ветке |

**Решено 2026-08-18: вариант 1** — ветка `p<N>-…` пушится в `origin`, ждём зелёного CI, мержим
локально. Реализовано: `ci.yml` и `red-lines.yml` триггерятся на push веток `p[1-5]-*` (без этого
push ветки не запускал ничего — триггер был только на `main`), в оба добавлен `concurrency` с
отменой предыдущего прогона на неглавных ветках. Протокол — `CLAUDE.md` §Git workflow, шаг 1б;
удаление удалённой ветки — шаг 7. Полноценные PR с merge queue (вариант 2) не берём, пока
`bench-gate.yml` не переведён на счётчики: его комментарии в PR сейчас ничего не значат (§11.5).

**Локальный гейт при этом не снимается.** Таблица выше писалась в расчёте на джобы `lint` и
`snapshot-cpu` из §4, которых ещё нет: сегодня CI гоняет `cargo check -p lumen-shell` и юнит-тесты
16 крейтов, то есть **слабее** локального гейта — не проверяет ни `clippy --workspace`, ни
снапшоты, ни scoped-тесты. Поэтому шаг 1б добавлен *поверх* `/lumen-task-finish`, а не вместо
него: CI ловит Linux и macOS, локальный гейт — всё остальное. Снимать локальный гейт можно будет
только после §11.3.

| Шаг | Было | Стало |
|---|---|---|
| Перед коммитом | `clippy -p <crate>` + `cargo test -p <crate>` | без изменений |
| Гейт | `clippy --workspace` + `scoped-test.sh` локально | без изменений (CI пока слабее) |
| Пиксельный гейт | `graphic_tests/run.py` при правках, двигающих пиксели | без изменений, локально (§9) |
| Перед мержем | — | push ветки → зелёный CI (Linux/macOS/Windows) |
| Мерж | сразу после локального гейта | после зелёного CI |
| После мержа | — | `git push origin --delete p<N>-…` |

## 9. Что не переносить

| Что | Почему |
|---|---|
| `graphic_tests/run.py` (~20 мин, 70+ страниц) | `gdigrab` снимает весь рабочий стол и требует фокуса окна; сравнение с Edge; порог 0.5 %. На shared runner нет GPU — wgpu уедет на программный бэкенд. Подробности — [graphic-tests.md](graphic-tests.md) |
| Любой перф-замер по wall-clock, включая нынешний `bench-gate.yml` | Шумные соседи на shared runner. Бэкенд решает всё: 116 мс DX12 против 53 мс Vulkan на одной машине (BUG-405, срез 14). Гейтить можно только счётчиком или идентичностью — [perf-method.md](perf-method.md) |
| Цикл правка→`check` | 4–6 с локально против минут раунд-трипа |

| Всё, что требует larger runners | Тарифицируется даже для публичных репозиториев (§2) |

## 10. Self-hosted runner (этап 2, опционально)

Если цель — именно разгрузить рабочую машину, а не автоматизировать проверки, то потолок GitHub-hosted раннеров здесь исчерпан: с них нельзя снять GPU-зависимую часть, а она и есть самая долгая (graphic tests ~20 мин, перф-прогоны).

Self-hosted runner на **втором** железе снимает и это: минуты не тарифицируются на любом плане, лимит джоба 5 дней вместо 6 часов, доступен реальный GPU и рабочий стол. Условия применимости:

- нужна вторая машина с Windows, дискретным или интегрированным GPU и залогиненной десктоп-сессией (иначе `gdigrab` бесполезен);
- на ней действует та же готча: любая смена фокуса рабочего стола во время прогона молча портит все скриншоты — значит машина должна быть выделенной, не рабочей;
- **на публичном репозитории self-hosted runner небезопасен по умолчанию**: PR от постороннего исполнит произвольный код на вашей машине. Обязательно ограничить триггеры (`push` в main и `workflow_dispatch`, без `pull_request` от форков) либо требовать ручного одобрения запусков.

Установка runner на ту же машину, где идёт разработка, смысла не имеет — ресурсы не освобождаются, добавляется только автоматизация запуска.

**Результат разведки** (прогон `32183754261`, ветка `p5-ci-jobs`, 2026-08-18). Блокирующие джобы зелёные, оба разведчика красные — ровно то, ради чего они и заводились:

| Джоб | Находка |
|---|---|
| `lint` / macos | `crates/core/src/memory_pressure.rs:209` — `unsafe` без `// SAFETY:`. Ровно предсказанная дыра: блок под macOS-`cfg`, clippy его никогда не видел, в реестре §10 `docs/lint-policy.md` его нет |
| `lint` / ubuntu | `crates/engine/layout/src/style.rs:22032` — `clippy::question_mark`. **Платформа ни при чём:** раннер берёт `dtolnay/rust-toolchain@stable` = 1.97.0, а на машине разработчика 1.96.1, и в 1.97 этот линт стал срабатывать шире. То есть CI и локальный гейт гоняют РАЗНЫЙ clippy |

Итого 2 из 3 — это не платформенная разница, а **недетерминизм самого теста**, при том что вся его посылка в детерминированности (tiny-skia, бандленный шрифт, без сети). Лечится `git diff -I'"generated":'` |

Три следствия, каждое требует решения перед снятием флагов:

1. **Расхождение тулчейнов надо закрыть явно** — либо пин `dtolnay/rust-toolchain@1.96.1` в CI (тогда CI перестаёт ловить новые линты, но гейты совпадают), либо `rustup update` на машине и правка «Rust 1.95+» в CLAUDE.md. Пока расхождение живо, «зелёный локально» и «зелёный в CI» — разные утверждения. Решение за пользователем.
2. **Список нарушений `lint` заведомо неполон.** `-D warnings` роняет сборку крейта на первой ошибке, поэтому виден один дефект на ОС, а не все: после правки `memory_pressure.rs` и `style.rs` прогон покажет следующий слой. Приём 2 — это цикл «починил → перегнал», а не один коммит.
3. **`49-background-blend-mode` плавает** — красный и зелёный на одном и том же коде и одной и той же ОС, с разницей в один прогон. Это не «протухший эталон» и не платформенная разница: регенерация ничего не чинит, а джоб, включённый блокирующим прямо сейчас, будет ронять чужие ветки случайным образом (и, что хуже, приучит их перезапускать). Заведён [BUG-784](../bugs/BUG-784-OPEN.md). Пока баг открыт, `snapshot-cpu` остаётся разведкой — это единственная причина, по которой он ещё не блокирующий: с эталонами всё в порядке, 80 из 81 совпали побайтно в обоих прогонах.

Отдельный вывод про сам метод: **два прогона одного коммита стоили дешевле, чем разбор одного.** Первый прогон выглядел как «нашли платформенную разницу растеризации» и уехал бы в задачу P3 на полдня; второй показал, что находка другого класса. Для любого нового CI-джоба, чей предмет — детерминизм, первый красный результат нельзя брать за факт до повторного прогона.
