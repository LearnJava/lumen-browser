# WPT pass-rate: методика и журнал прогонов

Задача `WPT-RUN-4` (`ROADMAP.md`, бриф — [`p2-wpt-runner-throughput.md`](../tasks/p2-wpt-runner-throughput.md)).

Этот файл отвечает на один вопрос: **какую долю Web Platform Tests проходит
Lumen** — и, что важнее, что именно этой цифрой измерено, а что нет. Числа
конкретных прогонов лежат рядом в `docs/wpt/runs/<дата>.json`, здесь — методика
и журнал.

---

## Знаменатель

**Все автоматизируемые тестовые id вендоренного `MANIFEST.json`, без изъятий.**

Почему манифест, а не файлы на диске: до `WPT-RUN-4` любой счёт корпуса в этом
репозитории брался из `run_report.py::all_vendored_test_ids()`, который просто
глобит `*.html`. Такое число несопоставимо ни с wpt.fyi, ни с дашбордами Servo
и Ladybird, причём ошибается в обе стороны сразу:

- **завышает** — `foo-ref.html` это файл, но не исполняемый тест: reftest-эталон
  считается вместе с самим тестом;
- **занижает** — один файл может давать несколько id: `?variant`-варианты и
  развёртка `.any.js` → `.any.html` / `.any.worker.html` / `.any.sharedworker.html`.

`MANIFEST.json` — это то, из чего `wptrunner` реально отбирает тесты, поэтому он
и есть единственный защитимый знаменатель. Считает его
[`tests/wpt/corpus_stats.py`](../../tests/wpt/corpus_stats.py).

### Что входит и что нет

| Тип манифеста | В знаменателе | Почему |
|---|---|---|
| `testharness` | да | исполняется сегодня |
| `reftest`, `print-reftest` | **да** | исполнителя нет (`TEST-4`) — но неисполненное считается непройденным |
| `crashtest`, `wdspec`, `aamtest` | **да** | то же самое |
| категории со скоупом 🚫 в `docs/wpt-status.md` | **да** | решение пользователя 2026-08-18: границу скоупа цифра не защищает |
| `support` | нет | это фикстуры (картинки, хелперы), а не тесты |
| `manual`, `visual` | нет, считаются отдельно | их не исполняет ни один раннер, включая апстримный — включение исказило бы то, что измерено, в любую сторону |
| `testharness` с `jsshell: true` | **да**, печатается отдельной строкой | wpt.fyi считает их 0 у любого браузера — см. ниже |

### jsshell-варианты остаются в знаменателе (WPT-JSSHELL-DENOM, 2026-10-27)

`// META: global=jsshell` в `.any.js` даёт id вида `/wasm/jsapi/…/foo.any.js` с
`{"jsshell": true}` в манифесте (`tools/manifest/sourcefile.py`, суффикс
`.any.js`). В корпусе их **78, все в `wasm/jsapi/`** — 12.7 п.п. `wasm`
(78 / 612), 0.11 п.п. всего корпуса (78 / 68 118). Решение — **не исключать**,
потому что wpt.fyi их тоже считает:

1. **wptrunner не выбрасывает их, а пишет SKIP.** `tools/wptrunner/wptrunner/wptrunner.py:302`:
   `test.jsshell and not executor_cls.supports_jsshell` → `test_end(status="SKIP",
   message="Executor does not support jsshell")`. `supports_jsshell = False` в
   `executors/base.py:282`, и ни один браузерный executor его не переопределяет —
   SKIP получает и Chrome, и Firefox, и Safari. Форматтер
   `formatters/wptreport.py::test_end` кладёт в `wptreport.json` каждый
   `test_end`, SKIP тоже.
2. **results-processor wpt.fyi SKIP не отбрасывает.**
   `wpt.fyi/results-processor/wptreport.py::summarize` пишет каждый результат
   как `{'s': 'S', 'c': [0, 0]}` (`'SKIP'` → `'S'` в `STATUS_ABBREVIATIONS`);
   фильтра по статусу там нет.
3. **Фронтенд wpt.fyi считает такой id как 0 из 1.**
   `wpt.fyi/webapp/views/wpt-results.js`: в подтестовом виде (вид по умолчанию,
   `isDefaultView()`) `aggregateTotalsBySubtest` для `total === 0` делает
   `total++` и `passes++` только при статусе `P`; в потестовом виде
   `aggregateTotalsByTest` при `newAggProcess` даёт `[0, 1]` для статуса не из
   `PASSING_STATUSES = ['O', 'P']`. Строки по статусу не фильтруются.

Итог: у wpt.fyi эти 78 id — 0 у всех браузеров, в знаменателе. Наша формула
(«не исполнили — значит не прошли») совпадает, исключение сделало бы цифру
несопоставимой. Чтобы недостижимый срез был виден, `corpus_stats.py` печатает
строку `of them jsshell: 78` (ключ `jsshell_ids` в `--json`), а в снимке
прогона они остаются обычным SKIP со счётом 0. Пересматривать — только если
wpt.fyi начнёт фильтровать `'S'` (проверка — `grep -n "'S'\|SKIP"` в двух
файлах выше).

Принцип, из которого всё вышеперечисленное следует: **не исполнили — значит не
прошли**. Знаменатель не подгоняется под возможности раннера, иначе цифра растёт
от того, что мы сузили измерение, а не улучшили движок.

## Формула

Та же форма, что у wpt.fyi, чтобы число значило то же самое:

- тест **с сабтестами**: `score = passed_subtests / total_subtests`;
- тест **без сабтестов**: `score = 1`, если статус `PASS`, иначе `0`;
- id, которого нет в отчёте (нет исполнителя, шард упал/повис, раннер пропустил):
  `score = 0`;
- `pass-rate = Σ score / |знаменатель|`.

Harness-статус (`OK`/`ERROR`/`TIMEOUT`/`CRASH`) в саму цифру не входит — он
отчитывается отдельно, потому что `ERROR` при частично прошедших сабтестах и
`ERROR` без единого сабтеста дают разный вклад.

## Потолок сегодняшней цифры

Верхняя граница цифры не зависит от качества движка: id типа, для которого в
[`tools/wptrunner/wptrunner/browsers/lumen.py`](../../tools/wptrunner/wptrunner/browsers/lumen.py)
нет исполнителя, не может дать ничего кроме нуля. Исполнителя два —
`testharness` (WPT-RUN-2) и `reftest` (`TEST-4` + `TEST-5`, закрыты
2026-08-19):

```
автоматизируемых id:      67 735
  testharness             37 319
  reftest                 27 386
  ------------------------------
  исполнимо сегодня       64 705   → потолок 95.5 %

  crashtest                1 892   ┐
  wdspec                     626   │ нет исполнителя — WPT-RUN-8
  print-reftest              416   │ (по wdspec сначала решение о скоупе)
  aamtest                     96   ┘
```

Цифру печатает `corpus_stats.py` последней строкой; с 2026-08-20 список типов
он **вычитывает из `lumen.py`** (`ast`, не `import`), а не держит константой.
Причина правки — ровно этот раздел: `TEST-4` зарегистрировал `reftest`
2026-08-19, константа осталась `{"testharness"}`, и потолок печатался как
55.1 % ещё сутки после того, как перестал быть правдой.

**Что это значит для публикации.** Пара «цифра при потолке» обязана брать
потолок того снимка, о котором говорит:

| снимок | исполнители | потолок |
|---|---|---|
| `runs/2026-08-18.json` (5.59 %) | testharness | **55.1 %** |
| `runs/2026-08-20-*-partial.json` (WPT-RUN-5) | testharness + reftest | 95.5 %, но фактически **85.0 %** |

Фактические 85.0 % у WPT-RUN-5 — из-за [BUG-792](../../bugs/BUG-792-FIXED.md):
7 190 id манифеста (10.6 % автоматизируемых, из них 7 156 исполнимого типа)
несут в имени `.https.`, исполняются и дают гарантированный ноль, потому что
тело close-delimited https-ответа теряется. Это не потолок исполнителей, а
дефект сборки — снимается перепрогоном `WPT-RUN-9`, после которого пара
возвращается к 95.5 %.

#### Сколько BUG-792 стоит цифре: замер (срез 32), +0.16 п.п., не 10.6

Потолок 85.0 % и цена 10.6 п.п. — разные величины, и вторая измерена.
`WPT-RUN-9` вернёт пару к 95.5 %, но саму цифру поднимет не на 10.6 пункта:
id без документа стоит ровно того, что он **набрал бы** с документом, а этого
у 7 190 https-id никто не спрашивал — они ни разу не исполнялись с телом.

Срез 32 ([`tests/wpt/tls_eof_audit.py`](../../tests/wpt/tls_eof_audit.py))
спросил, A/B на одном бинаре, 120 случайных id (seed 792). Оба арма —
приватные TLS-серверы над `tests/wpt/`, отдающие одни и те же байты
close-delimited (без `Content-Length`, `Connection: close`); различие ровно
одно: арм A закрывает сокет без TLS-shutdown (так делает `wptserve`), арм B
шлёт `close_notify`. Всё содержание фикса — «считать `UnexpectedEof` на
EOF-фреймировании концом тела», поэтому байты арма B — это байты, которые
починенный движок получил бы в арме A. Различие армов не предполагается, а
проверяется перед стартом: маркерная страница отдаётся обоими армами через
`--dump-layout`, и прогон отказывается идти, если арм A её не потерял (иначе
нулевая дельта прочиталась бы как «BUG-792 бесплатен»).

| величина | значение |
|---|---|
| арм A без документа | **120 из 120** id |
| id, прибавивших балл | **9 из 120** |
| средняя дельта на id | **+0.0371** (bootstrap CI90 +0.0147…+0.0633) |
| проекция на 3 004 probeable https-id | **+111 баллов = +0.164 п.п.** (CI90 +0.065…+0.281) |
| сабтестов: арм A → арм B | **0 → 269** (на 56 id) |
| статусы арма B | 61 `TIMEOUT`, 31 `OK`, 18 `ERROR`, 10 в потолок аудита |

**Прячет баг вердикты, а не баллы** — тот же вывод, что у среза 31 про backlog
хелперов. 49 id из 120 оживают (арм A без документа, арм B с вердиктом), 31 из
них отдаёт `OK`; то есть 10.6 % знаменателя сегодня не проверяют движок вообще.
Но починка переводит их в честные `TIMEOUT`/`ERROR`/`FAIL`, а не в баллы:
https-корпус — это service workers, fenced frames, mixed-content, speculation
rules, WebRTC, платформенные API, которых у движка нет.

**Прогон при этом дешевеет**, в отличие от BUG-796 и WPT-RUN-11, которые оба
удорожают: с телом 49 id из 120 отвечают быстрее 2 с и 61 упирается в
собственный потолок `testharness.js` (10 с, срез 29), тогда как сегодня все 120
выжигают полный тестовый таймаут раннера.

Обе оговорки замера — в сторону занижения: 10 id упёрлись в 30-секундный
потолок аудита в обоих армах и засчитаны как «нет вердикта» (если бы каждый
набрал единицу, проекция выросла бы до ≈0.53 п.п.), а 4 186 из 7 190 https-id
(reftest, testdriver и `.any`/`.window`, чей html `wptserve` генерирует на
лету) приватным сервером не отдаются и не измерены — перенос той же ставки на
2 634 генерируемых testharness-id дал бы порядка +0.3 п.п. суммарно.

### Вторая инфраструктурная поправка: 2 550 id адресованы неразрешимому хосту

Найдено 2026-08-21 (`WPT-RUN-5` срез 20, инструмент
[`tests/wpt/host_audit.py`](../../tests/wpt/host_audit.py)). WPT — многооригинный
набор: часть тестов обращается к соседнему origin через поддомены основного
хоста и через отдельный домен `not-web-platform.test`. Апстрим эти имена
разрешаются записью в `/etc/hosts` (`wpt make-hosts-file`); наш раннер этот шаг
пропускает и фиксирует `browser_host` в литерал `127.0.0.1`, а `wptserve`
строит поддомены **префиксом**, то есть браузеру достаётся `www1.127.0.0.1`.
Из 66 публикуемых сервером имён на машине прогона разрешается **одно**.

Затронуто **2 550 автоматизируемых id (3.8 % корпуса)**; на живом прогоне они
дают 69.4 % TIMEOUT против 18.1 % у остальных и набирают 5.38 % против 18.12 %.
Это **верхняя** граница поправки, а не измеренный ущерб: помеченные id — ровно
кросс-origin-тесты, они и так тяжелее среднего, и внутри категории разрыв
неоднороден (`html` 80.1 % против 27.9 % у соседей, а `fetch` 68.1 против 66.9,
то есть там хост не добавляет ничего). Оговорка относится к **обеим половинам**
прогона одинаково: `env_options` у них общий. Чинится в `WPT-RUN-10`.

### Третья поправка: 6 825 id ждут файл, которого нет в чекауте

Найдено 2026-08-21 (`WPT-RUN-5` срез 30, `find_missing_resources.py --root "" --ids`).
Статический скан всех 83 844 файлов чекаута: **96 путей**, на которые тесты
ссылаются `src=`/`href=`/`url()` и которых на диске нет, а вместе они блокируют
**6 825 автоматизируемых id (10.1 % корпуса)**. Считать надо именно id, а не
файлы: один `encoding`-файл с 17 `<meta name="variant">` — это семнадцать
строк манифеста и один файл. Четыре пути держат 5 572 id:
`/common/security-features/resources/common.sub.js` (2 208),
`/common/subset-tests.js` (1 582), `/common/reftest-wait.js` (1 518),
`/common/blank.html` (264) — все из `common/`, где у нас лежит 7 записей
против сотни у апстрима. `/resources/testdriver.js` и
`/resources/testharnessreport.js` в счёт не идут: их отдаёт статический
маршрут `wptrunner`, на диске их нет законно (`ROUTED_NOT_VENDORED` в том же
скрипте; без этой поправки backlog завышался на 3 236 id).

Направление ошибки — **занижение**, и в отличие от двух поправок выше оно
чистое: такой тест не медленный, а мёртвый — гарнесс не получает свой
`subsetTestByKey`/`idl_test`, не заводит ни одного сабтеста и висит до любого
потолка. Ущерб не в баллах, а в том, что 10 % знаменателя не проверяют движок
вообще. Довендоривание — `WPT-RUN-11`.

#### Сколько это стоит цифре: замер (срез 31), +0.10 п.п., не 9.6

Слова «ущерб не в баллах» выше были догадкой; срез 31
(`tests/wpt/missing_helper_audit.py`) их измерил, и догадка подтвердилась
численно. Перепись сначала расширилась: если считать не только
site-absolute ссылки (что делает `find_missing_resources.py`, и правильно —
он отвечает на вопрос «чего нет в дереве»), а всё, чего ждёт **сам id**,
включая соседний `src="helper.js"`, то блокированы **8 858 автоматизируемых
id (13.1 %)** по 1 941 пути: `testharness` 6 347, `reftest` 2 295, `wdspec`
128, `crashtest` 72, `print-reftest` 16. Из них прогон исполнил 7 088, и
сегодня они держат **590.4 балла** (в среднем 0.083), то есть наивный потолок
починки — 6 498 баллов, **9.6 п.п.**

A/B на одном бинаре: арм A — страница как отдана (хелпер даёт 404), арм B —
та же страница с того же приватного статического сервера, но запрос, которого
нет в чекауте, проваливается в апстрим **на запиненном коммите вендоринга**
(`tests/wpt/VENDOR.md`), скачивается один раз и кешируется в `.tmp/`.
Провал рекурсивен по построению: хелпер, тянущий свои хелперы, получает их
так же, поэтому арм B — это «WPT-RUN-11 сделан», а не «довендорили ровно
четыре файла». В служебное дерево `tests/wpt/` при этом не пишется ничего:
корпусный прогон читает файлы с диска на каждый запрос, и вендоринг посреди
прогона выдал бы поздним шардам другой корпус, чем ранним.

Результат — **+0.10 п.п., а не 9.6**, и распределён он крайне неравномерно.
Случайная выборка 80 id (76 засчитано) даёт среднюю дельту +0.0347, но весь
её вес несут четыре id из `/editing/run/`. Пост-стратификация:

| страта | id в популяции | проба | средняя дельта | проекция |
|---|---|---|---|---|
| `/editing/run/` (ждут `/common/subset-tests.js`) | 110 | 18 | **+0.630** (CI90 +0.554…+0.693) | **+69 баллов = +0.102 п.п.** |
| все остальные probeable | 5 621 | 72 | **ровно 0** (72 нуля из 72) | 0; правило трёх ≤ 234 балла = ≤ 0.35 п.п. |

То есть измеренная цена всего backlog-а — **+0.10 п.п.**, верхняя граница
**≤ 0.45 п.п.** Публиковать цифру с оговоркой «занижена на 10 % корпуса»
нельзя: занижена она на десятую долю пункта.

**Что backlog прячет на самом деле — вердикты, а не баллы.** Сабтестов в
случайной выборке 124 в арме A против **5 904** в арме B, а в страте
`/editing/run/` — 0 против **12 317**: хелпер разблокирует тест, тест
заводит свои сабтесты и они **падают**. Это и есть содержательный ущерб:
3 122 блокированных id стоят сегодня TIMEOUT-ом, то есть 4.6 % знаменателя
не проверяют движок вообще, — но починка переводит их в честные FAIL, а не
в баллы.

**И времени прогона это не экономит, а стоит.** На одних и тех же 76 id арм B
занял 16.4 мин против 11.7 у арма A (**×1.40**), а TIMEOUT-ов стало 50 вместо
54: разблокированный тест не «быстро отвечает», он дольше работает и чаще
всё равно упирается в потолок. Значит `WPT-RUN-11` — не задача про цифру и не
задача про пропускную способность; её оправдание — качество вердиктов для
`WPT-RUN-6`/`WPT-RUN-7`.

### Почему BUG-796 (`timeout: long` = 10 с) цифру НЕ занижает

[BUG-796](../../bugs/BUG-796-FIXED.md) **починен 2026-08-24 (P1)**; до этого он резал 8 196 объявленных `timeout: long`
id по 10-секундному потолку вместо 60-секундного, и срез 29 записал это как
«часть TIMEOUT-ов ложные, цифра занижена». **Замер (срез 30,
`tests/wpt/long_timeout_audit.py`) этого не подтвердил.** A/B на одном бинаре
— страница как отдана против той же страницы с починенным `meta.content`,
`timeout_multiplier` в обоих армах 1 — на **88 id**: 48 случайных из всей
популяции срезанных внутренним потолком и 40 из страты «в исходнике нет
структурной причины висеть» (вторая выборка снимает возражение, что первая
меряет в основном невендоренные хелперы). Восстановились **два**
(`/fetch/range/non-matching-range-response.html`,
`/long-animation-frame/loaf-forced-layout-duration.html`), **оба на нулевой
балл**; сабтестов 475 против 475, PASS 15 против 15, и ни у одного из 88 id
их число между армами не изменилось. Верхняя граница по правилу трёх —
**≤ 105 id из 3 079, то есть ≤ 0.16 п.п.**, и это в предположении, что каждый
восстановленный взял бы полный балл.

Причина такой чистой нулевой дельты — предыдущий раздел: 2 167 из 2 504

## Как воспроизвести

```bash
export LUMEN_PROFILE=dev-release
BIN=$(cygpath -w "$PWD/target/dev-release/lumen.exe")
# знаменатель, без прогона
tests/wpt/.venv/Scripts/python.exe tests/wpt/corpus_stats.py
# пилот (10 разнородных категорий, отлаживает оркестратор, не движок)
tests/wpt/.venv/Scripts/python.exe tests/wpt/run_corpus.py --binary "$BIN" --pilot
# весь корпус, с чекпойнтами и возможностью продолжить (рецепт WPT-RUN-18)
tests/wpt/.venv/Scripts/python.exe tests/wpt/run_corpus.py --binary "$BIN" --all \
    --parallel-shards 3 --processes auto --shared-queue --batch-small 150 \
    --max-browser-gb 4 --run-json docs/wpt/runs/<дата>.json
```

Бюджет памяти этого рецепта и замер «до/после» —
§«Память полного прогона (WPT-RUN-18)» ниже.

Прогон переживает перезапуск: `--resume` пропускает шарды, уже давшие отчёт;
`--aggregate-only` пересчитывает цифру по готовым отчётам, ничего не запуская.

Перед публикацией цифры — обязательный разбор её нулевого ведра (срез 15):

```bash
tests/wpt/.venv/Scripts/python.exe tests/wpt/score_audit.py --out-dir .tmp/wpt-corpus
```

Он раскладывает все id без вердикта на «тип без исполнителя» / «шард убит по
бюджету» / **утечка** (id, потерянный внутри отработавшего шарда), считает,
сколько убитые шарды стоили цифре, и заодно печатает, какая доля настенного
времени ушла на таймауты. Строка `LEAK` в выводе — стоп-сигнал: цифру с ней
публиковать нельзя, пока причина не найдена. Читать только он — безопасно, в
том числе по каталогу живого прогона.

### Память полного прогона (WPT-RUN-18)

WPT-RUN-16 шёл 6.5 ч вместо 2 ч 44 мин: 3 полосы × 14 браузеров на 32 ГБ ушли в
своп, и шарды, снятые в нём, дали ложные TIMEOUT (`editing`, `WebCryptoAPI`,
`webaudio`). Теперь у прогона один бюджет памяти:

- **`--processes auto`** — браузеров на полосу = `(свободно − --min-free-gb) /
  (1.5 ГБ × число полос)`, не больше числа потоков CPU и не меньше 2. 1.5 ГБ, а не
  среднее 1.0: здоровый браузер держит ~1 ГБ, но `editing`/`IndexedDB`/
  `referrer-policy` дают пики 2–4 ГБ. С 1.0 первый замер (15 браузеров на 22 ГБ)
  за 8 минут дошёл до 0.16 ГБ свободных, и сторож убил 23 браузера.
- **`--min-free-gb 6`** (мягкий пол) — полоса не берёт новый шард, пока свободно
  меньше, если другая полоса занята; `auto` оставляет эту память свободной.
- **`--kill-free-gb 2`** (жёсткий пол) — пока свободно меньше, сторож
  (`browser_rss_cap.py`) убивает самый большой `lumen` прогона (от 2 ГБ); его тест
  получает CRASH, строка в `rss-cap-kills.jsonl` — `"reason": "low-free"`,
  убийства по `--max-browser-gb` — без `reason`. Жёсткий пол выбран по замеру:
  в «до» своп начинает расти только при свободной памяти < 1 ГБ (при 1–6 ГБ
  прирост ≈ 0), а убийство на мягком полу 6 ГБ дало 60 убийств `low-free` за
  1 ч 45 мин (столбец A ниже).
- **Тяжёлая полоса** — файлы из `tests/wpt/heavy_tests.txt` (сейчас три
  `html5lib_*`, 170 id; у каждой строки причина) уходят из своих шардов и идут
  одним юнитом `heavy lane` **последними**, когда все остальные полосы свободны,
  на 2 браузерах. Из знаменателя не исключаются; `--no-heavy-lane` возвращает их
  в общие шарды, `--heavy-tests FILE` подменяет список. Файл пополнять только по
  замеру (`rss-cap-kills.jsonl` с ≥ 2 убийствами одного файла).
- **Последовательная полоса** (WPT-IDB-RUNNER) — у всех тестов прогона общие
  origin-ы wptserve и одно хранилище IndexedDB `<каталог бинаря>/data/idb`
  (`--user-data-dir` у браузера нет). `indexedDB.databases()` видит БД соседей:
  `abort-in-initial-upgradeneeded` получал 1…231 БД вместо 0, а `get-databases`/
  `idbfactory-origin-isolation` (`deleteAllDatabases`) удаляют БД параллельных
  тестов. Поэтому id из `tests/wpt/serial_tests.txt` (у каждой строки причина;
  `.any.js` — каждый вариант отдельной строкой) идут юнитом `serial lane` после
  тяжёлой полосы, одни, на **1** браузере; перед юнитом `data/idb` очищается.
  Кроме того, перед любым прогоном `data/idb` очищается целиком (накопленное от
  прошлых прогонов: 63 МБ после одного прогона `IndexedDB`, 450 МБ WAL после
  двух) — `--keep-idb` отключает. Из знаменателя ничего не исключается;
  `--no-serial-lane` возвращает тесты в общие шарды, `--serial-tests FILE`
  подменяет список; снимок и `state.json` пишут `serial_tests`. Пополнять —
  только тестами, которые читают или стирают всё хранилище origin-а.
- **Лог памяти** — `mem-log.tsv` в `--out-dir`: раз в 10 с свободная память,
  своп, число браузеров, их суммарный и максимальный RSS. В снимке прогона
  (`--run-json`): `low_free_kills`, `min_free_gb`, `kill_free_gb`, `heavy_tests`,
  `memory` (`min_free_seen_gb`, `max_swap_gb`, `low_free_polls`).

### Файл результатов по тестам и потестовое сравнение (WPT-RUN-17)

`--run-json docs/wpt/runs/<имя>.json` пишет рядом `<имя>.ids.tsv.gz` и кладёт в
снимок поле `"ids_file": "<имя>.ids.tsv.gz"`. Это по строке на каждый тест
знаменателя, сортировка по id, детерминированный gzip (повторная запись тех же
данных даёт тот же файл). Столбцы (формат — `tests/wpt/ids_file.py`):
`id`, `type` (testharness/reftest/…), `status` (OK/PASS/FAIL/TIMEOUT/ERROR/
CRASH/NOT-RUN/SKIP/…/`DROPPED`), `passed`, `total` (сабтесты), `score` — тот же
балл, что `score_reports` добавил категории, и `shard`. Скоринг не менялся:
цифры старых снимков сопоставимы.

**Размер**: 68 116 id → ≈ 493 КиБ (≈ 7.2 байта на id) — укладывается в цель
≤ 1.5 МБ на прогон; урезать столбцы не пришлось.

**`DROPPED`** — тест есть в `suite_start`, а `test_start` по нему нет (wptrunner
молча выбросил его после `Max restarts exceeded` / `init_failed in state
RunningState`). Такие id считаются в `scored.coverage` и перезапускаются при
`--retry-timeouts`/`--resume` так же, как TIMEOUT. Для прогона 2026-10-22
«с попапами» их 7 (`css/css-break` 5, `css/css-ui` 1, `editing` 1), для
оригинала — 12.

Сравнить два прогона по тестам:

```bash
python tests/wpt/run_diff.py docs/wpt/runs/A.json docs/wpt/runs/B.json
python tests/wpt/run_diff.py A.json B.json --prefix css/css-break,quirks --min-delta 0.2
python tests/wpt/run_diff.py A.json B.json --json
```

Вывод: категории с суммой «score старый → новый» и числом тестов хуже/лучше/
сменивших статус, затем списки WORSE и BETTER с переходом статусов
(`OK 1/4 -> TIMEOUT 0/4`) и разницей балла. Тест, которого нет в одном из
снимков, считается `(absent)` с баллом 0, поэтому суммы по категориям
складываются в разницу `per_category.score`. `scripts/quality_report.py` при
наличии `ids_file` у обоих снимков печатает под каждой просевшей категорией до
10 худших тестов. Пара прогонов одного бинаря на `quirks,workers` даёт 1 хуже /
1 лучше (шум таймаутов в `workers/…/importScripts`) — порог `--min-delta`
отсекает такое.

### Ловушки

- **`MANIFEST.json` обновляется один раз за прогон.** `run_corpus.py` делает это
  сам и дальше передаёт шардам `--no-manifest-update`. Дефолт `wptrunner` —
  обновлять на каждом запуске, то есть пересканировать 72k файлов ~400 раз.
- **Шард убивается по дереву процессов.** `Popen.kill()` снимает только Python,
  а `lumen.exe` остаётся держать BiDi-порт и ломает следующий шард. Никогда не
  по имени образа — только `taskkill /T /PID`.
- **`wss` и `pywebsocket3`.** См. `CLAUDE.md` → Known gotchas: патч живёт только
  в `.venv` и не переживает переустановку. Без него падает весь прогон, а не
  только `websockets`.
- **Цифра привязана к сборке.** В снимке прогона пишется путь к бинарю; сравнивать
  прогоны между разными коммитами без оговорки нельзя.
- **Идущий прогон считает старым кодом.** Python читает `run_corpus.py` один раз,
  при запуске, поэтому правка скоринга не действует на прогон, который уже идёт:
  его финальный снимок будет посчитан той версией, что была на момент старта.
  После любой правки скоринга снимок надо пересобрать — `--aggregate-only` по
  тому же `--out-dir` пересчитывает уже сохранённые отчёты и стоит секунды.

### Почему 12.55 % нельзя ставить рядом с 5.59 %

WPT-RUN-5 запускается на двух машинах параллельно (решение пользователя
2026-08-20): Windows-прогон в слоте `p2-work` и Linux-прогон на второй машине.
**Снимки хранятся раздельно и никогда не сливаются в один JSON** — у них разные
бинари, а с 2026-08-19 ещё и разный код (`TEST-4`/`TEST-5`).

Windows-половина оборвана на 246 шардах из 479 (03:25 → 11:27, 7.4 ч машинного
времени, 1.9 ГБ чекпойнтов в `.tmp/wpt-corpus/`, в git не попадают). Её 12.55 %
отличаются от 5.59 % тремя вещами сразу, ни одна из которых не «движок стал лучше»:

- **другой знаменатель** — 52 156 id по 99 покрытым категориям, а не 67 735 по всем
  273 (`--aggregate-only` считает частичный прогон по его собственному охвату);
- **исполняются reftest'ы** — `TEST-4`/`TEST-5` закрыты уже после прогона 18-го,
  так что 27 386 reftest-id впервые не идут автоматом в ноль;
- **https не исключается** — `skipped_https = 0` против 6 874 исключённых id в
  прошлый раз ([BUG-785](../../bugs/BUG-785-FIXED.md) закрыт).

Цифра к тому же занижена внутри собственного охвата: 18 шардов не дошли до конца
и их результаты восстановлены из raw-лога, ещё 18 315 id внутри покрытых
категорий не прогонялись вовсе. Сравнимой цифрой будет только завершённый прогон.

Окружение снимка: `dev-release`, wgpu-бэкенд **Vulkan** (Intel Iris Plus, кэш
`data/paint/backend_probe.txt`), `--processes=6`. Поля `platform`/`backend` в
формате снимка пока нет — при сравнении двух машин это придётся держать в голове
или дописать в `run_corpus.py`.

Снимок не переименован из `-windows-partial.json` в финальное имя — прогон

первая). Разбор — срез 16 в

### Как сравнивать две половины и что они дают вместе (срез 16)

`score_audit.py --snapshot A.json --compare B.json` сверяет два снимка на
пересечении охвата — это единственный корректный способ сопоставить прогоны
разных машин. На снимках 2026-08-20 (Windows 479/479, Linux 222 шарда):

- из **74 общих категорий 48 совпадают до последнего счётчика** (`ids`, `ran`,
  `harness_ok`, сабтесты, балл) — движок детерминирован, и расхождение платформ
  как источник ошибки цифры снимается замером, а не рассуждением;
- расхождения оставшихся 26 — почти целиком разница **охвата**: на исполненный
  id Windows даёт 0.1959, Linux 0.1828 (6.7 % относительных, и те за счёт того,
  что Linux дошёл до категорий вроде `encoding`, где набирать нечего);
- **слитая цифра** (по каждой категории берётся тот прогон, что исполнил больше
  её id) — **12.15 %** (8 227 из 67 735) при охвате 68.7 %.

Слитая цифра — не замена головной, а способ не выбрасывать половину работы:
после лечения Windows-дыры и завершения Linux-половины публиковать надо её,
с указанием, из скольких категорий каждая половина в неё вошла.

### Что этот прогон нашёл помимо цифры

- **Четыре битых `.ini` тихо выключали четыре категории целиком.** `wptrunner` парсит все
  `.ini` категории на старте шарда, и один нечитаемый файл роняет шард с `ParseError` до
  первого теста — шард завершается за 4 с и выглядит отработавшим. Из-за этого 759
  testharness-id (`accelerometer`, `battery-status`, `content-security-policy`,
  `css/css-shadow`) не прогонялись ни разу, а их гейт `--check` был мёртв: заявленное
  покрытие `TEST-3` по этим категориям не выполнялось. Файлы починены, генератор
  `expectations.py` больше не может выпустить такой файл (проверяет свой вывод тем же
  парсером). Дефект обнаружился именно потому, что скоринг идёт от манифеста: при счёте
  «по отчётам» эти id просто отсутствовали бы, не оставив следа.
- **`TIMEOUT` — самая массовая аномалия прогона** (10 766 из 30 445 прогнанных, 35 %).
  На `dom` разобрано: часть висит на сабтестах, требующих второго глобала
  ([BUG-480](../../bugs/BUG-480-OPEN.md), `<iframe>` без browsing context), часть не
  отчитывается вовсе. Систематический разбор — работа P3, не этой задачи.

### Пилот 2026-08-18: что он измерил на самом деле

Пилот запускался, чтобы поймать дефекты оркестратора до ночного прогона, и
поймал три — все три искажали цифру, и ни один не был виден без прогона:

1. **Скоринг по всему корпусу вместо охвата.** Прогон 10 категорий отчитался
   `0.58 %`, потому что делил на все 67 735 id — включая 263 категории, которые
   никто не просил запускать. Арифметически верно, по смыслу — ложь. Исправлено:
   частичный прогон считается по своим категориям (те же результаты → `7.52 %`).
2. **Флэтовый бюджет времени на шард.** 1200 с убивали `encoding` (1343 id)
   и `WebCryptoAPI` (313 id) и вдесятеро превышали то, что нужно `FileAPI`
   (125 id). Бюджет теперь масштабируется от размера шарда.
3. **Убитый шард терял всё.** `--log-wptreport` пишется один раз, в конце, так
   что оба убитых шарда унесли с собой 1656 id — те попали в знаменатель со
   счётом 0 и выглядели как провал движка. Добавлен параллельный mozlog-поток,
   из которого результаты восстанавливаются. **Доработано 2026-08-20:** спасение
   срабатывало только у шарда, от которого остался нечитаемый `.json`, а
   `run_shard` как раз удаляет пустой отчёт убитого шарда, чтобы тот не выглядел
   «нечитаемым» — то есть у убитых шардов, ради которых механизм и заводился,
   спасать было нечего. Агрегатор теперь перечисляет `*.raw.jsonl` наравне с
   отчётами; на 36 шардах Linux-прогона это вернуло 297 id (`ran` 1874 → 2171).

Отдельная находка пилота, не связанная с оркестратором —
[BUG-785](../../bugs/BUG-785-FIXED.md): движку нельзя доверить дополнительный CA,
поэтому весь `.https.`-корпус (7 190 id, 10.6 %) недостижим на уровне TLS.

### Почему `.https.` не запускается, но остаётся в знаменателе

**Дополнение 2026-08-20 (прогон WPT-RUN-5, Linux).** Причина, описанная ниже
([BUG-785](../../bugs/BUG-785-FIXED.md), `UnknownIssuer`), исправлена, и прогон
идёт БЕЗ `--skip-https` — но https по-прежнему даёт ноль, теперь из-за второго,
независимого дефекта: [BUG-792](../../bugs/BUG-792-FIXED.md), тело
close-delimited https-ответа теряется целиком, потому что `wptserve` закрывает
соединение без TLS `close_notify`. Замер на 37 шардах: 635 прогнанных
`.https.`-тестов — **0 harness OK, 0 сабтестов** (против 653 OK из 1362 у
не-https на том же прогоне), 2380 попаданий ошибки в логах. То есть охват тот
же — 7190 id, 10.6 % корпуса, — и до фикса BUG-792 они стоят ноль независимо
от того, запускать их или пропускать. Сколько из этих 10.6 % починка вернёт
цифре, измерено срезом 32 выше: **+0.16 п.п.**, а не 10.6. Ожидание из строки `WPT-RUN-5` ROADMAP
(«потолок поднимается почти до 96 %») в этой цифре НЕ материализуется.

Выборка 200 https-id из 65 категорий дала **200 TIMEOUT из 200**, ноль
сабтестов и 200 `UnknownIssuer` в логе. Отказ TLS при этом не быстрый: тест
выжидает полный таймаут, ~39 с, то есть все 6 874 https-id стоили бы **≈14
часов** прогона ради заранее известного нуля.

Отсюда `run_corpus.py --skip-https`: id **остаются в знаменателе** и считаются
непройденными — решение «весь манифест без изъятий» не пересматривается, — но
не запускаются, а сводка отдельной строкой печатает, сколько id не запущено
намеренно и почему. Разница между «не запускали» и «потеряли» видна в выводе:
`NOT RUN ON PURPOSE` против `RECOVERED`/`PROBLEM SHARDS`.

### Как BUG-786 двигает цифру — в обе стороны (замер 2026-08-20, срез 14)

Оговорка «часть reftest-PASS вакуумна из-за [BUG-786](../../bugs/BUG-786-OPEN.md),
поэтому после починки цифра может упасть» ходила по документам с 2026-08-20 в
односторонней форме. Замер её поправил: падение есть, подъём больше.

Считать надо обе стороны пары. CDATA-обёртку внутри `<style>` несут 4 824
reftest-id манифеста на стороне **эталона** против 2 309 на стороне теста, а
2 470 id сравниваются с одним `/css/reference/ref-filled-green-100px-square.xht`,
который у нас рендерится без своего зелёного квадрата. По вердиктам прогона
эталонная сторона цифру топит, а не надувает: `==`-пары с полной потерей стиля
эталоном дают **7.3 %** PASS (4 617 исполнено) против **27.6 %** у пар без

### Контрольный прогон: таймауты — не артефакт параллелизма

Пилот дал **838 TIMEOUT из 2453 прогнанных id (34 %)**, и до разбора было
неясно, свойство ли это тестов или следствие `--processes=6` (шесть окон Lumen
конкурируют за CPU, а таймаут теста — стенные часы). Проверено прямым
сравнением на категории `dom`:

| Прогон | Тесты | OK | TIMEOUT | ERROR | Сабтесты | Время |
|---|---|---|---|---|---|---|
| `--processes=6` | 320 | 229 | 90 | 1 | 2030/5616 | 267 с |
| `--processes=1` | 320 | 229 | 90 | 1 | 2030/5616 | 1170 с |

**Расхождений ноль** — совпали и статусы всех 320 тестов, и число прошедших
сабтестов. Параллелизм ускоряет прогон в 4.4× и не меняет исход, так что
полный прогон идёт с `--processes=6` без оговорок. Это независимое
подтверждение того же вывода среза 1 `WPT-RUN-3`, полученное на другом наборе.

Природа самих таймаутов (разобрано на `dom`, 90 случаев):

- **48 тестов частично проходят** и висят на отдельном сабтесте — внутри
  таймаутящих тестов 116 из 922 сабтестов всё же PASS. Висят те, что требуют
  второго глобала: `ownerDocument across globals`, `Document-characterSet-normalization-*`
  (грузит `<iframe>` на каждую кодировку). Первопричина — уже открытый
  [BUG-480](../../bugs/BUG-480-OPEN.md): у `<iframe>` нет отдельного browsing
  context, `contentWindow`/`contentDocument` отсутствуют. Нового бага не завожу.
- **42 теста не дают ни одного сабтеста** — harness не успевает отчитаться
  вовсе. Первопричина не установлена; в выборке преобладают `.xml`/`.xhtml`
  документы и `Document-contentType/*`. Разбор — движковая работа (P3), не эта
  задача; фиксируется здесь как незакрытый вопрос, а не как приписанный кому-то
  дефект.

Важное следствие для формулы: `TIMEOUT` **не означает ноль**. Скоринг считает
сабтесты, а не harness-статус, поэтому частично прошедший таймаутящий тест
приносит свою долю — цифра не проваливается от того, что harness не закрылся.

### Две цифры из-за сертификата (BUG-1271)

Сертификат тестового сервера с `*.localhost` в SAN rustls-webpki не принимает
(wildcard требует ≥2 меток после `*`), поэтому весь прогон шёл без https на
поддоменах: 4 344 отказа `certificate not valid for this hostname` в логах
189 шардов (13 964 id). [BUG-1271](../../bugs/BUG-1271-FIXED.md) починен
посреди прогона, сам прогон не трогали. После него те же 189 шардов
перепрогнаны тем же бинарём с новым сертификатом (`--prefixes` по списку
затронутых шардов, отдельный `--out-dir`, 59 мин), их отчёты подставлены
вместо исходных, остальные 276 шардов — как сняты. В перепрогоне отказов на
поддоменах ноль (остались 4 — на `nonexistent.localhost`, это задумано тестом).

Сдвиг — **+104.4 балла, +0.16 п.п.**, и он не однородный: 196 категорий
совпали до единицы, 70 разошлись.

| категория | как снято | с поддоменами | |
|---|---:|---:|---|
| `referrer-policy` | 515.25 | 607.85 | 339 id вверх, 58 вниз |
| `fetch` | 251.56 | 268.40 | |
| `upgrade-insecure-requests` | 87.33 | 98.33 | |
| `mixed-content` | 265.12 | 232.47 | 149 id вниз, 0 вверх |
| `client-hints` | 46.33 | 40.17 | 8 вниз — TIMEOUT вместо OK, шум повторов |

Падение `mixed-content` — честное: сабтесты «Expects blocked … swap-scheme
redirection» проходили, пока https-поддомен не открывался вовсе (отказ TLS
засчитывался как «заблокировано»), а с рабочим сертификатом цепочка доходит
до редиректа на `http://`, и тест получает `upgraded` вместо `blocked`
(`assert_equals: … expected "blocked" but got "upgraded"`, 29 вариантов
`fetch`, 29 `xhr`, по 9–11 у тегов и worklet). То есть прежние PASS были
ложными. Нынешний FAIL — тоже не движок, а хост стенда
([BUG-1285](../../bugs/BUG-1285-OPEN.md)): `http://*.localhost` для движка
a priori authenticated (Secure Contexts §3.1), поэтому http-хоп уходит в сеть
без блокировки, и категория `mixed-content` целиком не измеряет enforcement,
пока `browser_host = "localhost"`.

### Прирост +62.71 балла за 2.5 суток — весь в одной категории, и он не движковый

На 266 общих категориях like-for-like даёт `3 783.17 → 3 845.88`
(**+62.71**; выиграно +69.58, потеряно −6.87). Из них **+63.49 — одна
категория `websockets`**, то есть на всех остальных 265 категориях сумма
**отрицательная** (−0.78): точечные правки движка тонут в шуме, вывод среза 33
(«движок за 2.5 суток не сдвинулся») сохраняется.

Приписывать `websockets` движку нельзя по трём независимым причинам:

- **между снимками нет ни одного коммита по WebSocket** — `git log e7b012ec4..7880cbc2b -- crates/`
  даёт 32 коммита, ни один не трогает WS;
- **прирост не в TLS** — из 786 id категории по TLS отдаются 5, и все пять
  дают ноль; вырос обычный `ws://`;
- **выросло число сабтестов**: 938 → 1 534 при `harness OK` 341 → 470. Столько
  новых сабтестов не появляется от правки поведения — появляется от того, что
  тест впервые доходит до их объявления.

Остаётся платформа: базовый прогон Windows, этот Linux, а патч
`pywebsocket3` (`ssl.wrap_socket`, см. CLAUDE.md → Known gotchas) живёт только
внутри `.venv` и на двух машинах не одинаков. Проверяется это одним шардом —
`run_corpus.py --categories websockets` на Windows-машине на **этом же**
коммите; до такой проверки цифру `websockets` читать как свойство стенда, а не
движка.

| без хелпера (`battery-status`, `bluetooth`, `contacts`, `content-index`, `direct-sockets`, `idle-detection`, `managed`, `mediacapture-image`) | 219 | 146 | **0.00** |
