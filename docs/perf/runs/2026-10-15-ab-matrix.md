## Итог и ограничения (ручной раздел; генератор его не пишет)

Условия: один маршрут (прямой, IP автора, RU), один день, один проход + перепроверки расхождений голосованием (2 повтора Chrome и Lumen на 47 сайтах с расхождением; все записи — в `2026-10-15-ab-chrome.json` / `2026-10-15-ab-lumen.json`). Плечо Chrome — реальный Chrome for Testing 153 с JS; плечо Lumen — `lumen --dump-source` (HTTP-слой, JS не исполняется: BUG-1629, живое окно не отдаёт кадр), поэтому JS-стены и «мягкие» заглушки из бандлов считаются отдельно (`jschl`, `soft`), а фразы «unsupported browser» ищутся только в видимом тексте (без скриптов, стилей, `<noscript>`, комментариев). Ячейка `lumen / lumen` — токен `Lumen/x.y` в конце UA и бренд `Lumen` в `Sec-CH-UA`, остальные заголовки побайтно те же (COMPAT-AB-IDENTITY-KNOB).

**Р1/Р2 (токен и бренд CH).** Токен блокирует 1 сайт из 533 (0,19 %, порог 0,5 %): fiverr-com (PerimeterX 403, 3 из 3 прогонов); must-work — 0. Плечо Chrome после перепроверок: 0 сайтов «пущен без токена → заблокирован с ним» (первичные 5 — шум IP: stackoverflow, dns-shop-ru, domclick-ru, tandfonline-com, dellin-ru пустили при повторе). Бренд `Lumen` в `Sec-CH-UA` отказов не добавил. Вердикт: переход на Chrome-грамматику + `Lumen/x.y` допустим; fiverr-com — запись `chrome_unbranded` в пакете совместимости.

**Р4 (стек).** «Chrome пустил, Lumen заблокирован» — 25 из 533 (4,69 %), но к отпечатку TLS/H2 это не сводится:
- trust — 7 (rzd, bspb, alfabank, nspk, tbank, sberbank, vtb): `UnknownIssuer`, в хранилище Lumen нет российского корня, Chrome берёт его из ОС. Это пункт «OS-доверие» ADR-034, не rustls-отпечаток;
- dns — 2 (lenreg-ru, konami-net): у Chrome тоже ERROR, шум резолвера;
- jschl — 4 (Cloudflare-челлендж, проходит JS) и soft — 3 («обновите браузер» в видимом тексте исходника без JS): Chrome исполняет JS, Lumen в этом плече нет — измерить можно только после BUG-1629;
- antibot — 8 и tls — 1: 9 из 533 = 1,69 % (< 3 %), из них must-work 3 (t2-ru, dns-shop-ru, imgsrc-ru).
`header_matrix.py` на 6 из этих сайтов (`2026-10-15-ab-header-matrix.md`): t2-ru, dns-shop-ru, dellin-ru, domclick-ru отказывают во **всех** ячейках, в том числе с `curl_cffi impersonate=chrome` и заголовками Chrome, — это не TLS и не заголовки, а JS/cookie-челлендж (Chrome его проходит скриптом). Только eapteka-ru зависит от TLS (503 с `httpx`, 200 с chrome-TLS при любых заголовках). imgsrc-ru: рукопожатие обрывается и у `curl_cffi` — причина не в отпечатке, нужен разбор версии TLS/шифров. Вердикт: порог 3 % не достигнут (подтверждённо стеку — 1 сайт, 0,2 %); формально «любой must-work» сработал по автоматической атрибуции, но ручная проверка снимает его (t2-ru, dns-shop-ru — не стек). Проект TLS/H2 **не открывать**; перемерить, когда появится JS-плечо Lumen.

**Р16 (device-API, `window.chrome`).** Не измерен: плечо Lumen не исполняет JS, различия `window.chrome`/device-API в нём не видны. Решение «как в 7.4» остаётся, пересмотр — после BUG-1629 и стенда антиботов с JS-плечом.

**Не в этой таблице:** шум IP — hilton-com, kohls-com, caixa-gov-br (Chrome plain заблокирован, с токеном пущен); `Lumen пустил, Chrome заблокирован` (19) — в основном российские сайты, где Chrome-плечо получает NET_FAIL (причина не разобрана: маршрут или headless), и Akamai-отказы Chrome, которые плоский HTTP-запрос Lumen не воспроизводит.
