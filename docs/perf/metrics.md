# Журнал user-centric перф-метрик Lumen (PERF-2)

Хронология прогонов [`scripts/perf_metrics.py`](../../scripts/perf_metrics.py) по
корпусу реальных сайтов ([corpus.txt](corpus.txt)). Харнесс извлекает метрики
«по образцу» FCP / LCP / TTI + Total Blocking Time из таймлайна одной навигации,
который собирает `lumen --trace-nav` (PERF-1, Chrome Trace Event Format) —
никакого нового кода в движке, только раскладка готовых спанов в метрики.

Модель — [docs/build-speed.md](../build-speed.md): фиксированный протокол замера
+ журнал «метрика ↔ коммит». Отличие от [journal.md](journal.md) (perf_audit.py):
там пофазный аудит целиком (сеть/стиль/paint + RAM/зависания на живом окне),
здесь — узкий набор пользовательских метрик с регрессионным сравнением по каждой.

## Метрики (все в мс от старта навигации)

| Метрика | Из чего | Смысл |
|---|---|---|
| `ttfb_ms` | конец спана `fetch-document` | документ получен целиком (прокси TTFB — сеть не отдаёт под-байтовый тайминг) |
| `html_parse_ms` | длительность `parse-html` | парсинг HTML |
| `script_ms` | длительность `run-scripts` | исполнение JS на UI-потоке |
| `layout_ms` | длительность `layout` | каскад + бокс-дерево |
| `paint_ms` | длительность `paint` | CPU-растеризация (известный тормоз тяжёлых страниц) |
| `fcp_ms` | инстант `first-paint` | прокси First Contentful Paint |
| `lcp_ms` | конец спана `paint` | прокси Largest Contentful Paint |
| `tti_ms` | max(fcp, конец `run-scripts`) | прокси Time To Interactive |
| `tbt_ms` | Σ max(0, task − 50) по script-задачам | прокси Total Blocking Time (порог 50 мс как в Lighthouse) |
| `nav_ms` | длительность корневого `navigation` | полная загрузка |
| `doc_bytes` / `total_bytes` / `resources` | arg `size` net-спанов | детерминированные счётчики (сигнал регрессии, не зависит от сети) |

**Ограничение headless-пути.** `--trace-nav` красит страницу ОДИН раз в конце
(тот же CPU-путь, что `--screenshot`), поэтому `fcp`/`lcp`/`tti` схлопываются к
моменту завершения единственного paint — распределить их как в живом
инкрементальном рендере headless-путь не может (то же, что зафиксировано в
[journal.md](journal.md): headless paint ≠ живое окно). Реально различимые и
действенные числа этого пути — `ttfb` / `html_parse` / `script`(`tbt`) /
`layout` / `paint` и байтовые счётчики; `fcp`/`lcp`/`tti` даются «по образцу» для
полноты и как якорь общего времени. Живые FCP/LCP/TTI появятся, когда
PerformanceObserver paint-timing будет дописан в движке (JS-каркас частично
готов: `performance.now`, long-animation-frames, soft-navigation в `crates/js`).

## Протокол

```bash
# базлайн/регрессионный прогон (медиана из 3 устойчивее к сетевому шуму)
python scripts/perf_metrics.py --repeat 3 --timeout 60
# сравнение с прошлым коммитом (та же машина!)
python scripts/perf_metrics.py --compare docs/perf/metrics-runs/<дата>.json
# проверка извлечения метрик без сети (входит в ворота)
python scripts/perf_metrics.py --selftest
```

Сравнивать числа можно только между прогонами **одной машины**; ±20% на сетевых
фазах — шум, >20% по `nav_ms` на той же машине — находка. Сырые прогоны —
`docs/perf/metrics-runs/<дата>.json` (коммитятся; промежуточные трейсы остаются
в `.tmp/perf-metrics/`, не коммитятся).

Шаблон секции:

```markdown
## YYYY-MM-DD — <коммит> — <машина>

<таблица из summary.md>

**Сравнение с прошлым:** <дельты или «первый прогон»>
**Находки:** <список>
```

**Ответ на DoD («что доминирует») — единого победителя нет, состав зависит от
профиля сайта:**
- **CPU-растеризация (paint)** — крупнейший отдельный тормоз там, где есть много
  изображений/сложная вёрстка: theguardian **144.7 с из 157.4 с (92%)** — почти

  известный класс (docs/perf/journal.md, PERF-11/12 контекст).
- **Последовательный fetch картинок на UI-потоке** — второй по эффекту рычаг:
  netflix 10.1 с (49% — `fetch-images` в одиночку больше `script`+`layout`+`paint`
  вместе), uber 11.5 с (51%). Известная находка (ROADMAP.md `PERF`-преамбула,
  «последовательный fetch подресурсов в UI-потоке»), но раньше не было числа
  такого масштаба на реальном сайте.
- **Исполнение JS (run-scripts)** доминирует отдельно от paint/layout на
  JS-тяжёлых SPA: medium 16.6 с (80% — react-подобный движок Medium), google
  0.9 с (35%, абсолютно мало). Здесь ни «убрать с UI-потока», ни «параллелить»
  не помогают — это чистое время исполнения V8, лечится профилированием самого
  JS/бандла, а не конвейером загрузки.
- **Быстрые сайты (espn/wikipedia/google)** — все фазы малы и сопоставимы,
  доминанты нет в абсолютном выражении (доли — шум на суммах в единицы мс).
- **flipkart и etsy — 0% движка**: весь бюджет (120.3 с и 0.9 с) потрачен на
  `fetch-document`, дальше пайплайн не заходит вовсе (нет даже `parse-html`).
  Это не архитектурная перф-проблема Lumen — сервер/сеть отвечает медленно
  (flipkart) или отдаёт заглушку (etsy, см. ниже).

**«5 HUNG» — НЕ одна причина, разделяются на два разных класса:**
- **github — воспроизводимо headless, доминанта layout+paint (70%
  совместно: 36.8 с + 27.6 с из 90.8 с)** — единственный из пяти, где гипотеза
  задачи («дорогая раскладка») подтверждается напрямую и независимо от
  GUI/wgpu-монитора: чистый CPU-путь без окна всё равно тратит на layout/paint
  две трети времени. Кандидат на профилирование layout/paint конкретно на
  github.com.
- **duckduckgo/microsoft/baidu — TIMEOUT и headless на 240 с** (трейс не
  пишется до завершения — `run_trace_nav` сохраняет JSON один раз в конце,
  поэтому TIMEOUT не даёт частичных фаз). Отдельная проверка: прямой запуск
  `lumen --trace-nav` на duckduckgo с таймаутом 400 с — документ (315 КБ) и все
  23 JS-чанка (`_next/static/chunks/*.js`) успешно получены за первые секунды
  (сеть не виновата), после чего процесс не даёт больше никакого вывода и не
  завершается даже за 400 с. Раз все ресурсы уже локальны, а зависание
  наступает после — это похоже на **исполнение скрипта, которое никогда не
  возвращается** (`run-scripts`), а не на дорогой layout: у layout/paint нет
  таких порядков величины даже на самых тяжёлых сайтах корпуса (github — 64 с
  максимум). Это баг зависания JS, а не перф-профиль — отдельная триажная
  задача, не perf-тюнинг.
- **etsy — не воспроизводится headless вообще**: 0.9 с, только `fetch-document`,
  дальше пайплайн не идёт (пустой/заглушечный ответ или ранний выход по статусу
  ответа). Live-режимный HUNG для etsy, видимо, специфичен для GUI/окна
  (накопленное состояние вкладок, антибот на другом пути сети) — не
  подтверждается на чистом CPU-пути, нужна отдельная live-диагностика.

**Итог для решения «убрать работу с UI-потока» vs «параллелить»**: обе категории
реальны и относятся к разным сайтам — paint (theguardian/w3schools/github) просит
выноса растеризации с UI-потока или её ускорения, fetch-images (netflix/uber)
просит параллельного/конкурентного fetch подресурсов вместо последовательного.
Ни то, ни другое не решает JS-тяжёлые сайты (medium) или два из пяти «HUNG»
(duckduckgo/microsoft/baidu), которые требуют отдельной диагностики зависшего
`run-scripts`, а не перф-переделки конвейера.
