# Ревизия и пополнение очередей P1–P4

$ARGUMENTS — роли через пробел (`P1 P3`); пусто = P1 P2 P3 P4.

Ты — планировщик очередей, код не пишешь. Цель: в каждой очереди 6–10
задач, каждую из которых сессия Sonnet доведёт от взятия до merge+push.

**Не трогать:** `STATUS-P5.md` (рекуррентный, свой формат), `STATUS-P6.md`
(наполняет только пользователь — кандидатов для P6 только перечисли в отчёте).

## Шаг 0 — старт

```bash
git pull origin main
cd "$(bash scripts/worktree-pool.sh p5-work p5-queue-refill-$(date +%Y%m%d) | tail -1)"
git status --short          # свежий worktree может нести всё репо как staged-deleted
```

Прочитать: `docs/dev-roles.md` (§Task tracking schema, §Urgent lane, мандаты
ролей), `docs/git-workflow.md`, `docs/engine-gaps.md`, `docs/probe-method.md`.

## Шаг 1 — ревизия текущих указателей

Каждый `<source>:NN` раскрывать **отдельной** командой `sed -n 'NNp' <source>`
(`sed -n 'Ap;Bp'` печатает в порядке файла, не очереди). Для каждого:

| Проверка | Как | Действие |
|---|---|---|
| Указатель протух | строка — не задача (сосед, заголовок, пусто) | найти строку по ID, перенаправить |
| Задача закрыта | статус в ROADMAP/CSS-SPECS, строка в `BUGS-FIXED.md`, `git log --oneline --grep=<ID>` | удалить указатель |
| Задача взята | `git branch -a \| grep -i <id>` | оставить, не дублировать |
| Двойная очередь | ID в другом `STATUS-P*.md` | оставить у одной роли |
| Чужая роль | баги → только P3, CSS → только P4, `OPEN (ДОРАБОТКА → X)` — не P3 | перенести владельцу |
| Осиротевшая ДОРАБОТКА | `ДОРАБОТКА → X`, а X уже done | сверить баг с кодом, закрыть или вернуть в очередь |
| Размер | критерии шага 2 | если задача больше — нарезать (шаг 3) |

Строке `BUGS.md` на слово не верить: симптом сверить с кодом или пробой.

## Шаг 2 — критерий «влезает в сессию Sonnet»

Задача годится, только если выполнены **все** пункты:

- 1 крейт (максимум 2 со смежным интерфейсом), ожидаемый диф до ~400 строк кода без тестов;
- точка входа известна (`path:line`, функция или пункт спеки), архитектуру исследовать не надо;
- есть проверяемый критерий готовности (unit-тест, WPT-подкатегория,
  graphic-тест, `--dump-layout`/`--dump-display-list`), и в нём написано,
  какой результат ожидается;
- архитектурных решений и выбора между вариантами нет;
- не нужны живые сайты, VPN, перф-A/B и многочасовые прогоны;
- гейт (clippy + scoped-test или graphic run) укладывается в обычную сессию.

Большие архитектурные треки (BUG-935, BUG-286, BUG-341 на паузе и т.п.) в
Sonnet-очереди не дробить — только упомянуть в отчёте.

## Шаг 3 — нарезка и брифы

- Каждый срез — своя строка в мастер-списке роли: `ROADMAP.md` (P1/P2),
  `BUGS.md` (P3), `CSS-SPECS.md` (P4). Если срез не тривиальный, к нему нужен
  бриф `docs/tasks/<id>.md`.
- В брифе: цель; точка входа `path:line`; что не трогать; критерий готовности;
  команда гейта; зависимости от соседних срезов.
- Срезы ставить в порядке зависимостей: первому срезу результат второго не нужен.
- Номер нового бага брать по `origin/main` прямо перед коммитом: в параллельных сессиях бывает коллизия номеров.

## Шаг 4 — пополнение

Источники:

- **P1** — `ROADMAP.md`, фичи; видимое пользователю идёт выше невидимого.
- **P2** — `ROADMAP.md`, треки WPT / DEVX / CI.
- **P3** — `BUGS.md`, строки `OPEN` без «ДОРАБОТКА»; первыми — гейт-блокеры и видимые дефекты.
- **P4** — `CSS-SPECS.md` (⬜/🟡) и `// CSS:` в коде (`grep -rn "// CSS:" crates`, указатель `file:line`).

Нереализованная функциональность — задача ROADMAP, не баг. Указатели ставить
голыми строками `<source>:NN`, без заголовков и описаний. Порядок строк задаёт
приоритет и зависимости.

## Шаг 5 — коммит

1. `python scripts/remap_status_pointers.py --apply`, затем перечитать
   **каждый** указатель: протухший указатель после remap мог совпасть с соседом.
2. `python scripts/check_doc_links.py` (без `--update`: оно переписывает baseline).
3. Markdown правится только через Edit/sed. Python в текстовом режиме не
   использовать: в `BUGS.md` сырые CR.
4. `git add <явные пути>` → `git diff --cached --stat` → коммит. Сообщение на
   русском; в теле — почему выбраны именно эти задачи.
5. `merge --no-ff` в `main` → push. Если STATUS-файлы конфликтуют, пересобирать
   их по ID задач, а не по номерам строк. Затем освободить слот:
   `bash scripts/worktree-pool.sh release p5-work`.

## Шаг 6 — отчёт пользователю (по-русски)

По каждой роли:

- было → стало (число задач);
- удалённые указатели и причина (закрыто / протухло / чужая роль / занято веткой);
- добавленные задачи: ID, суть одной строкой, критерий готовности;
- нарезка: исходная задача → срезы.

Отдельными списками:

- кандидаты, которые не прошли шаг 2, и почему;
- предложения для P6;
- найденный, но не исправленный дрейф в `BUGS.md` / `ROADMAP.md`.

Если источник ничего не говорит о приоритете или границах задачи — спросить
пользователя, а не додумывать.
