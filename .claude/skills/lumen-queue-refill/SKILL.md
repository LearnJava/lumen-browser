# Ревизия и пополнение очередей P1–P4

$ARGUMENTS — роли через пробел (`P1 P3`); пусто = P1 P2 P3 P4.

Ты — планировщик очередей, код не пишешь. Цель: в каждой очереди до 25
задач, каждую из которых сессия Sonnet доведёт от взятия до merge+push.
Если подходящих задач меньше 25, ставь столько, сколько нашлось: задачу,
которая не прошла шаг 2, не добавляй ради количества.

## Главное правило — только дописывать

Все файлы этот скилл **дописывает**, а не переписывает:

- **`STATUS-P1…P4.md`** — новые указатели только в **конец** файла.
  Существующие строки не удалять, не переставлять, не перенаправлять.
- **`ROADMAP.md`, `BUGS.md`, `CSS-SPECS.md`** — новые строки только в **конец**
  таблицы, на последней строке файла. Существующие строки (статусы, описания,
  ячейки) не трогать. Вставка в середину сдвигает номера строк и ломает
  чужие указатели.
- **`docs/tasks/<id>.md`** — только новые файлы. Если бриф уже есть, его не
  переписывать, а предложить дополнение в отчёте.
- Не запускать `remap_status_pointers.py --apply` и никакие инструменты,
  которые переписывают файл целиком. При дописывании в конец номера строк не
  сдвигаются, и remap не нужен.
- Всё, что в существующих строках неверно (протухло, закрыто, задвоено, не той
  роли, слишком крупно), идёт **только в отчёт** с готовым предложением правки.
  Исправлять или нет, решает пользователь.

**Не трогать вовсе:** `STATUS-P5.md` (рекуррентный, свой формат),
`STATUS-P6.md` (наполняет только пользователь; кандидатов для P6 только
перечислить в отчёте).

## Шаг 0 — старт

```bash
git pull origin main
cd "$(bash scripts/worktree-pool.sh p5-work p5-queue-refill-$(date +%Y%m%d) | tail -1)"
git status --short          # свежий worktree может нести всё репо как staged-deleted
```

Прочитать: `docs/dev-roles.md` (§Task tracking schema, §Urgent lane, мандаты
ролей), `docs/git-workflow.md`, `docs/engine-gaps.md`, `docs/probe-method.md`.

## Шаг 1 — ревизия текущих указателей (только чтение)

Каждый `<source>:NN` раскрывать **отдельной** командой `sed -n 'NNp' <source>`
(`sed -n 'Ap;Bp'` печатает в порядке файла, не очереди). Для каждого указателя
проверить и записать вывод для отчёта:

| Проверка | Как |
|---|---|
| Указатель протух | на строке не задача (сосед, заголовок, пусто); найти правильный номер по ID |
| Задача закрыта | статус в ROADMAP/CSS-SPECS, строка в `BUGS-FIXED.md`, `git log --oneline --grep=<ID>` |
| Задача взята | `git branch -a \| grep -i <id>` |
| Двойная очередь | ID в другом `STATUS-P*.md` |
| Чужая роль | баги → только P3, CSS → только P4, `OPEN (ДОРАБОТКА → X)` — не P3 |
| Осиротевшая ДОРАБОТКА | `ДОРАБОТКА → X`, а X уже done — сверить баг с кодом |
| Размер | критерии шага 2; если задача крупнее — срезы дописываются (шаг 3), исходный указатель остаётся |

Живыми задачами считать указатели без замечаний. Число 25 считается с ними.

Строке `BUGS.md` на слово не верить: симптом сверить с кодом или пробой.

## Шаг 2 — критерий «влезает в сессию Sonnet»

Задача годится, только если выполнены **все** пункты:

- 1 крейт (максимум 2 со смежным интерфейсом), ожидаемый диф до ~400 строк кода без тестов;
- точка входа известна (`path:line`, функция или пункт спеки), архитектуру исследовать не надо;
- есть проверяемый критерий готовности (unit-тест, WPT-подкатегория,
  graphic-тест, `--dump-layout`/`--dump-display-list`), и в нём написано,
  какой результат ожидается;
- архитектурных решений и выбора между вариантами нет;
- не нужны живые сайты, VPN, перф-A/B и многочасовые прогоны;
- гейт (clippy + scoped-test или graphic run) укладывается в обычную сессию.

Большие архитектурные треки (BUG-935, BUG-286, BUG-341 на паузе и т.п.) в
Sonnet-очереди не дробить — только упомянуть в отчёте.

## Шаг 3 — нарезка и брифы

- Каждый срез — новая строка в **конце** мастер-списка роли: `ROADMAP.md`
  (P1/P2), `BUGS.md` (P3), `CSS-SPECS.md` (P4). Id среза ссылается на
  исходную задачу (`<ID>-S1`, `<ID>-S2`…). Строку исходной задачи не править.
- Если срез не тривиальный, к нему нужен новый бриф `docs/tasks/<id>.md`:
  цель; точка входа `path:line`; что не трогать; критерий готовности; команда
  гейта; зависимости от соседних срезов.
- Срезы дописывать в порядке зависимостей: первому срезу результат второго не нужен.
- Номер нового бага брать по `origin/main` прямо перед коммитом: в параллельных сессиях бывает коллизия номеров.

## Шаг 4 — пополнение

Дописать в конец каждой очереди `25 − <живых задач>` указателей. Если в
источниках не хватает задач, прошедших шаг 2, — остановиться на меньшем числе
и написать в отчёте, сколько не добрано и почему.

Источники:

- **P1** — `ROADMAP.md`, фичи; видимое пользователю идёт выше невидимого.
- **P2** — `ROADMAP.md`, треки WPT / DEVX / CI.
- **P3** — `BUGS.md`, строки `OPEN` без «ДОРАБОТКА»; первыми — гейт-блокеры и видимые дефекты.
- **P4** — `CSS-SPECS.md` (⬜/🟡) и `// CSS:` в коде (`grep -rn "// CSS:" crates`, указатель `file:line`).

Нереализованная функциональность — задача ROADMAP, не баг. Не дописывать
указатель на задачу, которая уже стоит в любой `STATUS-P*.md` или взята
веткой. Указатели — голыми строками `<source>:NN`, без заголовков и описаний.
Дописываемый блок упорядочить по приоритету и зависимостям.

Дописывать так: `printf '%s\n' 'ROADMAP.md:NN' >> STATUS-P1.md`. Перед этим
проверить, что файл кончается переводом строки (`tail -c1 STATUS-P1.md | xxd`).
Строки в таблицы — через Edit, якорь — последняя строка файла.

## Шаг 5 — проверка «ничего не переписано» и коммит

1. Каждый новый указатель перечитать `sed -n 'NNp'`: он должен попадать в свою строку.
2. `git diff --numstat`: у всех изменённых файлов **0 удалённых строк**
   (вторая колонка). Если где-то не 0 — откатить этот файл
   (`git checkout -- <файл>`) и дописать заново.
3. `python scripts/check_doc_links.py` (без `--update`: оно переписывает baseline).
4. Python в текстовом режиме для markdown не использовать: в `BUGS.md` сырые CR.
5. `git add <явные пути>` → `git diff --cached --stat` → коммит. Сообщение на
   русском; в теле — почему выбраны именно эти задачи.
6. `merge --no-ff` в `main` → push. Если STATUS-файл конфликтует, взять версию
   `main` и дописать свой блок в её конец заново. Затем освободить слот:
   `bash scripts/worktree-pool.sh release p5-work`.

## Шаг 6 — отчёт пользователю (по-русски)

По каждой роли:

- было → стало (число задач); если меньше 25 — почему не добрано;
- дописанные задачи: ID, суть одной строкой, критерий готовности;
- нарезка: исходная задача → дописанные срезы.

**Предложенные правки (не применены, ждут решения)** — по каждой готовая
команда или строка:

- указатели, которые нужно удалить (закрыто / занято веткой / задвоено) — с причиной;
- протухшие указатели: `STATUS-PN.md`: было `X:NN` → должно быть `X:MM`;
- указатели не той роли — куда перенести;
- крупные задачи, срезы которых уже дописаны: удалить ли исходный указатель;
- осиротевшие «ДОРАБОТКА» и другой дрейф в `BUGS.md` / `ROADMAP.md`.

Отдельными списками:

- кандидаты, которые не прошли шаг 2, и почему;
- предложения для P6.

Если источник ничего не говорит о приоритете или границах задачи — спросить
пользователя, а не додумывать.
