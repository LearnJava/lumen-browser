# Старт задачи — протокол координации Lumen

$ARGUMENTS — имя задачи (kebab-case, например `font-fallback`).
Если аргумент не передан — спроси у пользователя.

## Шаг 1 — Проверь, что уже занято

**Резервация задачи — это сама ветка `p<N>-…`**, ничего больше
(`docs/dev-roles.md` §«Reserving a task»). Никакого реестра «в работе» в
`lumen-plan.md` нет и быть не должно: этот файл — оглавление на 21 строку, и
`docs/doc-sync.md` §«What NOT to update» прямо запрещает держать в нём статус.

```bash
git pull origin main     # ОБЯЗАТЕЛЬНО до чтения STATUS — чужие ветки видны только после
git branch -a
```

!`git pull origin main 2>&1 | tail -2; git branch -a`

Если ветка `p<N>-<задача>` уже существует (локально или в `origin`) — задача
занята другой сессией. Сообщи пользователю и остановись, не дублируй работу.
Если ветка твоя и незакончена — продолжай её, а не создавай новую.

## Шаг 2 — Определи программиста и доменную зону

Роли, их домены и крейты — [docs/dev-roles.md](../../../docs/dev-roles.md)
(единственный источник; таблица в CLAUDE.md была удалена 2026-09-03 вместе с
дублирующим списком, который расходился с ней по крейтам).

Если пользователь указал «ты программист N» — проверь, что задача помечена
`[PN]` в `ROADMAP.md`. Если нет — уточни.

## Шаг 3 — Займи слот пула веткой задачи

Не создавай worktree на задачу — занимай свой постоянный слот (`target/`
остаётся тёплым, экономия 9–15 мин холодной сборки на каждую задачу):

```bash
cd "$(bash scripts/worktree-pool.sh p<N>-work p<N>-$ARGUMENTS | tail -1)"
```

Имя ветки — с обязательным префиксом разработчика `p<N>-`. Если ветка занята —
добавь суффикс `-v2` или уточни имя у пользователя. Если скрипт отказал
(в слоте незакоммиченная или невлитая работа) — не форсируй: разберись с тем,
что там лежит, это чья-то незавершённая задача.

После этого работа ведётся **только** в слоте: `.claude/worktrees/p<N>-work/`.
Собирать в слоте только профиль `dev-release`. Подробности — `docs/git-workflow.md`.

## Шаг 4 — Опубликуй ветку (это и есть резервация)

Коммита-резервации нет. Параллельная сессия видит занятость через `git branch`,
поэтому ветку надо опубликовать сразу, до первой правки кода
(`docs/git-workflow.md` §«Parallel session coordination», шаг 1.4):

```bash
git push origin p<N>-$ARGUMENTS
```

Строку-указатель в `STATUS-PN.md` **не трогай** — она остаётся на месте до
завершения задачи и удаляется только при закрытии.

## Шаг 5 — Сообщи пользователю

Выведи итог:
- Имя ветки (опубликована — задача зарезервирована) и путь слота
- Строка-указатель, с которой взята задача, и её источник
- Следующий шаг: какой файл открывать первым для реализации

Теперь можно начинать работу. Все дальнейшие коммиты — в этом worktree.
