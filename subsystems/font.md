## Gotchas

- **`fill_pixels` coverage is a frozen contract, not an implementation detail** (BUG-405 slice 3, 2026-08-11). Every text reference in the repo — CPU snapshots, graphic-test PNGs, PDF output — is a picture of this function's output, so the 4×4 sample grid, the half-open `[min_y, max_y)` edge rule and the strict `xint > x` "crossing to the right" criterion may not drift even by one grey level. The brute-force ray-cast that used to implement it (a ray cast per sample against *all* edges, `O(width · height · 16 · edges)`, 0.6 ms for one 16px glyph) was replaced by a scanline sweep with an active edge list, deliberately keeping the same intersection expressions so the output stays **byte-identical**: a sample is inside when the parity of `len - k` is odd, where `k` counts intersections `<= x`, and sorting does not change the values. The gate for any future change here is `scanline_fill_matches_bruteforce_on_real_font`, which keeps the old brute force as a reference implementation in the test module and compares bitmaps byte-for-byte across 995 rasterizations of Inter (5 sizes × 199 glyphs) — synthetic triangles are useless for this, they have no curves, no holes and no near-horizontal edges. **Slice 15 (2026-08-12) removed the per-sample walk itself** — an ablation census attributed 62 % of `fill_pixels` to it (9.03 ms of 14.47 ms over 990 Inter glyphs; 7.7 M iterations at 1.17 ns each, i.e. not a slow loop but 16 iterations per pixel). The sorted crossings of a sample row already describe the inside intervals, so coverage is now laid down as spans: `[xs[j], xs[j+1])` for every `j` with `len - j - 1` odd, plus a leading `(-inf, xs[0])` when `len` is odd (a degenerate edge set — the old code counted the left samples as inside there too). An interval boundary maps to a sample index exactly because samples sit at `x(s) = (s + 0.5)/N`, a value that is exactly representable in f32 for `N = 4`, so the old predicate `x(s) >= a` is decided in f64 as `s >= N·a - 0.5` without loss. Fully covered middles go into a per-pixel-row difference array whose prefix sum is taken once per *pixel* row instead of once per sample row, which makes a span cost O(1); the edge index array (`order`) is gone too — the edge array itself is sorted, and the row's crossing multiset does not depend on edge order. Result stays byte-identical (1.95× on the corpus, 16.1 → 11.6 µs per rasterization in a live `lenta.ru` scroll). Two more gates guard the paths the real-font gate cannot reach: `span_fill_matches_bruteforce_on_odd_crossing_rows` (a closed contour never yields an odd crossing count, so the leading-span branch needs hand-built edges — impossible to express through a glyph's `i16` points) and `span_fill_matches_bruteforce_on_random_edges` (300 pseudo-random edge sets).
- **The rasterizer's working buffers live in a thread-local `Scratch`, not in `Rasterizer`** (BUG-405 slice 17, 2026-08-12). `Rasterizer` is a `Copy` value constructed per rasterization at every call site (`renderer.rs::rasterize_and_insert`, `cpu_raster.rs`, `canvas2d.rs`), so there is nowhere on it to keep a buffer across glyphs — and a page paints hundreds of glyphs, each of which used to pay ~90 ns per allocation for its edge/coverage arrays. Every entry into `fill_pixels_in` clears everything it reads, so output cannot depend on what the previous glyph left behind; the gate for that is `raster_scratch_survives_between_glyphs` (cold thread → capacity 0, warm → non-zero, same glyph twice → no re-allocation), because no output-comparing test can see this arm at all.
- **Edges enter the active list by sample-row index, not by sorted `y`** (same slice). The scanline loop needs only *when* an edge becomes active, and that moment is an integer bounded by `height · 4`, so edges are bucketed by `first_sample_at_or_after(e.1)` with a counting sort instead of `sort_unstable_by(total_cmp)` — which also removes the per-sample-row float comparison. Order *within* one bucket is deliberately unspecified and must stay unobservable: it is safe only because the row's intersections are re-sorted by `total_cmp` (equal under it ⇒ bit-identical), so do not add a step that consumes the active list in order without re-sorting.
- **`Glyph::parse`'s intermediate buffers live in a thread-local `ParseScratch` too** (BUG-405 slice 18, 2026-08-12), for the same reason and with the same contract as the rasterizer's `Scratch` above: `endPtsOfContours`, the per-point flags and both coordinate strips used to be four one-shot `Vec`s per glyph, and on a corpus of 1905 parses (Inter, parents + composite components) those four allocations cost 0.74 µs of the 1.06 µs a parse takes — 3.3× when removed. Every entry into `parse_simple_outline_in` clears what it reads; `Glyph::parse` is **not** re-entrant (a composite's components are parsed sequentially, never nested), but the borrow is taken with `try_borrow_mut` and falls back to private buffers rather than panicking if that ever changes. Two gates, because output-comparing tests are blind to both arms: `parse_scratch_survives_between_glyphs` (the reuse itself) and `parse_scratch_is_cleared_between_glyphs` (a large glyph followed by a small one on the same thread vs. the small one on a cold thread). Note the census order of magnitude before optimising this path again: re-deriving the tables on every glyph (`has_cff` + `loca` + `glyf` + parsing `head`/`maxp`) is only 34 ns, i.e. 0.4 % of the article — the plausible-looking "look the table up once per face" fix is not where the time is.
- **A composite component with an identity matrix and a whole-number offset is assembled with integer addition, not the f32 formula** (BUG-405 slice 19, 2026-08-12). `glyph_resolved_inner` asks `integer_shift` once per component and routes it to `shift_points` (`x + dx` with a `clamp`) instead of `transform_points` (four multiplies, two adds and two `round()` per point). The result is **bit-identical by construction, not by comparison**: with `a = d = 1, b = c = 0` the formula degenerates to `x + dx`; `x` is an `i16` and `dx` is a whole number from an `i16`/`i8` (`Anchor::Offset`) or a difference of two such numbers (`Anchor::Points` under an identity matrix), so `|x| + |dx| < 2^17` and the f32 addition is exact (24-bit mantissa), `round()` over a whole value is the identity, and Rust's saturating `f32 as i16` cast is reproduced by the `clamp`. Keep the predicate narrow — any scale, rotation or fractional shift must fall through to the general formula, because the equivalence rests on exact equality, not on closeness. Two gates exist because neither the real font nor the pixel comparisons can see these arms: `shift_points_matches_general_formula_bit_for_bit` (the i16 boundaries, where a `wrapping_add` diverges from saturation) and `integer_shift_accepts_only_identity_with_whole_offset` (the predicate — Inter has no scaled component anywhere in the cmap-reachable corpus, so widening it breaks nothing else). Census caveat for the next optimisation of this path: the corpus (382 gids, 62 % composite) over-states the article twice over — a live scroll resolves 169–660 glyphs, not 1910 (the atlas answers the rest), and the composite share is a property of the **page's** font, 6.5 % on `lenta.ru` whose webfonts store Cyrillic as simple outlines.
- **Composite glyphs** are supported via `Font::glyph_resolved` (max recursion depth 8). **The resolved glyph's bbox is computed from the merged contours, not copied from the parent's header** (BUG-423): real fonts do write garbage there — «YS Text Home» (ya.ru) stores `(advance, xMin, yMin, xMax)` for its Cyrillic-from-Latin composites, i.e. `x_max < x_min`, and the rasterizer used to reject such a box, dropping the letter while its `hmtx` advance stayed correct (a hole exactly one letter wide). `Rasterizer::rasterize` applies the same fallback for a simple glyph with an inverted header (`BoundingBox::is_inverted` → `glyf::bbox_from_contours`). A point-derived box is a superset of the true one for quadratic curves, so nothing gets clipped. No bundled font has an inverted composite bbox (0 of 306/1881/589 in Golos Text/Inter/JetBrains Mono), which is why the whole test suite stayed green while real pages lost letters. Both alignment variants: `Anchor::Offset(dx, dy)` (modern, ARGS_ARE_XY_VALUES=1) and `Anchor::Points { parent, child }` (legacy TrueType pre-1996). Cyrillic uppercase А/В/Е/К/М/Н/О/Р/С/Т/Х (composite via Latin equivalents in Inter) render correctly. Always call `glyph_resolved`, not `glyph` directly.
- **Multi-size + variation-aware glyph atlas.** Glyphs rasterized at a bin-matched size (`SIZE_BINS = [8, 12, 16, 20, 24, 32, 48, 64]`), display scale = `font_size / size_bin`. Exact bin match → no scaling, crisp text. Cache key: `AtlasKey { face_id, glyph_id, size_bin, coords_hash }` where `coords_hash` is from normalized variation coords. Empty coords → hash=0 (backward-compatible with non-VF pages and snapshot tests).
- **Font fallback / matcher fully implemented** (CSS Fonts L4 §3.1+§5.2+§5.3). Per-char codepoint cascade: if primary face lacks a glyph, iterate other loaded faces; if none have it, render `.notdef`. **Phase 0 limitation:** cascade only covers already-loaded faces — CJK/emoji won't render unless explicitly listed in CSS.
- **Generic families resolve to real system faces (BUG-128, 2026-08-04).** `lumen_core::ext::generic_family_candidates(generic)` holds a per-OS ordered candidate list and `FontProvider::pick_generic_face` walks it (default trait method, so every provider gets it). On Windows: serif → Times New Roman, sans-serif → Arial, monospace → Consolas, cursive → Comic Sans MS, fantasy → Impact, system-ui → Segoe UI; macOS and Linux have their own lists ending in metric-compatible free faces (DejaVu/Liberation). **Both** render backends route every family through one helper (`Renderer::pick_family_face` / `femtovg_backend::pick_family_face`) so wgpu and femtovg never disagree on the face. `lumen_font::shared_system_index()` is a process-global `SystemFontIndex`: `FontRegistry::new()` (one per page) shares it instead of re-scanning the OS font directories per tab; `with_dirs` still builds its own for tests. Since BUG-128 ч.3 (2026-08-05) the same shared index also backs the layout measurer's lazy lookup of **concrete** families (`lumen_paint::SystemFaceSet`), so `font-family: Arial` is measured with Arial rather than with bundled Inter.
- **A generic name must never reach `pick_face` directly.** No OS installs a font whose family name is literally «serif», so `pick_face("serif", …)` returns `None` and the caller silently falls through to the bundled face — which is exactly how BUG-128 hid for so long (three call sites explicitly `continue`d on generics with a «Phase 0» comment). Use `is_generic_family` to branch, or the two `pick_family_face` helpers that already do.
- **`FontRegistry::register_from_bytes` keys on (family, weight, style, unicode_range), not just the first three (BUG-434, 2026-08-05).** A family's @font-face rules can list several `src: url(...)` subsets sharing one (weight, style) but partitioning the codepoint space via non-overlapping `unicode-range` (CSS Fonts L4 §5.1, e.g. Google Fonts serving Latin/Cyrillic/Greek as separate files). Before the fix the virtual-path key ignored the range, so the 2nd..Nth subset silently replaced the 1st — 9 `FontLoaded` events for one family left exactly 1 face in the registry. `unicode_range` is **not** stored on `FaceRecord` itself (`lumen-core` cannot depend on `lumen-font`'s `UnicodeRange` type — wrong direction in the `core → font` dependency graph) and isn't needed for selection anyway: cmap coverage is the ground truth, and Lumen already fetches every subset eagerly (no lazy per-range download). Both render backends now load every same-(weight, style, stretch) sibling of the family's primary face — wgpu's `Renderer::resolve_face_id_uncached` inserts them into `self.faces` so the existing cmap-based `pick_face_for_codepoint` scan can reach them; femtovg's `resolve_font_chain` appends their `FontId`s right after the primary in the fallback chain.
