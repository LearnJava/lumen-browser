# lumen-media-native ✅ (собственный `VideoDecoder` «lumen-native»: реестр декодеров поверх демуксеров, без FFmpeg)

- **Scope:** UX-VIDEO-NATIVE ([ADR-035](../docs/decisions/ADR-035-media-decoding-without-ffmpeg.md) п.1). `NativeVideoDecoder` реализует `lumen_core::ext::VideoDecoder`; контейнер разбирает `lumen-media-demux`, видео-/аудиопакеты декодируют бэкенды реестра. Подключён в штатной сборке: `window_mode.rs` вызывает `lumen_js::set_video_decoder(NativeVideoDecoder)` до создания JS-контекстов; с фичей шелла `ffmpeg-video` вместо него встаёт `FfmpegVideoDecoder` (dev-бэкенд).
- **Реестр** (`registry.rs`): список бэкендов кодеков. Встроенные: AV1 → `lumen-av1` (rav1d), Vorbis → `lewton` (`Registry::bundled()`). Бэкенды ОС (`COMPAT-MEDIA-OSDEC-*`) стоят перед ними (`Registry::builtin()` = ОС + встроенные): сейчас Windows — Media Foundation (см. ниже), macOS/Linux — `-MAC`/`-LINUX` (VideoToolbox / VA-API). Порядок по кодеку: аппаратный ОС → программный ОС → встроенный свободный. Реестр отвечает на `canPlayType` (`probably` — все кодеки из `codecs=` открываются, `maybe` — контейнер без `codecs`, `""` — иначе), поэтому страница не получает обещание на то, что не заиграет (ADR-034 п.2).
- **Сессия** (`session.rs`, `NativeSession`): один курсор демуксера на видео и звук. `frame_at(secs)` идёт вперёд без повторного чтения, перемотка назад/далеко вперёд — с ключевого кадра; `decode_audio_pcm` продолжает с позиции видео и отбрасывает устаревший звук. Поэтому порядок вызовов в шелле `frame_at` → `decode_audio_pcm`.
- **Путь в браузере:** `shim/video_element.js` (`startContainerLoad`, расширения `.mp4/.m4v/.webm/.ogg/.ogv`) → `__lumen_video_container_load(nid, src)` (зарегистрирован, только если установлен декодер) → `VideoGifStore::pending_container_loads` → `Lumen::tick_video_sessions` (`crates/shell/src/page_load.rs`): загрузка байтов (`fetch_video_bytes`, `RequestDestination::Media`), `decoder.open`, первый кадр, `VideoPlaybackState` в общую карту `playback`; сбой — в `load_failures` (`error` на элементе). Звук идёт в `platform::video_audio_sink::VideoPcmAudioSink` (rodio).
- **Картинка:** кадры регистрируются в рендерере под ключом `video:{nid}` (`crates/shell/src/video_tick.rs`), paint рисует у каждого `<video>` постер (если есть), а поверх него `video:{nid}` (`emit_video_content` в `crates/engine/paint/src/display_list/walk.rs`); незарегистрированный ключ прозрачен во всех трёх бэкендах. С `poster` первый кадр не регистрируется до `play()`/перемотки (HTML LS §4.8.11.7). До 2026-10-26 кадр рисовался только у `src` на `.gif` — mp4/webm играли звук поверх застывшего постера.
- **Известное ограничение:** нераспознанный кодек даёт `MEDIA_ERR_DECODE` (3), а не `SRC_NOT_SUPPORTED` (4) — развести можно типом сбоя в `load_failures`. Файл целиком читается в память до `open` (потоковой загрузки нет — как и у демуксера).
- **Windows: Media Foundation** (`mf/`, `cfg(windows)`, COMPAT-MEDIA-OSDEC-WIN, ADR-035 п.3): H.264 / HEVC (Annex B из `avcC`/`hvcC` — `annexb.rs`) и AAC-LC/HE (сырые кадры) декодируют готовые синхронные MFT ОС (`IMFTransform`), пакеты им отдаёт наш демуксер (`IMFSourceReader` не нужен — общий курсор держит видео и звук синхронными). Видео: NV12/P010 → RGBA (`yuv.rs`), звук → PCM i16. Функции `mfplat.dll` (`MFStartup`, `MFTEnumEx`, `MFCreate*`) **не линкуются**: `Api::get()` берёт их через `LoadLibraryExW(System32)`+`GetProcAddress`, иначе exe не запустится на Windows N/KN без Media Feature Pack. `mf::availability()` один раз опрашивает ОС, есть ли MFT для H.264/HEVC/AAC; реестр отвечает на `canPlayType` по факту (`avc1.PPCCLL` только Baseline/Main/High, `hvc1` Main/Main10, `mp4a.40.2/5/29`), `lumen_media_native::os_codec_status()` отдаёт оболочке те же флаги (`media_feature_pack_missing()` — N/KN), `WINDOWS_OPTIONAL_FEATURES_URI` — адрес страницы установки. `LUMEN_OS_DECODERS=0` (читается один раз при первой загрузке MF) отключает декодеры ОС — поведение N-редакции для отладки. Зависимость `windows` 0.58 (COM-интерфейсы).
- **D3D11VA** (`mf/d3d.rs`, `mf/video.rs`, COMPAT-MEDIA-OSDEC-WIN-D3D): видео сначала идёт через тот же MFT ОС, но с `MFT_MESSAGE_SET_D3D_MANAGER` (`IMFDXGIDeviceManager` над устройством D3D11 с `VIDEO_SUPPORT`, пул выходных текстур — `IMFVideoSampleAllocatorEx` из `evr.dll`, грузится как `mfplat.dll`); кадр читается `CopySubresourceRegion` → staging → `Map` и дальше идёт тем же NV12/P010 → RGBA (`yuv.rs`). Текстуры рендеру не передаются (нулевое копирование — отдельная задача). `MfVideoDecoder` = пробный аппаратный `MftDecoder` + программный запас: пока GPU не выдал первый кадр, отправленные пакеты помнятся (`probation`), и при ошибке (создание устройства, `SET_D3D_MANAGER`, `ProcessInput/Output`, чтение текстуры, 120 пакетов без кадра, `drain` без кадров) программный MFT получает их заново — воспроизведение не прерывается. После первого кадра сбой GPU уже не откатывается. Заранее аппаратный путь не включается при `LUMEN_OS_DECODERS=sw` (`mf::software_only()`) и для адаптеров из `data/d3d-blocklist.txt` (`mf/blocklist.rs`: `VendorId DeviceId|* версия-драйвера-строго-ниже|*`, версия из `CheckInterfaceSupport`). Лог — `[media] видео …` в stderr. Проверено на Intel UHD (driver 31.0.101.2140): 1080p H.264 и 320×180 расходятся с программным MFT на 0 в канале; HEVC проверен только программно (на машине нет «HEVC Video Extensions»).
- **Плашка «нужен компонент ОС»** (COMPAT-MEDIA-OSDEC-WIN-BAR): `missing_os_codec(bytes)` зовёт шелл после сбоя `VideoDecoder::open` (`page_load.rs`, `tick_video_sessions`) — демукс + `os_codec_status()` → `MissingOsCodec` (H.264 без декодера → Media Feature Pack, `ms-settings:optionalfeatures`; HEVC без декодера → «HEVC Video Extensions», поиск в Microsoft Store). Сигнал JS→оболочка не нужен: контейнер открывает сам шелл. Состояние и «Скрыть на сессию» — `crates/shell/src/media_bar.rs`, панель `#mediaBar` в `chrome.html`. `<audio>` идёт мимо `VideoDecoder` (`PlatformAudioPlayer`) и плашку не показывает.
- **macOS: VideoToolbox / AudioToolbox** (`apple/`, `cfg(target_os = "macos")`, COMPAT-MEDIA-OSDEC-MAC, ADR-035 п.3): H.264/HEVC — `VTDecompressionSession` над `CMVideoFormatDescription` с атомом `avcC`/`hvcC` (пакеты MP4 с префиксами длины идут как есть, Annex B не нужен), `kVTDecodeFrame_EnableTemporalProcessing` даёт кадры в порядке показа, обратный вызов копирует NV12/P010 в `yuv::SemiplanarFrame` (общий с `mf/`); аппаратный декодер просится `EnableHardwareAcceleratedVideoDecoder` (без «Require» — VideoToolbox сам откатывается на программный), `LUMEN_OS_DECODERS=sw` просит программный, `=0` отключает бэкенд. AAC — `AudioConverter` AAC → PCM i16, cookie = `AudioSpecificConfig` из `esds` (`esds.rs`). Фреймворки объявлены вручную в `apple/ffi.rs` (новых зависимостей нет), линкуются через `link(kind = "framework")` только на macOS. `availability()`: H.264 и AAC есть в каждой macOS, HEVC — `VTIsHardwareDecodeSupported` или Darwin ≥ 20 (программный с macOS 11). Профили `avc1`/`hvc1`/`mp4a` — общий `profile.rs`. Плашки об установке нет (`os_codec_status()` = `None`: на macOS кодеки входят в систему). **Не проверено на Mac:** код собран только как проверка типов на Windows (временный `cfg`), тесты — модуль `os_decoders_mac` в `src/tests.rs`, CI гоняет их на `macos-latest` в джобе `cross` (после пуша в `main`); живая проверка на Mac (mp4 H.264+AAC и HEVC со звуком, смена на `sw`) остаётся за владельцем.
- **Linux: GStreamer через `dlopen`** (`linux/`, `distro.rs`, `gst_caps.rs`, `reorder.rs`, `rgba.rs`, COMPAT-MEDIA-OSDEC-LINUX, ADR-035 п.3). *Почему GStreamer, а не libva + системный libavcodec:* ABI GStreamer 1.x стабилен, а `AVCodecContext`/`AVFrame` у FFmpeg меняют раскладку между мажорными версиями (смещение `pts` — `subsystems/media-ffmpeg.md`), вызывать `libavcodec` вслепую = гадать смещения; VA-API получается сам (`decodebin` выбирает `vah264dec`/`vah265dec`, в старых версиях `vaapih264dec`, по рангу выше `avdec_h264`), а свой разбор слайсов и DPB поверх libva без железа непроверяем, и ошибка там — падение драйвера. *Как устроено:* `linux/ffi.rs` — таблица функций GStreamer/GLib через `dlsym` (макрос `gst_api!`), сборка и запуск не зависят от наличия библиотек; `linux/pipeline.rs` — `appsrc name=src ! decodebin ! videoconvert ! video/x-raw,format=RGBA ! appsink` (звук: `audioconvert ! audioresample ! S16LE` с частотой и каналами дорожки); пакеты MP4 идут в `appsrc` как есть (`avc`/`hvc1`/`raw` + `codec_data` = `avcC`/`hvcC`/`AudioSpecificConfig`), штампов времени в `GstBuffer` не пишем, поэтому метки показа восстанавливает `reorder::PtsQueue` (кадр не выходит раньше, чем декодер получил все пакеты, показываемые до него). `linux::availability()` один раз инициализирует GStreamer и спрашивает реестр (`gst_element_factory_list_get_elements` + `can_sink_any_caps`) про H.264/HEVC/AAC; по нему отвечает `canPlayType`. `LUMEN_OS_DECODERS=0` отключает бэкенд, `=sw` убирает из выбора аппаратные декодеры (`va*`, `nv*`, `v4l2*`, `msdk*`, `qsv*` — ранг 0). *Нет кодеков:* `canPlayType` = `""`, `missing_os_codec` → `MissingOsCodec::LinuxCodecs(distro::current())`, шелл (`media_bar.rs`) показывает команду (Debian/Ubuntu — apt, Fedora — dnf + RPM Fusion, openSUSE — zypper + Packman, Arch — pacman, Flatpak — расширение `ffmpeg-full`) и кнопку «Скопировать команду» (буфер обмена). *Проверка:* модуль тестов `os_decoders_linux` (`tests.rs`); CI ubuntu ставит `gstreamer1.0-plugins-base`/`gstreamer1.0-libav`, `LUMEN_EXPECT_GSTREAMER=1` превращает отсутствие декодеров в ошибку. Аппаратный путь VA-API на железе не проверялся.
- **Не сделано (отдельные задачи):** кадры GPU без копирования в рендер. HEVC без расширения «HEVC Video Extensions» даёт `canPlayType` `""`.
- **Фикстуры:** `tests/data/av1-vorbis.webm` (ffmpeg 9: libaom-av1 + libvorbis), `tests/data/h264-aac.mp4` (320×180, 25 кадр/с, 2 с, B-кадры, AAC-LC стерео 44,1 кГц). Тесты — `src/tests.rs` (модуль `os_decoders` — `cfg(windows)`, при отсутствии декодера у машины пропускает проверки воспроизведения; отрицательные тесты идут на `Registry::bundled()` и не зависят от ОС).
