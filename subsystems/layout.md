# lumen-layout 🟡 (block + inline-flow + replaced + word-wrap + cascade)

- **Done:** `LayoutBox` tree, **specificity-based style cascade with !important**: for each rule the maximum specificity among its complex selectors is taken, all matched declarations sorted by `(important, specificity, rule_order, decl_index)` and applied in ascending order. `important` is first in key — `true > false` places !important-declarations at end, and they win over normal even with lower specificity (CSS Cascade L4 §8.1). On tie — later declared wins. **Matching complex selector — right-to-left with back-tracking** (`matches_chain`): for descendant and later-sibling combinators ALL candidates (ancestors / earlier-siblings) are iterated and the suffix is recursively verified — this correctly solves pathological cases like `.x + a ~ span` with multiple `a`-siblings without class `.x`. For child / next-sibling — single candidate, no back-tracking. Combinators: descendant / child / next-sibling / later-sibling. **Pseudo-classes:** all CSS3 structural and functional. **CSS Selectors L4 `:placeholder-shown`** (§15.1) — matcher `matches_placeholder_shown(doc, node)`. **CSS Selectors L4 form-state pseudo (§14.2 / §15.4 / §15.5):** `:required` / `:optional`, `:read-only` / `:read-write`, `:disabled` / `:enabled` — all pure attribute-based. **CSS Selectors L4 UI-state pseudo (§10.1 / §10.2 / §10.4):** `:checked`, `:indeterminate`, `:default` — pure DOM-based. **`:lang(...)` matcher** — RFC 4647 §3.3.1 basic filtering. **`:link` / `:visited` / `:any-link` matchers** — pure DOM-based, `:visited` always `false` (privacy-safe). **`:target` matcher** (`matches_target`) — case-sensitive id-attribute match against `Document::target()`. **`:target-within` matcher** (`matches_target_within`) — separate matcher via `any_descendant`. **`:fullscreen` / `:modal` / `:popover-open` matchers** — always `false` in Phase 0. **`:state(name)` matcher** — reads `data-lumen-state-<name>` sentinel attribute (`ElementInternals.states` reflection, same bridge pattern as `:fullscreen`/`:modal`). **`:current` / `:past` / `:future` matchers** — always `false` in Phase 0. **`:dir(...)` matcher** (`matches_dir`) — walking up parents via `element_directionality`. **CSS4 `:has(rs-list)`** via `matches_relative`. Attribute selectors: all operators, with ASCII case-insensitive flag support. Inherited properties: `color`, `font-size`, `line-height`, `font-style`, `font-weight`, `font-family`, `text-transform`, `text-align`, `text-decoration-line`. **`FontStyle`** via `font-style` property + UA stylesheet for semantic tags. **`FontWeight`** with keyword and numeric scale support. **`FontStretch`** (CSS Fonts L4 §2.5) — stored in tenths of percent, 9 keywords, inherited. `text_rendering_eq` compares font_style, font_weight, font_variant and font_stretch. **`font-family`** — `Vec<String>` prioritized list. **`font-variation-settings`** (CSS Fonts L4 §7) — `Vec<FontVariationSetting { tag: [u8;4], value: f32 }>`, inherited; `normal` → empty Vec; parser handles quoted 4-char tag + number, multiple comma-separated axes; renderer normalizes via fvar+avar. **`font-feature-settings`** (CSS Fonts L3 §6) — `Vec<FontFeatureSetting { tag: [u8;4], value: u32 }>`, inherited; consumed by lumen-font `Shaper::with_features` via `DrawText.font_features`. **`TextTransform`** — applied to `InlineSegment.text` at assembly. **`text-indent`** — first-line indent, inherited. **`white-space`** (Normal / Nowrap / Pre / PreWrap / PreLine / BreakSpaces) + L4 longhand **`white-space-collapse`**. **`opacity`** — CSS Color L3 §3.2, not inherited. **`outline`** — CSS Basic UI L4 §5. **`visibility`** — CSS Display L3 §4, **inherited**. **`overflow` / `overflow-x` / `overflow-y`** — CSS Overflow L3. **`text-overflow`** — CSS UI L4 §10.1. **`cursor`** — CSS UI L4 §8.1, inherited, full set of 36 standard keywords. **`box-shadow`** — `Vec<BoxShadow>`, parsing with balanced `()`. **`text-shadow`** — `Vec<TextShadow>`, **inherited**. **`border-radius`** — 4 fields, shorthand with 1-4 tokens. **`letter-spacing`** — added to word-width and word-boundary; `text_rendering_eq` accounts for letter_spacing. **`word-spacing`** — added only between words; word width unchanged. Properties with parsing: `display` (block/inline/none), `color` (full CSS3 named colors — 147 colors + `rebeccapurple` from CSS4 §6.1 + `transparent`; hex `#RGB`/`#RRGGBB`/`#RGBA`/`#RRGGBBAA` + `rgb()` / `rgba()` / `hsl()` / `hsla()` with commas or whitespace, slash-alpha modern syntax, percentages for channels, hue in `deg`/`turn`/`rad`/`grad` (CSS Color L4 §9)), `background-color`, `font-size`, `line-height`, `margin` (+ 4 sides), `padding` (+ 4 sides), `text-align` (left/center/right), **`text-decoration` / `text-decoration-line`**, **`width` / `height` (px/em/rem; `auto` = not set)**. ## Gotchas

- **Two families of text-width helpers exist and they must not drift (BUG-128, 2026-08-04).** `measure_text_w` ignores `font-family` and always measures with the measurer's fallback face; `measure_text_w_families` / `measure_text_w_varied` pass the CSS family list through. Line wrapping used the family-aware pair while min/max-content sizing, the list-marker width and the inter-word space width used the family-blind one — invisible while every family resolved to bundled Inter, but as soon as generics resolved to real system faces a shrink-to-fit box was sized with Inter and filled with Times/Consolas. All of those call sites now pass `seg.style.font_family`. When adding a new measurement site, reach for the `_families` variant unless there is genuinely no style in scope.

- **One `NodeId` can own several `LayoutBox`es, so the JS snapshot collectors are first-wins, not last-wins (BUG-382, 2026-07-29).** An element with inline content gets an anonymous run/line box for that content, and the box tree keeps the *element's* `NodeId` on it — `<div style="width:50px;height:20px">x</div>` yields two boxes with the same id, 50×20 and 50×19.2. `collect_layout_rects` / `collect_computed_styles` (both in `lib.rs`, both consumed by `getBoundingClientRect`/`getComputedStyle` via the shell and `lumen-driver`) used to `insert`, so the *inner* box won and JS was told the element is 19.2px tall with `width: auto`. They now `entry().or_insert(…)`: the recursion visits the principal box before its descendants, so the element's own border box wins. Consequence to keep in mind — for an inline element fragmented across lines this answers with the *first* fragment; CSSOM's union-of-fragments rectangle is not implemented. Any new per-node snapshot collector must make the same choice explicitly.

- **Synthesized small caps are a segment split, not a paint-time effect (`caps_synthesis`, `box_tree.rs`, 2026-07-29).** `font-variant-caps` cannot be rendered through the OpenType features it maps to: the bundled Inter has no `smcp`/`c2sc`/`pcap`/`c2pc` at all, and Lumen has three text paths (native femtovg, wgpu, CPU raster) of which the native femtovg one shapes text itself and ignores `DrawText.font_features` entirely (class BUG-109). So the synthesis runs *before* everything: `wrap_inline_run` (and `one_line_fallback`) split each `InlineSegment` into runs of `Plain`/`Capital` characters, uppercase the capital ones and give them a style with `font_size × SMALL_CAPS_SCALE`. Everything downstream — measurement, line breaking, fragment emission, painting — then sees ordinary text of two different sizes and needs no knowledge of the property. Two consequences worth knowing: (1) a smaller `font_size` on a fragment does **not** shrink the line box (line height comes from the block's own style, not per-fragment), but it *does* move the fragment — `apply_inline_vertical_align` centres a fragment's content area by half-leading instead of aligning baselines, so the capital run gets an explicit `vertical-align: <length>` correction; without it the small caps float above the baseline of the surrounding text. (2) the split cuts inside words (`Hello` → `H` + `ELLO`) and `wrap_inline_run` treats a segment boundary as a break opportunity, so `caps_synthesis` also returns a per-segment «no break before» flag — dropping it lets a narrow container tear a word in half. Do not add `smcp`/`c2sc` to `text_font_features()` “for fonts that have them”: the text reaching the shaper is already uppercased, so `c2sc` would shrink it a second time.

- **The cascade's `CascadeIndex` is cached per thread and keyed by `Stylesheet::revision`, not by the sheet's address (BUG-341 S21, 2026-07-28).** Building it walks every rule in the sheet several times over (top-level `RuleIndex`, one index per `@layer`/`@media`/`@supports` block, the `@media`/`@supports` activity evaluation, two sheet-wide predicate scans) — 0.14-0.22 ms on `chrome.html`. It used to be keyed by the sheet's **address**, which the allocator recycles the instant a sheet is freed, so `invalidate_rule_idx_cache()` ran at the top of every layout pass and inside every worker's `StyleEnvSnapshot::install` — reducing a cross-pass cache to a within-pass one: one rebuild per incremental cycle (7-19 % of it) and **33** per full pass across the worker pool. A `StylesheetRevision` is never recycled, so the invalidation is gone entirely. Two things to keep in mind when touching this: the cache holds **two** slots because a frame lays out chrome and page on one thread and a single slot would make them evict each other every frame; and `CascadeIndexStats` is thread-local *with a drain* — the rayon fan-out in `build_box` folds each worker's tally into the parent, exactly as `BoxBuildStats` does, because a process-wide counter is accurate but useless as a gate (any concurrent test would redden "this pass rebuilt nothing"). The gates are by counter, both arms, in `style.rs` (`bug341_s21_*`) and `main.rs` (`bug341_s21_interaction_cycles_do_not_reindex_the_stylesheet`): a silently rebuilt index yields byte-identical styles.
- **Pseudo-element cascades used to run per element for features almost nothing uses (BUG-341 S10, 2026-07-27).** Two of them, and neither was visible in any differential test because doing the work and discarding the result gives identical output. (1) `apply_webkit_scrollbar_pseudos` ran three full `::-webkit-scrollbar*` cascades on **every** element — CC-CSS-1 translates those onto the inherited `scrollbar-width`/`scrollbar-color`, and `assets/chrome/chrome.html` writes the rules *bare*, so all three matched everywhere: 55% of `compute_style` on the CC-12 fixture. (2) `counters::walk` probed `::before`/`::after` on every node — including nodes whose style was reused wholesale — solely to keep the CSS Generated Content L3 §3.2 quote-nesting counter continuous: 79% of the cascade stage on `CC12_KEY`. Now gated by node-independent per-sheet facts precomputed in `CascadeIndex` (`has_webkit_scrollbar_rules`, `has_quote_content` — the latter deliberately over-approximating, since `var()`/`attr()` can smuggle `open-quote` in from anywhere), and (S11, [ADR-022](../docs/decisions/ADR-022-webkit-scrollbar-scroll-containers-only.md)) by `element_can_have_scrollbar`: the translation runs only for elements whose `overflow` is `scroll`/`auto`, plus the root and `<body>`. `compute_pseudo_element_style` also matches **before** building the pseudo's starting style (`pseudo_inherited_style`) — the common outcome is "nothing matched", which used to build a 302-field style and throw it away. Keep the counter gates (`style::tests::webkit_scrollbar_cascade_*`, `pseudo_base_not_built_when_no_rule_matches`): a regression here is invisible in output and hides inside machine noise in wall-clock.
- **`::-webkit-scrollbar*` does not inherit; the properties it writes to do (ADR-022).** The translation targets the standard, *inherited* `scrollbar-width`/`scrollbar-color`, so whatever it computes for an element still propagates to that element's descendants by ordinary cascade inheritance — a bare `::-webkit-scrollbar { … }` matches `<body>` and thereby reaches the whole page, which is why Lumen's chrome renders identically after S11. What changed is the *source*: only a scroll container (or the root/`<body>`) can be styled by the pseudo in the first place, so a rule on a non-scrollable element no longer leaks into scrollable descendants. When touching this, keep `element_can_have_scrollbar` in step with paint's `emit_scrollbars` condition — they must agree on what "can show a scrollbar" means.
- **`ComputedStyle` construction is not where the cascade's time goes (BUG-341 S10).** Measured on the incremental path: the 302-field literal plus ~30 heap clones from the parent is **3%** of `compute_style` (0.66 ms of 21.7 ms per CC-12 hover pass). Splitting the struct into inherited/non-inherited halves, or `Arc`-ing the remaining heap fields the way S9 did for `custom_props`, would chase that 3%. Profile before assuming otherwise — and profile the *incremental* path, not `layout_measured_hyp`.

- **`layout_mutation_incremental_restyle` (BUG-341 S5/S6, `box_tree.rs`) is the incremental-cascade-aware sibling of `layout_mutation_incremental`.** Same body as `layout_streaming_incremental` (plain `build_box` + `graft_geometry` + `lay_out_incremental` + the post-layout passes) except the cascade call is `counters::incremental_precompute_counters(..., &delta)` instead of a full `precompute_counters` — reuses S3's mechanism instead of recomputing every node's `ComputedStyle`. Deliberately does **not** use S4's box-build skip (`incremental_build_box`) — S4 measured that in isolation as a net loss (`index_by_node`'s whole-tree hash index outweighs the savings), and S5/S6 didn't re-test it combined. Callers must only pass `dom_content_stable: true` when nothing but interactive state (`:hover`/`:focus`/`:active`) changed since `prev` — `false` whenever `dirty_roots` includes any DOM-content-mutation contribution (attribute/class/structure), even if that contribution ends up empty in a given cycle. See `Lumen::relayout_chrome_host` (`crates/shell/src/main.rs`) for the one current caller: S5's eligibility guard was whole-`ChromeModel`-equality (a coarse stand-in for a real diff); S6 replaced it with `lumen_chrome::bind_model_tracked`'s real per-cycle touched-node set (unioned into `dirty_roots` via `restyle_root_set_for_node_change` alongside the interactive-state root-sets) — the incremental path is now eligible whenever a previous pristine tree exists and viewport/Forced-Colors are stable, regardless of whether `bind_model` changed content that cycle. 4 differential tests in `incremental.rs` (`mutation_incremental_restyle_*`, S5's hover-transition/unchanged-state pair plus S6's dom-class-change/structural-change pair covering `restyle_root_set_for_node_change` at the full-pipeline level, not just the cascade alone). Not wired into the page pipeline (JS DOM mutations, `crates/js/src/v8_runtime.rs`) — no mutation-diff mechanism exists yet there to derive a safe `dirty_roots` for arbitrary content changes; that's a separate, still-open design (see BUG-341 "S6" "Not attempted").
- **`StateRestyleIndex` / `restyle_state_index` (BUG-341 S14, `style.rs`) — per-node narrowing of the flipped ancestor chain.** `:hover`/`:active`/`:focus-within` match the target *and every ancestor of it* (CSS Selectors L4 §4.3/§4.4.2/§4.5), so `restyle_root_set_for_state_change` treats a "nothing was hovered → deep node is hovered" transition as flipping the whole chain up to the document node — and a dirty root there forces a full re-cascade of the document. S14 filters that chain: a flip on node `N` is observable only through a compound that depends on dynamic state **and matches `N`** (`compound_could_match_after_state_flip` — every part must match structurally, with the dynamic-state pseudo-classes and any pseudo-element treated as "possible", since their value is exactly the thing in question). Everything such a compound reaches — its own subject, plus descendants via `N:hover X` — is inside `N`'s own subtree, so a node no state-dependent compound can match contributes nothing and is dropped. Soundness rests on the fact that every nested form the engine looks through for dynamic state (`:not()`/`:is()`/`:where()`/`:host()`/`:nth-child(… of …)`) evaluates its inner selector against the *same* node as the carrying compound; `:has()` is the exception (state on one node, subject on a distant ancestor) and, together with the presence of any shadow root, sets `StateRestyleIndex::conservative`, which restores the pre-S14 behaviour exactly. Over-approximation is one-directional — a compound whose state hides in a nested list (`:is(.tab:hover, .x)`) is treated as matching anything, costing narrowing but never correctness. Measured on the CC-12 chrome fixture: `precompute_counters` 9-12 → 0.41 ms, `CC12_HOVER` ≈3.7× faster by min. `restyle_state_index` replaced the S7 `restyle_state_needs_fanout` and folds both computations into the same single scan of the sheet.
- **`restyle_state_index().needs_fanout()`/`restyle_root_set_for_state_change` (BUG-341 S7 part 3, `style.rs`) — hover fan-out narrowing.** `restyle_root_set_for_state_change` (S3) took a `needs_fanout: bool` parameter (S14 moved it into `StateRestyleIndex`): `true` keeps the S3 conservative behaviour (each flipped node widens to its *parent's* whole subtree, needed for `N:hover + X`/`N:hover ~ X`); `false` narrows to just the flipped node itself, sound whenever no selector anywhere needs the wider reach. `restyle_state_index(doc, sheet)` computes this once per interactive-state transition by scanning every selector in `sheet` (including nested `@media`/`@layer`/`@supports`/`@scope`/`@starting-style`/`@container` blocks) for a compound depending on `:hover`/`:focus`/`:active`/`:focus-within`/`:focus-visible` (including inside `:not()`/`:is()`/`:where()`/`:host()`/`:nth-child(... of ...)`) followed anywhere toward the subject by a sibling combinator — a descendant combinator or subject position needs no widening (already inside the flipped node's own subtree). `:has()` containing a dynamic-state pseudo, or any shadow root present in the document, always forces `true` (both directions this v1 doesn't attempt to model — see BUG-349, fixed 2026-08-06, for the related, separate `:has()` gap this same shape had in `restyle_root_set_for_node_change`). `assets/chrome/chrome.html` has zero selectors needing the wider fanout, so real chrome hover/focus/active restyles narrow for real. Measured (A/B on the CC-12 `#sbTabs` sibling-tab-hover fixture, 6 tabs): no statistically significant wall-clock difference vs. the pre-narrowing widen-to-parent behaviour — the fixture's shared-parent subtree and the individually-changed-node set aren't different enough in size to move the needle past this machine's noise floor. Expected to matter on documents with wider `:hover`-styled sibling structures (a long list, one shared parent) — no such fixture exists yet to confirm.
- **`<picture>` / `<img srcset>` integrated in layout, but DPR=1.0 — Phase 0 stub.** `lumen-layout::box_tree::resolve_image_source` calls `pick_picture_source` / `pick_img_source` with `PictureParams { dpr: 1.0, supported_types: None }`. Density candidates (`srcset="… 2x"`) are **never selected** — picker always picks `1x`. Real DPR lives in `Renderer.scale_factor` and is not yet passed to layout. When relayout-on-resize lands, extend `resolve_image_source` with `dpr: f32` and pass it into `PictureParams` — picker API already supports it. Intrinsic dimensions from `<source>` are applied as presentational hints after CSS cascade (only into empty `style.width`/`style.height`). **`<source>` and `<track>` are `display: none`** in the UA stylesheet — previously they generated empty `BoxKind::Block` nodes.

- **`color(--name c1 c2 c3)` (CSS Color L5 §4, p4-color-profile 2026-07-15) is deliberately stateless.** `parse_css_color_fn` recognizes a dashed-ident first token and passes the channels through as already-sRGB — it does **not** look up `Stylesheet.color_profiles` (`ColorProfileRule`, css-parser) to validate the name was actually declared by `@color-profile`, and does not perform a real ICC transform. This mirrors the `@font-palette-values` deferral pattern but is even lighter: no post-cascade resolution pass exists for this feature, because the fallback value doesn't depend on stylesheet context. Test 142 is a `KNOWN_DEBTOR` (BUG-282, 10.16%) — Edge doesn't support `@color-profile`/custom-ident `color()` at all, so its reference screenshot is blank.
- **`@function` call resolution (CSS Functions and Mixins L1, p4-css-function 2026-07-15) runs outside `apply_declaration`, not inside it.** `compute_style`'s main declaration-application loop (`style.rs`, right after the existing `attr()` expansion) pre-resolves `var(` against `style.custom_props` and then scans for `--name(<args>)` call sites (`expand_custom_functions`) *before* handing the declaration to `apply_declaration` — this is why a call reached through a custom-property chain (`--gap: --double(5px); width: var(--gap);`) resolves correctly: the `var()` pre-pass makes the indirect call text visible to the scanner. Threading `Stylesheet.function_rules` into `apply_declaration` itself (touching its ~9 call sites, several of which have no `Stylesheet` at all — e.g. `compute_style_from_declarations`) was avoided as out of scope for the first slice. Consequence: this expansion only runs for the main cascade pass — the `color-scheme` pre-pass and SVG presentational-hints pass do not see custom function calls. An unresolved call (unknown name, missing required argument, or recursion past `FUNCTION_CALL_MAX_DEPTH`) makes the declaration invalid-at-computed-value-time (returns `None`, same treatment as an unresolvable `var()`) rather than panicking or falling back to `0`. Deferred: `returns` type-checking (stored raw, unchecked), conditional group rules inside the function body (`@media`/`@container` — `parse_declaration_block`'s recovery logic doesn't track nested-brace depth, so a body containing one would truncate early), named/keyword arguments. Test 143 exercises: direct call, zero-arg default, `calc()` in `result:`, chain-through-custom-property, local `--x:` decl feeding `result:`.
- **`::-webkit-scrollbar`/`-thumb`/`-track` translated onto `scrollbar-width`/`scrollbar-color` (CC-CSS-1, p1-css-chrome, 2026-07-24).** No new `css-parser` recognition needed — `PseudoElementKind::Unknown` already parses and case-insensitively matches any pseudo-element name, including these three. `apply_webkit_scrollbar_pseudos()` (`style.rs`, called at the end of `compute_style`) invokes the existing `compute_pseudo_element_style()` three times (same mechanism as `::before`/`::after`/`::marker`) and translates the result: `::-webkit-scrollbar{width}` buckets to `ScrollbarWidth::Thin` (≤9px) or `::Auto` (>9px) — CSS Scrollbars 1 §2 has no numeric keyword; `-thumb`/`-track{background}` become `scrollbar_color`'s `(thumb, track)` pair **only when both resolve** (no honest per-side default to graft the missing side onto at this layer — UA defaults live one level down in `paint::display_list`). `-webkit-font-smoothing` needed zero code: it already falls through `apply_declaration`'s unconditional catch-all like any unrecognized property. 4 unit tests (`style::tests::webkit_scrollbar_*`, `webkit_font_smoothing_is_parsed_and_ignored`).
- **`ComputedStyle.custom_props` is shared copy-on-write, and the cascade cache holds `Arc<ComputedStyle>` (BUG-341 S9, `style.rs` + `counters.rs`).** Two representation changes with one invariant between them: **nothing may mutate a style through a shared handle.** (1) `CustomProps` wraps `Arc<HashMap<String, String>>` — CSS Variables L1 inherits every custom property, so `compute_style` used to copy the parent's whole map into every node (measured 3.7–4.7 µs/node with chrome's 30 properties vs 0.31–0.46 µs with none). Reads go through `Deref`; the three write sites (the custom-property declaration pass, `apply_property_initial_values`, and the `inherits: false` `retain`) go through `make_mut`, so only nodes that actually declare a `--name` fork. Calling `make_mut` unconditionally — e.g. "just to be able to write" — silently reintroduces the per-node copy this type exists to remove, which is why the `retain` is additionally guarded by a "would this drop a key?" scan. `CustomProps::default()` is a process-wide singleton (property-free documents allocate one map total), and `PartialEq` short-circuits on `Arc::ptr_eq` explicitly rather than relying on `Arc`'s unspecified pointer specialisation — that fast path is what makes `graft_geometry`'s per-box `ComputedStyle` comparison cheap. (2) `CounterMap::styles` / `RestyleDelta::prev_styles` / `Lumen::{chrome,page}_prev_cascade_styles` are `HashMap<NodeId, Arc<ComputedStyle>>`, turning the incremental cascade's reuse path (every node outside the dirty root-set), the cache insert, and the per-cycle snapshot into refcount bumps. (`LayoutBox.style` followed in S12 — see the next bullet.) Gated by *identity*, not output: `style::tests::custom_props_{shared_with_parent_when_child_declares_none,copy_on_write_when_child_declares_one,empty_map_is_a_shared_singleton,eq_compares_contents_when_not_shared}` and `incremental::tests::incr_cascade_reuse_hands_back_the_same_style_allocation` compare pointers — a version that deep-copies passes every differential test and is merely slow, which is exactly how `graft_geometry` stayed inert for five slices (see BUG-341 "S8"/"S9").
- **`LayoutBox.style` is `Arc<ComputedStyle>`, copy-on-write (BUG-341 S12, `box_tree.rs`).** The same invariant as S9's `custom_props`: nothing may mutate a style through a shared handle. Reads are unchanged (`Arc` derefs, so `b.style.field` and `&b.style` still work); the copies that mattered were three per box per frame — `build_box` copying the entry out of `CounterMap::styles`, `lay_out_inner`'s `let s = b.style.clone()` snapshot (taken purely to dodge the borrow checker; measured at 1.2 ms of `lay_out`'s 3.7 ms on the CC-12 hover fixture), and the whole-tree `clone()` the incremental pipeline does once per frame to persist `prev`. All three are now refcount bumps. The passes that write a *used* value back into a box's style — flex item stretch (both axes), `font-size-adjust`, container-query restyle, `propagate_canvas_background`, the `::first-line` in-place restyle, the table cell's temporary `width` swap — go through `Arc::make_mut`, so they fork exactly the boxes they touch and the cascade cache (shared with the previous frame's tree) never sees a used value. **`apply_font_size_adjust` must keep its `FontSizeAdjust::None` test at the call site**, not only inside `apply_font_size_adjust_to_style`: reaching for `make_mut` in order to call it deep-copies the shared style on every box in the document for a property almost nothing sets. `graft_geometry` short-circuits its style compare on `Arc::ptr_eq` (both trees hold the same allocation whenever the incremental cascade reused a node), with the structural `==` still behind it so a node re-cascaded to an equal value stays reusable. Gated by identity: `incremental::tests::{built_boxes_share_the_cascade_cache_style_allocation,used_value_writeback_does_not_leak_into_the_cascade_cache}`. Still owned, and still deep-copied per frame: `InlineSegment::style`/`InlineFrag::style`, and the page-side transition scheduler's `collect_box_styles`/`prev_styles` snapshot.
- **`graft_geometry` compares against the cascade, not against the previous tree's styles (BUG-341 S13, `incremental.rs`).** `prev` is a *laid-out* tree and layout writes used values back into `LayoutBox::style` — `lay_out_flex` overwrites every flex item's `width`/`height`/`box_sizing` with the resolved used size, the post-layout passes rewrite more — so a plain `new.style == prev.style` answers "has this box been through layout since?", not "did the author's style change?". On the flexbox-built chrome document that rejected **81 of 318 boxes every interaction, all 81 differing only in those used-value fields**, and since a graft reject propagates to every ancestor it dragged 41 more with it. `graft_geometry_with_cascade` therefore takes the `CounterMap::styles` map of the pass that produced `prev` (`RestyleDelta::prev_styles` at the one production call site, `layout_mutation_incremental_restyle`) and compares against that unpolluted result: `Arc::ptr_eq` with `prev`, then `ptr_eq`/structural `==` against the cascade entry (the structural clause is not optional — a wide restyle like CC-12's `SIDEBAR`/`None` hover toggle re-cascades most of the document to the values it already had, and without it those boxes stay rejected), then the old fallback, and finally — only for boxes whose node has **no** cascade entry at all, i.e. the anonymous wrappers a flex container generates around inline content, keyed by a text node the cascade never visits — equality with `width`/`height`/`box_sizing` discounted, which is sound there because no author rule can put those on such a box. That last probe copies a style, so it must stay last. A reused subtree keeps its **own** freshly-cascaded style: only `rect` and `kind` come from `prev` (`kind` must, it holds layout output paint reads back; adopting the style would pin the pollution into the live tree and mis-size the box if it later went dirty). Result: 318/318 boxes reused on a chrome hover flip, `lay_out` 2.44 → 0.00 ms. Gated by count, not output — `bug341_s13_hover_flip_reuses_boxes_the_layout_pass_only_wrote_used_values_into` (lumen-shell) plus `graft_reuses_a_box_whose_prev_style_only_carries_used_values` / `graft_still_rejects_a_box_whose_cascade_style_changed` / `graft_stats_partition_the_visited_set`; the second of those is the counterweight without which the fix would degrade into "styles never matter" and no geometry-comparing test would notice.
- **Never gate work inside `build_box` on a thread-local (BUG-341 S15, `box_tree.rs`).** `build_box` fans any flex/grid/table container with `RAYON_MIN_FLEX_CHILDREN` (8) or more children out over rayon workers (ADR-016 M4.1), and a rayon worker's thread-locals start at their **defaults** — that is what `StyleEnvSnapshot::capture`/`install` exists to repair for interactive state and shadow sheets. S4's incremental box-build reuse was gated on the `INCREMENTAL_BOX_BUILD` thread-local read *inside* `build_box_or_reuse`, so it was silently off for every child of such a container; `assets/chrome/chrome.html` is built entirely out of them, so the mechanism reused essentially nothing. The gate is now the `prev_index: Option<&incremental::ReuseIndex>` parameter threaded down by reference, and the flag is consulted exactly once, at `incremental_build_box`, which decides whether an index exists at all. The same trap hit the *instrumentation*: `BoxBuildStats` is a thread-local tally, so the parallel branch drains each worker's tally and folds it into the thread running the parent container (exact even when rayon work-steals a closure onto the calling thread — what it takes from that thread comes straight back in the fold). Before S15 the counters reported "7 boxes built" for a 318-box document. Prefer a parameter over a thread-local anywhere below `build_box`; if you must use one, add it to `StyleEnvSnapshot`.
- **Box-build reuse is licensed by `CounterMap::clean_subtrees`, which needs `RestyleDelta::content_dirty` (BUG-341 S4/S15/S16).** `build_box_or_reuse` clones a whole `LayoutBox` subtree out of the previous tree instead of rebuilding it. Style equality alone is *not* enough to license that: `build_box` reads attribute values, text-node data and DOM structure, none of which a `ComputedStyle` comparison can see. `ContentDirty` is how a mutation source declares what it knows about that second half — `Untracked` (no record: reuse nothing), `Nothing` (pure interactive-state cycle), or `Nodes(&set)` (a **complete** per-node record; a subtree is reusable iff it contains none of them). S16 replaced S4's document-wide boolean, under which one changed omnibox character disabled reuse for all 318 chrome boxes. **`Nodes` is a promise, and a broken one produces a stale box — visible corruption, not a slow frame.** Only `lumen_chrome::bind_model_tracked` makes it today, and only because every raw `Document` mutator in `crates/chrome/src/model.rs` is wrapped and a source-level test (`every_dom_mutation_in_model_rs_goes_through_a_tracked_primitive`) refuses new un-wrapped calls. The page-side path (`DomTouched`, `v8_runtime.rs`) reports selector-relevant nodes only and has an `unattributed` escape hatch, so it stays `Untracked`. Correctness gate: `box_build_text_mutation_reuses_everything_but_the_mutated_chain` (a text-only mutation must not go stale *and* must still let siblings be cloned) plus `box_build_node_change_disables_reuse_conservatively` for the `Untracked` contract.
- **`NodeRestyleIndex` / `restyle_node_index` (BUG-341 S17, `style.rs`) — per-node narrowing of the DOM-mutation root-set.** S14's argument, applied to attribute writes instead of interactive-state flips. `restyle_root_set_for_node_change` used to map every changed node to its **parent** and re-cascade that parent's whole subtree: class/attribute selectors don't match ancestors, so the node's own subtree already covers it and every descendant rule (`node X`), but a *sibling* combinator (`node + X`, `node ~ X`) reaches outside it and the parent's subtree is the smallest thing containing both. The function now takes `(NodeId, NodeChange)` pairs — `NodeChange::Attr(name)` or `NodeChange::Unattributed` — plus a `NodeRestyleIndex` built by one scan of the sheet (`restyle_node_index`, the same shape as `restyle_state_index`), which collects every compound from which a sibling combinator is reachable and answers per node and per attribute whether any of them *could* match it once the parts keyed on that attribute are treated as unknown (`compound_could_match_after_attr_change`: everything else must match structurally; pseudo-elements and **all** pseudo-classes count as possible, since a pseudo-class may read the mutated attribute — `:checked` reads `checked`, `:placeholder-shown` reads `value`). If none can, the write is unobservable outside the node's subtree and the root-set is the node itself. `conservative` (pre-S17 behaviour verbatim — widen to the parent) is forced by `:nth-child(… of S)`/`:nth-last-child(… of S)` (sibling reach with no combinator to see it) and by any shadow root (S7's unscanned-shadow-sheet carve-out). **`:has()` anywhere in the sheet is handled separately, by `NodeRestyleIndex::has_has_dependency` (BUG-349, fixed 2026-08-06):** a `:has()`-affected ancestor can sit arbitrarily far above the mutated node, not just one level up at its parent, so `restyle_root_set_for_node_change` widens to `doc.root()` — the whole document — instead of the parent-only widening `conservative` triggers on its own. Before this fix the function widened `:has()` sheets to the parent (BUG-348's original, insufficient direction), which left an ancestor's `ComputedStyle` stale whenever it was more than one level above the mutated node — undetected because no fixture (chrome or graphic test) uses `:has()`. `:indeterminate` on a radio group and `:default` on a form's submit button read other elements' `name`/`checked`/`type` across the whole form; that is the same family of pre-existing gap, documented on the function, not introduced by S17. Measured on the CC-12 keystroke fixture: 12 re-cascaded elements → **1** (all 12 had produced byte-identical styles), boxes built 38 → 28, `CC12_KEY` ≈5% faster by min. Gates: `bug341_s17_keystroke_recascades_the_input_not_the_omnibox` (lumen-shell), `mutation_incremental_restyle_narrowed_attr_change_matches_full` (compares the **whole cascade**, since a colour change moves no boxes), `style::node_fanout_tests`.
- **The rayon fan-out threshold counts children the pass will *build*, not children the container *has* (BUG-341 S20, `box_tree.rs`).** ADR-016 M4.1 parallelises a flex/grid/table container's children at `RAYON_MIN_FLEX_CHILDREN` (8), a threshold sized against a **full** pass where each child costs a selector match, a cascade and a recursive build. On the incremental path since S15/S19 a child that is in the reuse index (`prev_index`) costs a `Mutex` lock and a move — so reading the threshold off `dom_children.len()` dispatched a worker per subtree the pass was about to relocate in O(1), and `assets/chrome/chrome.html` is built entirely out of such containers. Measured at ~1 ms of a 2.5 ms keystroke cycle, concentrated in the **self** time of `body` (0.33 ms), `.main-col` (0.27 ms) and `.omnibox-wrap` (0.45 ms), whose own work is ~4 µs each. The estimate now counts children that are elements **and** absent from `prev_index`; `prev_index: None` (every full-layout entry point) keeps `dom_children.len()` and M4.1's behaviour verbatim. Excluding non-elements is not cosmetic: `clean_subtrees` records elements only, so the whitespace text nodes between pretty-printed tags never enter the index and on their own held `body` above eight — a version filtering on `contains_key` alone changed nothing. Gated by count (`BoxBuildStats::fanouts`) on **both** arms — `bug341_s20_keystroke_moves_subtrees_without_dispatching_workers` asserts the full cycle still fans out, because the cheapest way to pass the incremental assertion is to stop parallelising at all. `CC12_KEY` ≈1.7× faster by min; `CC12_HOVER` unchanged (it builds 3 boxes, none an element, and never reaches the branch).
- **A wholesale box reuse is a claim the graft honours in O(1), not a fact it re-derives (BUG-341 S18, `incremental.rs` + `box_tree.rs`).** `build_box_or_reuse` cloning a subtree out of `prev` already *proves* that subtree may keep the previous pass's geometry — yet `mark_subtree_dirty` then marked all 318 chrome boxes dirty and `graft_geometry` compared each box against the very box it had been copied from, clearing the bit again. `DirtyBits::REUSED_SUBTREE` is that proof, carried on the root of each clone and consumed by `graft_geometry_with_cascade` (clear, mark clean, return "reusable" without descending). It rides in the box's own `dirty` field rather than a side set because the producers are **rayon workers** (S15's trap, third appearance): a shared set needs a lock on the hot path, a thread-local one loses every claim made on a worker. `mark_subtree_dirty` deliberately keeps walking *through* a claim, only preserving the bit — that is what keeps every graft exit that does not explicitly clean a box (identity mismatch, a trailing child with no predecessor) at its exact pre-S18 meaning, and it costs one byte write per box. Skipping that walk too would need an explicit revocation pass on each of those paths, where a missed revocation is a **stale clean box** — visible corruption, not a slow frame. Measured: `graft_geometry` 0.40-0.98 → 0.04-0.05 ms per keystroke cycle (4 boxes compared on a hover flip instead of 318), `CC12_KEY` ≈8-14% faster by min; `CC12_HOVER` inside this machine's noise. Gated by count: `bug341_s18_reused_subtrees_are_not_re_walked_by_the_graft` (lumen-shell) on `GraftStats::{visited,reused_wholesale}`. Note that `GraftStats::visited` therefore **no longer counts every box in the tree** — a per-box reject census (the S13 gate and its diagnostic) must run with box reuse off.
- **The reuse unit is a *move* out of the previous tree, not a copy of it (BUG-341 S19, `incremental.rs` + `box_tree.rs`).** `layout_mutation_incremental_restyle` takes `prev` **by value** and `incremental_build_box` takes `&mut LayoutBox`: `incremental::extract_clean_subtrees` walks `prev` top-down, stops at every node in `CounterMap::clean_subtrees` (that set is downward-closed, so the topmost clean box is exactly the unit `build_box_or_reuse` asks for) and **moves** the subtree into a `ReuseIndex = HashMap<NodeId, Mutex<Option<LayoutBox>>>`. Before this, each reuse deep-copied its subtree out of a `prev` the caller was only lending — 299 of chrome's 318 boxes per keystroke, 0.51-0.68 ms, the largest item in the cycle; the copy also had to be freed again every frame, which is why removing it bought more wall-clock (`CC12_HOVER` ≈1.6×) than the copy itself measured. The per-entry `Mutex` is not optional: the takers are **rayon workers** (S15's trap again), so a shared `&mut` is impossible and one lock around the map would queue them; each entry is taken at most once, which is also what stops a box from landing in two places. Walking only the spine replaced — and deleted — S4's `index_by_node`, whose whole-tree hash S4 had blamed for rejecting this mechanism and which S19's census measured at **0.02 ms**: re-measure an old negative result before optimizing what it points at. **Every emptied position keeps a husk carrying `DirtyBits::MOVED_OUT`, and `graft_geometry_with_cascade` rejects such a position as it would a changed identity.** The graft normally never reaches one (S18's `REUSED_SUBTREE` claim is honoured first), but a husk mistaken for a predecessor is a box declared clean with a subtree that no longer exists — visible corruption, not a slow frame — and the husk's `BoxKind::Skip` alone would not stop it colliding with a real `Skip` box. Gated by **conservation**, not output and not even by the reuse count (a copy and a move tally identically): `bug341_s19_reuse_takes_the_subtree_out_of_prev_instead_of_copying_it` asserts `prev` lost the boxes the new tree gained and holds one husk per reuse, `bug341_s19_graft_refuses_a_position_whose_subtree_was_moved_out` covers the husk, and lumen-shell's `bug341_s19_reuse_index_walks_the_spine_not_the_previous_tree` carries `BoxBuildStats::prev_index_visited` on the production document.
- **`CascadeStats` / `take_cascade_stats()` (BUG-341 S17, `counters.rs`) — public per-pass tally of cascade recomputes vs reuses.** Replaced the `#[cfg(test)]` `RECOMPUTE_COUNT` thread-local so gates outside `lumen-layout` — where the real chrome document lives — can assert on it, the same reason `BoxBuildStats` is public. `walk` is a plain recursion on the calling thread (unlike `build_box`, which fans out over rayon workers), so a thread-local tally here really does see the whole document; S15's trap does not apply.
- **A pseudo-element the sheet never targets is skipped whole-traversal, not cascade-by-cascade (BUG-341 S23, `style.rs` + `box_tree.rs`).** `CascadeIndex::pseudo_subjects` lists every pseudo-element name the sheet uses as a selector **subject** — the only position `matches_complex_for_pseudo` inspects, so the predicate is exactly as wide as the matcher it short-circuits — and `style::sheet_targets_pseudo(sheet, viewport, dark_mode, name)` exposes it. The point is what callers do with the answer: `apply_first_line_pseudo_styles` is a post-layout walk that used to ask the cascade about `::first-line` on **every block box in the document** (123 probes, zero hits, per interaction cycle on `chrome.html`, which has no such rule), so it now checks once and does not recurse at all; `build_box`'s per-inline-block probe is guarded the same way; `compute_pseudo_element_style_inner` short-circuits everything else. **`::marker` is exempt and must stay exempt** — CSS Lists L3 §2.1 synthesizes a marker style out of `list-style-type` with no rule at all, so "the sheet does not mention it" says nothing about whether the cascade should return one. The kind↔name correspondence lives in a single function, `pseudo_element_name`, which `pseudo_element_matches` delegates to: a predicate that drifted from its matcher would silently drop a pseudo-element's styling — visible corruption, not a slow frame — so the two are made structurally unable to disagree instead of kept in sync by review. Add a new pseudo-element by extending that one function. Gated by count on both arms (`bug341_s23_first_line_is_probed_only_by_a_sheet_that_uses_it`): the cheapest way to zero a probe count is to stop applying the pseudo-element altogether, which the second arm catches.
- **The per-node cascade cache is carried from pass to pass, not rebuilt (BUG-341 S24, `counters.rs`).** `CascadeStyles` (the type behind `CounterMap::styles`) is moved **into** the pass via `RestyleDelta::prev_styles` and back out of it via `CounterMap::into_styles`; `counters::walk` restamps a reused entry in place — one `get_mut` where S3-S23 needed a `contains_key`, an index and an insert into a fresh map — and the pipeline's per-frame `styles().clone()` is gone from both the chrome and the page path. Two invariants hold this up, and breaking either is visible corruption rather than a slow frame. **(1) The graft must be shown the cascade `prev` was built from, and that is no longer the live map.** A recomputed node's live entry holds *this* pass's style, and the freshly built box holds the very same `Arc`, so `graft_geometry_with_cascade`'s pointer test would call exactly the changed nodes unchanged and keep their old geometry. `CounterMap::replaced_styles` records what each pass displaced (one entry on a keystroke cycle, none on a hover flip) and `CounterMap::prev_cascade()` hands the graft a `PrevCascade` that reads displaced-first, live-second. Anything that starts consulting `styles()` directly for a "previous style" question reintroduces the bug. **(2) An entry exists iff the immediately preceding pass visited that node.** Nothing named this before S24, but it is what forces a recompute for a node detached and re-attached, or moved to a new parent, whose style was cascaded under a different inherited chain — the reuse rule's whole safety argument rests on absence. Entries therefore carry a pass ordinal and `finish_pass` sweeps the untouched ones whenever `entries.len()` and the visit count disagree (never in the steady state; the old rebuild's price on a pass that really removed nodes). Note that `lumen_dom` allocates `NodeId`s monotonically and never frees a node, so a stale entry is a wrong-*pass* hazard, not a wrong-*node* one. Gated by counter on both arms — `bug341_s24_interaction_cycles_carry_the_cascade_cache_instead_of_rebuilding_it` (`main.rs`: `passes_lived` grows with the cycle count, the steady state never sweeps, and a pass that detaches rows both sweeps and leaves no detached node behind) and `bug341_s24_the_pass_records_the_style_it_displaced_for_the_graft` (`incremental.rs`). A rebuilt map produces byte-identical styles, so no differential test can see the regression.
- **The box-build stage reads a child's `display` off the cascade cache, never by cascading it again (BUG-341 S25, `box_tree.rs`).** `build_box_inner`'s child loop has to decide which formatting context each child joins, and it asked with a full `compute_style` — up to three per element child, because `is_inline_content`, `is_inline_block` and the `display:none` branch inside the inline-collect loop each ran their own. `precompute_counters` has already cascaded every one of those nodes against exactly the parent style the probe passes as `inherited`, and `build_box_inner` builds the child's box out of **that** cached entry whatever the probe answered — so the probes were not merely a second cascade, they were an independent derivation that could **disagree** with the box (a child routed into an inline context whose own `display` says otherwise). `box_tree::probe_display` reads `CounterMap::style_arc` first and keeps `compute_style` only for a genuine miss (a caller holding a map that predates the node; on chrome it never fires for an element). Measured on `chrome.html`: 14 probes per keystroke cycle at 0.21-0.25 ms of a 0.63 ms cycle, 2 per hover cycle at 0.07-0.08 ms of 0.29 ms — and one of those two is `<html>`, which carries the design system's custom properties and was the most expensive cascade in the document, re-run every hover frame to be told it is not inline. `CC12_KEY` ≈22-31 % faster by min; `CC12_HOVER` inside the protocol's resolution, no claim. **Do not confuse this with the other `compute_style` the stage makes**: `counters.style_arc(id)` misses at the top of `build_box_inner` for every non-element box (the cascade records elements only), and those are 16 calls / 0.012-0.038 ms per cycle — a text node matches no selector, so the cost is the struct, not the cascade, and removing it is a question about whether a `BoxKind::Skip` box needs a style at all. The two are counted separately (`BoxBuildStats::display_probes` / `display_probe_cascades` vs `style_misses`) for exactly that reason. Gated by count on **both** arms — `bug341_s25_the_box_build_stage_reads_display_off_the_cascade_cache` (lumen-shell) asserts zero cascades *and* a non-zero probe count, because the cheapest way to zero the first is to stop asking, which puts every child in the wrong formatting context; what the answers must be is gated separately in `box_tree.rs` on a fixture exercising all three probes at once.
- **A counter snapshot is stored only where a counter is actually in scope (BUG-341 S23, `counters.rs`).** `counters::walk` used to insert one `CounterSnapshot` per element unconditionally; in a document that never uses `counter-reset`/`-increment`/`-set` all of them are clones of an empty map (828 of them per pass on `chrome.html`), and both consumers read a snapshot through `snap.and_then(|s| s.get(name))`, so an empty snapshot and an absent one are indistinguishable. The insert is now conditional on the **live counter stacks** being non-empty rather than on a sheet-wide predicate, so a document that uses counters in one subtree still pays nothing outside it. `CounterMap::counter_snapshot_count()` exists for the census: deriving the count from `styles`' size (one entry per element) was the assumption that would have hidden this cost. `CounterMap::with_capacity` additionally sizes `styles`/`clean_subtrees` up front — both are rebuilt from scratch every pass and used to rehash their way to ~830 entries. Gated on both arms (`bug341_s23_counter_snapshots_are_stored_only_where_a_counter_is_in_scope`): storing nothing at all passes the "no snapshots" assertion and renders every `counter()` as `0`.
- **A cycle whose delta says nothing changed does not walk the document (BUG-341 S26, `counters.rs`).** After S14 emptied the hover root-set and S16 gave the cascade a per-node content record, a chrome hover cycle re-cascaded **zero** elements — and still entered all 1740 nodes to establish that, which the S26 census measured at 50-60 % of the pass on `CC12_KEY` and ~70 % on `CC12_HOVER`, more than box build, layout and graft together. `RestyleDelta::is_noop` (empty `dirty_roots`, `ContentDirty::nothing_changed`, a non-empty carried cache that recorded no generated content) routes the pass to `CounterMap::carried_unchanged` instead. This is **equivalence, not a heuristic**: `walk`'s `force` can only be set by a miss in the carried cache, impossible for a node the previous pass wrote, so every element would take the reuse branch and every node report itself clean. Three points where a plausible implementation is *visible corruption* rather than a slow frame. **(1) `clean_subtrees` holds the document root's element children and nothing else** — the exact outcome, not a shortcut, because the set's only consumer (`extract_clean_subtrees`) stops at the topmost member it meets; non-elements are excluded because `walk` records cleanliness on its element branch only, so admitting one would hand the reuse index a box the mechanism has never seen. **(2) The pass ordinal is deliberately not bumped.** S24's invariant is "an entry exists iff the immediately *preceding* pass visited that node", and a skipping pass visited nobody — calling `begin_pass` would expire the whole cache and re-cascade the entire document on the next keystroke, with correct output. **(3) `nodes`/`quotes` are rebuilt by the walk, not carried**, so a skipped pass hands back empty ones; the licence is the `CascadeStyles::generated_content` bit the walking pass stamps in. That is deliberately not a stylesheet predicate (the S10/S23 shape): `counter-reset` can come from a `style` attribute, which no sheet scan sees. `CascadeStats` gained `visited`/`clean_inserts` so a gate can assert on the traversal itself. Gated by count on both arms — `bug341_s26_hover_cycles_do_not_re_walk_the_cascade` (lumen-shell) and `bug341_s26_an_unchanged_cycle_skips_the_walk_unless_it_generates_content` (a document with counters must keep walking *and* still report the right `counter()` values). `CC12_HOVER` lower in six A/B rounds out of six (min −9…−21 %, p50 −12…−26 %); `CC12_KEY` unchanged, its delta is not empty.
- **`FlatTree::children_of` short-circuits on an empty override map (BUG-341 S26, `lumen-dom`).** Whether a document has any composed-tree override is a fact about the *document*, not about the node — and it is "no" for every page without Shadow DOM — yet each call hashed its `NodeId` to discover that. The lookup sat on every traversal in the engine (cascade, box build, a11y tree), ~13 ns a time over 828 elements per walk.
- **A pass enters only the spine of its delta, not the document (BUG-341 S27, `counters.rs`).** The general case of S26: that slice skipped the walk for a delta naming *nobody*, this one skips every subtree the delta cannot reach. `restyle_spine` builds the **ancestor closure** of `dirty_roots` and `ContentDirty::Nodes` — the closure, not the sets, because a node's dirtiness has to be visible to everything above it (an ancestor of a content-mutated node must leave `clean_subtrees`; a dirty root must be reached before its subtree is forced). `skip_clean_subtree`, at both of `walk`'s recursion points, declines a child outside it and pays the one debt a skip leaves: `CascadeStyles::confirm` restamps the entry's S24 pass ordinal without reading a style, matching a selector or touching the counter state. That restamp is deliberate and was priced first — a replay **split by operation** put bare recursion at 0.012-0.017 ms and recursion-plus-restamp at 0.037-0.044 ms over the real document, so dropping the ordinal instead (and teaching `reuse`/`finish_pass` to tolerate a stale one) would buy ~6 % of the pass, below the A/B protocol's resolution, in exchange for weakening the invariant that makes a re-parented node recompute. One `clean_subtrees` insert per skipped subtree, not per element (S26's `carried_unchanged` argument). **Four pass-wide licences**, any of which restores the pre-S27 traversal verbatim: `ContentDirty::Untracked`; a composed tree that is not the DOM tree (`FlatTree::is_plain` — the closure walks `Node::parent`); quote content in the sheet (`quote_depth` is a running document-order counter); generated content recorded by the previous pass. **Three per-position ones**, and the second is the one a plausible implementation misses: an ancestor is re-cascading; **the parent is content-mutated**, because its child list may have *gained* that child from elsewhere and no delta names an arriving node, only the parent that received it — skipping it keeps a style cascaded under a different inherited chain; the counter stacks are non-empty here (`counter-increment` without a reset leaks across siblings, so this is positional, not per-pass). `CascadeStats` gained `walk_ns`/`skipped_subtrees`/`confirmed`/`confirm_misses`. Gated by count on both arms — `bug341_s27_a_keystroke_walks_its_own_chain_not_the_document` (lumen-shell; verified red without the licence at 1740 of 1740 nodes instead of 55), `bug341_s27_a_skipped_subtree_still_pays_the_pass_ordinal` (two cycles naming nodes in *different* branches, so the second walks into what the first skipped), `..._children_of_a_content_mutated_node_are_never_skipped`, `..._a_document_with_counters_is_still_walked_in_full`. The differential test asserts `skipped_subtrees > 0` **before** comparing, because a differential test over a mechanism that skipped nothing passes trivially. Chrome keystroke cycle: 1740 → **55** nodes entered, 12 subtrees skipped, walk 0.14-0.55 → 0.05-0.09 ms, `CC12_KEY` lower in five A/B rounds of six (−6…−17 % by min); `CC12_HOVER` unchanged, S26 already skips its walk entirely.
- **`lay_out_inner` carries permanent `scope_detail` scopes (BUG-341 S12).** `LUMEN_PROFILE_TREE=1 LUMEN_PROFILE_DETAIL=1` splits the `lay_out` stage into `lo_translate` (the clean-subtree fast path), `lo_chex` (per-box `ch`/`ex` metrics), `lo_style_ref`, `lo_svg` and `lo_wrap`. Their **call counts** are the point, more than their times: `lo_translate` vs `lo_style_ref` is the first honest "boxes reused vs boxes re-laid-out" counter this engine has had (1425 vs 1696 on `CC12_HOVER`), and `lo_svg`/`lo_wrap` both being **zero** on the incremental path is what proves the expensive content work is already grafted away. Use them before optimizing anything inside `lay_out`.
- **A replaced element's intrinsic size is a content-box size, so it must not be fed to `style.width` verbatim under `box-sizing: border-box` (BUG-099).** `build_box`'s replaced branches fill an unset `style.width`/`style.height` with the element's intrinsic dimensions (`<canvas>` bitmap, the 300×150 UA defaults of `<video>`/`<iframe>`). That value then goes through the ordinary sizing path, where `border-box` subtracts borders and padding from it — shrinking the element below its intrinsic size instead of growing the border box around it. The `<canvas>` branch compensates per axis before storing. **This is not the same question as the `<img>` dimension attributes:** HTML Rendering §15.4.1 maps `width`/`height` attributes to the CSS properties for `img`/`video`/`iframe`/`embed`/`object`, and there `border-box` subtracting is correct — but that list deliberately omits `canvas`, whose attributes are only the bitmap size. Check the §15.4.1 list before deciding which of the two behaviours a new replaced element wants.
- **A post-hoc subtree relocation must move `svg_paint_matrix` in lockstep with `rect`, not just `rect` (BUG-424, `shift_tree`/`shift_y_box`).** An `SvgShape`'s document-space paint CTM (`svg_paint_matrix`, BUG-244) is computed once, during `lay_out_svg_element_position`, and baked in relative to whatever `(ox, oy)` that call happened to receive. Several callers relocate an *already-laid-out* subtree afterwards by patching `rect.x`/`rect.y` directly instead of re-running SVG layout — flex/grid cross-axis alignment (`AlignValue::Center`/`End` in `lay_out_flex`, via `shift_y_box`) and absolute/anchor positioning (via `shift_tree`). Before the fix neither function touched `svg_paint_matrix`, so a flex-centered icon's axis-aligned `rect` (the fast path paint uses for `has_rot_skew == false`) moved correctly while the CTM (used only when a shape is rotated/skewed, or per BUG-424 (а) when a `<path>`/`<polyline>`/`<polygon>` carries a pure viewBox scale) silently kept the pre-alignment origin — invisible until something routes more shapes through the CTM path. The fix adds `dx`/`dy` straight onto `matrix[4]`/`matrix[5]`: translating a matrix by a document-space offset *after* its existing transform only ever touches its `e`/`f` components, so this is exact, not an approximation. Any future function that moves a subtree's `rect` post-layout (a third such site would not be surprising) must do the same.
- **`<path>`/`<polyline>`/`<polygon>` bypassed the CTM even under a pure scale, because the gate only checked for rotation/skew (BUG-424 (а), `emit_svg_shape`).** Rect/Circle/Ellipse/Line get their scale baked into `b.rect` by `apply_transform_to_bbox` during layout, so a scaled-but-unrotated shape already painted correctly through the axis-aligned fast path — the `has_rot_skew` gate (checks only the matrix's off-diagonal `b`/`c` terms) was written with those shapes in mind. `Path` is different: its `b.rect` is deliberately collapsed to a zero-size anchor point (BUG-174 — a path's true extent needs the parsed `d` data, which layout doesn't have), so it carries no scale information outside `svg_paint_matrix` at all. A `<symbol viewBox="0 0 24 24">` icon scaled down to 14px (no rotation — the common sprite-icon case) used to paint the raw, unscaled `d`/`points` vertices with only a document-space shift. The fix widens the CTM gate to `has_rot_skew || (shape is Path && matrix's scale ≠ 1)`, `Path`-only so Rect/Circle/Ellipse/Line keep their existing exact fast path unchanged.
- **`lay_out_flex` communicates an item's used size by writing into the item's own style — and must put the specification back afterwards (BUG-333/BUG-343, `SavedItemSizing`).** `lay_out`'s `available_height` argument is the *containing block* size for percentage resolution, not an override of the box's own size, so the only channel for "this item's used main size is N px" is `box_sizing: border-box` + `style.width`/`style.height = Px(N)` on the item, set right before the recursive call. That is fine; leaving it set is not. The engine lays the same subtree out **more than once with different available space** — most commonly a flex container's own Step-1 intrinsic probe, which runs an item under the container's full width and an *indefinite* height, followed by the real pass. A px value burnt in by the first pass makes the second unable to re-resolve a percentage (`width:100%` stuck at the probe's number) or to recover from a collapse (a `height:28px` row shrunk to 0 against the probe's `main = 0` stayed at 0 forever — the whole chrome sidebar). All three write sites (main-axis column, main-axis row, cross-axis stretch) now bracket the recursive `lay_out` with `SavedItemSizing::capture`/`restore`. Two consequences: `--dump-layout` prints `w=`/`h=` **as specified** (`w=100.00%`), never as resolved — read `rect=(…)` for used geometry; and several older workarounds in `lay_out_flex` (BUG-104, BUG-158, BUG-209) exist only because the value used to stick, so read their comments as history rather than as live constraints before building on them.
- **An empty `font_family` on a content box is a bug, not "the default" (BUG-128 ч.2, 2026-08-04).** `ComputedStyle::root()` used to leave the list empty, but both render backends (`Renderer::resolve_face_id`, `FemtovgBackend::resolve_font_chain`) read an empty list as *"this `DrawText` came from chrome"* and answer with the bundled chrome UI face (Golos Text, DS-4) — so a page with no declared `font-family` was painted in the browser's own UI font, not in Inter as the tracker assumed. The root style now carries `style::DEFAULT_FONT_FAMILY` (`"serif"`, the UA default of Edge/Chrome/Firefox), and the quirks table font reset (`apply_ua_table_font_reset`) resets to the same list rather than to `Vec::new()`. When adding any new site that fabricates a `ComputedStyle` for *content*, seed it from `root()` or `default_font_family()` — never an empty vec, or that subtree silently renders in chrome typography.
