  [`scripts/gen_tokens.py`](../scripts/gen_tokens.py) parses the four CSS
  custom-property blocks of the design-system prototype
  (`docs/design/lumen-v3_3.html`: `:root`, `body[data-theme="light"]`,
  `body[data-theme="dark"]`, `body[data-profile=*]`) and generates
  [`crates/shell/src/theme_tokens.rs`](../crates/shell/src/theme_tokens.rs) —
  typed `radius`/`space`/`size`/`badge`/`light`/`dark`/`profile` modules of

  `--check` mode diffs against the committed file (exit 1 on drift, no write).
  DS-1 only wires the module (`mod theme_tokens;` in `main.rs`, currently
  unconsumed — `#![allow(dead_code)]` on the generated file) — consumers land
  slice by slice per `docs/tasks/p1-design-v3.md` (DS-2 onward).
- **Done (DS-2 `Palette`/tab-strip/address-bar on tokens, 2026-07-22):**
  `panels::themes::Palette::DARK`/`LIGHT` are now built field-by-field from
  `theme_tokens::{dark,light}` instead of bespoke hex literals — the 7
  design-system-named roles map 1:1 (`tab_bar_bg`←`SURFACE_1`,
  `tab_active_bg`←`SURFACE_2`, `input_bg`←`SURFACE_1`, `text`←`TEXT_PRIMARY`,
  `text_dim`←`TEXT_SECONDARY`, `divider`←`STROKE`,
  `accent`←`theme_tokens::profile::PERSONAL`); the remaining Lumen-only roles
  (`header_bg`, `row_alt_bg`, `item_bg`, `item_selected_bg`, `overlay_border`,
  `tab_inactive_bg`) are pinned to the nearest surface tier with the mapping
  decision documented per field in `themes.rs`. One deliberate deviation from the DS-2 brief's literal
  `overlay_bg←OVERLAY_BG` instruction: `Palette::overlay_bg` is the *opaque*
  floating-panel/dropdown surface used by ~20 panels (the prototype's
  `.dropdown`/`.popover`/`.modal` all use `--surface-0`), not the translucent
  full-screen modal scrim the prototype's `--overlay-bg` custom property
  actually names — mapping it to the scrim token would have made every panel
  in the chrome render half-transparent over page content. `tabs/strip.rs`'s
  layout-toggle and settings-gear buttons now take `&Palette` and are
  theme-aware (`BAR_BG` constant removed); `address_bar.rs`'s omnibox focus
  ring and caret now read `pal.accent` instead of a fixed blue (matches the
  prototype's `.omnibox:focus-within{ border-color:var(--accent) }`) — the
  `HistoryFts` result-tag colour, which used to reuse the same constant by
  coincidence, is now its own `HISTORY_TAG` constant so the tag legend's
  fixed colour-per-category scheme (unrelated to theming) is unaffected.
- **Done (DS-3 chrome corner radii on `radius::{SM,MD,LG}` tokens, 2026-07-22):**
  every literal chrome corner radius across ~20 panel/tab-strip modules
  (`FillRoundedRect`/`DrawBorder` `radii` fields, `uniform_radii(r)`/`radii(r)`/
  `corners(r)` call sites, and local `RADIUS`/`PANEL_RADIUS`/`BTN_RADIUS`/
  `CARD_RADIUS`/`CHIP_RADIUS` constants) now reads `theme_tokens::radius::{SM,MD,LG}`
  (2/4/6 px) instead of ad-hoc literals. Values outside the three-step scale
  were re-quantised: `>6` (pill-shaped controls) clamp down to `LG` per the
  design-system rule (no pills in chrome — cheaper fillrate, denser UI), and
  in-between literals (3, 5, 7…) round to the nearest token. Nested "border +
  1px-inset content" pairs (nine panels: `cert_panel`, `history_panel`,
  `permission_panel`, `print_panel`(tooltip), `read_later_panel`,
  `settings_panel`(panel + tooltip), `shields_panel`, `shortcuts_panel`) keep
  their concentric-radius relationship via `radius::LG - 1.0` / `radius::MD -
  1.0` rather than being flattened to a single token, since that inset is a
  border-width derivation, not an independent design choice. Left untouched,
  deliberately: true circles/dots (`radius = size / 2.0` — status dots, avatar
  swatches, spinner/badge circles) since they are not a corner-radius-scale
  choice; `surface/theme.rs`'s `Theme::radius_{sm,md,lg}` (ADR-009
  `SurfaceManager` token set — ADR-009 migration is out of DS-track scope per
  `docs/tasks/p1-design-v3.md`); and `newtab.rs`/`reader_view.rs`'s embedded
  page-content CSS strings (New Tab tile grid, reader-mode article body — not
  yet on the design-token system at all at the time of this bullet;
  `newtab.rs` picked up `radius::LG` for its tile/badge radii in DS-11,
  `reader_view.rs` remains deferred, not chrome paint radii). Verified:
  `cargo test -p lumen-shell` (1620
  tests, unaffected `theme_tokens_radius_lg_matches_prototype` still pins
  `radius::LG == 6.0`); `cargo clippy -p lumen-shell --all-targets -- -D
  warnings` clean; headless `--screenshot` smoke-tested (no crash). Live
  per-panel before/after screenshots were not captured for every one of the
  ~20 touched overlays — the change is a value substitution onto an already
  spec'd 2/4/6 scale, not new geometry.
- **Done (DS-4 bundled Golos Text + JetBrains Mono chrome fonts, 2026-07-22):**
  [`crates/engine/paint/src/chrome_fonts.rs`](../crates/engine/paint/src/chrome_fonts.rs)
  bundles `GolosText-Regular.ttf`/`GolosText-Medium.ttf` (default chrome UI
  font) and `JetBrainsMono-Regular.ttf` (omnibox URL field + DevTools
  console/inspector/network panels), all SIL OFL 1.1 (`assets/fonts/OFL-*.txt`).
  Fonts arrive as static instances (Golos Text upstream ships only a variable
  `[wght]` font; `fonttools varLib.instancer` pinned `wght=400`/`500` — no
  variable-font runtime support needed in either render path). Wired as
  reserved `DrawText.font_family` names — `"Golos Text"`/`"Golos Text
  Medium"`/`"JetBrains Mono"` — in **both** live-window backends: femtovg
  (`FemtovgBackend::resolve_font_chain`, new `chrome_font_id`/
  `chrome_font_medium_id`/`mono_font_id` fields loaded via `add_font_mem`
  alongside bundled Inter) and the wgpu default (`Renderer::resolve_face_id`,
  mirrored `chrome_face_id`/`chrome_face_medium_id`/`mono_face_id` `usize`
  indices into `self.faces`, pushed right after the default Inter face at
  construction) — ADR-017 can probe either backend as the live default, so
  both must agree. An **empty** `font_family` — every chrome `DrawText` call
  site in `crates/shell/src` passes one, confirmed by grep audit, since
  content DrawText commands always carry a non-empty family from the CSS
  cascade — now defaults to bundled Golos instead of falling straight to
  Inter; Inter still backstops the chain for any glyph missing from Golos/
  Mono. Explicit opt-in to `"JetBrains Mono"` at 4 call sites: the omnibox URL
  input (`address_bar.rs`, dropdown suggestion labels/tags stay Golos-default)
  and the DevTools console/inspector/network panel `make_text` helpers.
  **Known caveat:** the reserved-name match is a plain string equality on
  `font_family`, not a chrome/content flag — page content that explicitly sets
  `font-family: "JetBrains Mono"` (a real, commonly-installed developer font,
  e.g. a syntax-highlighted code block on a blog) will render with the
  bundled copy rather than consulting the system `FontProvider`. Accepted:
  same glyphs, same family, just always our bundled build instead of
  deferring to the OS — no rendering break, only a minor loss of "use
  whatever the OS has" purity that would require a non-string signal
  (e.g. a dedicated `DisplayCommand::DrawText` field) to fully close, out of
  scope for this slice. Headless/CPU rendering (`--screenshot`, WPT, graphic
  tests) never draws chrome — only page content — so this default cannot
  affect it; verified `cargo test -p lumen-shell` green and a headless
  `--screenshot` smoke run does not panic. `cargo clippy -p lumen-paint
  --all-features --all-targets` and `cargo clippy -p lumen-shell --all-targets`
  both clean.

## Gotchas

- **A Resource Timing row belongs to the document that *asked* for the load, and the two obvious places to reset the queue are both wrong ([BUG-839](../bugs/BUG-839-FIXED.md), 2026-08-25).** `crates/shell/src/resource_timing.rs` parks the `Event::ResourceTimed` rows the network layer publishes until the event loop can hand them to the page (`PersistentJs::deliver_resource_timings`, one batch per step — a page pulling forty images would otherwise cost forty JS hops in one tick). Two ordering traps, both measured rather than reasoned: **(1)** draining must happen only when there *is* a runtime to hand the rows to, because most of a page's images finish before its JS context exists and an early `take_rows()` throws them away; **(2)** the per-navigation `clear()` must run where the *load* starts (the streaming-state reset block, both copies), **not** in `set_js_ctx` — that runs after `source.load` has already fetched the document's stylesheets, scripts and images, so clearing there discards exactly the rows the page is owed. The first version of the fix did precisely that and measured 0 entries on a page whose three subresources the probe's own server had served. **(3)** The per-step drain is not early enough on its own: the document's stylesheets and scripts are fetched *during parsing*, before the runtime exists, and WPT's `performance-timeline/case-sensitivity.any.js` reads `getEntriesByType('resource')` synchronously on the first line of the first script — a probe reading it from a `setTimeout` cannot see this difference. So `parse_and_layout` hands the already-finished rows over right after `install_dom` and before the classic-script loop, and the per-step drain covers only the tail. **(4)** That in turn needs the queue suspended for the duration of a navigation (`clear()` raises the flag, `set_js_ctx` lowers it): while the new document is fetching, the runtime the shell still holds belongs to the *outgoing* page, and an unsuspended drain would hand it the incoming page's rows. The JSON crosses into JS as a *string literal*, because the shim runs `JSON.parse` on it — embedding it bare on the "valid JSON is a valid JS expression" reasoning is what made every `popstate` deliver `state: null` for months (BUG-829).


- **Registering decoded pixels in the renderer is not the same as telling layout the image's size (BUG-735, 2026-08-10).** The intrinsic size reaches layout through exactly one channel — `apply_intrinsic_size` filling the `<img>`'s empty `width`/`height` content attributes (the presentational hint the cascade then reads). A new image path that only calls `register_image` paints the pixels but leaves `height: auto` resolving to 0, because without an intrinsic pair there is no aspect ratio. Three paths call it directly (final `fetch_and_decode_images`, lazy, video-GIF); the streaming/dynamic path (`spawn_image_requests` → `LoadEvent::ImageDecoded`) deliberately does **not** — its event carries no `node_id` and its requests are deduped by URL (`stream_images_requested`), so a second `<img>` with the same `src` never gets an event at all. It instead records `src → (w, h)` in `Lumen::stream_image_sizes` and lets `apply_stream_intrinsic_sizes` (Step 1.7 of `RedrawRequested`) walk the live document. **That pass must stay scheduled from both producers** — a fresh decode *and* the tail of `apply_relayout_result` — because a client-rendered page replaces the `<img>` node itself (React re-render): schedule it only on decode and the outcome becomes a race, which on live `tbank.ru` read as "21 zero-height images in one run, none in the next". Convergence relies on `apply_intrinsic_size` returning whether it actually wrote anything; keep that contract if you add a caller.

- **The JS geometry/computed-style snapshot must be published from every path that produces a layout tree, not just from relayout (BUG-382, 2026-07-29).** `getComputedStyle()`/`getBoundingClientRect()` never ask the layout engine — they read the map the shell pushes via `update_layout_rects`/`update_computed_styles`. Those pushes used to live only in `relayout()` and `reload()`; the fresh-load path (`apply_loaded_page`) pushed rects only from inside the lazy-image block (so only for pages carrying `loading="lazy"`) and never pushed styles at all — a loaded page answered `""`/all-zeros unless an unrelated relayout raced ahead of the first script, which read as "works one load in four". `apply_loaded_page` now publishes rects + styles + viewport unconditionally, right after `self.layout_box` is installed and before `load`/`pageshow`. When adding a new path that installs a `layout_box`, publish there too — the symptom is silent and intermittent, and neither API fails loudly.

- **HiDPI / DPR partially supported.** Renderer stores `scale_factor` from winit. `ScaleFactorChanged` updates it on-the-fly. **Not yet supported:** layout viewport is hardcoded 1024×720 — `inner_size` not passed to layout, no relayout on `Resized`. Requires structural pipeline refactor (layout runs before window creation) — P1 concern.

Срез 3 gave the sub-document ITS OWN `overflow: scroll|auto` containers: `FrameHandle::scroll_containers` mirrors the page's `Lumen::scroll_containers`, rebuilt by the same `lumen_layout::collect_scroll_containers` alongside `FrameHandle::layout`; `Lumen::try_scroll_frame_overflow_container` mirrors `try_scroll_overflow_container` at the sub-document level and is checked in `mouse_wheel.rs` BEFORE the frame's own scroll (deepest scroller under the cursor wins, same rule the page already followed for its own containers vs. the viewport). Срез 4 closed the remainder: a scrollbar visual + click/drag for the FRAME'S OWN scroll (not its descendants' overflow containers, which stay wheel-only like the page's). `frames::frame_scrollbar_overlay` reuses `scrollbar::build_scrollbar_overlay` unmodified per visible `FrameHandle`, wrapped in `PushClipRect`+`PushTransform` to the frame's on-screen box via the new `frames::frame_box_page_origin` (the HOST box's origin, not content's — does not subtract the frame's own scroll, only ancestors', unlike `frame_page_origin`) minus the page's own scroll — the same "raw overlay" coordinate convention `build_validation_tooltip`/`show_frame_validation_tooltip` already used. `Lumen::classify_frame_scrollbar_click` (in `scrolling.rs`) picks the deepest matching frame (mirrors `pointer_target`'s descent) and is checked in `mouse_input.rs` ahead of the page's own scrollbar check; a thumb hit arms `Lumen::frame_scroll_drag: Option<(usize, scrollbar::ScrollDrag)>` (a sibling of `scroll_drag` that also remembers which frame), applied on `CursorMoved` via the new `Lumen::drag_frame_scrollbar_to`; an above/below track click jumps instantly by `page_step(h.viewport.height)` (no smooth animation — a frame scroll has none, срез 17). `frame_scroll_drag` is cleared everywhere `scroll_drag` already was (mouse-up, the three navigation reset sites, init) since the frame list is rebuilt whole on navigation. `Lumen::update_cursor_icon` checks the frame scrollbar ahead of the page's. Live drag verification not done — no raw mouse-down/move/up automation primitive exists (`AutomationCommand` has `Click`/`Scroll`/`Type` only), and `--screenshot` cannot see ANY per-frame overlay including the page's own scrollbar (`overlay_buf` is rebuilt fresh every frame and never written back to `self.display_list`). 7 new unit tests on the pure functions (`frame_box_page_origin`, `frame_content_height`, `frame_scrollbar_overlay`).

- **A form control inside a frame is classified by the page's own `forms::classify_click` and shown by re-laying-out the child at an UNCHANGED viewport (BUG-480 slice 18, 2026-08-29).** `crate::forms` takes any `&Document`, so nothing about «what does a click on `<summary>` do» is duplicated for the child — what is new is making the result visible: `frames::relayout_frame_content` computes the child's layout at its current size and **clears** its `content_dl`, an empty list being the only «repaint me» flag `rebuild_frame_display_lists` understands, which is how the edit reaches the display lists of every ancestor frame as well. It then hands off to `sync_frame_viewports` — not to save code, but because the mutation may have moved the host box of a NESTED frame (an opened `<details>` above it), and the depth ordering lives only there; the stale-scroll clamp comes from the same call, since a `<details>` can be closed on a frame scrolled to its bottom. Slice 13's «host size unchanged → skip» gate fires *always* on this path, which is why the layout is computed directly rather than through that pass. The `toggle` event goes out by a direct `eval_js` on the frame handle: `route_eval_js` only knows `self.js_ctx`, the page's context. NOT covered, each for its own reason: the popup-anchored controls (`<select>`, colour, date, file) draw their overlay from the *page's* `layout_box` and are addressed by a bare `NodeId`, and submitting the child's form is frame navigation; both log a line to stderr rather than going silent, so a click on a `<select>` in a frame is not mistaken for a lost event.
- **A link in the child navigates the frame; the URL half is the page's, only the destination is new (BUG-480 slice 19, 2026-08-29).** `crate::links` answers «fragment or load», «is this scheme navigable» and «is this the same document» identically for a page and for a sub-document — those are questions about a URL, not about who clicked — so `Lumen::frame_link_click` reuses them whole and adds only `LinkTarget`: `_self`/absent changes the clicked frame, `_top` the page, `_parent` the frame one level up (or the page at depth 0). The href resolves against `FrameHandle::base`, a new field, because the handle's `url` cannot yield it: `about:blank`/`about:srcdoc` inherit the host's base; and the resolution base is a *parameter* of `frames::navigate_frame`, since `target=_parent` changes someone else's sub-document while the address was still written by the clicker. `frames::FrameLoadEnv` exists for the same reason the slice needed a refactor at all: the twenty providers a sub-document load needs lived only inside `parse_and_layout`, so a later load from a live window had nothing to load *with*; bundling them into one `Clone` value carried through `LoadedPage` into `Lumen` also collapsed the 25-argument `load_frame_sub_documents` and let the body of its loop become `spawn_frame`, which navigation calls with a destination instead of the markup's. A navigation **replaces** the handle rather than editing it (different `Document`, JS context and cascade) and `drop_frame_subtree` takes the whole nested subtree with it in a loop to a fixed point — the list is flat, and a grandchild points at the middle frame's document, which is being removed on the same step; `host_src` is deliberately carried over, being half the key `splice_one_frame` finds the placeholder by, and the placeholder comes from the parent's layout of an attribute a navigation never touches. Because the index no longer addresses anything, `Lumen::refresh_frames(None)` re-syncs every frame instead of slice 18's `Some(idx)`. Two defects found beside the subject: `V8JsRuntime::register_frame_document` always pushed while `_lumen_frame_binding` takes the first match by `host_nid`, so the parent's `contentDocument`/`contentWindow` would have kept answering with the discarded document and `window.length` would have grown per navigation (`frame_bridge::upsert_binding` now replaces in place, `bid` preserved — the nested browsing context survives, only its document changes); and **`Lumen::js_ctx` is `None` in a live window** — since ADR-023 the engine thread is on by default and `set_js_ctx` deposits the handle in `EngineJsState`, leaving the UI field empty, so reading `self.js_ctx` directly instead of going through `route_*` silently does nothing. `Lumen::clone_js_ctx` is the way to hold that handle when a router's single `FnOnce` will not do (the load calls four different methods on the parent synchronously). Not covered: session history for a frame navigation, an error document for a failed one (the previous document stays), a named or `_blank` target (an unknown name would have to *create* a window, BUG-883), and the load runs synchronously on the UI thread.
- **The child submits its forms; the submission is the page's code, only the destination is new (BUG-480 slice 20, 2026-08-29).** `Lumen::run_frame_form_submission` mirrors `run_form_submission` argument for argument, because constraint validation, field collection, enctype, encoding and the cancelable `submit` event are questions about a *form*, not about which document holds it — `lumen_dom::submit_form`/`forms::enctype_of_form`/`forms::encode_form_fields` take any `&Document` and are reused unchanged. Three things are the slice's own. The `submit` event is dispatched into the **child's** runtime by a direct `eval_js_value` on the frame handle (`route_query_js` knows only `self.js_ctx`, the page's context), so the child's own handler is what can `preventDefault()`. The destination comes from `Lumen::link_destination`, opened up from slice 19 rather than re-derived: HTML LS §4.10.21.4 step 15 points at the very §4.6.3 that `<a target>` uses, so the two cannot answer differently. And a failed constraint validation has to draw its tooltip **over the page** while the control lives in the child, which is what `frames::frame_page_origin` is for — the same host-rect sum `splice_one_frame` uses to place pixels, with each level's own `scroll_y` subtracted; it returns `None` rather than `(0, 0)` when a link of the chain has no host box yet, since the origin of the page would put the tooltip in the window corner as if it belonged there. Both of the page's entry points exist here: the native click (through `frame_form_click`) and `form.submit()`/`requestSubmit()` from the child's own script, whose `NavigateRequest::SubmitForm` the frame pump in `about_to_wait` used to drain and drop with every other frame navigation. `fire_submit_event` splits them exactly as on the page — `requestSubmit()` has already dispatched the event on the JS side and `submit()` skips it by spec (§4.10.21.3). Deliberately *not* diverging from the page: POST still only logs, and `formaction`/`formmethod`/`formenctype`/`formtarget` on the submitter are ignored, because the page ignores them too. Not covered: session history, so back/forward does not return to the pre-submission document.

- **A sub-document's `window` gets a `resize` event and a ticking `requestAnimationFrame` (FRAME-1, 2026-09-01).** Two independent additions. `PersistentJs::fire_window_resize` (mirrors `fire_window_scroll`) calls `_lumen_fire_window_resize_event` in the shim, which dispatches a non-bubbling/non-cancelable `Event('resize')` on `window` only (HTML LS §7.4.4 — unlike `scroll`, `resize` has no legacy `document`-target form); `frames.rs::sync_frame_viewports` fires it exactly when the host `<iframe>` content box actually changed size, via a `viewport_changed` bool computed alongside the pre-existing "nothing changed — skip" gate so a relayout triggered only by an interactive-state change (slice 23) does not spuriously fire it. This closes the case slice 12's own doc comment already named: `load_frame_sub_documents` fires the child's `load` on the temporary `FRAME_UA_DEFAULT_SIZE` (300×150) layout, because the real host box isn't known until the parent's own layout completes a few lines later in the same synchronous `parse_and_layout` call — a page that reads its size in `load` used to cache that placeholder forever, and now gets told to re-measure. Second: `about_to_wait.rs` pumps `has_raf_pending`/`take_raf_pending`/`run_animation_frame`/`take_dom_dirty` for every `frame_js_handles` entry — one synchronous pass, since frames are never engine-threaded (see the comment where that `Vec` is built) — sharing `last_raf_batch_ms`/`RAF_MIN_INTERVAL_MS` with the page's own pump so the combined rate stays ⩽60 Hz (BUG-271); a rAF callback that dirties the child's DOM relays out through the same `refresh_frames(Some(idx))` slice 25 uses for bridge/own mutations. Verified live and committed as `tests/wpt/verify_frame_resize_raf.py`. Not covered: `window.innerWidth`/`innerHeight` stay `undefined` in a frame exactly as on the page itself ([BUG-529](../bugs/BUG-529-OPEN.md)) — a `resize` handler must re-measure via `getBoundingClientRect()`. And despite the task's original framing, the browser's OWN `scroll-behavior:smooth` animation and animated-GIF ticking are NOT driven by this rAF pump — they are separate, page-only Rust-side tickers (`Lumen::scroll_anim`, `Lumen::animated_gifs`) keyed off `RedrawRequested`, with no per-frame equivalent added here; a frame's smooth scroll still jumps instantly (slice 17's deviation note) and its GIF still shows one static frame (slice 15's).

- **A frame navigation no longer blocks the whole event loop for the fetch (FRAME-4 slice 3, 2026-09-02).** Every trigger of a frame document replacement (link click — own or `target`-routed, native form submit, the child's own `form.submit()` drained each tick, and history back/forward through a frame) funnels through `Lumen::replace_frame_document`, which used to call `frames::navigate_frame` — fetch, parse, script execution, layout — synchronously inline. It now mirrors how the page itself already loads (`start_streaming_load`/`render_bytes` + `LoadEvent`/`EventLoopProxy`) rather than inventing a new mechanism: `navigate_frame` split into `frames::prepare_frame_navigation` (the short host-tree lock, i.e. everything that was BEFORE the network) and `frames::run_frame_navigation` (the `spawn_frame` call itself, now inside `std::thread::spawn`). Both are pure functions with no access to `Lumen::frames`, which is what makes the split thread-safe without new locking: `Document` is `Send + Sync` by construction (compile-time assert in `lumen_dom::lib.rs`), `PersistentJs: Send + Sync`, so the child's JS runtime — created *inside* the background thread by `run_scripts_with_dom` — crosses back to the UI thread the same way the page's own JS handle already does inside `RenderDone` (ADR-014/B-1). The background thread reports back via a new `LoadEvent::FrameNavDone { host_doc, host, old_doc, generation, handles }`, applied by `Lumen::on_frame_nav_done` → `frames::apply_frame_navigation`. Two invariants the synchronous path never needed: (1) a frame's index into `Lumen::frames` does not survive even a synchronous navigation (slice 19), let alone an async pause in the middle of one — identity is carried by `old_doc: Arc<Mutex<Document>>` instead, and `apply_frame_navigation` looks it up by `Arc::ptr_eq`, silently dropping a response whose subtree is already gone (an ancestor navigated on its own, or the whole page reloaded — both of the sites that wholesale-replace `self.frames` now also clear `frame_nav_requests`); (2) two clicks on the same frame in quick succession both read the *same* `old_doc` (neither has applied yet), so presence-of-`old_doc` alone cannot tell a stale first click from the second — `frames::FrameNavRequest` is a `(host_doc, host) → generation` slot (keyed by `Arc::ptr_eq`, not a pointer hash, since a freed `Arc` allocation can be reused by an unrelated document — ABA), bumped synchronously at request time and checked against the value carried back in `FrameNavDone`; a stale generation is dropped even if its `old_doc` is technically still present. `replace_frame_document`'s return value changed meaning from "document replaced" to "request accepted" without needing a caller-side rewrite: history bookkeeping (`navigate_frame_to`/`traverse_frame`) and the `hovered_frame`/`focused_frame`/`active_frame` reset only ever needed the address and identity known *before* the network round-trip — the reset itself moved from `replace_frame_document` into `on_frame_nav_done`, which is actually more correct than before: while the response is in flight the old sub-document is still the one on screen, so hover/focus on it stays valid until the swap really happens.

- **Popup-anchored form controls (`<select>`, colour picker, date picker, `<input type=file>`) now work inside a frame (FRAME-6, 2026-09-02, branch `p1-frame6-form-overlays`).** Previously `frame_form_click` (`frame_forms.rs`) printed a stub to stderr for all four `FormClickAction::Open*` variants and did nothing — the page's popup mechanism addresses its anchor by a bare `NodeId` against `self.layout_box`, which is the PAGE's layout tree and cannot resolve a frame's own `NodeId` space. Three new `Lumen` fields (`state.rs`) mirror the page's `color_picker_node`/`date_picker_node`/`select_dropdown_node` but key on `(frame index, NodeId)` — `frame_color_picker`/`frame_date_picker` (+ `frame_date_picker_year`/`_month`) / `frame_select_dropdown` — the same pairing `frame_text_cursor` (FRAME-2) already uses, for the same reason. A new `Lumen::frame_overlay_anchor(idx, node)` (`frame_forms.rs`) finds the control's box in the frame's OWN layout tree and translates it into page coordinates via `frames::frame_page_origin` — the same translation `show_frame_validation_tooltip` (FRAME-4) already performs for the validation tooltip — so the *existing* `forms::build_color_picker`/`build_date_picker`/`build_select_dropdown`/`build_base_select_dropdown` paint the popup unmodified, just with a frame-derived anchor (`redraw_requested.rs`). A click on the open popup itself (swatch/day/option) is resolved by three new blocks in `click.rs::handle_click_at_inner`, positioned before the page/frame hit-test dispatch (the popup is viewport-locked over everything, like the page's own) and following the same "hit → apply, else → close" rule the page's three checks already use; a mutation goes through `forms::set_value`/`apply_select_choice` on the frame's own `Document`, followed by `Lumen::refresh_frames(Some(idx))`. `<input type=file>` (`Lumen::open_frame_file_picker`) is the one control that is not purely geometric: it registers the OS-picked file's access token on the *frame's own* origin via `lumen_js::file_input::origin_for_url(&handle.url)` — the same derivation `install_dom` itself uses to compute `page_origin` before installing that frame's file-read bindings — rather than the page's `active_document_origin()` (a single global holding whichever document's bindings were installed *last*, not necessarily the one that owns the click). The three new fields are reset alongside the existing `frame_text_cursor`/page-picker resets on page navigation (`page_load.rs`) and tab switch (`tabs_cmd.rs`), and alongside `hovered_frame`/`focused_frame`/`active_frame` in `frame_links.rs::on_frame_nav_done` — the same staleness class: after a frame's document is replaced, a leftover `(idx, NodeId)` could resolve to an unrelated node in the new tree. No new unit tests (same reason as the rest of the FRAME series — the orchestration lives on `Lumen`, which shell's tests never construct); verified via `cargo test -p lumen-shell --bin lumen` (1714/1714, no regressions) and a live `--mcp-live-port` smoke run (opening/clicking all three geometric popups inside a real `<iframe>` returns `success: true` with no panic and no leftover stub message). Not visually verifiable — the same automation gap FRAME-7 slice 6 already hit: `AutomationCommand::Screenshot` rasterizes `self.display_list` only, and no per-frame overlay (caret, validation tooltip, and now these popups) is ever written back into it.


- **`main.rs` is no longer the only home of `impl Lumen` (SPLIT-SH1, 2026-08-26).** Three modules now carry parts of it, split by subject rather than by file position: `relayout.rs` (display-list ownership, `refresh_dynamic_css`, `relayout`/`relayout_chrome`/`relayout_form`, the rAF turn and its lock-free flags, the off-thread layout job of ADR-016, `poll_engine_commit`, and `set_js_ctx`/`take_js_ctx`), `chrome_ui.rs` (`relayout_chrome_host`, `chrome_model_snapshot`, chrome hit-testing, `dispatch_chrome_action`, the chrome a11y snapshot) and `page_load.rs` (`reload`, the streaming load, image/media subresources of the current document, `apply_loaded_page`). Nothing about the move is special to these methods — an `impl Lumen { … }` block compiles unchanged in any crate-root child module next to `use crate::*;`, because private items of the crate root are visible to its descendants; the one unavoidable edit is `fn` → `pub(crate) fn` for a method still called from `main.rs`, since the parent module cannot see a child's private items. Consequence when grepping: a `Lumen` method is no longer necessarily in `main.rs`, and the remaining `impl Lumen` there is two blocks, not one — the small first block (resize grips, the file picker, fullscreen-resize arming, the zoom preview) and the core block after `PipOsWindow`.
- **`PageSource` and the session-history entry have left `main.rs` too (SPLIT-SH3b, 2026-08-27).** `page_source.rs` holds the `PageSource` enum and all of its loading (`from_arg`, `resolve_href`, `load_bytes`, `load_bytes_streaming`, `load`), the `RawPage` those return, the `cache_control_no_store` predicate pulled out of `load_bytes`, and the two constructors that turn an automation- or JS-supplied URL string into a `PageSource` (`page_source_for_automation_url`, `resolve_js_navigation`) — the last two used to sit 700 lines higher in `main.rs`, which is the only reason they read as a separate subject. `nav_history.rs` holds `NavEntry` (plus `shift_history_entry`/`shift_multi_step`) and `JsNavigateRequest`. Two types that lived in the same region are not navigation at all and went by subject instead: `DomTouchedSummary` to `persistent_js.rs` (its only user in the whole crate is `PersistentJs::take_dom_touched`) and `should_restore_session` to `session_persist.rs`. **The re-export trap worth knowing:** a private `use` in the crate root doubles as a re-export for every submodule's `use crate::*;`, but it must carry the cfg of whoever actually uses it — `cache_control_no_store`'s only caller outside `page_source.rs` is the test module, so its re-export is `#[cfg(test)]`; an unconditional one is an unused import in the ordinary build. Grepping for that name in `main.rs` is misleading in its own right, since `RawPage` has an identically-named field.

- **The page cascade and the first layout run BEFORE the document's scripts ([BUG-443](../bugs/BUG-443-FIXED.md), 2026-08-30).** `parse_and_layout` used to run `parse → run_scripts_with_dom → DOMContentLoaded → iframes → images → CSS → fonts → layout`, so anything the page read during parsing answered `""` / a zero rect: there was no cascade and no box tree yet. The CSS + `@font-face` + measurer stretch is now the free fn `build_page_cascade` → `PageCascade` (`page_pipeline.rs`), called before the scripts; a page with at least one script then pays one `layout_page` pass whose `JsLayoutSnapshot` (`collect_layout_rects` + `collect_computed_styles` + `collect_custom_properties` + viewport — the same four tables `apply_loaded_page` pushes) travels into `run_scripts_with_dom` as the new `parse_time_layout` argument and is published right after `install_dom`. **Three invariants this order rests on.** A script-inserted `<style>`/`<link>` must still reach the *first* cascade, so `inline_style_fingerprint` **and** the new `stylesheet_link_fingerprint` (`doc_extract.rs`) are captured before the scripts and compared after them — `build_page_cascade` re-runs only on a mismatch, which is what keeps an ordinary load at exactly one network pass for its CSS; anything new that changes the stylesheet set from Rust must move one of those two hashes or the rebuild will not see it. The post-script snapshot is skipped when the scripts touched neither the cascade nor the tree, and the DOM half of that test **reads** `dom_dirty_flag()` rather than calling `take_dom_dirty()` — taking it would swallow the relayout the shell schedules for itself after the load. And both layout passes go through `layout_page`, which brackets `set_print_media` (BUG-270); the flag is per-pass and thread-local, so two hand-written passes would eventually drift. The other two callers of `run_scripts_with_dom` (`frames.rs`, `hibernate.rs`) pass `None`: both lay their document out only after the call returns. Not covered: this is not a forced synchronous layout — a script that mutates the DOM and reads geometry in the same turn still sees pre-mutation values, and a `DOMContentLoaded` handler sees geometry without images (spec-correct: they decode further down).
