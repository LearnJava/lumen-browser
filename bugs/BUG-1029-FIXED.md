# BUG-1029: прогоны WPT оставляют живые процессы `lumen` — 2026-09-07 машина дважды ушла в OOM

**Статус:** FIXED 2026-09-13
**Дата:** 2026-09-07
**Компонент:** тулинг (`tests/wpt/run_report.py` + вендоренный
`tools/wptrunner/` — снятие браузера после обрыва прогона), не движок
**Владелец:** P2 (тулинг WPT)
**Найден:** 2026-09-07 при разборе [BUG-1027](BUG-1027-FIXED.md) — по журналу
ядра, а не по логу прогона

## Симптом

Дважды за день ядро убило `lumen` глобальным OOM:

```
сен 07 12:36:35 Out of memory: Killed process 366032 (lumen) total-vm:187703776kB, anon-rss:1068344kB, oom_score_adj:200
сен 07 13:53:44 Out of memory: Killed process 484445 (lumen) total-vm:24510800kB,  anon-rss:1699468kB, oom_score_adj:200
```

Для сессии это выглядит как «браузер молча исчез» — ни паники, ни core dump
(SIGKILL их не оставляет), в логе прогона обрыв на произвольном тесте.

## Механизм

Таблица процессов из того же дампа ядра (12:36:35):

| pid | RSS | swap |
|---|---|---|
| 363491 `lumen` | 1057 МБ | 1651 МБ |
| 366032 `lumen` | 1044 МБ | 1700 МБ |
| 369366 `lumen` | 1061 МБ | 839 МБ |
| 363462/363464/363495 `lumen` | ~50 МБ | ~180 МБ каждый |
| **итого шесть `lumen`** | **3.2 ГБ** | **4.7 ГБ** |

Свободного свопа на момент убийства — 196 КБ из 7.6 ГБ; машина 7.6 ГБ RAM +
7.6 ГБ zram. Параллельно шла сборка (`rustc`, ~0.5 ГБ). Во втором эпизоде
(13:53) картина зеркальная: один `lumen` на 1.7 ГБ + восемь `rustc` ~2.5 ГБ.

Шесть одновременных инстансов — это не один прогон: `run_report.py` поднимает
`lumen --bidi-port N` на каждый worker, а когда `wptrunner` виснет и его
снимают `kill -9` (штатный сценарий [BUG-1006](BUG-1006-FIXED.md), три
независимые репродукции), внуки переживают родителя и остаются висеть до
конца сессии. Каждый такой сирота держит V8-изолят и wgpu-контекст — около
1 ГБ RSS.

Жертву ядро выбирает по `oom_score_adj=200`, который все процессы сессий
наследуют от юнита `run-claude-manager.sh`: под нож идёт `lumen`, даже когда
память съел не он. Плюс `total-vm` у `lumen` — 24–183 ГБ (резерв V8/wgpu,
коммит постраничный), что дополнительно поднимает его `oom_score`.

## Что надо сделать

1. Снимать браузер по process group, а не по pid: `kill -9` по родителю
   оставляет внуков живыми — это и есть источник сирот.
2. Перед стартом прогона зачищать stale-инстансы (`lumen --bidi-port` без
   живого родителя) и логировать, сколько нашлось: сейчас накопление не видно
   никому до самого OOM.
3. Не совмещать сборку и прогон WPT на этой машине — оба эпизода накрыли её
   именно на этом сочетании. Механизм на выбор: межсессионный лок на
   «тяжёлое» или ограничение `CARGO_BUILD_JOBS` по числу активных сессий.
4. Рассмотреть `MemoryHigh=` на юните `run-claude-manager.sh`, чтобы ядро
   давило группу сессий, а не выбирало жертву глобально. Правка вне репозитория
   — требует явного согласия пользователя.

## Границы

К [BUG-1027](BUG-1027-FIXED.md) отношения не имеет: там детерминированный
`abort()` по переполнению стека с core dump, здесь SIGKILL от ядра без следа

2026-09-07 обе причины какое-то время считались одной.

## Срез P3 2026-09-08

Предыдущий коммит (`fbbc70242`, «`run_report.py` — вызов
`port_guard.ensure_free` перед прогоном») закрыл смежный BUG-1022 (коллизия за
фиксированные порты `wptserve` из `config.json`), но не пункт 2 этого бага:
`ensure_free` ищет держателей ТОЛЬКО среди `configured_ports()` — порт
`lumen --bidi-port N` назначается ОС на каждый запуск и ни разу не встречается
ни в `config.json`, ни в `SERVER_MARKERS`/`RECLAIMABLE`-логике, поэтому
осиротевший браузер ей попросту не виден. Формулировка того коммита (и старый
комментарий в `run_report.py`) ошибочно приписывала эту защиту уже влитому
коду.

Реализовано (пункт 2 — «зачищать stale-инстансы перед стартом»):
`tests/wpt/port_guard.py` — `classify()` обобщён параметром `child_markers`
(был жёстко завязан на `SERVER_MARKERS`), добавлен `LUMEN_MARKERS =
("--bidi-port", "--ipc-server")` и две новые функции: `survey_lumen_orphans`
(сканирует таблицу процессов ОС по командной строке, не по порту —
классифицирует той же orphan/live/stale-логикой, что и `wptserve`) и
`reap_lumen_orphans` (убивает найденные orphan/stale, логирует сколько).
Вызывается один раз в начале `run_report.py` (рядом с уже существующим
`ensure_free`) и перед каждым шардом в `run_corpus.py` (рядом с тем же
вызовом; `kill_tree` там же по-прежнему первая линия защиты для таймаутов
СВОИХ шардов — этот вызов ловит то, что осталось от постороннего SIGKILL,
который `kill_tree` в принципе не может увидеть, поскольку SIGKILL не
запускает никакой Python-код). Комментарий в `run_report.py`, ложно
приписывавший реап осиротевших браузеров уже влитому `ensure_free`, исправлен.
`port_guard.py --selftest` расширен синтетическим orphan-процессом
(`python -c "..." --bidi-port 0`) — detect/classify/reap проверены отдельно
от уже существующего `wptserve`-кейса, все новые проверки зелёные (Windows,
`.venv` не нужен — модуль не тянет `wptrunner`).

Пункт 1 («снимать браузер по process group, а не по pid») в буквальной
формулировке отвергнут: `run_corpus.py::kill_tree`'s собственный комментарий
уже документирует, что `os.killpg` в этом окружении НЕ достаёт `lumen` —
`wptrunner` кладёт каждый запущенный браузер в СОБСТВЕННУЮ группу, а не в
группу вызывающего, поэтому `killpg` по группе `run_smoke.py` их не видит.
Рабочий эквивалент (обход PID-дерева, что и делает `kill_tree`) уже
существует для таймаутов внутри `run_corpus.py`; для внешнего `kill -9` по
всей сессии эквивалента процессной группе не существует в принципе — единственная
работающая защита в этом случае и есть зачистка при следующем старте, теперь
реализованная выше.

Пункты 3 (не совмещать сборку и прогон WPT) и 4 (`MemoryHigh=` на юните
сессий) не тронуты этим срезом — пункт 3 требует решения о
блокировке/лимите между параллельными P-сессиями (не только тулинговая
правка), пункт 4 явно вне репозитория и требует согласия пользователя (см.
текст пункта в разделе выше). Статус остаётся `OPEN` — из четырёх пунктов
закрыт второй; риск глобального OOM от накопления осиротевших `lumen`
существенно снижен (реап на каждом старте `run_report.py`/`run_corpus.py`),
но архитектурно не устранён для сценариев вне этих двух точек входа (ручные
запуски `run_smoke.py` напрямую, `verify_*.py`-пробы).

## Срез P3 2026-09-13 (пункт 3, закрытие карточки)

Пользователь подтвердил решение по пункту 3: межсессионная блокировка
сборка↔WPT реализуется лок-файлом внутри репозитория, пункт 4 остаётся вне
репозитория и не реализуется (правка системного юнита требует отдельного
согласия и не является тулинговой задачей).

Реализовано: `tests/wpt/heavy_lock.py` — OS-уровневый advisory lock
(`msvcrt.locking` на Windows, `fcntl.flock` иначе; освобождается сам при
любом завершении держателя, включая `kill -9`, в отличие от pid-файла).
Сознательно курьезный, не жёсткий гейт: обе стороны ждут лок не дольше
`timeout` (по умолчанию 5 минут), после чего продолжают без него с громким
предупреждением в лог — жёсткая блокировка позволила бы многочасовому
`--all`-прогону WPT застопорить сборку каждой параллельной P-сессии на всё
время прогона, что хуже редкого OOM, который лок призван снизить.

Подключено в двух точках:
* `run_report.py` — держит лок на время самого прогона (`run_smoke.run`),
  рядом с уже существующими `port_guard.ensure_free`/`reap_lumen_orphans`;
* `run_corpus.py` — держит лок на каждый шард отдельно (`run_shard`), не на
  весь `--resume`'мый прогон целиком: многодневный корпусный прогон иначе
  держал бы лок днями и морил голодом сборки всех сессий на машине, а шард —
  это и есть точка реального всплеска памяти (`--processes` живых `lumen`).

Для сборки — обёртка `scripts/cargo-heavy.sh <cargo-subcommand> [args...]`
(вызывает `heavy_lock.py run --owner "cargo ..." -- cargo ...`), для ручного
использования — `python tests/wpt/heavy_lock.py run --owner LABEL --timeout N
-- <command...>`; `report`/`selftest` — по образцу `port_guard.py --report`/
`--selftest`. Метаданные держателя пишутся в отдельный файл-компаньон
(`.heavy.lock.owner`, атомарная замена через `os.replace`), не в сам
файл лока — на Windows `msvcrt.locking` блокирует байт мандаторно (не только
для записи, но и для чтения из другого хэндла), поэтому диагностическое
чтение через сам файл лока изредка падало бы `OSError`. Оба файла
рантаймовые, добавлены в `.gitignore`, в репозитории не появляются.

`python tests/wpt/heavy_lock.py selftest` — acquire/contend/timeout-fallback/
release, 8/8 проверок зелёные. Ручная проверка конкуренции (holder-процесс
держит лок 5с, второй вызов с `--timeout 2` корректно видит его занятым,
ждёт, логирует предупреждение BUG-1029 и продолжает без лока по истечении
таймаута; после освобождения `report` снова показывает `free`).

Существующее поведение `run_report.py`/`run_corpus.py` не изменилось при
свободном локе (типичный случай — единственная активная сессия) — правка
добавляет только сериализацию при реальной конкуренции с тяжёлой сборкой.
`python -m py_compile` всех трёх изменённых модулей чист; живой WPT-прогон не
требовался — правка не трогает сам конвейер тестирования, только окружающую
memory-дисциплину, что покрывается selftest'ом модуля.

Пункт 4 (`MemoryHigh=` на systemd-юните `run-claude-manager.sh`) закрывается
без реализации — правка вне `D:\RustProjects\lumen-browser\`, запрещена
рабочей границей CLAUDE.md без явного согласия пользователя на конкретное
изменение конфигурации хоста; если тот же класс OOM повторится после этого
среза, годится как следующий шаг, но не тулинговая задача P3.

Все четыре пункта остатка закрыты (1-2 — срез 2026-09-08, 3 — этот срез, 4 —
сознательно оставлен вне репозитория). Статус: `FIXED`.
