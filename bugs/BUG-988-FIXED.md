# BUG-988 — рабочий поток уходит в бесконечный спин на целое ядро и переживает навигации

**Статус:** FIXED 2026-09-05
**Заведён:** 2026-09-04 (наблюдение за живым прогоном корпуса со стороны ОС)
**Область:** js (`crates/js/src/worker.rs::WORKER_SHIM`) / shell (`crates/shell/src/lumen/bfcache.rs::park_current_page`)
**Владелец:** P3

## Симптом

В живом прогоне поток, родившийся в середине сессии, начинает жечь **целое ядро**
и не прекращает до смерти процесса, переживая при этом смену документа во всех
последующих вкладках.

## Что говорит измерение

Наблюдение со стороны ОС (сэмплер 1 Гц, `scripts/observe/watch_lumen.ps1`,
PID 18600, 16:01–16:27):

- поток `tid 17048` создан в **16:10:12** (загружался `costco.com`), последний
  раз замечен в 16:27:30 — за секунду до смерти процесса;
- прирост процессорного времени этого потока: медиана **984 мс на секунду
  наблюдения**, p90 1016 мс; выше 800 мс/с — в **94 %** сэмплов. 1000 мс/с = одно
  ядро целиком;
- он пережил двадцать навигаций: Costco → Medium → Mozilla → W3Schools → ING →
  Coinbase → Snapchat → Internet Archive → Telegraph → Indiatimes → Facebook →
  Instagram → X → LinkedIn → … → конец прогона.

Цена видна в CPU всего процесса — скачок одномоментный и необратимый:

| Отрезок наблюдения | Медиана CPU процесса |
|---|---|
| 16:01–16:10 (до рождения потока) | **4.7 %** |
| 16:10–16:27 (после) | **151.1 %** |

Дельта 146 % — ровно цена одного ядра. Состав сайтов на обоих отрезках
сопоставим, то есть это не «страницы стали тяжелее».

## Диагноз (P3 2026-09-05, статический разбор — без повторного живого прогона)

Цепочка, объясняющая ровно наблюдаемую форму («родился при загрузке одной
страницы, пережил произвольное число последующих навигаций, жрёт целое ядро,
не спит на I/O»):

1. **`crates/shell/src/lumen/bfcache.rs::park_current_page`** (BUG-835) на КАЖДОЙ
   навигации, для которой `bfcache_eligible()` истинно, клонирует
   `Arc<dyn PersistentJs>` живого JS-рантайма уходящей страницы в
   `self.parked_pages` — рантайм остаётся живым «ради будущего
   `history.back()`». Комментарий рядом верно описывает половину эффекта:
   «nothing pumps a parked runtime… so its timers and animation frames are
   paused for exactly as long as the page is in the back/forward cache» — это
   верно для таймеров/rAF самого рантайма (ими управляет внешняя прокачка
   `route_task_js`/`route_query_js`, которая после навигации достаёт только
   активный `js_ctx`), но **не для `Worker`**, у которого своя независимая ОС-нить.
2. **`crates/js/src/worker.rs::run_worker_thread_v8`** (цикл воркера, строки
   ~1798–1827) не завязан ни на что, кроме собственного канала и `close_flag`:
   `loop { … run_worker_tasks(&rt) … rx.recv_timeout(wait) … }`. Он не знает и
   не может узнать, что родительский документ «запаркован» — прокачка сверху к
   нему никогда и не подключалась.
3. Клампинг `setInterval` внутри воркера (`_clamp(delay, nesting)`,
   `crates/js/src/worker.rs`) даёт пол **4 мс** после 5 уровней вложенности —
   до ~250 срабатываний/сек на отдельном потоке; при заметной работе в
   колбэке (аналитика/реклама/ленивая подгрузка — типично для e-commerce вроде
   Costco) это забирает целое ядро активной работой, не блокировкой на I/O.
4. `_lumen_bfcache_blocked()` (`crates/js/src/shim/web_api_shim_mid_b.js`) —
   единственный gate для park-эвристики — проверял только открытый
   WebSocket/EventSource и `unload`/`beforeunload`-хендлеры. Страница с
   активным `Worker` беспрепятственно проходила в `park_current_page`.
5. Эвикция парковки (`PARKED_PAGES_MAX = 2`,
   `crates/shell/src/page_state.rs`) убирает самую старую запись только в
   момент, когда паркуется **новая** eligible-страница. Большинство реальных
   сайтов (WebSocket-аналитика, `beforeunload`) сами не park-eligible — значит
   следующие 20 навигаций из наблюдения park вообще не совершали, запись
   Costco никогда не вытеснялась, и её воркер тикал до самой смерти процесса.

Итого: `park_current_page`/`ParkedPage` — это «условие остановки, завязанное на
жизнь документа», реализованное для таймеров/rAF самого рантайма, но забытое
для уже запущенных `Worker`-потоков того же рантайма (`WorkerRegistry` — поле
`V8JsRuntime`, `crates/js/src/v8_runtime/runtime.rs:198-200`, при обычной,
непаркованной навигации падает вместе с рантаймом и корректно останавливает
воркер через разрыв канала — брешь есть только на park-пути).

Диагноз получен статическим разбором (двумя независимыми проходами, сошедшимися
на одном механизме), не повторным живым прогоном — конкретно тот поток из
наблюдения 16:10:12 живьём не переисследован, см. «Не закрыто этим фиксом» ниже.

## Фикс P3 2026-09-05

`_lumen_bfcache_blocked()` (`crates/js/src/shim/web_api_shim_mid_b.js`) теперь
дополнительно денает park-эвристику при живом `Worker` — новый геттер
`globalThis._lumen_has_active_worker()`, добавленный в `WORKER_SHIM`
(`crates/js/src/worker.rs`), читает уже существующий `_workerRegistry` (main-
thread реестр id → `Worker`-инстанс, заполняемый конструктором и очищаемый
`.terminate()`) и сообщает «есть хотя бы одна живая запись». Страница с активным
`Worker` теперь берёт тот же путь, что страница с открытым WebSocket/SSE —
падает в `bfcache_thaw` (свежий рантайм при восстановлении), а не в
whole-runtime park, так что старый рантайм (и с ним `WorkerRegistry`) дропается
обычным образом при уходе со страницы — ровно как для любой другой
park-ineligible страницы, где воркер уже и так корректно останавливался через
разрыв канала.

Регрессия: `bfcache_blocked_true_when_worker_active` /
`bfcache_blocked_false_after_worker_terminated`
(`crates/js/src/dom/tests/v8_ws_sse.rs`) — создают `new Worker('data:...')` и
проверяют переключение `_lumen_bfcache_blocked()`.

### Проверка фикса

- `cargo test -p lumen-js --features v8-backend` — зелёный (новые тесты + весь
  существующий `bfcache_blocked_*`-набор).
- `cargo clippy -p lumen-js -p lumen-shell --all-targets --features v8-backend
  -- -D warnings` — чисто.
- `cargo test -p lumen-driver --no-fail-fast` (193 теста) и
  `cargo test -p lumen-shell --bins --no-fail-fast` (1722 теста) — зелёные.
- Полный `scripts/scoped-test.sh` не удалось прогнать до конца — замыкание
  обратных зависимостей от `lumen-js` тянет `lumen-driver`, а тот транзитивно
  тянет `lumen-network` в тот же `cargo test`-вызов, и попадает в уже
  задокументированный [BUG-805](bugs/BUG-805-OPEN.md) («гейт не может стать
  зелёным ни на одной правке, чьё замыкание втягивает `lumen-network`»);
  процесс завис без роста CPU, снят вручную. Не регрессия этого фикса — то же
  замыкание виснет на несвязанных правках.

## Не закрыто этим фиксом

- **`SharedWorker`** — тот же класс дефекта, но не через park: соединение
  живёт в процесс-глобальном `HUB_V8`
  (`crates/js/src/shared_worker.rs::hub_v8`, `static OnceLock`), полностью
  независимом от жизни любого конкретного `V8JsRuntime`/park-состояния.
  Ничто в shell не уведомляет хаб о том, что документ, подключившийся к
  `SharedWorker`, ушёл/уничтожен (`close_shared_worker_port_v8` вызывается
  только явным `port.close()` из самого скрипта) — поэтому `SharedWorker`
  переживает НЕ навигацию, а вообще любое закрытие вкладки, до самой смерти
  процесса. Заведён отдельно: [BUG-999](bugs/BUG-999-OPEN.md).
- Сам поток из живого наблюдения 16:10:12 не переисследован повторным живым
  прогоном (Costco → Medium с `LUMEN_PROFILE_TREE=1`/`--features tracy`) —
  диагноз статический. Если после этого фикса аналогичный симптом
  воспроизведётся живьём ещё раз, это будет означать, что триггером был
  `SharedWorker` (BUG-999), а не обычный `Worker`.
