# BUG-425 — вертикальный сайдбар: вкладки нарисованы одна поверх другой, пропал заголовок группы, подписи переносятся

**Статус:** FIXED 2026-07-31
**Компонент:** chrome (`assets/chrome/chrome.html` — `#sbTabs` / `.sb-tab` /
`.sb-section-title`), layout (вертикальная раскладка списка внутри сайдбара,
`crates/engine/layout/src/box_tree.rs::lay_out_inner`)
**Найден:** P1, 2026-07-28, при сверке движкового хрома с макетом
`docs/design/lumen-v3_3.html`
**Исправлено:** P1, 2026-07-31

## Симптом

Ассет хрома, отрисованный движком как страница
(`lumen --screenshot .tmp/chrome-asset.png assets/chrome/chrome.html`,
ширина 1024):

1. **Все элементы списка вкладок нарисованы на одной строке, поверх друг
   друга** (визуально — нечитаемая каша примерно на y≈195). В макете это
   вертикальный список из 5 строк с отступом 4 px и вложенностью (дерево
   вкладок: «Re: правки по релизу» вложен в «Почта — Входящие», «Выписка за
   июль» — в «Т-Банк — Счета»).
2. **Заголовок группы `ВКЛАДКИ · ЛИЧНОЕ` не виден** — в макете он есть над
   списком.
3. Подписи, укладывающиеся в макете в одну строку, переносятся в две:
   «Новое пространство», «Восстановить закрытые».

## Разбор

Пункты 1 и 2 закрылись побочным эффектом фикса BUG-333/343 (flex
writeback, 2026-07-29) — на ревизии 2026-07-31 `--dump-layout` уже показывал
`.sb-tab` на различных `y` и видимый `.sb-section-label`; отдельного фикса не
потребовалось, это подтверждено скриншотом и дампом перед началом работы над
пунктом 3.

Пункт 3 (перенос подписи в две строки) — самостоятельный дефект:
`box_tree.rs::lay_out_inner` безусловно относит **любой** `BoxKind::FormControl`
(`<button>`, `<select>`, …) к «replaced»-элементам CSS 2.1 §10.3.2 и без явного
`width` даёт ему `width: 0` (реплейсед-бокс не растягивается на контейнер).
Это верно для form-контролов с UA-default рендерингом, но неверно, когда автор
явно поставил `display: flex`/`grid` — CSS Display L3 §2.4 блокифицирует бокс в
настоящий flex/grid-контейнер с обычными потомками (в `.ws-add` это
`<svg class="icon">` + `<span class="lbl">`), и его auto-ширина должна
считаться как у обычного блока (заполнить доступное пространство), а не как у
`<img>`/`<video>`. `.ws-add` — кнопка «Новое пространство» в
`flex-direction: column` контейнере `.sb-workspaces` (у него `align-items` по
умолчанию `stretch`) — из-за бага получала ширину 0, и вложенный `<span>` с
текстом переносился в две строки при укладке в почти нулевую доступную
ширину.

**Фикс:** `is_replaced` для `BoxKind::FormControl` теперь `false`, когда
`s.display` — `Flex`/`InlineFlex`/`Grid`/`InlineGrid`; в остальных случаях
(UA-default рендеринг form-контрола) поведение не меняется.

## Побочный эффект

Тот же `<button>` с `display:flex` и без явного `width`, но в контейнере с
`align-items: center`/`flex-start`/`flex-end` (а не `stretch`), тоже теперь
получает auto-ширину = «заполнить контейнер» вместо ожидаемого
shrink-to-fit + позиционирование по кросс-оси. Раньше это маскировалось тем же
багом (реплейсед-элемент давал ширину 0, что визуально было ближе к
content-based размеру, чем к «залить всё»). Конкретный пример — кнопка
«Восстановить закрытые» (`.nt-restore`) в `.newtab{ align-items: center }`:
раньше рисовалась с оверфлоу текста, теперь — на всю ширину `.newtab` вместо
узкой центрированной «таблетки». Корень — `lay_out_flex` вообще не считает
cross-axis alignment для `flex-direction: column` (в коде так и написано:
«column cross axis (width) not handled in wrap Phase 0»). Заведено отдельно:
[BUG-460](BUG-460-OPEN.md).
