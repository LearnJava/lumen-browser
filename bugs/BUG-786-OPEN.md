# BUG-786 — `<![CDATA[` в `<style>` (`.xht`/XHTML) съедает первое правило блока (при единственном правиле — весь встроенный CSS)

**Статус:** OPEN (ДОРАБОТКА → [GAP-XMLDOC](../ROADMAP.md))
**Тип:** нереализованная функциональность, не дефект реализованного кода — ведётся как задача `GAP-XMLDOC` в [ROADMAP.md](../ROADMAP.md), P3 как баг не берёт. Переклассифицировано 2026-09-02 ре-триажем пула WPT-RUN-5/6: срезы заводили багом всё подряд, потому что правила заведения ([docs/probe-method.md §8](../docs/probe-method.md)) тогда ещё не было. Файл сохраняет номер и путь — на него ссылаются CLAUDE.md, STATUS-файлы и python-тулинг, а запись наблюдений остаётся полезной там, где лежит.
**Заведён:** 2026-08-19 (TEST-4, первый смоук-прогон reftest-executor'а)
**Область:** движковый парсинг документов с `Content-Type: application/xhtml+xml` (нет отдельного XML-пути; вероятно `crates/engine/html-parser`)
**Владелец:** P1/P3 (движок). Заведён P2 в ходе тулинговой задачи, здесь не чинится.

## Симптом

Найдено при смоук-прогоне нового reftest-executor'а (TEST-4) на 4 простых
`css/`-reftest-ах: `css/css-backgrounds/background-334.html` дал `FAIL`
(4880 различающихся пикселей) против собственного эталона
`reference/background-334-ref.xht`, хотя тестовая страница рендерится
корректно (см. скриншот теста — залитый зелёный квадрат, чёрная точечная
рамка, без красного — в точности то, что требует условие прохождения).

Эталон `.xht`:

```xml
<style type="text/css"><![CDATA[
div { background-color: #CCC; border: black dotted 5px; width: 150px; }
img {vertical-align: top;}
]]></style>
...
<div><img src="../support/50x50-green.png" height="150" alt="..." /></div>
```

Ожидаемый border-box — 150 (content) + 2×5 (border) = **160×160**, серый фон
под изображением, точечная чёрная рамка. Фактический рендер (`--screenshot`)
— сплошной зелёный квадрат **без рамки и без серого фона**, размер контента
**150×~148** (border не добавлен вовсе). Минимальный repro (`--dump-layout`
на `<style><![CDATA[ div{width:100px;height:100px} ]]></style><div></div>`)
подтверждает: `div` получает `width=1008` (авто, полная ширина родителя) и
`height=0` — объявление не применилось. Читать вместе с разделом «Уточнение
механизма» ниже: в этом репро правило одно, поэтому потеря выглядит полной;
на деле съедается **первое правило каждого CDATA-блока**, а не блок целиком.

## Механизм (подтверждено, не предположение)

`wptserve` отдаёт `.xht`/`.xhtml` с `Content-Type: application/xhtml+xml`
(`tools/wptserve/wptserve/constants.py:6`) — реальным XML MIME-типом, для
которого спецификация требует XML-парсинга документа (и, соответственно,
стандартной XML-семантики CDATA внутри `<style>`).

`application/xhtml+xml` нигде не упоминается в пути загрузки top-level
документа (`grep -rn "xhtml+xml" crates/` находит только
`crates/js/src/dom_parser.rs`/`dom.rs` — это `DOMParser.parseFromString` из
JS, не относится к загрузке страницы) — то есть у Lumen нет отдельного
XML-пути для документов; они уходят в тот же HTML5-токенизатор, что и
`text/html`. По HTML5-алгоритму `<style>` — RAWTEXT-элемент, где
`<![CDATA[`/`]]>` не имеют специального смысла и остаются буквальным
текстом; в результате всё содержимое между тегами становится невалидным CSS
(строка начинается с `<![CDATA[`) и правила не применяются.

Это системный класс проблемы, не специфичный для одного теста: паттерн
`<style><![CDATA[ ... ]]></style>` — стандартная идиома старых
CSS2.1-референсов WPT, сериализуемых как строгий XHTML (DOCTYPE
`-//W3C//DTD XHTML 1.0 Strict//EN`). Масштаб по корпусу не оценивался в
рамках этой сессии (P2-тулинг, не движковая работа) — оценка масштаба и
решение (отдельный XML-парсер для `application/xhtml+xml` vs. частный
CDATA-strip в RAWTEXT-состоянии токенизатора для `<style>`/`<script>`) —
на усмотрение владельца.

## Масштаб по корпусу (замер P2, 2026-08-20, WPT-RUN-5)

Раздел «Механизм» оставлял масштаб неоценённым. Замер сделан инструментом
`tests/wpt/cdata_audit.py` (заведён этой же сессией) по `MANIFEST.json` и по
живому прогону WPT-RUN-5 (107 из 479 шардов, весь `css/CSS2` уже отработал).

**Сколько id задето.** Из 27 386 reftest-id манифеста 7 629 — `.xht`/`.xhtml`,
и у **2 196** из них `<style>` самого теста содержит CDATA, то есть тест
исполняется с полностью выброшенным собственным стилем (1 901 — где CDATA
есть и у эталона, 294 — только у теста, 1 — эталон не разрезолвился).

**Дефект не только валит тесты, но и выдаёт ложные PASS.** Reftest сравнивает
две страницы; если стиль теряют обе, они рендерятся одинаково и пара получает
**PASS**, хотя движок не применил ни одного объявления из проверяемого блока.
Подтверждено напрямую на `css/CSS2/bidi-text/bidi-box-model-001.xht` (стоит
PASS в прогоне): `--dump-display-list` для теста и для его эталона
`bidi-box-model-001-ref.xht` даёт **побайтово совпадающие пять `DrawText` и
ни одной команды рамки**, хотя тест задаёт `span { border: 5px solid gray;
border-color: orange purple teal yellow }`. Оба файла несут CDATA, оба
остались без CSS — вердикт PASS ничего не измерил.

Второй канал ложных PASS — пары, где CDATA только у теста, а эталон
общий вида «здесь нет красного» (`css/CSS2/reference/ref-if-there-is-no-red.xht`).
Выброшенный стиль уносит с собой и красный: `css/CSS2/borders/border-width-013.xht`
(проверяет, что `border-width: 8%` невалиден) проходит именно потому, что
`border-color: red` тоже не применился. Таких PASS в прогоне 74.

**Вклад в цифру.** На отработанных к моменту замера шардах: 2 468 reftest-PASS
всего, из них **451 (18.3 %)** — на тестах с выброшенным инлайн-стилем
(377 «CDATA с обеих сторон» + 74 «только у теста»). Это верхняя граница
инфляции, а не утверждение, что каждый такой PASS ложный. Практическое
следствие: часть PASS после починки превратится в честные FAIL. Считать это
падением цифры **нельзя** — замер среза 14 (раздел «Сторона ЭТАЛОНА» ниже)
показал, что задавленных тем же дефектом FAIL примерно вдвое больше, и в сумме
починка цифру поднимает. Перепроверять тем же `cdata_audit.py`.

## Уточнение верхней границы прямым замером (P2, 2026-08-20)

Граница выше — структурная («у теста есть CDATA»), и она завышена примерно
**впятеро**. `tests/wpt/inert_style_audit.py` спрашивает не исходник, а
движок: рендерит страницу как отдана и с вырезанным всем авторским CSS,
сравнивает display list и layout-дамп; совпали оба — ни одно объявление не
сработало. На случайной выборке 400 из 4 543 reftest-PASS живого прогона
WPT-RUN-5 (seed 786):

* CDATA-класс в выборке — 35 PASS, из них реально «стиль ничего не решил»
  только **7 (20 %)**. У остальных есть работающий CSS помимо CDATA-блока
  (`<link>`, второй `<style>`, атрибут `style`) — CDATA-блок у них всё равно
  потерян, но пара не вырождается в «обе стороны голые».
* По всему набору PASS CDATA-класс — 459 из 4 543 (10.1 %), значит прямая
  оценка вакуумных PASS от этого бага — **около 2 % PASS (~80 тестов)**,
  а не ~460.
* И этот баг — **не главный** механизм вакуумных PASS: из 29 `inert`-PASS
  выборки 22 к CDATA не относятся (11 `.xht`, 9 `.html`, 2 `.svg`).

Читать вместе: падение headline-цифры после починки будет заметно меньше,
чем следовало из структурной границы. Подробности и оговорки (семейство
«негативных» тестов CSS2.1, где inert-рендер — это и есть утверждение теста)
— `docs/tasks/p2-wpt-runner-throughput.md`, срез 12.

## Уточнение механизма прямым замером (P2, 2026-08-20, срез 13): теряется ПЕРВОЕ правило блока, а не блок целиком

Раздел «Механизм» выше говорит «всё содержимое между тегами становится
невалидным CSS и правила не применяются». Первая половина верна, вторая —
нет, и разница крупная.

Замер. Тот же путь загрузки, что в исходном репро (страница по http,
`--dump-layout`), но в CDATA-блоке **несколько** правил:

```html
<style type="text/css"><![CDATA[
#a { width: 100px; height: 100px; }
#b { width: 200px; height: 60px; }
#c { width: 300px; height: 40px; }
]]></style>
```

```
Block rect=(8.00, 8.00, 1008.00, 0.00)                     ← #a  потеряно
Block rect=(8.00, 8.00, 200.00, 60.00)   w=200.00 h=60.00  ← #b  ПРИМЕНИЛОСЬ
Block rect=(8.00, 68.00, 300.00, 40.00)  w=300.00 h=40.00  ← #c  ПРИМЕНИЛОСЬ
```

Причина ровно та, что описана в «Механизме», доведённая до конца: строка
`<![CDATA[` — невалидный старт правила, и CSS-парсер по спеке съедает её как
prelude «плохого правила» вместе с **первым же блоком `{…}`**, то есть
первым авторским правилом. Дальше поток снова валиден. Закрывающий `]]>`
последнее правило не уносит: `#c` стоит прямо перед ним и применяется.
Проверено и на нескольких `<style>` в одном документе (каждый теряет своё
первое правило, независимо), и на `@media screen{…}` в роли первого
конструкта (теряется весь at-блок), и на CDATA, записанной в одну строку с
правилами.

**Почему исходное репро выглядело как полная потеря.** В нём одно правило —
оно же первое, поэтому терялось всё. То же и у
`background-334-ref.xht`: `div{…}` первое (отсюда пропавшие рамка и серый
фон), `img{vertical-align:top}` второе — оно применялось, просто ничего не
видно.

**Сколько это стоит по корпусу.** Во всех `.xht`/`.xhtml` вендоренного WPT
4327 `<style>`-блоков с CDATA; правил в блоке: 1 — **736 блоков (17.0 %)**,
2 — 997, 3 — 1128, 4 — 773, 5 — 259, 6 и больше — 431. То есть **полную**
потерю стиля даёт примерно каждый шестой блок, а в остальных 83 % пропадает
одно правило из нескольких. Это независимо подтверждает прямой замер из
предыдущего раздела (7 из 35 CDATA-PASS, 20 %, оказались реально
вакуумными — тот же порядок, что 17 % блоков с одним правилом) и объясняет
его: вакуумны именно те, где терять было нечего сверх первого правила.

Практических следствий два. Первое: оценивать масштаб по «у теста есть
CDATA» нельзя ни в какую сторону — тест с пятью правилами теряет одно и чаще
всего честно падает, а не вырождается в вакуумный PASS. Второе: приоритет
бага от этого не падает — потеря первого правила на 4327 блоках остаётся
системной, просто её симптом «часть стиля пропала», а не «стиля нет».

## Сторона ЭТАЛОНА: вдвое больший охват и обратный знак (P2, 2026-08-20, срез 14)

Все замеры выше считают документ **теста**. Между тем рефтест — пара, и вторая
её сторона задета вдвое сильнее. По `MANIFEST.json` (27 138 reftest-id с
разрешимым эталоном): CDATA только у эталона — **4 824 id**, у обеих сторон —
1 935, только у теста — 374. Полная потеря стиля эталоном (все его CDATA-блоки
из одного правила) — **4 704 id на 539 файлах**, и **2 470** из них приходятся
на один файл: `/css/reference/ref-filled-green-100px-square.xht`, самый
переиспользуемый эталон корпуса. Его `--dump-display-list` — три `DrawText`
инструкции и ни одного `FillRect`; с выкинутыми маркерами CDATA
(`?lumen_repair=1`) появляется `FillRect (8.00, 27.20, 100.00, 100.00)
#008000ff`. То есть «filled green square» из инструкции у нас не рисует сам
эталон.

Этого не видел ни один прошлый замер: `cdata_audit.classify` читает только
файл теста, поэтому обычный `.html`-тест против `.xht`-эталона всюду стоял
`plain` — «баг не при чём». `blank_render_audit.cdata_class` теперь
двусторонний.

**Знак эффекта на этой стороне обратный.** Исполненные `==`-пары прогона
WPT-RUN-5 в разбивке по потере стиля эталоном: без потери — 16 916 исполнено,
**27.6 %** PASS; полная потеря — 4 617, **7.3 %**; частичная — 2 055, **14.9 %**.
Движок рисует тест правильно, эталон выходит голым, пара падает.

**Цена дефекта, замеренная, а не оценённая.** Режим
`tests/wpt/blank_render_audit.py --repair N` рендерит обе стороны пары дважды —
как отдано и с выкинутыми маркерами CDATA — и сортирует пару в вердикт,
который у неё есть, и в тот, который будет после починки. Прокси вердикта —
побайтовое равенство display list (достаточно для совпадения пикселей, не
необходимо, поэтому всякая посчитанная подвижка реальна). Выборка 150 + 150 из
733 PASS и 6 313 FAIL, у которых CDATA есть хоть на одной стороне:

* записанный **FAIL** → PASS после починки: **12 из 150 (8.0 %)**, прокси
  воспроизводит вердикт на всех 150 → **не менее 505** PASS прибавится;
* записанный **PASS** → FAIL: **19 из 150 (12.7 %)**, прокси читает 46 из 150 →
  **от 93 до 303** PASS убудет.

Итог: починка даёт **чистый плюс 200…410 reftest-PASS** (сейчас на `==`-парах
набрано 5 319). Стоявшая с 2026-08-20 оговорка «после починки headline может
УПАСТЬ» верна лишь наполовину: падение есть, но подъём примерно вдвое больше.
Публиковать обе половины. Подробности и оговорки — срез 14 в
`docs/tasks/p2-wpt-runner-throughput.md`.

## Вторая грань того же корня: самозакрывающиеся теги (срез 11, 2026-08-21)

Потеря CDATA — не единственное следствие отсутствия XML-пути. HTML5-токенизатор
игнорирует `/>` у не-void-элемента, поэтому в `.xhtml`/`.xht`-документе
`<div class="a"/>` открывает `<div>` и не закрывает его: следующий
`</div>` съедает именно его, а внешний контейнер остаётся открытым. Ряд из N
**сестринских** элементов превращается в цепочку из N **вложенных**.

Замерено по корпусу: самозакрывающиеся не-void теги есть в **447 из 14 004**
`.xhtml`/`.xht`-файлов, из них 39 — с 18 и более такими тегами.

Само по себе это «всего лишь» неверное дерево, но в связке с
[BUG-802](BUG-802-FIXED.md) (layout вложенного `flex-direction: column` стоит
O(2^глубины)) оно вешает браузер: пять файлов
`css/css-flexbox/flexbox-justify-content-vert-*.xhtml` с 27 такими тегами
подряд не раскладываются и за минуту, и в снимке WPT-RUN-5 стоили 318
TIMEOUT-вердиктов (каждая повесила процесс браузера на весь остаток шарда).
Проверка прямая: те же 27 контейнеров с корректно закрытыми детьми
(`<div class="a"></div>`) раскладываются за 96 мс.

## Третья грань того же корня: `<script>` (срез 16, 2026-08-21)

CDATA и самозакрывающиеся теги описывают, что происходит с **вёрсткой**.
Скрипты страдают от того же отсутствия XML-пути, и именно это превращает тест
не в «отрендерился не так» (FAIL), а в TIMEOUT: движок никогда не доходит до
`testharness.js` или до тела теста, страница молчит, `wptrunner` убивает её по
таймауту. Три конструкции, каждая измерена отдельной страницей в живом окне
(`tests/wpt/verify_document_and_record_gaps.py`, таблица в его docstring):

1. **Префиксный `<h:script src="/resources/testharness.js"/>`** — XML-парсер
   разрешает префикс `h:` в XHTML-namespace, HTML-парсер видит неизвестное имя
   элемента `h:script`. Скриптом такой узел не становится: внешний файл **даже
   не запрашивается** — в логе прогона у каждого
   `dom/nodes/Element-*-svg.svg` есть `Распарсено: 36 DOM-узлов … 9
   paint-команд` и ни одного `GET /resources/testharness.js`. Проба:
   варианты `svg-doc-external` (нет GET) и `svg-doc-inline` (нет ни маркера,
   ни исключения).
2. **Самозакрывающийся `<script src="..."/>`** — в XML тег закрыт, в HTML
   `/>` игнорируется и всё до ближайшего `</script>` становится **текстом**
   этого элемента. Первый такой тег съедает остаток документа: у
   `css/cssom/MediaList2.xhtml` в логе есть `Загружен скрипт: testharness.js`
   и нет ни `testharnessreport.js`, ни тела теста, хотя preload-сканер нашёл
   оба. Проба: `xhtml-selfclosed-script` — внешний файл грузится, ни один
   маркер после него не печатается.
3. **`<![CDATA[` в начале инлайнового скрипта** — в HTML это не разметка, а
   первые символы текста скрипта, то есть синтаксическая ошибка:
   `script error: JS runtime error: Unexpected token '<'`. Дальше её съедает
   [BUG-591](BUG-591-FIXED.md) (исключение не долетает ни до одного
   слушателя), поэтому наружу не выходит ничего. Проба: `xhtml-doc` и
   `svg-root-cdata-script` против `xhtml-inline-plain` и

## GAP-XMLDOC срез 1: CDATA-обёртка снята (P1, 2026-09-13)

Первая грань («потеря CDATA в `<style>`/`<script>`») починена точечно, без
полноценного XML-парсера. `crates/engine/html-parser/src/xml_cdata.rs`
(`strip_cdata_wrapper`) снимает одиночную обёртку `<![CDATA[ ... ]]>` (с
допуском окружающих пробелов) с RAWTEXT-содержимого; вызывается из
`tree_builder::mode_text` на `</style>`/`</script>`/`</noframes>`, только
когда `IncrementalTreeBuilder::xml_mode` включён — новая точка входа
[`lumen_html_parser::parse_xml_flavoured`], а не изменение поведения
`parse()` по умолчанию (HTML5-семантика для обычных документов не тронута,
`plain_parse_does_not_strip_cdata` — регрессионный тест на это).

Точка вызова — `crates/shell/src/page_pipeline.rs::parse_and_layout`:
`is_xml_flavoured_document` решает по MIME (`application/xhtml+xml`,
`image/svg+xml`, `…+xml`, `application(text)/xml`) и, если тип отсутствует
или общий, по расширению адреса (`.xhtml`/`.xht`/`.svg`).

Закрывает часть 3 («`<script>`», срез 16) — случай «`<![CDATA[` в начале
инлайн-скрипта» — тем же механизмом, поскольку он тоже RAWTEXT-обёртка.
Не закрывает: самозакрывающийся `<script src="…"/>` (срез 16, случай 2),
префиксный `<h:script>` (случай 1), самозакрывающиеся не-void теги вообще
(срез 11) — остаётся за GAP-XMLDOC, следующие срезы.

## GAP-XMLDOC срез 2: самозакрывающиеся теги в XML-режиме (P1, 2026-09-13)

Закрывает «Вторая грань» (срез 11) и случай 2 из «Третьей грани» (срез 16):
`<div class="a"/>` больше не открывает элемент, который никогда не
закрывается. Механизм — новый `IncrementalTreeBuilder::push_open_element`
(`tree_builder.rs`): в обычном HTML5-разборе (`parse`) self-closing флаг
не-void элемента по-прежнему игнорируется (спека этого и требует — иначе
`<br/>текст` вёл бы себя иначе, чем должен); в `xml_mode` (тот же флаг,
что и CDATA-срез — переименован из `xml_cdata_mode` в `xml_mode`, теперь у
него два потребителя) элемент, помеченный `self_closing`, вставляется в
дерево и сразу же снимается со стека открытых элементов — реального XML-
парсера как не было, так и нет, но для целей уже открытого тестового
корпуса разница не видна.

Покрыты вызовом `push_open_element` (пять мест `mode_in_body`, где
push не переключает insertion mode): generic block elements (`is_block_element`
— то самое `<div>`, из-за которого 27 `flexbox-justify-content-vert-*.xhtml`
висли на O(2^глубины) [BUG-802](BUG-802-FIXED.md)), `h1..h6`, `li`, `dt`/`dd`
и generic fallback (любой другой неспециальный тег). RAWTEXT-элементы
(`title`/`style`/`script`/`noframes`, `mode_in_head`) получили отдельную
правку: раньше self-closing тег всё равно толкался в open_elements и
переключал builder в `Text`-режим, где generic StartTag не обрабатывается —
следующая разметка (`<p>after</p>` после `<script src="…"/>`) молча
терялась вместо того чтобы стать соседом. Теперь в `xml_mode` self-closing
`<script>`/`<style>`/`<noframes>`/`<title>` не толкается на стек и не
переключает режим вовсе — ведёт себя как `<meta>`/`<link>`.

**Сознательно не тронуто** (осталось на следующие срезы GAP-XMLDOC):
`<table>`/`<select>`/`<button>` и formatting-элементы (`<a>`,
`<b>`, …) — их push-сайты попутно переключают insertion mode или трогают
active-formatting-list; self-closing версия каждого из них потребовала бы
отдельного разбора, что делает mode/список согласованным после немедленного
pop, а самозакрывающиеся `<table/>`/`<select/>` не встречены ни в одном
измерении корпуса этого бага — расширять `push_open_element` на них без
измеренного случая было бы гаданием. Токенизатор (`tokenizer.rs`) не тронут:
self-closing флаг для RAWTEXT-тегов он вычисляет верно уже с самого первого
коммита крейта, разница была только в tree builder.

## GAP-XMLDOC срез 9 (2026-09-14): self-closing `<textarea/>` в xml_mode

Закрывает `<textarea>` из списка «сознательно не тронуто» выше — единственный
измеренный по корпусу случай (`grep -rlE '<textarea([[:space:]][^>]*)?/>'` по

Причина была не в токенизаторе (self-closing флаг для RCDATA он и так вычисляет
верно), а в том, что стартовый тег `<textarea>` обрабатывается в
`mode_in_body`, а не в `mode_in_head` — RAWTEXT-фикс среза 2
(`title`/`style`/`script`/`noframes`) правил только `mode_in_head`, ветка
`<textarea>` в `mode_in_body` продолжала матчить `Token::StartTag { ref name,

элемент на `open_elements` и переключала `insertion_mode` в `Text` — тот же
паттерн, что чинил срез 2, только в другом месте разбора.

Правка — ровно тот же приём, что уже применён к `title`/`style`/`script`/
`noframes` (`if !(self.xml_mode && self_closing) { push; switch mode }`),
только на сайте `<textarea>`. Обычный HTML5-разбор (`parse`, `xml_mode ==
false`) не изменился — self-closing по-прежнему игнорируется на не-void
элементе, `<textarea/>` продолжает открывать реальный `<textarea>`, чьё
содержимое тянется до `</textarea>`.

Тесты: `xml_flavoured_self_closing_textarea_does_not_swallow_following_markup`
(в `xml_mode` `<textarea/><p>after</p>` — `<p>` должен выжить соседом, не
потеряться в тексте textarea) и
`plain_parse_self_closing_textarea_still_consumes_following_text` (обычный
`parse` не регрессирует). `cargo test -p lumen-html-parser` — 455/455 юнит +
9/9 интеграционных зелёные. `cargo clippy -p lumen-html-parser --all-targets
-- -D warnings` — чисто. `scripts/scoped-test.sh` (все обратные зависимости) —
зелёный, кроме того же чужого дрейфа CPU-эталонов

## GAP-XMLDOC срез 16 (2026-09-14): self-closing `<table>`/`<select>`/`<button>` в xml_mode — не «неизмерено», а живой дефект (`p1-gap-xmldoc-srez16`)

Срез 11 (общий ре-замер) записал `<table>`/`<select>`/`<button>`
self-closing как «0 хитов по корпусу, остаётся неизмеренным» и явно
предупредил: «расширять `push_open_element` на них без измеренного случая
было бы гаданием». Взял этот пункт как первую строку `STATUS-P1.md`
(`ROADMAP.md:896`) и вместо очередного grep по корпусу написал целевой
юнит-тест на сам механизм (`xml_flavoured_self_closing_table_select_button_do_not_nest_siblings`)
— он не прошёл: `<table/><select/><button/>` вложились друг в друга вместо
того, чтобы остаться соседями, тем же паттерном, что «Вторая грань» этого
бага описывала для `<div/>` до среза 2.

**Причина — не «неизмерено», а отдельный, необобщённый push-сайт.**
`table`/`select`/`button` в `mode_in_body` — единственные три
не-RAWTEXT-элемента во всём `mode_in_body`, что вставляются через голый
`self.open_elements.push(el)` вместо `push_open_element(el, self_closing)`,
и при этом деструктурируют токен как `Token::StartTag { ref name, ref attrs, .. }`
— поле `self_closing` не просто не учитывается, оно даже не связывается с
именем. Срез 2 обобщил `push_open_element` на пять мест `mode_in_body` и
явно назвал два класса, которые он НЕ тронул: RAWTEXT-элементы (закрыты
отдельно срезами 2/9) и эти три, потому что каждый из них ещё и
переключает `insertion_mode` (`InTable`/`InSelect`) или трогает
active-formatting — что требует решения, переключать ли режим при
немедленном self-closing pop, не просто скопировать вызов.

Фикс — тот же приём, что уже применён к `<textarea>` (срез 9): деструктурировать
`self_closing`, звать `push_open_element(el, self_closing)` вместо голого
`push`, и переключать `insertion_mode` только если элемент реально остался
открытым (`!(self.xml_mode && self_closing)`) — для `<button>` этого шага
не требуется, он не меняет insertion mode ни при каком исходе. Обычный
HTML5-разбор (`parse`, `xml_mode == false`) не регрессирует:
`push_open_element` уже безусловно игнорирует `self_closing` вне
`xml_mode`/foreign content, так что `insertion_mode`-переключение
происходит как раньше на каждом self-closing `<table>`/`<select>`.

Тест: `xml_flavoured_self_closing_table_select_button_do_not_nest_siblings`
(`tree_builder.rs`) — `<table/><select/><button/>` в xml_mode дают три
соседних элемента `<body>`, не три уровня вложенности. `cargo test -p
lumen-html-parser --lib` — 470/470 зелёные (был 469, включая новый тест).
`cargo clippy -p lumen-html-parser --all-targets --profile dev-release --
-D warnings` — чисто. `tree_builder.rs` пересёк собственный baseline (5416
→ 5455 строк), `scripts/file-size-baseline.tsv` обновлён тем же коммитом.

## GAP-XMLDOC срез 17 (2026-09-14): self-closing `<a>`/formatting elements/`<nobr>` в xml_mode — тот же необобщённый push-сайт, что срез 16 (`p1-gap-xmldoc-srez17`)

Взял следующую невычеркнутую строку `STATUS-P1.md` (`ROADMAP.md:896`,
всё ещё GAP-XMLDOC) и следующий пункт из инвентаря `docs/engine-gaps.md`,
оставленного срезом 16 открытым: «self-closing formatting elements (`<a>`,
`<b>`, …, active-formatting-list-touching, всё ещё неизмерено)».

**Тот же класс дефекта, что и срез 16, третий по счёту push-сайт того же
рода.** `<a>`, двенадцать §13.2.4.3 formatting-элементов
(`is_formatting_element`) и `<nobr>` — три отдельных match-рукава в
`mode_in_body`, все три вставляют элемент голым
`self.open_elements.push(el)` вместо `push_open_element(el, self_closing)`,
и ни один не деструктурировал `self_closing` из токена вовсе (у `<a>`
паттерн был `ref name, ref attrs, ..` — поле терялось на границе
деструктуризации, как у `table`/`select`/`button` до среза 16).

Фикс — тот же приём: деструктурировать `self_closing`, заменить голый
`push` на `push_open_element(el, self_closing)`. Бэкенд-логика
active-formatting (`push_active_formatting`) не тронута и не должна
быть — она уже тег-агностична и одинаково работает независимо от того,
остался ли элемент открытым на `open_elements`.

**Важное отличие от div/table/select/button: `push_active_formatting`
не убирает элемент из active-formatting при self-closing pop.** Значит
самозакрытый `<b id="x"/>`, за которым следует текст или другой
formatting-старт-тег, всё ещё триггерит `reconstruct_active_formatting()`
(она — первая инструкция в каждом из этих рукавов и в обработке текста)
и оборачивает следующий контент в НОВЫЙ клон `<b>` — это корректное
§13.2.4.3 "residual style"-поведение (то же самое произошло бы с `<b>`,
неявно закрытым посторонним конечным тегом), не относится к этому фиксу
и не должно тестироваться как «должны остаться соседями» — первая версия
теста именно на этом ловилась (`<a/><b/><nobr/>` реконструирует `<a>`
как обёртку `<b>` ещё ДО фикса, потому что рукав `<b>` тоже начинается с
`reconstruct_active_formatting()`, независимо от пуш-сайта). Проверяемый
здесь эффект — исключительно про `open_elements`: то, что НЕ триггерит
реконструкцию (например `<li>`, чей рукав её не вызывает), должно стать
соседом самозакрытого formatting-элемента, а не его потомком.

Тесты (`tree_builder.rs`):
- `xml_flavoured_self_closing_formatting_elements_do_not_nest_siblings` —
  `<b id="x"/><li id="y">tail</li>` в xml_mode: `<li>` — сосед
  самозакрытого `<b>`, не его потомок (`<li>` намеренно выбран как проба:
  его рукав не вызывает `reconstruct_active_formatting`, поэтому
  изолирует эффект `open_elements`-стека от реконструкции).
- `xml_flavoured_self_closing_formatting_element_reconstructs_for_trailing_text`
  — документирует то самое НЕ являющееся багом reconstruction-поведение:
  `<b id="x"/>tail` даёт `<body>` с двумя детьми — исходный самозакрытый
  `<b>` и новый реконструированный `<b>`, оборачивающий `tail`.

`cargo test -p lumen-html-parser --lib` — 472/472 зелёные (было 470,
включая два новых теста). `cargo clippy -p lumen-html-parser --all-targets
--profile dev-release -- -D warnings` — чисто. `tree_builder.rs` пересёк
собственный baseline (5455 → 5527 строк), `scripts/file-size-baseline.tsv`
обновлён тем же коммитом только для этой строки — остальные 11 файлов уже
были выше своих baseline-чисел на момент старта (чужой недокоммиченный
дрейф, не относящийся к этому срезу; не трогаю их записи, чтобы не
прикрывать чужой рост своим коммитом).

Остаток по-прежнему открыт: сама область «нет настоящего XML-парсера»
как таковая.

**Не в этом срезе:** сама архитектура полноценного XML-парсера. (Строка

## GAP-XMLDOC срез 21 (2026-09-15): `<!DOCTYPE html [ ... ]>` internal subset в xml_mode (`p1-gap-xmldoc-srez21`)

Срез 20 закрыл последний известный push-сайт self-closing-класса; следующая
невычеркнутая строка `STATUS-P1.md` (`ROADMAP.md:896`) снова потребовала
новый измеренный случай, не «ещё один тег». Найден им же приёмом grep по
вендоренному корпусу (`<!DOCTYPE[^>]*\[`) — **11 файлов**, из которых три
реальные testharness-проверки, не reftest/manual-фикстуры:
`dom/nodes/ProcessingInstruction-in-doctype.xhtml`,
`dom/nodes/Comment-in-doctype.xhtml`, `css/cssom/xml-stylesheet-pi-in-doctype.xhtml`
— все три с телом вида `<!DOCTYPE html [<?x y?>]><html ...>` /
`<!DOCTYPE html [<!--x-->]><html ...>`.

**Причина — отдельный класс от self-closing (срезы 2/16-20): не push-сайт
дерева, а сам токенизатор DOCTYPE.** `Tokenizer::consume_doctype`'s bogus
DOCTYPE state (ветка «съесть всё до `>`») по HTML5 спеке безусловно
останавливается на первом `>` — верно для HTML, где internal subset не
существует вовсе, но `<?x y?>` или `<!--x-->` внутри `[...]` несут свой
собственный `>` раньше настоящего конца DOCTYPE-токена. Результат до
фикса: `<!DOCTYPE html [<?x y?>]>` токенизируется как DOCTYPE, оборванный
на `?>`, а `]>` остаётся отдельной, ничем не защищённой разметкой на
верхнем уровне документа — `documentElement` перестаёт быть прямым
соседом doctype-узла.

**Фикс — только в xml_mode, тем же приёмом изоляции, что CDATA/self-closing
(флаг, не смена поведения `parse()` по умолчанию).** Новое поле
`Tokenizer::xml_mode` (сеттер `set_xml_mode`, по аналогии с
`cdata_allowed`, но взводится один раз, не перед каждым токеном — режим
документа не меняется по ходу разбора) добавлено в `Tokenizer` и
`PushTokenizer` (тот создаёт внутренний `Tokenizer` заново на каждый
`tokenize()`-вызов, так же, как уже делает с `cdata_allowed`). `run_pull`
взводит его из `builder.xml_mode` сразу после создания токенизатора;
`parse_xml_flavoured` синхронизирует то же на `builder.tokenizer` (push
путь `IncrementalTreeBuilder::feed`), хотя реальный вызывающий сейчас
всегда использует pull (`page_pipeline.rs`) — тот же принцип, что держит
pull/push паритетными по всем предыдущим срезам GAP-XMLDOC.

В `xml_mode`, после имени/PUBLIC/SYSTEM identifiers, если следующий
непробельный символ — `[`, токенизатор пропускает internal subset:
считает вложенность `<...>`-конструкций (глубина растёт на `<`, падает на
`>` только если глубина > 0) и ищет `]` именно на глубине 0 — тот самый
случай, когда `>` внутри `<?...?>`/`<!--...-->` не может преждевременно
закрыть subset. После него — обычный поиск финального `>`, не тронутый.

Тесты: три в `tokenizer.rs`
(`doctype_internal_subset_with_pi_ignored_without_xml_mode` — регрессионный
якорь на HTML5-поведение без флага,
`doctype_internal_subset_with_pi_in_xml_mode`,
`doctype_internal_subset_with_comment_in_xml_mode`) и один в
`tree_builder.rs`
(`xml_flavoured_doctype_internal_subset_with_pi_does_not_break_root_structure`
— строит документ целиком через `parse_xml_flavoured` и проверяет, что
корень — ровно `[doctype, html]`, без разбитых остатков subset). `cargo
test -p lumen-html-parser --lib` — 480/480 зелёные (было 476). `cargo
clippy -p lumen-html-parser --all-targets -- -D warnings` — чисто.
`tree_builder.rs` пересёк собственный baseline (5657 → 5684),
`scripts/file-size-baseline.tsv` обновлён тем же коммитом только для этой
строки. `scripts/scoped-test.sh` (все обратные зависимости) — тот же
