# BUG-998 — `history.back()`/`forward()` через JS не доводят document_ready, следующий `eval` теряет JS-контекст

**Статус:** OPEN
**Заведён:** 2026-09-04 (смоук-тест нового режима `--mode session` в `scripts/perf_audit.py`, AUDIT-1)
**Область:** вероятно js (`crates/js/src/dom.rs` — `_lumen_history_go`/`_lumen_history_traverse`) / shell (`navigation.rs::navigate_by`, кросс-документный path из BUG-835)
**Владелец:** P3

## Симптом

Кросс-документный `history.back()`/`history.forward()`, вызванный со стороны
страницы (`eval` через MCP, не шелл-навигация), после навигации между двумя
разными сайтами:

1. `history.back()` выполняется без ошибки;
2. последующий `wait document_ready` (таймаут 5с, до этого пробовал 40с — тот
   же исход) НЕ дожидается готовности — `Wait error: wait timeout:
   DocumentReady`;
3. следующий `eval` на той же вкладке падает с `Eval error: JS context not
   available` — то есть страница осталась в состоянии без рабочего
   JS-рантайма, а не просто «готовность ещё не наступила».

Voспроизведено дважды подряд (свежий процесс каждый раз), детерминированно:

```
python scripts/perf_audit.py --mode session --only example --only hn \
    --session-tabs 2 --dwell 1 --scroll-ticks 1 --timeout 40
```

Последовательность: `new_tab(example.com)` → `new_tab(hn)` → `navigate(example.com)`
→ `wait document_ready` (OK) → `navigate(hn)` → `wait document_ready` (OK) →
`eval("history.back()")` → `wait document_ready` (**TIMEOUT**) →
`eval("history.forward()")` → `wait document_ready` (**TIMEOUT**) →
`eval("document.querySelectorAll('iframe').length")` на этой же вкладке →
**`JS context not available`**.

## Почему это похоже на отдельный дефект, а не на уже известные

- [BUG-835](BUG-835-FIXED.md) (FIXED 2026-08-23) чинил ровно такой класс —
  «`history.back()` через границу документа замораживает страницу» — фиксом
  `ParkedPage` (живой JS-рантайм паркуется целиком, а не сбрасывается). Это
  наблюдение похоже на регрессию того фикса **либо** на путь, который он не
  накрыл: там репро — обход НАЗАД с восстановлением, здесь дополнительно
  падает `forward()` следующим шагом и вообще теряется JS-контекст (BUG-835
  фиксировал зависание, не потерю контекста).
- [BUG-973](BUG-973-OPEN.md) (OPEN) — про резолюцию `delta` при сдвиге стека
  МЕЖДУ вызовом и дренажом очереди в том же тике (конкурентные same-document
  навигации). Здесь один-единственный вызов на вкладку между двумя `wait`,
  без конкурентных навигаций — другая форма.

Ни один из двух не описывает именно «второй `eval` теряет JS-контекст» —
похоже на новый фасет, но точная линия к первопричине не пройдена (не входит
в объём AUDIT-1, которым это найдено).

## Первый шаг

Живой пробой сузить: (1) тот же сценарий, но `history.back()` в пределах
ОДНОГО документа (fragment/pushState) — если ОК, дефект специфичен для
кросс-документного пути `ParkedPage`; (2) добавить `LUMEN_FRAME_LOG=2` вокруг
вызова, посмотреть, доходит ли обход до шелла и что делает `bfcache_thaw`
после фикса BUG-835.

## Как это блокирует

`scripts/perf_audit.py --mode session` (режим C дорожки AUDIT-1) не может
доверять шагу «назад-вперёд» — он стабильно даёт `DEGRADED`, а шаг «фрейм»
следом каскадно ломается тем же самым (общий JS-контекст вкладки). Режим
сам по себе рабочий (открытие вкладок/скролл/попап/приближённое закрытие
работают), это не блокирует его использование, просто эти два под-исхода
сейчас не несут сигнала.
