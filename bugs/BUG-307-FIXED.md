# BUG-307: UI-поток «не отвечает» на тяжёлых вкладках; сессия умирает необратимо

**Статус:** FIXED 2026-08-06 (корень минимального однотабового репро на ria.ru; см. «Срез 2026-08-06 (P3) — найден и исправлен корень» ниже. Первоначальный 14-вкладочный RAM-pressure сценарий из отчёта 2026-07-17 этим фиксом НЕ переверифицирован — см. заметку в конце)
**Дата:** 2026-07-17
**Компонент:** shell (main thread) / ADR-016 (границы off-thread не покрывают этот путь)
**Найден:** живой перф-аудит `/lumen-perf-audit`; «приложение не отвечает» видел пользователь вживую

## Симптом

Метрика IsHungAppWindow (та же эвристика, по которой Windows пишет
«Не отвечает») в живом прогоне 14 вкладок (docs/perf/runs/2026-07-17-live.json):

```
lenta  hung=2.5с
ria    hung=39.0с   (окно висело всё время обработки после загрузки)
rbc    hung=47.5с   ready=23.4с
stackoverflow / habr — окно зависло НЕОБРАТИМО (даже navigate/new_tab
  отваливаются по «automation command timed out») → авторестарт харнесса
```

В прогоне без рестартов (2026-07-17, первый live-прогон): после
github (2.1 ГБ) + stackoverflow (3.4 ГБ) окно умерло навсегда — habr, mdn,
rbc не загрузились вовсе (TIMEOUT 240с каждый), хотя поодиночке эти сайты
грузятся за секунды. Для пользователя это «браузер завис, надо убивать
процесс» — худший класс UX-дефекта.

## Наблюдения

- Корреляция с RAM: необратимое зависание наступает после вкладок-гигантов
  (BUG-306); после авторестарта окна те же сайты грузятся нормально
  (crates 1.7с, docs-rs 1.1с, mdn 3.2с).
- Обратимые зависания (39–48 с на ria/rbc) — похоже на длинные синхронные
  участки на main thread (paint/layout/JS-дренаж), несмотря на влитые
  ADR-016 M0–M4 (off-thread layout/render существуют — проверить, какие
  пути всё ещё блокируют event loop).

## Ожидание

UI-поток не блокируется дольше сотен миллисекунд независимо от тяжести
вкладки; деградация допустима (janky-кадры), смерть сессии — нет.
Возможно нужен watchdog + принудительная выгрузка вкладки-агрессора.

## Диагностика

`LUMEN_FRAME_LOG=1` + Tracy на живом окне github→stackoverflow;
`scripts/perf_audit.py --only github --only stackoverflow --only habr`
воспроизводит за ~5 минут (колонка «не отвечает, с» в сводке).

## Повторный прогон 2026-07-20

Воспроизводится после S12b-18/BUG-297/316/308: два независимых полных
прогона корпуса (`docs/perf/runs/2026-07-20-live.json`, движок `a014c9e6`),
в обоих github.com HUNG → авторестарт харнесса; во втором прогоне
habr.com тоже HUNG → авторестарт (ранее в стабильном режиме habr грузился).
В первом прогоне (сразу после `cargo build`, машина была под нагрузкой
антивируса на свежий бинарник — см. ниже) зависания были тяжелее: после
github-рестарта crates/habr/rbc не смогли получить даже новую вкладку
(`Navigate error: automation command timed out`, «без вкладки» в сводке) —
это утяжелённый вариант того же необратимого каскада, а не новый класс
дефекта. Второй прогон (тёплый бинарник, чуть более спокойная машина)
восстанавливался штатно после github-рестарта — crates/docs-rs/stackoverflow
после него снова OK, что подтверждает наблюдение «после авторестарта
сайты грузятся нормально» из первого репорта.

**Важная методологическая находка:** оба прогона 2026-07-20 показали
равномерно завышенное время готовности (`ready_s`) почти на всех сайтах
относительно `2026-07-17-live.json` (+56%…+1290%, включая тривиальные
example.com/hn.com). Проверено headless `--phases` на crates.io/docs.rs
изолированно — там всё быстро и в норме (screenshot totals 1.8с),
т.е. это НЕ регрессия движка, а шум самого живого многовкладочного
харнесса (машина только что закончила 13-минутную сборку; плюс сама
конструкция кумулятивной RAM/множества вкладок в одном окне не даёт
чистого per-site таймингa). Живой Δ%-сравнение по `ready_s` признано
непригодным для детекции регрессий — использовать `--phases` для этого
впредь, живой прогон — только для RAM/hung/JS-ошибок/визуальной приёмки.

## Срез 2026-08-05 (P3) — минимальный однотабовый репро, не требует мульти-таб RAM-давления

Найдено при попытке измерить остаток BUG-286 (`content-visibility` scroll-стопор)
живым скроллом на ria.ru: скролл вообще не понадобился — окно стало полностью
неотзывчивым на любую automation-команду (`scroll`, `eval`) уже через ~1с
после `[bench] first non-empty frame`, на **одной свежей вкладке**, без
предшествующих тяжёлых вкладок (github/stackoverflow из прежних прогонов).
Это меньший и куда более быстрый репро, чем 14-вкладочный `/lumen-perf-audit`,
описанный выше.

**Как воспроизвести** (одна команда, `--mcp-live-port`, без предварительных
вкладок):

```
target/dev-release/lumen.exe --mcp-live-port <port> about:blank
# navigate → https://ria.ru
# wait document_ready, дождаться "[frame:cold-start] RenderDone" в stderr (~9-10с)
# любая automation-команда (scroll/eval) после этого: "automation command timed out"
```

**Замеры этого среза:**

- `TotalProcessorTime` процесса (PowerShell `Get-Process`) абсолютно плоский
  все 15+с окна зависания (5250мс, ни на мс не растёт) — **не busy-loop**
  (0% CPU), а настоящий deadlock/parked-без-пробуждения: ни таймеры JS
  (виден периодический `cm.ria.ru/chat/info`-поллинг каждые ~10с ДО зависания,
  ноль повторов ПОСЛЕ), ни сеть, ни фреймы не идут вообще.
- 5 последовательных `eval` попыток по 30с (`AutomationHandle::DEFAULT_TIMEOUT`,
  `crates/driver/src/live_session.rs:38`) — **все 5 таймаутят**, т.е. окно
  не отвечало ≥150с непрерывно на одной вкладке без какого-либо давления
  памяти от других вкладок. Это дольше, чем «обратимые 39-48с» из прогона
  2026-07-17 — возможно, дело не в объёме памяти корпуса, а в чём-то
  специфичном для конкретной страницы/сессии (см. ниже).
- **Проверено и отклонено:** `LUMEN_NO_ENGINE_THREAD=1` (откат ADR-023,
  синхронный layout на UI-потоке) — зависание воспроизводится идентично,
  то есть корень НЕ во флипе движкового потока 2026-07-28.
- **Контрольный тест:** тот же automation-канал (scroll/eval) на локальной
  статической странице (`samples/page.html`) после явного 15-секундного
  простоя (специально дольше, чем реальный idle-park происходит на живом
  окне) отвечает моментально (1-5мс) — то есть штатное `ControlFlow::Wait`
  парковка + `EventLoopProxy`-пробуждение (`AutomationHandle::execute`,
  `crates/driver/src/automation.rs:79-83`) работают исправно там, где нет
  фоновой JS/сетевой активности реальной страницы. Зависание — не общая
  регрессия механизма парковки/пробуждения, а нечто, специфичное для
  состояния, в которое попадает вкладка именно на ria.ru (или похожих
  сайтах с фоновыми таймерами/service-worker-подобной активностью).
- **Побочное наблюдение по логу** (не проверено как причина): непосредственно
  перед зависанием страница успевает залогировать `### Service worker
  register` (собственный `console.log` страницы) и тут же поймать
  `fetch error: invalid url: invalid url: missing scheme:
  "/firebase-messaging-sw.js"` — паттерн той же семьи багов, что
  BUG-346/347/359/362/370 (относительные URL не резолвятся) и особенно
  **BUG-638** (`<audio>.src` с относительным URL перманентно вешает
  JS-движок/automation-канал: нативный вызов никогда не возвращается в JS,
  ноль вывода в консоли, 0% CPU) — тот же класс симптома («нативный вызов
  из JS не возвращается, канал глохнет насмерть, без единой ошибки в
  консоли»), возможно тот же корень применительно к попытке service-worker
  fetch с относительным URL вместо `<audio>`. Не подтверждено — нужен
  дебаггер/трасса конкретно этого пути (`navigator.serviceWorker.register`
  → внутренний fetch), это следующий шаг для того, кто продолжит.

**Вывод для приоритизации:** пока не закрыт этот баг, любая работа над
BUG-286/«Задачей 3» (частичный пересчёт каскада, `docs/tasks/p3-cascade-perf.md`)
бессмысленна на этом конкретном сайте — страница не доживает до состояния,
где ~1с cascade-стопор вообще успевает стать заметным на фоне полной,
судя по всему необратимой (в пределах ≥150с) неотзывчивости. BUG-307
переоценён этим срезом с «UX-дефект под RAM-давлением многих вкладок» на
«воспроизводится тривиально на одной свежей вкладке одного конкретного
реального сайта» — не изучено, обобщается ли на другие сайты с похожими
паттернами (SW-регистрация/относительные fetch-URL) или это узко про
ria.ru. Скрипт репро (не закоммичен, disposable) описан выше и
восстанавливается по любому МCP-клиенту из `scripts/mt_stall_bench.py`.

## Срез 2026-08-06 (P3) — гипотеза «unbounded fetch-read» ОПРОВЕРГНУТА, фикс всё равно влит

**Обнаруженный и устранённый смежный дефект (не корень этого бага, но
самостоятельная проблема):** ни один сокет в `lumen-network`, используемый
обычным `fetch()`/навигацией/`fetch_with_body_sync`, не имел
`set_read_timeout` — сервер, который принял соединение и никогда не
отвечает, блокировал читающий поток БЕСКОНЕЧНО (`connect()`, вызывается из
`fetch_with_redirect`/`fetch_with_body_sync`, `crates/network/src/lib.rs`).
Так как `fetch()` без `AbortSignal` синхронно вызывает `_lumen_fetch_sync`/
`_lumen_fetch_cancellable(…, timeout_ms=0)` прямо на JS-потоке
(`crates/js/src/dom.rs:6521`, ветка `useAsync=false`), залипший фетч
блокировал бы весь JS-поток без предела. **Исправлено:** `connect()` получил
параметр `read_timeout: Option<Duration>`; вызовы для обычного
request/response-трафика передают `Some(FETCH_READ_TIMEOUT=60s)`, вызовы для
WebSocket (`websocket/mod.rs`) и SSE (`sse.rs`) передают `None` (эти
соединения намеренно простаивают дольше). Регресс-тест
`connect_with_read_timeout_bounds_a_stalled_server` поднимает локальный
`TcpListener`, принимает соединение и никогда не пишет ответ — до фикса это
воспроизводило бы точную форму бага (`read()` висит вечно); с фиксом `read()`
возвращает `WouldBlock`/`TimedOut` за ~150мс (тестовый таймаут).

**Проверено вживую на исходном репро (ria.ru, тот же сценарий, что выше) —
БАГ ВСЁ РАВНО ВОСПРОИЗВОДИТСЯ ИДЕНТИЧНО С ФИКСОМ**: 6 последовательных eval
по 30с (180с суммарно, больше исходных ≥150с) — все 6 таймаутят, окно
мёртво. Это ценный отрицательный результат: если бы причиной был застрявший
`fetch()`-сокет без таймаута, окно должно было бы «отпустить» JS-поток не
позже 60с (новый `FETCH_READ_TIMEOUT`) — второй eval-попытки уже застало бы
восстановление. Раз не восстановилось за 180с — **корень этого конкретного
хэнга НЕ в сетевом чтении**, гипотеза отклонена. Фикс всё равно оставлен в
силе (закрывает независимый, самостоятельно воспроизводимый класс дефекта —
любой действительно застрявший сервер теперь не топит вкладку навечно), но
BUG-307 остаётся OPEN.

**Уточнённая точка хэнга** (из свежего `.tmp/bug307_live.log` этого прогона):
последняя строчка в stderr перед полной тишиной — `fetch error: invalid
url: invalid url: missing scheme: "/firebase-messaging-sw.js"`
(`crates/js/src/v8_runtime.rs:2420` или `:2564`, синхронный `_lumen_fetch_sync`/
`_lumen_fetch_cancellable`, URL парсится и падает МГНОВЕННО, без сетевого
I/O — не хэнг сам по себе). После этой строки — вообще ничего: ни фреймов,
ни сетевых логов, ни таймеров, тишина ≥180с. Проверена и отклонена версия
«упавший fetch → `.catch()` → активация SW → `spawn_sw_worker_v8` (новый V8-
поток) деадлочит с главным потоком»: цепочка `_sw_run_lifecycle`
(`crates/js/src/dom.rs:4906`) зовёт `_lumen_sw_activate_script`
(→`spawn_sw_worker_v8`) только если её собственный `fetch(scriptURL)`
УСПЕШЕН — если это именно тот failed fetch, что видно в логе, `.catch(function(){})`
молча гасит его и цепочка к `spawn_sw_worker_v8` не доходит вовсе. Значит
залипание — что-то ДРУГОЕ, происходящее в то же самое окно времени
(возможно, независимый путь в собственном JS-бандле ria.ru), не эта SW-
цепочка. **Следующий шаг остаётся тем же, что и раньше: нужен реальный
дебаггер/тред-дамп в момент хэнга** — без него дальнейшее сужение (какой
именно вызов паркует JS-поток без пробуждения, при 0% CPU) гаданием не
делается.

## Срез 2026-08-06 (P3) — найден и исправлен корень

Установлен WinDbg (`winget install Microsoft.WinDbg`; `cdb.exe` из
`amd64/` внутри пакета не запускается напрямую из `WindowsApps` — ACL
блокирует exec, но копия папки в обычный каталог запускается штатно).
Воспроизвёл минимальный однотабовый репро (та же схема, что в срезе выше:
`--mcp-live-port`, `about:blank` → `navigate https://ria.ru` → `document_ready`
→ `scroll`), снял **неинвазивный** полный дамп памяти (`cdb -pv -p <pid> -c
".dump /ma file.dmp; qd"` — не трогает процесс, в отличие от `-p` без `-pv`,
которое инвазивно приаттачивается и может убить/уронить дебажимый процесс
при обрыве сессии дебаггера) в момент, когда automation-канал уже не отвечал.

Стек-дамп всех 26 потоков (`cdb -z file.dmp -c "~*kb 200; q"`) показал:

- **`main` (winit UI-поток)** блокирован в `EngineThread::query` →
  `Receiver::recv()` — ждёт ответ от движкового потока.
- **`lumen-engine`** блокирован внутри `V8JsRuntime::run()` → тоже `recv()` —
  ждёт следующую задачу (нормальное состояние, симптом, не причина).
- **`lumen-v8`** (поток, реально исполняющий JS) стоит в
  `Mutex::lock_contended` **внутри native-биндинга WebSocket**, вызванного
  из JS (`v8::Script::Run` → `native_fn_trampoline` → geттер/метод WS) —
  ждёт мьютекс.
- Безымянный поток блокирован в `WebSocketSession::recv()` → блокирующий
  `socket.read()` на живом TLS-сокете (rustls) — **держит тот самый мьютекс**
  всё время ожидания.

Корень — `crates/network/src/lib.rs` (`JsWebSocketSessionImpl`): фоновый
поток чтения WS удерживал `Arc<Mutex<Box<dyn WebSocketSession>>>` (`session`)
на всё время блокирующего `recv()` **без таймаута** (осознанно — комментарий
в `websocket/mod.rs` объяснял это тем, что WS-соединение должно простаивать
между сообщениями дольше обычного bounded-fetch). Любой JS-вызов
`send`/`close`/чтения `protocol` (все методы `JsWebSocketSessionImpl`) берёт
тот же `session` — если сокет простаивает (сервер ничего не шлёт), ожидание
бесконечно, а так как V8 в Lumen однопоточен, это вешает ВЕСЬ JS-поток, а
через `EngineThread::query` — и UI-поток целиком. ria.ru открывает WebSocket
(судя по логам — live-лента); стоило JS-коду вызвать любой метод сокета, пока
поток-читатель ждал следующего сообщения — наступал зафиксированный
«0% CPU, ни одного лога, ≥180с» дедлок.

**Фикс** (без переделки full-duplex TLS-стрима, что потребовало бы более
глубокой архитектурной работы): добавлен `WebSocketSession::recv_timeout`
(`lumen_core::ext`, дефолт делегирует в `recv()`) — ограниченное по времени
ожидание фрейма, вместо неограниченного `recv()`. Реализация в
`WebSocket` (`websocket/mod.rs` + новый `frame::try_read_frame`,
`websocket/frame.rs`) читает первый байт нового фрейма обычным
(не `read_exact`) `read()` — таймаут здесь не теряет состояние протокола,
так как либо читается 0 байт, либо весь байт целиком; после первого байта
фрейм дочитывается как раньше. Фоновый поток в `JsWebSocketSessionImpl`
(`crates/network/src/lib.rs`) теперь опрашивает `recv_timeout(200мс)` в
цикле, отпуская `session` на каждой итерации простоя — это ограничивает
худший случай ожидания JS-вызова примерно 200мс вместо бесконечности.
Между разлочиванием и повторной блокировкой добавлен `sleep(1мс)`: без него
`std::sync::Mutex` (не FIFO) в наблюдаемых прогонах систематически отдавал
блокировку обратно тому же потоку-читателю, и `send_text` реально ждал
секундами, несмотря на 200-мс окно (эмпирически найдено через флейки
регресс-теста — 5/6 неудач без `sleep`, 6/6 успехов с ним).
`protocol()` дополнительно закэширован при коннекте (значение никогда не
меняется), поэтому больше не берёт `session` вовсе.

Тесты: `ws_recv_timeout_returns_none_when_idle_then_delivers_later` (таймаут
не блокирует и не теряет кадр), `ws_send_not_blocked_by_idle_recv_thread`
(регресс BUG-307 — `send_text` на простаивающем соединении завершается
за миллисекунды, не за секунды/бесконечность). `cargo test -p lumen-network
--lib`: 2134/2134. Живая проверка — тот же ria.ru-репро, дважды: `scroll`
после `document_ready` отвечает за 0.002с/0.001с (было — 30с timeout, затем
`automation command timed out` до самой смерти окна).

**Не переверифицировано этим фиксом:** исходный 14-вкладочный сценарий из
отчёта 2026-07-17 (`docs/perf/runs/2026-07-17-live.json`, github/stackoverflow/
