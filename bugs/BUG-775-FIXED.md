# BUG-775 — `HTMLTrackElement` никогда не диспатчит `load`/`error`: любой скрипт, ждущий готовности `<track>`, зависает навсегда

**Статус:** FIXED 2026-08-24 (P1)
**Компонент:** js (`crates/js/src/video_bindings.rs` — `VIDEO_SHIM`, секция «`<track>` loading»; натив `__lumen_vtt_parse`; `crates/js/src/dom.rs` — `_lumen_resource_track` / `_lumen_resource_try_prepare`)
**Найден:** P2, WPT-VENDOR-webvtt, 2026-08-18 — `run_report.py --all --root webvtt --recursive`
**Поглощает:** [BUG-795](BUG-795-DUPLICATE.md) (тот же дефект, найден 2026-08-21 срезом 4 WPT-RUN-6; добавлял к описанию отсутствующий `HTMLTrackElement.prototype.track` — он реализован тем же фиксом)

## Симптом

Любой скрипт, который создаёт `<track>`, вешает `onload`/`onerror` и ждёт
одно из них перед проверкой `video.textTracks[0].cues` — стандартный
паттерн всех тестов `webvtt/parsing/file-parsing/tests/*.html` (генерируются
по `webvtt/parsing/file-parsing/README.md`) — зависает до внешнего таймаута
`wptrunner` (~10 с) и падает `TEST_END: Test TIMEOUT`, 0 сабтестов пройдено.

```js
var track = document.createElement('track');
track.src = 'support/header-garbage.vtt';
track.onload = this.step_func(trackLoaded);
track.onerror = this.step_func(trackError);
video.appendChild(track);
// ни trackLoaded, ни trackError не вызываются никогда
```

Вторая половина того же дефекта (из BUG-795): `HTMLTrackElement.prototype.track`
не установлен вовсе, поэтому `track.track.mode = 'showing'` — форма, которую
использует `track-helpers.js::check_cues_from_track`, потребитель каждого
`track-webvtt-*.html` — падает `TypeError: Cannot set properties of undefined`.

## Причина

Загрузка `.vtt` жила **только** в шелле: `crates/shell/src/tracks.rs::load_video_tracks`
обходит **разобранный** документ ровно один раз за навигацию, фетчит `src`
выбранного трека, парсит cues и кладёт результат в `TextTrackStore` — для
оверлея и для ленивого геттера `video.textTracks`.

Из этого следуют оба симптома сразу:

* `<track>`, созданный через `document.createElement`, в этот обход не попадает
  никогда — он появляется после него. Такой трек не фетчился вообще: ни запроса,
  ни разбора, ни события.
* даже для разметочного `<track>` цепочка «шелл разобрал VTT» и цепочка
  «страница слушает `track.onload`» не связаны ничем: `fireEvent()`
  (`video_bindings.rs`) вызывался для `<video>`/`<audio>` (`play`/`playing`/
  `seeking`/…) и ни разу для `<track>`. Дискретного сигнала «готово» в системе
  не было вовсе — только текущее состояние по запросу.

Заявка предлагала диспатчить событие «после того, как `load_video_tracks`
отработал». Это не работает как фикс: для интересующего случая
`load_video_tracks` не отрабатывает никогда, потому что элемента ещё нет.

## Что сделано

Модель обработки трека (HTML LS §4.8.11.1 «start the track processing model»)
перенесена на JS-сторону, где элемент виден в момент его вставки.

**1. Учёт элемента (`dom.rs`).** `_lumen_resource_track` — существующий механизм
BUG-571/BUG-703, помнящий созданные скриптом `<script>`/`<link>` до их вставки —
принял третий тег, `track`. В `_lumen_resource_try_prepare` у него отдельная
ветка, потому что условие запуска у `<track>` **другое**: §4.8.11.1 шаг 3
требует, чтобы родителем был медиаэлемент, и **ничего не говорит про нахождение
в документе**. Половина WPT-тестов этой категории (`signature-invalid.html`,
`header-regions.html`) вообще никогда не добавляет `<video>` никуда — проверка
`_lumen_resource_is_connected`, которой пользуются `<script>` и `<link>`,
отсекла бы их все.

**2. Сама модель (`video_bindings.rs`, `VIDEO_SHIM`).** `startTrackLoad(nid)`:
проверяет, что родитель — `VIDEO`/`AUDIO`; ставит `readyState = LOADING`;
кладёт `TextTrack` в список медиаэлемента **сразу**, до прихода байтов (список
обязан быть в порядке дерева, а сборка по завершении упорядочила бы его по
скорости ответа); прыгает через `setTimeout(…, 0)` — по той же паре причин, что
и внешний `<script>` в `dom.rs`: фетч у Lumen синхронный изнутри, а
`track.onload = …` присваивают уже **после** `appendChild`; затем читает тело,
разбирает и диспатчит `load` либо `error`.

**3. Разбор — на Rust-стороне.** Новый натив `__lumen_vtt_parse(text)` отдаёт
JSON `{ok, cues}` через тот же `lumen_dom::vtt::parse_vtt`, которым пользуется
шелл: второй реализации WebVTT-парсера в шиме не появилось. Ошибка разбора
возвращается как `ok: false`, а не как пустой список cues — HTML §4.8.11.1
шаг 8 требует `error` для «not a valid WebVTT file» и `load` для валидного
файла без cues, и `signature-invalid.html` проверяет ровно этот раздел на
одиннадцати битых заголовках.

**4. Три формы URL.** `blob:lumen/` и `data:` читаются локально, по сырому
значению атрибута, **до** резолва базы: у `fetch()` нет ветки ни для той, ни для
другой (`blob:` ушёл бы в сетевой слой и умер), а весь каталог
`webvtt/parsing/cue-text-parsing/` строит трек через `URL.createObjectURL`.
Сеть — через обычный `fetch()` с резолвом относительно базы документа.

**5. `HTMLTrackElement.track` / `.readyState` + константы** `NONE`/`LOADING`/
`LOADED`/`ERROR` — на прототипе (после BUG-849 обёртка делит один прототип на
интерфейс, а состояние всё равно ключуется по nid). `.track` создаёт `TextTrack`
при первом чтении и отдаёт **тот же объект** дальше: чтение до загрузки не
должно порождать второй, который загрузка потом подменила бы за спиной страницы.

**6. `event.target`.** `_lumen_dispatch` — в отличие от пузырьковых путей —
`target` не проставляет, а `event.target` это то, чем каждый сгенерированный
WebVTT-тест добирается обратно до элемента (`var track = event.target; var video
= track.parentNode;`). Проставляется вручную перед диспатчем.

### Два сознательных отступления от спеки

Оба — в сторону «событие всё-таки приходит»:

* **загрузка не привязана к режиму текстового трека.** §4.8.11.1 шаг 2 требует
  не запускать модель, пока mode === `disabled`, и перезапускать её при смене
  режима. У движка нет ни механизма пользовательских предпочтений, ни
  перезапуска по смене режима, поэтому такая привязка означала бы, что страница,
  не выставившая `default`, висит на `onload` вечно — ровно тот дефект, который
  чинится. Сам режим при этом считается по спеке, так что `cues` у disabled-трека
  остаётся `null` и становится читаемым в ту же секунду, когда страница выставит
  `mode`.
* **cues, загруженные здесь, не доезжают до оверлея шелла** (тот стор пишет
  Rust-обход), поэтому скриптовый трек виден странице, но не отрисовывается
  поверх видео.

## Остаток (не этот баг)

Категория перестала висеть, и то, что раньше пряталось за TIMEOUT, стало
быстрыми FAIL с внятным текстом. Три разных механизма, все заведены отдельно:

* **[BUG-902](BUG-902-OPEN.md)** — поверхность `VTTCue`: нет `getCueAsHTML()`
  (78 сабтестов `cue-text-parsing`), настройки cue (`align`/`line`/`position`/
  `size`/`region`) не отдаются странице, хотя `lumen_dom::vtt` их разбирает;
  `VTTRegion` отсутствует целиком.
* **[BUG-903](BUG-903-OPEN.md)** — конформность самого `parse_vtt`: блок не
  завершается на второй строке таймингов (`arrows.vtt` — 6 cues по спеке, 0 у
  нас), и подпись принимает form feed после `WEBVTT`.
* **[BUG-570](BUG-570-OPEN.md)** — `VTTCue`/`TextTrackCue`/`TrackEvent` не
  установлены как глобальные конструкторы (заведён раньше, не трогался).

Не покрыто этим фиксом и не измерялось:

* **разметочный `<track>`** по-прежнему не диспатчит `load`: он грузится
  Rust-обходом до того, как страница успевает повесить обработчик, — тот же
  класс, что [BUG-804](BUG-804-FIXED.md) (разметочные `<script src>`/`<link>`
  тоже молчат). `track.track` у такого элемента отдаёт пустой `TextTrack`, а не
  снимок шелла.
* **`track.src = …` после вставки** (вставили пустой трек, потом присвоили src)
  модель не перезапускает — спека требует, но ни один из 48 тестов категории так
  не написан.
* `TextTrack.oncuechange` для скриптового трека не проверялся.
