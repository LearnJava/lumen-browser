# BUG-303: github.com — JS-исполнение не завершается (≥240 с) и на V8

**Статус:** FIXED (side effect) 2026-07-30
**Дата найдена:** 2026-07-17
**Компонент:** js (V8-рантайм / event loop)
**Найден:** перф-аудит `/lumen-perf-audit`, прогон 2026-07-17 (docs/perf/runs/2026-07-17.json)

## Симптом (исходный)

`--dump-layout https://github.com/` (и `--screenshot`) не завершались за
240 с таймаута, при этом `--dump-source` той же страницы — 0.7 с, т.е. сеть
и парсинг были в норме; висела именно стадия JS/каскад/layout.

```
github  TIMEOUT  http=200  src=0.7s  lay=240.29s(timeout)  shot=240.29s(timeout)
stderr: module error: JS runtime error: Automatic publicPath is not supported in this browser
```

## Проверка 2026-07-30 (P1, задача BUGS.md:303)

Симптом **не воспроизводится**. Три подряд запуска на актуальном `main`
(коммит `eb9e85d3f`, dev-release):

```
--dump-source https://github.com/                → 0.7s (без изменений)
--dump-layout https://github.com/ (×3 подряд)     → 6.6–6.7s, идентичный layout-дамп
--screenshot .. https://github.com/               → 22.0s, снимок 1024×32768 сохранён
```

`LUMEN_PROFILE_TREE=1` подтверждает: вся стадия layout укладывается в
`layout_measured_hyp` 5.2с (`precompute_counters` 4.1с, `build_box` 1.0с,
`lay_out` 0.15с) — никакого зависшего цикла нет. Строка
`Automatic publicPath is not supported in this browser`, бывшая в исходном
репорте, в stderr вообще не появляется — сам JS-путь, который её печатал,
больше не существует в этом виде.

## Причина исчезновения

Между находкой (2026-07-17) и проверкой (2026-07-30) весь стек ES-модулей на
V8 был переписан набело: **S12b-23** («ESM (`<script type=module>`) на V8»,
коммит `888e6e13a`, закрывает BUG-350) заменил самодельную ESM-эмуляцию на
нативный `ResolveModuleCallback`/`HostImportModuleDynamicallyCallback` V8
(`crates/js/src/v8_esm.rs`). Старый путь, судя по всему, при ошибке резолва
модуля (webpack-рантайм github.com пытается вычислить `publicPath` через
`document.currentScript`, которого нет, и уходит в собственный fallback)
не бросал исключение быстро, а зацикливался/подвисал на повторных попытках —
вероятно, на сетевом уровне (повторный fetch того же неверно
резолвленного URL). Новый путь бросает `module '<specifier>' not found`
**синхронно и один раз на каждый затронутый `<script type=module>`** (в логе
их 7 — по числу top-level модульных тегов страницы) и не хендшейкает
никакой цикл — отсюда исчезновение зависания как побочный эффект чужой
задачи, не целевой фикс.

## Остаточная находка

Сообщения `module 'https://github.com/wp-runtime-b5235be89f8471a4.js' not
found` — это отдельный, реальный дефект резолвинга спецификатора у *внешних*
`<script type=module src=…>` (не у исходного зависания): заведён отдельно
как [BUG-459](BUG-459-OPEN.md). Он не влияет на «зависает навсегда» (DoD
исходного бага выполнен — загрузка укладывается в секунды, деградация
фич ожидаема), поэтому не блокирует закрытие BUG-303.

## DoD

- [x] Загрузка github.com завершается за разумное время (6.6–22с, не 240с+).
- [x] Деградация фич ожидаема и не мешает работе остального конвейера
      (layout/paint отрабатывают штатно на неисполнившихся модулях).
- Watchdog на JS-фазу загрузки (упомянутый в исходном «Ожидании») отдельно
  не заводится — без воспроизводимого зависания риск гипотетический;
  переоценить, если аналогичный сайт снова покажет hard-hang на V8.
