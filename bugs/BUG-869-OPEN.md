# BUG-869 — `WebSocket.send()` пишет в сокет синхронно: медленный получатель замораживает документ, `bufferedAmount` всегда 0

**Статус:** OPEN (ДОРАБОТКА → [GAP-WSASYNC](../ROADMAP.md))
**Тип:** нереализованная функциональность, не дефект реализованного кода — ведётся как задача `GAP-WSASYNC` в [ROADMAP.md](../ROADMAP.md), P3 как баг не берёт. Переклассифицировано 2026-09-02 ре-триажем пула WPT-RUN-5/6: срезы заводили багом всё подряд, потому что правила заведения ([docs/probe-method.md §8](../docs/probe-method.md)) тогда ещё не было. Файл сохраняет номер и путь — на него ссылаются CLAUDE.md, STATUS-файлы и python-тулинг, а запись наблюдений остаётся полезной там, где лежит.
**Заведён:** 2026-08-23 (WPT-RUN-6, срез 26 — живой замер, варианты `ws-backpressure`, `ws-backpressure-steps`)
**Область:** `crates/js/src/v8_runtime.rs:3543`/`:3554` — нативы `_lumen_ws_send`/`_lumen_ws_send_bin` зовут `sess.send_text`/`send_binary` прямо из потока JS, под `registry.lock()`; ниже `crates/network/src/websocket/mod.rs:189` — `send_frame` → `frame::write_frame(&mut self.stream, …)`, обычный блокирующий `Write` в TCP-сокет. Очереди отправки нет вовсе: `crates/js/src/dom.rs:9880` увеличивает `this.bufferedAmount += n`, но ниже по коду счётчик не уменьшается по мере слива, а на практике остаётся 0
**Владелец:** P1/P3 (`lumen-js`/`lumen-network`). Заведён P2 в ходе WPT-задачи, здесь не чинится.

## Симптом

Пока получатель читает медленнее, чем страница пишет, буфер отправки TCP
заполняется и `write` блокируется — вместе с ним встаёт **весь документ**:
не идут таймеры, не идёт рендер, не исполняется ни один следующий стейтмент.
По спеке `send()` обязан вернуться немедленно, поставив данные в очередь и
отразив их в `bufferedAmount`.

## Прямое измерение

`tests/wpt/verify_worker_port_storage_gaps.py --variant ws-backpressure-steps`
(2026-08-23, dev-release, Linux, `main` = `c14b8068c`, `--seconds 9`).
Собственный RFC 6455-сервер пробы отвечает на каждый кадр `/echo-size` с
задержкой 0.1 с — ровно та обратная тяга, которую создаёт
`websockets/send-many-64K-messages-with-backpressure.any.js`. Страница шлёт
50 сообщений по 65536 байт, замеряя каждое:

```
wbs-open
wbs-sent-0  ms=170 buffered=0
wbs-sent-1  ms=311 buffered=0
wbs-sent-2  ms=314 buffered=0
…
wbs-sent-26 ms=312 buffered=0     ← лог обрывается здесь, процесс убит по бюджету
PROBE tick — ни одного за весь прогон (ticks = 0)
```

Каждый `send()` держит поток ~312 мс; 50 таких — 15+ с синхронной
блокировки в одном тике. `setInterval(500)` не сработал **ни разу** —
страница мертва по всем признакам, это ещё и готовый источник механизма
`hung-browser` (одна такая страница забирает остаток шарда).

Что это **не**: не размер кадра. Соседний вариант `ws-send-sizes` против
эхо-сервера без задержки шлёт 1, 1024, 16384, 65535, 65536 и 131072 байт
и получает эхо на все шесть, плюс 50 мелких сообщений подряд, при 13 тиках
за прогон. Блокирует именно неуспевающий получатель.

## Отношение к соседям

Тот же синхронный дизайн уже записан для фазы соединения:
[BUG-856](BUG-856-OPEN.md) (конструктор блокирует документ до конца
хэндшейка) и [BUG-772](BUG-772-FIXED.md) (его же половина на отказанном
порту). Здесь — фаза передачи, отдельный код и отдельный фикс, но общий
корень: сокет обслуживается из потока JS, а не из своего.

## Масштаб

**2** id остатка снимка WPT-RUN-5:
`websockets/send-many-64K-messages-with-backpressure.any.html`
(`?default`, `?wss`) — подтест буквально называется «should not hang».

Ещё два, `websockets/keeping-connection-open/001.html` (`?default`, `?wss`),
в первой редакции числились здесь же, и это была ошибка атрибуции —
исправлено в тот же день. Соединение бездействие переживает
(`--variant ws-idle`: 4 с молчания, эхо после них проходит), а обрезаны они
раньше своих 20 с не движком, а гарнессом: файл объявлен
`<meta name=timeout content=long>`, но `meta.content` читается как
`undefined` ([BUG-796](BUG-796-FIXED.md)), поэтому `testharness.js` даёт им
10 с вместо 60 при `test_timeout: 60` со стороны раннера. Ни при какой
починке `send` они не прошли бы, пока не починен BUG-796 — **он починен
2026-08-24**, так что этот барьер снят и потолок у них теперь настоящий;
перемерить эти два id заново, прежние 10-секундные обрезки о `send` ничего
не говорят.

## Направление починки (не предписание)

Вынести запись в поток сокета (как минимум — очередь + фоновый писатель),
`send()` ставит кадр в очередь и увеличивает `bufferedAmount`, писатель
уменьшает по мере слива. Это тот же разворот, которого требуют BUG-856/772
для соединения, поэтому имеет смысл делать одной работой.

## Как проверить фикс

1. `tests/wpt/.venv/bin/python tests/wpt/verify_worker_port_storage_gaps.py
   --variant ws-backpressure` — ожидается `wb-received 50`,
   `wb-close clean=true` и ненулевой счётчик тиков.
2. WPT: `run_report.py --all --root websockets --recursive`.
