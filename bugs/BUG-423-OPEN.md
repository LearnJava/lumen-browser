# BUG-423 — сабсеты `unicode-range` одной @font-face-семьи затирают друг друга: с реальных страниц пропадают буквы

**Статус:** OPEN
**Компонент:** font (`crates/engine/font/src/font_registry.rs:56` —
`FontRegistry::register_from_bytes`), shell (`crates/shell/src/main.rs:12102` —
обработчик `LoadEvent::FontLoaded`)
**Найден:** P1, 2026-07-28, при показе живого окна на https://yandex.ru
**Приоритет:** высокий — текст на реальных сайтах становится нечитаемым, задет
и хром браузера

## Симптом

Через несколько секунд после загрузки https://yandex.ru из текста пропадает
часть букв — и на странице, и в UI браузера:

| Должно быть | Нарисовано |
|---|---|
| `Костя · Личный` (аватар хрома) | `тя · Личны` |
| `Восстановленная вкладка` (заголовок вкладки) | `т н вл нн я вк` |
| `Главная` (меню Дзена) | `Гл вн я` |
| `Санкт-Петербург` | `нкт-П т б г` |

**На месте пропавших букв остаются пробелы ровно их ширины** — то есть layout
знает метрики этих глифов, а рисование их не находит. На старте того же окна
(до загрузки страницы) текст хрома был целым.

## Механизм (установлен)

yandex.ru отдаёт «Stella Sans» **16 сабсетами** — одна и та же тройка
`(family="Stella Sans", weight=400, style=normal)`, разные `unicode-range`.
В логе ровно 16 строк `@font-face async загружен: «Stella Sans» weight=400`.

1. `FontRegistry::register_from_bytes` ключует запись виртуальным путём
   `@font-face:<family>/<weight>/<style>` — `unicode-range` в ключ не входит.
   Документированное поведение метода: «Если для той же (family, weight, style)
   запись уже есть — она заменяется: CSS @font-face последнего правила wins».
   Правило верно для двух конкурирующих правил, но **сабсеты одной семьи не
   конкурируют — они дополняют друг друга**, и последний пришедший вытирает 15
   предыдущих.
2. Обработчик `LoadEvent::FontLoaded` передаёт в реестр только
   `(family, weight, style, bytes)`. Разобранный `unicode_range` уходит мимо —
   в `self.web_fonts` (`LoadedWebFont`), который читает `MultiFontMeasurer`
   при relayout.
3. Отсюда расхождение: **измеритель видит все 16 сабсетов** и резервирует
   правильные ширины, **рендер видит один** (`r.set_font_provider(page_font_registry)`)
   и не может нарисовать кодпоинты вне его покрытия. Симптом «дыры ровно по
   ширине буквы» — прямое следствие.

## Что не установлено

Почему одновременно посыпался текст **хрома**. Провайдер шрифтов у рендерера
один на хром и страницу (та же строка `set_font_provider`), так что связь
правдоподобна, но цепочка для хрома (у него собственные семьи Golos Text /
JetBrains Mono, DS-4) не прослежена. Проверить это — первый шаг починки: если
хром задет по другой причине, это отдельный баг.

## Воспроизведение

```bash
cargo build -p lumen-shell --profile dev-release
./target/dev-release/lumen.exe --maximized https://yandex.ru
# ждать ~10 с, смотреть на текст страницы И на заголовок вкладки/аватар хрома
```

## Что нужно сделать

1. Включить `unicode-range` в идентичность записи реестра — ключ
   `(family, weight, style, range)` либо список сабсетов на одну семью с
   выбором face по кодпоинту (как это уже делает измеритель).
2. Провести `unicode_range` из `FontLoaded` в реестр — сейчас он теряется на
   границе шелл → font.
3. Регресс-тест в `lumen-font`: два `@font-face` одной семьи и веса с
   непересекающимися `unicode-range`; оба набора символов должны
   разрешаться в свои face-ы, а не в последний зарегистрированный.
