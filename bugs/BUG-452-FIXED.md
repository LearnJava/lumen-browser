# BUG-452 — `<canvas width="0">` даёт 300×150: разбор атрибутов размера роняет ноль через `||`

**Статус:** FIXED 2026-08-30
**Компонент:** js (`crates/js/src/shim/web_api_shim_mid.js` — `_lumen_canvas_dims`,
`tabIndex`; `crates/js/src/shim/web_api_shim_tail_b.js` — `_lumen_parse_integer`,
`_lumen_define_reflection`), layout (`crates/engine/layout/src/box_tree.rs` —
ветка `is_canvas_element`), dom (новый `crates/engine/dom/src/attr_int.rs`)
**Найден:** 2026-07-28 (P2), WPT-VENDOR-html-canvas
**Перепроверен:** 2026-07-29 на main — воспроизводится, плюс отрицательное значение
(номер сменён с BUG-424: 424 занят чужим багом хрома)

## Симптом

```
<canvas id=z width=0 height=0>   →  z.width x z.height = 300x150   (атрибуты: '0'/'0')
n.width = 0                      →  n.width = 300,  getAttribute('width') = '0'
```

То есть сеттер честно пишет атрибут, а геттер его игнорирует. По HTML LS §4.12.4
`width`/`height` — `unsigned long` с дефолтом 300/150, и **`0` — валидное
значение**: нулевой canvas допустим, у него просто нет пикселей.

## Причина

```js
// было, crates/js/src/shim/web_api_shim_mid.js
var w = (aw !== null) ? (parseInt(aw, 10) || 300) : 300;
var h = (ah !== null) ? (parseInt(ah, 10) || 150) : 150;
if (w < 1) w = 1;
if (h < 1) h = 1;
```

`parseInt('0', 10)` даёт `0`, а `0 || 300` — `300`.

## Что показала проба ДО правки

Заявка называла два дефекта (ноль и отрицательное). Проба по таблице ожиданий
вендоренных WPT `2d.canvas.host.size.attributes.*` нашла **семь**, в четырёх
разных местах, и механизм одного из двух названных оказался не тем:

| # | вход | было | спека | где |
|---|---|---|---|---|
| 1 | `width="0"` | 300 | 0 | `_lumen_canvas_dims` (заявка) |
| 2 | `width="0x100"` | 300 | 0 | там же — `parseInt` даёт 0, и `\|\|` роняет его так же, как настоящий ноль |
| 3 | `width="-100"` | **1** | 300 | там же — `-100` truthy, проходит `\|\|` насквозь, и его добивает кламп `< 1`; заявка предсказывала 300 |
| 4 | `width="4294967291"` | 4294967291 | 300 | там же — верхней границы §2.6.2 не было вовсе; в заявке нет |
| 5 | `<img width="100px">` | 0 | 100 | `_lumen_parse_integer` (ДРУГОЙ файл шима) — обрывался на первом не-цифре |
| 6 | `<img width="2147483648">` | 2147483648 | 0 | `_lumen_define_reflection`, та же отсутствующая граница |
| 7 | `tabindex="3zzz"` | −1 | 3 | тот же `_lumen_parse_integer`; плюс `tabIndex` — рукописный аксессор, мимо границы таблицы |

Восьмое место нашлось чтением, а не пробой: **layout считает те же атрибуты
третьей реализацией** — `v.trim().parse::<u32>()` (`box_tree.rs`), чьи правила не
совпадают ни со спекой, ни с `parseInt`. `width="100.999"` укладывался боксом
300 CSS px, а из скрипта читался как 100 — то есть JS и layout расходились на
одном и том же атрибуте.

## Что сделано

Одно правило — по одной реализации на язык.

* **`_lumen_parse_integer`** (`web_api_shim_tail_b.js`) приведён к §2.4.4.1
  дословно: пропуск **ASCII** whitespace (был `trim()`, который ест ещё и
  U+00A0), необязательный знак, обязательная первая цифра, сбор цифр и
  **останов** — хвост игнорируется, а не отвергается. Прежний комментарий
  («deliberately stricter than `parseInt`, which would accept '12px'») описывал
  не спеку: строже `parseInt` здесь и есть ошибка, шаг 8 собирает цифры и
  возвращает. Сверено с эталонной реализацией самого WPT
  (`tests/wpt/html/dom/reflection.js::ReflectionTests.parseInt`).
* **Границы отражения** §2.6.2 (`_LUMEN_LONG_MIN`/`_LUMEN_LONG_MAX`) добавлены в
  геттер и сеттер `long`/`ulong` таблицы отражения и в рукописный `tabIndex`.
* **`_lumen_canvas_dims`** зовёт общий разбор + границу; клампы `< 1` сняты.
  Нативный бэкинг-стор сохраняет свой `clamp(1, MAX_CANVAS_DIM)`
  (`canvas2d.rs`) — это деталь аллокации, и она больше не наблюдаема из JS;
  ровно эту путаницу две снятые строки и кодировали.
* **`tabIndex`-сеттер** переведён с разбора строки на приведение WebIDL `long`
  (ToNumber + усечение), как у `long`-строки таблицы рядом: у аргумента сеттера
  и у значения атрибута правила РАЗНЫЕ (`el.tabIndex = '3px'` → 0, тогда как
  `tabindex="3px"` → 3), а разбор строки делал их одинаковыми.
* **Rust-зеркало** — новый `lumen_dom::attr_int` (`parse_integer`,
  `parse_non_negative_integer`, `reflect_unsigned_long`) с таблицей WPT в
  собственных тестах; `box_tree.rs` зовёт его вместо `parse::<u32>()`.

## Данные WPT

`element/canvas-host/*`, серия `2d.canvas.host.size.attributes.*` (7 сабтестов
падали сообщением `assert_equals: canvas.width === 0 (got 300[number], expected
0[number])`). Смежные сабтесты той же серии падают на
`getComputedStyle(canvas).getPropertyValue("width")` = `""` — это **не** этот баг,
а [BUG-382](BUG-382-OPEN.md) (снимок computed-style не доезжает до JS-контекста);
после этой правки они по-прежнему падают там.

## Чего правка НЕ делает

* `getImageData(0,0,1,1)` на нулевом холсте по-прежнему не бросает — и не должен:
  `IndexSizeError` по спеке бросается при нулевых `sw`/`sh`, а не на нулевом
  холсте (`createImageData(0,0)` бросает и бросал). Заявка называла это неверно.
* Значение `canvas.width` после присваивания отрицательного — 300, и это уже было
  верно: §2.6.2 требует для сеттера «вне 0…2147483647 → дефолт», а не
  обёртывания в `4294967291`, как предполагало «Направление починки» заявки.
  Атрибут получает `'300'`, IDL и content согласованы.

## Проверка

* `cargo test -p lumen-js --features v8-backend` — 3340 тестов зелены; новый файл
  `crates/js/src/dom/tests/v8_core/canvas_size_attributes.rs` (5 тестов) держит
  таблицу WPT, границу диапазона, согласие геттера с сеттером и оба соседних
  места (`<img>`, `tabindex`).
* `cargo test -p lumen-dom` (287) и `-p lumen-layout` (3640) зелены; таблица WPT
  продублирована в `attr_int.rs`, потому что расхождение двух зеркал и было
  половиной бага.
* Нейтральность display list: `dump_golden.py` — 12/12 совпадают с эталоном,
  детерминированные CPU-снапшоты (`lumen-driver … cases::snapshot_cpu`) зелены.
  Все `<canvas>` корпуса объявлены целыми числами, на которых старый
  `parse::<u32>()` и новое правило отвечают одинаково, поэтому пиксели не
  двигаются; разошлись бы они только на дробном/hex/с-хвостом атрибуте, которого
  в корпусе нет.
* Один тест пришлось **исправить, а не подогнать**:
  `dom_suspend_focus::tab_index_reflects_the_content_attribute` утверждал
  `tabindex='2px'` → −1, то есть записывал поведение слишком строгого разбора как
  правило. Ожидание заменено на 3 (спека + эталон WPT) и дополнено случаями
  «действительно неразбираемое» и «вне диапазона».
