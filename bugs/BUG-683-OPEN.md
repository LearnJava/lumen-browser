# BUG-683 — github.com stagnalone tab retains ~890 MB of unaccounted Rust-side memory

**Статус:** OPEN
**Компонент:** layout/dom (не локализовано — нужна перепись структур)
**Найден:** P3, срез 3 [BUG-306](BUG-306-OPEN.md), 2026-08-06

## Симптом

Мульти-табовый живой репро BUG-306 (среза 3, `docs/perf/corpus.txt` порядок:
example, ya, hn, w3, rust-lang, lenta, github) с временным counting
`#[global_allocator]` (см. BUG-306 срез 3) показал `rust_alloc` (реальная
Rust-куча процесса) по вкладкам:

```
example        —      (первая вкладка, отчёт ещё не успел напечататься)
ya         108.2 МБ
hn         114.2 МБ
w3         114.2 МБ
rust-lang  140.1 МБ
lenta      189.5 МБ   (после 6 вкладок)
github    1079.0 МБ   (после добавления 7-й вкладки — Δ = +889.5 МБ)
```

Одна вкладка github.com добавляет ~890 МБ Rust-кучи — на два порядка больше,
чем любой другой сайт корпуса добавил за всю свою вкладку (2-53 МБ дельты на
сайт для ya/hn/w3/rust-lang/lenta). При этом известные счётчики
(`img_cache`/`prefetch`/`web_fonts`/`dl_cache` из `LUMEN_MEM_REPORT`) для
всех вкладок вместе взятых дают лишь единицы МБ — вся 890-мегабайтная разница
живёт в структурах, которые `LUMEN_MEM_REPORT` не считает: DOM-дерево, CSSOM,
`ComputedStyle`, layout-box, display-list-source, и любая Rust-обвязка JS-
движка вне `js_malloc` (который остался в норме — 77.9 МБ, гипотеза «V8-хип»
отдельно опровергнута в BUG-306).

## Почему это не BUG-306 напрямую

BUG-306 задавал вопрос «куда уходит память процесса при работе с реальными
сайтами» — на него срез 3 ответил (94.6% RSS атрибутировано:
`rust_alloc + js_malloc + gpu`). Этот баг — узкий следующий вопрос: «почему
Rust-куча ОДНОЙ конкретной страницы (github.com) непропорционально велика».
github.com — легитимно тяжёлая JS SPA, но 890 МБ чистого Rust-side состояния
(не JS-хипа, не GPU) для одной страницы, скорее всего, включает или
дублирование структур, или неосвобождаемые промежуточные данные, а не только
«ожидаемый вес большого DOM».

## Диагностика (не выполнена в этом срезе)

Перепись Rust-структур конкретно для github.com:
1. Подсчитать число DOM-узлов / CSSOM-правил / `ComputedStyle`-инстансов
   (`--dump-layout`/живой `resource://a11y_tree`/`resource://layout` дают
   число узлов) и сравнить с ожидаемым весом на узел (`size_of::<...>()` ×
   count) — если фактический `rust_alloc` на порядок больше расчётного,
   искать дублирование/утечку конкретной структуры.
2. Сравнить headless (`--dump-layout`/`--screenshot`, без живого окна/wgpu)
   vs живое окно на той же странице — изолирует, паразитная память в
   paint/display-list retained-состоянии или в самом layout/DOM.
3. Профиль по времени: снять `rust_alloc` сразу после `document_ready` и
   через 30-60 с — если растёт дальше без взаимодействия, это SPA-полинг/
   утечка, а не разовая стоимость первого рендера.

См. методологию: [reference_memory_diagnosis_toolkit], `docs/perf-method.md`.
