# BUG-683 — github.com stagnalone tab retains ~890 MB of unaccounted Rust-side memory

**Статус:** OPEN
**Компонент:** layout/dom (не локализовано — нужна перепись структур)
**Найден:** P3, срез 3 [BUG-306](BUG-306-OPEN.md), 2026-08-06

## Симптом

Мульти-табовый живой репро BUG-306 (среза 3, `docs/perf/corpus.txt` порядок:
example, ya, hn, w3, rust-lang, lenta, github) с временным counting
`#[global_allocator]` (см. BUG-306 срез 3) показал `rust_alloc` (реальная
Rust-куча процесса) по вкладкам:

```
example        —      (первая вкладка, отчёт ещё не успел напечататься)
ya         108.2 МБ
hn         114.2 МБ
w3         114.2 МБ
rust-lang  140.1 МБ
lenta      189.5 МБ   (после 6 вкладок)
github    1079.0 МБ   (после добавления 7-й вкладки — Δ = +889.5 МБ)
```

Одна вкладка github.com добавляет ~890 МБ Rust-кучи — на два порядка больше,
чем любой другой сайт корпуса добавил за всю свою вкладку (2-53 МБ дельты на
сайт для ya/hn/w3/rust-lang/lenta). При этом известные счётчики
(`img_cache`/`prefetch`/`web_fonts`/`dl_cache` из `LUMEN_MEM_REPORT`) для
всех вкладок вместе взятых дают лишь единицы МБ — вся 890-мегабайтная разница
живёт в структурах, которые `LUMEN_MEM_REPORT` не считает: DOM-дерево, CSSOM,
`ComputedStyle`, layout-box, display-list-source, и любая Rust-обвязка JS-
движка вне `js_malloc` (который остался в норме — 77.9 МБ, гипотеза «V8-хип»
отдельно опровергнута в BUG-306).

## Почему это не BUG-306 напрямую

BUG-306 задавал вопрос «куда уходит память процесса при работе с реальными
сайтами» — на него срез 3 ответил (94.6% RSS атрибутировано:
`rust_alloc + js_malloc + gpu`). Этот баг — узкий следующий вопрос: «почему
Rust-куча ОДНОЙ конкретной страницы (github.com) непропорционально велика».
github.com — легитимно тяжёлая JS SPA, но 890 МБ чистого Rust-side состояния
(не JS-хипа, не GPU) для одной страницы, скорее всего, включает или
дублирование структур, или неосвобождаемые промежуточные данные, а не только
«ожидаемый вес большого DOM».

## Диагностика (не выполнена в этом срезе)

Перепись Rust-структур конкретно для github.com:
1. Подсчитать число DOM-узлов / CSSOM-правил / `ComputedStyle`-инстансов
   (`--dump-layout`/живой `resource://a11y_tree`/`resource://layout` дают
   число узлов) и сравнить с ожидаемым весом на узел (`size_of::<...>()` ×
   count) — если фактический `rust_alloc` на порядок больше расчётного,
   искать дублирование/утечку конкретной структуры.
2. Сравнить headless (`--dump-layout`/`--screenshot`, без живого окна/wgpu)
   vs живое окно на той же странице — изолирует, паразитная память в
   paint/display-list retained-состоянии или в самом layout/DOM.
3. Профиль по времени: снять `rust_alloc` сразу после `document_ready` и
   через 30-60 с — если растёт дальше без взаимодействия, это SPA-полинг/
   утечка, а не разовая стоимость первого рендера.

См. методологию: [reference_memory_diagnosis_toolkit], `docs/perf-method.md`.

## Срез 1 (P6, 2026-09-23): headless-перепись, живой замер заблокирован

Шаг 1 (headless-часть) выполнен частично. `lumen.exe --dump-layout
https://github.com` (сборка dev-release от 2026-09-20, HEAD совпадает по
DOM/layout-коду с текущим main) на неавторизованной landing-странице даёт
дерево layout-боксов: 1854 узла без учёта текстовых суб-дескрипторов
(`seg[N]`/`line[N]`/`frag[N]`), 2110 с ними, 5409 строк дампа всего (счётчики
по видам — `Block` 948, `SvgShape` 229, `InlineRun` 249, `InlineBlockRow` 134,
`Skip` 126, `SvgRoot` 108, `FormControl` 34, `Image` 24, остальное —
текстовые фрагменты).

Эти ~2000 узлов — на порядок меньше, чем нужно для объяснения 890 МБ как
«ожидаемого веса на узел» (даже щедрые 1-2 КБ/узел на DOM+CSSOM+ComputedStyle+
layout-box дают только единицы МБ). Но headless `--dump-layout` **не
выполняет JS** (`crates/shell/src/dump_mode.rs` не содержит ни одного пути к
`eval_js`/`route_*_js`/V8) — это статический разбор присланного HTML, без
клиентской гидратации. У github.com (SPA, React-подобный клиентский рендер,
множество скрытых меню/модалок/аналитики) реальный живой DOM после гидратации
почти наверняка на порядок больше headless-снимка. Проверить это (шаг 2:
headless vs живое окно) не удалось — заблокировано инструментарием живого
окна:

- `scripts/mem_perf.py --page https://github.com` стабильно падает на
  `_wait_for_mcp_token`: `[mcp] token: …` объективно пишется в
  `stderr.log` в первые ~200 мс (подтверждено ручным `cat` сразу после сбоя
  скрипта), но `_wait_for_mcp_token` не находит его ни за 20 с (дефолт), ни
  за 60 с (временный патч, не закоммичен, откачен). Не похоже на гонку
  таймаута — похоже на то, что скрипт читает не тот файл/не те данные в
  этой среде. Не расследовано глубже (не тулинг этой роли).
- Ручной JSON-RPC клиент к тому же порту подключается нормально (`initialize`
  проходит), но `eval` на `https://github.com` либо не отвечает вовсе (таймаут
  сокета), либо отвечает `{"error": "Eval error: JS context not available"}`
  спустя десятки секунд после `navigate`. `https://example.com` в той же
  сессии тоже не ответил на `eval` (таймаут на самом `navigate`). Сеть не
  виновата — `curl https://github.com` из той же машины отвечает `200` за
  2.8 с.

Похоже на нестабильность живого MCP-канала в этой конкретной среде
(возможно, специфика песочницы/раскладки процессов), а не на новый движковый
баг — `"JS context not available"` имеет длинную историю уже закрытых карточек
(BUG-296/380/397/438/1034) для других сценариев, дублировать без более
сильных доказательств не стал. Шаги 2 и 3 (headless-vs-живое, профиль по
времени) остаются не выполненными — нужен рабочий живой канал (другая
среда/сессия) или починка `mem_perf.py`'s `_wait_for_mcp_token` под эту среду.

## Дрейф трекера, снят из STATUS-P3.md 2026-09-19 (P3)

Указатель `STATUS-P3.md:1` вёл на эту строку. Собственная ревизия
[BUG-306](BUG-306-OPEN.md) от 2026-09-01 уже зафиксировала: «BUG-683 …
**не в очереди P3** (нет строки в `STATUS-P3.md`) — это профилировочная
задача домена P1/P2». Тем не менее указатель на неё существовал в
`STATUS-P3.md` с 2026-08-31 (пережил массовый перенос закрытых багов в
`BUGS-FIXED.md` тем же коммитом, который и завёл инструмент перенумерации,
`git log --follow -p -- STATUS-P3.md`) и с тех пор только перенумеровывался
скриптом при каждом сдвиге строк выше него — содержательно никто не
перепроверял. Диагностика этой задачи (перепись Rust-структур конкретно на
github.com — раздел выше) требует профилировочного среза, не точечного
JS/Rust-фикса, что и заявлено её собственным `bugs/BUG-683-OPEN.md`
(«Владелец: не указан, но диагностика — не сделана в этом срезе», см.
классификацию BUG-306). Указатель снят; сама задача остаётся `OPEN` для
P1/P2, если у них найдётся время на прицельный профилировочный срез.
