# BUG-935 — M4 incremental restyle for the rAF-dirty pump is dead code under the default (engine-thread-on) build; a page with an active rAF+DOM-mutation loop pays a full off-thread cascade recompute on every tick

**Статус:** OPEN
**Компонент:** shell (`crates/shell/src/relayout.rs` — `relayout_raf_dirty`, `relayout_raf_dirty_readback`, `submit_relayout_job`, `try_relayout_raf_incremental`)
**Найден:** 2026-09-01 (P3), при ревизии BUG-286 (DEBTOR, `content-visibility:auto` scroll stopor) — свежий живой замер на ria.ru показал не одну паузу ~580мс, а 33 полных off-thread relayout'а (по 850–2600мс каждый) за ~15–20с сессии, все при неизменном `dl=1690 styled=1744` (без роста DOM)

## Симптом

Живой прогон (`--mcp-live-port`, `LUMEN_PROFILE_TREE=1`+`LUMEN_FRAME_LOG=1`,
метод BUG-286 «Замер 2026-08-06») на https://ria.ru, повторённый 2026-09-01
на свежем `dev-release`: **33** записи `[engine] relayout Nms (off-thread)
dl=1690 styled=1744` за один запуск (9 — ещё до первого MCP `scroll`-вызова,
во время начальной загрузки/settle; 24 — во время и после 20 тиков скролла).
Все с одинаковым `dl`/`styled` — размер DOM не растёт, т.е. это не
раскрытие `content-visibility` (тот срабатывает один раз и увеличивает
`styled`), а нечто, дёргающее relayout непрерывно на одной и той же
странице.

Соответствующие MCP `scroll`-вызовы получали RTT 850–1400мс вместо
ожидаемых 1–5мс (BUG-286's 2026-08-06 замер: «scroll держит 2-6мс без
повторов») — round-trip блокируется, пока идёт relayout (вероятно,
блокировка на `Document`-мьютексе, которым relayout тоже пользуется через
свой снимок).

## Корень

`ria.ru` держит на главной странице `videojs`-плеер (лог содержит `[JS
error] VIDEOJS: ERROR: ...` — сам плеер не критичен, но подтверждает его
активность), который гоняет `requestAnimationFrame`-цикл и на каждом тике
трогает DOM (UI-контролы плеера). Каждый такой тик помечает `dom_dirty` и
вызывает `Lumen::relayout_raf_dirty()` (`about_to_wait.rs:392`).

`relayout_raf_dirty` (`relayout.rs:337`):

```rust
pub(crate) fn relayout_raf_dirty(&mut self) {
    if !self.submit_relayout_job() && !self.try_relayout_raf_incremental() {
        self.relayout();
    }
}
```

`&&` короткого замыкания: `submit_relayout_job()` вызывается первым и, пока
движковый поток жив (`LUMEN_ENGINE_THREAD=1` — дефолт с ADR-023,
2026-07-28), **всегда** возвращает `true` (единственное условие отказа —
отсутствие `LayoutSource`/вырожденный viewport). Поэтому `||`-ветка с
`try_relayout_raf_incremental()` — M4-инкрементальный путь
(`layout_mutation_incremental`/`relayout_page_incremental_restyle`,
переиспользующий `self.layout_box` вместо полного `compute_layout`) —
**никогда не выполняется на дефолтной сборке**. Симметричная функция
`relayout_raf_dirty_readback` (`relayout.rs:486`, RedrawRequested-путь)
устроена так же: `readback_relayout_job()` (тоже полный, тоже
приоритетный, пока движковый поток жив) закрывает `&&` раньше, чем
инкрементальный путь успевает сработать.

Старый doc-комментарий `relayout_raf_dirty` утверждал обратное — «tries the
incremental path first ... before falling back to ... submit_relayout_job
(engine thread)» (не совпадало с кодом ни в одном билде; поправлен в этой
же сессии, см. «Что уже сделано» ниже). Сестринская функция
`relayout_raf_dirty_readback` документирована **корректно** («in the
single-thread fallback path, tries the incremental layout ... before the
full relayout») — т.е. везде, где движковый поток включён (дефолт),
`try_relayout_raf_incremental` — код для `LUMEN_NO_ENGINE_THREAD=1`, а не
для основной конфигурации.

`make_relayout_job` (`relayout.rs:726`, тело задания `submit_relayout_job`)
зовёт `compute_layout(&document, &stylesheet, viewport, ...)` — полный
пересчёт каскада для ВСЕГО документа (та же стоимость, что и корень
BUG-286: `docs/tasks/p3-cascade-perf.md` «Задача 3»), просто исполняемый
асинхронно на движковом потоке вместо UI-потока. Async ⇒ UI не блокируется
(картинка не подвисает), но движковый поток остаётся занят полным
пересчётом на каждый rAF-тик с DOM-мутацией — на странице с активным
rAF+DOM-цикл (видеоплеер, карусель, «живая лента» и т.п.) это превращается
в непрерывный, а не разовый расход: пока цикл идёт, движковый поток почти
всегда занят одним relayout'ом и сразу берёт следующий (сообщение
`EngineThread::submit`'а coalescing'ит промежуточные заявки — очередь не
растёт бесконечно, — но полезная работа M4 всё равно теряется: каждый
принятый к исполнению relayout всё равно **полный**, не инкрементальный).

## Почему не тот же баг, что BUG-286

BUG-286 — про **маршрутизацию** (`self.relayout()` → `self.relayout_raf_dirty()`
для конкретного триггера `content-visibility` relevance) и её конечный вывод
был «одна пауза ~580мс, повторный full recompute сайт не запрашивает».
Замер 2026-09-01 подтверждает, что маршрутизация content-visibility сама по
себе не сломана (никакого регресса в её логике нет), но показывает, что
**тот же** `relayout_raf_dirty`, куда BUG-286 маршрутизировал триггер,
обслуживает и rAF-DOM-мутации — и там M4-инкрементальный путь,
специально построенный, чтобы такие мутации не стоили полного пересчёта
каскада, не работает на дефолтной сборке. BUG-286 остаётся закрытым в
своём скоупе (маршрутизация верна); это отдельная, точно
локализованная находка.

## Что уже сделано в этой сессии (P3, 2026-09-01)

Поправлен doc-комментарий `relayout_raf_dirty` (`relayout.rs:334-338`) —
описывал не тот порядок вызовов, который реально исполняется; приведён в
соответствие с кодом и с формулировкой сестринской функции.

## Предполагаемый фикс (НЕ сделан этой сессией — нужен перф-замер, не точечная правка)

Наивно — поменять порядок в обеих функциях местами
(`try_relayout_raf_incremental` до `submit_relayout_job`/`readback_relayout_job`),
чтобы M4 реально работал под дефолтной сборкой. Это меняет задокументированный
инвариант «async-safe триггер уходит off-thread, UI-поток не блокируется» —
`try_relayout_raf_incremental` синхронный и исполняется НА UI-потоке (мутирует
`self.layout_box`/`self.page_prev_cascade_styles`, которые UI-поток
единолично владеет), т.е. переключение сделает rAF-DOM-мутации ЧАСТИЧНО
UI-блокирующими вместо полностью асинхронных — компромисс «дешевле, но на
UI-потоке» вместо «дороже, но всегда off-thread». Нужен тот же протокол, что
и любая правка на этом файле по `docs/perf-method.md`: census ДО, интерливед
A/B (стоимость инкрементального прохода на UI-потоке per rAF-tick против
частоты пропущенных кадров) на представительном наборе сайтов с активным
rAF-циклом (ria.ru — готовый стенд), не только на синтетике. Масштаб и риск
измерения — сравним с BUG-341 (27 срезов), не точечный P3-фикс; следующая
сессия должна начать с `docs/perf-method.md` и живого замера на ria.ru по
методу этого файла.

## S2 (P3, 2026-09-20) — зависание НЕ на загрузке: первый кадр документа рисуется, дальше тишина при почти нулевой загрузке CPU

Пересборка `dev-release` в этой сессии (тот же слот, тот же коммит census-скрипта
из S1) и повтор репро-команды файла (без изменений в коде) дал **другую**
картину, чем S1: `[wgpu] pipeline …` warm-up для `mask`/`circle`/`mipgen`/
`cross-fade` пайплайнов (эти инициализируются лениво при первом реальном
использовании) — то есть, в отличие от S1 (`dl 0 cmds`, красится только
chrome), в этой сессии контент документа **дорисовался** хотя бы раз. Тем не
менее после строки `pipeline cross-fade-pipeline: 33ms` — полная тишина: ни
одной новой `[frame]`, `[JS]`, `→ GET`/`← NNN` строки за 45+с (два опроса лога
с интервалом 20с и 30с, ноль новых строк).

Процесс (`lumen.exe`, не `lumen-shell.exe` — итоговый бинарь называется иначе)
жив всё это время (виден в `tasklist`), но `CPU-время` за 15с реального
ожидания выросло всего на ~1.3с (`765484`→`765616` в единицах `tasklist`,
т.е. почти простой) — значит это не busy-loop/спин на JS-стороне (там было бы
почти 100% одного ядра), а настоящая блокировка где-то (мьютекс, channel
`recv`, синхронный I/O) уже ПОСЛЕ первого кадра. `taskkill /F` подтвердил,
что процесс всё ещё был жив и ничего не обрабатывал сам (без внешнего
`SIGKILL`-аналога не завершился).

Два разных застоя в двух разных сессиях на одной и той же команде (S1: до
первого кадра; S2: сразу после первого кадра) говорят, что дефект,
блокирующий репро этого бага, недетерминирован по месту — воспроизводится
где-то в широком окне «загрузка скриптов → первый рендер → далее», не в одной
фиксированной точке. `[JS error] Uncaught TypeError: Cannot read properties
of undefined (reading 'length')` (`<anonymous>:4:57`, дважды, оба раза до
зависания в обеих сессиях) — стабильный маркер, но причинно-следственная
связь с зависанием не установлена (ошибка одна и та же что в S1, но там
зависание было РАНЬШЕ неё по логу, здесь — позже).

Правки кода снова не делались (только этот раздел документа). Следующий
срез — не пытаться воспроизвести живьём вслепую ещё раз (третий раз подряд
даёт третью картину, стенд нестабилен), а: (1) подключиться MCP-клиентом
СРАЗУ после первых признаков зависания и проверить, отвечает ли сам MCP-порт

(2) если процесс просто зависает на каждом повторе — снять стек потоков
живого `lumen.exe` внешним отладчиком (`windbg`/`cdb -p <pid>`) в момент
зависания, а не читать код вслепую.

## S3 (P3, 2026-09-20) — пункт (1) выполнен: подтверждён настоящий deadlock UI-потока на lenta.ru, отдельно от ria.ru-стопоров S1/S2

Написан `scripts/bug935_hang_probe.py`: запускает репро, ждёт первую покраску
контента (как в census-скрипте), затем детектирует «тишину» в stderr-логе
(15с без новой строки) и в этот момент шлёт MCP `resources/read` на
`resource://console` (лёгкий запрос — читает уже накопленный буфер
console-логов через `AutomationCommand::ConsoleLog`, без нового relayout) с
собственным сокетным таймаутом, отдельным от `DEFAULT_TIMEOUT=30с` в
`live_session.rs`, — чтобы отличить «сервер не ответил вовсе» от «ответил
дольше моего таймаута».

**На `https://ria.ru`** (четвёртый живой прогон подряд, четвёртая картина: в
этот раз контент так и не дорисовался за 90с — форма S1, не S2) проба
ответила МГНОВЕННО (0.0с) на тишину в логе после блока `Service worker
register` (`fb_permission_denied` — see лог): IPC-поток и обработчик
`AutomationCommand` в `winit`-event loop живы и дренируют канал, тишина в
stderr — не деадлок процесса, а просто ничего интересного не логируется,
пока страница либо ждёт сеть, либо крутит JS, который ничего не пишет в
`[JS]`/`[frame]`. Это **не** воспроизводит зависание BUG-935 (relayout-путь
никогда не активировался — `dl` так и не стал ненулевым), а закрывает
незавершённый пункт (1) предыдущего среза для этого конкретного стенда:
процесс НЕ завис в смысле «весь UI-поток встал».

**На `https://lenta.ru`** (взят как альтернативный rAF/карусель-стенд —
`docs/perf/corpus.txt`, тот же класс страницы: новостная лента с
каруселью/видео) картина другая и воспроизводится настоящим deadlock:
контент дорисовался (`painted=True`, `[frame] total 319ms dl 1552 cmds`
и ещё два кадра `Identical`/`band blit`), после чего пошла пачка
рекламных/аналитических fetch (top100.ru, `easylist`-блокировки
`sentry-saas.rambler-co.ru`/`tns-counter.ru`/`kraken.rambler.ru`), лог
замолкает — и MCP `resources/read(resource://console)` **не отвечает за все
60с** пробы (`Console log error: automation command timed out` —
`AutomationHandle::execute`'s собственный `DEFAULT_TIMEOUT=30с` истёк
первым, что подтверждает: `winit`-event loop не обработал ни один
`AutomationCommand` минимум 30 секунд подряд). Это первое воспроизведение в
этом баге, где отличие «весь процесс встал» от «встал только JS/render»
разрешено однозначно в пользу первого — UI-поток **не** дренирует свой
командный канал, то есть либо сам заблокирован (мьютекс/канал/синхронный
I/O на UI-потоке), либо событийный цикл `winit` не докручивается до обработки
пользовательских событий по другой причине. И `tasklist` на PID процесса,
поднятого из-под git-bash, сам зависал на 5-секундном таймауте (отдельная
шероховатость среды, не бага — PID, который возвращает `subprocess.Popen`
под MSYS-питоном, не всегда совпадает с нативным Windows PID достаточно
надёжно для `tasklist`/`taskkill` по нему; не мешает диагнозу выше, но
следующая попытка снять стек живого процесса должна найти PID независимо,
например через `wmic process where "name='lumen.exe'"` или Task Manager
вручную).

Правки кода не делались (только скрипт-проба и этот раздел). В среде этой
сессии не оказалось ни `cdb`/`windbg` (Debugging Tools for Windows), ни
`gdb`, ни `procdump` — пункт (2) предыдущего среза («снять стек потоков
внешним отладчиком») невыполним без внешней установки инструмента (`winget
install Microsoft.WinDbg` или аналог), а это системное изменение вне
`D:\RustProjects\lumen-browser\`, которое протокол требует согласовать с
пользователем, а не делать самостоятельно. Следующий срез должен либо (а)
получить подтверждение пользователя на установку Debugging Tools for
Windows и снять стек `lumen.exe` в момент зависания на `lenta.ru` (стенд
теперь известен как воспроизводимый и более стабильный, чем `ria.ru`), либо
(б) продолжить локализацию без отладчика — по логике кода, окно тишины
начинается сразу после блока рекламных `fetch`, часть из которых
блокируется `easylist` (`network error: blocked`) — стоит проверить, не
держит ли обработка `fetch`-ошибки/CSP-блокировки на UI-потоке блокирующий
примитив (мьютекс сети, `Sender`/`Receiver` без второй стороны), которым
затем оказывается заблокирован и `winit`'s `about_to_wait`/событийный цикл
целиком.

**Попытка установки отладчика (эта же сессия, с согласия пользователя):**
`winget install Microsoft.WinDbg` нашёл уже установленную Store-версию — её
`cdb.exe`/`dbgeng.dll` (`WindowsApps\Microsoft.WinDbg_...\amd64\`) лежат в
MSIX-песочнице: прямой запуск извне пакета даёт «отказано в доступе» даже на
`-version`, то есть эта копия для `cdb -p <pid>` из скрипта/шелла не годится.
Попытка поставить классический "Debugging Tools for Windows" через
`Microsoft.WindowsSDK.10.0.26100` (`winsdksetup.exe /features
OptionId.WindowsDesktopDebuggers /quiet`) зависла сама: 0% CPU, ноль сетевых
соединений, ни одного файла лога за 90+с — сессия работает под
неповышенным токеном (`net session` → отказано в доступе), а инсталлятору
для системной установки нужна elevation, запрос которой в этой безголовой
среде показать (и подтвердить) некому; процессы пришлось прибить
(`taskkill`). Пользователь подтвердил, что поставит Debugging Tools for
Windows сам на десктопе (кликнув UAC вручную) — следующая сессия должна
**начать** с проверки `where cdb`/`where windbg` (или прямого пути
`C:\Program Files (x86)\Windows Kits\10\Debuggers\x64\cdb.exe`), и только
если он появился — переходить к снятию стека `lumen.exe` в момент
зависания на `lenta.ru` (репро-команда та же, стенд подтверждён в этом
срезе). Если инструмента всё ещё нет — идти путём (б) выше (чтение кода
вокруг обработки `fetch`/`easylist`-блокировки на UI-потоке).

## S4 (P3, 2026-09-20) — найден и починен реальный deadlock-механизм из S3 (без отладчика, чтением кода); исходный M4-incremental-путь бага пока не тронут

Отладчик (`cdb`/`windbg`) в среде так и не появился (S3's два пути установки
не сработали, пользователь ставит вручную на десктопе). Пошёл путём (б) из
S3 — чтение кода вокруг обработки `fetch` на UI-потоке, без живого прогона.

Нашёл: `crates/network/src/lib.rs` `connect_inner` (`:1169`, `:1202`) вызывал
`TcpStream::connect(addr)` — **без какого-либо таймаута** на сам TCP-connect
(SYN-хендшейк). `FETCH_READ_TIMEOUT=60s` (введён BUG-307, тот же файл,
`:1100`) бьёт по чтению уже установленного соединения, но не по самому
`connect()`. Хост, который на попытку соединения отдаёт "packets dropped, no
RST" (blackhole — типично для части рекламных/аналитических доменов за
firewall/adblock-инфраструктурой хостера, не самого easylist-блока, который
у нас отклоняется раньше, до сети, `network/src/lib.rs:2280-2325`), блокирует
`TcpStream::connect` на платформенный таймаут SYN-retry (может быть больше
минуты).

Путь до UI-потока: `fetch()` без `AbortSignal` (обычный вызов, каким рекламные
скрипты и зовут beacon-запросы) идёт синхронно
(`web_api_shim_mid_b2.js:1102-1104` → `_lumen_fetch_sync`,
`v8_runtime/install/net.rs:408-441`, без `AbortToken`/таймаута) внутри
**ordered** (не коалесцирующегося) `EngineThread`-таска
(`about_to_wait.rs:260-269`, `engine_bridge.rs:104`). `EngineThread::query()`
(`engine_thread.rs:230-245`) блокируется на `reply_rx.recv()` без таймаута —
и очередь FIFO, так что любой последующий `query()` (в т.ч.
`drain_query_js` на КАЖДОМ `on_about_to_wait()`, включая обработку
`AutomationCommand::ConsoleLog`, `about_to_wait.rs:972`) блокируется позади
застрявшего connect — что и объясняет S3-находку «`winit`-event loop не
дренирует `AutomationCommand`-канал 30+с при 0% CPU»: это не спин, это
цепочка блокирующих `recv()` за один незавершённый TCP-connect.

**Фикс:** `CONNECT_TIMEOUT = 10s` (новая константа, `lib.rs:~1101`),
применена в обоих местах `TcpStream::connect(addr)` (прямой путь и SOCKS5-
прокси) через `TcpStream::connect_timeout(addr, CONNECT_TIMEOUT)`. В отличие
от `read_timeout`, это не `Option`-параметр по вызывающей стороне — connect
всегда должен быть ограничен по времени, независимо от того, живёт ли после
него соединение долго (WebSocket/SSE) или недолго (обычный fetch); только
после установления соединения `read_timeout` расходится на "None" для
долгоживущих кейсов.

Deterministic unit-тест на сам connect-timeout не добавлен — воспроизвести
управляемый blackhole (no RST) на localhost без внешней нероутируемой сети
не получилось надёжно в этой среде (в отличие от read-timeout-теста
`connect_with_read_timeout_bounds_a_stalled_server`, где peer кооперативен и
просто не пишет байты — здесь peer должен НЕ ответить на TCP уровне, что
песочница либо эмулирует недетерминированно, либо возвращает "unreachable"
мгновенно вместо тайм-аута). `cargo test -p lumen-network --lib` (2293
теста) зелёный без регрессий, `clippy -p lumen-network --all-targets -D
warnings` чист.

**Не тронуто** этим срезом: сам исходный симптом BUG-935 (M4-incremental
relayout-путь мёртв под движковым потоком) — это отдельная, ещё не
затронутая находка того же файла (см. «Предполагаемый фикс» выше); S1-S3
были блокированы на нестабильности стенда/невозможности воспроизвести
исходный симптом, а не на этом deadlock'е напрямую — но обнаруженный
deadlock — правдоподобный кандидат на ОДНУ из причин, почему живой прогон на
рекламно-тяжёлых сайтах (ria.ru, lenta.ru) не доходит до состояния,
которое исходный симптом описывает (полное зависание раньше, чем
relayout-путь успевает провериться). Следующая сессия должна повторить S1-
S3 репро на `lenta.ru` С этим фиксом — если зависание исчезло, это
подтверждает причину и открывает дорогу к собственно M4-инкрементальному
census'у, ради которого баг заведён; если зависание осталось — искать
другой блокирующий примитив тем же методом.

## S5 (P3, 2026-09-20) — S4-фикс подтверждён живьём на lenta.ru; найден и не тронут соседний источник того же класса зависания (FIFO `EngineThread::query()` без таймаута)

Повторил репро S3 (`scripts/bug935_hang_probe.py https://lenta.ru`) на
собранном `dev-release` этой ветки (уже содержит S4 — `CONNECT_TIMEOUT=10s`
влит в `main` до старта этой сессии). Результат прямо противоположен S3:
`painted=True`, тишина в логе детектирована через 15с как и раньше, но на
этот раз `resources/read(resource://console)` **ответил за 4.7с** (S3: не
ответил вовсе за 60с). `tasklist` до/после пробы показывает штатный рост
RSS, процесс не завис. Это подтверждает диагноз S4: TCP-connect без
таймаута был как минимум одним реальным источником deadlock'а на этом
стенде, и его фикс наблюдаемо чинит хотя бы часть картины.

Дальше пошёл на более длинный прогон (не 90с probe-скрипта, а прямой запуск
на ~5 минут с тем же `LUMEN_PROFILE_TREE=1 LUMEN_FRAME_LOG=1`), чтобы
проверить не только «первую тишину», но и устойчивость дальше по времени
жизни вкладки — ровно то, что нужно для census'а M4-incremental-пути, ради
которого баг заведён. За первые ~220с — 4 `[engine] relayout` (146-242мс,
все full off-thread — `try_relayout_raf_incremental` по-прежнему не
исполняется под дефолтным движковым потоком, «Корень» раздела всё ещё
живой), заметно меньше исходных «33 по 850-2600мс», но страница и трафик от
рекламных доменов за сессию/день отличаются — это не количественное
опровержение исходного репорта, просто другой снимок того же живого сайта.

Затем прямой MCP-запрос (отдельный скрипт с одним переиспользуемым
`socket.makefile()`, не пересоздающимся на каждый вызов — попытка с новым
`makefile()` на каждый `call()` даёт ложный "connection error" на стороне
клиента и не годится для диагностики) к тому же процессу спустя ~230с работы
показал: `initialize` отвечает мгновенно (0.008с — TCP/IPC-приёмник жив), но
`resources/read(resource://console)` **не ответил за 25с**. Лог в этот
момент показывал незавершённые попытки к `kraken.rambler.ru`/`kraken-mdt.
rambler.ru` (часть блокируется easylist до сети, часть — TLS-ошибками
сертификата, которые возвращаются быстро) непосредственно перед тишиной.

Это **не новый независимый deadlock** — это тот же механизм, который S4 уже
назвал и явно пометил как нетронутый: `fetch()` без `AbortSignal` идёт
синхронно внутри **ordered** (не latest-wins) `EngineThread`-таска
(`_lumen_fetch_sync`), а `EngineThread::query()` (`engine_thread.rs:230-245`,
`reply_rx.recv()` без таймаута) исполняется по очереди FIFO — если очередь
уже держит синхронный fetch к серверу, для которого действует
`FETCH_READ_TIMEOUT=60s` (не `CONNECT_TIMEOUT=10s`, тот случай S4 не
покрывает — соединение уже установлено, зависание в чтении ответа/TLS-
рукопожатии на уже открытом сокете), **любой** последующий `query()`,
включая `AutomationCommand::ConsoleLog`, блокируется на срок до 60с. S4
починил один из двух путей входа в этот класс (connect), а не саму FIFO-
очередь без таймаута — она и есть настоящий корень «непредсказуемо долгого
зависания MCP/automation-канала», а не то, где именно застревает конкретный
сетевой вызов внутри неё.

**Правки кода не делались** (только измерение и этот раздел) — по тем же
причинам, что и раньше: точечно добавить таймаут в `EngineThread::query()`
затронуло бы ВСЕ его вызовы (`eval_js_value`, `take_dom_dirty`,
`take_raf_pending`, не только automation-путь), и `docs/plan/architecture.md`
инвариант "исполняется по порядку" для этого канала не обсуждает поведение
при таймауте не пришедшего ответа (спасательный откат на дефолт для каждого
вызывающего места пришлось бы проектировать отдельно) — ровно тот случай
«не точечная правка, нужен перф-протокол», о котором предупреждает раздел
«Предполагаемый фикс» выше, только теперь применительно к `query()`, а не
к `relayout_raf_dirty`.

**Итог:** S4 подтверждён рабочим на живом стенде — не откатывать. Основной
симптом бага (M4-incremental-путь не используется под движковым потоком)
по-прежнему воспроизводится (4 relayout'а по 146-242мс за ~220с). Найден
второй, отдельный от `relayout_raf_dirty`, вход в тот же класс «FIFO-
очередь блокируется без таймаута на синхронном сетевом вызове» —
`EngineThread::query()`. Следующая сессия должна решить, в каком порядке
брать три независимые находки этого бага (M4-incremental-роутинг,
`EngineThread::query()`-таймаут, оставшиеся сетевые пути без таймаута) —
это архитектурное решение, не входящее в scope одного среза.

## S6 (P3, 2026-09-20) — таймаут в `EngineThread::query()` (первая из трёх находок S5)

Из трёх независимых находок S5 взята первая: `EngineThread::query()`
(`crates/shell/src/engine_thread.rs`) больше не блокируется на
`reply_rx.recv()` без предела. Добавлена константа `QUERY_TIMEOUT = 5s`
(запас над наблюдёнными full-relayout 146–2600мс из S3/S5, много меньше
`FETCH_READ_TIMEOUT=60s`) и переход на `reply_rx.recv_timeout(QUERY_TIMEOUT)`.
Оба исхода — `Disconnected` (поток завершён) и `Timeout` (задание застряло в
FIFO позади долгого синхронного соседа) — возвращают `None`, который
вызывающая сторона (`route_query_js` и все его потребители: `take_dom_dirty`,
`take_raf_pending`, `eval_js_value` и т.д.) уже трактует как «без JS» —
новый режим отказа не заведён, существующий лишь ограничен сверху. Задание
из очереди никуда не девается и всё равно исполнится (мутация состояния `S`
не теряется) — теряется только ответ, который уже некому принять.

Добавлен регрессионный тест
`engine_thread::tests::query_times_out_when_stuck_behind_long_task`:
блокирующий `task()` (сон `QUERY_TIMEOUT + 1s`) перед `query()` — раньше
`query()` ждал бы весь срок соседа, теперь возвращает `None` не позже
`QUERY_TIMEOUT`. `cargo clippy -p lumen-shell --all-targets -- -D warnings`
и `cargo test -p lumen-shell -- engine_thread` — зелёные (35/35).

**Не сделано** (осталось для будущих срезов, из списка S5): M4-incremental-
роутинг всё ещё не исполняется под движковым потоком (основной симптом
бага); остальные сетевые пути (`fetch`/XHR) внутри `Task` по-прежнему без
собственного таймаута на чтение — `QUERY_TIMEOUT` бьёт только по стороне
ожидания вызывающего, а не по длительности самого сетевого вызова.

## S7 (P3, 2026-09-20) — тот же класс дедлока найден и починен в WebSocket-хендшейке

Продолжение аудита «синхронный сетевой вызов без таймаута блокирует ordered
`EngineThread`-задание» (S4/S5/S6 закрыли TCP-connect и `EngineThread::query()`).
Прочитан `crates/network/src/websocket/mod.rs::connect`/`connect_deflate`: оба
вызывают внутренний `connect(..., read_timeout: None)` с комментарием «No read
timeout — WebSocket сидит idle дольше любого fetch», что верно для **уже
установленного** соединения, но тем же `None` неявно накрывало и сам
`upgrade::perform`/`perform_with_deflate` — открывающий HTTP-хендшейк
(`GET ... Upgrade: websocket` → ожидание `101`), который читает построчно
через `read_exact` (`websocket/upgrade.rs::read_line`) без собственного предела.
Сервер/прокси, принявший TCP/TLS-соединение (проходит `CONNECT_TIMEOUT=10s` из
S4), но не ответивший `101` (зависший прокси, сервер, не понимающий Upgrade и
просто держащий сокет), блокирует этот `read_exact` навсегда — тот же класс,
что S4 (TCP-connect) и S5 (`fetch` без таймаута на чтение), только третий
самостоятельный вход, ранее не проверенный ни одним срезом.

**Фикс:** `connect`/`connect_deflate` (`websocket/mod.rs`) теперь выставляют
`FETCH_READ_TIMEOUT` (60s, та же константа, что бьёт по `fetch`/XHR) на сокет
ПЕРЕД вызовом `upgrade::perform`/`perform_with_deflate` и снимают его
(`set_read_timeout(None)`) сразу после — независимо от исхода — прежде чем
хендшейк-результат уходит наверх через `?`. Долгоживущий пост-хендшейк сокет
остаётся без таймаута, как и было (комментарий на месте уточнён — раньше он
говорил «No read timeout» без оговорки, что это только про фазу ПОСЛЕ
хендшейка).

Regression-тест `ws_handshake_read_times_out_against_a_stalled_server`
(`crates/network/src/lib.rs`): сервер принимает TCP и держит соединение 2с, ни
разу не отвечая `101`; клиентский `TcpStream` получает короткий
`read_timeout=150ms` (не настоящий `FETCH_READ_TIMEOUT=60s` — тест бьёт по
тому же механизму `upgrade::perform`, не ждёт реальный таймаут), `upgrade::perform`
обязан вернуть `Err` быстрее 1с вместо зависания. `cargo test -p lumen-network
--lib` — 2294/2294 зелёных (было 2293 — тест новый), `cargo clippy -p
lumen-network --all-targets -- -D warnings` чист.

**Не тронуто:** основной симптом бага (M4-incremental routing мёртв под
движковым потоком) по-прежнему не тронут — это отдельная, самая крупная из
трёх находок S5, требующая полного перф-протокола (census + A/B), не
точечного фикса. Не проверено, есть ли аналогичный непокрытый хендшейк-путь у
`EventSource`/SSE (`crates/network/src/sse.rs`) — SSE тоже открывает
соединение и держит его долго, но не было включено в скоуп этого среза
(другой сервер-паттерн: чистый HTTP-ответ с `Content-Type:
text/event-stream`, а не отдельный протокол-хендшейк как WS); стоит
проверить в следующем срезе, если аудит сетевых таймаутов продолжится.

## S8 (P3, 2026-09-20) — тот же класс дедлока найден и починен в хендшейке SSE (`EventSource`)

Продолжение аудита S4/S5/S6/S7 («синхронный сетевой вызов без таймаута
блокирует ordered `EngineThread`-задание»). S7 явно оставил непроверенным
`EventSource` (`crates/network/src/sse.rs`) — «стоит проверить, если аудит
сетевых таймаутов продолжится».

`EventSource::open_connection` читал статус-строку и заголовки ответа через
`BufReader::read_line` вообще без таймаута — комментарий на месте («No read
timeout: an EventSource connection is meant to sit idle between server-sent
events far longer than any bounded fetch») верен только для уже установленного
потокового тела, но по ошибке накрывал и сам открывающий HTTP-обмен. Путь до
UI-потока идентичен S7: `_lumen_sse_connect` (`crates/js/src/v8_runtime/install/net.rs:1403`)
вызывает `provider.connect_sse(&url)` **синхронно** прямо из JS-биндинга —
внутри того же ordered `EngineThread`-таска, что и `fetch`/WS. Сервер/прокси,
принявший TCP/TLS-соединение (проходит `CONNECT_TIMEOUT=10s` из S4), но не
приславший ни строки ответа, блокирует `read_line` навсегда — третий
самостоятельный вход в тот же класс (первый — TCP-connect S4, второй —
`EngineThread::query()` S6, третий — WS-хендшейк S7).

**Фикс:** `open_connection` выставляет `FETCH_READ_TIMEOUT` (60s, та же
константа, что WS-хендшейк) на сырой сокет ПЕРЕД чтением статус-строки и
заголовков и снимает его (`set_read_timeout(None)`) сразу после — до того, как
поток становится долгоживущим idle-ридером тела, сохраняемым в
`self.stream`. Логика чтения статус-строки/заголовков вынесена в отдельную
функцию `read_response_head<R: BufRead>` — по тому же соображению, что и
`websocket::upgrade::perform` в S7: чтобы регрессионный тест мог прогнать её
напрямую на сыром `TcpStream` с коротким `read_timeout`, не дожидаясь
настоящих 60с.

Regression-тест `sse_handshake_read_times_out_against_a_stalled_server`
(`crates/network/src/sse.rs`): сервер принимает TCP и держит соединение 2с, ни
разу не отвечая; клиентский `TcpStream` получает `read_timeout=150ms`,
`read_response_head` обязан вернуть `Err` быстрее 1с вместо зависания.
`cargo test -p lumen-network --lib` — 2295/2295 зелёных (было 2294 — тест
новый), `cargo clippy -p lumen-network --all-targets -- -D warnings` чист.

**Не тронуто:** основной симптом бага (M4-incremental routing мёртв под
движковым потоком) по-прежнему не тронут — самая крупная из находок S5,
требует полного перф-протокола (census + A/B), не точечного фикса. Аудит
«синхронный сетевой вызов без собственного таймаута на ordered
`EngineThread`-задаче» пройден по всем путям, которые называли S4/S5/S6/S7 —
TCP-connect, `EngineThread::query()`, WS-хендшейк, SSE-хендшейк; следующая
сессия должна решить, остались ли ещё непроверенные сетевые входы этого
класса (например TLS-хендшейк отдельно от TCP-connect — не проверялся ни
одним срезом), или переходить к самому M4-incremental census'у.

## S9 (P3, 2026-09-20) — тот же класс дедлока найден и починен в самом TLS-хендшейке (не только в WS/SSE HTTP-обмене поверх него)

Продолжение аудита S4/S5/S6/S7/S8. S8 явно оставил открытым вопрос
«TLS-хендшейк отдельно от TCP-connect — не проверялся ни одним срезом».

Прочитан `connect_inner` (`crates/network/src/lib.rs:1154`): `read_timeout`
выставляется на сокет ДО TLS-хендшейка, но только когда вызывающая сторона
передала `Some(...)`. `websocket::mod.rs::connect`/`connect_deflate` и
`sse.rs::connect` (все три места, где вызывается сетевой `connect()`) зовут
его с `read_timeout: None` — намеренно, чтобы уже установленное
долгоживущее соединение могло простаивать сколь угодно (idle между
кадрами/событиями). Побочный эффект: `None` действовал и на сам
`conn.complete_io(&mut tcp)` (rustls-хендшейк) — TLS-версия того же
дефекта, что S7/S8 нашли в HTTP-обмене НАД хендшейком (`upgrade::perform`/
`read_response_head`), только на уровень раньше. Сервер/прокси, принявший
TCP-соединение (проходит `CONNECT_TIMEOUT=10s` из S4), но не завершивший
TLS-рукопожатие (не прислал `ServerHello`, завис после `ClientHello`),
блокировал `complete_io` навсегда — четвёртый самостоятельный вход в тот
же класс «синхронный сетевой вызов без таймаута на ordered
`EngineThread`-задаче» (после TCP-connect S4, `EngineThread::query()` S6,
WS-хендшейк S7, SSE-хендшейк S8).

**Фикс:** `connect_inner` (`lib.rs`) выставляет `FETCH_READ_TIMEOUT` (60s,
та же константа) на сокет перед `conn.complete_io(&mut tcp)`, когда
`read_timeout` — `None`, и снимает его (`set_read_timeout(None)`) сразу
после — независимо от исхода, до того как соединение уходит наверх как
долгоживущее. Когда `read_timeout` — `Some(...)` (обычный `fetch`/XHR),
поведение не меняется: тот таймаут и так уже покрывал хендшейк.

Regression-тест `tls_handshake_read_times_out_against_a_stalled_server`
(`crates/network/src/lib.rs`): реальный `rustls::ClientConnection` против
сервера, который принимает TCP и держит соединение 2с, не отправляя ни
байта; `complete_io` с коротким `read_timeout=150ms` на сокете обязан
вернуть `Err` быстрее 1с вместо зависания — драйвит тот же механизм,
что и фикс, напрямую (не через полный `connect_inner`, которому нужна
живая DNS-резолюция). `cargo test -p lumen-network --lib` — 2296/2296
зелёных (было 2295 — тест новый), `cargo clippy -p lumen-network
--all-targets -- -D warnings` чист.

**Не тронуто:** основной симптом бага (M4-incremental routing мёртв под
движковым потоком) по-прежнему не тронут — самая крупная из находок S5,
требует полного перф-протокола (census + A/B), не точечного фикса. Аудит
«синхронный сетевой вызов без собственного таймаута на ordered
`EngineThread`-задаче» пройден по всем путям, названным S3/S5/S8:
TCP-connect, `EngineThread::query()`, WS-хендшейк, SSE-хендшейк,
TLS-хендшейк. Не проверено: остаются ли ещё сетевые примитивы этого
класса (SOCKS5-хендшейк `socks5_connect` в `connect_inner` — вызывается
ПОСЛЕ `TcpStream::connect_timeout`, до всякого `read_timeout`, не
проверялся). Следующая сессия должна решить, продолжать ли аудит (SOCKS5)
или переходить к самому M4-incremental census'у на подтверждённом стенде
lenta.ru (S5).

## S10 (P3, 2026-09-20) — тот же класс дедлока найден и починен в SOCKS5-хендшейке (последний непроверенный вход из списка S9)

Продолжение аудита S4/S5/S6/S7/S8/S9. S9 явно оставил открытым вопрос:
«остаются ли ещё сетевые примитивы этого класса (SOCKS5-хендшейк
`socks5_connect` в `connect_inner` — вызывается ПОСЛЕ
`TcpStream::connect_timeout`, до всякого `read_timeout`, не проверялся)».

Прочитан `crates/network/src/socks5.rs::socks5_connect`: метод-негоциация,
опциональная RFC 1929 username/password авторизация и CONNECT-запрос/ответ
читаются через несколько `read_exact` подряд на сокете, который приходит из
`connect_inner` (`lib.rs:1179`) сразу после `TcpStream::connect_timeout` —
**вообще без какого-либо read timeout**, ни временного, ни постоянного (в
отличие от TLS/WS/SSE путей S7-S9, где `read_timeout: None` хотя бы
устанавливался явно намеренно для долгоживущего тела). SOCKS5-прокси
(например Tor daemon), который принял TCP-соединение (проходит
`CONNECT_TIMEOUT=10s` из S4), но завис на любой из трёх фаз обмена (не
ответил на приветствие, запросил авторизацию и не проверил её, не ответил на
CONNECT), блокирует `read_exact` навсегда — пятый и последний
самостоятельный вход в тот же класс «синхронный сетевой вызов без
собственного таймаута на ordered `EngineThread`-задаче» (после TCP-connect
S4, `EngineThread::query()` S6, WS-хендшейк S7, SSE-хендшейк S8,
TLS-хендшейк S9).

**Фикс:** `connect_inner` (`lib.rs`, SOCKS5-ветка) выставляет
`FETCH_READ_TIMEOUT` (60s, та же константа, что и остальные четыре фикса) на
`proxy_tcp` ПЕРЕД вызовом `socks5::socks5_connect` и снимает его
(`set_read_timeout(None)`) сразу после успешного туннелирования — до того,
как дальше по функции `connect_inner` применяется вызывающий `read_timeout`
(для обычного `fetch`/XHR) или собственный `FETCH_READ_TIMEOUT` на TLS-
хендшейк (S9, для WS/SSE). `socks5_connect` сам не тронут — таймаут целиком
снаружи, на уровне сокета, как и во всех предыдущих срезах этого аудита.

Regression-тест `socks5_handshake_read_times_out_against_a_stalled_server`
(`crates/network/src/socks5.rs`): сервер принимает TCP и держит соединение
2с, не отвечая на приветствие; клиентский `TcpStream` получает
`read_timeout=150ms` (тест бьёт по `socks5_connect` напрямую, не через
полный `connect_inner`, которому нужен настоящий SOCKS5-прокси), функция
обязана вернуть `Err` быстрее 1с вместо зависания. `cargo test -p
lumen-network --lib` — 2297/2297 зелёных (было 2296 — тест новый), `cargo
clippy -p lumen-network --all-targets -- -D warnings` чист.

**Итог аудита S4-S10:** все известные синхронные сетевые примитивы на
ordered `EngineThread`-задаче теперь ограничены по времени: TCP-connect,
`EngineThread::query()`, WS-хендшейк, SSE-хендшейк, TLS-хендшейк,
SOCKS5-хендшейк. **Не тронуто:** основной симптом бага (M4-incremental
routing мёртв под движковым потоком) — самая крупная из находок S5, требует
полного перф-протокола (census + A/B на живом стенде, S5 подтвердил
`lenta.ru` как воспроизводимый и стабильный). Следующая сессия должна
перейти к собственно M4-incremental census'у — аудит таймаутов сетевых
примитивов этого класса исчерпан, дальнейшая работа по этому багу — census,
не поиск новых точек дедлока.

## S11 (P3, 2026-09-20) — первый успешный M4-incremental census: подтверждён и количественно измерен основной симптом, попутно найден и починен новый блокер census'а (`DEFAULT_TIMEOUT` короче `FETCH_READ_TIMEOUT`)

Продолжение с того места, на котором остановился S10 («аудит таймаутов
сетевых примитивов исчерпан, следующая сессия должна перейти к собственно
M4-incremental census'у»). Запущен `scripts/bug935_raf_relayout_census.py
https://lenta.ru --settle-s 20 --ticks 20` на подтверждённом S5 стенде.

**Блокер census'а (найден и починен первым):** прогон падал с `Scroll
error: automation command timed out` посреди 20 scroll-тиков. Причина —
`crates/driver/src/live_session.rs::DEFAULT_TIMEOUT = 30s` (таймаут
одного automation-round-trip'а) меньше `lumen_network`'s
`FETCH_READ_TIMEOUT = 60s` (S4-S10 ограничили этим значением все сетевые
примитивы на том же ordered `EngineThread`-FIFO). Automation-команда
(`scroll`), поставленная в очередь позади синхронного сетевого вызова,
который легитимно (не бесконечно, но и не мгновенно) занимает до 60с,
физически не может успеть за 30с — не деадлок, а бюджетное несоответствие
между двумя независимо выбранными константами одного и того же тракта.
Подтверждено пробой `bug935_hang_probe.py --probe-timeout-s 70`: MCP
ответил за 13.5с на «тишину» — канал жив, просто медленный.

**Фикс:** `DEFAULT_TIMEOUT` поднят с 30с до 65с (`live_session.rs`) — с
запасом над `FETCH_READ_TIMEOUT=60s`, задокументирована связь двух
констант в разных крейтах (нет прямой ссылки, `FETCH_READ_TIMEOUT`
приватна в `lumen-network`, значение продублировано в комментарии).
`cargo clippy -p lumen-driver --all-targets -- -D warnings` чист, `cargo
test -p lumen-driver --lib` — 83/83 зелёных, без регрессий.

**Собственно census (после фикса):** первый успешный прогон, дошедший до
конца всех 20 scroll-тиков на `lenta.ru`.

```
relayout до document_ready:     0
relayout за 20с settle (без scroll): 1  (312мс, dl=1583 styled=1144)
relayout за 20 scroll-тиков:    3  (419-1812мс, все off-thread ПОЛНЫЕ —
                                    dl/styled не растут между ними, т.е.
                                    не content-visibility, тот же класс,
                                    что открывающий репорт бага)

scroll RTT ms: min=388.7 avg=18030.2 max=59154.5
все значения (20 тиков по порядку):
15699, 33271, 30964, 48101, 2481, 389, 593, 32461, 59155, 14288,
15047, 10658, 13571, 11728, 11901, 11979, 11688, 12055, 12481, 12096
```

Это первое количественное подтверждение основного симптома бага на
живом сайте с этим срезом кода (S4-S10 не трогали M4-роутинг вовсе):
`scroll` RTT держится в диапазоне **10-33с** для 17 из 20 тиков (не
850-1400мс, как в исходном 2026-09-01 замере — сайт/трафик другие, но
порядок хуже, не лучше), с двумя выбросами до 48с и 59с. Три полных
off-thread relayout'а за 20 тиков — не «один на каждый тик», значит
`EngineThread` coalescing (S5's «сообщение `submit`'а коалесцирует
промежуточные заявки») действительно работает и не даёт очереди расти
неограниченно, но даже 3 полных пересчёта каскада достаточно, чтобы почти
весь 20-тиковый прогон (17/20 RTT выше 10с) провёл в состоянии «движковый
поток занят», подтверждая диагноз «Корня» раздела buга буквально на
цифрах, не только по логике кода.

**Не сделано:** сама правка M4-роутинга (смена порядка `||`-веток в
`relayout_raf_dirty`/`relayout_raf_dirty_readback`) по-прежнему не
внесена — census теперь ЕСТЬ (что и было условием для перехода к правке
по `docs/perf-method.md`), но интерливед A/B «до/после» смены порядка
на этом же стенде — отдельный следующий шаг, не входящий в этот срез
(его размер и риск сопоставимы с отдельным полноценным срезом, а не
довеском к уже большому S11). Следующая сессия должна: (1) внести
смену порядка веток, (2) прогнать этот же census-скрипт на этой же
странице интерливед несколько раз до/после, сравнить RTT/relayout-счётчик,
(3) отдельно измерить долю пропущенных кадров/задержку ввода на
UI-потоке от синхронного `try_relayout_raf_incremental` — именно тот
компромисс, который «Предполагаемый фикс» выше называет ценой перехода.

## S12 (P3, 2026-09-20) — смена порядка веток измерена живьём и ОТКАЧЕНА: подтверждённая регрессия, найден настоящий блокер M4-fast-path

Продолжение с того места, на котором остановился S11 («следующая сессия должна
(1) внести смену порядка веток, (2) прогнать census interleaved, (3) измерить
долю пропущенных кадров»). Сначала добавлено логирование под
`LUMEN_FRAME_LOG=1` в `try_relayout_raf_incremental` (`relayout.rs`) — до этого
среза путь не печатал вообще ничего, так что census S11 не мог увидеть его
собственную стоимость (`docs/perf-method.md` §2 «профилируй ТОТ путь, который
меняешь»). Новая строка: `[engine] relayout {ms}ms (incremental, on-thread)
dl=... styled=... restyle={0|1}` — последнее поле отличает дешёвую
cascade-skip ветку (`page_prev_cascade_styles` был `Some`) от дорогой полной
`relayout_page_incremental` без cascade-skip. Census-скрипт
(`scripts/bug935_raf_relayout_census.py`) расширен: `RELAYOUT_RE` дополнен
`ANY_RELAYOUT_RE`, разбивка по типу (`off-thread` / `incremental, on-thread`)
вместо одной колонки.

Затем внесена сама правка (1) — `||`-порядок в `relayout_raf_dirty`/
`relayout_raf_dirty_readback` поменян местами, `try_relayout_raf_incremental`
пробуется первым. Прогнан census (`lenta.ru`, `--settle-s 20 --ticks 20`) на
собранном `dev-release` этой ветки.

**Результат — регрессия, не выигрыш:** все 8 инкрементальных relayout'ов за
прогон вышли `restyle=0` (0 из 8 — cascade-skip путь ни разу не сработал),
т.е. каждый тик шёл через дорогую ветку `relayout_page_incremental` (без
cascade-skip) **синхронно на UI-потоке** вместо off-thread. Стоимость по
логу: 650–850мс на тик (6 записей), и один провал в 7293.78мс +
7363.17мс подряд (`[frame] total 14295.82ms`, `js 12923.45`) — это не шум
станка, это НАСТОЯЩАЯ блокировка UI-потока на 14+с, вызванная именно этой
правкой (при исходном порядке та же ситуация ушла бы off-thread и не
блокировала бы MCP/automation-канал). Census не дошёл до конца 20 тиков —
упал на очередном `scroll` с `automation command timed out`, тем же классом
симптома, который S3-S10 чинили для СЕТЕВЫХ вызовов на ordered
`EngineThread`-FIFO, только на этот раз источник другой: `scroll`
обрабатывается на самом UI-потоке (`winit`'s `about_to_wait`/`RedrawRequested`),
который эта правка теперь занимает синхронным layout'ом — лог не даёт точно
сказать, какой из восьми тиков не уложился в `DEFAULT_TIMEOUT=65s`, но
направление однозначно: on-thread путь **хуже** исходного off-thread для
этого сайта, не лучше.

**Корень регрессии — не "стоимость try_relayout_raf_incremental" сама по
себе, а то, что дешёвая часть его логики недостижима с этого call site:**
cascade-skip ветка (`fresh_cascade_styles = Some(...)`) требует
`self.page_prev_cascade_styles` быть `Some` НА ВХОДЕ в
`try_relayout_raf_incremental` (`relayout.rs:315`, `.take()`). Но это поле
устанавливается в `Some` ровно в одном месте кода — в конце самой этой
cascade-skip ветки (после её успешного прохода), и обнуляется в `None` во
всех остальных производителях: `relayout()` (полный синхронный),
`readback_relayout_job`, `poll_engine_commit`'s `apply_relayout_result`
(`relayout.rs:789`, доккомментарий там прямо говорит: «forcing the next
incremental attempt onto the safe full-cascade-plus-graft fallback for one
cycle»). До этого среза комментарий читался как обещание, что ПОСЛЕ одного
цикла на полной ветке следующий цикл получит `Some` и пойдёт по дешёвому
пути — но `else`-ветка самого `try_relayout_raf_incremental`
(`relayout_page_incremental`, не `_restyle`) тоже не заполняет
`fresh_cascade_styles` (она статически `None` для этой ветки, `relayout.rs`
строка с `(dl, lb, None)`), поэтому цепочка «полная попытка → следующая
дешёвая» никогда не замыкается через ЭТОТ путь: если `page_prev_cascade_styles`
уже `None` на входе (обычный случай — предыдущий цикл шёл через `relayout()`
или через `submit_relayout_job`/`readback_relayout_job`, что при старом
порядке было ВСЕГДА, а при новом порядке — с первого же тика, раз
предыдущий тоже не восстановил кэш), он остаётся `None` бесконечно, и
`try_relayout_raf_incremental` навсегда застревает в дорогой ветке.
Другими словами: без дополнительной правки, заполняющей
`page_prev_cascade_styles` из non-restyle-ветки (или без отдельного
источника, который умеет его сеять), «дешёвый M4-путь» в этом коде **вообще
недостижим** при input вида «непрерывный rAF+DOM-цикл», единственном
сценарии, ради которого баг заведён — 0/8 в этом прогоне, не выборка, а
структурная невозможность по коду.

**Действие:** правка (1) отменена (`git` в этом же срезе — обе функции
вернули исходный порядок `submit_relayout_job`/`readback_relayout_job`
первыми), логирование в `try_relayout_raf_incremental` и расширение
census-скрипта **оставлены** (безвредны под `LUMEN_FRAME_LOG`, и это они
обнаружили находку — без них регрессия осталась бы невидимой числом, только
«страница подвисла один раз» на глаз). `cargo clippy -p lumen-shell
--all-targets -- -D warnings` чист, `cargo test -p lumen-shell --bins --
relayout` — 10/10 зелёных на откаченном коде.

**Не сделано / следующий срез:** (2) и (3) из плана S11 больше не имеют
смысла в исходной формулировке — интерливед A/B "старый порядок vs новый
порядок" при 0/8 cascade-skip сравнивал бы "off-thread всегда" с "on-thread
всегда чуть дороже + иногда 10x дороже", результат предсказан этим срезом
без полного протокола. Настоящий следующий шаг — НЕ повторная попытка
смены порядка, а починка самого условия входа в cascade-skip: либо (а)
научить non-restyle-ветку `try_relayout_raf_incremental`
(`relayout_page_incremental`) тоже возвращать/строить `CascadeStyles` для
следующего цикла (структурная правка алгоритма, не однострочная), либо (б)
завести отдельный путь заполнения `page_prev_cascade_styles` из
`relayout()`/`readback_relayout_job`, если это вообще безопасно (эти пути
не гарантируют то же самое множество узлов, что ждёт cascade-skip —
нужна отдельная проверка инварианта, не точечная правка). Только после
одного из этих двух — есть смысл возвращаться к смене порядка `||`-веток
и к пунктам (2)/(3) плана S11.

## S13 (P3, 2026-09-20) — починен корень регрессии S12: не-restyle ветка `try_relayout_raf_incremental` теперь тоже сеет `page_prev_cascade_styles`

Продолжение с того места, где остановился S12 («настоящий следующий шаг — НЕ
повторная попытка смены порядка, а починка самого условия входа в
cascade-skip»). S12 нашёл два возможных направления: (а) научить не-restyle
ветку `try_relayout_raf_incremental` (`relayout_page_incremental`) тоже
возвращать/строить `CascadeStyles` для следующего цикла, либо (б) отдельный
путь заполнения из `relayout()`/`readback_relayout_job`. Взято (а) — оно
безопаснее: не-restyle ветка и так уже гоняет полный каскад внутри
`layout_mutation_incremental` (`layout_streaming_incremental` →
`precompute_counters`), просто выбрасывала результат.

**Находка при чтении:** `grep` по всему дереву `page_prev_cascade_styles`
показал, что ДО этого среза поле не устанавливалось в `Some` вообще нигде в
кодовой базе, кроме самой restyle-ветки `try_relayout_raf_incremental` (и то
только после того, как restyle-ветка уже успешно исполнилась). Раз вход в
restyle-ветку сам требует, чтобы поле уже было `Some`, а единственный
производитель `Some` — сама эта ветка, цепочка не может начаться ни разу ни
при каком порядке вызовов и ни при какой сборке (не только под
`LUMEN_ENGINE_THREAD=1`, как формулировал корень бага раньше) — дешёвый путь
был мёртв структурно, с первого коммита BUG-341 S7. S12's эксперимент со сменой
`||`-порядка ничего не мог изменить именно поэтому: 0/8 `restyle=1` — не
статистическая случайность конкретного прогона, а гарантированный исход при
любом количестве тиков.

**Фикс** (три места, `crates/engine/layout/src/box_tree/entry.rs` +
`crates/shell/src/relayout.rs`):

1. `layout_streaming_incremental_with_counters` — рядом с существующей
   `layout_streaming_incremental` (тонкая обёртка над ней, отбрасывающая
   `CounterMap`, чтобы не трогать её единственного другого вызывающего —
   `page_load.rs`'s стриминговый путь загрузки, которому кэш не нужен).
2. `layout_mutation_incremental_with_counters` — аналогично для
   `layout_mutation_incremental`.
3. `relayout_page_incremental`/`compute_layout_incremental` (`relayout.rs`)
   теперь возвращают `CounterMap` третьим элементом кортежа (единственный
   вызывающий — `try_relayout_raf_incremental`, сигнатуру можно было менять
   без обёртки).
4. `try_relayout_raf_incremental`: `fresh_cascade_styles` для обеих веток
   (restyle и full) теперь именно `CascadeStyles` (не `Option`), и
   `self.page_prev_cascade_styles = Some(fresh_cascade_styles)` пишется
   безусловно после `apply_relayout_result`, а не только для restyle-ветки.
   `self.page_prev_interactive = new_interactive` — туда же (раньше тоже
   писалось только restyle-веткой; без синхронного обновления после
   full-ветки следующий цикл сравнивал бы новое hover/focus/active состояние
   не с тем, что реально было на входе в last full pass).
   Различение «какая ветка сработала» для отладочного лога
   (`restyle={0|1}`) вынесено в отдельный `bool used_restyle`, заданный по
   месту в каждой ветке — раньше он читался как `fresh_cascade_styles.is_some()`,
   что после этой правки было бы всегда `true` и потеряло бы смысл.

**Почему это корректно (не просто компилируется):** `CascadeStyles`,
которую строит full-cascade ветка (`layout_mutation_incremental_with_counters`
→ `layout_streaming_incremental_with_counters` → `precompute_counters`), —
самый обычный полный каскад того же вида, что и самый первый проход страницы
(`layout_measured_hyp_with_counters`, тот же путь, который сегодня сеет
кэш для потомков `layout_mutation_incremental_restyle` при инициализации
других циклов, например chrome-хоста, BUG-341 S6/S7). Контракт restyle-пути
(`delta.prev_styles` должен быть «`CounterMap::styles()`, который тот же
документ произвёл на прошлом цикле») ничего не говорит про то, каким путём
тот прошлый цикл был получен — только что он полный и актуальный. Full-ветка
даёт именно это: `precompute_counters` не пропускает ни одного узла (в
отличие от restyle-пути, который сознательно скипает чистые поддеревья), so
её результат — даже более надёжный источник кэша, не менее. Пройденный
пасс-ординал (`CascadeStyles::pass`) при этом стартует с 0 у каждого
свежепостроенного `CounterMap` (`with_capacity`) — ровно то же значение,
что и у самого первого прохода страницы, так что цепочка `pass 0 (full) →
pass 1 (restyle, reuse valid) → …` работает без специального случая.

**Тест:** `mutation_incremental_with_counters_seeds_a_cache_matching_a_fresh_full_cascade`
(`crates/engine/layout/src/incremental.rs`) — сравнивает
`layout_mutation_incremental_with_counters`'s `CounterMap::into_styles()` с
`CounterMap`, которую даёт `layout_measured_hyp_with_counters` над тем же
итоговым DOM с нуля; `CascadeStyles::eq` сравнивает результат каскада, не
пасс-ординалы (как и differential-тесты BUG-341), так что это именно
проверка «то же содержимое, независимо от того, каким путём получено».
`cargo test -p lumen-layout --lib -- incremental` — 52/52 зелёных (включая
новый), `cargo clippy -p lumen-layout --all-targets -- -D warnings` и
`cargo clippy -p lumen-shell --all-targets --features v8 -- -D warnings` —
чистые.

**Эффект под дефолтной сборкой:** по-прежнему нулевой сам по себе —
`try_relayout_raf_incremental` вызывается из `relayout_raf_dirty` только
когда `submit_relayout_job()` вернул `false`, а под `LUMEN_ENGINE_THREAD=1`
(дефолт с ADR-023) она возвращает `true` почти всегда — см. «Корень» раздела
выше, этот срез его не трогал. Значение этого среза — убрать структурный
блокер, который делал ЛЮБУЮ попытку задействовать дешёвый путь (в том числе
S12's смену порядка) заведомо провальной независимо от порядка вызовов;
S12's «650-850мс на тик, 0/8 restyle» был прямым следствием именно этого
отсутствия, не самой смены порядка.

**Не сделано / следующий срез:** сама смена `||`-порядка в
`relayout_raf_dirty`/`relayout_raf_dirty_readback` по-прежнему не внесена —
теперь у неё есть шанс не повторить регрессию S12 (после одного full-цикла
кэш будет `Some`, второй тик того же rAF-цикла уже может пойти по
cascade-skip), но это нужно измерить заново тем же протоколом (census +
интерливед A/B на `lenta.ru`, S5/S11's подтверждённый стенд), не
предполагать. Следующая сессия должна повторить S11/S12's эксперимент на
этом фиксе: (1) внести смену порядка, (2) прогнать
`scripts/bug935_raf_relayout_census.py` на `lenta.ru`, (3) проверить долю
`restyle=1` по логу `[engine] relayout … (incremental, on-thread) … restyle=…`
и RTT `scroll` — если `restyle=1` теперь ненулевая доля тиков и RTT не хуже
исходного off-thread baseline (S11: 10-33с на 17/20 тиков), это первое
реальное измерение выигрыша M4; если снова 0/N — искать следующий блокер тем
же методом, а не повторять S12 вслепую.

## S14 (P3, 2026-09-20) — смена порядка веток повторена под S13-фиксом: `restyle=1` наконец достигается, но census снова не дошёл до конца — найден новый кандидат-блокер (contention на `document.lock()` с движковым потоком)

Продолжение с того места, где остановился S13 («следующая сессия должна
повторить S11/S12's эксперимент на этом фиксе»). Сначала расширен
`scripts/bug935_raf_relayout_census.py`: `ANY_RELAYOUT_RE` теперь опционально
разбирает поле `restyle=` (S12/S13 добавили его в лог, но census его не читал),
разбивка по `incremental, on-thread` печатает долю `restyle=1`.

Затем внесена сама смена `||`-порядка (`try_relayout_raf_incremental` первым в
обеих функциях, `relayout_raf_dirty`/`relayout_raf_dirty_readback`). Прогнан
census (`lenta.ru`, `--settle-s 20 --ticks 20`) на собранном `dev-release`
этой ветки.

**Хорошая новость — S13-фикс работает:** первый тик пошёл по дорогой
non-restyle ветке (`restyle=0`, 251.92мс — сеет кэш), все следующие пять тиков
подряд — `restyle=1` (121–173мс каждый), т.е. cascade-skip путь теперь
реально достижим на живом rAF+DOM-цикле, чего не было ни разу за S12 (0/8).

**Но census снова не дошёл до конца — тот же класс отказа, что S12:** после
шести дешёвых тиков подряд — два `[engine] relayout` по **7047.49мс** и
**6752.74мс**, ОБА с `restyle=1`, после чего `automation command timed out`
(`DEFAULT_TIMEOUT=65s` исчерпан кумулятивно за несколько `scroll`-вызовов, тем
же способом, что S12 остановил прогон). Резкая аномалия: `[profile]`-разбивка,
напечатанная непосредственно перед строкой `relayout`, показывает, что все
внутренние стадии cascade-skip ветки (`layout_mutation_incremental_restyle` +
`build_flat_tree`/`build_shadow_sheets`/`precompute_counters`/`build_box`/
`post_build_tree_walks`/`graft_geometry`/`lay_out`/`post_layout_passes`) в
сумме дают **<1мс** — то есть измеренные 7047/6752мс тратятся НЕ на сам layout
(та часть функции, что профилируется), а на что-то ДО начала профилируемых
стадий внутри `try_relayout_raf_incremental` (после `incr_t0`, до
`layout_mutation_incremental_restyle`): кандидаты — `refresh_dynamic_css()`,
`src.document.lock().unwrap()` (`relayout.rs:333`), или сами вызовы
`restyle_state_index`/`restyle_root_set_for_state_change`.

Совпадение по времени показательно: та же `[frame]`-строка (тот самый
`scroll`, что подвис) отчиталась `total 13372.82ms` с `js 12059.20` —
двенадцать секунд внутри этого кадра ушло на JS. Под дефолтной сборкой
(движковый поток, ADR-023) JS исполняется НЕ на UI-потоке (`fire_raf_turn_async`
шлёт `run_animation_frame` в `EngineThread` асинхронной задачей), а
`try_relayout_raf_incremental` теперь (после смены порядка) исполняется НА
UI-потоке и берёт `src.document.lock()` для чтения дерева перед восстроением
root-set. Правдоподобная гипотеза (не подтверждена инструментально в этом
срезе — не измерялось время до/после `lock()` отдельно): пока движковый поток
удерживает `Document`-мьютекс во время долгого (12с — вероятно, тяжёлый
рекламный/аналитический скрипт, судя по `easylist`-блокировкам в логе вокруг
этого места) JS-прохода, UI-поточный `try_relayout_raf_incremental` блокируется
на этом же мьютексе на весь оставшийся срок хода — ровно то время, что и
наблюдаемые 7047/6752мс. Если верно, это плата, которую off-thread
`submit_relayout_job` НИКОГДА не перекладывает на UI-поток напрямую (он тоже
конкурирует за мьютекс, но делает это на СВОЁМ, не на UI-потоке, поэтому
automation-канал не блокируется тем же способом).

**Действие:** правка (смена `||`-порядка) отменена (обе функции вернули
исходный порядок), доккомментарии дополнены итогом этого среза. Расширение
census-скрипта (`restyle=` разбор) **оставлено** — безвредно и уже показало
свою ценность (без него S13-фикс остался бы неизмеренным числом). `cargo
clippy -p lumen-shell --all-targets --features v8 -- -D warnings` чист,
`cargo test -p lumen-shell --bins --features v8 -- relayout` — 10/10 зелёных
на откаченном коде.

**Не сделано / следующий срез:** гипотеза «UI-поточный `try_relayout_raf_incremental`
блокируется на `document.lock()` контенцией с движковым JS-потоком» не
подтверждена инструментально — нужен отдельный таймер ВНУТРИ
`try_relayout_raf_incremental` (до и после `src.document.lock()`, до и после
`refresh_dynamic_css()`), чтобы локализовать, какая именно операция съедает
7с при <1мс профилируемого layout. Если гипотеза подтвердится, смена
`||`-порядка структурно небезопасна без дополнительной защиты (например,
`try_lock()` с быстрым откатом на `submit_relayout_job`, если мьютекс занят) —
это не однострочная правка, а отдельная архитектурная развилка. Основной
симптом бага (M4-incremental routing не работает под дефолтной сборкой)
по-прежнему открыт.

## S15 (P3, 2026-09-20) — S14's `document.lock()` hypothesis instrumented and REFUTED; the real cost is a synchronous engine-thread round-trip in `apply_relayout_result` that S14's swap experiment exposed on the UI thread

Продолжение с того места, где остановился S14 («гипотеза не подтверждена
инструментально — нужен отдельный таймер ВНУТРИ `try_relayout_raf_incremental`,
до и после `src.document.lock()`, до и после `refresh_dynamic_css()`»).

**Инструментирование (оставлено под `LUMEN_FRAME_LOG=1`, безвредно):**
таймер вокруг `src.document.lock()` в restyle-ветке `try_relayout_raf_incremental`
(`lock_wait_ms`) и вокруг построения `dirty_roots`/индексов (`dirty_roots_ms`),
добавлены в итоговую строку `[engine] relayout … (incremental, on-thread)`.
Затем повторён S14's эксперимент (`||`-порядок временно свопнут, сборка
`dev-release`, census на `lenta.ru`).

**S14's гипотеза опровергнута числами:** `lock_wait_ms=0.00` на **всех**
измеренных тиках этой сессии, включая outlier в 5880.54мс общего `incr_ms` —
ожидание на `document.lock()` в этой конкретной точке не является причиной
задержки. S14 предположил контенцию по мьютексу, не измерив её напрямую;
измерение показывает, что мьютекс здесь не виноват.

**Найден второй `document.lock()`, отдельный от первого:** `compute_layout_incremental_restyle`
(`relayout.rs:1414`, вызывается ИЗ `relayout_page_incremental_restyle` уже
ПОСЛЕ того, как вызывающий снял свой лок на строке 365) берёт **свой
собственный** лок на тот же `Mutex<Document>`. Добавлен таймер
(`[engine] restyle-wrapper …ms total: font_parse=…ms lock2_wait=…ms
paint_ordered=…ms`) — в одном прогоне `lock2_wait` доходил до 857.03мс, что
показывает реальную, но вторичную контенцию (не главный источник — см. ниже).

**Настоящий доминирующий источник — `apply_relayout_result`, не сам layout:**
таймер вокруг всего вызова `self.apply_relayout_result(...)` в
`try_relayout_raf_incremental` (`apply_ms=`) показал, что эта функция съедает
**почти весь** `incr_ms` на КАЖДОМ тике, не только на outlier'ах:
нормальные тики — `apply_ms` 300-450мс при `incr_ms` 320-460мс (restyle-wrapper
сам — 10-12мс); outlier — `apply_ms=6766.39мс` при `incr_ms=7635.48мс`.
Чтение `apply_relayout_result` (`relayout.rs:889-936`) нашло механизм:
секция JS-observer push (`self.js_present` gate) собирает rects/client
rects/hit-test-tree/computed styles/pseudo styles/custom properties/
stylesheet/viewport/scroll-states и одним пакетом зовёт
`route_query_js(self.engine_thread.as_ref(), self.js_ctx.as_ref(), move |js| {…})` —
**синхронный ordered round-trip на движковый поток** (тот же механизм,
`EngineThread::query()`, что S6 ограничил `QUERY_TIMEOUT=5s`), исполняющий
там `deliver_layout_observers`/`deliver_media_query_changes`/
`deliver_lazy_images` и прочий JS-пуш.

**Почему это объясняет и S12, и S14 разом:** под исходным (не свопнутым)
`||`-порядком `apply_relayout_result` тоже вызывается — из
`submit_relayout_job`'s асинхронной engine-thread задачи — но там она уже
исполняется НА движковом потоке (сам себе round-trip не нужен, или он
локальный) и не блокирует UI-поток. Смена `||`-порядка (S12, повторно S14)
переносит `try_relayout_raf_incremental` целиком на UI-поток, включая эту
секцию — и теперь UI-поток синхронно ждёт `route_query_js`'а ответа от ТОГО ЖЕ
движкового потока, чья ordered FIFO-очередь может быть занята долгим
синхронным `fetch`/сетевым вызовом (тот же класс, что S4-S10 чинили с
таймаутами) — вплоть до `QUERY_TIMEOUT=5s` на один запрос, что и даёт
наблюдаемые 5.9-7.6с. Это не контенция на мьютексе (S14's гипотеза) и не
дороговизна самого layout'а (S12/S13 уже показали <1мс на профилируемые
стадии) — это структурная разница между «async-safe off-thread» и
«on-thread» путём, которую «Предполагаемый фикс» в начале файла предсказывал
абстрактно («переключение сделает rAF-DOM-мутации ЧАСТИЧНО UI-блокирующими»),
теперь локализована до конкретного вызова с конкретным механизмом.

**Действие:** `||`-порядок снова откачен (обе функции вернули исходный
порядок). Все три новых таймера (`lock_wait_ms`/`dirty_roots_ms` в
`try_relayout_raf_incremental`, `restyle-wrapper` в
`compute_layout_incremental_restyle`, `apply_ms` вокруг
`apply_relayout_result`) оставлены под `LUMEN_FRAME_LOG=1` — без них это
открытие осталось бы недоступным следующему срезу. `cargo clippy -p
lumen-shell --all-targets --features v8 -- -D warnings` чист, `cargo test -p
lumen-shell --bins --features v8 -- relayout` — 10/10 зелёных на откаченном
коде.

**Не сделано / следующий срез:** основной симптом бага (M4-incremental
routing не работает под дефолтной сборкой) по-прежнему открыт — но теперь
понятно, ПОЧЕМУ прямая смена `||`-порядка не годится: `apply_relayout_result`
должна либо (а) остаться асинхронной даже когда сам layout выполнен на
UI-потоке (разделить «синхронный layout» и «асинхронный JS-push» вместо
текущего одного вызова, вынести `route_query_js`-секцию в отдельную
engine-thread задачу, не дожидаясь её на UI-потоке), либо (б) для этого
конкретного JS-push использовать неблокирующий/latest-wins механизм вместо
ordered `query()`, раз результат (`lazy_reqs`) уже допускает `unwrap_or_default()`
при таймауте. Оба варианта — архитектурная правка, не однострочная. Вторичная
находка (второй `document.lock()` в `compute_layout_incremental_restyle`,
857мс в одном прогоне) тоже не устранена — отдельный, менее приоритетный
источник задержки на том же пути.

## S16 (P3, 2026-09-20) — doc-comment drift fixed: `relayout_raf_dirty`'s warning still named S14's refuted lock-contention guess, not S15's confirmed root cause

## S17 (P3, 2026-09-20) — S15's option (б) implemented: the JS-observer push in `apply_relayout_result` is now decoupled from the synchronous on-thread incremental path

Продолжение с того места, где остановился S16 («следующая сессия должна взять
один из двух вариантов S15 и провести измерение по протоколу»). Взято S15's
вариант (б) — не переписывать сам `route_query_js`-механизм для всех
вызывающих, а дать конкретному проблемному call site (`try_relayout_raf_incremental`)
неблокирующий путь, раз его результат (`lazy_reqs`) и так уже трактуется как
опциональный (`unwrap_or_default()`).

**Фикс** (`crates/shell/src/relayout.rs`, `crates/shell/src/lumen/state.rs`,
`crates/shell/src/window_mode.rs`):

1. `apply_relayout_result` получил новый параметр `defer_js_push: bool`. Три
   существующих вызывающих (`relayout()`, `readback_relayout_job`,
   `poll_engine_commit`) передают `false` — байт-идентичное поведение, тот же
   блокирующий `route_query_js`, что и раньше. Четвёртый — `try_relayout_raf_incremental` —
   теперь передаёт `true`.
2. Под `defer_js_push == true` JS-observer push (rects/styles/`deliver_layout_observers`/
   `deliver_media_query_changes`/`deliver_lazy_images`/scroll-states — тот же
   набор вызовов, что и раньше) уходит через уже существующий fire-and-forget
   роутер [`route_task_js`] (`engine_bridge.rs`, использовался раньше только
   для `eval_js`/`tick_timers` и подобных void-действий) вместо блокирующего
   `route_query_js`. Вызывающий (`try_relayout_raf_incremental`, на UI-потоке)
   больше не ждёт ответа от движкового потока в этой точке — снимается ровно
   тот блокирующий раунд-трип, который S15 нашёл источником 5.9-7.6с
   зависаний при свопнутом `||`-порядке.
3. `take_lazy_image_requests()`'s результат недоступен вызывающему синхронно
   в этой ветке — добавлено новое поле `Lumen::pending_lazy_image_reqs`

   `dom_dirty_flag`/`raf_pending_flag`, только очередь, а не булев флаг):
   fire-and-forget задача складывает в него найденные lazy-image-запросы,
   а `apply_relayout_result` **безусловно** (для всех четырёх производителей,
   не только для деferred-ветки) дренирует эту очередь перед вызовом

   тиком, подхватывается следующим relayout'ом любого рода, максимум с
   задержкой в один цикл.

**Эффект под дефолтной сборкой: нулевой сам по себе, как и S13.**
`try_relayout_raf_incremental` по-прежнему не вызывается под

недостижим; ценность этого среза — снять блокер, найденный S15, ПЕРЕД

(`relayout_raf_dirty`, снаружи вызова) и `incr_ms` (`[engine] relayout …

впритык — включая выбросы: `outer_ms=1285.79` / `incr_ms=1285.43`,
`outer_ms=2281.55` / `incr_ms=2281.24`. S18's ~7x/~12x разрыв (`outer`-подобный
`js`-шаг ~7.0с против `incr_ms`~1.07с) **не воспроизвёлся** в этом прогоне —
похоже, S18 действительно сопоставил две строки от разных тиков, как сам и
подозревал; на этом стенде и в этом прогоне разрыва между таймером снаружи
и таймером внутри функции нет.

**Что реально доминирует в выбросах:** `restyle-wrapper` (`relayout.rs:1536`,
`compute_layout_incremental_restyle`) логирует `lock2_wait_ms` — время
`document.lock()` (`relayout.rs:1563`), ВТОРОГО, независимого захвата того
же `Mutex<Document>`, который вызывающий (`try_relayout_raf_incremental`)
уже отпустил перед вызовом этой функции (S15's находка, ещё не устранённая).
На спокойных тиках `lock2_wait_ms=0.00`; на выбросах —
`lock2_wait_ms=531.07/394.22/512.83/586.99/293.76`мс, что почти один в один
объясняет соответствующий рост `apply_ms` (315→744→1252→1759→…мс) и, через
него, `incr_ms`/`outer_ms` (328→1286→1656→2282→2420→1321мс). Ряд не
монотонный — `lock2_wait`/`apply_ms`/`outer_ms` растут и падают вместе
(последний замер в серии: `lock_wait_ms=258.85` — другой, первый лок,
впервые за прогон не ноль, `apply_ms=757.58` упал обратно), то есть это не
утечка/накопление, а контеншн: что-то на движковом потоке периодически
держит `Mutex<Document>` по 0.3-0.6с одновременно с тем, как UI-поток здесь
пытается взять его повторно.

**Не установлено в этом срезе:** ЧТО именно на движковом потоке держит лок
в эти окна (рекламный трафик — `kraken.rambler.ru`/`cnt.rambler.ru`/
`top100.ru` — идёт непрерывно все эти тики, но прямой причинности с
конкретным held-lock интервалом не показано; кандидат — синхронный
`_lumen_fetch_sync`/JS rAF turn на движковом потоке, тот же класс, что S4/S5
нашли для `EngineThread::query()` FIFO, но здесь захват `Document`, не
`reply_rx.recv()`). Один `[frame] total 7272.56ms` с `js=6895.39ms` замечен
в этой же серии — на порядок больше, чем сам `incr_ms` этого тика
(1655.79мс) — подтверждает, что параллельно с M4-путём на странице
продолжает происходить отдельный, гораздо более крупный синхронный JS-стопор
(тот же механизм, что S3-S5 уже документировали для рекламных
fetch/FIFO-цепочки), который census этого бага не должен путать с
собственно M4-инкрементальным путём — они складываются, но это два разных
источника задержки.

Своп кода **отменён** после снятия замера (`git checkout -- relayout.rs`) —
как и в S12/S14/S18, это не финальный фикс: код вернулся к S19-состоянию
(короткое замыкание `submit_relayout_job`/`readback_relayout_job` первым,
`try_relayout_raf_incremental` недостижим на дефолтной сборке). Правок,
которые остаются в этом срезе, нет — только раздел документа.

**Следующий срез должен:** инструментировать вызывающую сторону
`compute_layout_incremental_restyle`'s `document.lock()` (`relayout.rs:1563`)
— найти, какой именно код на движковом потоке удерживает `Mutex<Document>`
в 0.3-0.6с окнах, коррелирующих с рекламным трафиком (добавить лог с
таймстампом захвата/отпускания на стороне движкового потока, не только
времени ожидания на UI-стороне) — прежде чем снова трогать `||`-порядок.
Если этот лок и есть последний блокер для завершения census'а, устранение
его (или хотя бы понимание его природы) — предпосылка того, ради чего весь
трек затевался: сравнить частоту/стоимость M4-инкрементального пути против
полного `submit_relayout_job` на устойчивом, а не постоянно
переоткрываемом стенде.

## S21 (P3, 2026-09-20) — engine-thread `Task`-таймер снаружи (S20's предпосылка) нашёл не lock-contention, а сами `Task`-замыкания, блокирующие движковый поток на секунды-минуты — вероятная настоящая доминанта симптома, отдельная от M4-incremental-пути

Продолжение с того места, где остановился S20 («инструментировать вызывающую
сторону `compute_layout_incremental_restyle`'s `document.lock()` — найти,
какой именно код на движковом потоке удерживает `Mutex<Document>` в 0.3-0.6с
окнах»).

**Правка** (`crates/shell/src/engine_thread.rs`, `run_batch`): внешний таймер
вокруг **каждого** `EngineMsg::Task`-замыкания (generic-обёртка — модуль
намеренно не знает, что внутри: JS-тик, DOM-мутация, `document.lock()` и
т.п., см. заголовок файла). Под `LUMEN_FRAME_LOG=1` печатает `[engine] task
{ms}ms (engine-thread Task, generic wrapper)` для абсолютно любого `Task`,
независимо от того, какой вызывающий (`tick_timers`/`run_animation_frame`/
`eval_js`/`set_js_ctx`/…) его поставил — единая точка, через которую проходят
все они (`engine_thread.rs::run_batch`).

**Живой замер** (`lenta.ru`, `--maximized`, ~4 минуты стенда S3/S5/S18-S20,
дефолтная сборка — `||`-порядок НЕ менялся, M4-incremental-путь в этом срезе
недостижим как обычно): из 200+ `Task`-строк подавляющее большинство — доли
мс (JS-пуш observer'ов и т.п., ожидаемо дёшево), но **10 записей превысили
1000мс**, включая:

```
3307.92, 3613.26, 3797.86, 5212.50, 20882.73, 23428.71, 23888.07, 233934.20
```

Последнее число — **233.9 секунды** на ОДНОМ `Task`-замыкании. Процесс не
падает и не виснет насовсем — после каждой такой строки лог продолжается
штатно (новые `[frame]`/сетевые записи идут дальше), то есть это не deadlock
(S3/S4's находка), а очень долгая, но конечная синхронная работа,
выполняемая **на движковом потоке внутри одного `Task`**, которая блокирует
абсолютно всё остальное, что стоит в FIFO-очереди позади неё — relayout
`Run`-задания (S20's «Corень» напрямую от этого страдает: `submit_relayout_job`
коалесцируется, но должен ДОЖДАТЬСЯ своей очереди после текущего `Task`),
`query()`-чтения (уже ограничены `QUERY_TIMEOUT=5s` с S6, но само задание
внутри очереди никуда не девается, просто отвечает `None` раньше срока —
S6's doc-комментарий), automation-канал.

**Правдоподобный механизм (не подтверждён инструментально до конца этого
среза, но согласуется по порядку величины):** S4-S10 добавили таймаут на
КАЖДЫЙ отдельный синхронный сетевой примитив (TCP-connect, WS/SSE/TLS/SOCKS5-
хендшейк, `EngineThread::query()`) — но ни один из них не ограничивает
суммарное время ОДНОГО JS-тика/`Task`, который может внутри себя вызвать НЕСКОЛЬКО
таких примитивов подряд. Конкретный, уже найденный чтением кода пример —
`DohResolver::resolve()` (`crates/network/src/doh.rs::resolve`, RFC 8484): на
каждое разрешение НОВОГО хоста уходит **два последовательных** HTTP GET-запроса
к DoH-эндпоинту (AAAA, потом A, `fn query`, `:316`) — каждый идёт через тот же
`connect_inner`, что и обычный `fetch` (то же самое `CONNECT_TIMEOUT=10s`/
`FETCH_READ_TIMEOUT=60s` из S4/S9), но НИЧЕГО не ограничивает их СУММУ. Два
подряд ~10-12с исхода дают наблюдаемые 20.9/23.4/23.9с почти точь-в-точь;
234с ближе к 3-4 последовательным `FETCH_READ_TIMEOUT=60s`-исходам подряд —
согласуется с гипотезой «страница выполняет НЕСКОЛЬКО последовательных
синхронных сетевых вызовов (рекламные/аналитические `fetch`/резолвы к разным
хостам — лог вокруг всех крупных `Task` полон `kraken.rambler.ru`/
`cnt.rambler.ru`/TLS `UnknownIssuer`-ошибок к `kraken-mdt.rambler.ru`,
`✗ … (easylist)`) в ОДНОМ JS-тике, и каждый шаг платит свой уже
ограниченный, но НЕ агрегированный таймаут».

**Значение для остального бага:** это, вероятно, **более крупный источник**
наблюдаемых зависаний, чем сам M4-incremental-роутинг (S1-S20's фокус) —
относительно скромные «3 полных relayout'а по 419-1812мс» из S11 меркнут
перед engine-thread `Task`, блокирующим весь поток на десятки-сотни секунд.
Не отменяет находку S1-S20 (M4-путь всё ещё мёртв под движковым потоком,
отдельная, независимо верная проблема), но объясняет, ПОЧЕМУ census на
рекламно-тяжёлых сайтах (`ria.ru`, `lenta.ru`) так труден для чистого
измерения на протяжении всего трека S1-S20 — стенд сам периодически
проваливается в многосекундные-многоминутные паузы по независимой от
relayout причине.

**Не сделано / не подтверждено в этом срезе:**
- Гипотеза про `DohResolver`/цепочку последовательных сетевых вызовов внутри
  одного JS-тика — правдоподобна по порядку величины, но НЕ подтверждена
  прямым логом (какой именно вызов исполнялся во время каждого конкретного
  долгого `Task`, инструментация этого среза этого не различает — `run_batch`
  не знает, что внутри замыкания). Следующий срез должен либо (а) добавить
  метку вызывающего в сам `Task`-message (например, `&'static str` label на
  `EngineMsg::Task`, проброшенный через `route_task_js`/`route_eval_js`/
  `route_query_js` на все call-site'ы) — самый прямой путь, либо (б)
  временно залогировать вход/выход из `DohResolver::query`/`resolve` под тем
  же `LUMEN_FRAME_LOG`, чтобы увидеть, действительно ли долгие `Task`
  совпадают по длительности с DNS-резолвом, а не с чем-то ещё.
- Никакой фикс не внесён — это диагностическая находка, не точечная правка:
  если гипотеза подтвердится, вероятные направления — распараллелить
  AAAA/A-запросы `DohResolver::resolve()` (сейчас строго последовательны),
  и/или завести общий бюджет на суммарное время синхронных сетевых вызовов
  ОДНОГО JS-тика (архитектурное решение, требует протокола
  `docs/perf-method.md`, не входит в этот срез).
- Сам `||`-порядок `relayout_raf_dirty`/`_readback` не трогался — это
  предпосылка S18/S19/S20's плана («сравнить `outer_ms`/`incr_ms`, повторить
  своп»), которая теперь встаёт в очередь ПОСЛЕ этой более крупной находки:
  бессмысленно измерять эффект M4-fast-path на стенде, где сам движковый
  поток непредсказуемо замирает на десятки-сотни секунд по независимой
  причине — сначала нужно понять/ограничить это, иначе любой census
  интерливед A/B (S11-S20) продолжит давать шумные, невоспроизводимые числа
  ровно как в S1-S20.

**Тесты:** `cargo clippy -p lumen-shell --all-targets --features v8 -- -D
warnings` чист, `cargo test -p lumen-shell --bins --features v8 -- relayout
engine_thread` — 45/45 зелёных (тот же набор, без регрессий). Инструментация
gated `LUMEN_FRAME_LOG` — под дефолтной сборкой (флаг выключен) поведение
байт-идентично, добавлен только `Instant::now()`+условный `eprintln!` внутри
уже существующей точки диспетчеризации `Task`.

## Воспроизведение

```
LUMEN_PROFILE_TREE=1 LUMEN_FRAME_LOG=1 cargo run --profile dev-release -p lumen-shell -- --mcp-live-port 18790 https://ria.ru
```

Подключиться MCP-клиентом (токен в stderr `[mcp] token: ...`), `wait
document_ready`, подождать ~2с, наблюдать `[engine] relayout Nms
(off-thread) dl=... styled=...` в логе даже без единого `scroll`-вызова —
уже на этапе settle. Любая реальная страница с активным
rAF+DOM-мутацией (видео-плеер, карусель, «живая лента») воспроизводит то же.
