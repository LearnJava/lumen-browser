# BUG-1367 — Строка в `content` не разбирается по CSS-экранированию: `\"`, `\A`, `\41` не декодируются, экранированная кавычка обрывает значение

**Статус:** OPEN
**Заведён:** 2026-10-07 (P2, WPT-RUN-14 срез 14, `css/CSS2` (text, linebox, fonts, generated-content, lists, bidi-text))
**Область:** layout (`crates/engine/layout/src/style/parse/content.rs::parse_content_items` — литерал ищется до первой кавычки, без обработки `\`)

## Симптом

`parse_content_items` (`content.rs:25`) читает литерал до следующей кавычки того же вида и кладёт его в `ContentItem::String` как есть. `--dump-display-list`, `::before { content: … }`:

| значение | нарисовано | ожидается |
|---|---|---|
| `"x\41 y"` | `x\41 y` | `xAy` |
| `"x\0041y"` | `x\0041y` | `xAy` |
| `"x\f101y"` | `x\f101y` | `x` + U+F101 + `y` |
| `"L1\A L2"` (`white-space: pre`) | `L1\A L2` одной строкой | два абзаца `L1` / `L2` |
| `"x\"y"` | `x\` — а текст следующего правила (`} #f::before{content:}`) попадает в значение | `x"y` |

Последнее хуже остальных: экранированная кавычка обрывает литерал, и остаток объявления/правила вываливается на страницу как текст. На реальных страницах `content: "\201C"` / `"\2014"` / `"\""` — обычный приём для кавычек и разделителей.

## Как найдено

WPT-RUN-14 срез 14: после правки однодвоеточных селекторов (BUG-1366) 15 `thick` в `generated-content/{after,before}-content-display-*`, `content-171…177`, `content-white-space-*` содержат `\A` / `\201C` в `content`. Проба на отдельных страницах — таблица выше.

## Что делать

Читать литерал по CSS Syntax L3 §4.3.5 («consume a string token»): `\` + `\n` — склейка строк, `\` + 1–6 hex-цифр (+ один пробел) — кодпоинт, `\` + любой другой символ — он сам; незакрытая строка — bad-string. Тот же разбор нужен остальным строковым значениям (`font-family: "a\"b"`, `quotes`, `attr()` имя) — проверить, нет ли общей функции в `css-parser`.

## Как проверить

`css/CSS2/generated-content/content-171.xht`, `content-white-space-001.xht`, `after-content-display-015.xht`.
