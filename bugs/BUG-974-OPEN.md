# BUG-974: процентные padding/margin строчного flex-элемента резолвятся против его собственного главного размера, а не против ширины контейнера

**Статус:** OPEN
**Компонент:** layout (`crates/engine/layout/src/box_tree/flex.rs::lay_out_flex`, строчная ветка финального прохода)
**Найден:** P3, 2026-09-03, побочной пробой при BUG-341 S41 (сосед по коду того дефекта, который S41 исправил в колоночной ветке).

## Симптом

Процентный `padding`/`margin` flex-элемента в строчном (`flex-direction: row`)
контейнере считается от неправильной базы. Тот же элемент, положенный обычным
блоком в контейнер той же ширины, получает правильный размер.

Проба (`crates/engine/layout/src/box_tree/tests/flex_align_content.rs`, обе
половины в одном документе, чтобы исключить различие в контейнере):

```rust
let html = r#"<div id="flex"><div id="a"></div></div><div id="blk"><div id="c"></div></div>"#;
let css = "body{margin:0} #flex{display:flex;width:400px;height:100px} #blk{width:400px}\
           #a,#c{width:100px;height:20px;padding-left:10%}";
// PROBE flex-item.width=114  block.width=140
```

Ожидается 140 у обоих: `width: 100px` (content-box) + `padding-left` = 10 % от
ширины содержащего блока (400) = 40. Блок так и делает. Flex-элемент даёт 114,
то есть 10 % посчитаны от ~140 — от его собственного разрешённого главного
размера, а не от контейнера.

Спека однозначна: процент в `padding`/`margin` резолвится против **inline-размера
содержащего блока** (CSS 2.1 §8.1/§8.4), а для flex-элемента содержащий блок —
контентная область flex-контейнера (CSS Flexbox L1 §4). Собственный размер
элемента базой быть не может ни в одном случае.

## Причина

`lay_out_flex`'s строчная ветка передаёт в `lay_out_with_used_size` в качестве
`available_width` **разрешённый главный размер элемента** (`inner_main`):

```rust
lay_out_with_used_size(
    &mut children[i],
    content_x + main_cursor,
    content_y + cross_cursor,
    inner_main,                      // <- сюда должна идти база процентов
    explicit_cross,
    ...
    UsedSizeOverride { width: Some(used_main), ..Default::default() },
);
```

Внутри `lay_out_inner` этот аргумент играет две роли сразу: «сколько места
досталось моему margin-box'у» (для auto-ширины) и «база для резолва моих
процентов» (`let cb = available_width;`). Строчной ветке нужна была только
первая роль — ширину элемента она и так задаёт явно через `UsedSizeOverride`,
— но вместе с ней она молча переопределила и вторую.

Это тот же класс, что BUG-341 S41 и BUG-294: **аргумент `available_width`
перегружен**, и каждый вызывающий, который подставляет туда «свой» размер,
ломает одно из двух его значений. S41 починил колоночную ветку (там страдала
ширина: горизонтальные поля списывались дважды), эта ветка страдает базой
процентов.

## Предлагаемая правка

Передавать в `available_width` контентную ширину контейнера (`content_width`) —
она и есть содержащий блок элемента. Ширину элемента строчная ветка задаёт
`UsedSizeOverride { width: Some(used_main) }`, поэтому auto-ширина оттуда не
берётся и подмена базы ничего больше не заденет. Требуется проверить, что
`avail_bb` (ветка резолва явной ширины в `lay_out_inner`) не начнёт считать
иначе для элементов с `box-sizing: border-box` и процентной шириной.

## Цена

Правка двигает пиксели на любой странице с процентными `padding`/`margin`
у элементов строчного flex-контейнера — это частая разметка, — поэтому нужен
полный `python graphic_tests/run.py --continue-on-fail`, а не только
`dump_golden.py`.
