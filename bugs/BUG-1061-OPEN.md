# BUG-1061 — зависший вызов `ffmpeg` роняет весь графический прогон, несмотря на `--continue-on-fail`

**Статус:** OPEN
**Тип:** дефект реализованного кода — `ffmpeg_diff`/`ffmpeg_crop` в `graphic_tests/run.py` не перехватывают `subprocess.TimeoutExpired`, поэтому исключение всплывает из `run_one` в `main` и завершает процесс.
**Заведён:** 2026-09-19 (замер «можно ли заменить ffmpeg-захват снимками Lumen», два оборвавшихся прогона `--ipc`)
**Область:** тулинг графических тестов (`graphic_tests/run.py:1317-1323`, единственный вызов — `:1633`)
**Владелец:** P2.

## Симптом

Прогон `python graphic_tests/run.py --ipc --continue-on-fail` завершается
трейсбеком на произвольном тесте, не доходя до конца набора:

```
subprocess.TimeoutExpired: Command '[... ffmpeg.exe -i 01-sanity-edge.png
 -i 01-sanity-lumen-cropped.png -filter_complex blend=all_mode=difference
 01-sanity-diff.png -y]' timed out after 15 seconds
```

Наблюдено дважды подряд на одном бинарнике: первый запуск оборвался на
TEST-01, второй — на TEST-21 (успев пройти 20 тестов). Флаг
`--continue-on-fail` не помогает: он обрабатывает *провал теста*, а не
исключение из вспомогательной функции.

Цена отказа непропорциональна: один медленный вызов `ffmpeg` стоит всего
прогона (~20 мин в gdigrab-режиме), и чем больше набор, тем меньше шансов
дойти до конца — при частоте «примерно раз на два десятка вызовов» и двух
вызовах на тест полный набор из 156 тестов почти гарантированно не
завершается.

## Причина

Обе обёртки зовут `subprocess.run(..., timeout=15)` без `try`:

```python
def ffmpeg_diff(edge_png: str, lumen_png: str, out_png: str) -> None:
    subprocess.run(
        [FFMPEG, '-i', edge_png, '-i', lumen_png,
         '-filter_complex', 'blend=all_mode=difference',
         out_png, '-y'],
        capture_output=True, timeout=15,
    )
```

Само зависание изолированно **не воспроизводится**: та же команда на тех же
файлах проходит 6/6 подряд. Наиболее вероятный механизм — `stdin`: `ffmpeg`
читает стандартный ввод для интерактивных команд (в его собственном выводе
есть `Press [q] to stop, [?] for help`), а `subprocess.run` без явного
`stdin` наследует его от родителя. На пайпе, который никогда не закрывается
и никогда не отдаёт данных, чтение блокируется.

Косвенное подтверждение: с `stdin=subprocess.DEVNULL` за ~300 вызовов
(полный прогон 156 тестов, по два вызова `ffmpeg` на тест) не случилось ни
одного зависания, тогда как без него оборвались оба предыдущих прогона.
Это наблюдение, а не доказанный корень — проверка гипотезы входит в объём
починки.

## Ожидание

Отказ одного вызова `ffmpeg` деградирует **один** тест (ERROR с внятной
причиной), а не прогон целиком.

## Побочный риск, который нельзя потерять при починке

Простой `try/except` вокруг вызова недостаточен: `run_one` дальше проверяет
`os.path.exists(diff_png)` и читает файл через `diff_stats`. Diff-PNG от
**предыдущего** прогона лежит на том же пути (имена детерминированы по
`stem`), поэтому проглоченный отказ `ffmpeg` заставит метрику посчитать
устаревшую картинку как свежий результат — молча и правдоподобно. Выходной
файл нужно удалять до вызова и проверять его появление после.

## Как чинить

1. Явный `stdin=subprocess.DEVNULL` в обеих обёртках — проверить, снимает ли
   это зависания само по себе (тогда ретрай не нужен).
2. Удаление выходного файла до вызова + проверка появления после (см. выше).
3. Отказ после всех попыток — ERROR одного теста с причиной в отчёте, без
   прерывания прогона.

раннер тоже рапортует как «тесты провалились»); задача TEST-9 (гибридный
захват) снимает большую часть вызовов `ffmpeg`, но не все — кроп
Edge-эталона остаётся.
