# BUG-802 — layout вложенных `flex-direction: column` стоит O(2^глубины): 22 уровня вешают браузер насмерть

**Статус:** OPEN
**Заведён:** 2026-08-21 (WPT-RUN-6, срез 11 — разбор коллатерального `no-output`)
**Область:** `crates/engine/layout/src/box_tree.rs:10805-10824` (`needs_prelayout` в `layout_flex_container`) + финальный проход `lay_out_with_used_size` (`:11204`, `:11281`)
**Владелец:** P1/P3 (движок). Заведён P2 в ходе WPT-задачи, здесь не чинится.

## Симптом

Цепочка вложенных `display: flex; flex-direction: column` раскладывается за
время, удваивающееся с каждым уровнем вложенности. Это не зависание с
бесконечным циклом (в отличие от [BUG-801](BUG-801-OPEN.md)) — процесс
завершается, просто не в этой жизни:

```bash
python3 - <<'PY'
n = 22
css = "<style>div.f{height:200px;display:flex;flex-direction:column;}</style>"
open('/tmp/f.html','w').write('<!DOCTYPE html><html><head>%s</head><body>%s%s</body></html>'
                              % (css, '<div class="f">' * n, '</div>' * n))
PY
time lumen --dump-layout /tmp/f.html    # ~10 c при n=22, ~76 c при n=24
```

Детей у контейнеров нет вообще — достаточно самих вложенных контейнеров.

## Измерения (dev-release, Linux, 2026-08-21)

Одна и та же страница, меняется только `display`/`flex-direction` контейнера.
Базовый оверхед процесса ≈ 85 мс, он и есть «плоская» строка:

| глубина | `flex-direction: column` | `flex-direction: row` | `display: grid` | `display: block` | `inline-block` |
|---|---|---|---|---|---|
| 12 | 100 мс | — | — | — | — |
| 16 | 231 мс | — | — | — | — |
| 18 | 686 мс | 84 мс | 85 мс | 117 мс | 120 мс |
| 20 | 2 453 мс | — | — | — | — |
| 22 | 9 590 мс | 135 мс | 86 мс | 133 мс | 121 мс |
| 24 | 37 304 мс | — | — | — | — |

За вычетом базового оверхеда: 15 → 146 → 2 368 → 37 219 мс на глубинах
12/16/20/24, то есть ×16 на каждые четыре уровня — **ровно ×2 на уровень**.
Взрывается только колоночный flex; строчный flex, grid, block и inline-block
на той же глубине плоские.

## Причина (локализована чтением кода)

`box_tree.rs:10805-10824`, предварительный проход по флекс-элементам:

```rust
let needs_prelayout = {
    let is = &children[i].style;
    if is_column {
        match &is.flex_basis {
            FlexBasis::Auto | FlexBasis::Content => true,          // <-- всегда
            FlexBasis::Length(_) => { is.min_height.is_none() && is.overflow_y == Overflow::Visible }
        }
    } else {
        match &is.flex_basis {
            FlexBasis::Auto | FlexBasis::Content => is.width.is_some(),   // <-- почти всегда false
            FlexBasis::Length(_) => false,
        }
    }
};
if needs_prelayout {
    lay_out(&mut children[i], ...);      // полный рекурсивный layout поддерева
}
```

`flex-basis` по умолчанию `auto`, поэтому в колоночном контейнере
`needs_prelayout` истинно **для каждого элемента всегда**: элемент получает
полный рекурсивный `lay_out` здесь и второй — в основном проходе
(`lay_out_with_used_size`, `:11204`/`:11281`). Два полных прохода на уровень
перемножаются вниз по дереву — это и есть 2^глубины. В строчном направлении
предпроход почти всегда не нужен (`is.width.is_some()`), поэтому строка
плоская.

Комментарий прямо над этим кодом описывает ровно этот класс дефекта как уже
закрытый ([BUG-341](BUG-341-OPEN.md): «every flex item paid for two full
recursive layouts instead of one, compounding multiplicatively with
flex-nesting depth»). Правка BUG-341 сузила предпроход по условию, но для
`is_column` + `flex-basis: auto` условие осталось константой `true`, то есть
для самой частой на практике конфигурации ничего не изменилось.

Что нужно: колоночному контейнеру предпроход нужен ради **высоты контента**
элемента (гипотетический main size), но это intrinsic-измерение, а не полный
layout с расстановкой — либо кэшировать результат предпрохода и не повторять
его в основном (у элемента к тому моменту уже есть `rect.height`), либо
считать высоту тем же способом, каким строчное направление считает ширину
(`flex_auto_base_main_width`).

## Цена (WPT-корпус, снимок 2026-08-20 Linux, 479/479 шардов)

**318 TIMEOUT-вердиктов** от пяти страниц. Пять процессов браузера в шарде
`css__css-flexbox` повисли на файлах
`css/css-flexbox/flexbox-justify-content-vert-00{1a,1b,2,4,5}.xhtml`, и
каждый унёс с собой 62-65 следующих тестов шарда (механизм разделяемого
процесса — тот же, что описан в BUG-801; классификация коллатерали —
`tests/wpt/timeout_audit.py`, механизм `hung-browser`).

Триггер в этих файлах — не глубокая вёрстка, а **самозакрывающиеся теги в
XHTML**: `<div class="a"/>` внутри `<div class="flexbox">`. Своего XML-пути у
движка нет (см. [BUG-786](BUG-786-OPEN.md)), HTML5-токенизатор игнорирует
`/>` у не-void-элемента, поэтому 27 сестринских контейнеров разбираются как
27 **вложенных** — и страница попадает ровно в экспоненту. Проверено: те же
27 контейнеров с корректно закрытыми детьми (`<div class="a"></div>`)
раскладываются за 96 мс, а 27 вложенных — не укладываются и в минуту.

По корпусу самозакрывающиеся не-void теги есть в 447 из 14 004 `.xhtml`/`.xht`
файлов, из них 39 — с 18 и более такими тегами (глубина, на которой
экспонента уже видна).

Для живых сайтов важнее другое: 18-22 уровня вложенного колоночного flex —
обычная величина для современной вёрстки, и её достаточно, чтобы страница
открывалась секунды вместо миллисекунд. Дефект не требует ни битого HTML, ни
WPT.

## Как проверить фикс

```bash
time lumen --dump-layout /tmp/f.html    # n=24 должно быть ~0.1 c, не 76 c
```

плюс исходный файл корпуса:

```bash
timeout 30 lumen --dump-layout tests/wpt/css/css-flexbox/flexbox-justify-content-vert-001a.xhtml
```

Регрессионный тест: замер числа рекурсивных `lay_out` на вложенном колоночном
flex (счётчик, а не настенное время — `docs/perf-method.md`), рядом с
существующими flex-тестами `crates/engine/layout/src/box_tree.rs`
(`flex_column_item_margin_top_applied_once` и соседи).

## Уточнение WPT-RUN-6 срезом 23 (2026-08-22)

(`nested-flex-exponential`, таблица `MEASURED` в
`tests/wpt/verify_layout_hangs.py`), все пять — виновники `hung-browser`,
вместе 318 чужих TIMEOUT-ов.

dev-release, Linux, коммит `3ae02b208`): глубина 8 → 0,01 с, 12 → 0,03 с,
14 → 0,08 с, 16 → 0,27 с, 18 → 1,21 с, 20 → 4,91 с — отношение соседних
уровней ≈ 2,0, то есть степенной рост никуда не делся. Строка
`flex-nesting-20` в `--repros` фиксирует это как ожидание `slow`; после фикса
она должна стать `ok` (порог пробы — 3 с).
