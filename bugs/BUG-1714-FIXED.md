# BUG-1714 — vkvideo.ru: строковый `setTimeout` держит поток движка 2–9 с (в одном прогоне ≥ 98 с), пока JS-чанки страницы грузятся по одному

**Статус:** FIXED 2026-10-26 (P6)
**Заведён:** 2026-10-26 (Chat, живая проверка vkvideo.ru по запросу пользователя)
**Область:** js/shell (причина не локализована; стек — `_lumen_tick_timers` → строковый обработчик таймера `(0, eval)(src)`, `crates/js/src/shim/web_api_shim_mid_b.js:959`; задача движка — per-tick pump-батч `crates/shell/src/app/about_to_wait.rs:290`)

## Симптом

`https://vkvideo.ru/video-213276384_456243633`, `dev-release` от 2026-10-23, `--maximized`, `LUMEN_NO_ADBLOCK=1`, без прокси.

- Прогон с `LUMEN_JS_STALL_SAMPLE_MS=1000`: за 100 с 17 JS-задач дольше 1 с, самые длинные 7.1 / 8.1 / 9.1 с. Почти все с одним и тем же стеком:
  ```
  [js-stall] задача идёт 9122 мс, JS-стек:
  [js-stall]   #0 eval (<no-script>:18705:71)
  [js-stall]   #1 _lumen_tick_timers (<no-script>:20692:27)
  ```
  то есть страница вызвала `setTimeout("<строка кода>")`, и код строки выполняется секундами. Пока задача идёт, в stderr подряд идут `→ GET / ← 200` для `https://st1-24.vkvideo.ru/dist/web/chunks/*.js`, **по одному**: следующий запрос начинается только после ответа на предыдущий. Похоже, вставленные из этого кода `<script src>`-чанки скачиваются и выполняются синхронно на потоке движка, а не асинхронно, как в браузерах.
- Первый прогон (без сэмплера): поток движка занят больше 98 с подряд, MCP `eval` отклоняется с ошибкой `engine thread busy: eval not run within 5.0 s (running task from crates\shell\src\app\about_to_wait.rs:290:13 for 98.2 s)`. Последняя строка stderr — `→ GET …/chunks/b448c5cb.….js` без ответа (из 102 запросов ответ пришёл на 99). Окно в это время не реагирует.

Есть ещё отдельный фатальный дефект страницы — BUG-1713 (`TextDecoder('ascii')`). Если на момент разбора он уже исправлен, SPA пойдёт дальше и картина задач может измениться — перемерить.

## Проба

Скрипт `.tmp/vk_video_probe.py` в основном checkout (в репозиторий не входит) повторяет шаблон `scripts/probe_yt_stall.py`: `lumen --mcp-live-port N --maximized about:blank`, затем `navigate` на URL, `eval` состояния раз в 3 с. Достаточно `scripts/probe_yt_stall.py target/dev-release/lumen.exe 100 https://vkvideo.ru/video-213276384_456243633 vk` (там уже стоит `LUMEN_JS_STALL_SAMPLE_MS=500`) и затем `grep -A4 "задача идёт" .tmp/yt.vk.stderr.log`.

## Что делать

1. Локализовать, что делает строковый обработчик: вывести в `_lumen_timer_string_handler` (`web_api_shim_mid_b.js:942-959`) первые ~200 символов `src`, если выполнение дольше 1 с (временно, под env), и понять, какой вызов внутри идёт синхронно: вставка `<script src>` (dynamic script → обязан быть async, HTML §4.12.1.1 «non-parser-inserted»), синхронный XHR, `document.write` или что-то ещё.
2. Если это синхронная загрузка динамически вставленных скриптов, исправить: загрузка — через сеть без блокировки потока, выполнение — отдельной задачей после прихода ответа, порядок — как в спеке (`async=false` динамические скрипты выполняются по порядку вставки, остальные — по мере готовности).
3. Отдельно выяснить зависание ≥ 98 с из первого прогона: какой из запросов чанков остался без ответа и почему ожидание не ограничено таймаутом. Если это та же синхронная загрузка, она висит на одном запросе.
4. Регресс-тест: страница, которая из строкового `setTimeout` вставляет 3 `<script src>` с медленным сервером (локальная фикстура), — задача таймера завершается быстро, скрипты выполняются позже, `eval` через MCP в это время отвечает.

## Как проверить

Повторить пробу: `[js-stall]` со стеком `_lumen_tick_timers → eval` дольше 1 с нет (или есть и объяснён тяжёлым кодом самой страницы — тогда приложить профиль), MCP `eval` всё время отвечает, запросы чанков идут параллельно.

## Исправление

- Причина не в строковом `setTimeout`: `[js-stall]` называл кадр `eval` потому, что весь шим исполняется как eval-скрипт, а строка 18783 — это колбэк `_lumen_link_hint_fetch` (`web_api_shim_mid.js`). Страница вставляет сотню `<link rel=preload|modulepreload|prefetch href=…/chunks/*.js>`; каждый такой колбэк вызывал синхронный нативный `_lumen_link_prefetch_sync` и держал поток движка на всё скачивание, а колбэки одного тика шли друг за другом — отсюда последовательные `→ GET / ← 200` и задачи 2–9 с (и ≥ 98 с при зависшем запросе).
- `_lumen_fetch_async_start`: третий сегмент `load` — `preload:<nonce>`, destination = `as` подсказки; запрос идёт в рабочем потоке через `fetch_preload_cached` (тот же `PREFETCH_CACHE` и CSP-гейт, что у синхронного натива).
- `_lumen_link_hint_fetch`: запрос ставится в `_lumen_fetch_track`, по готовности `_lumen_link_hint_settle` читает ответ и стреляет `load`/`error`. Без async-моста (нет `_lumen_fetch_async_start`) остаётся прежний синхронный путь.
- Регресс-тест: `preload_links_do_not_block_the_engine_thread` (`v8_webworker.rs`) — три подсказки по 800 мс: задача таймера возвращается < 300 мс, загрузки идут параллельно.
- Остаётся: подсказки не ограничены по числу одновременных потоков; живой прогон vkvideo.ru после фикса — см. отчёт сессии.
