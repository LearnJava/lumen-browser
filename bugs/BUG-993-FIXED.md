# BUG-993 — снимок экрана и признак `broken_render` противоречат друг другу в обе стороны

**Статус:** FIXED (диагностика; исходный вопрос закрыт, обнаруженный дефект вынесен отдельно)
**Заведён:** 2026-09-04 (побайтовая сверка снимков прогона с журналом здоровья)
**Закрыт:** 2026-09-05 (P3)
**Область:** путь снятия снимка (`resource://screenshot` → CPU-растеризатор, `cpu_raster.rs`) против эвристики `broken_render` (`crates/shell/src/health_log.rs`)
**Владелец:** P3

## Симптом

Два независимых признака «страница ничего не нарисовала» расходятся, причём в обе
стороны — значит минимум один из них врёт, и неизвестно который.

## Что говорит измерение

Прогон 100 сайтов 2026-09-04, 88 снимков `.png`:

- **38 из 88 файлов побайтово идентичны** (одна и та же md5, 38 743 байта) — это
  один пустой кадр;
- из них 27 — сайты со статусом `TIMEOUT`/`HUNG`, там пусто и должно быть пусто;
- **11 имеют статус `OK`**: archive, bing, canva, cnbc, duolingo, gemini,
  khanacademy, msft-login, quora, tiktok, weibo;
- из этих 11 движок сам сообщил `broken_render` только про **6**;
- обратный случай: **character.ai** — `broken_render` сработал, а снимок весит
  110 627 байт и содержимое в нём есть.

Для четырёх из пяти «снимок пуст, движок молчит» (bing, canva, quora, tiktok)
строго утверждать, что движок молчал, нельзя — их сессии стёрты перезаписью
журнала ([BUG-991](BUG-991-FIXED.md)). Чистый случай один — **cnbc**: он грузился
в 15:58, внутри уцелевшего отрезка журнала, `ready_s = 101.86`, три ошибки
консоли, `broken_render` не сработал, снимок пуст.

## Диагноз (P3, 2026-09-05)

**Ни один из признаков не врёт — они честно отвечают на разные моменты времени.**

Первым шагом headless `--dump-display-list https://www.cnbc.com/` (без сети-
таймингов живого окна) дал **1418 команд, 919 `DrawText`** — движок безусловно
умеет нарисовать эту страницу, путь снимка (`Renderer::render_to_image_cpu`,
общий код для headless `--screenshot` и живого `resource://screenshot`) не
сломан на уровне рисования команд.

Дальше — живой прогон (`--mcp-live-port --maximized --health-log`, реальная
сеть, реальный `www.cnbc.com`), с опросом `resource://layout` и
`resource://screenshot` каждые 5–6 секунд после `navigate`:

```
t+5s   boxes=0     max_h=0.0      (страница ещё грузится)
t+42s  boxes=2062  max_h=15805.6  PNG ~491 КБ  — страница ПОЛНОСТЬЮ отрисована
t+47s  boxes=57    max_h=0.0      PNG 38743 байт, md5 ba789b37… — тот самый «пустой кадр»
t+52..149s  boxes=57  max_h=0.0   — состояние не меняется до конца окна наблюдения (149с)
```

Тот же провал воспроизведён дважды (разные процессы, разное сетевое время до
пика — t+12s и t+42s), и **воспроизведён с `LUMEN_NO_ADBLOCK=1`** (то есть не
объясняется тем, что сайт «наказывает» посетителя со встроенным блокировщиком
рекламы за заблокированный `gpt.js` — с рекламой, загружающейся штатно, тот же
обвал случается в том же временнóм окне). В обоих запусках коллапс совпадает по
времени с записью в консоли:

```
[JS error] TypeError: object is not iterable (cannot read property Symbol(Symbol.iterator))
[unhandled-rejection] TypeError: object is not iterable (cannot read property Symbol(Symbol.iterator))
```

После коллапса дерево — 57–60 боксов, почти все `<script>` с нулевым размером;
ни одного бокса с текстом/картинкой. Это форма, типичная для необработанного
исключения при рендере React-подобного SPA без Error Boundary — по умолчанию
React снимает с экрана всё приложение при необработанной ошибке рендера, а не
только сломавшийся компонент. `document.write()` как механизм обвала исключён:
после `load` он no-op ([BUG-701](BUG-701-FIXED.md)), стирать дерево нечем.

**Вывод:**

1. Путь снимка (`resource://screenshot`) не виноват — он рисует ровно то, что
   реально в `self.display_list` на момент чтения, и на пике (t+42s) это
   подтверждено (2062 бокса, живая картинка). Все выводы «CPU-растеризатор теряет
   картинку» для этого случая отпадают.
2. Эвристика `broken_render` тоже не соврала для cnbc — она сработала бы ровно
   так же честно, если бы проверялась заново на t+47s+ (страница на тот момент
   действительно пуста, `rendered_units == 0`). Она **не соврала, потому что
   не проверялась повторно**: `broken_render` считается один раз, сразу в
   `apply_loaded_page` (см. `docs/perf/health.md`), а перф-аудит снимает
   `resource://screenshot` намного позже (после `document_ready`+dwell) —
   то есть два признака смотрят на страницу в **разные моменты**, а не на одно и
   то же состояние с противоречивым результатом.
3. Значит «11 сайтов OK со снимком-пустышкой» из отчёта 2026-09-04 — это, как
   минимум для cnbc, не свидетельство сломанного рендера/эвристики, а
   свидетельство **отдельного дефекта**: страница рендерится нормально и потом
   сама разваливается. Заведён как усиление уже существующего
   [BUG-994](BUG-994-OPEN.md) (см. его файл — та же сигнатура «not iterable»,
   тот же класс «DOM-коллекция без `Symbol.iterator`»), точный вызывающий код
   внутри минифицированного бандла cnbc не локализован.
4. Обратный случай (character.ai: `broken_render` сработал, снимок непустой)
   этим срезом не перепроверялся живым прогоном — сырых данных того запуска
   (`health.<pid>.log`) не сохранилось (перезаписаны, [BUG-991](BUG-991-FIXED.md)).
   Симметричное объяснение того же рода (эвристика проверила ДО того, как
   реальный контент дорисовался — гонка в обратную сторону) правдоподобно, но
   не подтверждено измерением; если конкретный кейс всплывёт снова на новом
   прогоне со свежим журналом, разбирать его отдельно.

## Что теперь можно и нельзя утверждать

- **Нельзя** делать вывод «CPU-путь снимка теряет картинку» из пустого PNG —
  без повторного измерения в момент снимка неизвестно, был ли на странице реальный
  контент к этому моменту.
- **Можно** доверять и снимку, и `broken_render` как раздельным, но
  **однократным** замерам состояния страницы в момент своего собственного
  вызова — не как двум согласованным наблюдениям одного и того же состояния.
- Однократность самой эвристики (проверка ровно один раз в `apply_loaded_page`,
  без повтора к моменту снимка) задокументирована как известное ограничение —
  добавлено в `docs/perf/health.md` §Честные ограничения.
