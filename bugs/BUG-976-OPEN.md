# BUG-976: спавн нового V8-изолята синхронно изнутри `pump_raf_engine_thread` вешает процесс без паники

**Статус:** OPEN
**Компонент:** shell (`crates/shell/src/relayout.rs::pump_raf_engine_thread`) / js (`rusty_v8` isolate creation, `run_scripts_with_dom`)
**Найден:** P1, 2026-09-04, при реализации [FRAME-8](../ROADMAP.md) (BUG-885).

## Симптом

Создание НОВОГО V8-изолята (`crates/shell/src/frames.rs::spawn_frame` →
`run_scripts_with_dom`) на ad-hoc `std::thread::spawn`-потоке, запущенное
**синхронно изнутри** `Lumen::pump_raf_engine_thread`, сразу по завершении
движкового rAF/task-хода (ADR-023: движковый поток включён по умолчанию),
вешает весь процесс целиком:

- движковый поток перестаёт тикать таймеры страницы — `setInterval`,
  запущенный до этого штатно тикавший каждые 500 мс, замолкает навсегда;
- сообщения об ошибке/панике нет НИ ОДНОГО — `RUST_BACKTRACE`/stderr пусты;
- фоновый поток, спавнящий новый изолят, получает сетевой ответ (виден
  `← 200 .../vwjh-child.html`) и на этом обрывается — следующий вызов
  (`run_scripts_with_dom`/что-то внутри него) не завершается никогда.

## Прямое измерение

`tests/wpt/verify_window_history_jsurl_gaps.py --variant frame-parser`
(2026-09-04, dev-release, движковый поток по умолчанию включён): проба
динамически создаёт `<iframe>` из обработчика `window.onload` и назначает
`src`. Первый парсерный фрейм грузится штатно (`parser-frame-load-attr`,
`parser-frame-load-listener`), но со следующим тиком (`PROBE tick 1`)
процесс замолкает.

Отладка потребовала записи в файл с явным `sync_all()` — обычный
`eprintln!` не успевал долететь до диска при принудительном
`TerminateProcess` (probe harness использует `proc.terminate()`/`proc.kill()`
на Windows, что форсит `TerminateProcess` без штатного завершения потоков).
Файловый лог показал: код скана (`Lumen::poll_dynamic_frames`) отрабатывал
целиком, `spawn_frame` уходил на фоновый поток и **получал HTTP-ответ**
(`← 200 http://127.0.0.1:.../vwjh-child.html?from=dynamic`) — и на этом
хвост обрывается. Никакого дальнейшего вывода (ни от движкового потока, ни
от фонового) за оставшиеся ~14 с окна пробы.

## Что уже исключено

- Не блокировка через `engine.query()`/`clone_js_ctx()` в UI-потоке —
  трассировка показала, что и `poll_dynamic_frames`, и последующий
  `relayout_raf_dirty()` **успешно завершаются** за тот же тик, где найден
  новый фрейм; хэндл фонового потока успевает получить сетевой ответ.
- Не гонка «повторный скан до ответа» — `Lumen::pending_new_frames`-бронь
  гарантирует ровно один фоновый поток на host-узел.
- Тот же приём (`std::thread::spawn`, создание дочернего V8-изолята внутри
  `spawn_frame`) из обработчика клика по ссылке внутри фрейма
  (`frame_links.rs::replace_frame_document`, FRAME-4 срез 3) гонки не
  ловит — используется в продакшене без нареканий. Отличие — именно
  соседство по времени с только что завершившимся движковым ходом
  (`pump_raf_engine_thread`'s `take_dom_dirty_lockfree()` возвращает `true`
  сразу после того, как движковый поток закончил обрабатывать пачку
  сообщений с только что мутировавшим DOM).

## Кандидат причины (не доказан)

V8 требует единую `Platform` на процесс; создание нового `Isolate` может
контендить на её внутренние структуры (список зарегистрированных изолятов,
задачи фоновой компиляции/GC) с изолятом движкового потока, который
буквально в этот момент отпустил очередь после хода. Если новый изолят
создаётся ДО того, как движковый поток успевает вернуться в состояние
парковки (`recv()`), возможен настоящий deadlock на уровне `rusty_v8`/V8
Platform lock, а не на уровне каналов `EngineThread`.

## Обход (не фикс)

[FRAME-8](../ROADMAP.md) откладывает сам `std::thread::spawn` на один
полный проход event loop — детектирование (скан) остаётся внутри
`pump_raf_engine_thread`, а спавн переезжает в
`Lumen::dispatch_pending_frame_loads`, вызываемый из начала
`on_about_to_wait` СЛЕДУЮЩЕГО тика (`crates/shell/src/lumen/frame_dynamic.rs`).
Это убрало зависание во всех измеренных прогонах (десятки повторов), но не
объясняет механизм — если гипотеза выше верна, отсрочка просто даёт
движковому потоку время вернуться на `recv()` между ходом и спавном, а не
устраняет саму возможность гонки при другом тайминге.

## Риск

Любой будущий код, который решит спавнить дочерний V8-контекст
(`run_scripts_with_dom` или эквивалент) синхронно изнутри
`pump_raf_engine_thread` или любого другого места, выполняющегося сразу
по завершении движкового хода без отсрочки, рискует повторить то же
зависание — без единого диагностического сообщения, что делает его
крайне дорогим в отладке.
