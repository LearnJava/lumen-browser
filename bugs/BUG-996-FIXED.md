# BUG-996 — после свопа листа OneTrust релейаут fandom.com не оседает минутами

**Статус:** FIXED 2026-09-05
**Заведён:** 2026-09-04 (P3, при проверке фикса BUG-987)
**Нумерация:** исходно BUG-995; номер освободился после коллизии с параллельной
сессией P2 (WPT-RUN-7, `focused_node`/text_input — другой дефект), переименован
в BUG-996
**Область:** shell (`crates/shell/src/app/mod.rs::window_event`, ветка
`WindowEvent::Resized`)
**Владелец:** P3

## Симптом

На живом fandom.com после инъекции стилей OneTrust (`CSS пересобран после
правки <style>: 2731 правил`) процесс уходит в релейаут, который жжёт ~2 ядра
и не завершается за 4.5+ минут: сетевых действий нет (лог замер, последняя
строка — та самая пересборка), память стабильна ~1.33 ГБ, окно живо.

## Почему виден только сейчас

До фикса BUG-987 (этап 1 — стеки) процесс в этой же точке умирал крэшем
(`thread 'main' has overflowed its stack`), поэтому «что происходит после
свопа» никогда не наблюдалось. Фикс убрал крэш — и вскрылся этот слой.

## Что говорит измерение

- Живой прогон 2026-09-04 с фиксированным бинарём: CPU 132.7 с → 190.8 с за
  30 с стены (~1.9–2.5 ядра), затем 190.8 с → 474.8 с за 150 с (~1.9 ядра),
  лог заморожен на строке пересборки с ~65 с от старта; процесс убит
  принудительно на ~5-й минуте.
- Не глубина дерева: оффлайн-страницы `<div>`×N (150…5000) на тех же стеках
  оседают за секунды (dump-layout, screenshot).

## Первый шаг — выполнено (P3 2026-09-05)

`--trace-nav` headless на fandom.com **не воспроизводит** предмет бага вовсе:
дамп-режимы не гоняют per-frame цикл (`dump_mode.rs`: «event loop's per-frame
pumps (timers/rAF) are absent»), поэтому асинхронный скрипт OneTrust, который
и запускает своп листа, никогда не получает тика — `--trace-nav` (400 c)
завершается штатно (`rc=0`), строка «CSS пересобран» не появляется вовсе.
Headless в принципе не годится для этого дефекта, а не «прошёл чисто».

Живой прогон (`--maximized`, `LUMEN_FRAME_LOG=1`) с временной инструментовкой
(caller-бэктрейс на каждый синхронный `relayout()`, тайминг `tick_timers`/
`run_animation_frame`, дамп `[win-event]` на каждое некадровое окно-событие)
разделил гипотезу однозначно: **много дорогих проходов, а не один**. За 220 с
после финального свопа (2731 правил) синхронный `relayout()` вызывался **32
раза подряд**, каждый по 5.3–6.7 с, и **ни разу** за это время не сработали ни
`tick_timers`, ни `run_animation_frame` — движок ни разу не вернул управление
JS-таймерам, застряв в UI-потоке.

Интерливинг `[win-event]`/`[relayout-sync]` назвал триггер: перед КАЖДЫМ из 32
вызовов приходит `WindowEvent::Resized(1920×1017)` — размер, побайтово равный
уже применённому (`actual`/`renderer` в том же логе). Обработчик `Resized`
безусловно гонит полный `relayout()` на любое входящее событие, даже когда
размер не изменился. Механизм замыкания: relayout блокирует message pump на
5+ секунд → Windows считает верхнеуровневое окно зависшим → shell/DWM начинает
опрашивать его (сигнатура в бэктрейсе последнего вызова —
`SendMessageTimeoutW`/`IsIconic`/`GetWindowTextW`/`IsCompositionActive`/
`LookupIconIdFromDirectoryEx`, ровно набор вызовов «ghost window» пробы
зависшего окна) и в процессе повторно доставляет `WM_SIZE` с тем же размером
→ `Resized` → новый безусловный `relayout()` → снова 5+ с блокировки → окно
опять выглядит зависшим. Цикл самоподдерживающийся и не сходится сам: каждый
проход валиден и конечен (это НЕ бесконечная рекурсия и не рост данных), но
пул давит его заново раньше, чем сообщение способно закончиться естественным
образом.

Дорогой сам по себе полный рестайл 2731 правил × DOM (5.3–6.7 с одного прохода)
остаётся отдельным, не закрытым этим фиксом наблюдением — родственная зона
BUG-341 (инкрементальный рестайл, пауза по решению пользователя 2026-07-28).

## Фикс P3 2026-09-05

`crates/shell/src/app/mod.rs::window_event`, ветка `WindowEvent::Resized`:
добавлено поле `Lumen::last_resized_physical: Option<(u32, u32)>`
(`crates/shell/src/lumen/state.rs`), хранящее физический размер последнего
`Resized`, на который реально прогонялся `relayout()`. Входящее событие с тем
же размером теперь возвращается раньше `renderer.resize()`/`relayout()` —
безусловный повторный проход убран, а настоящее изменение размера всегда
отличается от последнего применённого, так что реальный ресайз фикс пропустить
не может.

Временная инструментовка (backtrace на каждый `relayout()`, тайминг
`tick_timers`/`run_animation_frame`, дамп `[win-event]`, замер
`[apply] observers`/`[commit] arrival`) была диагностической и удалена этим же
коммитом — она свою задачу выполнила (разделила «один дорогой проход» и
«много дорогих проходов», нашла триггер), закреплять в коде было нечего.

### Проверка фикса

Живой прогон, тот же сценарий (`--maximized`, `LUMEN_FRAME_LOG=1`, fandom.com,
90 с окна): после каждого из двух свопов листа (2100 и 2731 правил) —
**ровно один** `[engine] relayout` (5.74 с и 11.31 с соответственно, оба
`(off-thread)` — обычный путь ADR-016, не шторм), дальше кадры стабилизируются
на `delta Identical` / `band blit`, ~20–25 мс/кадр. Никакого повторного
`Resized` с идентичным размером, никакого зависания. `cargo build -p
lumen-shell --profile dev-release` и `cargo clippy -p lumen-shell
--all-targets -- -D warnings` чисты.

Дорогой единичный рестайл (5.3–11.3 с на 2731 правил × DOM без
инкрементальности) фиксом не тронут — это отдельный дефект производительности
каскада, а не этот баг; продолжение — зона BUG-341 при возобновлении по
явному запросу пользователя.
