# BUG-396 — GIF-декодер отклоняет спек-валидный кадр без предшествующего Graphic Control Extension («invalid code in LZW stream»)

**Статус:** FIXED 2026-08-11
**Компонент:** image (`crates/engine/image/src/gif.rs` —
`decode_gif_animated`, `GifCursor`/`AnimatedGif::frame_image`)
**Найден:** P2, WPT-VENDOR-gif (2026-07-28), прямая проба на реальном
вендоренном GIF-файле (`tests/wpt/gif/reset-no-gce.gif`) — категория сама
по себе не прогоняется (единственный тест `reftest`, неподдерживаемый тип
для минимального экзекьютора), проба через `cargo test`/`include_bytes!`
подставлена вместо `run_report.py`

## Симптом

`tests/wpt/gif/reset-no-gce.gif` — 3-кадровый GIF (2×2, non-looping,
глобальная палитра из 4 цветов: 0=чёрный, 1=красный, 2=зелёный, 3=синий).
Кадр 0 несёт GCE с disposal=2 ("restore to background") и
`transparent_index=0` (чёрный — эффекта нет, кадр полностью красный).
Кадр 1 несёт GCE с disposal=2 и `transparent_index=2` (зелёный — весь
кадр становится прозрачным). Кадр 2 **не имеет предшествующего GCE
вовсе** — именно это и тестирует upstream (комментарий в
`reset-no-gce-1.html`): "The third frame is all green, there is no gce
preceeding it, so there is no transparent index."

`decode_gif_animated` (metadata-проход, читал каждый кадр через
`reader.next_frame_info()`/`reader.read_into_buffer()`) успешно
декодировал кадр 0 (`[255,0,0,255]` ×4, корректно), но падал на кадре 1:

```
next_frame_info ERROR at idx 1: invalid code in LZW stream
```

Вся анимация при этом умирала целиком: `decode_gif_animated` возвращал
`Err`, значит ни `decode_gif` (первый кадр), ни `frame_image` не были
доступны — картинка на странице не появлялась вовсе.

## Независимая проверка: файл валиден

Тот же файл, открытый Pillow (`PIL.Image`, независимый декодер) из
`tests/wpt/.venv`, декодируется без ошибок и даёт ровно ожидаемый
upstream-комментарием результат:

```
n_frames 3
0 disposal 2 transparency 0    [(255,0,0,255)]×4   — красный, непрозрачный
1 disposal 2 transparency None [(0,0,0,0)]×4        — полностью прозрачный (transparent_index=2 совпал с заливкой)
2 disposal 2 transparency None [(0,255,0,255)]×4    — зелёный, непрозрачный (нет GCE ⇒ нет transparent_index)
```

Файл байт-в-байт идентичен апстримному (сверено `xxd`-диффом после
`git sparse-checkout`) — повреждения при вендоринге нет.

## Причина

Заявка предполагала «дефект LZW-декодера крейта `gif` при переходе между
кадрами с разными GCE-конфигурациями». Разбор LZW-потока показал другое:
**GCE тут ни при чём, и разные кадры ни при чём** — все три кадра несут
структурно одинаковые LZW-данные (`8c a3 00` у кадра 0, `94 a5 00` у
кадров 1 и 2, `min_code_size=2`), и пиксели каждого из них декодируются
верно. Ошибка возникала не «на кадре 1», а при попытке домотать
**хвост кадра 0** — второй вызов `next_frame_info()`.

Разбор потока кадра 0 по битам (LSB-first):

| код | ширина | значение | смысл |
|---|---|---|---|
| 1 | 3 | 4 | CLEAR |
| 2 | 3 | 1 | литерал «красный» |
| 3 | 3 | 6 | KwKwK → «11», заводит запись 6 |
| 4 | **4** | 1 | литерал «красный» → буфер 2×2 заполнен |
| 5 | **4** | 5 | EOI |

Ширина кода растёт **на один код раньше**, чем её наращивает `weezl`
(через который работает крейт `gif`): весь поток писал энкодер
early-change-семейства (giflib и производные — таблица энкодера всегда на
одну запись впереди таблицы декодера, поэтому декодер обязан расширяться
при `next_code == 2^width − 1`, а `weezl` расширяется при
`next_code == 2^width`). Читая код 4 тремя битами вместо четырёх, `weezl`
разъезжается с потоком и на пятом коде видит `10` — несуществующую запись
(`next_code == 8`), отсюда `invalid code in LZW stream`.

Проверено скриптом-декодером на обоих соглашениях: при
`next_code == 2^width − 1` оба потока читаются до чистого EOI, при
`next_code == 2^width` — падают ровно на пятом коде, уже **после** того
как все 4 пикселя выданы.

**Дефект, который лечится в Lumen, — не в ширине кода, а в том, что
`gif.rs` заставлял декодер вообще дочитывать этот хвост.** Пиксели кадра
кончаются на четвёртом коде; браузеры (Blink `GIFLZWContext::doLZW`) и
Pillow останавливают LZW ровно на `width × height` пикселях и до хвоста не
доходят. Lumen же читал кадр парой `next_frame_info()` +
`read_into_buffer()`: `read_into_buffer` останавливается на заполненном
буфере (`PixelConverter::fill_buffer` → `Ok(true)`), а следующий
`next_frame_info()` доводит LZW-поток текущего кадра до конца
(`DecodeSubBlock` → `LzwReader::decode_bytes(&[], OutputBuffer::None)`) —
и вот тут хвостовые биты и разбирались.

## Что сделано

`crates/engine/image/src/gif.rs` — оба прохода разведены так, чтобы
LZW-декодер никогда не работал за пределами пикселей кадра:

* **Контейнерный проход** (`container_options()`, новая функция) —
  `DecodeOptions::skip_frame_decoding(true)`. `decode_gif_animated`
  теперь просто идёт по контейнеру и собирает `frame.delay`; LZW-данные
  перешагиваются как есть, не разжимаясь. Побочно ушёл и разовый
  `vec![0u8; width*height*4]`-буфер под выбрасываемые пиксели — на
  метаданных не аллоцируется ничего.
* **Пиксельный проход** — `GifCursor` получил поле `frames:
  Box<FrameDecoder>` (`gif::streaming_decoder::FrameDecoder`, глобальная
  палитра ставится из `reader.global_palette()`). `frame_image` читает
  кадр через `reader.read_next_frame()` (отдаёт кадр с несжатыми
  LZW-байтами) и распаковывает его
  `frames.decode_lzw_encoded_frame_into_buffer(frame, &mut buffer)` —
  этот путь останавливается на заполненном кадровом буфере и хвост не
  трогает.

Апгрейд/патч зависимости не понадобился: `gif` остаётся на `0.14.2`,
новых зависимостей нет.

Результат на фикстуре — ровно то, что описывает upstream:
3 кадра, delays `20/20/0` cs, кадр 0 непрозрачный красный, кадр 1
полностью прозрачный (`alpha == 0` во всех пикселях), кадр 2 —
непрозрачный зелёный (GCE нет ⇒ `transparent_index` нет).

## Регрессия

`cargo test -p lumen-image gif::` — 29 тестов, два новых:

* `bug396_early_change_lzw_tail_does_not_kill_animation` — 3 кадра,
  размер, per-frame delays;
* `bug396_frame_without_gce_has_no_transparent_index` — пиксели всех трёх
  кадров, включая «зелёный обязан остаться непрозрачным» у кадра без GCE.

Фикстура встроена в тест байт-в-байт (`RESET_NO_GCE_GIF`, 90 байт,
разложена по структуре GIF с комментариями), чтобы тест не зависел от
наличия вендоренного `tests/wpt/gif/` — совпадение с файлом проверено при
разработке.

## Побочный эффект (осознанный)

`decode_gif_animated` больше не разжимает кадры при загрузке, значит
не валидирует их. GIF с действительно битым LZW-потоком теперь принимается
на загрузке, а ошибка всплывает при запросе конкретного кадра
(`frame_image` → `Err`); для кадра 0 поведение не меняется, потому что
`decode_gif` = `decode_gif_animated(..)?.frame_image(0)`. Это ближе к
браузерам, которые показывают анимацию до первого сломанного кадра, а не
отбрасывают файл целиком.

## Связанные

* Категория `gif` — скоуп ⬜ (кандидат), единственный тест —
  reftest-пара (`reset-no-gce-1.html`/`reset-no-gce-ref.html`),
  неподдерживаемый тип для минимального `wptrunner`-экзекьютора
  (тот же класс гэпа, что `apng`/`acid`/`animation-worklet`/
  `accessibility`'s crashtests) — прогон дал бы `Unsupported test type
  reftest`, 0/0, без сигнала; находка получена прямой пробой декодера
  на реальном вендоренном файле вместо прогона, тот же приём, что
  `eyedropper`/`geolocation` (см. `tests/wpt/VENDOR.md`).
* Не связан с BUG-272 (Canvas 2D `arc`) или другими image-находками —
  первый вендоринг-баг конкретно в GIF-декодере.
* [BUG-763](BUG-763-OPEN.md) — заведён при этом разборе: кадры **меньше**
  логического экрана не компонуются на экранный холст с учётом
  `left`/`top`/disposal, буфер кадра пишется с начала экранного буфера.
  Дефект существовал и до фикса BUG-396 и им не затронут (фикстура
  BUG-396 его не задевает: кадр = экран).
