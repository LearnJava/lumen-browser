# BUG-448 — `getImageData(sx, sy, sw, sh)` игнорирует все четыре аргумента и всегда отдаёт весь холст

**Статус:** OPEN
**Компонент:** js (`crates/js/src/dom.rs:5224-5235` — шим `getImageData`;
натив `crates/js/src/canvas2d.rs:1003` `_lumen_canvas2d_get_image_data(nid)`)
**Найден:** 2026-07-29 (P2), WPT-VENDOR-html-canvas, проба `--dump-layout`

## Симптом

Метод объявлен с сигнатурой спеки, но параметры прочитаны только в ветке отказа:

```js
// crates/js/src/dom.rs:5224
getImageData: function(x, y, sw, sh) {
    var raw = _lumen_canvas2d_get_image_data(nid);          // <- аргументы не переданы
    if (!raw) { return { width: sw|0, height: sh|0, data: new Uint8ClampedArray((sw|0)*(sh|0)*4) }; }
    ...
    return { width: w, height: h, data: arr };              // <- w,h всего холста
}
```

Натив принимает **только** `nid` и сериализует весь битмап целиком
(`"{w},{h},{hex_rgba}"`), поэтому запрошенный прямоугольник не доезжает до движка
вообще. Проба (холст 60×30, три непересекающиеся полосы `#ff0000` / `#00ff00` /
`#0000ff` по x = 0..10 / 20..30 / 40..50):

```
C1 read(5,5)=255,0,0,255  read(25,5)=255,0,0,255  read(45,5)=255,0,0,255  read(15,5)=255,0,0,255
C3 strip = getImageData(24, 5, 3, 1) -> len=7200 (ожидалось 12), px=255/0/0 255/0/0 255/0/0
```

Все четыре точки читаются как пиксель `(0, 0)`, а трёхпиксельная полоска приходит
объектом на 7200 байт — это ровно `60 * 30 * 4`, то есть весь холст.
`getImageData(0, 0, w, h)` — единственный вызов, который случайно даёт верный ответ,
и именно им пользуются graphic-тесты, поэтому дефект до сих пор не был виден
(см. [[feedback_green_test_can_mask_broken_feature]]).

Тот же вызов через `big.data[(y*60+x)*4]` даёт правильные цвета (`C2` в пробе), что
доказывает: битмап в движке верный, ломается только выборка прямоугольника.

## Почему это важнее, чем выглядит

1. **Портит все чтения пикселей на странице.** Любой код вида
   `ctx.getImageData(x, y, 1, 1)` (пипетка, hit-test, чтение под курсором) получает
   пиксель `(0,0)` — молча, без исключения.
2. **Отравляет диагностику.** Прежняя сессия WPT-VENDOR-html-canvas сделала по такому
   чтению вывод «hsl() не поддержан вовсе» — вывод оказался верным (BUG-451), но
   доказательство было недействительным: читался чужой пиксель.
3. **Цена вызова.** Транспорт — hex-строка на весь холст: у стандартных 300×150 это
   360 000 символов и 180 000 `parseInt(substr(...), 16)` на **каждый**
   `getImageData(0,0,1,1)`.

## Сопутствующий дефект того же шима

`putImageData` (`dom.rs:5253`) реализует только трёхаргументную форму; спековые
`dirtyX/dirtyY/dirtyWidth/dirtyHeight` (7-аргументная форма) молча отбрасываются.

## Ожидаемое поведение (HTML LS §4.12.5.1.10)

`getImageData(sx, sy, sw, sh)` возвращает `ImageData` ровно `sw × sh`, взятый с
origin `(sx, sy)`; область вне холста заполняется прозрачно-чёрным;
`sw`/`sh` = 0 → `IndexSizeError`; нечисловые/нефинитные аргументы → `TypeError`.

## Как чинить

Пробросить прямоугольник в натив: `_lumen_canvas2d_get_image_data(nid, sx, sy, sw, sh)`
и вырезать область на стороне Rust (там битмап уже в руках), а не отдавать холст
целиком. Это же убирает и проблему цены. Заодно перевести транспорт с hex-строки на
`Uint8ClampedArray`/`ArrayBuffer`, если V8-биндинг это позволяет.

## Воспроизведение

`.tmp/probe-color.html` из ветки `p2-wpt-vendor-html-canvas`, запуск
`lumen.exe --dump-layout .tmp/probe-color.html`, строки `C1`/`C3`.
