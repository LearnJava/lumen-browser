# BUG-952 — исключение, брошенное внутри колбэка таймера, не долетает никуда: ни строки в логе, ни `window.onerror`, страница просто перестаёт что-либо делать в этом таске

**Статус:** FIXED 2026-09-23 (P6, повторная проба подтвердила закрытие BUG-591)
**Тип:** дефект реализованного кода — синхронная ошибка скрипта уже логируется (`script error: …`), тот же путь отчёта не подключён к колбэкам `setTimeout`/`setInterval`.
**Заведён:** 2026-09-01 (WPT-RUN-6, срез 32, живая проба `verify_slice32_gaps.py --variant timer-callback-exception`)
**Область:** js (движок V8-раннер — обработчик колбэков таймера; отчёт об ошибке уже существует для верхнеуровневого `rt.eval`/module-скриптов, судя по строкам `script error:`/`module error:` в логе браузера, но не переиспользован для таймерных задач)
**Владелец:** P3.

## Симптом

`TypeError`, брошенный внутри функции, переданной в `setTimeout`, не
производит ничего наблюдаемого: ни строки `script error: …`/`[JS error]
Uncaught …` в логе браузера (как для синхронно брошенных ошибок — см.
`swallowed_errors` в `tests/wpt/timeout_audit.py`), ни вызова
`window.onerror`, ни `unhandledrejection`-подобного события. Колбэк просто
обрывается на строке исключения; код ПОСЛЕ него в том же колбэке не
выполняется, но остальной цикл событий жив — соседние таймеры продолжают
срабатывать штатно.

Если единственный эффект колбэка — вызвать `done()`/резолвить промис теста,
падение теста выглядит не как FAIL, а как TIMEOUT: харнесс никогда не узнаёт,
что что-то пошло не так.

## Прямое измерение

Живая проба (`--variant timer-callback-exception`, dev-release): страница
ставит `performance.mark`, затем `setTimeout(fn, 200)`, где `fn` первой же
строкой читает `window.performance.timing.navigationStart` (атрибут не
существует — `window.performance.timing` есть `undefined`, что само по себе
ожидаемо, устаревший Navigation Timing L1 не реализован). Второй,
независимый `setTimeout(fn2, 1000)` печатает контрольную метку.

Результат в логе браузера: `PROBE script-start` → `PROBE tick 1` → `PROBE
tick 2` → **`PROBE outer-alive`** (второй таймер сработал штатно) → тики
продолжаются. `PROBE timercb-done` (последняя строка первого колбэка,
ПОСЛЕ броска) не напечатана НИ РАЗУ — колбэк оборвался на исключении. Ни
одной строки вида `script error:`/`module error:`/`[JS error]` нигде в логе
— полное молчание, хотя те же строки печатаются для синхронно брошенных
ошибок (см. `swallowed_errors` в результатах `timeout_audit.py`, где 39
разных текстов исключений УЖЕ попадают в лог браузера).

## Кого это держит

`user-timing/measure.html` — тот же паттерн буквально: `measure_test_cb`
(колбэк `step_timeout`, т.е. обычный `setTimeout`) первой веткой читает
`window.performance.timing.navigationStart` без проверки — бросает, `done()`
не вызывается, TIMEOUT. Тот же файл использует `window.performance.timing`
(легаси Navigation Timing L1) в единственном месте, поэтому чинить нужно
именно отчёт об исключении, а не добавлять `performance.timing` — страница
всё равно повиснет на первом же непойманном исключении в любом другом
таймере. Тем же паттерном объясняются `user-timing/measure_navigation_timing.html`
и `navigation-timing/test-navigate-within-document.html` (не проверено
пробой по отдельности — общий вывод по чтению исходников, оба используют
`step_timeout`/`setTimeout` в цепочке до `done()`).

## Направление починки

Найти точку, где V8-раннер вызывает колбэк `setTimeout`/`setInterval`
(нативная функция, зарегистрированная под `setTimeout`), обернуть вызов в
`TryCatch` и прогнать пойманное исключение через тот же путь отчёта, что уже
существует для верхнеуровневых скриптов (судя по формату `script error:
JS runtime error: …` — вероятно один общий хелпер, которым таймерный путь
просто не пользуется).

## Закрыт (P6, 2026-09-23)

Живое MCP-окно в сессии недоступно (см. соседние срезы BUG-683/BUG-791/BUG-638
того же дня — [[feedback_background_launched_window_breaks_mcp_js_context]]),
но эту пробу заменяет не headless-дамп, а прямой `cargo test -p lumen-js`:
V8-раннер поднимается in-process, без окна/MCP вообще, и уже есть готовый
регрессионный тест ровно на этот сценарий —
`bug591_timer_exception_fires_window_error_with_five_arg_onerror`
(`crates/js/src/dom/tests/v8_core/selectors_canvas_window.rs:1408`):
`setTimeout(function() { thisFunctionDoesNotExist(); }, 0)` →
`_lumen_tick_timers()` → проверяет, что `window.onerror` получает 5
аргументов и `error`-событие несёт `ReferenceError`.

Прогон подтвердил: тест зелёный, и, что важнее для исходного симптома —
в stdout теста печатается `[JS error] Uncaught ReferenceError:
thisFunctionDoesNotExist is not defined` через штатный лог-путь (не молчание,
как утверждала исходная заявка). Соседний
`worker::tests_v8::v8_worker_timer_exception_is_reported_and_the_loop_continues`
тоже зелёный — обрыв колбэка не топит цикл событий воркера.

[BUG-591](BUG-591-FIXED.md) (FIXED 2026-08-23) — тот самый P1-трек, который
подключил репорт исключений отовсюду, включая таймеры, первым же срезом
(«window 'error'/onerror … теперь диспатчится для необработанного исключения
из таймера»). Заявка BUG-952 заведена 2026-09-01, на 9 дней позже фикса —
дубликат по факту, просто не сверенный с уже закрытым BUG-591 в момент
заявки. Диагноз из «Направления починки» («нативный `setTimeout`», отдельный
от `_lumen_report_exception` путь) в текущем коде действительно не
существует, как и отметил триаж.
