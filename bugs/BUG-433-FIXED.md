# BUG-433

**Статус:** FIXED 2026-07-29
**Компонент:** layout (flexbox)
**Файл:** `crates/engine/layout/src/box_tree.rs` (`lay_out_flex`)

## Описание

Flex-элемент сжимается ниже своего **автоматического минимального размера**
(CSS Flexbox §4.5 «Automatic Minimum Size of Flex Items»): при `min-width: auto`
(инициальное значение для flex-элемента) минимум равен content-based minimum
size, то есть min-content-ширине содержимого. Lumen этот минимум не применяет и
распределяет дефицит по `flex-shrink` вплоть до нуля, из-за чего ряд, который
обязан переполнить контейнер, вместо этого «ужимается» и вся его геометрия
уезжает.

## Минимальный воспроизводитель

```html
<style>
  * { margin:0; padding:0; box-sizing:border-box; }
  .row  { display:flex; width:300px; }
  .fixed{ width:200px; height:20px; background:#f00; }
</style>
<div class="row">
  <div class="item"><div class="fixed"></div></div>
  <div class="item"><div class="fixed"></div></div>
</div>
```

`--dump-layout` (2026-07-29):

```
Block rect=(0.00, 0.00, 300.00, 20.00) display=flex w=300.00
  Block rect=(0.00, 0.00, 150.00, 20.00) w=150.00      ← должно быть 200
    Block rect=(0.00, 0.00, 200.00, 20.00) bg=#ff0000ff
  Block rect=(150.00, 0.00, 150.00, 20.00) w=150.00    ← должно быть 200, x=200
    Block rect=(150.00, 0.00, 200.00, 20.00) bg=#ff0000ff
```

Ожидаемо (Edge/Chromium): оба `.item` = 200px, второй в `x=200`, ряд переполняет
контейнер на 100px. Обратите внимание, что вложенный `.fixed` остаётся 200px —
то есть содержимое вылезает за пределы собственного flex-элемента, а не
масштабируется вместе с ним.

## Как нашли

Ревизия BUG-101 (TEST-59 `59-image-set-cross-fade.html`, 2026-07-29). Ряд 1 —
пять `.group`-флекс-элементов по 220px + 4 гэпа по 16px = 1164px в контейнере
974px. Edge оставляет их по 220px (шаг 236) и обрезает пятый по
`overflow:hidden`; Lumen ужал до 182px (шаг 198), из-за чего сдвинулись все
ячейки и подписи ряда — попиксельно это давало ~70% расхождения в каждой из
четырёх видимых ячеек. Видно прямо в `--dump-display-list`: `DrawText` подписей
ряда 1 имеет `w=182.00`, у ряда 2 (три группы, дефицита нет) — `w=220.00`, а
`DrawBackgroundImage`/`DrawBorder` самой `.cell` при этом остаются 220px и
перекрывают соседа.

## Влияние

Основной вклад в остаточный дифф TEST-59; класс дефекта общий — любой flex-ряд
с фиксированными по ширине детьми, не влезающий в контейнер, раскладывается не
как в референсных движках.

## Исправление (2026-07-29)

Две части.

**1. Пол по главной оси — `flex_item_min_main_width`.** Явный `min-width`
резолвится как есть. `min-width: auto` (то есть `None`) даёт content-based
minimum size — *меньшее* из:

* **content size suggestion** — min-content-ширина **содержимого** элемента,
* **specified size suggestion** — собственная определённая `width` элемента,
  если она есть,

ограниченное определённой `max-width`. При `overflow-x != visible` пола нет:
у scroll-контейнера content-based минимума не бывает, и без этой оговорки
идиома «обрезающий flex-ребёнок с `overflow:hidden`» начала бы переполнять ряд.

**2. Распределение дефицита — цикл §9.7 step 4 вместо одного прохода.**
Элемент с `flex-shrink: 0` заморожен сразу (но тоже прижат к своему минимуму).
Дальше на каждой итерации остаток дефицита раскладывается по ещё гибким
пропорционально `flex-shrink × базовый размер`; кто ушёл ниже своего пола —
замораживается на нём, и следующая итерация раскладывает уже неусвоенный им
остаток. Цикл ограничен `n` проходами: каждый замораживает минимум один
элемент. Одного прохода мало принципиально — заморозка одного элемента меняет
веса всех остальных.

### Тонкость, которую вскрыл существующий тест

Первая версия считала пол через `min_content_outer_width`, а та для бокса с
заданной `width` возвращает саму эту ширину. Это уронило
`flex_probe_pass_does_not_burn_percentage_width_into_style` (BUG-343): там
элемент `width:300px` держит единственного ребёнка `width:100%`, чей вклад в
min-content равен нулю. По §4.5 его content size suggestion = 0, значит пол = 0
и элемент обязан ужаться до 200px; старый вариант видел пол 300px, замораживал
оба элемента и переполнял 400px-контейнер.

Поэтому content size suggestion интринсик: считается по содержимому, **как если
бы собственной `width` у элемента не было**. `min_content_outer_width` разделена
на неё же (короткое замыкание на собственной `width` осталось — её зовут другие
места) и `min_content_outer_width_of_contents`, которую использует пол.
У потомков собственные ширины по-прежнему учитываются — обходится только
преферред-размер самого элемента.

### Границы

* Колонка не тронута: она складывает свой content-пол в базовый размер (ветка
  `is_column` в `all_hyp`), поэтому `mins` для неё — нули. Возможный остаточный
  дефект column-оси в этом баге не разбирался.
* Пол считается только для линий с дефицитом, поэтому рекурсивный обход
  `min_content_outer_width_of_contents` не попадает на общий путь (BUG-341).

### Проверка

* Репро из этого файла через `--dump-layout`: 200 + 200, второй в `x=200`, ряд
  переполняет контейнер — как в Edge/Chromium.
* TEST-59: 25.02% → 22.16% (замерено на сборках main и ветки подряд). Ряд 1
  встал на шаг 236 как ряд 2, перекрытие ячеек ушло; CPU-эталон перегенерирован.
* Остальные 151 графических теста не сдвинулись (сверка всего набора с
  последним полным прогоном; единственное расхождение — TEST-90 +0.37 п.п. —

  `latest.json`, а не регрессией).
* 4 юнит-теста в `box_tree.rs`: репро, перераспределение остатка дефицита,
  разбор specified/content suggestion, отсутствие пола у scroll-контейнера.
