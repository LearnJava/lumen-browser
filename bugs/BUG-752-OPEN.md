# BUG-752 — движок игнорирует `<base href>` при резолвинге подресурсов и ссылок: `Document::base_href()` реализована и покрыта тестами, но не вызывается ни из одного продакшн-места

**Статус:** OPEN
**Компонент:** shell (`crates/shell/src/main.rs` — `ResourceBase`/`ResourceBase::resolve`, строится из URL страницы), dom (`crates/engine/dom/src/lib.rs:1272` — `Document::base_href()`, вызовов вне собственных юнит-тестов нет)
**Найден:** P3, при закрытии [BUG-377](BUG-377-FIXED.md) (пункт 3 его плана «Как чинить» — проверить движок отдельно), 2026-08-10

## Симптом

Страница по `https://example.com/a/page.html` с `<base href="/other/">` и
`<img src="pic.png">` должна грузить `https://example.com/other/pic.png`.
Движок грузит `https://example.com/a/pic.png` — `<base>` не учитывается.

То же для любого относительного `href`/`src`, который резолвит шелл:
`<link rel=stylesheet>`, `<script src>`, `<img>`, preload-диспетчер
(`ResourceBase::resolve_str`), и путь `File(...)` (страница с диска —
резолвится относительно директории файла независимо от `<base>`).

## Причина

`ResourceBase` (`main.rs:4144-4151`) — это ровно «откуда взялась страница»:
`File(PathBuf)` или `Url(String)`, оба заполняются при загрузке страницы. В
`ResourceBase::resolve` (`main.rs:4154`) `href` резолвится напрямив относительно
этого значения; документа функция не видит вовсе, поэтому места, где мог бы
примениться `<base href>`, в ней нет.

Функция-то есть: `Document::base_href()` (`crates/engine/dom/src/lib.rs:1272`,
первый `<base href>` в pre-order, ровно по HTML LS §4.2.3) — с пятью
юнит-тестами (`base_href_extracts_attribute`, `..._returns_none_without_base`,
`..._returns_none_when_base_has_no_href`, `..._finds_first_in_document_order`,
`..._case_insensitive_attribute`). Но `grep -rn base_href crates/ --include=*.rs`
даёт только само определение и эти тесты: **продакшн-вызовов ноль**. Тесты
зелёные, поведение браузера — нет; классический случай, когда наличие
покрытой тестами функции читается как «фича есть».

JS-сторона расхождения уже чинится независимо и **этим багом не покрывается**:
шим считает базовый URL сам (`_lumen_document_base_url()` в
`crates/js/src/dom.rs`, `<base>`-aware), и на него завязаны `fetch()`,
`new Request()`, `Worker`/`SharedWorker`, IDL-рефлексия вида `url`
(BUG-383) и `Node.baseURI` (BUG-377). То есть **скрипт и движок сейчас
резолвят один и тот же относительный URL по-разному**, когда на странице
есть `<base>`: `new Image().src = 'pic.png'` из JS уйдёт по одному адресу,
а тот же `<img src="pic.png">` в разметке — по другому.

## Влияние

- Любой сайт с `<base href>` (частая схема у статических генераторов,
  документационных порталов и страниц, отдаваемых из подкаталога) грузит
  подресурсы не по тем адресам — картинки/стили/скрипты просто 404.
- Расхождение движка и JS внутри одной страницы (см. выше) — худший вид
  бага: половина ресурсов приезжает, половина нет, и причина не локальна.

## Как чинить

1. Дать `ResourceBase` знать про базовый URL документа: либо третий вариант /
   поле «base URL из `<base href>`, отрезолвленный относительно URL страницы»,
   заполняемое после парсинга документа, либо передавать `&Document` в
   `resolve`. Первый вариант дешевле: `<base>` не меняется на каждый ресурс.
2. Заполнять его из `Document::base_href()` в местах постройки `ResourceBase`
   (загрузка страницы + все пересоздания при навигации) и не забыть путь
   `File(...)` — там `<base href>` тоже применим и должен превращать резолв
   из «относительно директории файла» в «относительно базового URL».
3. Динамика: `<base href>` может быть вставлен/изменён скриптом уже после
   загрузки. Решить явно — пересчитывать при мутации `<base>` или
   зафиксировать снимок и записать ограничение (у шима свой пересчёт на
   каждый вызов, так что расхождение вернётся, если здесь взять снимок).
4. Гейт: тест на резолв подресурса при наличии `<base href>` — абсолютного и
   относительного — плюс проверка, что движок и `_lumen_document_base_url()`
   дают одну строку на одной странице.
