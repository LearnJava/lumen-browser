# BUG-722: динамический `<link rel=stylesheet>` не шлёт `load`/`error` — загрузчик, ждущий `link.onload`, висит вечно

**Статус:** FIXED 2026-08-09
**Компонент:** js (`crates/js/src/dom.rs` — `WEB_API_SHIM`, машинерия
`_lumen_resource_*`)
**Найден:** P3, разбор [BUG-703](BUG-703-FIXED.md) (`https://www.tbank.ru/`), 2026-08-09
**Исправлен:** P3, 2026-08-09

## Симптом

`<link rel=stylesheet>`, вставленный скриптом
(`document.createElement('link')` → `head.appendChild`), **загружается и
применяется** — шелл сам собирает href'ы из дерева и вливает лист в каскад, —
но со стороны JS не происходит ничего: ни `load`, ни `error`, ни через
`link.onload`, ни через `addEventListener('load', …)`.

Минимальная проба (страница, `link.href` рядом с ней):

```js
var l = document.createElement('link');
l.rel = 'stylesheet'; l.href = 'b703_link.css';
l.onload = function () { events.push('onload'); };
l.addEventListener('load', function () { events.push('listener-load'); });
document.head.appendChild(l);
```

До фикса через 2 с: `events: []`, при этом `getComputedStyle(target).color`
уже `rgb(1, 2, 3)` из этого самого листа — то есть ресурс получен и применён,
а событие потеряно.

Отдельно (не чинится здесь): `link.sheet` — `undefined`, это CSSOM-пробел
[BUG-471](BUG-471-OPEN.md).

## Почему это ломает страницы

`'onload' in link` возвращает `true`, поэтому фича-детект в коде страниц
выбирает **событийную** ветку, а не таймерный фолбэк. Канонический пример —
загрузчик микроблоков Tramvai (`platform.js`, функция `$d`/`addLink` на
`tbank.ru`):

```js
'onload' in o ? o.onload = a : setTimeout(a, 50)
```

Промис `a` не резолвится никогда. Дальше `resolvePageDeps` ждёт
`Promise.all([стиль, скрипт])` по каждому блоку страницы, и весь клиентский
рендер не начинается — при этом ни исключения, ни отклонённого промиса, ни
строки в консоли. Ровно тот класс тихого отказа, ради которого в BUG-703
пришлось ставить временный `set_promise_reject_callback`.

## Как найден

Трассировщик «зависших» промисов, поднятый в prescript
(`LUMEN_DIAG_PRESCRIPT`): обёртка `Promise.prototype.then`, которая вешает на
каждый промис при первом `.then` пару-наблюдателя, помнит стек места вызова и
через 10/25 с печатает всё, что так и не уселось, сгруппированное по стеку.
На `tbank.ru` дал 277 висящих промисов, из них один кластер в 81 штуку с
общим стеком в `platform.js` — по колонкам стека (`<anonymous>:1:529980`) в
скачанном бандле нашлась ровно функция `$d`. Приём переносимый и дешёвый:
он показывает **место остановки** без бисекции бандла, когда отказ тихий
(ни throw, ни reject). Скрипт — `.tmp/b703_pending.js`.

## Причина

Машинерия BUG-571 («вставленный скриптом элемент делает что-то при
подключении к документу») была написана строго под `<script>`:
`_lumen_script_track` возвращался сразу, если тег не `script`, поэтому
`<link>` вообще не попадал в карту отложенных элементов, и никакой ветки
«обработать связанный ресурс» для него не существовало.

## Фикс

Та же машинерия обобщена с `<script>` на `<script>|<link>`:

- `_lumen_script_pending`/`_lumen_script_track`/`_lumen_script_try_prepare`/
  `_lumen_script_after_insert`/`_lumen_script_is_connected`/
  `_lumen_script_fire` переименованы в `_lumen_resource_*` — карта теперь
  хранит не `true`, а вид элемента (`'script'` | `'link'`), и по нему
  `_lumen_resource_try_prepare` выбирает ветку подготовки. Удаление ключа
  при подготовке по-прежнему играет роль флага «already started», так что
  перемещение уже обработанного элемента по дереву не грузит его повторно.
- Новая `_lumen_link_prepare(nid)` — HTML LS §4.6.7 «process the linked
  resource»: токенизирует `rel`, требует токен `stylesheet`, читает `href`
  (пустой — ни загрузки, ни события), затем через хоп задачи (по той же
  причине, что и внешний `<script>`: `link.onload = …` пишут **после**
  `appendChild`) делает `fetch`, дочитывает тело (нечитанный ответ держит
  свой слот — [BUG-721](BUG-721-FIXED.md)) и шлёт `load`, а на любой отказ
  или не-2xx — `error`.

**Сознательные границы фикса** (описаны комментарием в коде):

- Только `rel=stylesheet`. `preload`/`prefetch`/`icon` не трогаются: чтобы
  дать по ним событие, их пришлось бы самим скачать, а этого страница не
  просила. Проверяется тестом `dynamic_preload_link_fires_nothing`.
- Только элементы, созданные через `createElement`/`createElementNS`, — как
  и у `<script>`; `<link>` из разметки обрабатывает парсер, и его события
  сюда не относятся.
- `fetch` — второй запрос за тем же URL (тёплый по HTTP-кэшу), а не отчёт
  загрузчика каскада: шелл пересобирает href'ы по всему дереву
  (`main.rs::collect_link_hrefs`) и не имеет сигнала завершения по узлу.
  Поэтому `load` здесь значит «байты приехали», а не «лист в каскаде», —
  ровно то же приближение, что уже делает путь внешнего `<script>`.

## Проверка

Юнит-тесты (`crates/js/src/dom.rs`, `dom::tests`), 4/4 зелёные —
`cargo test -p lumen-js --features v8-backend --lib -- stylesheet_link preload_link`:

- `dynamic_stylesheet_link_fires_load` — `load` доходит и до IDL-атрибута, и
  до слушателя (счётчик 2);
- `dynamic_stylesheet_link_fires_error_on_http_failure` — 404 даёт `error`, а
  не зависание;
- `dynamic_preload_link_fires_nothing` — граница скоупа;
- `detached_stylesheet_link_loads_only_once_connected` — собранный отдельно
  `<link>` грузится ровно тогда, когда поддерево подключают к документу, и
  не грузится, пока он вне документа.

Живая страница `https://www.tbank.ru/` (`.tmp/probe703.py`, срез через 30 с
после `document_ready`): React-узлов **10 → 105**, React-контейнеров 1 → 2,
`.application.innerHTML` 77 → 5550 символов — главный корень наконец
монтируется. Висящих промисов по трассировщику **277 → 25**, кластер из 81
исчез целиком. До эталонных 2380 узлов Edge всё ещё далеко —
[BUG-703](BUG-703-FIXED.md) остаётся открытым, остаток описан там.

## Смежное, здесь не чинится

На странице по схеме `file://` этот путь шлёт `error` вместо `load`: шимовый
`fetch` не умеет `file://` и вдобавок теряет двоеточие диска
(`file://D/RustProjects/...` в тексте ошибки) — при том, что сам лист шелл
загружает и применяет. Пробел не новый и не привнесён этим фиксом: внешний
динамический `<script>` на локальной странице падает там же и по той же
причине (общий `_url_resolve` + `fetch`). Заведено отдельно —
[BUG-723](BUG-723-OPEN.md).
