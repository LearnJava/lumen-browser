# BUG-307: UI-поток «не отвечает» на тяжёлых вкладках; сессия умирает необратимо

**Статус:** OPEN
**Дата:** 2026-07-17
**Компонент:** shell (main thread) / ADR-016 (границы off-thread не покрывают этот путь)
**Найден:** живой перф-аудит `/lumen-perf-audit`; «приложение не отвечает» видел пользователь вживую

## Симптом

Метрика IsHungAppWindow (та же эвристика, по которой Windows пишет
«Не отвечает») в живом прогоне 14 вкладок (docs/perf/runs/2026-07-17-live.json):

```
lenta  hung=2.5с
ria    hung=39.0с   (окно висело всё время обработки после загрузки)
rbc    hung=47.5с   ready=23.4с
stackoverflow / habr — окно зависло НЕОБРАТИМО (даже navigate/new_tab
  отваливаются по «automation command timed out») → авторестарт харнесса
```

В прогоне без рестартов (2026-07-17, первый live-прогон): после
github (2.1 ГБ) + stackoverflow (3.4 ГБ) окно умерло навсегда — habr, mdn,
rbc не загрузились вовсе (TIMEOUT 240с каждый), хотя поодиночке эти сайты
грузятся за секунды. Для пользователя это «браузер завис, надо убивать
процесс» — худший класс UX-дефекта.

## Наблюдения

- Корреляция с RAM: необратимое зависание наступает после вкладок-гигантов
  (BUG-306); после авторестарта окна те же сайты грузятся нормально
  (crates 1.7с, docs-rs 1.1с, mdn 3.2с).
- Обратимые зависания (39–48 с на ria/rbc) — похоже на длинные синхронные
  участки на main thread (paint/layout/JS-дренаж), несмотря на влитые
  ADR-016 M0–M4 (off-thread layout/render существуют — проверить, какие
  пути всё ещё блокируют event loop).

## Ожидание

UI-поток не блокируется дольше сотен миллисекунд независимо от тяжести
вкладки; деградация допустима (janky-кадры), смерть сессии — нет.
Возможно нужен watchdog + принудительная выгрузка вкладки-агрессора.

## Диагностика

`LUMEN_FRAME_LOG=1` + Tracy на живом окне github→stackoverflow;
`scripts/perf_audit.py --only github --only stackoverflow --only habr`
воспроизводит за ~5 минут (колонка «не отвечает, с» в сводке).

## Повторный прогон 2026-07-20

Воспроизводится после S12b-18/BUG-297/316/308: два независимых полных
прогона корпуса (`docs/perf/runs/2026-07-20-live.json`, движок `a014c9e6`),
в обоих github.com HUNG → авторестарт харнесса; во втором прогоне
habr.com тоже HUNG → авторестарт (ранее в стабильном режиме habr грузился).
В первом прогоне (сразу после `cargo build`, машина была под нагрузкой
антивируса на свежий бинарник — см. ниже) зависания были тяжелее: после
github-рестарта crates/habr/rbc не смогли получить даже новую вкладку
(`Navigate error: automation command timed out`, «без вкладки» в сводке) —
это утяжелённый вариант того же необратимого каскада, а не новый класс
дефекта. Второй прогон (тёплый бинарник, чуть более спокойная машина)
восстанавливался штатно после github-рестарта — crates/docs-rs/stackoverflow
после него снова OK, что подтверждает наблюдение «после авторестарта
сайты грузятся нормально» из первого репорта.

**Важная методологическая находка:** оба прогона 2026-07-20 показали
равномерно завышенное время готовности (`ready_s`) почти на всех сайтах
относительно `2026-07-17-live.json` (+56%…+1290%, включая тривиальные
example.com/hn.com). Проверено headless `--phases` на crates.io/docs.rs
изолированно — там всё быстро и в норме (screenshot totals 1.8с),
т.е. это НЕ регрессия движка, а шум самого живого многовкладочного
харнесса (машина только что закончила 13-минутную сборку; плюс сама
конструкция кумулятивной RAM/множества вкладок в одном окне не даёт
чистого per-site таймингa). Живой Δ%-сравнение по `ready_s` признано
непригодным для детекции регрессий — использовать `--phases` для этого
впредь, живой прогон — только для RAM/hung/JS-ошибок/визуальной приёмки.

## Срез 2026-08-05 (P3) — минимальный однотабовый репро, не требует мульти-таб RAM-давления

Найдено при попытке измерить остаток BUG-286 (`content-visibility` scroll-стопор)
живым скроллом на ria.ru: скролл вообще не понадобился — окно стало полностью
неотзывчивым на любую automation-команду (`scroll`, `eval`) уже через ~1с
после `[bench] first non-empty frame`, на **одной свежей вкладке**, без
предшествующих тяжёлых вкладок (github/stackoverflow из прежних прогонов).
Это меньший и куда более быстрый репро, чем 14-вкладочный `/lumen-perf-audit`,
описанный выше.

**Как воспроизвести** (одна команда, `--mcp-live-port`, без предварительных
вкладок):

```
target/dev-release/lumen.exe --mcp-live-port <port> about:blank
# navigate → https://ria.ru
# wait document_ready, дождаться "[frame:cold-start] RenderDone" в stderr (~9-10с)
# любая automation-команда (scroll/eval) после этого: "automation command timed out"
```

**Замеры этого среза:**

- `TotalProcessorTime` процесса (PowerShell `Get-Process`) абсолютно плоский
  все 15+с окна зависания (5250мс, ни на мс не растёт) — **не busy-loop**
  (0% CPU), а настоящий deadlock/parked-без-пробуждения: ни таймеры JS
  (виден периодический `cm.ria.ru/chat/info`-поллинг каждые ~10с ДО зависания,
  ноль повторов ПОСЛЕ), ни сеть, ни фреймы не идут вообще.
- 5 последовательных `eval` попыток по 30с (`AutomationHandle::DEFAULT_TIMEOUT`,
  `crates/driver/src/live_session.rs:38`) — **все 5 таймаутят**, т.е. окно
  не отвечало ≥150с непрерывно на одной вкладке без какого-либо давления
  памяти от других вкладок. Это дольше, чем «обратимые 39-48с» из прогона
  2026-07-17 — возможно, дело не в объёме памяти корпуса, а в чём-то
  специфичном для конкретной страницы/сессии (см. ниже).
- **Проверено и отклонено:** `LUMEN_NO_ENGINE_THREAD=1` (откат ADR-023,
  синхронный layout на UI-потоке) — зависание воспроизводится идентично,
  то есть корень НЕ во флипе движкового потока 2026-07-28.
- **Контрольный тест:** тот же automation-канал (scroll/eval) на локальной
  статической странице (`samples/page.html`) после явного 15-секундного
  простоя (специально дольше, чем реальный idle-park происходит на живом
  окне) отвечает моментально (1-5мс) — то есть штатное `ControlFlow::Wait`
  парковка + `EventLoopProxy`-пробуждение (`AutomationHandle::execute`,
  `crates/driver/src/automation.rs:79-83`) работают исправно там, где нет
  фоновой JS/сетевой активности реальной страницы. Зависание — не общая
  регрессия механизма парковки/пробуждения, а нечто, специфичное для
  состояния, в которое попадает вкладка именно на ria.ru (или похожих
  сайтах с фоновыми таймерами/service-worker-подобной активностью).
- **Побочное наблюдение по логу** (не проверено как причина): непосредственно
  перед зависанием страница успевает залогировать `### Service worker
  register` (собственный `console.log` страницы) и тут же поймать
  `fetch error: invalid url: invalid url: missing scheme:
  "/firebase-messaging-sw.js"` — паттерн той же семьи багов, что
  BUG-346/347/359/362/370 (относительные URL не резолвятся) и особенно
  **BUG-638** (`<audio>.src` с относительным URL перманентно вешает
  JS-движок/automation-канал: нативный вызов никогда не возвращается в JS,
  ноль вывода в консоли, 0% CPU) — тот же класс симптома («нативный вызов
  из JS не возвращается, канал глохнет насмерть, без единой ошибки в
  консоли»), возможно тот же корень применительно к попытке service-worker
  fetch с относительным URL вместо `<audio>`. Не подтверждено — нужен
  дебаггер/трасса конкретно этого пути (`navigator.serviceWorker.register`
  → внутренний fetch), это следующий шаг для того, кто продолжит.

**Вывод для приоритизации:** пока не закрыт этот баг, любая работа над
BUG-286/«Задачей 3» (частичный пересчёт каскада, `docs/tasks/p3-cascade-perf.md`)
бессмысленна на этом конкретном сайте — страница не доживает до состояния,
где ~1с cascade-стопор вообще успевает стать заметным на фоне полной,
судя по всему необратимой (в пределах ≥150с) неотзывчивости. BUG-307
переоценён этим срезом с «UX-дефект под RAM-давлением многих вкладок» на
«воспроизводится тривиально на одной свежей вкладке одного конкретного
реального сайта» — не изучено, обобщается ли на другие сайты с похожими
паттернами (SW-регистрация/относительные fetch-URL) или это узко про
ria.ru. Скрипт репро (не закоммичен, disposable) описан выше и
восстанавливается по любому МCP-клиенту из `scripts/mt_stall_bench.py`.
