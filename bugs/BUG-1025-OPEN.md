# BUG-1025 — `<img src="data:image/svg+xml,...">` не всегда даёт `load`: `svg-in-img-auto.html` виснет на первом сабтесте до 60-секундного тайм-аута

**Статус:** OPEN
**Заведён:** 2026-09-07 (P2, WPT-RUN-7 срез 22 — локализация ресурсного механизма BUG-1011,
побочная находка на файле, ранее не изолированном тем баг-репортом)
**Область:** `svg-embedded-sizing.js` (`tests/wpt/html/rendering/replaced-elements/`) строит
`<img>` с `src="data:image/svg+xml,<svg .../>"` и вешает `placeholder.addEventListener('load', …)`
(`svg-sizing.js:284` окрестность) — событие `load` для этого конкретного `<img>` не приходит
(или приходит не для первой сгенерированной комбинации), из-за чего вся последовательная цепочка
сабтестов (каждый следующий стартует только из колбэка `checkSize`/`cont(id+1)` предыдущего)
блокируется на первом же сабтесте
**Владелец:** P1/P3

## Симптом

Изолированный прогон одного файла (`run_smoke.py`, `target/dev-release/lumen`, dev-release),
3/3 повтора подряд, **100 % детерминировано**:

```
TEST_START: /html/rendering/replaced-elements/svg-embedded-sizing/svg-in-img-auto.html
… (ровно 60.16 с спустя) …
TEST_END: Test TIMEOUT. Subtests passed 0/1. Unexpected 0
```

`0/1` — не «0 из многих», а признак того, что харнесс успел зарегистрировать (`async_test(...)`)
ровно один сабтест и застрял на нём: `testPlaceholderWithHeight("img", null)`
(`svg-in-img-auto.html`) генерирует комбинации размеров цепочкой (следующий `async_test`
создаётся только из колбэка предыдущего — `checkSize` → `cont(id+1)`, см.
`svg-embedded-sizing.js`), поэтому зависание первого `<img>`-плейсхолдера на `load` останавливает
весь файл, а не один сабтест из многих.

Все три изолированных прогона заняли одинаковые ~70–72 с суммарно (~16 с CPU, ~26 % загрузки —
т.е. большая часть времени процесс простаивает в ожидании, а не считает), что соответствует
`<meta name=timeout content=long>` (60 000 мс) + обвязка `run_smoke.py`.

## Почему это важно

1. Отдельный, ранее не задокументированный движковый гэп: `<img>` с `data:image/svg+xml,...`
   URI не гарантированно получает `load`. Тот же класс дефекта, что [BUG-999](BUG-999-OPEN.md)
   (там — программно вставленный `<iframe src>` не даёт `load`), но другой элемент/URI-схема.
2. Побочный эффект на диагностику WPT-RUN-7: этот файл лежит в той же директории
   (`replaced-elements/svg-embedded-sizing/`), что и уже известные из
   [BUG-1011](BUG-1011-OPEN.md) `svg-in-iframe-{auto,fixed}.html` (детерминированные ~31–38 с,
   72 реальных FAIL по раскладке, не TIMEOUT). В общем прогоне категории (`--check`,
   один и тот же persistent-процесс `lumen` на директорию/шард) все три файла подряд отъедают
   у своего воркера ~23 с + ~60 с ≈ 85 с почти без прогресса — см. §Локализация (2026-09-07,
   срез 22) в BUG-1011 для точной раскладки по `--log-raw`-таймлайну одного воркера.

## Воспроизведение

```
LUMEN_PROFILE=dev-release tests/wpt/.venv/bin/python tests/wpt/run_smoke.py \
  --binary target/dev-release/lumen \
  /html/rendering/replaced-elements/svg-embedded-sizing/svg-in-img-auto.html
```

Читать `TEST_END: Test TIMEOUT. Subtests passed 0/1` — детерминировано на 3/3 запусках.

## Что не проверялось

- Не локализовано до конкретного call site в `lumen-net`/`lumen-dom`/парсере `data:`-URI:
  не проверено, парсится ли вообще `data:image/svg+xml,<svg .../>` в валидный образ (в отличие
  от `data:image/svg+xml;base64,...`, эта ветка без base64-энкодинга, с сырым XML после запятой,
  требующим URL-декодирования содержимого) — гипотеза «URI не декодируется/не распознаётся как
  SVG» не проверена ни против «декодируется, но `load` просто не диспатчится для inline `<img>`».
- Не проверено, воспроизводится ли на других файлах той же генерируемой серии с другим
  `placeholder` (`svg-in-object-auto.html` и т.п., см. `gen-svgsizing-tests.py` в шапке файла) —
  если да, это подтверждает «класс URI», если нет — сужает до чего-то специфичного для `<img>`.
- Baseline `html/rendering` не содержит этот файл как `expected: TIMEOUT` — категория целиком
  всё ещё не закоммичена из-за [BUG-1011](BUG-1011-OPEN.md).
