**Компонент:** canvas (`crates/engine/canvas/src/color.rs:23-83` — `CanvasColor::from_css_str`),

**Найден:** 2026-07-28 (P2), WPT-VENDOR-html-canvas — доминирующий класс отказов среза
**Перепроверен:** 2026-07-29 на main — воспроизводится; режим отказа уточнён ниже

## Симптом

`Context2D` не пользуется CSS-парсером движка, а имеет свой:

```rust
// crates/engine/canvas/src/color.rs:23-38
/// Parse a CSS color string.  Supports:
/// `#rrggbb`, `#rgb`, `rgb(r,g,b)`, `rgba(r,g,b,a)`, named colors.
pub fn from_css_str(s: &str) -> Option<Self> { … }
```

Доккомментарий честен — это и есть весь список. Проба (`--dump-layout`; база заливается
непрозрачным синим, маркером ставится `fillStyle='#f00'`, затем испытуемое значение и
один `fillRect` — четыре исхода различимы по пикселю):

| Значение | Пиксель | Вердикт |
|---|---|---|
| `#0f0`, `lime`, `rgb(0,255,0)` | `0,255,0,255` | принято |
| `#00ff0080` | `0,128,126,255` | принято, альфа работает |
| `rgba(0,255,0,0.5)` | `0,127,127,255` | принято, альфа работает |
| `rgba(0,255,0,0)`, `transparent` | `0,0,255,255` | принято |
| **`hsl(120,100%,50%)`** | `255,0,0,255` | **ОТВЕРГНУТО** |
| `hsl(120 100% 50%)` | `255,0,0,255` | ОТВЕРГНУТО |
| `rgb(0 255 0)` | `255,0,0,255` | ОТВЕРГНУТО |
| `rgb(0% 100% 0%)` | `255,0,0,255` | ОТВЕРГНУТО |
| `hwb(120 0% 0%)` | `255,0,0,255` | ОТВЕРГНУТО |
| `oklch(0.87 0.29 142)` | `255,0,0,255` | ОТВЕРГНУТО |
| `color(srgb 0 1 0)` | `255,0,0,255` | ОТВЕРГНУТО |
| `color-mix(in srgb, lime, lime)` | `255,0,0,255` | ОТВЕРГНУТО |
| `currentColor` | `255,0,0,255` | ОТВЕРГНУТО |

**Режим отказа (уточнено 2026-07-29, отдельной пробой).** Отвергнутое значение не
даёт ни исключения, ни отката в чёрный: рисование продолжается **предыдущим**
цветом. Проверено так — база `#ff0000` на весь холст, затем испытуемое значение и
`fillRect` того же прямоугольника:

```
D in="hsl(120,100%,50%)"  px=255,0,0,255   get=hsl(120,100%,50%)
D in="rgb(0 255 0)"       px=255,0,0,255   get=rgb(0 255 0)
D in="oklch(0.5 0.1 200)" px=255,0,0,255   get=oklch(0.5 0.1 200)
D in="not-a-color"        px=255,0,0,255   get=not-a-color
D in=""                   px=255,0,0,255   get=
```

Для по-настоящему невалидного значения (`not-a-color`, `''`) это ровно то, чего
требует спека. Вредно оно для **валидных, но не поддержанных** форм (`hsl()`,
пробельный `rgb()`, Color 4): страница получает не свой цвет и никакого сигнала об
ошибке. Обе таблицы ниже (и прежняя проба, и прогон WPT) читают именно этот эффект —
«красный маркер» в них и есть удержанный предыдущий цвет, а не откат в чёрный.

Отдельно от Color 4: **`hsl()`/`hsla()` не поддержаны вовсе**, ни в запятой, ни в
пробельной форме — это не экзотика уровня `oklch`, а синтаксис из CSS 2.1, массовый на
реальных сайтах. `globalAlpha` и альфа цвета работают (`globalAlpha=0.5` над синим даёт
`0,127,127,255`) — сломан именно разбор строки.

## Симптом 2: `fillStyle` не валидируется и не сериализуется

Геттер отдаёт **ровно ту строку, что записали**, включая заведомо невалидную:

```
ctx.fillStyle = '#0F0';          ctx.fillStyle  →  '#0F0'    (спека: '#00ff00')
ctx.fillStyle = 'rgba(0,255,0,0.5)';  →  'rgba(0,255,0,0.5)' (спека: 'rgba(0, 255, 0, 0.5)')
ctx.fillStyle = 'not-a-color';   ctx.fillStyle  →  'not-a-color'
```

HTML LS §4.12.5.1.3 требует: невалидное значение **игнорируется** (атрибут сохраняет
предыдущее), валидное — сериализуется канонически (`#rrggbb` строчными, либо
`rgba(r, g, b, a)` при альфе < 1). Сейчас атрибут — просто поле-строка: рисование
использует результат разбора, а чтение — исходный текст, поэтому запись мусора и
читается как мусор. Это отдельно от таблицы выше: из-за него падают все
`_assertSame(ctx.fillStyle, old)` в `element/the-canvas-state` и вся серия
`2d.fillStyle.parse.*` даже там, где цвет всё-таки закрашен верно.

## Направление починки — парсер уже есть в графе зависимостей

`lumen-canvas` **уже зависит от `lumen-layout`** (`crates/engine/canvas/Cargo.toml:11`),
а в `lumen_layout::style::parse_color` (`style.rs:21822`) лежит полный CSS-парсер цвета:
именованные, hex, функциональные формы, `hwb`/`lab`/`lch`/`oklab`/`oklch`/`color()` и
`color-mix()` (модуль `color_mix.rs`). То есть починка — не «написать парсер Color 4», а
**удалить дублирующий и вызвать существующий**, сконвертировав `Color → CanvasColor`.
Тот же приём закрывает `strokeStyle`, `shadowColor` и `addColorStop`, которые все
вызывают `CanvasColor::from_css_str` (`crates/js/src/canvas2d.rs:421,431,654,753,1448,…`).

Отдельная часть (в `dom.rs`, не в парсере): сделать `fillStyle`/`strokeStyle` настоящими
аксессорами — сеттер разбирает и при неудаче **не меняет** состояние, геттер отдаёт
каноническую сериализацию.

## Исправлено 2026-08-30 (P3)

Взято направление из раздела выше: дублирующий парсер **удалён**, а не дописан.
`CanvasColor::from_css_str` — теперь обёртка в две строки над
`lumen_layout::parse_color`, то есть Canvas 2D разбирает цвет ровно тем же кодом,
что и каскад. Все формы из таблицы симптома приняты (проба «после» ниже).

`fillStyle`/`strokeStyle`/`shadowColor` стали настоящими аксессорами: натив
возвращает **каноническую сериализацию** принятого цвета либо `undefined`, а шим
на `undefined` не трогает ни атрибут, ни растеризатор — то есть невалидное
значение игнорируется обеими сторонами сразу, а не «атрибутом отдельно, цветом
отдельно», как было.

### Проба «до» нашла шесть дефектов вместо двух заявленных

Прогонялась таблицей входов через `CanvasColor::from_css_str` до правки; каждый
кандидат на панику — в своём потоке, чтобы одна не унесла пробу целиком.

1. **`ctx.fillStyle = 'rgb('` роняет процесс.** `&sl[4..sl.len() - 1]` при
   `len == 4` даёт диапазон `4..3` — паника среза. То же у `'rgba('`. Строка
   приходит со страницы, то есть это страница-контролируемая паника в
   production-коде (запрещена политикой проекта).
2. **`#±a` роняет `parse_hex_color` — и не в canvas, а в `lumen-layout`.**
   Длина hex-хвоста считается в БАЙТАХ, срезы идут байтовыми индексами, поэтому
   один не-ASCII символ проходит проверку длины и рвёт границу UTF-8. Достижимо
   из любого `style` страницы, а не только из Canvas 2D; закрыто там же одной
   проверкой `is_ascii_hexdigit` до всех веток.
3. **`#rgba` (четырёхзначный hex) отвергался** — CSS Color 4 §5.2, в таблице
   заявки его не было.
4. **Именованных цветов было 20 из 148**: `rebeccapurple` → отказ. Доккомментарий
   старого парсера обещал «named colors» без оговорок.
5. **`rgb(-5, 300, 0)` отвергался** вместо клампа в `rgb(0, 255, 0)`.
6. **Альфа квантовалась усечением, а каскад — округлением**: `rgba(…, 0.5)`
   давал `a = 127` в canvas и `a = 128` в стиле. Один и тот же CSS — два разных
   цвета в зависимости от того, кто его прочитал.

### Сериализация альфы

Альфа хранится байтом, а §4.12.5.1.3 сериализует её числом 0–1, поэтому прямое
`a / 255` дало бы `0.502` там, где `2d.fillStyle.get.halftransparent` требует
ровно `0.5`. Печатается **кратчайшая десятичная дробь, которая обратно даёт тот
же байт** (128 → `0.5`, 115 → `0.45`). Тест гоняет все 256 значений через круг
«сериализация → разбор».

### Попутно

- `parse_color` научился `hwb()` — этой функции не было **нигде** в движке
  (обратные конверсии в `color_mix.rs` были, но приватные и только для
  смешивания), то есть закрыт и CSS-путь, а не только canvas. Относительная форма
  `hwb(from …)` отвергается **явно**: `MixColorSpace::Hwb` не поддержан в
  `relative_origin_channels`, и вариант `ColorFn` молча давал бы неверный цвет.
- `parse_color` научился `color()` — он был доступен только каскаду, через
  `CssColor::Wide`, то есть недостижим для потребителя без `CssColor`.
- У 2D-контекста `OffscreenCanvas` появились геттеры `fillStyle`/`strokeStyle` —
  их не было вовсе, атрибут читался как `undefined`.
