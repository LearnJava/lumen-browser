# BUG-734: `<img>` игнорирует intrinsic-соотношение, если сторона задана из CSS

**Статус:** FIXED 2026-08-09
**Компонент:** layout (`crates/engine/layout/src/box_tree.rs` — ветка
`is_image_element` в `build_box_kind`, auto-ширина замещаемого элемента в
`lay_out_inner`)
**Найден:** P3 при разборе [BUG-733](BUG-733-OPEN.md), 2026-08-09

## Симптом

Задать `<img>` одну сторону из CSS и оставить вторую `auto` — и картинка
получает не пропорциональный, а **сырой intrinsic-размер по второй оси**:
`width: 100px; height: auto` на картинке 852×725 давало `100×725` вместо
`100×85`. Вертикальное растяжение в 8.5 раза; на реальной странице такая
картинка либо расползается на весь экран, либо (если intrinsic-размер ещё
неизвестен) схлопывается в нулевую высоту и выглядит как «браузер не показывает
картинки».

Под это попадает и самый частый в вебе responsive-идиом — `max-width: 100%;
height: auto`.

## Сверка с эталоном (headless Edge, картинка 852×725)

| CSS на `<img>` | Edge | Lumen до | Lumen после |
|---|---|---|---|
| `max-width: 100%` (контейнер 100px), `height: auto` | 100×85 | 100×725 | 100×85 |
| `width: 100%` (контейнер 100px), `height: auto` | 100×85 | 100×725 | 100×85 |
| `width: 100px; height: auto` | 100×85 | 100×725 | 100×85 |
| `height: 100px; width: auto` | 118×100 | 852×100 | 117.5×100 |
| без CSS | 852×725 | 852×725 | 852×725 |
| `max-width: 100%` (контейнер 100px), высота не объявлена | 100×85 | 100×725 | 100×725 → [BUG-735](BUG-735-OPEN.md) |

Последняя строка — **не** этот дефект: Edge даёт 100×725 ровно так же, если
атрибуты `width`/`height` у элемента действительно есть (проверено
`<img width="852" height="725" style="max-width:100%">` → 100×725). Расхождение
там в том, что Lumen эти атрибуты **сам дописывает** в DOM; провенанс — своя
заявка.

## Механизм

Intrinsic-размер приезжает в layout единственным путём: shell декодирует
картинку и `apply_intrinsic_size` (main.rs) дописывает `<img>` пустые атрибуты
`width`/`height`, а `apply_image_presentational_hints` (style.rs) кладёт их в
`style.width`/`style.height` как presentational hint до каскада. Дальше
`build_box_kind` **повторно** подставлял те же значения уже ПОСЛЕ каскада —
`if style.width.is_none() { … }` / `if style.height.is_none() { … }` — из
`ImageSource::intrinsic_*` (их наполняет `pick_img_source` →
`fill_intrinsic_dims` из тех же атрибутов).

Два следствия:

1. **Авторский `auto` проигрывал hint-у.** `height: auto` каскад корректно
   переводил в `None`, но пост-каскадная подстановка возвращала сырые 725 —
   presentational hint (specificity 0) перебивал author-объявление, чего сам
   комментарий рядом обещал не делать.
2. **Соотношения не было вовсе.** Даже без (1) вторая сторона считалась бы как
   0: intrinsic ratio нигде не участвовал в расчёте размера. Единственный
   ratio-код — `apply_intrinsic_size` в shell ([BUG-269](BUG-269-FIXED.md)) —
   считает недостающую сторону **из HTML-атрибутов**, то есть закрывает только
   случай «автор задал размер атрибутом», а не «автор задал размер из CSS».
   Реальные страницы задают размер картинок исключительно из CSS.

## Фикс

Соотношение доставляется в расчёт как `style.aspect_ratio` — это ровно то, что
говорит CSS Sizing L4 §4.1: на замещаемом элементе initial-значение
`aspect-ratio: auto` означает «использовать intrinsic ratio». Поэтому в ветке
`is_image_element`:

* известны обе стороны intrinsic → `style.aspect_ratio` заполняется
  (`(iw, ih)`), но **только если автор не задал свой** — author-ский
  `aspect-ratio` выигрывает;
* сырое значение подставляется теперь ровно в одном случае «обе стороны auto» и
  только в ширину; высоту из неё выводит ratio-ветка — и выводит **после**
  клампа `min-`/`max-width`, из-за чего `max-width: 100%` наконец пересчитывает
  высоту;
* известна одна сторона (`<source width>` без `height`) → ratio не построить,
  поведение прежнее.

Высоту при `height: auto` считает уже существующая ветка
`else if let Some((aw, ah)) = s.aspect_ratio` в расчёте высоты блока — новый код
там не понадобился. Симметричный случай «`width: auto` + заданная высота»
добавлен в auto-ширину замещаемого элемента (`is_replaced`), где раньше
безусловно стоял `0.0`; считается в border-box пространстве — так же, как
соседняя ratio-ветка высоты.

## Проверка

* 7 юнит-тестов `bug734_*` в `box_tree.rs` — все шесть форм из таблицы выше плюс
  «intrinsic неизвестен → коробка нулевая, как раньше».
* `lumen-layout` целиком: 3521 тест (было 3514 + 7 новых), 0 падений.
* `dump_golden.py` 12/12 без изменений.
* `--dump-display-list` по всем **174** страницам (`graphic_tests/*.html` +
  `samples/*.html`) до и после — дампы **побайтово идентичны**: корпус
  графических тестов этот идиом не покрывает вовсе (везде либо оба атрибута
  заданы, либо обе стороны auto). Полный визуальный прогон поэтому не мог дать
  другого результата. Обратная сторона — регресс этого поведения корпус не
  поймает; добавление кейса в `18-images.html` оставлено отдельной задачей.
* Отдельно проверено, что расчёт картинки как flex-элемента не сдвинулся:
  дампы baseline и фикса на flex-странице совпадают (сам по себе он неверен —
  [BUG-736](BUG-736-OPEN.md), но это не регресс).

## Что этот фикс НЕ закрывает

им никогда не сообщается intrinsic-размер — [BUG-735](BUG-735-OPEN.md).
