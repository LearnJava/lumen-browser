# BUG-1062 — сломанный gdigrab-захват рапортуется как массовая регрессия рендера (155/156 FAILED), а не как невалидный прогон

**Статус:** FIXED 2026-09-23 (P3)
**Тип:** дефект реализованного кода — `run.py` продолжает прогон после `ERROR` на калибровочном TEST-00, хотя без crop-offset все последующие сравнения заведомо бессмысленны.
**Заведён:** 2026-09-19 (замер «можно ли заменить ffmpeg-захват снимками Lumen», контрольный gdigrab-прогон)
**Область:** тулинг графических тестов (`graphic_tests/run.py` — калибровка TEST-00, `_load_crop_offset`/`_save_crop_offset`)
**Владелец:** P2.

## Симптом

gdigrab-прогон, запущенный из процесса вне foreground-цепочки Windows
(фоновая задача), дал:

```
1/156 tests ERRORED (снимок/ffmpeg/IPC): 00
155/156 tests FAILED: 01, 02, 03, ... 156
```

с диффом 92–100 % на каждом тесте и десятками строк
`KNOWN_DEBTORS РЕГРЕССИЯ: 99.93% > baseline 3.02%`. Окно Lumen при этом
показывало только фон страницы — сплошной синий прямоугольник без
содержимого (подтверждено скриншотом пользователя; заголовок окна —
`Lumen — 152 grid place content`, то есть страницы грузились).

Тот же бинарник, запущенный из foreground-процесса, даёт
`TEST-00: PASS (0.00%)`, а полный прогон — штатные `12/156 FAILED`
и `46 known-debtor`. То есть регрессии рендера не было вовсе.

## Причина

Две независимые части.

**1. Окно без нормальной презентации.** Окно, созданное процессом вне
foreground-цепочки, не получает корректной презентации, а `gdigrab` снимает
**экран**, а не фреймбуфер приложения. Отсюда пустой кадр. Это внешнее по
отношению к раннеру ограничение способа захвата, а не дефект движка.

**2. Диагностика раннера вводит в заблуждение — это и есть баг.** TEST-00
существует ровно для того, чтобы найти магента-маркеры и вычислить
crop-offset. При его `ERROR` offset не определён (или взят устаревшим из
сохранённого файла), поэтому каждый следующий тест кропает не ту область и
сравнивает мусор. Раннер тем не менее прогоняет все 155 оставшихся тестов
и печатает их как провалы тестов, включая срабатывания debtor-ратчета —
формулировка «РЕГРЕССИЯ 99.93 % против baseline 3.02 %» прямо предлагает
неверный вывод. Отличить это от настоящей массовой регрессии можно только
по строке ERROR на TEST-00, потерянной среди 155 строк FAIL.

Цена ошибки высокая и уже задокументирована на соседнем классе: в
`bugs/BUG-103-OPEN.md` «99.53 %» пришлось задним числом опознавать как
`blank-gdigrab артефакт`, а в `BUG-099` один из прогонов дал «ложные 100 %,
desktop focus увели во время gdigrab».

## Ожидание

`ERROR` на TEST-00 обрывает прогон немедленно с явным сообщением вида
«калибровка не удалась — захват сломан, результаты невалидны», без 155
бессмысленных сравнений и без единого срабатывания debtor-ратчета.

## Как чинить

1. Провал калибровки → немедленный выход с ненулевым кодом и внятной
   причиной; `--continue-on-fail` этого **не** переопределяет (он про
   провалы тестов, не про сломанный инструмент).
2. Не подставлять сохранённый crop-offset из прошлого прогона, когда
   калибровка текущего провалилась, — либо offset получен сейчас, либо
   прогона нет.
3. Дешёвая страховка от того же класса: если подряд N тестов дают дифф
   > ~90 %, это сломанный захват, а не регрессия — прервать с тем же
   сообщением.

Связано: BUG-1061 (тот же прогон, другой класс отказа тулинга); режим
`--ipc` этой ловушки не имеет вовсе (снимок приходит от (0,0), калибровка не
нужна) — задача TEST-9.

## Исправлено

В основном цикле `run.py` (`graphic_tests/run.py`, main()) сразу после
формирования `entry`/`status` для очередного теста:

1. **Провал калибровки останавливает прогон немедленно.** Если `tid == '00'`
   и `status == 'ERROR'` (магента-маркер не найден — `find_marker_origin`
   вернул `None`), раннер печатает явное сообщение («захват сломан,
   результаты невалидны») и возвращает код `1`, минуя проверку
   `args.continue_on_fail` — этот флаг гасит только обычные провалы тестов,
   не провал инструмента. Поскольку функция выходит сразу, ни один из
   оставшихся 155 тестов не запускается — тем самым закрыт и пункт 2 «как
   чинить»: подставлять стейл-offset из `crop_offset.txt` больше некому,
   потому что раннер не доходит до следующего теста в принципе.
2. **Страховка на случай, когда TEST-00 сам не даёт `ERROR`** (например,
   живое окно без сбоя gdigrab-снимка, но с пустым/чужим кадром экрана —
   маркер найден на неверных координатах и дальше высокий дифф идёт по всем
   тестам без единого явного `ERROR`): счётчик `consecutive_high_diff`
   считает тесты подряд с `pct >= 90.0`; при достижении
   `BROKEN_CAPTURE_STREAK = 5` прогон обрывается тем же способом (код `1`,
   сообщение, не переопределяется `--continue-on-fail`).

Оба пути перед выходом сохраняют уже накопленные `results` через
`save_results()` (если это полный прогон, не `--only`/`--bisect`) — частичный
`latest.json` виден для диагностики, но код возврата `1` и явный текст не
дают принять его за «всё прошло».

Изменение — только в Python-тулинге (`graphic_tests/run.py`), движка не
касается: правка проверена разбором `ast.parse` и `python run.py --help`
(живой прогон 20-минутного пайплайна для проверки самого тулинга не
запускался — воспроизвести исходный симптом можно только сломанным
захватом, который является внешним по отношению к раннеру условием).
