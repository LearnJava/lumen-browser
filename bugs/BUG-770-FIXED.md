# BUG-770 — живое окно намертво встаёт на 24-й странице прогона графтестов: харнесс перестал читать stderr, труба заполнилась, `eprintln!` заблокировал UI-поток

**Статус:** FIXED 2026-08-12
**Компонент:** test-harness (`graphic_tests/run.py`, `LiveWindowClient.__init__` /
`_drain_stderr`) — первичная причина; shell/paint (запись в stderr с UI-потока) — вторичная
устойчивость
**Найден:** 2026-08-12 (P3), при попытке снять пиксельный гейт полного прогона графтестов для
[BUG-405](BUG-405-OPEN.md) срез 5
**Починен:** 2026-08-12 (P3), ветка `p3-bug-770` — обе половины, см. «Что сделано»

## Симптом

`python graphic_tests/run.py --continue-on-fail` (live-режим, дефолт) доходит до TEST-22 и
встаёт: **окно перестаёт отвечать вообще** (это видно и глазами — пользователь сообщил
«приложение зависает и не отвечает… зависло на тесте 22 transform»), а прогон печатает

```
TEST-22: PASS (0.00%)
TEST-23: ERROR (live: tools/call: {'code': -32603, 'message': 'Wait error: automation command timed out'})
TEST-24: ERROR (live: … 'Navigate error: automation command timed out'})
…
TEST-153: ERROR (live: [WinError 10054] Удаленный хост принудительно разорвал существующее подключение)
```

Итог: **130 из 153 тестов ERROR**, то есть полного прогона графтестов сейчас не существует ни
для кого — «дельта vs предыдущий прогон» тоже врёт («Изменений нет», потому что сравниваются
два одинаково сломанных прогона).

Воспроизводится детерминированно: два полных прогона встали на одном и том же тесте.
`run.py --only 23` при этом **PASS** — дело не в странице.

## Механизм (измерен, не предположен)

1. `LiveWindowClient.__init__` (`graphic_tests/run.py:1028`) поднимает окно с
   `stderr=subprocess.PIPE, text=True` — **без `encoding=`**, поэтому Python декодирует
   поток кодировкой консоли (здесь `charmap`/cp1252), а Lumen печатает в stderr русские
   строки в UTF-8.
2. `_read_token` вычитывает первые строки и отдаёт остаток фоновому потоку `_drain_stderr`.
   На первой же не-ASCII строке поток умирает:
   `UnicodeDecodeError('charmap', b'DX12: present=ok … (496 \xd0\xbc\xd1\x81) \xe2\x80\x94 …', 89, 90, 'character maps to <undefined>')`
   — и `except Exception: pass` в `_drain_stderr` **глотает это молча**. Замер: поток
   прочитал **2 строки** и умер, `alive False`.
3. Трубу больше не читает никто. Lumen продолжает писать в stderr, буфер трубы Windows
   (единицы КБ) заполняется, и очередной `eprintln!` блокирует **пишущий поток**.
4. Пишет UI-поток, поэтому окно встаёт целиком: автоматизация не обслуживается
   (`automation command timed out`), затем соединение рвётся (10054). Номер теста
   детерминирован, потому что детерминирован объём stderr до этого момента.

### Что отделяет причину от совпадений

Пробники (`.tmp/hang*.py` в сессии, цикл один и тот же — `navigate` + `wait document_ready`
по списку `TESTS` в его порядке):

| пробник | stderr окна | результат |
|---|---|---|
| свой клиент, те же флаги окна (`--no-scrollbar --deterministic --viewport 1024x720`) | в **файл** | 30 страниц, зависания нет |
| свой клиент + полный цикл `capture_lumen_live` (settle → `_bring_pid_to_front` → gdigrab) | в **файл** | 30 страниц, зависания нет |
| свой клиент, простой 240 с при живом окне, затем навигации | в **файл** | зависания нет (не «по времени») |
| **`rp.LiveWindowClient` из run.py** (PIPE + поток-дренаж), цикл без Edge/diff | в **трубу** | **HANG на #23**, ровно как в полном прогоне |

То есть отличие ровно одно — кто и как читает stderr окна.

## Как воспроизвести

```bash
LUMEN_PROFILE=dev-release python graphic_tests/run.py --continue-on-fail   # встанет на TEST-23
```

Минимальный репро без ffmpeg/Edge — поднять окно клиентом харнесса и просто ходить по
страницам:

```python
import sys, os, glob, time
sys.path.insert(0, 'graphic_tests')
import run as rp
port = rp._free_tcp_port()
c = rp.LiveWindowClient(rp.LUMEN, rp.REPO, port)          # stderr=PIPE, text=True
for p in sorted(glob.glob('graphic_tests/[0-2][0-9]-*.html')):
    c.navigate('file:///' + os.path.abspath(p).replace(chr(92), '/'))
    c.wait_document_ready()                               # таймаут на ~24-й странице
    print(p, flush=True)
```

## Что сделано

Обе половины — они независимы, каждая снимает зависание сама по себе (см. «Гейт»).

1. **Харнесс (`graphic_tests/run.py`) — снимает первичную причину.** Оба `Popen` с трубой
   получили `encoding='utf-8', errors='replace'`: `LiveWindowClient.__init__` (stderr) и
   `LumenIpcClient.__init__` (stdout, ровно та же ловушка `text=True` без кодировки).
   `_drain_stderr`/`_drain_stdout` больше не глотают исключение — печатают
   `ВНИМАНИЕ: дренаж … упал (…), см. BUG-770`. Молчаливая смерть дренажа и есть то, из-за
   чего дефект выглядел как зависание движка на конкретной странице: настоящая причина
   наступала за ~20 страниц до первого видимого симптома.
2. **Движок (`crates/shell/src/diag_stderr.rs`, новый модуль) — устойчивость.** Между
   процессом и настоящим stderr вставлен неблокирующий сток:

   ```text
   eprintln!  →  своя труба  →  поток-читатель  →  кольцевой буфер (1 МиБ)
                                                        │
                                       поток-писатель ◀─┘  →  настоящий stderr
   ```

   `SetStdHandle(STD_ERROR_HANDLE, …)` перенаправляет stderr всего процесса, поэтому правка
   не зависит от 457 мест вызова `eprintln!` и не может быть обойдена новым вызовом. Читатель
   никогда не ждёт писателя: переполненное кольцо роняет самые старые куски и **сообщает** об
   этом строкой `[diag] потеряно N байт stderr — потребитель не читал трубу`, как только
   потребитель снова начинает читать. Теряются строки, а не кадры, и потеря наблюдаема —
   молчаливое проглатывание и было исходной ловушкой.

   Сток ставится, только если stderr **действительно труба** (`GetFileType == FILE_TYPE_PIPE`):
   консоль и файл заблокироваться навсегда не могут, поэтому интерактивный запуск и запуск с
   логом в файл не меняются ни на байт — ни лишних потоков, ни буферизации. Плечо отката —
   `LUMEN_NO_STDERR_SINK=1` (docs/automation.md). Поток-писатель отвязан, поэтому `main`
   разделён на `main`/`run_cli`, и `diag_stderr::flush(2 c)` вызывается на выходе из процесса
   (включая три `process::exit(2)` в `bench_frames.rs`) — иначе терялся бы хвост лога.

   Windows-only: зависание измерено там, и буфер трубы там самый маленький. На остальных ОС
   `install`/`flush` — no-op.

Печать `[probe]`/`[engine-thread]` **не** трогалась: перепись показала 95 байт на страницу
(две строки), т.е. объём диагностики сам по себе не дефект — дефектом было блокирующее
поведение записи.

## Гейт

Плечи A/B на одном бинарнике, все 158 страниц `graphic_tests/*.html` через **настоящий**
`rp.LiveWindowClient` (`stderr=PIPE`), дренаж принудительно мёртв (`_drain_stderr` заменён на
no-op — точная модель молча умершего потока):

| плечо | сток | дренаж | результат |
|---|---|---|---|
| A | `LUMEN_NO_STDERR_SINK=1` | мёртв | **HANG на 28-й странице**, `Wait error: automation command timed out` — исходный симптом |
| B | включён | мёртв | **158/158**, 11 с |
| C | `LUMEN_NO_STDERR_SINK=1` | починенный (UTF-8) | **158/158**, 11 с |

A↔B — гейт движковой половины, A↔C — харнессной. Перепись объёма stderr (`stderr` в файл,
30 навигаций): 96 байт на старте + **95 байт на страницу**, откуда и берётся детерминированный
номер страницы — труба Windows (~4 КиБ) переполняется примерно на 24–28-й.

## Остаток

`stderr=subprocess.PIPE, text=True` без `encoding=` остался ещё в шести местах python-тулинга
(`tests/wpt/verify_bug380_navigation_staleness.py`, `verify_devx6_bidi_scenarios.py`,
`verify_s3_bidi_session.py`, `verify_s6_await_promise.py`, `scripts/input_perf.py`,
`scripts/mem_perf.py`). Зависания движка они больше не вызывают — это снимает сток, — но своё
чтение stderr там всё ещё упадёт `UnicodeDecodeError` на русской строке. Это владение P2/P1,
отдельной строкой в BUGS.md не заводилось: симптом громкий и локальный (падение скрипта), а не
молчаливый.

## Последствия для гейтов

Пока баг был открыт, «полный прогон графтестов» как пиксельный гейт был недоступен: 130 из 153
тестов ERROR по причине, не связанной с проверяемой правкой. Замена, применённая в BUG-405 срез
5 — свип wgpu-рендера всех 159 страниц через `Renderer::render_to_image` (headless GPU) с
побайтовым сравнением плеч A/B; ограничение свипа описано там же. Полный 20-минутный прогон с
gdigrab в сессии этого фикса не выполнялся (не помещается в один передний вызов и требует, чтобы
никто не трогал рабочий стол) — снят гейт механизма, а не пиксельный.
