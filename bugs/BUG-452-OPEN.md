# BUG-452 — `<canvas width="0">` даёт 300×150: разбор атрибутов размера роняет ноль через `||`

**Статус:** OPEN
**Компонент:** js (`crates/js/src/dom.rs:5334-5343` — `_lumen_canvas_dims`; геттеры
`width`/`height` `dom.rs:6052-6072`)
**Найден:** 2026-07-28 (P2), WPT-VENDOR-html-canvas
**Перепроверен:** 2026-07-29 на main — воспроизводится, плюс отрицательное значение
(номер сменён с BUG-424: 424 занят чужим багом хрома)

## Симптом

```
<canvas id=z width=0 height=0>   →  z.width x z.height = 300x150   (атрибуты: '0'/'0')
n.width = 0                      →  n.width = 300,  getAttribute('width') = '0'
```

То есть сеттер честно пишет атрибут, а геттер его игнорирует: `canvas.width = 0;
canvas.width` возвращает `300`. По HTML LS §4.12.4 `width`/`height` — `unsigned long` с
дефолтом 300/150, и **`0` — валидное значение**: нулевой canvas допустим, у него просто
нет пикселей (`getContext('2d')` при этом обязан вернуть контекст, а `getImageData`
на нём — бросить `IndexSizeError`).

## Причина

```js
// crates/js/src/dom.rs:5338-5341
var w = (aw !== null) ? (parseInt(aw, 10) || 300) : 300;
var h = (ah !== null) ? (parseInt(ah, 10) || 150) : 150;
if (w < 1) w = 1;
if (h < 1) h = 1;
```

`parseInt('0', 10)` даёт `0`, а `0 || 300` — `300`: классическая ловушка `||` вместо
проверки на `NaN`. Тем же путём теряется и отрицательное значение (проба 2026-07-29:
`c.width = -5` → `c.width === 300`, тогда как WebIDL `unsigned long` требует
обёртывания в `4294967291`). Клампы `w < 1` до нуля уже не доходят. Побочно тем же путём
теряется различие «атрибут отсутствует» (правильно 300) и «атрибут равен нулю»
(должно быть 0), а бэкинг-битмап нулевого canvas молча становится 300×150 —
`getImageData(0,0,1,1)` на нём **успешно возвращает пиксель** вместо `IndexSizeError`
(проба: `getImageData ok w=300`).

## Данные WPT

`element/canvas-host/*` — серия `2d.canvas.host.size.attributes.*` (7 сабтестов падают
сообщением `assert_equals: canvas.width === 0 (got 300[number], expected 0[number])`).
Смежные сабтесты той же серии падают на `getComputedStyle(canvas).getPropertyValue("width")`
= `""` — это **не** этот баг, а уже заведённый [BUG-382](BUG-382-OPEN.md) (снимок
computed-style не доезжает до JS-контекста).

## Направление починки

```js
var wp = parseInt(aw, 10);  var w = (aw !== null && !isNaN(wp) && wp >= 0) ? wp : 300;
```

и убрать клампы `< 1` (нулевой размер валиден) — вместо этого гейтить сами операции
рисования и бросать `IndexSizeError` из `getImageData`/`createImageData` при нулевой
области, как требует спека. Тот же разбор нужен и геттерам `width`/`height`
(`dom.rs:6057`, `:6071`), где для не-canvas элементов стоит зеркальная ловушка
`parseInt(v, 10) || 0`.

Смежное по тому же файлу: [BUG-450](BUG-450-FIXED.md) (члены `HTMLCanvasElement` стоят
на каждом элементе, а `getContext` нарушает контракт аргумента).
