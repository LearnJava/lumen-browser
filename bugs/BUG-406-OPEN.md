# BUG-406 — DX12: компиляция 16 wgpu-пайплайнов при старте стоит 3–7 с против 0.28 с на Vulkan (то же железо)

**Статус:** OPEN
**Компонент:** paint (`Renderer::init_pipelines`, `crates/engine/paint/src/renderer.rs`) —
16 вызовов `device.create_render_pipeline` при создании бэкенда
**Найден:** 2026-07-28 (P3), инструментальный замер стадий cold-start по заявке пользователя
(«запускается очень медленно и часто зависает на голубом экране») — см. `bugs/BUG-274-OPEN.md`,
срез 2026-07-28

## Симптом

При старте окно несколько секунд не отвечает: заголовок — «Lumen 0.5.0 (Не отвечает)», окно
залито сплошной синей заливкой DWM. На видео-репродукции это состояние держится ~9 с, первый
непустой кадр — `[bench] first non-empty frame: 9889ms`.

## Данные

Инструментация (`LUMEN_FRAME_LOG=1`, две метки вокруг adapter/device-запроса и вокруг
`init_pipelines` в `Renderer::new_async`), dev-release, Intel Iris Plus, Windows 10:

| Бэкенд | probe | adapter+device | **init_pipelines (16 шт.)** | first non-empty frame |
|---|---|---|---|---|
| Vulkan | ~1.0–1.2 с | ~0.27–0.41 с | **0.26–0.40 с** | ~1.6–3.3 с |
| DX12 | — (форс) | ~0.27–0.47 с | **3.0–7.0 с** | ~3.6–8.6 с |

Одно и то же железо, один и тот же процесс, одни и те же шейдеры. Проба и получение
adapter/device на обоих API стоят одинаково — **вся разница в компиляции пайплайнов**.
DX12 идёт через naga → HLSL → FXC/DXC, Vulkan — через SPIR-V.

Разброс 3.0–7.0 с между запусками не изучен; похоже на переменный вклад драйверного on-disk
PSO-кэша Intel (первый прогон холодный, последующие теплее), но не подтверждено.

## Почему это всё ещё актуально после смены порядка бэкендов

2026-07-28 оконная цепочка выбора переведена на Vulkan-first (`renderer.rs::new_async`,
решение пользователя), и `backend_probe::pick_backend` уже пробовал Vulkan первым. На машинах,
где Vulkan проходит пробу, медленный путь больше не выбирается — но баг не закрыт:

- на машинах с [BUG-275](BUG-275-OPEN.md) (Vulkan презентует белое окно на части Intel iGPU)
  проба честно отклоняет Vulkan и падает на DX12 — там пользователь платит эти 3–7 с;
- `LUMEN_NO_BACKEND_PROBE=1` и headless-путь (`new_headless_async`, намеренно оставлен
  DX12-first ради стабильности эталонных картинок) идут по DX12;
- **липкий кэш пробы**: `pick_backend` кладёт принятого кандидата в
  `<exe_dir>/data/paint/backend_probe.txt` и в следующий раз пробует его первым. Пока в кэше
  лежал `DX12` (эпоха, когда Vulkan отклонялся как белый), каждый запуск молча уходил в
  медленный путь — на этой машине так и было, пока файл не удалили вручную. То есть смена
  порядка не помогает тем, у кого уже закэширован DX12.

## Что нужно сделать (варианты, ни один не реализован)

1. **Ленивая компиляция редких пайплайнов.** Из 16 на типовой странице нужны ~5
   (fill/rrect/text/image/gradient); остальные ~11
   (blur/backdrop/mask×4/filter/blend/composite/cross_fade/mipgen) компилировать при первом
   реальном использовании. Стоимость переезжает с запуска на момент первого появления эффекта.
   Требует перевода полей `Renderer` на `OnceCell`-подобные и передачи `&device` в точки
   использования.
2. **Компиляция пайплайнов в фоновом потоке.** `device`/`queue` — `Send + Sync`, а
   `init_pipelines` не трогает ни окно, ни surface (только `device`/`queue`/`format`/
   `font_bytes`), поэтому её можно унести с UI-потока и собрать `Renderer` из
   (surface+device+queue, оставшихся на главном потоке) + (готовые пайплайны с фона).
   **Важно:** унести на фон создание *самого бэкенда* целиком — уже пробовали 2026-07-28 и это
   не работает: `instance.create_surface(window)` молча проваливается для всех кандидатов при
   вызове не с потока-владельца окна (подробности в `bugs/BUG-274-OPEN.md`). Делить надо именно
   по границе «surface на главном / компиляция на фоне».
3. **Драйверный PSO-кэш / `wgpu` pipeline cache.** Проверить, отдаёт ли wgpu 26 доступ к
   `PipelineCache` на DX12-бэкенде и переживает ли он перезапуск процесса; если да — сохранять
   рядом с `backend_probe.txt` по той же портативной конвенции (`<exe_dir>/data/paint/`).
4. **Разобраться с липким кэшем пробы** (см. выше): как минимум перепроверять закэшированного
   кандидата, если он заметно медленнее альтернативы, либо хранить в кэше замер и
   инвалидировать его при смене драйвера.

Перед выбором варианта стоит померить, какие именно из 16 пайплайнов дают основной вклад —
сейчас известна только суммарная цифра.

## Как воспроизвести

```bash
# медленный путь (форс DX12, минуя пробу)
WGPU_BACKEND=dx12 LUMEN_FRAME_LOG=1 target/dev-release/lumen.exe samples/page.html
# быстрый путь для сравнения
WGPU_BACKEND=vulkan LUMEN_FRAME_LOG=1 target/dev-release/lumen.exe samples/page.html
```

Сравнить строки `[wgpu] init_pipelines: …ms` и `[bench] first non-empty frame: …`.
