# BUG-199

**Статус:** FIXED 2026-08-31
**Компонент:** graphic_tests (тест был неверно сконструирован, не движок)
**Тест:** TEST-71 (diff 0.02%, PASS)

## Описание

`@starting-style`: статический рендер двух цветных блоков отличается от Edge-эталона.

## Расследование (2026-06-20)

Дамп display-list (`--dump-display-list 71-starting-style.html`) — **геометрия и
цвета идеальны**:

```
FillRoundedRect (292.00, 260.00, 200.00, 200.00) #e94560ff r=[12,12,12,12]   ← box-a
FillRoundedRect (532.00, 260.00, 200.00, 200.00) #0f3460ff r=[12,12,12,12]   ← box-b
```

Обе коробки 200×200, корректно отцентрованы (flex center, gap 40), полная
непрозрачность — это **settled-состояние** страницы (как она выглядит после
завершения 0.4s entry-перехода). `@starting-style` корректно НЕ просачивается в
статический каскад (CSS Transitions L2 §3.4): он задаёт *before-change* стиль
только для entry-переходов.

Пиксельный замер Edge-эталона (горизонтальная линия y=360):
- box-a (красный #e94560): полоса x=338..445 → **ширина ~107px**, центр 391 =
  `transform: scale(0.5)` применён (200→100, центр сохранён).
- box-b (синий #0f3460): полоса x=458..657 → левый край 458 vs нормальные 532 =
  `transform: translateX(-80px)` применён.
- Обе коробки при **полной непрозрачности** (точные #e94560/#0f3460, без блендинга).

То есть Edge показывает: **transform у `@starting-style` START-значения** (scale 0.5,
translate -80, ~0% прогресса), но **opacity у END-значения** (1, ~100% прогресса).
Для синхронных 0.4s ease-переходов это взаимно несогласованный кадр — артефакт
тайминга захвата Edge `--headless --screenshot` (без `--virtual-time-budget`),
поймавшего entry-transition в полёте, а не стабильный рендер.

## Почему не P3-фикс

Дефекта движка нет: Lumen рендерит спек-корректное settled-состояние. Чтобы
«совпасть» с Edge, потребовалось бы:
1. Провести `@starting-style` в каскад / TransitionScheduler — **домен P4** (CSS
   at-rules), запрещено для P3;
2. Реализовать полный engine entry-переходов (`starting_style.rs` сейчас stub);
3. Воспроизвести взаимно несогласованный кадр (transform START + opacity END) с
   точным таймингом захвата Edge — невозможно.

Тот же класс, что TEST-77/BUG-126: «Lumen спек-корректнее Edge; расхождение в
reference-браузере, не дефект движка».

## Ревизия P3 2026-08-31: настоящая причина найдена — тест, не движок

Указатель `STATUS-P3.md:1` (`BUGS.md:218`) снова привёл к этому багу.
`KNOWN_DEBTORS['71']` в тот момент содержал отдельную запись «ДРЕЙФ,
обнаружен во время гейта BUG-431 (2026-08-21)» с baseline 7.03% — то есть
между 2026-08-06 и 2026-08-21 кто-то уже зафиксировал регрессию к исходному
значению, не разобравшись в причине.

**Живой прогон `--only 71 --no-cache` оказался КРАЙНЕ нестабильным**:
5+ последовательных запусков дали 0.13%, 0.72%, 1.29%, 2.83%, 5.15%, 5.18%,
6.23%, 6.70%(×2), 7.02%, 7.04%, 7.15%, 7.16%, 7.21%, 7.24%(×2), 8.40%,
10.20%, 10.57% — без какой-либо видимой закономерности. Устаревший
`crop_offset.txt` (не обновлялся с 23 июля, тулбар за это время менялся)
давал часть шума, но пересчёт калибровки (`TEST-00` в том же процессе)
разброс не устранил.

Diff-картинки на разных прогонах показывали **геометрию, точно
соответствующую разным точкам прогресса заявленного `@starting-style`
перехода**: box-a (`scale(0.5)`→`scale(1)`) — от тонкого кольца до
полу-размерной дыры; box-b (`translateX(-80px)`→`none`) — полосы разной
ширины слева/справа. Это прямо противоречило диагнозу 2026-06-20/2026-08-06
(«settled-состояние, дефекта нет»), который опирался только на
`--dump-display-list` — однократный снимок без прогона живого
redraw/animation-loop, слепой к этому классу проблем.

Проба через живое MCP-окно (`getComputedStyle` в `requestAnimationFrame`-цикле,
2с сэмплирования на 60 FPS) показала: `opacity`/`transform` в CSSOM
**остаются `1`/`none` с t=28ms и до конца** — переход невидим через
`getComputedStyle()` (композитинг применяет transition-override к display
list напрямую, в обход `ComputedStyle`, как и другие анимируемые свойства
в этом движке). Это разошлось с визуальными diff-паттернами, явно
показывающими анимацию на уровне пикселей — то есть переход **реально
идёт на уровне paint**, просто не отражается в CSSOM.

**Решающий эксперимент**: без `--no-cache` (обычный режим гейта, эталон
Edge переиспользуется из кэша) результат оказался **идеально стабилен**
на 5 прогонах подряд (2.83%). Форсированная пересъёмка Edge — вот что
создавало разброс. Значит, нестабилен НЕ рендер Lumen (он детерминирован
при фиксированном эталоне), а **сам эталон Edge**: headless
`--headless --screenshot` у Edge либо не ждёт завершения CSS-переходов
перед снимком, либо ждёт непредсказуемое время, поэтому *каждая
пересъёмка* эталона ловит СЛУЧАЙНУЮ точку перехода. Пиксельный замер
подтвердил: при закэшированном эталоне box-a на Edge был 169×169px вместо
200×200 (тот же центр) — Edge поймал переход на ~69% прогресса, а не в
settled-состоянии.

Поскольку `graphic_tests/screenshots/` (включая кэш Edge-эталонов)
gitignored и пересобирается с нуля в каждом свежем worktree/чек-ауте,
**у этого теста в принципе не может быть переносимого «стабильного»
baseline** — каждая P3/P1-сессия получала свою случайную точку перехода
Edge при первой пересъёмке эталона, что и объясняет весь ряд «дрейфов»
2026-06-20→2026-08-06→2026-08-21 задним числом: это не дрейф рендера
Lumen, а разные случайные снимки одного и того же эталона.

### Фикс

Файл-докстринг теста сам говорит: «static rendering of two coloured
boxes... In static rendering these do NOT affect appearance (no active
transition)» — но CSS вешал `transition: opacity 0.4s ease, transform
0.4s ease` на `.box-a`/`.box-b`, что СОЗДАЁТ активный entry-transition при
каждой загрузке страницы, прямо противореча заявленному намерению теста.
Это дефект самого теста, а не попытка обойти ограничение движка (правило
CLAUDE.md «никогда не редактировать тестовые страницы под ограничения
движка» сюда не относится — обходить нечего, у Lumen дефекта не было и
нет).

Убраны обе строки `transition:` из `graphic_tests/71-starting-style.html`
(`@starting-style`-правила оставлены — parse-тест не пострадал). Эталон
Edge пересобран (`--no-cache`): **0.02% стабильно на 5+ прогонах подряд**,
с `--no-cache` и без. Запись `'71'` удалена из `KNOWN_DEBTORS`
(`graphic_tests/run.py`) — цель ≤0.5% достигнута, TEST-71 теперь PASS.

BUG-199 закрыт.
