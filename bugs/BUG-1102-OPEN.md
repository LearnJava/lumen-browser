# BUG-1102 — developer.mozilla.org: skip-links схлопываются в столбец «по одной букве на строку», паинт-стадия растягивается до ~104 с

**Статус:** OPEN
**Тип:** дефект (живой сайт), гипотеза о едином корне с перф-симптомом не подтверждена.
**Заведён:** 2026-09-23 (P6, RP-10 — повторный аудит реальных сайтов против Edge).
**Область:** не локализовано (подозрение — layout: расчёт ширины строчного/флекс-контейнера
для `<a class="...skip-link...">`); паинт-стадия — CPU-путь растеризации
(`crates/engine/paint`, тот же CPU-скриншот, что BUG-221/BUG-272).
**Владелец:** P4 (layout) для визуального дефекта; P3/P4 совместно для paint-стоимости.

## Симптом 1 — визуальный

Живой скриншот `developer.mozilla.org/en-US/` (RP-10 compat-прогон,
`.tmp/perf-audit/20260923-022309/mdn.png`, не коммитится) показывает два блока
«Skip to main content» / «Skip to search» ссылок, отрендеренных **по одной букве на
строке**, вертикальным столбцом в левом верхнем углу — вместо однострочной ссылки:

Основная навигация/сайдбар под ними не видна вовсе — страница выглядит как почти
пустая с двумя колонками текста-«стенкой». Это НЕ общая регрессия рендера — тот же
прогон дал нормальную вёрстку на `hn`/`rust-lang`/`docs-rs` (скриншоты того же
прогона), так что дефект специфичен для CSS/разметки этого конкретного элемента
mdn (skip-link, обычно `position:absolute` + `width`/`clip` трюк для
screen-reader-only контента, который должен становиться видимым и однострочным по
`:focus`).

**Гипотеза:** элемент получает вычисленную ширину близкую к нулю (например
`width: 1px` из общего a11y-паттерна «visually hidden», который движок не снимает
на нужном селекторе/состоянии), из-за чего каждая буква переносится как отдельная
строка — классический симптом контейнера уже с шириной ~1 символа. Не подтверждено
`--dump-layout`/`LUMEN_PROFILE_TREE` в этой сессии — только скриншот.

## Симптом 2 — перф

`--phases --only mdn` (headless, тот же коммит `d530491e1`):

```
mdn https://developer.mozilla.org/en-US/ ... OK total=104.48s dominant=paint
source=1.43s layout=23.5s screenshot=104.48s RAM_peak=395.4MB CPU=89.42s
```

Паинт-стадия (CPU-скриншот, `--screenshot`) доминирует с большим отрывом — 104 с
против 23.5 с на layout+JS и 1.4 с на сеть. Для страницы такого класса (документация,
сравнимая по духу с `rust-lang.org`, у которого тот же прогон дал `paint` в единицы
секунд) это на порядок дороже. **Не подтверждено**, что симптом 2 вызван тем же
корнем, что симптом 1 (колонка «по букве на строку» технически means множество узких
строчных боксов с текстом — потенциально много лишних строк для укладки и
растеризации, что могло бы объяснить часть паинт-стоимости, но это неподтверждённая
гипотеза, не измерение).

## Сравнение с историей

Живой прогон 2026-07-20 (`docs/perf/runs/2026-07-20-live.json`, режим `live`/`stability`,
не `compat` — сравнение приблизительное) дал `mdn` `ready=7.0s`, `err=2`, без упоминания
подобного визуального дефекта в журнале того прогона. Не установлено, является ли это
новой регрессией движка, дрейфом разметки самого mdn.org, или тем, что 2026-07-20 не
смотрел на скриншот прицельно (тот прогон анализировал вкладки многовкладочного
`stability`-харнесса, где эффект мог быть не замечен).

## Не проверено

- `--dump-layout`/`LUMEN_PROFILE_TREE=1` для точной локализации CSS-правила,
  схлопывающего ширину skip-link.
- Профиль паинт-стадии по типам `DisplayCommand` (`LUMEN_PROFILE_TREE`/ручной таймер) —
  не установлено, что именно доминирует внутри 104 с (текст/глифы vs фон/тени vs общее
  число боксов).
- Edge headless для того же URL — не запускался в этой сессии.
