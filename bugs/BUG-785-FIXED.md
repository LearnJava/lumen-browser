# BUG-785 — нет способа доверить движку дополнительный CA: весь HTTPS-корпус WPT недостижим

**Статус:** FIXED 2026-08-20
**Заведён:** 2026-08-18 (WPT-RUN-4, пилотный прогон корпуса)
**Область:** `lumen-network` (`crates/network/src/lib.rs`, `crates/network/src/dot.rs`)
**Владелец:** P1/P3 (движок), но исправлено P2 с явного разрешения пользователя
(единая точка расширения `RootCertStore` — небольшая, изолированная правка в
`lumen-network`, вне обычного скоупа P2, но не требующая знания остального
движка).

## Симптом

Каждый `.https.`-тест WPT падает, не начавшись:

```
network error: TLS handshake: invalid peer certificate: UnknownIssuer
```

В пилотном прогоне (`tests/wpt/run_corpus.py --pilot`) на этом полностью
провалилась категория `WebCryptoAPI`: 134 зафиксированных `UnknownIssuer` до
того, как шард был убит по таймауту — ни один тест не отчитался.

## Механизм

`rustls::RootCertStore` в `lumen-network` собирается **только** из
`webpki_roots::TLS_SERVER_ROOTS`, в четырёх независимых местах:

- `crates/network/src/lib.rs:1620`, `:1633`, `:1650`, `:1666`
- `crates/network/src/dot.rs:265` (DoT, отдельный конфиг)

Ни одна из этих точек не читает дополнительный корневой сертификат — нет ни
CLI-флага, ни переменной окружения, ни файла конфигурации. Поэтому
самоподписанный CA принципиально не может быть принят, а WPT по своей
архитектуре обслуживает `https`-тесты именно самоподписанным CA
(`tests/wpt/certs/ca-cert.pem`, вендорен и передаётся `wptrunner` через
`--ca-cert-path`, см. `run_smoke.py`).

Обходного пути в рамках правил проекта нет: установка CA в системное
хранилище Windows — изменение системных настроек безопасности, за границей
допустимого.

## Масштаб

По манифесту вендоренного корпуса (`tests/wpt/corpus_stats.py`):

```
автоматизируемых id:  67 735
из них .https.:        7 190   (10.6%)
```

Крупнейшие пострадавшие категории: `webnn` (572), `html` (521),
`speculation-rules` (519), `mixed-content` (387), `service-workers` (328),
`WebCryptoAPI` (308), `css` (286), `content-security-policy` (225).

То есть **10.6% pass-rate прибито инфраструктурой, а не качеством движка**.

### Замер на выборке (2026-08-18, WPT-RUN-4)

Равномерная выборка **200 `.https.`-id из 65 категорий** (шаг по
отсортированному списку всех 6874 https-testharness-id), `--processes=6`:

```
результат:      200 TIMEOUT из 200        (ни одного другого статуса)
сабтесты:       0 / 0                     (harness не стартует вовсе)
UnknownIssuer:  200 попаданий в логе      (по одному на тест)
время на тест:  ~39 000 мс                (медиана близка к среднему)
время выборки:  1464 с на 200 id
```

Вторичный эффект оказался дороже основного: TLS-рукопожатие **не** отказывает
быстро — каждый тест выжидает полный таймаут исполнителя. Экстраполяция на все
6874 id: **≈14 часов** чистого времени прогона ради заранее известного нуля.

Поэтому `tests/wpt/run_corpus.py` получил `--skip-https`: эти id **остаются в
знаменателе** и считаются непройденными (решение о знаменателе не меняется), но
не запускаются, а сводка печатает отдельной строкой, сколько id не запущено
намеренно и почему. Как только баг починят, флаг перестаёт быть нужен — и
первый же прогон без него покажет, сколько из этих 6874 id движок реально
проходит.

## Что считать починкой

Точка расширения доверенных корней — единая для всех пяти мест, где сейчас
дублируется сборка `RootCertStore`. Форма (флаг, env, файл в
`<exe_dir>/data/`) — на усмотрение владельца; для WPT достаточно, чтобы
`wptrunner` мог передать путь к `ca-cert.pem`, который уже вендорен.

Проверка: `.https.`-тест из `WebCryptoAPI` добегает и отчитывается
содержательно (не обязательно проходит) вместо `UnknownIssuer`.

## Связи

- `WPT-RUN-2` объявляла HTTPS-порт починенным, и это верно на своём уровне —
  порт действительно выделяется (было `invalid port: "None"`). Дальше запрос
  доходит до TLS и умирает уже там; это другой, не покрытый той задачей слой.
- Цифра pass-rate и её оговорки — `docs/wpt/pass-rate.md`.

## Починка (2026-08-20)

Единая точка сборки `RootCertStore` — `tls::trusted_root_store()`
(`crates/network/src/tls/mod.rs`): встроенные `webpki-roots` плюс, если задана
переменная окружения `LUMEN_EXTRA_CA_CERT`, сертификаты из указанного ею
PEM-файла (парсинг — `rustls-pemfile`, partner-crate к `rustls`, а не
самописный base64/PEM-разбор — «не пишите свой crypto», `docs/plan/tech-stack.md`
§5). Файл читается и кэшируется один раз (`OnceLock`); нечитаемый файл или
пустой/битый PEM молча деградируют к пустому списку (с диагностикой в stderr),
TLS продолжает работать на встроенных корнях. Все пять мест, дублировавших
сборку `RootCertStore` (`lib.rs` ×4, `dot.rs` ×1), переведены на эту функцию.

`tools/wptrunner/wptrunner/browsers/lumen.py` (продуктовый плагин Lumen для
wptrunner, не часть неизменяемого вендоренного ядра) прокидывает уже
существующий `--ca-cert-path` (`tests/wpt/certs/ca-cert.pem`, `run_smoke.py`)
в `LUMEN_EXTRA_CA_CERT` при запуске дочернего процесса — `browser_kwargs`
добавляет `ca_cert_path` в `**kwargs`, `LumenBrowser.__init__` кладёт его в
`env`. `--skip-https` (`tests/wpt/run_corpus.py`) можно снимать в WPT-RUN-5.

**Проверка (живой прогон):** `run_smoke.py` на
`/WebCryptoAPI/crypto_key_cached_slots.https.any.html` — TLS-рукопожатие
проходит, HTML/JS реально грузятся по HTTPS (`Reload: https://127.0.0.1:18443/...`,
`загрузка 471 байт`), `UnknownIssuer` нигде не встречается. Тест всё равно
кончается `TIMEOUT`, но по другой, не связанной с TLS причине
(`add_completion_callback is not defined` — отдельный, не заведённый этой
задачей гэп) — именно критерий «Что считать починкой» выше: тест добегает и
отчитывается содержательно, а не падает до отправки запроса.

Регрессионные тесты — `crates/network/src/tls/mod.rs` (`parse_pem_certs_*`,
`trusted_root_store_includes_builtin_roots_even_without_env_var`) и сквозной
`crates/network/tests/cases/bug785_extra_ca.rs` (реальное TLS-рукопожатие по
loopback против сертификата WPT: без добавления CA — `UnknownIssuer`, с
добавлением — успех).
