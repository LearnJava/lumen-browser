# BUG-1853 — portal.nextera.ru: WebP-логотип кашей, SVG-иконка микрофона битым глифом, центральная колонка 487px против 820px в Chrome

**Статус:** OPEN (срез 2026-11-26: дефекты 1 и 2 исправлены, дефект 3 пере-диагностирован —
см. «Срез фикса»)
**Заведён:** 2026-11-26 (ZCode, живое сравнение с Chrome 158 при равных вьюпортах 1920×845)
**Область:** paint (декод/отрисовка WebP; отрисовка маленьких inline-SVG), layout (flex-размер
центральной колонки главной — исходная гипотеза «грид, семейство BUG-1846» опровергнута)

## Симптом

Домашний экран portal.nextera.ru (залогиненный, тёмная тема) в Lumen отличается от Chrome
тремя дефектами (снимки на момент заведения: `.tmp/lumen_home.png` / `.tmp/chrome_home.png`,
вне репозитория):

1. **WebP-логотип рисуется кашей.** `IMG.home-balls-float` → `…/up-assets/logo-balls-c-ofFbLl23.webp`
   (natural 448×58, отрисуется 180×23, `complete=true`): глянцевая цепочка шариков в Chrome —
   в Lumen тёмные бесформенные пятна.
2. **SVG-иконка микрофона — битый глиф.** Кнопка `#pttBtn` композера содержит inline-SVG
   12×12 viewBox 16 (`<rect x=5 y=1 width=6 height=9 rx=3/>` + два `<path>`): в Lumen рисуется
   как пустой прямоугольничек (path не виден), в Chrome — полноценная иконка микрофона.
   Соседний плюс-кнопка (`pp-plus-btn`) и круглая кнопка отправки при этом выглядят нормально.
3. **Центральная колонка главной — 487px против 820px в Chrome.** `.home-input-card` и
   `.home-hello` в Lumen 487px, в Chrome — 820px.

## Срез фикса 2026-11-26 (ветка bug-1853-fix)

**Дефект 1 — ИСПРАВЛЕН (не был декодером).** Реальная причина: файл — **анимированный WebP**
(VP8X flags Animation+Alpha, `ANIM`+61 `ANMF`-кадр), декодер отдавал статично только кадр 0
(тёмное «начало» анимации), Chrome проигрывает анимацию. Декод кадра 0 при этом попиксельно
верный — зонд `lumen-image::webp::decode_webp` vs PIL: 0 различий на 25 984 пикселях.
Сделано: проигрывание анимированного WebP по образцу GIF — `lumen-image::AnimatedWebp`
(ленивый forward-курсор над `image-webp` 0.2 `read_frame`/`reset_animation`, per-frame
задержки контейнерным проходом по ANMF-заголовкам), обёртка `AnimatedImage::{Gif,Webp}` —
единый тип тика shell; формат-нейтральный `LoopCount` (бывш. `GifLoopCount`);
`DecodedImage::Animated` несёт оба формата. Проверка на живом портале: PrintWindow-снимок
реального кадра показывает середину анимации (кадры сменяются), лог `Загружена
WebP-анимация: … 61 кадров`. Хвост: `resource://screenshot` (CPU-путь) держит кадр 0 —
кэш CPU-снимков не видит `register_image`-обновления, то же верно и для GIF (известный
разрыв CPU-скриншота, не регресс этого среза).

**Дефект 2 — ИСПРАВЛЕН.** Реальная разметка `#pttBtn`:
`<path d="M2 8a6 6 0 0012 0">` — дуга с **компактной записью arc-флагов без разделителей**.
По грамматике §path флаги — одиночные цифры, `0 0012 0` = large-arc 0, sweep 0, число 12;
`try_arc_params` читал их жадным `try_number` → «0012» поглощалась целиком, дуга получала
мусорные параметры и весь path отбрасывался. Разреженная запись `0 0 12 0` рисовалась
верно — на этом сошёлся зонд-тройка (`.tmp/bug1853/svg_probe3.html`): A (компакт) — только
rect, B (разреженный) — полная иконка, повторяя симптом портала. Сделано: `try_flag`
(ровно один байт `0`/`1`) в `paint::svg_path`; тесты: портал-микрофон, `1101 0`, продолжение
после слитых флагов.

**Дефект 3 — ПЕРЕ-ДИАГНОСТИРОВАН (не грид).** Реальная цепочка: `.home-input-card` —
`display:block` в обёртке `div[style*="max-width:700px"]` (inline `width:100%;
max-width:700px`), родитель — flex-строка `justify-content:center`; ширина 820px задаётся
правилом `#screen-home [style*="max-width:700px"] { margin: auto; max-width:
var(--feed-w) !important; }` поверх `:root { --feed-w: 1440px }` → `html.pp-shell {
--feed-w: 820px }`. Замеры на живой странице (ветка bug-1853-fix, бинарь с срезом):

| проба на живой обёртке | Lumen | Chrome |
|---|---|---|
| inline как есть (width:100%, override до 820) | 487px | 820px |
| `width:50%` | 243px (база ≈ 487) | 928px (база = контейнер) |
| `width:800px` | **700px** (эффективный cap — inline max-width:700) | 800px |
| `width:auto; max-width:none` | 487px (fit-content) | — |

То есть в layout `!important`-override с `var(--feed-w)` не действует (эффективный
max-width остаётся inline 700px), при этом `getComputedStyle().maxWidth` отдаёт 820px —
раскол computed-vs-layout на каскаде с `var()`; и процентная ширина flex-элемента
разрешается против его собственного fit-content (≈487px), а не контейнера. Синтетический
репродюс (`.tmp/bug1853/col_repro.html`: flex-строка + тот же attr-селектор + var) в том же
бинаре даёт верные 820px на 1024 и 1920 — расхождение требует полного контекста страницы
(гипотезы: второй атриб-селектор/порядок листов, специфичность с `html.pp-shell`,
взаимодействие fit-content-фазы flex с %-шириной). `#homeAmbient` (display:none в Chrome,
computed display "" в Lumen — правило `html.pp-shell #homeAmbient` не применилось) скрытием
не влияет на ширину — отдельный кандидат, не причина колонки.

## Как проверить

Снимки `.home-input-card`/логотипа/микрофона в Lumen и Chrome при 1920×845 совпадают;
`logo-balls-c-*.webp` проигрывается (кадры сменяются в живом окне); `#pttBtn` SVG читается
как микрофон. Для среза: (1) живой PrintWindow-снимок — анимация идёт ✓; (2) `#pttBtn`
после пересборки с фиксом svg_path — микрофон из дуги+ножки ✓/нет; (3) колонка — OPEN до
локализации раскола каскада.

Смежные: BUG-1846 (композер чата — грид; **колонка главной к нему больше не относится**),
BUG-1841..1847 (портальная серия), BUG-1851 (WS-куки — влита, логин стабилен).
