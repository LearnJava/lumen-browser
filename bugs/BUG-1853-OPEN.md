# BUG-1853 — portal.nextera.ru: WebP-логотип кашей, SVG-иконка микрофона битым глифом, центральная колонка 487px против 820px в Chrome

**Статус:** OPEN (дефекты 1–3 исправлены 2026-11-26/27; остаток — дефект 4 `#homeAmbient`)
**Заведён:** 2026-11-26 (ZCode, живое сравнение с Chrome 158 при равных вьюпортах 1920×845)
**Область:** paint (декод/отрисовка WebP; отрисовка маленьких inline-SVG), layout (колоночный
flex — поперечный сайзинг элемента)

## Симптом

Домашний экран portal.nextera.ru в Lumen отличался от Chrome четырьмя дефектами
(снимки на момент заведения: `.tmp/lumen_home.png` / `.tmp/chrome_home.png`, вне репозитория):

1. **WebP-логотип рисуется кашей.** `IMG.home-balls-float` → `…/logo-balls-c-ofFbLl23.webp`
   (natural 448×58, отрисовывается 180×23).
2. **SVG-иконка микрофона — битый глиф.** Кнопка `#pttBtn` композера содержит inline-SVG
   12×12 viewBox 16 (`<rect x=5 y=1 width=6 height=9 rx=3/>` + два `<path>`).
3. **Центральная колонка главной — 487px против 820px в Chrome.** `.home-input-card` и
   `.home-hello` в Lumen были 487px, в Chrome — 820px.
4. **`#homeAmbient` не скрывается** — правило `html.pp-shell #homeAmbient { display:none }`
   не применилось (computed display в Lumen `""`), в Chrome — `none`. На ширину колонки не
   влияет (элемент `position:absolute`), декоративный ambient-слой.

## Дефект 1 — ИСПРАВЛЕН (не был декодером)

Реальная причина: файл — **анимированный WebP** (VP8X flags Animation+Alpha, `ANIM`+61
`ANMF`-кадр), декодер отдавал статично только кадр 0 (тёмное «начало» анимации), Chrome
проигрывает анимацию. Декод кадра 0 попиксельно верный — зонд `lumen-image::webp::decode_webp`
vs PIL: 0 различий на 25 984 пикселях. Сделано: проигрывание анимированного WebP по образцу
GIF — `lumen-image::AnimatedWebp` (ленивый forward-курсор над `image-webp` 0.2
`read_frame`/`reset_animation`, per-frame задержки контейнерным проходом по ANMF-заголовкам),
обёртка `AnimatedImage::{Gif,Webp}` — единый тип тика shell; формат-нейтральный `LoopCount`
(бывш. `GifLoopCount`); `DecodedImage::Animated` несёт оба формата. Проверка на живом портале:
PrintWindow-снимок реального кадра показывает середину анимации, лог «Загружена WebP-анимация:
… 61 кадров». Хвост: `resource://screenshot` (CPU-путь) держит кадр 0 — кэш CPU-снимков не
видит `register_image`-обновлений, то же верно и для GIF (известный разрыв CPU-скриншота).

## Дефект 2 — ИСПРАВЛЕН

Реальная разметка `#pttBtn`: `<path d="M2 8a6 6 0 0012 0">` — дуга с **компактной записью
arc-флагов без разделителей**. По грамматике §path флаги — одиночные цифры, `0 0012 0` =
large-arc 0, sweep 0, число 12; `try_arc_params` читал их жадным `try_number` → «0012»
поглощалась целиком, дуга получала мусорные параметры и весь path отбрасывался. Разреженная
запись `0 0 12 0` рисовалась верно — на этом сошёлся зонд-тройка
(`.tmp/bug1853/svg_probe3.html`). Сделано: `try_flag` (ровно один байт `0`/`1`) в
`paint::svg_path`; тесты: портал-микрофон, `1101 0`, продолжение после слитых флагов.
Живая проверка 2026-11-27: `#pttBtn` в залогиненном Lumen — svg с rect+2 path.

## Дефект 3 — ИСПРАВЛЕН (колоночный flex, а не каскад)

История диагноза: исходная гипотеза «грид, семейство BUG-1846» опровергнута; вторая версия
(«раскол computed-vs-layout на каскаде `!important`+`var()`» + «%-ширина от собственного
fit-content») тоже оказалась артефактом. Реальная цепочка, установленная 2026-11-27
декомпозицией на живых репродюксах (`.tmp/bug1853/repro_col*.py`):

- На странице обёртка `div[style*="max-width:700px"]` (inline `width:100%; max-width:700px`)
  — элемент **колоночного** flex (`#screen-home.active` = flex column), правило
  `#screen-home [style*="max-width:700px"] { margin:auto; max-width:var(--feed-w) !important }`
  поднимает max-width до 820.
- `layout::box_tree::flex::column_item_avail_cross` при авто-маргинах или не-stretch
  выравнивании безусловно ставил элемент в **fit-content** (max-content приветствия: 329/476/487 —
  растёт с длиной строки с датой), игнорируя определённую `width:100%`. Отсюда же «50% = половина
  собственного fit-content» (243px) и срабатывание DEVX-8a 2026-11-26: ребёнок-карточка (601px)
  вылезал из сжатой обёртки (476px) — паника debug-сборки на живом портале.
- Вторая половина: у элемента с определённой шириной и авто-маргинами §10.3.3 блочного
  расклада уже распределяет остаток между авто-маргинами (элемент сам вставал в центр при
  пробе), а `column_item_cross_shift` добавлял те же 90px сверху — двойное центрирование
  (x=180 вместо 90).

Фикс: (1) в `column_item_avail_cross` определённая ширина (`width` разрешается) уводит элемент
из fit-content-ветки в `avail_cross` — проценты разрешает сам layout элемента, где available и
есть контейнер (иначе — двойное разрешение процентов); (2) `column_item_cross_shift` считает
«желаемое §8.1 − уже распределённое §10.3.3» (параметр `laid_base`), а не приращивает поверх.

Проверка: юнит-тесты `flex_axes` (4 новых, 44/44); матрица репродюсов C1–C11/R1–R2 — все 820/90
или честный fit-content 73.32; живой портал 2026-11-27, залогиненный: обёртка/карточка/
приветствие **820px, x=550** при docW 1920 — Chrome при docW 1904 даёт 820, x=542 (та же
геометрия с поправкой на скроллбар).

## Дефект 4 — `#homeAmbient`, OPEN

Правило `html.pp-shell #homeAmbient { display:none }` в Lumen не применилось (computed
display `""`, не пустой блок и не none — тоже странность `getComputedStyle`). При этом
`html.pp-shell { --feed-w }` применяется, а в синтетике `html.pp-shell #amb` (класс добавлен
скриптом) отрабатывает. Элемент `position:absolute`, скрытие не влияет на ширину. Кандидаты:
поздний инжект листа/элемента, инвалидация, странность computed display. Не локализовано.
