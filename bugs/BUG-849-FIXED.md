# BUG-849 — `document.createElement` стоит ~140 мкс и навсегда удерживает JS-обёртку: 20 000 элементов — 2,8 с, 40 000 — фатальный OOM V8 и смерть процесса

**Статус:** FIXED 2026-08-23 (P1)
**Заведён:** 2026-08-22 (WPT-RUN-6, срез 23 — найден прямым прогоном страниц, маркер `dom-wrapper-oom` по измеренному списку id)
**Область:** `crates/js/src/dom.rs:3507` (`_lumen_make_element` — интернирование в `_lumen_element_wrappers[nid]`), `crates/js/src/dom.rs:4091` (`_lumen_build_element` — тело обёртки, ~1 480 строк и 26 `Object.defineProperty` на элемент), `crates/js/src/dom.rs:16524` (`_lumen_gc_collect` — единственный, кто чистит карту, и зовут его по idle-тику шелла)
**Владелец:** P1/P3 (`lumen-js`). Заведён P2 в ходе WPT-задачи, здесь не чинится.

## Симптом

```js
for (var i = 0; i < 20000; i++) { document.body.appendChild(document.createElement('div')); }
```

20 000 элементов создаются 2 847 мс. На 40 000 процесс умирает:

```
# Fatal JavaScript out of memory: Ineffective mark-compacts near heap limit
… Mark-Compact 1394.3 (1402.5) -> 1393.9 (1402.5) MB … allocation failure
```

Выход процесса — 133 (core dump). Никакого исключения в страницу не приходит:
умирает весь браузер, а вместе с ним — весь остаток шарда в прогоне WPT.

## Прямое измерение

2026-08-22, dev-release, Linux, коммит `3ae02b208`, `--dump-layout` на локальной
странице (`.tmp/s23/dom20k.html`, `dom40k.html`):

| элементов | результат |
|---|---|
| 20 000 | `[JS] created 20000 in 2847 ms` (≈142 мкс на элемент), процесс жив |
| 40 000 | куча дорастает до 1,4 ГБ, `Fatal JavaScript out of memory`, `rc=133` |

## Причина (локализована чтением кода)

```js
// dom.rs:3507
var cached = _lumen_element_wrappers[nid];
if (cached !== undefined) return cached;
var built = _lumen_build_element(nid);
_lumen_element_wrappers[nid] = built;
```

Интернирование само по себе обязательно — оно даёт `===`-идентичность узлов и
переживание expando-свойств ([BUG-291](BUG-291-FIXED.md)). Проблема в двух
других вещах:

1. **Цена одной обёртки.** `_lumen_build_element` — функция на ~1 480 строк с 26
   `Object.defineProperty`; каждый элемент получает собственный комплект
   аксессоров и замыканий, отсюда ~142 мкс и заметные мегабайты на тысячу узлов.
   Обычный движок кладёт это на прототип и хранит на объекте только `nid`.
2. **Карта только растёт.** `_lumen_element_wrappers` — обычный объект с сильными
   ссылками; чистит его один `_lumen_gc_collect(nids)`, которому шелл на idle-тике
   передаёт освобождённые арены nid. Узлы живого документа не освобождаются
   никогда, поэтому обёртки живут до конца документа — даже те, к которым скрипт
   больше не обратится. `WeakRef`/`FinalizationRegistry` здесь не используются.

## Масштаб

**1 id** остатка снимка WPT-RUN-5 — `/css/selectors/invalidation/has-complexity.html`
(строит дерево из десятков тысяч узлов, чтобы померить инвалидацию `:has()`).
Та же страница умирает одинаково и в корпусном прогоне, и в пробе, то есть это
не артефакт пробы. Кроме WPT дефект бьёт по любой странице, строящей крупный DOM
из скрипта: реальный сайт с 40 000 узлов — не экзотика.

## Проверка фикса

Страница целиком (сохранить куда угодно и открыть `--dump-layout`):

```html
<!doctype html><meta charset=utf-8><body><script>
var t0 = Date.now();
for (var i = 0; i < 40000; i++) { document.body.appendChild(document.createElement('div')); }
console.log('created 40000 in', Date.now() - t0, 'ms');
</script>
```

Сегодня она умирает с `rc=133`; после фикса должна печатать строку, а время на
элемент — упасть на порядок (сейчас ~142 мкс). Отдельно стоит проверить, что `===`-идентичность и expando-свойства
(тесты BUG-291) не сломались.

## Починено (P1, 2026-08-23)

Интерфейс обёртки переехал на **общий прототип на интерфейс** — тот же ход
«на прототип интерфейса, а не на каждый экземпляр», который [BUG-383](BUG-383-FIXED.md)
уже сделал для рефлектируемых IDL-атрибутов. Интернирование (`_lumen_element_wrappers`,
BUG-291) не тронуто: чинилась цена одной обёртки, а не факт её удержания.

Перепись «до» (счётчик, не время — `docs/perf-method.md`): на одном узле
**236 собственных свойств**, из них 251 функция-аксессор + ~83 метода. Складывались
они из трёх мест: литерал `_lumen_build_element` (126 свойств), блок
`Object.defineProperty(_obj, …)`/`_obj.x = …` после него (35) и по паре аксессоров
на каждое из 84 имён `_LUMEN_EVENT_HANDLER_ATTRS` (`_lumen_define_on_handler_prop`).
После фикса собственное свойство ровно **одно** — `__nid__`; плюс до четырёх
ленивых слотов (`classList`/`style`/`dataset`/`attributes`), которые раньше были
переменными замыкания строителя и создавались **всегда**, а теперь — только если
их прочитали.

Как устроено (`crates/js/src/dom.rs`):

* `_LUMEN_WRAPPER_MEMBERS` (бывший литерал), `_LUMEN_WRAPPER_CD_MEMBERS`
  (`data`/`nodeValue` для Text/Comment) и `_LUMEN_WRAPPER_ON_MEMBERS`
  (`on<type>`, только элементы) строятся **один раз** на загрузке шима.
* `_lumen_wrapper_proto_for(iface, isCharacterData)` мемоизирует по прототипу
  интерфейса объект `Object.create(iface)` со всеми общими членами. Он стоит
  **ниже** прототипа интерфейса в цепочке, поэтому затенение сохранилось ровно
  таким, каким его давали собственные свойства (случай BUG-383 —
  `select.remove(index)` против `HTMLSelectElement.prototype.remove`), а
  `instanceof` (BUG-322) не изменился.
* Каждый член читает свой узел через `this.__nid__` — префикс
  `var nid = this.__nid__;` в начале тела. Отсюда ограничение, которого раньше
  не было: член нельзя звать с чужим `this`, а вложенный колбэк внутри члена
  не должен повторять этот префикс (`this` там — глобальный объект).
* `_lumen_retarget_wrapper(el, iface)` — для тех, кто перевешивал прототип живой
  обёртки. `svg.rs` делал `Object.setPrototypeOf(el, Ctor.prototype)` в расчёте
  на то, что «методы всё равно собственные»; теперь это выбросило бы весь
  интерфейс, поэтому вызов идёт через хелпер.
* `<selectlist>` и посев `on*` из уже стоящих контент-атрибутов остались
  поэлементными: первый — редкий тег без своего интерфейса (общий прототип
  достался бы всем `HTMLUnknownElement`), второй по определению зависит от узла.

Замер после фикса (Windows, dev-release, `--dump-layout`, 20 000 итераций;
`.tmp/b849/bench.html`, скрипт трансформации — `.tmp/b849/xform.py`):

| | до | после |
|---|---|---|
| `_lumen_build_element` | 129,6 мкс | **3,1 мкс** (42×) |
| `document.createElement` | 176,3 мкс | **6,0 мкс** (29×) |
| `appendChild` | 6,3 мкс | 3,0 мкс |
| чтение `el.id` | 2,5 мкс | 0,3 мкс |
| собственных свойств на узел | 236 | **1** |

Страница проверки из раздела выше печатает `created 40000 in 327 ms` вместо
`rc=133` (движок упирается в собственный лимит арены в 40 000 узлов раньше, чем
в кучу V8, — на 200 000 приходит штатный `QuotaExceededError`, это отдельный
предел, а не OOM).

Регрессии: `cargo test -p lumen-js --features v8-backend` (3054 теста) зелёный,
добавлено шесть тестов на инварианты, которые этот переезд сделал наблюдаемыми
(`wrapper_members_are_inherited_not_own`, `wrapper_lazy_slots_are_per_node_and_stable`,
`wrapper_on_handlers_and_expandos_stay_per_node`, `wrapper_dialog_return_value_is_per_node`,
`wrapper_members_still_shadow_the_interface_prototype`,
`wrapper_character_data_members_are_text_only`); сквозная проба
`.tmp/b849/probe.html` — 30 из 30, включая типизированный SVG через
`createElementNS`; `dump_golden.py` — 12 из 12 дампов совпадают.

**Наблюдаемое изменение, не баг:** `Object.keys(el)`/`for…in` по узлу больше не
перечисляют интерфейс — как в настоящем движке, где он живёт на прототипе. Код,
который сериализовал элемент перебором собственных свойств (например возврат
значения из `eval`), увидит теперь пустой объект.

**Не чинилось здесь:** карта `_lumen_element_wrappers` по-прежнему растёт и
чистится только `_lumen_gc_collect` по освобождённым nid (причина №2 из разбора
выше). Обёртка живого узла и должна жить, пока жив узел; цена этого удержания
упала с ~236 свойств до одного, чего хватило, чтобы дефект перестал убивать
процесс. Ссылка на этот механизм есть и в [BUG-877](BUG-877-OPEN.md).
