# BUG-1840 — Открытие PCM-вывода на первом тике играющего `<video>` держит поток браузера ~630 мс

**Статус:** OPEN
**Заведён:** 2026-11-24 (ZCode, на проверке фикса [BUG-1838](BUG-1838-FIXED.md))
**Компонент:** shell ([`crates/shell/src/video_tick.rs`](../crates/shell/src/video_tick.rs) — создание
`VideoPcmAudioSink` в цикле `due` шага 2.6; [`crates/shell/src/platform/video_audio_sink.rs`](../crates/shell/src/platform/video_audio_sink.rs) —
`new()`)

## Симптом

После фикса BUG-1838 (открытие медиа-сессии уехало в фон) на `https://okko.tv/` остался один кадр

```
video аудио: открыт вывод nid=1011 (48000 Гц, 2 кан.)
[frame] total 630.01ms  (scroll_y 0, dl 1894 cmds)
[frame]   top: scroll 0.32 sda 0.15 anim 628.69 js 0.00 build 0.75 paint 0.09 (лог 0.00)
```

То есть весь кадр — `anim`, а `anim` в этом месте (шаги 2/2b/2.5/2.6) — цикл выдачи кадров видео.
Прогоны того же сайта, где событие `video аудио: открыт вывод` не наступало, дают максимум 82 и 305 мс
(`305` — чужой scroll-обработчик, `anim` 0.48 мс), то есть кадр ≥ 500 мс коррелирует именно с
открытием вывода. Замер: три прогона по 70–130 с, direct, холодный профиль, `dev-release`; логи
`.tmp/bug1838/after{1,2,3}` (gitignored). 630 мс — единственный такой кадр в after2 и ровно одно
событие открытия вывода.

## Механизм

`VideoPcmAudioSink::new()` = `rodio::OutputStream::try_default()` + `Sink::try_new` — инициализация
WASAPI и устройства вывода (Windows: ~0.5–0.7 с на этой машине). Вызывается из
`Lumen::tick_video_sessions` на первом `due`-тике играющего узла, то есть прямо в шаге 2.6
обработчика кадра; пока устройство открывается, поток браузера стоит.

`OutputStream` — `!Send` (это записано и в doc-комментарии типа), поэтому трюк BUG-1838 — «создать в
воркере, прислать событием» — здесь неприменим: сессия декодера `Send`, а поток вывода нет.

Отдельно: sink открывается и для `muted`/`volume == 0` — немой баннер okko.tv всё равно открыл
устройство и тут же получил `set_volume(0)`; `pcm_chunk` в цикле считается по `is_playing`, флаг
`muted` на него не влияет.

## Что делать

1. **Дешёвый срез:** не открывать sink, пока узел `muted`/volume 0 (`video_gif_store.audio_levels`) —
   на `unmute` он создастся на ближайшем тике, но уже по действию пользователя, а не в кадре после
   `window.load`. Проверка: тот же прогон okko.tv, ждать отсутствия кадра ≥ 500 мс при
   `video аудио: открыт вывод`.
2. **Полный срез:** аудио-поток на узел, владеющий `OutputStream`/`Sink`, PCM — по каналу из тика;
   создание устройства уезжает с UI-потока, `!Send` перестаёт мешать. Стоимость — второй поток на
   каждый играющий `<video>` с аудиодорожкой, и аккуратное закрытие при навигации/паузе.
3. Заодно решить, декодировать ли PCM для немого узла вообще: сейчас `decode_audio_pcm` крутится и для
   `muted`, а результат уходит в нулевую громкость.

## Репро

