# BUG-1786 — `wasm/core`: финальный `promise_test` не получает завершения — на деле каждое ожидание `WebAssembly.compile` платило системный тик

**Статус:** FIXED 2026-11-03 (P1)
**Заведён:** 2026-11-03 (P1, разбор остатка WASM-V8-NATIVE-S1)
**Перенумерован:** BUG-1784 → BUG-1786 (2026-11-05) — номер 1784 на main занят другим багом (SITES-TRIAGE-2, getComputedStyle, влит с zshift-трека VTT-RENDER-S2); перенумерация до merge снимает add/add-конфликт и дубль номера
**Область:** js (`crates/js/src/v8_runtime/thread.rs` — ожидание JS-потока между прокачками очереди платформы)

## Симптом

В самых больших сгенерированных spec-файлах `wasm/core` файл не успевал завершиться:

```
subtests: 9840/9841 passed ... statuses: TIMEOUT=1
```

Недостающий сабтест — финальный `promise_test(_ => chain, testNum() + "Reinitialize the default imports")`
из `tests/wpt/wasm/core/js/harness/async_index.js`, счётчики в `promise_test` давали
`created=2 started=2 done=1`: оба `promise_test` начались, завершился только первый (пустая
цепочка). Обработчик `Promise.resolve(promise).catch(step_func).then(() => test.done())`
(`tests/wpt/resources/testharness.js:758-769`) не срабатывал, хотя посторонний `.then`, подцепленный
к той же цепочке, — срабатывал, и все 9840 сабтестов проходили. Это выглядело как потерянная
реакция на промис.

## Причина

Потерянной реакции нет: страница **не успевала**, и её срезал собственный таймер харнесса. В журнале
разбора TIMEOUT приходит именно от `testharness.js`, а не от раннера:

```
TIMEOUT #2596 Reinitialize the default imports - Test timed out
Subtests passed 8552/8553
```

То есть харнесс пометил TIMEOUT-ом выполняющийся `promise_test` цепочки — поэтому `done` и остался
равен 1, а цепочка разрешилась уже после вердикта. Отсюда же и «пустая очередь платформы»: каждая
компиляция завершается, поток просто спит положенный тик между двумя завершениями.

Почему не успевала: `async_index.js` строит цепочку последовательно, по одному
`WebAssembly.compile(...)` на модуль (`async_index.js:171`), и каждый `await` стоил один парк
JS-потока. Замер пробой (2000 последовательных компиляций 8-байтного модуля):

```
BENCH compile N=2000 total=2879 ms per_op=1.439 ms
```

1,439 мс на круг — это `recv_timeout(1 мс)` из BUG-1752: Windows округляет любое ожидание меньше
системного тика вверх (1 мс после `timeBeginPeriod(1)`, 15,6 мс без него), то есть вся задержка
круглого оборота — это парковка, а не компиляция. В самом большом файле около 5 тысяч модулей:
`simd/simd_f64x2_pmin_pmax.wast.js.html` проходил в одиночку за 10,44 с, `simd_f32x4_pmin_pmax` —
за 10,50 с (15521 сабтест), `f64.wast.js.html` — за 3,5 с. При параллельном прогоне к этому
добавляется конкуренция за CPU, и крупнейшие файлы перестают укладываться в потолки.

## Что сделано

`crates/js/src/v8_runtime/thread.rs`:

1. `run_platform_tasks` принимает `spin_until` и, пока очередь платформы пуста и этот момент не
   наступил, крутит `std::thread::yield_now()` вместо возврата к парковке. `yield_now` отдаёт ядро
   компиляторам V8 и возвращается, как только они отработали, — задержка падает до их оборота.
   Скобка стора и сэмплера (`job_started`/`job_finished`) держится только на прокол очереди — он
   может исполнить JS (реакция промиса), и сторож обязан его видеть; сам спин вне скобки, иначе
   `terminate()` свободного рантайма отвечал бы `true` — это ловит тест `compat_hang.rs`.
2. Новый `PLATFORM_SPIN` (500 мкс от момента последней задачи) ограничивает спин: страница, у
   которой задачи кончились, тратит не больше этих 500 мкс CPU, дальше — обычный шаг 1…32 мс.
   Спин включается только после первой настоящей задачи (`last_task_at` — `Option<Instant>`):
   свежий изолят паркуется как раньше и не горит CPU впустую.
3. Внешний цикл сначала пробует `try_recv` (команда исполняется без парковки), затем прокачивает
   платформу и паркуется на канал только если платформа молчала дольше `PLATFORM_SPIN`.
   `PLATFORM_HOT_WINDOW` (500 мс, шаг не растёт) и шаг 1→32 мс для простоя — без изменений.

## Замеры

| что | до | после |
|---|---|---|
| один последовательный `await WebAssembly.compile` (8-байтный модуль) | 1,439 мс | 0,021 мс |
| `simd/simd_f64x2_pmin_pmax.wast.js.html` в одиночку | 10,44 с | 4,92 с |
| `simd/simd_f32x4_pmin_pmax.wast.js.html` в одиночку | 10,50 с | 5,24 с |
| `wasm/core`, `--processes 4` | 2 TIMEOUT из 258 | 258/258 `harness OK`, 188274/188283 сабтестов (99,995 %) |
| `wasm/core`, `--processes 8` | 9 TIMEOUT (замер прошлой сессии) | 258/258 `harness OK` (2 прогона из 3; в третьем 257/258 — `simd_f32x4_cmp.wast.js.html`) |

На `--processes 8` на 4-ядерном ноутбуке стена по-прежнему 24–30 с на крупнейший файл: восемь
браузеров делят восемь потоков, и выигрыш идёт в запас до потолка, а не в секунды. Единственный
оставшийся TIMEOUT — воспроизводимо машинная конкуренция, а не зависание: тот же файл в одиночку
проходит все 15521 сабтест.

## Как проверить

```
python tests/wpt/run_corpus.py --categories wasm --prefixes wasm/core --processes 8
```

Проба латентности (одноразовая, в дереве не осталась): страница с `promise_test`, который делает
2000 последовательных `await WebAssembly.compile(new Uint8Array([0,97,115,109,1,0,0,0]))` и печатает
`performance.now()`-дельту; до фикса 2879 мс, после — 43 мс.
