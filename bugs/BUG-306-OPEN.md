# BUG-306: github.com раздувает процесс до ~2.9 ГБ одной вкладкой

**Статус:** OPEN
**Дата:** 2026-07-17
**Компонент:** js/dom (подозрение) — атрибуция не сделана
**Найден:** живой перф-аудит `/lumen-perf-audit` (docs/perf/runs/2026-07-17-live.json)

## Симптом

В живом окне (вкладка на сайт, кумулятивная RAM процесса, WinAPI WorkingSet):

```
lenta   ram=610 МБ   (6 вкладок открыто)
github  ram=2904 МБ  (+~2.3 ГБ на одну вкладку github.com; ready=45с)
```

Воспроизводится стабильно (в прогоне без --maximized: 613 → 2101 МБ, +1.5 ГБ;
следом stackoverflow добавил ещё +1.26 ГБ до 3.36 ГБ). После такой вкладки
сессия вскоре умирает — см. [BUG-307](BUG-307-OPEN.md).

## Контекст

- Известные memory-срезы BUG-272 касались lenta.ru (кэши изображений/строк);
  здесь другой профиль: гигабайты появляются на JS-тяжёлом сайте — вероятно
  V8-хип / удержание DOM/строк шимом, а не кэш картинок.
- `module error: Automatic publicPath is not supported` — бандл github
  частично падает (см. BUG-303), но до этого успевает съесть гигабайты.

## Диагностика

`LUMEN_MEM_REPORT=1` на живом окне с одной вкладкой github.com; разбивка
Rust-heap / V8 / GPU (см. reference-инструментарий BUG-272). Логи прогона:
`.tmp/perf-audit/20260717-*/live.stderr.0.log`.

## Повторный прогон 2026-07-20

Воспроизводится идентично после S12b-18 (V8-миграция продолжается) и после
BUG-297/316/308 фиксов: github.com HUNG (`Wait error: automation command
timed out`) в обоих повторах живого аудита (`docs/perf/runs/2026-07-20-live.json`,
коммит движка `a014c9e6`). RAM не удалось измерить в этот раз — вкладка
зависает раньше, чем скрипт успевает опросить WorkingSet, до самого зависания
успевает вырасти сравнимо (наблюдалось визуально в gdigrab-снимках соседнего
эксперимента). Статус не меняется, не регрессия.

## Диагностический гэп найден и закрыт 2026-08-06 (P3)

`LUMEN_MEM_REPORT=1` (методология [reference_memory_diagnosis_toolkit], пункт 1)
должен был показывать V8-хип (`js_malloc`/`js_used` в MEM_REPORT-строке) — но
`PersistentJs::debug_js_heap` (`crates/shell/src/main.rs`) никогда не был
перенесён на V8 после S12b-миграции: `V8PersistentJs` не переопределял метод,
поэтому он всегда падал в трейт-дефолт `(-1, -1)`. Комментарий над дефолтом
буквально гласил «QuickJS heap» — с S12b-F2/F4 QuickJS в воркспейсе вообще
нет, инструмент был мёртв для единственного поддерживаемого движка с момента
выпиливания QuickJS. Никто не заметил, т.к. `(-1, -1)` не паникует и не ломает
формат строки, просто печатает бессмысленные отрицательные мегабайты.

**Фикс:** `V8JsRuntime::debug_heap_stats()` (`crates/js/src/v8_runtime.rs`) —
дергает `v8::Isolate::get_heap_statistics()` через существующий `self.run(...)`
джоб-канал на JS-поток (изолят не `Send`, статистика читается только оттуда).
`V8PersistentJs::debug_js_heap` делегирует в него. Регресс-тест
`debug_heap_stats_reports_nonzero_isolate_heap` (`v8_runtime.rs`, feature
`v8-backend`).

**Живая проверка на github.com** (`.claude/worktrees/p3-work`, dev-release,
одна вкладка, без взаимодействия, ~3.5 мин после первого непустого кадра):

```
MEM_REPORT dl_cmds=3032 prev_styles=1048 dl_cache=0.0MB img_cache=0/0.0MB
  prefetch=30/6.3MB web_fonts=3/1.0MB gifs=0/0.0MB js_malloc=79.7MB js_used=45.3MB
PrivateMemorySize64 = 1579466752 (1.58 ГБ), стабильно (не растёт после первого кадра)
GPU Process Memory \Local Usage = 465223680 (0.47 ГБ)
```

Известные Rust-хранилища + V8-хип ≈ 90 МБ, GPU Local Usage ≈ 465 МБ — сумма
≈ 555 МБ против 1.58 ГБ private bytes. **Гипотеза «V8-хип» из симптома
опровергнута**: V8-хип (80 МБ) — на два порядка меньше остатка (~1 ГБ),
никак не может быть основным потребителем. Остаток не GPU (уже вычтен) и не
известные Rust-кэши (уже вычтены) → либо C-heap фрагментация/аллокатор
(нужен counting-allocator, п.3 методологии), либо неучтённая Rust-структура
(DOM-дерево/CSSOM/display-list retained-состояние — 2381 DOM-узлов/6690
CSS-правил само по себе не должно давать гигабайты). Не воспроизведён рост до
2.9 ГБ на этом прогоне (одна вкладка, без взаимодействия, без скролла) — рост
в исходном отчёте мог требовать скролла/навигации/несколько минут SPA-полинга
или нескольких вкладок одновременно; следующая сессия должна воспроизводить
с более длинным/интерактивным сценарием и подключить временный counting
`#[global_allocator]` (см. методологию, п.3) для локализации оставшегося ~1 ГБ.
Инструмент (`LUMEN_MEM_REPORT`) теперь пригоден для этого — раньше был мёртв.

## Срез с counting-allocator + скролл-сценарием, 2026-08-06 (P3, вторая сессия дня)

Выполнена рекомендация предыдущего среза: временный counting
`#[global_allocator]` (обёртка над `System`, атомарный счётчик `alloc-dealloc`
байт, паттерн из [reference_memory_diagnosis_toolkit] п.3 — код жил только в
рабочей ветке `p3-bug-306`, **убран перед мержем**, в `main` не попал) выведен
новым полем `rust_alloc=` в строку `MEM_REPORT`; прогон — 4 минуты живого
скролла github.com (одна вкладка, `.tmp/bug306_probe.py`, MCP `scroll`
`{selector:"body"}` попеременно вниз/вверх раз в ~1.2с, `--mcp-live-port`,
`LUMEN_MEM_REPORT=1`, dev-release):

```
t=23.7с  ready              RSS=1392.6МБ  rust_alloc=988.9МБ
t=34.7с  +11с idle          RSS=1810.3МБ  rust_alloc=988.9МБ   (пик RSS, rust_alloc не растёт)
t=57.9с  scroll#10          RSS=1493.5МБ  rust_alloc=602.4МБ   (просадка -317/-386МБ после осадки)
t=278с   scroll done (190×) RSS=1500.8МБ  rust_alloc=602.5МБ   (плато, +7.3МБ за 4 мин скролла)
GPU Local Usage: 415.9МБ (старт) → 476.4МБ (конец, +60.5МБ — новые текстуры при скролле)
```

Три вывода:

1. **Скролл сам по себе НЕ воспроизводит раздутие до 2.9 ГБ** — одна вкладка
   github.com выходит на плато ~1.5 ГБ и держится там весь 4-минутный скролл
   (`rust_alloc` плоский 602.5 МБ, RSS ползёт на +7 МБ — это новые
   декодированные изображения/текстуры под скроллом, не утечка). Рост в
   исходном отчёте (2.9 ГБ) требует ЛИБО нескольких вкладок одновременно
   (исходный симптом: «610→2904 МБ» — это ДЕЛЬТА поверх уже открытых 6
   вкладок lenta, не абсолютное число одной вкладки), ЛИБО более длинного
   SPA-поллинга, чем 4 минуты — не воспроизведено в этом срезе, следующий шаг.
2. **RSS-пик сразу после ready (1810 МБ) — не рост Rust-кучи**: `rust_alloc`
   не меняется между `ready` и `+11с idle` (988.9→988.9), при этом RSS
   прыгает +418МБ и затем проседает −317МБ к `scroll#10`. Значит переходный
   скачок — GPU-коммит/драйвер при первом полном paint тяжёлой страницы или
   отложенное освобождение сетевых/декодерных буферов ОС, не Rust-аллокатор.
3. **Модель атрибуции предыдущего среза была занижена в ~6.7 раза.**
   Предыдущий срез суммировал только 5 «известных» Rust-хранилищ
   (`dl_cache`/`img_cache`/`prefetch`/`web_fonts`/`gifs` — те же поля, что
   `scripts/mem_perf.py`'s `_RUST_KEYS`) и получил ~90 МБ, отсюда вывод «весь
   остаток ~1 ГБ — не Rust». Реальная Rust-куча (по counting-allocator) на
   плато — **602.5 МБ**, а не 90 МБ: DOM-дерево/CSSOM/`ComputedStyle`/layout-box/
   display-list-source и Rust-обвязка JS-движка не входят ни в один из пяти
   счётчиков `debug_stats()`, но живут в той же куче. Уточнённая раскладка
   плато (RSS 1500.8 МБ): rust_alloc 602.5 + GPU 476.4 ≈ 1078.9 МБ атрибутировано,
   **остаток сузился с ~1 ГБ до ~422 МБ** (V8 внутренний C-heap/собственный
   аллокатор — V8 не обязан ходить через глобальный Rust-аллокатор,
   thread-стеки, TLS/сетевые буферы, фрагментация). `scripts/mem_perf.py`'s
   `rust_known_mb`/`unattributed_mb` столбцы остаются занижены/завышены
   соответственно тем же фактором, пока в него (или в `MEM_REPORT`) не попадёт
   постоянный counting-allocator — не сделано в этом срезе (временная
   инструментация, не мержилась).

**Дальше:** воспроизвести с несколькими одновременными вкладками (как в
исходном отчёте — 6 вкладок lenta + github) и/или дольше 4 минут SPA-поллинга;
если постоянный вывод `rust_alloc=` окажется нужен регулярно — заводить как
отдельную P1/P2 задачу (постоянный counting-allocator в движке), не решать
точечно в рамках одного диагностического среза P3.

## Срез 3, мульти-табовый репро + полная атрибуция, 2026-08-06 (P3, третья сессия дня)

Выполнена рекомендация среза 2. Вместо одной вкладки+скролла — воспроизведён
ТОЧНО исходный сценарий: MCP `new_tab` в порядке `docs/perf/corpus.txt`
(example, ya, hn, w3, rust-lang, lenta, github — тот же порядок, что дал
610→2904 МБ в `docs/perf/runs/2026-07-17-live.json`), с тем же временным
counting `#[global_allocator]`, что и в срезе 2 (код жил только в рабочей
ветке `p3-bug-306`, **убран перед мержем**), плюс дополнительно `gpu_local_mb()`
на каждом шаге (`scripts/mem_perf.py::gpu_local_mb`, `.tmp/bug306_multitab_probe.py`
— временный скрипт, не коммитился).

Плато через 5 с idle-hold после открытия 7-й (github) вкладки:

```
RSS=1750.6МБ  rust_alloc=1079.5МБ  js_malloc=77.9МБ  gpu=498.4МБ
неатрибуцировано = RSS − rust_alloc − js_malloc − gpu = 94.8МБ (5.4%)
```

Ряд по вкладкам (rss / rust_alloc / js_malloc / gpu):

```
example    545.4 /    — /    — / 417.9
ya         667.3 / 108.2 / 21.9 / 454.0
hn         694.4 / 114.2 / 10.6 / 455.7
w3         694.4 / 114.2 /    — / 455.7
rust-lang  733.4 / 140.1 /  9.0 / 458.8
lenta      823.6 / 189.5 / 19.9 / 464.1
github    2282.2 / 1079.0 / 77.9 / 487.7   (пик сразу после навигации)
hold+5с   1750.6 / 1079.5 / 77.9 / 498.4   (плато, держится весь 40с hold)
```

Три вывода:

1. **Память теперь атрибутирована почти полностью (94.6%, было ~73% в
   срезе 2).** `rust_alloc + js_malloc + gpu = 1655.8МБ` из `1750.6МБ` RSS.
   Гипотеза «V8-хип» окончательно опровергнута: `js_malloc` — 77.9 МБ, на
   порядок меньше `rust_alloc`. Остаток 94.8МБ (thread-стеки/TLS/сетевые
   буферы/фрагментация) достаточно мал, чтобы не требовать дальнейшей
   декомпозиции — вопрос «куда уходит память» для этого сценария закрыт.
2. **Механизм скачка 610→2904МБ из исходного отчёта воспроизведён и
   локализован: github.com сам по себе стоит ~890МБ Rust-кучи** (`rust_alloc`
   189.5МБ после 6 вкладок → 1079.0МБ после добавления github, Δ=889.5МБ),
   при этом известные кэши (`img_cache`/`prefetch`/`web_fonts`/`dl_cache`)
   дают лишь единицы МБ — вся разница живёт в НЕучтённых пятью счётчиками
   Rust-структурах: DOM-дерево, CSSOM, `ComputedStyle`, layout-box,
   display-list-source (см. вывод 3 среза 2, здесь подтверждён количественно
   для конкретной тяжёлой SPA-страницы). Одна вкладка github.com удерживает
   на два порядка больше Rust-памяти, чем более лёгкие сайты корпуса (108-190МБ
   у ya/hn/w3/rust-lang/lenta) — непропорционально даже для JS-тяжёлого SPA,
   заслуживает отдельного прицельного среза (перепись структур конкретно на
   github.com), но это уже узкая, а не расплывчатая задача.
3. **40-секундный idle-hold не снижает `rust_alloc` (плато держится ровно на
   1079.5МБ) — это ОЖИДАЕМО, не признак утечки.** `tab_lifecycle::manager.rs`
   переводит фоновую вкладку в T1 (`BackgroundRecent`) СРАЗУ при открытии
   следующей вкладки (`open_tab()` → `tab.hide()` + `advance_tier()`,
   `t0_to_t1_ms=0`) — то есть переход тира происходит мгновенно и корректно.
   Но T1 по документированному дизайну (`tab_lifecycle/state.rs:15-17`)
   **ничего не освобождает** («JS event loop paused (heap retained), layout
   retained, images retained»): реальное освобождение памяти начинается
   только с T2 (`t1_to_t2_ms` = 5 мин по умолчанию — JS heap → диск,
   картинки сбрасываются) и T3 (>30 мин — полный DOM-снапшот на диск).
   За 40 с ни один фоновый таб не мог дойти даже до T2, так что плоское
   плато — не баг lifecycle-машины, а ожидаемое поведение в пределах первых
   пяти минут.

**Итог по BUG-306:** диагностический гэп закрыт (было ~73% атрибуции без
`rust_alloc`, стало 94.6%). Корневая причина скачка 610→2904МБ — не утечка
и не V8-хип, а совокупность (а) полного удержания Rust-side DOM/CSSOM/layout
состояния КАЖДОЙ открытой вкладки, пока она не достигнет T2/T3 (архитектурно
ожидаемо в первые 5 минут — это дизайн, а не дефект) и (б) непропорционально
большого веса ОДНОЙ конкретной страницы (github.com, ~890МБ). (а) — это не
точечный P3-баг, а вопрос: должен ли T1 (0-5 мин) освобождать больше, чем
сегодня документировано, — архитектурное решение, домен P1. (б) —
самостоятельная, уже узко очерченная задача («перепись Rust-структур,
удерживаемых для github.com конкретно»), которую стоит завести отдельным
пунктом, если у P1/P3 найдётся время; сам BUG-306 в его исходной формулировке
(«куда уходит память») можно считать отвеченным.
