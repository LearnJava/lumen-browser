# BUG-743: `<style>`, вставленный после загрузки документа, не попадает в каскад

**Статус:** FIXED 2026-08-10
**Компонент:** shell (`crates/shell/src/main.rs` — `parse_and_layout` / `LayoutSource`)
**Найден:** P3 при разборе пункта 4 [BUG-733](BUG-733-FIXED.md), 2026-08-10

## Что происходит

Таблица стилей страницы собирается ровно один раз за навигацию:
`parse_and_layout` выполняет скрипты (`run_scripts_with_dom`), затем склеивает
инлайновые `<style>` (`extract_style_blocks`) с внешними `<link
rel=stylesheet>` и парсит результат в `LayoutSource::stylesheet`. Дальше этот
`Arc<Stylesheet>` живёт до следующей навигации и никогда не пересобирается.

Отсюда граница: `<style>`, добавленный **синхронным** скриптом на этапе разбора
(он успевает до сборки CSS), работает; всё, что вставлено позже —
из обработчика `load`, из `setTimeout`, из rAF, из промиса, из автоматизации —
не попадает в каскад **никогда**. Ни один селектор такого листа не срабатывает,
элемент остаётся с дефолтными стилями.

Локальное репро (`.tmp/b733_late.html`): четыре одинаковых правила
`position: fixed`, различается только момент вставки листа.

| Вставка листа | Результат |
|---|---|
| `<style>` в `<head>` разметки | `fixed` ✔ |
| `document.head.appendChild(style)` в inline-скрипте | `fixed` ✔ |
| то же в обработчике `load` | `static` ✘ |
| то же в `setTimeout` | `static` ✘ |
| то же из `eval` автоматизации | `static` ✘ |

Порядок мутаций значения не имеет: `textContent` до/после `appendChild`,
`appendChild(textNode)`, `innerHTML` у самого `<style>`, вставка в `<body>`,
`insertBefore` — все варианты одинаково работают до сборки CSS и одинаково
мертвы после.

Отдельный, более узкий дефект того же места: `<style>`, полученный **парсингом
`innerHTML`** (`div.innerHTML = '<style>…'`, затем перенос узла в `<head>`),
не работает никогда и вдобавок не виден `document.getElementsByTagName('style')`.
Заведён отдельно как [BUG-744](BUG-744-OPEN.md) — этим фиксом он не закрыт.

## Почему это важно

Это пункт 4 [BUG-733](BUG-733-FIXED.md) — cookie-баннер `tbank.ru` рисуется в
обычном потоке слева вверху вместо плавающей карточки справа внизу. Его правило

```css
.CookieConsentBannerDesktop_wrapper__8Mw8I { position: fixed; bottom: 16px; right: 16px; z-index: 200; }
```

лежит в 23-м из 28 `<style>` живой страницы (893 символа, ничего экзотического),
но в исходном HTML этого блока нет — его вставляет клиентский рендер после
загрузки. Движок текст видит (`style.textContent` его отдаёт), а каскад — нет.
Тот же механизм гасит любой CSS-in-JS (styled-components, emotion, CSS-модули с
клиентской вставкой) на любом сайте, поэтому чинится не для одной страницы.

## Как проверено

Живая проба на `tbank.ru`: свежий `<style>` с правилом по `id`, вставленный
через MCP `eval`, не применяется ни к баннеру, ни к специально созданному
контрольному `<div>` — то есть дело не в узле и не в селекторе, а в том, что
лист вообще не доезжает до каскада.

```
python .tmp/b733_late.py       # локально, печатает position/background для четырёх случаев
```

## Фикс (2026-08-10)

Каскад стал пересобираемым, но по-прежнему без сети.

* При загрузке (`parse_and_layout`) в `DynamicCssBase` откладывается всё, что
  инлайновые `<style>` изменить не могут: текст, притянутый их `@import`-ами
  (префикс — CSS Cascade L4 §6.5), и тела внешних `<link rel=stylesheet>`
  (суффикс). Префикс вырезается из результата `inline_css_imports` по
  инварианту «результат оканчивается исходным текстом» — он закреплён тестом
  `inline_css_imports_result_ends_with_source_text`.
* На каждом релейауте `Lumen::refresh_dynamic_css` сверяет дешёвый хэш
  инлайновых блоков (`inline_style_fingerprint` — обходит те же узлы, что
  `walk_style_blocks`, но не собирает строку). Совпал — не делается ничего;
  разошёлся — лист склеивается из памяти и парсится заново, а
  `page_prev_cascade_styles` сбрасывается, чтобы инкрементальный рестайл не
  переиспользовал стили от старого листа.
* Точки входа: `relayout`, `make_relayout_job` (снимок для движкового потока) и
  `try_relayout_raf_incremental` — последний при смене листа возвращает `false`,
  отдавая проход полному релейауту: новый лист может задеть любой узел.
* Пути восстановления (bfcache-thaw, разморозка вкладки, sidebar) получают
  `dynamic_css: None` и ведут себя как раньше — там сохранён только собранный
  лист, а не части, из которых он собран, так что пересборка молча потеряла бы
  внешний CSS.

Сеть в релейауте не трогается осознанно: `@import` и `@font-face` **внутри
нового** листа останутся незагруженными. Обычный CSS-in-JS ни того, ни другого
не использует; если понадобится — это отдельная задача с загрузкой в фоне.

Проверка: локальное репро — все четыре случая `fixed` с верным фоном. Живая
`tbank.ru`, три прогона подряд одинаково: баннер `position: fixed`,
`bottom: 16px`, `right: 16px`, `z-index: 200`, белый фон,
`CookieConsentBannerDesktop_row__5T0nW` — `display: flex` (было: `static`,
прозрачный, `block`). Дампы display list по 12 эталонам не изменились
(`dump_golden.py` — 12/12 PASS): страницы гейта не вставляют `<style>` из
скриптов, поэтому отпечаток на них не меняется и пересборка не запускается.

Пункт 4 [BUG-733](BUG-733-FIXED.md) этим **не закрыт**: баннер встал в поток
плавающих боксов, но рисуется полосой во всю ширину вьюпорта со сдвигом влево —
[BUG-745](BUG-745-FIXED.md) (нет shrink-to-fit у абсолютно позиционированного
бокса).
