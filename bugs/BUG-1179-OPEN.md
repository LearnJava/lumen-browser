# BUG-1179 — imdb: страница челленджа остаётся документом 26–88 с после получения настоящей

**Статус:** OPEN
**Заведён:** 2026-09-25 (P6, по ходу закрытия [BUG-493](BUG-493-FIXED.md); видимое окно `--maximized`,
`LUMEN_NO_ADBLOCK=1`, Chrome 153 тем же способом).
**Область:** не локализовано — между концом загрузки HTML (`Streaming завершён, финальный
pipeline (off-thread)`) и коммитом документа. Кандидаты: финальный pipeline на HTML 1.4 МБ,
исполнение ~25 синхронных скриптов Next.js, ожидание чего-то в очереди движкового потока.

## Симптом

`https://www.imdb.com/` → `202` + челлендж AWS WAF → `verify` → повторный `GET` → `200`, тело
1 378 770–1 395 397 байт. Опрос `eval` каждые 4–10 с (`.tmp/b493/poll.py` в слоте `p6-work`):

| Прогон | Последний опрос со старым документом (13 узлов, `title` пуст) | Первый опрос с настоящим | `[bench] first non-empty frame` |
|---|---|---|---|
| imdb2 | 73 с | 88 с (1971 узел) | 86.7 с |
| imdb3 | 37 с | 58 с (1960 узлов) | 56.6 с |
| imdb4 (`LUMEN_PROFILE_TREE=1`) | 26 с | 38 с (1977 узлов) | 37.2 с |

При этом в imdb3 все 35 подресурсов настоящей страницы (CSS, чанки Next.js) запрошены уже к
9-й секунде, а число запросов между 9 и 29 с не растёт. Окно всё это время показывает пустую
страницу челленджа. Chrome 153: `load` за 21.7 с, 5331 узел.

`LUMEN_PROFILE_TREE=1` (imdb4) между `Streaming завершён` и первым кадром печатает только один
`layout_measured_hyp` на 20 мс — время уходит не в layout.

## Что сделать

1. Разложить интервал «тело получено → документ закоммичен» по фазам: разбор HTML, каскад,
   исполнение каждого синхронного скрипта (время на скрипт), ожидание сети. Подходящие
   инструменты — `LUMEN_V8_PROFILE=1` и `[engine] task`-лог (BUG-935).
2. По результату — чинить самую дорогую фазу или заводить её отдельно.

Критерий: на imdb настоящий документ становится текущим не позже чем через ~2× Chrome от
навигации, и разброс между прогонами объяснён.
