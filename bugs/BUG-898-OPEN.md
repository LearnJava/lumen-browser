# BUG-898 — декодер WebAssembly материализует объявленное число локальных переменных без всякой границы: 32-байтный модуль стоит 6,95 с и гигабайты памяти (форма DoS)

**Статус:** OPEN
**Заведён:** 2026-08-23 (WPT-RUN-6, срез 29 — живой замер, варианты `wasm-corpus`/`wasm-corpus-split`/`wasm-decode` + выборка стека)
**Область:** js (`crates/js/src/wasm/parser.rs:653-661` — `parse_code_section`: `let n = r.u32()?;` затем `for _ in 0..n { locals.push(ty) }`, где `n` — недоверенное 32-битное число из тела модуля)
**Владелец:** P1/P3. Заведён P2 в ходе WPT-задачи, здесь не чинится.

## Симптом

Один вызов `WebAssembly.validate()` на 32-байтном модуле занимает **6,95 с**.
Байты (первые 24 из 32):

```
00 61 73 6d 01 00 00 00   ← magic + version
01 04 01 60 00 00         ← type section: () -> ()
03 02 01 00               ← function section
0a 0c 01 0a 02 ff ...     ← code section: тело, 2 группы локальных, число = ff…
```

Декодер читает LEB128-число локальных переменных группы и тут же кладёт
столько элементов в `Vec`. Объявленное число ничем не ограничено, поэтому
модуль в тридцать два байта заставляет движок выполнить ~4·10⁹ `push` и
попытаться выделить под них память. Ни спецификационного предела (JS API:
50 000 локальных на функцию), ни проверки «объявлено больше, чем осталось
байт» в коде нет.

Это не только медленно — это форма отказа в обслуживании: страница вешает
вкладку тридцатью двумя байтами, без сети и без большого файла.

## Цена по WPT

`wasm/core/bulk-memory/memory_copy.wast.js.html`,
`wasm/core/memory64/memory_copy64.wast.js.html`. Автономный прогон под

декодере, а не в объёме.

## Что дальше

Две независимые правки в `parse_code_section`: (1) отвергать объявленное
число локальных, если оно больше остатка байтов тела — оно физически не может
быть закодировано; (2) применить предел реализации (50 000 на функцию, как в
JS API), возвращая `Err`, а не выделяя память. Тот же аудит стоит сделать по
всем `for _ in 0..count` этого файла: `count` в каждой секции приходит из
модуля.
