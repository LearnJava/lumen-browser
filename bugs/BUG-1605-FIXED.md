# BUG-1605 — UX-CHROME-PANELS: панель спецвозможностей (`#accessOverlay`, Ctrl+Shift+Q) не появляется в живом окне

**Статус:** FIXED 2026-10-11
**Заведён:** 2026-10-11 (живая проверка UI-работы P6 за 2026-10-09/10; регрессия найдена `git bisect`)
**Область:** shell/chrome (`crates/shell/src/chrome_ui.rs` — `take_content_area`/`salvage_layout_boxes`, сборка модели; `assets/chrome/chrome.html` — `#accessOverlay`; `crates/chrome/src/model.rs` — `bind_access`)
**Внёсший коммит:** `ff845dc05` «UX-CHROME-PANELS срез 2: панель спецвозможностей в движковом chrome» (в `main` — слияние `4098869e9`)

## Симптом

В живом окне Ctrl+Shift+Q не показывает ничего: ни модала, ни затемнения контента. До `ff845dc05` по тому же сочетанию открывалась центрированная панель «Accessibility» (размер шрифта, reduced motion, forced colors, курсор) с затемнённым фоном. Воспроизводится и на текущем `main` `e1c2cd96a`.

## Что изменил `ff845dc05`

- Удалил легаси-отрисовку `panels::a11y_panel::build_a11y_panel` из `redraw_requested.rs` (блок `if self.a11y_panel.visible { … overlay_buf.append(…) }`).
- Ввёл модал `#accessOverlay` (`.modal-overlay`, `position:absolute; inset:0`) внутри `#contentArea` в `chrome.html`; состояние — `ChromeAccessModel { open: a11y_panel.visible, … }`, `.open` ставит `bind_access` ([model.rs:2260](../crates/chrome/src/model.rs#L2260)).
- Добавил `ACCESS_OVERLAY` в список `take_content_area`, который должен вынести модал из `#contentArea` в дерево chrome ([chrome_ui.rs:259](../crates/shell/src/chrome_ui.rs#L259)).

Старый путь удалён, а новый до кадра не доходит. Модульные тесты модели (`model.rs`: `.open` на `#accessOverlay`) проходят — живой отрисовки они не проверяют. Корневая причина (класс не выставляется в живом цикле / бокс не переживает `take_content_area` / модал не попадает в слой chrome поверх страницы) **не установлена**.

## Воспроизведение

1. Скопировать `lumen.exe` в пустую папку (чтобы не трогать `data/` рабочего профиля), рядом `python -m http.server 8137` со страницей `en.html` (белый фон, заголовок «Hello world»).
2. `LUMEN_NO_ADBLOCK=1 lumen.exe --maximized http://127.0.0.1:8137/en.html`, подождать 2.5 с.
3. Нажать Ctrl+Shift+Q (настоящий ввод — SendInput, без MCP), подождать 2 с, снять окно.
4. Ожидается: центр страницы затемнён оверлеем, по центру — модал. Фактически: кадр не изменился.

Метрика автоматической проверки — средняя яркость прямоугольника `(400,300)–(1400,800)` окна 1920×1017: до регрессии 255 → 169 (оверлей), после — 255 → 255.

## Корневая причина и исправление (2026-10-11)

Дело не в `#accessOverlay`, а во всех всплывающих блоках из `#contentArea` (`SALVAGED_POPOVER_IDS`: строка поиска, палитра, модалы, панели DevTools, приватность, «Прочитать позже», меню вкладки и др.). `relayout_chrome_host` оставляет их в дереве chrome, а `build_chrome_overlay_strips` режет весь `chrome_dl` четырьмя полосами вокруг `chrome_page_host_rect` — все они лежат внутри этого прямоугольника, поэтому не рисовались. Раньше их перекрывал легаси-оверлей, который срезы UX-CHROME-PANELS удаляли по одному. Живой проверки (SendInput + захват окна) у срезов не было — только модельные тесты.

Исправление: на время рисования chrome те же блоки отцепляются из `layout` (`take_floating_panel`), рисуются отдельным списком `chrome_popover_dl` по z-index без клипа и возвращаются в дерево (хит-тест и инкрементальный базис видят их на месте). `redraw_requested.rs` кладёт список в `overlay_buf`. Заодно `FindOpen` (Ctrl+F, vim `/`) не вызывал `relayout_chrome_host` — строка поиска не получала `.open`.

Проверено вживую (`.tmp`-зонд, SendInput, `--maximized`): Ctrl+Shift+Q, Ctrl+K, Ctrl+F, F12, Ctrl+Shift+Y, Ctrl+Shift+E, список профилей, кнопка перевода — каждое меняет кадр. Найдено попутно: [BUG-1607](BUG-1607-OPEN.md) (модал сплющен), [BUG-1608](BUG-1608-FIXED.md) (красный тест на `main`).
