# BUG-750 — перебор каталога отдаёт handle-ы без гранта: `getFile()` на элементе листинга возвращает пустой `File`, а спуск на подкаталог — `NotAllowedError`

**Статус:** OPEN
**Компонент:** js (`crates/js/src/filesystem_access.rs` — `FileSystemDirectoryHandle.prototype.entries`, и производные от неё `values`/`keys`)
**Найден:** P3, при закрытии [BUG-372](BUG-372-FIXED.md), 2026-08-10

## Симптом

`entries()` читает список каталога нативом `_lumen_dir_entries`, но строит из
него handle-ы с пустым грантом:

```js
var handle = e.kind === 'directory'
  ? new FileSystemDirectoryHandle(e.name, '')
  : new FileSystemFileHandle(e.name, '', 0);
```

Такой объект — настоящий экземпляр настоящего класса, у него верные `name` и
`kind`, он проходит `instanceof`, у него есть все методы. Но:

* `getFile()` резолвится пустым `File` (пустой токен читается ничем);
* `getFileHandle()`/`getDirectoryHandle()` на нём отвечают `NotAllowedError`
  (пустой `pathId` не найден в `DIR_REG`);
* `isSameEntry()` всегда `false` — сравнение по пустому идентификатору
  отбрасывается явной проверкой `mine.pathId !== ''`.

То есть основной способ обхода дерева —

```js
for await (const [name, handle] of root.entries()) { … }
```

— возвращает объекты, которые выглядят рабочими и молча дают неверные данные.
Признак ровно тот же, что закрывала [BUG-372](BUG-372-FIXED.md).

## Почему это не просто «недоделка»

Для каталога, выбранного пользователем через `showDirectoryPicker()`, это
**сознательное** ограничение [BUG-371](BUG-371-FIXED.md): листинг не должен сам
по себе выдавать право чтения на всё содержимое каталога — иначе один диалог
превращается в грант на поддерево. Комментарий в коде так и говорит: вызывающий
обязан перезапросить запись по имени через `getFileHandle`/`getDirectoryHandle`.

Но после BUG-372 тем же кодом ходят по **OPFS** — песочнице самого origin, где
выдавать нечего: страница уже владеет всем деревом, и перезапрос по имени вернёт
ей ровно тот же грант. Здесь ограничение не защищает ничего и только ломает
штатный обход.

## Ожидается

`entries()`/`values()`/`keys()` отдают handle-ы, которыми можно пользоваться —
по крайней мере в пределах writable-гранта.

Правка (любая из двух):

* выдавать грант при перечислении, если у родительского гранта
  `DirGrant::writable == true` (OPFS — да, выбранный каталог — нет);
* либо не выдавать заранее, а до-запрашивать по имени лениво внутри `next()`
  тем же нативом, что и `getFileHandle` — тогда правило «грант выдаётся на
  явный запрос по имени» сохраняется буквально, и разница между двумя видами
  каталогов исчезает сама.

Второй вариант ближе к тому, что делают браузеры, и не требует новой развилки в
модели прав.

## Заметки

* Async-итерация как таковая (`Symbol.asyncIterator`, наследование от
  `FileSystemHandle`, WebIDL-форма классов) — отдельная заявка
  [BUG-374](BUG-374-OPEN.md); здесь речь только о содержимом выдаваемых
  handle-ов.
