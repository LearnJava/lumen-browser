# BUG-770 — живое окно намертво встаёт на 24-й странице прогона графтестов: харнесс перестал читать stderr, труба заполнилась, `eprintln!` заблокировал UI-поток

**Статус:** OPEN
**Компонент:** test-harness (`graphic_tests/run.py`, `LiveWindowClient.__init__` /
`_drain_stderr`) — первичная причина; shell/paint (запись в stderr с UI-потока) — вторичная
устойчивость
**Найден:** 2026-08-12 (P3), при попытке снять пиксельный гейт полного прогона графтестов для
[BUG-405](BUG-405-OPEN.md) срез 5

## Симптом

`python graphic_tests/run.py --continue-on-fail` (live-режим, дефолт) доходит до TEST-22 и
встаёт: **окно перестаёт отвечать вообще** (это видно и глазами — пользователь сообщил
«приложение зависает и не отвечает… зависло на тесте 22 transform»), а прогон печатает

```
TEST-22: PASS (0.00%)
TEST-23: ERROR (live: tools/call: {'code': -32603, 'message': 'Wait error: automation command timed out'})
TEST-24: ERROR (live: … 'Navigate error: automation command timed out'})
…
TEST-153: ERROR (live: [WinError 10054] Удаленный хост принудительно разорвал существующее подключение)
```

Итог: **130 из 153 тестов ERROR**, то есть полного прогона графтестов сейчас не существует ни
для кого — «дельта vs предыдущий прогон» тоже врёт («Изменений нет», потому что сравниваются
два одинаково сломанных прогона).

Воспроизводится детерминированно: два полных прогона встали на одном и том же тесте.
`run.py --only 23` при этом **PASS** — дело не в странице.

## Механизм (измерен, не предположен)

1. `LiveWindowClient.__init__` (`graphic_tests/run.py:1028`) поднимает окно с
   `stderr=subprocess.PIPE, text=True` — **без `encoding=`**, поэтому Python декодирует
   поток кодировкой консоли (здесь `charmap`/cp1252), а Lumen печатает в stderr русские
   строки в UTF-8.
2. `_read_token` вычитывает первые строки и отдаёт остаток фоновому потоку `_drain_stderr`.
   На первой же не-ASCII строке поток умирает:
   `UnicodeDecodeError('charmap', b'DX12: present=ok … (496 \xd0\xbc\xd1\x81) \xe2\x80\x94 …', 89, 90, 'character maps to <undefined>')`
   — и `except Exception: pass` в `_drain_stderr` **глотает это молча**. Замер: поток
   прочитал **2 строки** и умер, `alive False`.
3. Трубу больше не читает никто. Lumen продолжает писать в stderr, буфер трубы Windows
   (единицы КБ) заполняется, и очередной `eprintln!` блокирует **пишущий поток**.
4. Пишет UI-поток, поэтому окно встаёт целиком: автоматизация не обслуживается
   (`automation command timed out`), затем соединение рвётся (10054). Номер теста
   детерминирован, потому что детерминирован объём stderr до этого момента.

### Что отделяет причину от совпадений

Пробники (`.tmp/hang*.py` в сессии, цикл один и тот же — `navigate` + `wait document_ready`
по списку `TESTS` в его порядке):

| пробник | stderr окна | результат |
|---|---|---|
| свой клиент, те же флаги окна (`--no-scrollbar --deterministic --viewport 1024x720`) | в **файл** | 30 страниц, зависания нет |
| свой клиент + полный цикл `capture_lumen_live` (settle → `_bring_pid_to_front` → gdigrab) | в **файл** | 30 страниц, зависания нет |
| свой клиент, простой 240 с при живом окне, затем навигации | в **файл** | зависания нет (не «по времени») |
| **`rp.LiveWindowClient` из run.py** (PIPE + поток-дренаж), цикл без Edge/diff | в **трубу** | **HANG на #23**, ровно как в полном прогоне |

То есть отличие ровно одно — кто и как читает stderr окна.

## Как воспроизвести

```bash
LUMEN_PROFILE=dev-release python graphic_tests/run.py --continue-on-fail   # встанет на TEST-23
```

Минимальный репро без ffmpeg/Edge — поднять окно клиентом харнесса и просто ходить по
страницам:

```python
import sys, os, glob, time
sys.path.insert(0, 'graphic_tests')
import run as rp
port = rp._free_tcp_port()
c = rp.LiveWindowClient(rp.LUMEN, rp.REPO, port)          # stderr=PIPE, text=True
for p in sorted(glob.glob('graphic_tests/[0-2][0-9]-*.html')):
    c.navigate('file:///' + os.path.abspath(p).replace(chr(92), '/'))
    c.wait_document_ready()                               # таймаут на ~24-й странице
    print(p, flush=True)
```

## Куда чинить

1. **Харнесс (P2, `graphic_tests/run.py`) — снимает симптом.** `Popen(..., text=True)` обязан
   получить `encoding='utf-8', errors='replace'`: русские строки Lumen тогда декодируются, а
   любой битый байт не роняет чтение. `_drain_stderr` не должен глотать исключение — молчаливая
   смерть дренажа и есть то, из-за чего дефект выглядел как зависание движка на конкретной
   странице. Тот же дефект возможен в любом другом месте, где харнесс держит `stderr=PIPE`
   (проверить `LumenIpcClient`, `graphic_tests/run.py:864`).
2. **Движок (P3/P1) — устойчивость.** Браузер не обязан вставать намертво из-за того, что
   потребитель его stderr перестал читать: диагностическая печать с UI-потока — блокирующая
   операция над трубой, которой владеет чужой процесс. Варианты: писать диагностику из
   отдельного потока через неблокирующую очередь (терять строки, а не кадры), либо не печатать
   ничего кроме фатального с UI-потока. Отдельный вопрос — стоит ли `[probe]`/`[engine-thread]`
   печатать вообще без `LUMEN_FRAME_LOG`.

## Последствия для гейтов

Пока баг открыт, «полный прогон графтестов» как пиксельный гейт недоступен: 130 из 153 тестов
ERROR по причине, не связанной с проверяемой правкой. Замена, применённая в BUG-405 срез 5 —
свип wgpu-рендера всех 159 страниц через `Renderer::render_to_image` (headless GPU) с
побайтовым сравнением плеч A/B; ограничение свипа описано там же.
