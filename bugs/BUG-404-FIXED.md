# BUG-404 — `flush_pointer_moves` использует захардкоженную геометрию вместо `page_offset()`

**Статус:** FIXED 2026-07-31
**Компонент:** shell (`crates/shell/src/main.rs::flush_pointer_moves`, right-click tab context menu, `tabs/strip.rs`)
**Найден:** P1, скоупинг CC-15 (2026-07-28), при аудите зависимостей от `toolbar::CHROME_H`

## Закрытие (P1, 2026-07-31)

Проверка сайтов из этой находки:

1. **`flush_pointer_moves`** — уже переведён на `page_point()`/`page_offset()` попутно фиксом
   BUG-437 (см. комментарий на месте вызова, `main.rs:16880-16884`): «same conversion as
   `handle_click_at` — `page_point()`, not the legacy `left_dock()`/`CHROME_H` pair». Отдельного
   изменения не потребовалось, симптом из этой находки больше не воспроизводится.
2. **Правый клик по вкладке** (второй сайт, CC-15-3) — исправлен: индекс вкладки под курсором
   теперь резолвится через `Lumen::chrome_hit_test(x_css, y_css)` + поиск ближайшего предка с
   атрибутом `data-tab-id` (`Lumen::chrome_data_id`), тот же приём, что `ChromeAction::SelectTab`
   уже использует для левого клика (`main.rs`, ветка `MouseInput(Pressed, Right)`). Больше не
   зависит от `TAB_BAR_HEIGHT`/`ARCHIVE_BTN_W`/`LAYOUT_BTN_W`/`SETTINGS_BTN_W`.
   Это был последний живой потребитель `tabs::strip::hit_test`/`TabHit` — CC-15-3 не смогла их
   удалить именно из-за этого сайта (см. её комментарий, ранее в шапке этого файла). Удалены
   вместе с приватными хелперами, ставшими мёртвыми (`tab_x_range`, `adblock_cb_x_range`,
   `TAB_PAD`, `CLOSE_SZ`, `ADBLOCK_CB_SZ`) и четырьмя их юнит-тестами. `cargo clippy -p lumen-shell
   --all-targets -- -D warnings` чист, `cargo test -p lumen-shell` (пакет `tabs::strip`) — 48/48
   OK. Ручная проверка правого клика мышью не выполнена (нет автоматизации правого клика в MCP —
   `docs/automation.md` не документирует такой tool); фикс проверен на уровне кода — зеркалирует
   уже рабочий и покрытый левым кликом путь `ChromeAction::SelectTab`.
3. **Три оставшихся сайта** (командная палитра / щиты / разрешения, CC-15-4) — при разборе
   выяснилось, что это не тот же класс бага (не всегда `CHROME_H`-дрейф; для командной палитры
   и вовсе не зависит от него) и не сводится к замене офсета — `.cp-row` не несёт `data-action`
   вовсе, так что просто гейтировать/удалить легаси-хит-тест сломает активацию строк палитры.
   Нужен либо замер реального layout-rect chrome-узла, либо новые `ChromeAction`. Вынесено в
   отдельный баг — [BUG-461](BUG-461-OPEN.md) — с деталями, почему это не быстрый фикс.

## Симптом

`flush_pointer_moves()` (`main.rs:17562-17593`) — реальный (не automation-only) путь, который на
каждый `about_to_wait` разбирает буфер `pointermove`-семплов и диспатчит `mousemove` в DOM. Расчёт
page-координат:

```rust
let panel_x_offset = self.left_dock().map_or(0.0, |(_, w)| w);
let page_x = (x_css - panel_x_offset) + self.scroll_x;
let page_y = (y_css - toolbar::CHROME_H) + self.scroll_y;
```

использует `self.left_dock()`/`toolbar::CHROME_H` напрямую — те же две величины, которые CC-5 уже
объединила в `page_offset()` (`main.rs:9394-9402`) именно потому, что под `css_chrome_enabled == true`
правильный офсет — это измеренный `chrome_page_host_rect` (x, y) движкового хрома, а не константа
`CHROME_H`/`left_dock()`. `left_dock()` также не включает ширину открытого AI/Web-сайдбара
(`chrome_page_host_rect.x` — включает, CC-10b).

Это тот же класс бага, что CC-14 нашла и исправила в `resolve_automation_target` (MCP/BiDi `click`/`type`,
`main.rs:23916`, доккомент прямо на это ссылается) — но `flush_pointer_moves` не был проверен/исправлен
в том же срезе. В отличие от automation-пути, это затрагивает **обычную живую мышь** — каждый
`mousemove`/hover под движковым хромом (дефолт с CC-14) координируется потенциально неверно, особенно
при открытом AI/Web-сайдбаре (X-офсет) или если реальная высота движкового хрома отличается от
константы `CHROME_H` (Y-офсет).

## Второй сайт того же класса (найден P1, CC-15-3, 2026-07-28)

Правый клик по вкладке (открытие контекстного меню вкладки, `main.rs`, ветка
`MouseInput(Pressed, Right)`) хит-тестит полосу **легаси**-геометрией и без гейта:

```rust
let tab_area_w = self.viewport_width_css()
    - tabs::archive::ARCHIVE_BTN_W
    - tabs::strip::LAYOUT_BTN_W
    - tabs::strip::SETTINGS_BTN_W;
if let tabs::strip::TabHit::Tab(idx) =
    tabs::strip::hit_test(&self.tab_strip, x_css, y_css, tab_area_w)
```

`strip::hit_test` считает, что полоса занимает `y = 0..TAB_BAR_HEIGHT` (константа 36 px), а
вкладки равномерно делят `tab_area_w`, вычтя ширины трёх легаси-кнопок, которых в движковом
хроме нет. Реальная раскладка вкладок движкового хрома — это layout-бокс `#tabStrip`, её
геометрию нужно брать из хит-теста хрома (`chrome_hit_test` + `data-tab-id`), как это уже
делает левый клик. Под дефолтным хромом правый клик поэтому попадает в вкладку с неверным
индексом (или мимо).

Именно из-за этого живого потребителя CC-15-3 **не** удалила `strip::hit_test`/`TabHit`,
хотя строка задачи CC-15-3 их перечисляла: удаление сломало бы контекстное меню совсем.
Их можно снять только вместе с фиксом этого сайта.

## Третий-пятый сайты того же класса — оверлеи (найдены P1, CC-15-4, 2026-07-28)

Хит-тесты трёх оверлеев вызываются **без гейта** `!css_chrome_enabled`, легаси-геометрией, и
безусловно `return`-ят после попадания, то есть съедают клик:

| Оверлей | Сайт в `main.rs` | Легаси-геометрия |
|---|---|---|
| Командная палитра | `command_palette::hit_test` (ветка `MouseInput(Pressed, Left)`) | `box_origin(viewport_w)`, строки по `ROW_H` от верха бокса |
| Щиты | `shields_panel::hit_test` | прямоугольник 220×90 в правом верхнем углу, `y = toolbar::CHROME_H + 4` |
| Разрешения | `permission_panel::hit_test` | прямоугольник в левом верхнем углу, `y = toolbar::CHROME_H + 4` |

Под дефолтным движковым хромом эти оверлеи рисует хром (`#cpOverlay`, `#permPopover`), а их
реальные боксы задаёт CSS, не эти константы. Пока оверлей открыт, клик в *старом* прямоугольнике
поглощается невидимым легаси-хит-тестом и не доезжает ни до страницы, ни до DOM хрома; для
палитры это ещё и активация строки по неверному индексу (легаси-раскладка строк не совпадает с
`.cp-row` хрома) либо ложное закрытие.

Поведение существует с флипа CC-14 — CC-15-4 (удаление покраски этих панелей) его не меняет, а
только делает очевидным: панели больше не рисуются, а кликам всё ещё отвечают. Именно поэтому
CC-15-4 **не** удалила эти три `hit_test` вместе с билдерами.

## Причина

`page_offset()` появился в CC-5 (после `flush_pointer_moves`, судя по всему, уже существовавшего с
захардкоженной формулой) — единая точка не была ретроактивно применена ко всем более старым
координатным сайтам, только к новым/найденным при последующих аудитах (CC-14 нашла один такой —
`resolve_automation_target` — но не искала остальные систематически).

## Что нужно сделать

Заменить обе строки на `let (page_x_offset, page_y_offset) = self.page_offset();` (тот же паттерн,
что `resolve_automation_target` использует после фикса CC-14) и пересчитать `page_x`/`page_y`
соответственно. Стоит грепом проверить main.rs на другие оставшиеся прямые использования
`toolbar::CHROME_H`/`left_dock()` в живых (не automation, не legacy-only-гейтированных) путях — есть
шанс, что это не единственный оставшийся сайт (не проверено полностью в рамках этой находки, скоупинг
CC-15 не ставил целью исчерпывающий аудит всех вызывающих мест).
