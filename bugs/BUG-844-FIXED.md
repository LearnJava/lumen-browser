# BUG-844 — EventSource: поток, законченный телом ответа (`Content-Length`, а не закрытием сокета), не считается законченным — ни `error`, ни переподключения; а на переподключениях, которые всё же происходят, не стреляет `open`

**Статус:** FIXED 2026-08-25
**Заведён:** 2026-08-22 (WPT-RUN-6, срез 22 — найден живым замером, есть маркер `eventsource-no-reconnect`)
**Область:** `crates/network/src/sse.rs:393` (переподключение — только по завершению чтения соединения), `crates/js/src/dom.rs:7521` (`_lumen_sse_pump_one`, ветка `ev.t === 'open'`), `crates/js/src/dom.rs:7538` (ветка `close` — переподключение шима)
**Владелец:** P1/P3 (`lumen-network` + `lumen-js`). Заведён P2 в ходе WPT-задачи, здесь не чинится.

## Симптом

Ответ вида «HTTP/1.1 200, `Content-Type: text/event-stream`,
`Content-Length: N`, соединение keep-alive» — именно так отвечает **любой**
`.py`-обработчик под `wptserve` (`eventsource/resources/message.py`,
`last-event-id.py`):

```js
var es = new EventSource('resources/message.py?message=retry%3A3000%0Adata%3Ax');
es.onopen = () => console.log('open');       // приходит ровно один раз
// поток кончился — но readyState остаётся 1 (OPEN) навсегда,
// `error` не приходит, переподключения нет
```

А на пути, где поток заканчивается закрытием сокета, переподключение есть, но
`open` больше не стреляет ни разу.

## Прямое измерение

`tests/wpt/verify_perf_idb_sse_gaps.py` (2026-08-22, dev-release, Linux,
коммит `bafa603d9`, `--seconds 6`, страницы живы — 11 тиков). Пробный сервер
записывает каждое соединение, поэтому «переподключения не было» доказано
независимо от страницы:

| вариант | ожидалось | получено |
|---|---|---|
| `sse-lengthed` (форма `wptserve`) | `sse-open` ×2 | `sse-open` ×1, `sse-message data=lengthed`, `sse-lengthed-checked readyState=1`; сервер видит **одно** соединение за 6 с |
| `sse-reconnect-onopen` (поток закрыт сокетом) | `sse-open n=2 at≈400` | `sse-open n=1 at=32`, `sse-opens-total 1`; сервер видит **14** соединений с шагом ≈400 мс |

То есть обе половины контракта расходятся с наблюдаемой реальностью в разные
стороны: там, где переподключение обязано быть, его нет; там, где оно есть,
о нём не сообщают.

Контроль: доставка сообщений, `lastEventId` и отправка `Last-Event-ID` на
переподключении работают (`sse-basic`, `sse-id-reconnect` — заголовок
`Last-Event-ID: 42` виден на сервере), `retry:` без пробела после двоеточия
парсится верно (шаг 400 мс из `retry:400`).

## Причина (локализована чтением кода)

`crates/network/src/sse.rs:393` переподключается после того, как **чтение
соединения завершилось**. Для HTTP/1.0-ответа это закрытие сокета, а для
keep-alive-ответа с `Content-Length` конец тела не завершает соединение —
цикл продолжает ждать байты, которых не будет. Спека (HTML LS §9.2.5
«reestablish the connection») говорит про конец *потока*, а не сокета.

Второй фасет — в шиме:

```js
// dom.rs:7521
if (ev.t === 'open') {
    if (es._readyState === 2) { continue; }
    es._readyState = 1;
    _lumen_sse_fire(es, 'open', new Event('open', …));
```

сам по себе он корректен, но после переподключения из ветки `close`
(`dom.rs:7538`) новое соединение открывается вызовом `_lumen_sse_connect`
напрямую, и события `open` в очередь не попадает — измерение показывает 14
соединений и один `open`.

## Масштаб

Маркер `eventsource-no-reconnect` в `tests/wpt/timeout_audit.py` — **8 id**
остатка снимка WPT-RUN-5, то есть весь `eventsource`-остаток:
`format-field-retry`, `format-field-retry-bogus`, `format-field-id`,
`format-field-id-2`, `format-data-before-final-empty-line`,
`format-field-id-null.window`, `eventsource-reconnect.window`,
`eventsource-close.window`. Каждый из них ждёт либо второго `open`, либо
второго сообщения — то есть переподключения, которого под `wptserve` не
происходит вовсе.

## Направление починки (не предписание)

Считать поток законченным по концу тела ответа (в том числе при keep-alive),
а не только по закрытию сокета, и после переподключения класть в очередь
событие `open` — тем же путём, каким его кладёт первое соединение.

## Как проверить фикс

1. `tests/wpt/.venv/bin/python tests/wpt/verify_perf_idb_sse_gaps.py --variant
   sse-lengthed --variant sse-reconnect-onopen` — ожидаются несколько
   соединений в `sse connects` для первого и `sse-open n=2` для второго.
2. WPT: `run_report.py --all --root eventsource` — семейства
   `format-field-retry*`/`format-field-id*` должны перестать быть TIMEOUT.

## Починено (P1, 2026-08-25)

Заявка называла два дефекта (поток не кончается; `open` не стреляет на
переподключении), и оба на месте — но починка каждого упирается в то, что
раньше в коде вообще не было выражено.

**1. Где кончается поток — решает обрамление тела, а не сокет.** `fill_queue`
читал `stream.read(&mut buf)` до нуля, то есть считал концом потока только
закрытие соединения. По RFC 7230 §3.3.3 это верно ровно для одного из трёх
случаев; при `Content-Length` и при `chunked` тело кончается, а сокет живёт —
и это форма любого `.py`-обработчика `wptserve`. Введён `SseFraming`
(`Length`/`Chunked`/`Eof`), выбираемый по заголовкам ответа, и `read_body`,
который отдаёт `Ok(0)` по концу ТЕЛА. `Transfer-Encoding` выигрывает у
`Content-Length` (§3.3.3 п. 3).

**2. `open` на переподключении.** Событие `open` клалось в очередь руками —
один раз, при создании сессии (`JsSseSessionImpl::new`), — а переподключение
живёт внутри `next_event` и об этом ходе ничего не знало. Поэтому источником
`open` стал сам обработчик соединения: `EventSource::connect_stream` уже
публиковал `Event::SseConnected` на каждое announce-соединение, и добавленный
`JsSseControlSink` превращает его в `JsSseEvent::Open`. Ручной первый `Open`
убран — иначе первое соединение отдавало бы два. Очередь поэтому создаётся ДО
рукопожатия и передаётся в `JsSseSessionImpl::new` снаружи.

**3. Третий дефект, которого заявка не называла: `close` означал два разных
события.** Шим на `JsSseEvent::Close` фиксировал `error` и САМ планировал
переподключение через `setTimeout` — то есть переподключение существовало в
двух местах сразу, а нативная сессия про это не знала. Разведено на два
события: `Reconnecting` («поток кончился, сессия переустанавливает
соединение») → `readyState = CONNECTING` + `error`, как требует HTML LS §9.2.5
шаг 1; `Close` остался терминальным (страница позвала `close()`). Шимовый
таймер переподключения и флаг `_reconnecting` удалены — переподключение теперь
ровно в одном месте.

**4. `retry:` действует с момента разбора поля, а не с диспатча события**
(§9.2.6): поток вправе задать задержку и не отдать ни одного события —
`SseParser::take_retry` закрывает этот случай.

### Замер после починки

Одноразовая проба (`sse_probe.rs`, локальный сервер, удалена перед коммитом),
Windows, `retry: 300`, окно 1.5 с:

| сценарий | до (заявка) | после |
|---|---|---|
| `Content-Length` + keep-alive (форма `wptserve`) | 1 соединение за 6 с | **5 соединений**, у каждого свой `SseConnected` |
| поток закрыт сокетом | переподключения шли, `open` только на первом | 5 соединений, `open` на **каждом** |
| незавершённый блок (BUG-845) | `data === "test2\ntest1"`, `Last-Event-ID: test` | `data === "a"`, **ни одного** `Last-Event-ID` |
| `chunked` + last-chunk | — | 5 соединений |
| 500 на переподключении | — | терминальная ошибка (§9.2.5 «fail the connection») |
| порт закрыт на переподключении | — | терминальная ошибка |

Ловушка самой пробы, стоившая одного прогона: сервер держал сокет в
ПОСЛЕДОВАТЕЛЬНОМ accept-цикле, поэтому переподключение вставало в backlog и
«1 соединение» читалось как отсутствие переподключения; и размер первого чанка
был на единицу больше тела, отчего разбор `chunked` ломался. Оба раза проба
мерила себя.

### Тесты

Проба одноразовая, поэтому поведение закреплено постоянными тестами в
`crates/network/src/sse.rs` (10 новых): разбор (`reset_stream`, разделение
буфера id и строки id источника, `take_retry`, дословное тело
`format-data-before-final-empty-line.any.html`) и три живых теста обрамления
против собственного сервера, ДЕРЖАЩЕГО сокет 10 с.

Про дедлайн в живых тестах: без него они зелёные и при сломанном обрамлении —
чтение до закрытия сокета тоже кончается, просто через 10 с. Проверено
мутацией (`framing = Eof`): тест держался 20 с и **всё равно проходил**.
Отличает исправное поведение только время, поэтому события читаются в отдельном
потоке с бюджетом 3 с. Мутационная проверка всех восьми решений
(откат буфера id, немедленная запись id, очистка строки/типа, продвижение id в
`dispatch`, `chunked` как `Eof`, приоритет `Content-Length`, CRLF после чанка,
`take_retry`) — каждая мутация валит тесты. Эквивалентная мутация: обход
ветки `size == 0` не наблюдаем, потому что следующее чтение нулевой длины
всё равно даёт `Ok(0)`, а сокет клиент не переиспользует.

### Остаток

`Event::SseError` теперь публикуется на КАЖДЫЙ конец потока, а не только на
ошибку чтения; потребителей в шелле у него нет (единственный — новый
`JsSseControlSink`), поэтому в лог пользователя это не попадает. Ветка
`ev.t === 'error'` в шиме по-прежнему обнуляет `_handle`, не позвав
`_lumen_sse_close` — запись в нативном реестре сессий подтекает на каждый
EventSource, умерший ошибкой. Дефект существовал до этой правки и не входит в
BUG-844.
