# BUG-917 — IndexedDB: каждый «грязный» флаш пересериализует весь снапшот баз и перезеркаливает всю схему, O(все базы × все хранилища × все индексы)

**Статус:** OPEN
**Заведён:** 2026-08-25 (P1, измерен в ходе [BUG-843](BUG-843-FIXED.md))
**Область:** `crates/js/src/dom.rs` (`IDB_SHIM`: `_idb_persist_if_dirty`, `_idb_serialize`, `_idb_persist_schema`), вызывается из `_lumen_idb_flush`
**Владелец:** P1/P3 (`lumen-js`)

## Симптом

Любая мутация (`put`, апгрейд, удаление базы) ставит `_idb_dirty`, и в конце
флаша `_idb_persist_if_dirty()` делает две вещи целиком, без инкрементальности:

* `_idb_serialize()` — `JSON.stringify` **всего** `_idb_databases` вместе с
  записями всех хранилищ всех баз происхождения;
* `_idb_persist_schema()` — обход всех баз, всех хранилищ и всех индексов с
  отдельным нативным вызовом `_lumen_idb_schema_op` на каждую строку
  (`SetVersion` + `CreateStore` + `CreateIndex`).

Комментарий в коде это признаёт («populating idb_records row-by-row is a future
incremental optimisation»), но цена не измерялась.

## Почему это заметно именно сейчас

Само по себе — старый дефект. Его сделал видимым BUG-843: заблокированное
`deleteDatabase` больше не выкидывает базу из `_idb_databases` немедленно, а
страница, которая не закрывает соединение, не выкидывает её никогда. Базы
накапливаются в пределах одного шарда WPT (браузер переиспользуется между
тестами), и стоимость каждого следующего флаша растёт вместе с ними.

## Прямое измерение

A/B на одной машине (Windows, dev-release, Vulkan),
`run_report.py --all --root IndexedDB --recursive`, 231 id, суммарное время
самих тестов из `--log-raw`:

| | до BUG-843 | после |
|---|---|---|
| сумма | 406 с | 1231 с |
| `idb-explicit-commit.any.html` | 0.1 с | 17.4 с |
| `structured-clone.any.html?21-40` | 1.5 с | 31.5 с |

Замедлились **все** 231 id, а не только те, где что-то блокируется — признак
общей, а не точечной стоимости. Телеметрия того же прогона показала флаш
примерно раз в 0.85–0.9 с при одной записи в очереди, то есть страница платит
такт событийного цикла и полную пересериализацию за операцию.

## Направление починки (не предписание)

Инкрементальная персистентность: писать в структурный бэкенд только изменённую
базу/хранилище/индекс (диффом или по журналу операций), а `_idb_serialize`
делать не чаще, чем нужно, — например, дебаунсом по событийному циклу вместо
«каждый грязный флаш». Смотреть вместе с `docs/perf-method.md`: гейт по
счётчику вызовов `_lumen_idb_schema_op`, а не по секундомеру.

## Как проверить фикс

Тот же A/B по всей категории `IndexedDB`; ожидание — сумма времени тестов
возвращается к порядку 400–500 с при неизменных вердиктах подтестов.
