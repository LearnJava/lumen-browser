# BUG-1034: run-scripts входит в активный CPU-спин без возврата в event loop на реальных сайтах (duckduckgo, baidu, microsoft) — автоматизационный канал полностью не отвечает

**Статус:** OPEN
**Компонент:** js (v8_runtime, конкретное место не локализовано — нужен V8 CPU-профайлер, недоступный в этой сессии)
**Найден:** P1, THREAD-3 срез 1, 2026-09-08, живой `--bidi-port`/`--maximized` + headless `--trace-nav`

## Симптом

Три сайта из «5 HUNG» корпуса `docs/perf/corpus-top100-foreign.txt` (THREAD-0,
2026-09-04) переизмерены прицельно с текущим движком (коммит `3aa1b2aa0`/
`2eb888afa`). Во всех трёх — не «зависший promise» (гипотеза THREAD-0), а
**активный, потребляющий CPU цикл**, начинающийся сразу после последнего
загруженного скрипта и не отпускающий главный поток:

- **duckduckgo.com**: headless `--trace-nav` не завершается за 180+ с (было
  заявлено «не завершается за 240–400с»). Живой `--bidi-port --maximized
  --health-log` (`LUMEN_NO_ADBLOCK=1`, см. ниже почему это обязательно):
  BiDi-канал полностью не отвечает сразу после навигации (`script.evaluate`
  с 6с таймаутом — TIMEOUT), память растёт непрерывно (923 МБ → 1.3+ ГБ за
  десятки секунд, не плато), `UserModeTime` растёт на ~4.7с CPU за 3с
  реального времени (>150% одного ядра). Через 15–30 с повторный
  `script.evaluate` в ТОТ ЖЕ контекст отвечает `JS context not available`
  (не таймаут — контекст/realm уже уничтожен или заменён, но окно не
  закрывается и процесс живёт).
- **baidu.com**: тот же класс — headless не завершается за 90+ с сразу после
  загрузки последнего скрипта (`hectorstatic.baidu.com/...js`).
  `UserModeTime` растёт монотонно и быстро (+~10с CPU на 8с реального
  времени), но `WorkingSetSize` стабильна (~190 МБ, без роста) — чистый
  busy-loop без утечки, в отличие от duckduckgo.
- **microsoft.com**: двухфазно. Первая фаза (~20с) — сетевая: DNS-резолвинг
  внешних CDN-хостов (`az725175.vo.msecnd.net`, `assets.onestore.ms`)
  проваливается (`os error 11001`, хост не существует), это просто
  медленный, но конечный сетевой путь. Вторая фаза начинается сразу после
  этого — тот же спин-паттерн, что у duckduckgo/baidu (`UserModeTime` +8–10с
  CPU на 8с интервал).

Во всех трёх случаях **автоматизационный канал (BiDi/MCP) полностью не
отвечает во время спина** — что отличает находку от гипотезы THREAD-0
(«похоже на никогда не возвращающийся run-scripts, а не на дорогой layout»):
это подтверждается напрямую (не по аналогии с layout/paint), а не
опровергает её — просто уточняет механизм: главный поток занят синхронным
исполнением, которое НЕ является ни ожиданием промиса (тогда event loop и
`about_to_wait`-таймеры продолжали бы тикать и канал бы отвечал), ни paint/
layout (у них нет такого порядка величины даже на самых тяжёлых сайтах
корпуса — github, самый дорогой layout/paint случай, укладывается в 35–40с
каждая фаза).

## Что уже исключено

- **Не сеть**: THREAD-0 уже показал, что все ресурсы duckduckgo получены за
  секунды. Этот срез подтверждает то же для baidu (все чанки — `Загружен
  скрипт` — до зависания) и характеризует microsoft отдельно (сетевая фаза
  реальна, но конечна и не является причиной итогового зависания).
- **Не блокировщик рекламы**: изначальный тест (adblock по умолчанию)
  показал, что EasyList блокирует **100%** JS-чанков duckduckgo.com (см.
  отдельный [BUG-1035](BUG-1035-OPEN.md) — это настоящий, но ДРУГОЙ дефект).
  Повтор с `LUMEN_NO_ADBLOCK=1`: все чанки грузятся успешно, зависание
  остаётся идентичным по форме (спин сразу после последнего скрипта) — adblock
  не является причиной этого бага, только независимо усугубляет UX на этом
  конкретном сайте.
- **Не layout/paint**: `--trace-nav`'ов трейс для духа зависания недоступен
  (процесс не успевает дойти до financial paint), но по механизму (спин без
  событий, автоматизационный канал мёртв) это не совместимо с layout/paint —
  они бы не блокировали BiDi-обработчик, который живёт в отдельном
  обработчике событий цикла, а не внутри самого прохода раскладки.

## Что НЕ удалось (ограничение среды этой сессии)

Обычная техника локализации «тихого зависания» — трассировщик висящих
промисов через `Promise.prototype.then` в preload-скрипте (BiDi
`script.addPreloadScript`) — оказалась неприменима: она печатает отчёт через
`setTimeout`, а `setTimeout` тикает только если event loop жив. Раз
автоматизационный канал (который завязан на тот же `about_to_wait` тик, что
и таймеры JS) не отвечает вовсе, ни один `console.error`-репорт из
преload-скрипта не долетел до `health.<pid>.log`, несмотря на то что сам
преload-скрипт гарантированно выполнился (иначе первая же навигация упала бы
с ошибкой скрипта, а не таймаутом). Это САМО по себе диагностический сигнал
(см. выше), но не даёт стек вызова.

Нативного sampling-профайлера (`cdb`/`windbg`/Visual Studio) на машине этой
сессии не нашлось (`where` не находит `cdb.exe`/`windbg.exe`/`devenv.exe`/
`procdump.exe`, поиск по `Windows Kits\10` пуст) — следующий срез должен
начать с установки/доступа к сэмплирующему профайлеру (или сборки с фичей
`tracy`, `Cargo.toml` её уже объявляет) и снятия нативного стека вызовов
процесса, пока он крутится в спине, чтобы увидеть, в каком именно Rust-коде
(V8 builtin, наш нативный биндинг DOM API, GC) происходит цикл.

## Гипотезы для следующего среза (не проверены)

1. Общий паттерн современных бандлов (webpack/turbopack module registry,
   feature-detection busy-poll) вызывает нативный API, который либо
   отсутствует и подставляет медленный fallback, либо реализован с
   квадратичной/экспоненциальной сложностью и на большом входе выглядит как
   зависание, а не баг «никогда не завершается». Разница duckduckgo (память
   растёт) vs baidu (память плоская) намекает на РАЗНЫЕ конкретные причины
   под одним и тем же наблюдаемым симптомом «спин + мёртвый автоматизационный
   канал» — не обязательно один и тот же баг.
2. Растущая память duckduckgo может быть отдельным, более узким классом (уже
   известным движку — см. `docs/perf/journal.md`, PERF-11/12) — накопление
   promise-цепочек/замыканий в цикле без `await`.

## Как воспроизвести

```
LUMEN_NO_ADBLOCK=1 target/dev-release/lumen.exe --trace-nav out.json https://www.baidu.com/
# зависает; UserModeTime (wmic process where "name='lumen.exe'" get UserModeTime)
# растёт непрерывно, WorkingSetSize стабильна — то же для duckduckgo.com (с
# растущей WorkingSetSize) и https://www.microsoft.com/ (после ~20с сетевой
# фазы)
```
