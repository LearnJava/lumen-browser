# BUG-1858 — portal.nextera.ru, чат: пользовательские пузыри сообщений прижаты влево и уже, чем в Chrome

**Статус:** OPEN (найден 2026-11-27; 2026-11-27 исправлена доминирующая часть —
центрирование `.messages-area`, влито на ветке `bug-1853-fix`; остаток — расхождение
computed-vs-layout на динамических узлах, см. «Локализация 2026-11-27 (вторая половина)»)
**Область:** layout (колоночный flex — поперечные авто-маргины; style-инвалидация для
динамически вставленных узлов)

## Симптом

Залогиненный чат (`Некстер`, личный): сообщения пользователя («Тестовый пинг…») в Lumen
жмутся к левому краю колонки сообщений и переносятся на две строки; в Chrome тот же чат
рисует пузырь правее/центральнее и в одну строку.

Снимки: `.tmp/bug1853/chat_lumen.png` / `chat_chrome.png` (вне репозитория), 1920-вьюпорт,
у обоих движков `docW` отличается на скроллбар (1920 vs 1904).

## Замеры

Chrome (CDP-цепочка от листа текста вверх, 2026-11-27):

| узел | w, px | x, px | display | ml |
|---|---|---|---|---|
| `p` (текст пузыря) | 442 | 633 | block | 0 |
| `.msg-bubble.md` | 468 | 620 | block | 0 |
| обёртка (flex-колонка) | 704 | 620 | flex | **44px** |
| `.msg.user.human.pp-cont` | 776 | 562 | flex row | 0 |
| `.messages-area` | **820** | 542 | flex column | **542px** (auto) |
| `.pp-chatflex` (родитель) | 1904 | 0 | flex column | 0 |

Lumen (числовая цепочка не снята — логин-петля обрывала замер; по скриншоту): пузырь
≈368px, две строки, x≈424 при том же экране — т.е. обёртка сообщения уже, чем 704px
Chrome, и/или `margin-left:44px` обёртки не сработал.

Примечание: `.messages-area` центрируется авто-маргинами внутри колоночного flex
(820 из 1904) — это та же схема, что починена в BUG-1853 (`column_item_avail_cross`);
сам `messages-area` после фикса BUG-1853 центрируется (домашняя проверка 2026-11-27),
так что остаточное расхождение — ниже по дереву (обёртка сообщения / ширина пузыря).

## Воспроизведение

Живой портал, залогиненный чат. Логин в Lumen не переживает перезапуск процесса
(каждый запуск — заново через Keycloak; Chrome в том же профиле сохранял) — отдельное
наблюдение, дефектность не подтверждена.

## Как проверять

Снуть цепочку `msg-bubble → … → messages-area` в обоих движках при равном docW
(скрипты-образцы: `.tmp/bug1853/bubble_probe.py`, `chat_compare.py`; адресный захват
пользовательского пузыря — `.tmp/bug1853/capture2.py`).

## Локализация 2026-11-27, часть 1 — ИСПРАВЛЕНА (колоночный flex, авто-маргины)

`column_item_cross_shift` (`flex_trampoline.rs`) вычитал из сдвига §8.1
«уже распределённое §10.3.3» (`block_applied`) для **любого** айтема с определённой
шириной, но свой расклад решает авто-маргины против контейнера только обычный
блок/flow-root (§10.3.3), табличная обёртка (§17.4) и multicol. Вложенный
flex/grid-контейнер (BoxKind::Block, display по стилю), замещаемый бокс и form
control кладутся на origin с нулевыми маргинами — вычитание гасило весь сдвиг
(550−550=0): `.messages-area` (820px, margin:auto, сама flex) стояла на x=0 вместо
x=550. Живая матрица до/после: flex-айтем и grid-айтем 0→550, img 0→550, input
0→549 (w=822 — отдельная причуда FormControl), блок/таблица/flow-root/multicol
550→550 (без двойного сдвига). Тесты: 5 новых в `flex_axes` (49/49), полный
`cargo test -p lumen-layout` зелёный (единственный красный — тайминг-флак
`deep_chain_with_margins…`, соло зелёный).

## Локализация 2026-11-27, часть 2 — OPEN (расхождение computed-vs-layout на динамических узлах)

После фикса части 1 (проверено живым порталом, dev-release): `.messages-area` x=550
(Chrome 542 при docW 1904 — та же геометрия с поправкой на скроллбар), `.msg` x=570
(=Chrome 562+8). Остаток в строке пользователя `.msg.user.human.pp-cont` (flex row,
pl 14): обёртка `<div style="min-width:0;flex:1">` с авторским
`.msg.user>div{margin-left:44px;align-items:flex-start}` стоит на x=584 (=начало
контента, маргин мёртв) и w=752 (весь контент); в Chrome x=620, w=704. Диагностика
на живом окне (`.tmp/bug1853/capture2.py`, свипы и инлайны):

- `getComputedStyle` отдаёт ml=44px, ai=start — свежий каскад;
- инлайновый `marginLeft:44px` работает идеально (x=628, w=708);
- инлайновый `marginLeft:88px` — тоже (x=672, w=664); авторское правило — нет;
- вычисленные B4-репродюсы (точная копия строки, свежий расклад в чистом
  документе) раскладываются правильно — x=58, w=708 (масштаб 400px-копии);
- сопутствующая находка свежего расклада (`.tmp/bug1853/prepro.py`, `bisect.py`):
  row-flex при дефолтном `align-items` контейнера задаивает маргин flex-контейнерного
  айтема (x=102=58+44, w=664=708−44; с `align-items:start` — правильно). Маленький
  отдельный дефект в row-пути, на живую строку не влияет (там `ai:start`);

Вывод: box-tree держит для динамически вставленного узла устаревший/чужой
computed style (маргин/align из авторского правила не дошли до расклада), тогда как
DOM-уровень (getComputedStyle) видит свежий. Кэши переиспользования безопасны
(`Arc::ptr_eq` + поляное сравнение в `graft_geometry_with_cascade`) — значит свежий
каскад до расклада не доходит: **дыра инвалидации стилей**. Тот же почерк в двух
других местах:

- страница логина (Keycloak): `.pf-v5-c-form-control` в `.nx-locale` (flex, jc:end)
  жил с геометрией w=42 при свежем computed width=362 (width:100%), select 120px
  торчал из обёртки на 78px (`.tmp/bug1853/loginprobe.py`);
- BUG-1853 дефект 4: `#homeAmbient` computed display `""` после позднего добавления
  `pp-shell` на `<html>` — вероятно, тот же слой.

Кандидат-механика: инвалидация не доходит до узлов, чьё соответствие зависит от
поздно изменившихся входов (приход стилейшего CSS, добавление класса предку для
child/descendant-комбинаторов, поздний класс на корне). Что проверять: путь
инвалидации при (а) добавлении таблицы стилей, (б) мутации классов предков для
`E > F`/`E F` селекторов, (в) мутации класса на `<html>`. Живой инструмент:
`x-scope-relayout` (MCP-TOTAL S2e) — форс-релайаут одного узла, различает stale-геометрию
vs чужой каскад.

Смежные: BUG-1846 (композер чата — грид), BUG-1853 (домашняя колонка — та же страница;
дефект 4 `#homeAmbient` — тот же почерк), BUG-1859 (DEVX-8a на сайдбаре — транзиент).
