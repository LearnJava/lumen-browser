# BUG-949 — `scrollY` читает старое значение до следующего прохода шелла: `scrollTo()` не синхронный

**Статус:** OPEN
**Тип:** дефект реализованного кода — очередь заведена намеренно (комментарий `runtime.rs:93` про coalescing), но CSSOM View требует, чтобы чтение форсировало применение отложенной прокрутки.
**Заведён:** 2026-09-01 (WPT-RUN-6, срез 31, живая проба `verify_scroll_view_transition_gaps.py --variant scroll-anchor-read`)
**Область:** js (`crates/js/src/v8_runtime/runtime.rs` — `pending_page_scrolls`/`page_scroll_y`; `crates/js/src/v8_runtime/install/platform.rs:349` — `_lumen_request_page_scroll`)
**Владелец:** P3.

## Симптом

`window.scrollTo(0, 150)` ставит запрошенную позицию в очередь
(`pending_page_scrolls`, `Vec<(f32, bool)>`) вместо того, чтобы применить
её перед возвратом. `scrollY`/`pageYOffset` читают `page_scroll_y` —
отдельное поле, которое обновляет ТОЛЬКО шелл на своём следующем проходе
(`set_page_scroll_y`, вызывается «once per rendering update» по
собственному doc-комментарию `v8_dragdrop_scroll_pointer.rs:254`). CSSOM
View §3 требует, чтобы `scrollTo`/`scrollBy` синхронно (или, для
`behavior: smooth`, по завершении анимации) отражались в последующем
чтении `scrollY`, и чтобы `reading-scroll-forces-anchoring.html` из CSS
Scroll Anchoring §3 форсировало ожидающую поправку якоря перед чтением.

## Прямое измерение

Живая проба (`--variant scroll-anchor-read`, dev-release, страница с
реальным фоном — не «спейсер без фона», гоча `sessionStorage`/`scrollTo`
на пустом контенте исключена): `scrollTo(0, 150)`, немедленное чтение —
`0`; после `requestAnimationFrame` — всё ещё `0`; после `setTimeout(fn, 0)`
— всё ещё `0`; после роста высоты блока на 100px — по-прежнему `0`; и
только спустя ~500мс (следующий тик пробы) значение становится `150`.
Ни один синхронный или однокадровый путь не видит прокрутку вовсе — она
применяется на существенно более позднем проходе, чем `raf`/микротаск.

## Кого это держит

`css/css-scroll-anchoring/reading-scroll-forces-anchoring.html` — тест
скроллит, растит элемент выше во вьюпорте и читает `scrollY` сразу; первая
же проверка не совпадает, потому что `scrollTo` ещё не применился, а не
потому, что якорение не сработало (последнее не проверяется этим измерением
— вопрос якорения остаётся открытым до починки базовой асинхронности).

## Направление починки

`page_scroll_y`/`pending_page_scrolls` — намеренный coalescing-механизм по
своему собственному комментарию (`runtime.rs:93`), видимо ради того, чтобы
не гонять layout/paint на каждый `scrollTo` в кадре. Синхронное чтение
`scrollY` требует форсировать применение отложенной прокрутки ПЕРЕД
возвратом значения геттера — то есть `_lumen_get_page_scroll_y` должен
сначала слить `pending_page_scrolls` (если непустой и `smooth == false`)
в `page_scroll_y`, а не просто прочитать поле. `behavior: smooth` — второй
случай, где CSSOM View разрешает промежуточные значения, но требует, чтобы
финальное чтение после завершения анимации совпало с целью.
