# BUG-1003 — `resize-observer`: два подтеста дают разный результат от прогона к прогону на одном бинаре

**Статус:** FIXED 2026-09-29 (P6)
**Заведён:** 2026-09-05 (P2, WPT-RUN-7 срез 6 — перегенерация expectations baseline после
фикса выборки среза 4)
**Область:** не локализован. Кандидаты — тайминг `ResizeObserver`-колбэков относительно
фрагментированных inline-боксов (`fragments.html`) и что-то в самом `notify.html`, обе
страницы синхронизируются через `requestAnimationFrame`
**Владелец:** P1/P3, исправлено P6

## Симптом

`--update-expected --all --root resize-observer --recursive` затем немедленный `--check`
на том же бинаре и том же прогоне дают расхождение вместо ожидаемых 0 регрессий:

- `/resize-observer/fragments.html` — подтест `Removing 2nd fragment` в run 1
  (`--update-expected`) дал `UNEXPECTED-PASS`, авто-narrowing убрал его `expected: FAIL`
  из `.ini`; в трёх последующих изолированных `--check` подряд тот же подтест на том же
  бинаре стабильно `FAIL`. То есть PASS был исключением (1 из 4 наблюдений), не новой
  нормой.
- `/resize-observer/notify.html` — один из последующих `--check`-прогонов (после
  восстановления `fragments.html` к прежнему baseline) дал `REGRESSION: expected OK, got
  ERROR`; повторный `--check` сразу после — снова `OK`. Тоже однократный, не
  воспроизводится подряд.

## Почему это важно

Оба симптома делают подтестовый baseline `resize-observer` невоспроизводимым тем же
классом дефекта, что [BUG-999](BUG-999-FIXED.md): гейт `--check` увидит регрессию на
чистом `main` без единого движкового изменения просто потому, что ему не повезло с
прогоном. Baseline этой категории **не тронут** этим срезом (изменения к
`fragments.html.ini` откачены обратно, `svg-with-css-box-002.svg.ini`, сгенерированный
попутно, удалён) — категория остаётся в состоянии до среза 4/5, перегенерация отложена до
локализации причины.

## Воспроизведение

```
LUMEN_PROFILE=dev-release python tests/wpt/run_report.py \
  --binary target/dev-release/lumen --all --root resize-observer --recursive --check
```

Запустить 3–5 раз подряд на одном бинаре без пересборки — расхождение по конкретному
файлу/подтесту плавает от прогона к прогону (не обязательно те же два, что в этой находке).

## Что не проверялось

Не локализовано до конкретного call site — не проверялось, коррелирует ли исход с
реальным wall-clock jitter (`rAF`-тайминг под нагрузкой параллельных `wptserve`-процессов)
или это структурная гонка в реализации `ResizeObserver`/layout fragmentation. Нужна серия
изолированных прогонов одного файла (`run_smoke.py <id>`) с диагностикой по каждому кадру,
не прогон всей категории.

## Причина и исправление (2026-09-29, P6)

Локализовано зондом-тестом (rAF → смена класса → лог `set/RO/rafA/rafB` в одном
файле): уведомление ResizeObserver приходило через ~20–40 мс после смены DOM, то
есть вровень со следующим rAF-кадром (окно 2×rAF в `fragments.html` — ~15 мс запаса).
Путь: rAF-ход завершился → асинхронный relayout на движковом потоке → коммит на UI →
отложенный `route_task_js` (`defer_js_push`) → `_lumen_deliver_resize_observers`.
Следующий rAF-батч (`pump_raf_engine_thread`) уходит в ту же FIFO движкового потока и
мог обогнать отложенный push — исход зависел от джиттера, отсюда «1 из 4».

Что сделано:

1. `crates/shell/src/relayout.rs::pump_raf_engine_thread` — следующий rAF-батч не
   стартует, пока relayout предыдущего хода не закоммичен (`engine_job_generation !=
   engine_applied_generation`), но не дольше `RAF_RELAYOUT_HOLD_MS` = 100 мс. Порядок
   «rAF → layout → observers → следующий кадр» теперь детерминирован.
2. `web_api_shim_mid_b4.js` — детерминизм вскрыл, что прежняя гонка маскировала
   расхождения со Resize Observer §3.4: изменение, сделанное *внутри* колбэка, в том же
   кадре доставляется только для целей глубже самой мелкой уже уведомлённой
   (`_ro_depth`, `_ro_min_depth`), остальное — в следующем кадре после rAF-колбэков
   (`_ro_deliver_after_raf`, вызывается из `_lumen_run_raf_callbacks`); окно шлюза —
   один кадр (32 мс), потом задержанное уходит по таймеру. Без шлюза
   `ResizeTestHelper` из `notify.html` дважды продвигал шаг и падал в `ERROR`.
3. Там же: для элемента с `transform` размер берётся из used-`width`/`height`
   (`_ro_untransformed_border_size`), а не из ограничивающей рамки
   `getBoundingClientRect()` — transform больше не читается как ресайз
   (`notify.html` test4). Родственный дефект вне этого пункта: `offsetWidth`/
   `clientWidth` тоже возвращают трансформированный bbox.

Baseline `resize-observer` перегенерирован (`--update-expected`): прежний был снят с
состояния, дававшего 42 ложные «регрессии» на чистом `main` (idlharness, `observe.html`
TIMEOUT). Два подряд `--check` на одном бинаре: 0 регрессий.

## Остаток

- `eventloop.html` test2 (`move target in dom while inside event loop`) проходит ~2/3
  прогонов, в baseline записан `FAIL` (проход = информационный `unexpected pass`, не
  гейт). Старый бинарь стабильно падал в нём, так что это не новая регрессия.
- `svg.html`: подтесты 3–8 честно `FAIL` (SVG-цели не дают box), каждый жжёт 1 с
  таймаута `ResizeTestHelper`, поэтому файловый таймаут падает на границе разных
  подтестов (`test8`/`test9`) — при `--check` изредка «new TIMEOUT» на `test8`. Это
  свойство накопленных таймаутов, а не гонки доставки.
