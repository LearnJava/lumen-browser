# BUG-1011 — `html/rendering`: три `--check` подряд дают три РАЗНЫХ набора регрессий

**Статус:** OPEN
**Заведён:** 2026-09-06 (P2, WPT-RUN-7 срез 15 — дробление `html/*` по под-путям,
продолжение среза 14)
**Область:** файлы, где регрессии наблюдались в широком прогоне, исключены как источник
(см. §Изоляция 2026-09-07 — все четыре детерминированы в одиночном прогоне); не
локализован сам механизм — что-то в длинном последовательном `run_report.py`-прогоне
по всей категории. Затронутые в широком прогоне файлы не пересекались между прогонами —
`non-replaced-elements/form-controls/resets.html` (TIMEOUT), `replaced-elements/svg-inline-sizing/svg-inline.html`
(один подтест PASS→FAIL), `replaced-elements/svg-embedded-sizing/svg-in-iframe-{auto,fixed}.html`
(оба TIMEOUT, включая harness)
**Владелец:** P1/P3 (после локализации механизма накопления, не этих файлов)

## Симптом

`--update-expected --all --root html/rendering --recursive` прошёл штатно (134/150 harness OK,
1892/3115 подтестов, 102 новых `.ini`). Немедленный `--check` на том же бинаре и том же
свежесозданном baseline дал:

- прогон 1 (`--processes=4`): **0 регрессий** — совпал с прогоном, из которого baseline
  записан;
- прогон 2 (`--processes=4`, без изменений между прогонами): **1 регрессия** —
  `form-controls/resets.html` внезапный TIMEOUT (harness, не подтест);
- прогон 3 (`--processes=4`): **1 регрессия**, другой файл — `svg-inline-sizing/svg-inline.html`,
  один параметризованный подтест перевернулся PASS→FAIL (`svgWidthStyle: '100px', svgHeightStyle:
  '50%', ...`);
- прогон 4 (сериализовано, `--processes` не передан, т.е. wptrunner default = 1): **4
  регрессии**, третий, ни разу не совпадающий набор — `svg-embedded-sizing/svg-in-iframe-auto.html`
  и `svg-in-iframe-fixed.html`, оба целиком TIMEOUT (harness) плюс по одному их подтесту.

Baseline `html/rendering` не закоммичен — `.ini`-файлы, записанные `--update-expected`,
откачены `git clean -fd tests/wpt/metadata/html/rendering/` до исходного (отсутствующего)
состояния этим же срезом.

## Почему это важно

Тот же класс находки, что [BUG-1003](BUG-1003-OPEN.md)/[BUG-1004](BUG-1004-OPEN.md)
(«два `--check` подряд без изменений между ними дали разные регрессии»), но с третьим
и четвёртым независимым подтверждением на том же прогоне: три из четырёх попыток дают
разные наборы, а серийный (`--processes` не задан) прогон не устранил проблему и не
уменьшил её масштаб — наоборот, дал вдвое больше регрессий, чем любой параллельный прогон.
Это отводит гипотезу «дело в конкуренции четырёх процессов за CPU/порты» (предположение
проверено явно этим срезом, в отличие от BUG-1003/1004, где параллелизм не варьировался).

**Изоляция (2026-09-07) опровергает вторую половину вывода** — «недетерминированность
движка в раскладке SVG» — см. §Изоляция ниже: все четыре файла один-в-один воспроизводимы
вне контекста полной категории. Значит проблема не в раскладке SVG/`<input>`, а в чём-то,
что появляется только при длинном последовательном прогоне многих файлов подряд внутри
одного процесса `run_report.py` — тот же класс гипотезы, что растущий (не колеблющийся)
счётчик регрессий в [BUG-1022](BUG-1022-OPEN.md) (6 → 19 → 27 на `html/semantics`).

## Изоляция (2026-09-07)

`run_smoke.py` на одном id в цикле, `timeout 90`, без `--processes` (один процесс на
запуск), скрипт `.tmp/bug1011-localize/run_isolated.sh` (не закоммичен, скретч):

- `svg-in-iframe-auto.html` — 10/10 запусков: **0 TIMEOUT**, harness OK каждый раз,
  31–38 с на прогон (не близко к 90-секундному пределу), одинаковый набор 72 FAIL-подтестов
  байт-в-байт (md5 совпал во всех 10 логах) — реальный, стабильный дефект раскладки
  (`Wrong width expected 400 but got 300` и т.п.), не флак;
- `svg-in-iframe-fixed.html` — 10/10: тот же результат, тоже 72 FAIL, тоже одинаковый
  md5 во всех 10 логах, 0 TIMEOUT;
- `svg-inline.html` (`replaced-elements/svg-inline-sizing/`) — 5/5: 172 FAIL-подтеста,
  identичный набор во всех 5 логах (md5 совпал), 11–14 с на прогон;
- `resets.html` (`non-replaced-elements/form-controls/`) — 5/5: **0 unexpected**, чистый
  PASS каждый раз, 14–17 с на прогон, без следа TIMEOUT.

**Вывод**: ни один из четырёх файлов не флакует в изоляции — все четыре детерминированы
на 100 % (byte-identical результат на 5–10 повторов). Гипотеза «недетерминированность
раскладки SVG/`<iframe>`» из первой версии этой находки отведена. Наблюдаемые в широком
прогоне TIMEOUT/меняющиеся регрессии — не свойство этих тестов, а артефакт длинного
`run_report.py`-прогона по всей категории (134/150 файлов подряд в одном процессе) —
совпадает с направлением, уже отмеченным в BUG-1022 («растущий счётчик» → гипотеза утечки
портов/хендлов/памяти между последовательно исполняемыми тестами внутри одного прогона,
не между отдельными `--check`-запусками). Следующий шаг локализации — не эти четыре файла
(закрыто), а сам `run_report.py`/`wptrunner`: снять `--log-raw`/мониторинг открытых
дескрипторов на всём прогоне `html/rendering` целиком и найти, что растёт от файла к файлу.

## Воспроизведение

```
LUMEN_PROFILE=dev-release <venv>/python tests/wpt/run_report.py \
  --binary target/dev-release/lumen --all --root html/rendering --recursive --update-expected
LUMEN_PROFILE=dev-release <venv>/python tests/wpt/run_report.py \
  --binary target/dev-release/lumen --all --root html/rendering --recursive --check
# повторить --check несколько раз подряд без изменений между прогонами — набор регрессий
# меняется от раза к разу, включая при отсутствии --processes (сериализованный прогон)
```

## Локализация (2026-09-07, срез 22)

Три независимых проверки на том же баннере («растущий/меняющийся счётчик регрессий»),
общем с [BUG-1003](BUG-1003-OPEN.md)/[BUG-1004](BUG-1004-OPEN.md)/[BUG-1005](BUG-1005-OPEN.md)/
[BUG-1022](BUG-1022-OPEN.md)/[BUG-1024](BUG-1024-OPEN.md):

**1. Механическая находка в самом харнессе — `PYTHONHASHSEED` нигде не пинится.**
`grep -rn PYTHONHASHSEED` по всему дереву (кроме `.claude/worktrees/`) — пусто. Дефолтный
`TestQueueBuilder` для этих прогонов — `SingleTestSource` (`tools/wptrunner/wptrunner/
testloader.py`), не `PathGroupedSource`: `run_report.py`/`run_smoke.py` никогда не передают
`--run-by-dir`/`--fully-parallel`/`--test-groups`, а `--run-by-dir`'s argparse-дефолт — `False`.
`SingleTestSource.make_groups` раскладывает тесты по `processes` воркерам через
`hash(test.id) % processes` — **один** `TestGroup` на воркер на всю категорию (не на
директорию), и `restart_on_new_group` физически не может сработать посреди прогона, раз группа
одна. Также подтверждено: `run_smoke.py` явно передаёт `--no-restart-on-unexpected`
(`run_smoke.py:100`), поэтому обычный FAIL/TIMEOUT не перезапускает браузер — один и тот же
процесс `lumen --bidi-port` действительно обслуживает свою `1/N`-ю всей категории от начала до
конца. Поскольку `run_report.py` каждый раз стартует новый интерпретёр Python, а хеш `str`
рандомизирован по умолчанию, распределение `test.id → воркер` **не воспроизводится** между
независимыми запусками `--check` — эмпирически подтверждено (`hash(x) % 6` на одних и тех же
4 строках в трёх запусках `python3` подряд дало три разных набора).

**2. Но фиксация `PYTHONHASHSEED=0` не убирает флуктуацию** — это ключевой результат среза:
4 последовательных `--check` (`--processes 6`, тот же бинарь, тот же только что записанный
baseline, ничего не менялось между прогонами) с зафиксированным сидом:

| прогон | регрессий | файл(ы) |
|---|---|---|
| 1 | 0 | — |
| 2 | 4 | `svg-embedded-sizing/svg-in-iframe-percentage.html` (2 сабтеста PASS→FAIL) + `svg-in-iframe-auto.html` (2, включая новый TIMEOUT) |
| 3 | 1 | `svg-in-iframe-auto.html` (1 сабтест PASS→FAIL) |
| 4 | 1 | `svg-in-iframe-fixed.html` (1 сабтест PASS→FAIL) |

Раз распределение тестов по воркерам детерминировано (сид зафиксирован) и всё равно наблюдается
разброс 0/4/1/1 — гипотеза «дело только в рандомизации `hash(test.id) % processes` между
запусками» отведена как единственное объяснение; она реальна как механический факт харнесса
(см. п.1), но не объясняет флуктуацию сама по себе. При этом за все 4 прогона регрессии не
вышли за пределы `replaced-elements/svg-embedded-sizing/svg-in-iframe-{auto,fixed,percentage}.html`
— та же тройка (плюс новый `percentage`-вариант), что и в исходном широком прогоне и в
§Изоляция, а не случайные новые директории.

**3. Мониторинг `/proc/<pid>/{fd,status}` (1 Гц, весь прогон, все PID `target/dev-release/
lumen` разом) фд-утечки не показал** — во всех наблюдаемых `lumen`-процессах количество
открытых дескрипторов держалось в диапазоне 40–70 весь прогон, без выраженного роста. Зато
**RSS одного и того же PID вырос со ~108 МБ до ~2.5 ГБ за первые ~25 с** его работы в одном из
прогонов (`--log-raw`, PID 334141) — не плавный линейный рост «файл за файлом», а резкий скачок
именно на двух конкретных файлах (см. п.4), с последующим падением до ~0.5 ГБ. Значит ресурс,
за которым стоит смотреть в первую очередь — память (heap/DOM/JS retention для конкретных
файлов), не файловые дескрипторы/порты, вопреки более ранней гипотезе BUG-1022.

**4. `--log-raw` + сопоставление `process_output`-таймлайна с ростом RSS даёт точную
привязку к файлам, а не абстрактную «позицию в очереди»:** в том же прогоне (PID 334141)
воркер быстро (по ~0.2 с на файл) прошёл десяток `non-replaced-elements/tables/*` и
`the-fieldset-and-legend-elements/*`, затем в 3.0 с зашёл на
`replaced-elements/svg-embedded-sizing/svg-in-iframe-auto.html` — и следующая строка вывода
появилась только в 25.8 с (**~23 с** без единой строки в stdout/stderr, ровно тот же порядок
величины, что и `31–38 с` из §Изоляция минус время запуска процесса), после чего воркер тут же
зашёл на **`svg-in-img-auto.html`** (третий, ранее не изолированный §Изоляцией файл той же
директории) — и следующая строка вывода появилась только в **86.0 с**, т.е. ровно **~60.2 с**
без прогресса, что почти точно совпадает с дефолтным тайм-аутом WPT-теста (`<meta name=timeout
content=long>` → 60 000 мс). Изолированный прогон `svg-in-img-auto.html` (`run_smoke.py`, вне
контекста категории) подтвердил это как **самостоятельный, 100% детерминированный TIMEOUT**
(`TEST_END: Test TIMEOUT. Subtests passed 0/1`, 3/3 повторов, ровно 60.16 с между `TEST_START`
и `TEST_END`) — заведено отдельно как [BUG-1025](BUG-1025-OPEN.md) (движковый гэп: `<img
src="data:image/svg+xml,...">` не даёт `load` для первой сгенерированной комбинации, вся
цепочка последовательных сабтестов виснет на первом же).

**Вывод**: `replaced-elements/svg-embedded-sizing/` — не «случайная директория», а директория
с тремя тяжёлыми/пограничными файлами подряд (`svg-in-iframe-{auto,fixed}` по ~25–38 с каждый,
реальные детерминированные FAIL-дефекты раскладки; `svg-in-img-auto` — детерминированный полный
60-секундный TIMEOUT, [BUG-1025](BUG-1025-OPEN.md)) в одном and том же, никогда не
перезапускаемом посреди прогона `lumen`-процессе. Сама раскладка (FAIL-детали) и сам TIMEOUT
(`svg-in-img-auto`) полностью детерминированы в изоляции — не флак. Флакует конкретно
пограничный тайминг **сабтестов** `svg-in-iframe-{auto,fixed,percentage}` (PASS↔FAIL на
отдельных `rAF`-зависимых сабтестах, не whole-file TIMEOUT), что по совокупности признаков —
детерминированные тяжёлые соседи в том же процессе + погранично медленные rAF-синхронизованные
сабтесты — больше похоже на обычную wall-clock-чувствительность (эти сабтесты и без соседей
чувствительны к моменту снятия `getBoundingClientRect()` относительно `requestAnimationFrame`),
усиленную тем, что операционная система/цикл событий воркера уже потрудился на двух тяжёлых
соседних файлах прямо перед ними, чем классическую «утекающую» аккумуляцию ресурса на уровне
файловых дескрипторов или портов.

## Что не проверялось

- Не проверено на **третьем/четвёртом** независимом воркере/PID — вывод п.3–4 сделан по одному
  PID из одного прогона; не подтверждено, что RSS-скачок на 2.5 ГБ воспроизводится 1-в-1 на
  других воркерах/прогонах (просто не совпадает по времени с их собственным содержимым очереди).
- Не проверено, снимает ли флуктуацию `svg-in-iframe-*` увеличенный `--timeout-multiplier`
  (если да — подтверждает «пограничный тайминг», если нет — возвращает к «накоплению»).
- Не проверено на других категориях ([BUG-1022](BUG-1022-OPEN.md) `html/semantics`,
  [BUG-1024](BUG-1024-OPEN.md) `html/canvas`) — не изолирован их аналог «тяжёлый сосед по
  директории/шарду»; воспроизводимость вывода этого среза на них не подтверждена.
- `svg-in-img-auto.html`/BUG-1025 сам по себе не мешает `--check` (детерминированный TIMEOUT
  войдёт в baseline как `expected: TIMEOUT`, как только категория будет закоммичена) — его
  значение здесь чисто диагностическое: он показывает, что воркер, которому достаётся вся
  директория `svg-embedded-sizing/`, проводит ~85 с почти без прогресса на трёх файлах подряд,
  и именно в этом окне соседние сабтесты флакуют.
