# BUG-771 — вид окна меняется после прокрутки: текст хрома в кадре компоновки рисуется темнее, чем в монолитном

**Статус:** OPEN
**Заведён:** 2026-08-12 (P3, по заявке пользователя «после скролла страницы вид страницы меняется»)
**Подсистема:** paint (`crates/engine/paint/src/renderer.rs` — путь
`try_page_compose` → `render_impl(.., RenderPassMode::Compose)`), скролл-композитор
BUG-405

---

## Симптом

Прокрутить страницу вниз и вернуться на то же смещение — окно выглядит иначе,
чем до прокрутки. Разница только в ТЕКСТЕ: те же глифы на тех же позициях
получают бо́льшую плотность (визуально текст «жирнеет»/становится контрастнее).

Замер (окно 1900×1040, dpr 1, Vulkan, три снимка экрана на одном смещении 0:
`a` — после отстоя, `b` — через 3 с без прокрутки, `c` — после 10 тиков по
120 px вниз и 10 вверх; доля пикселей с |Δr|+|Δg|+|Δb| > 60):

| страница | шум страницы (a→b) | после прокрутки туда-обратно (b→c) |
|---|---|---|
| `lenta.ru` | 0.00 % | **0.17 %** |
| `lenta.ru`, `LUMEN_NO_SCROLL_COMPOSITOR=1` | 0.00 % | **0.00 %** |
| локальная `.tmp/tall.html` (400 абзацев + `position: fixed` строка) | 0.00 % | **0.10 %** |
| та же локальная, `LUMEN_NO_SCROLL_COMPOSITOR=1` | 0.00 % | **0.00 %** |

Сеть в симптоме не участвует: локальная страница воспроизводит его так же.

## Где именно расходятся пиксели

Разница собрана в узкие полосы строк, и это ровно строки ТЕКСТА:

* локальная страница: `y 40..51` (заголовок вкладки) и `y 75..87` (строка
  адреса) — то есть **только хром окна**; тело страницы и её собственная
  `position: fixed` строка совпадают побайтово;
* `lenta.ru`: те же две полосы хрома плюс `y 112..128` и `y 137..149` —
  строки баннера «Лента добра деактивирована»; тело статьи совпадает.

Карта пикселей одной буквы (8× увеличение, `<` темнее):

```
до прокрутки (монолит)     после прокрутки (компоновка)
====:.===-                 ***.:+**=.
-+=:.-+:=+                 #=:.++:++.
.=:  -+.=+                 #- .*+:++.
```

Позиции глифов совпадают пиксель в пиксель, отличается только плотность:
в области заголовка вкладки пикселей темнее 128 — 91 до прокрутки и 175 после
(средняя яркость 232.7 → 229.2).

## Что уже исключено

1. **Собственная анимация страницы** — контроль `a→b` (та же пауза без
   прокрутки) даёт 0.00 % на всех прогонах.
2. **Накопление по кадрам** (гипотеза «каждый кадр компоновки кладёт хром на
   свою же копию»): плотность меняется ОДИН раз и дальше не растёт — замер по
   0/1/2/4/8/16 тикам даёт 1243 тёмных пикселя на нулевом тике и 1073 на всех
   последующих, без дрейфа. Кроме того, level 0 в кадре компоновки открывается
   `LoadOpChoice::Clear(canvas_bg)`, то есть поверхность очищается и в этом
   пути тоже.
3. **Полоса композитора как источник расхождения** — тело страницы, которое
   как раз приходит блитом полосы, совпадает побайтово. Расходится то, что
   рисуется КАЖДЫЙ кадр поверх блита (overlay).
4. **Скролл сам по себе** — с `LUMEN_NO_SCROLL_COMPOSITOR=1` та же прокрутка
   не меняет ни одного пикселя.

## Что известно про механизм

Не назван. Факты, из которых он должен следовать:

* расходится только `overlay` (хром), а не контент полосы;
* геометрия глифов одинаковая — значит дело не в позиции квада и не в
  подпиксельном сдвиге, а в множителе покрытия/альфы либо в содержимом атласа;
* переход необратим, пока кадры идут компоновкой: после прокрутки картинка
  держится (попытка вернуть кадр в монолит правкой DOM через `eval` в пробе
  `.tmp/shot_toggle.py` монолитный кадр не вызвала — `page-compose` продолжал
  отдавать HIT, `c→d` 0.00 %). Проверить обратимость правильнее рычагом,
  который гарантированно выключает композитор на кадр.

Кандидаты, которые стоит проверить в этом порядке:

1. Двойная отрисовка хрома в одном из путей (плотность как от двух alpha-over
   поверх одного фона): сравнить `text-sub: команд/символов/квадов` кадра
   компоновки и монолитного кадра на ОДНОЙ странице.
2. Замена записей глифа в атласе между снимками (эвикция под давлением памяти
   полосы: 24 МБ текстур полосы + offscreen-уровни) и повторная растеризация с
   другими параметрами — гейт: счётчик `glyphs: rasterized ... за процесс` на
   кадрах перехода.
3. Различие уровня прозрачности/цвета текста хрома между двумя вызовами
   `render_impl` (кадр компоновки зовёт его с пустым `content`).

## Репро

```bash
# в слоте p3-work
python .tmp/shot_roundtrip.py rt_local \
  --url "file:///D:/.../.tmp/tall.html"                     # 0.10 %
python .tmp/shot_roundtrip.py rt_local_off \
  --url "file:///D:/.../.tmp/tall.html" \
  --env LUMEN_NO_SCROLL_COMPOSITOR=1                        # 0.00 %
```

`.tmp/shot_roundtrip.py` (перепись этого бага): поднимает окно через
`--mcp-live-port`, ресайзит его в 1900×1040, снимает экран `PIL.ImageGrab` до
и после прокрутки туда-обратно и считает диффы. Снимок живого окна через
`resource://screenshot` для этой задачи НЕ годится — он идёт по CPU-пути
(BUG-221) и не показывает то, что рисует композитор.
