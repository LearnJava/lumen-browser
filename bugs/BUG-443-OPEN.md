# BUG-443 — `getComputedStyle()`/`getBoundingClientRect()` на этапе разбора (инлайновый `<script>`, `DOMContentLoaded`) читают пустой снимок: раскладки к этому моменту ещё не было, а принудительного flush-а из JS нет

**Статус:** OPEN
**Компонент:** shell (`crates/shell/src/main.rs::parse_and_layout` — порядок фаз
`parse → CSS → run_scripts_with_dom → images → layout`; `notify_dom_content_loaded`
вызывается сразу после скриптов, `main.rs:5466`), js (`crates/js/src/dom.rs` —
`_lumen_get_computed_style` / `_lumen_get_bounding_rect` читают снимок и не умеют
его запросить)
**Найден:** P1, 2026-07-29, при фиксе [BUG-382](BUG-382-FIXED.md)

## Симптом

После [BUG-382](BUG-382-FIXED.md) снимок геометрии и стилей публикуется сразу по
завершении первичной раскладки, поэтому всё, что исполняется **после** неё
(`load`, `pageshow`, таймеры, rAF, промис-джобы, автоматизация), видит верные
значения. Остаётся ровно один класс кода — исполняющийся **во время разбора**:

* инлайновый `<script>` в `<head>`/`<body>`;
* обработчик `DOMContentLoaded`.

Для них `getComputedStyle(el)` отдаёт `""` по каждому свойству, а
`getBoundingClientRect()` — нулевой прямоугольник.

## Причина

Не доставка, а порядок фаз конвейера: `parse_and_layout` исполняет скрипты
страницы (`run_scripts_with_dom`) и сразу за ними шлёт `DOMContentLoaded` — обе
фазы идут **до** первой раскладки (картинки и раскладка ниже по функции).
Публиковать в этот момент нечего: дерева боксов ещё не существует.

Настоящие браузеры отвечают на такой запрос принудительной синхронной
раскладкой («forced synchronous layout» / layout thrashing): чтение свойства,
зависящего от геометрии, вытесняет незакрытую раскладку прямо внутри вызова.
В Lumen такого механизма нет — JS-рантайм не может попросить раскладку: у него
нет ни доступа к `LayoutSource`/вьюпорту, ни канала к движку (`lumen-js` не
зависит от `lumen-layout`).

## Влияние

Большинство страничного кода (и все популярные фреймворки) инициализируются
именно на `DOMContentLoaded`, поэтому практический охват дефекта широкий, хотя
после BUG-382 он и заметно уже: любое измерение, сделанное в инициализаторе,
получает `0`/`""`, а не значение, и падает в `NaN` ниже по стеку.

Для WPT: тесты, меряющие геометрию/стиль синхронно в теле теста (а не в
`onload`/`async_test`), продолжают давать шум.

## Как чинить (эскиз, не решение)

Нужен канал «JS → раскладка по требованию». Прямой вызов из `lumen-js`
невозможен без цикла в графе зависимостей, поэтому естественная форма — ext-трейт
в `lumen-core` (как `WindowingBackend`/`RenderBackend` из
[`subsystems/core.md`](../subsystems/core.md)), который реализует сторона,
владеющая `LayoutSource` + вьюпортом, и который натив дёргает перед чтением
снимка. Открытые вопросы, которые надо решить до реализации:

* с чем считать раскладку на этапе разбора (картинки ещё не загружены,
  веб-шрифты не зарегистрированы) — браузеры считают ровно с тем, что есть;
* инвалидация: понадобится «грязный» флаг, иначе каждое чтение = полная
  раскладка (то самое layout thrashing, только без кэша);
* стыковка с движковым потоком (ADR-016) — вызов синхронный.

Объём и цена делают это отдельной задачей, а не довеском к BUG-382.
