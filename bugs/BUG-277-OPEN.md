## Причина (гипотеза)

Femtovg и wgpu рендерят субпиксели, AA-кромки и текст по-разному. Femtovg за годы работы
«подстроился» под Edge-эталоны через KNOWN_DEBTOR-цикл. Wgpu-путь этих итераций не проходил.

Крупные провалы (≥10%): TEST-49 (28%), TEST-59 (24%), TEST-76/101/104 (~20%), TEST-62 (16%),
TEST-56 (14%) — вероятно, системные различия (сглаживание текста, градиенты, blending-mode).

## Срез 1 (2026-07-21, P1) — TEST-76 root-cause найден и исправлен

`renderer.rs`'s wgpu paths for `DrawLinearGradient`/`DrawRadialGradient`/`PushMaskLinearGradient`/
`PushMaskRadialGradient` resolved `Px`/`Calc` stop positions via
`resolve_gradient_stops(stops, 1.0)` — a hardcoded `line_len = 1.0` instead of the actual
gradient-line length in CSS px that `cpu_raster.rs`/femtovg use (`linear_uv_endpoints`'s
`2.0 * half_len`, and `radius_x.max(radius_y)` for radial). On TEST-76's
`calc(50% ± 2px)` hard-stop linear gradient this collapsed/mis-scaled the stop band, producing
the 20.15% divergence. Fixed: `linear_gradient_uv_endpoints` now returns `line_len` alongside the
UV endpoints (mirrors `cpu_raster::linear_uv_endpoints`); the radial draw path uses
`radius_x.max(radius_y)`; the two mask variants use the equivalent formulas from
`cpu_raster::render_mask`. TEST-76 74× improved: 20.15% → 0.96% (matches the pre-wgpu femtovg
baseline of 0.64%, residual is AA/font-parity — diff image confirms only thin path-edge fringes
remain, no band mispositioning). `KNOWN_DEBTORS['76']` ratcheted to 0.96%.

Does **not** close BUG-277: the fix only applies to gradients with `Px`/`Calc` stop positions.
TEST-101/104/59/etc remain at their prior numbers — unrelated causes (border-radius AA,
image-set blend, non-gradient tests). Next candidates for a further slice: TEST-49 (28.15%,
background-blend-mode), TEST-62/56 (scroll-snap/border-radius, ≥14%).

## Срез 2 (2026-07-22, P1) — TEST-49 background-blend-mode root-cause найден и исправлен

`background-blend-mode` на top-level боксе (без родительского stacking-context) не
композитился вовсе в wgpu-окне: фоновые blend-слои сидели на `from_level == 1`, чей
«родитель» — реальная swapchain-поверхность, у которой нет `TEXTURE_BINDING` usage и её
нельзя сэмплировать. `renderer.rs`'s `Composite` требует `from_level > 1`, чтобы прочитать
родительский слой, поэтому blend молча падал в plain alpha-over — эффект пропадал целиком
(отсюда 28.15% на TEST-49).

Три части фикса:
1. **Изоляция (`display_list.rs::emit_background_image`).** Когда не-нижний фоновый слой
   реально блендит (`blend_mode != Normal`; `i == 0` всегда подавляется), стек слоёв
   оборачивается в собственную `PushOpacity{alpha:1.0}`/`PopOpacity`-группу. Это даёт
   blend-паре свой двухуровневый offscreen-стек независимо от вложенности предков (нижний
   слой на уровне изоляции, верхний — на уровень выше), так что `Composite` идёт на
   `from_level == 2` (родитель = сэмплируемая offscreen-текстура). Совпадает с семантикой
   CSS Compositing L1 §8.3 «background forms an isolated group» и с cpu_raster/femtovg
   (их immediate-mode canvas на этот момент уже содержит только контент самого бокса —
   CPU-снимки не изменились, `cpu_snapshots_match_references` зелёный).
2. **Un-premultiply в `BLEND_SHADER`.** Offscreen-слои копят ПРЕМУЛЬТИПЛИРОВАННЫЙ контент
   (каждый draw композитится straight-alpha `ALPHA_BLENDING` от прозрачно-чёрного clear →
   rgb остаётся домноженным на alpha). Формулы CSS Compositing L1 §8 ждут straight Cs/Cd —
   теперь делим обратно на alpha (`select(rgb/a, 0, a<=0)`). Прежний код трактовал
   премультиплированный rgb как straight → неверно при alpha<1; заодно чинит «изолирующий
   offscreen-слой чернел при multiply-против-прозрачного».
3. **Per-composite uniform-буфер blend-режима.** `self.blend_mode_uniform` писался через
   `queue.write_buffer` один раз на `PushBlendMode`/`PopBlendMode`; при 2+ таких парах в
   кадре все blend-проходы читали ПОСЛЕДНЕ записанный режим (все write_buffer лендятся до
   сабмита единого энкодера) — тот же класс hazard'а, что уже решён для `filter_param_bufs`.
   Теперь — свежий буфер на каждый composite (`make_blend_mode_param_buf`).

Результат: **TEST-49 28.15% → 2.74%** (10×; остаток — AA-кромка/font-parity, rule 2/3),
KNOWN_DEBTOR ратчет. TEST-148 (isolation) 6.30% → 5.44% — un-premultiply убрал чернение
изолирующего слоя. Полный wgpu-прогон 1–71 без регрессий (дрейф в пределах gdigrab-допуска);
пути не-blend страниц не задеты (display-list байт-в-байт), подтверждено
`cpu_snapshots_match_references`.

Does **not** close BUG-277: mix-blend-mode на top-level боксах (TEST-56 14.12%, и остаток
TEST-148) — отдельный путь, не покрытый background-only изоляцией этого среза; требует
изоляции для самих mix-blend-элементов. Не-blend долги (border-radius AA, filter, image-set,
SVG-AA) не тронуты.

## Срез 3 (2026-08-05, P3) — mix-blend-mode на верхнем уровне: TEST-56 и TEST-148 закрыты

Срез 2 оставлял открытым `mix-blend-mode` на боксах без offscreen-предка. Разбор нашёл
**два независимых дефекта**, оба в wgpu-исполнителе; дисплей-лист не тронут вовсе.

**1. Блэнд в поверхность кадра молча вырождался в alpha-over.** Элемент с
`mix-blend-mode` без offscreen-предка даёт `Composite { from_level: 1 }`, где
«родитель» — swapchain-поверхность. Её нельзя сэмплировать (`TEXTURE_BINDING` у
поверхности не запросить — это не наш `TextureDescriptor`, а `SurfaceConfiguration`),
поэтому исполнитель требовал `from_level > 1` и иначе рисовал обычный source-over —
эффект пропадал целиком (ровно тот же механизм, что срез 2 нашёл для
`background-blend-mode`, но там его удалось обойти изоляцией фонового стека, а здесь
изолировать нечего: блэнд идёт против backdrop-а, а не между своими же слоями).

Фикс: поверхность конфигурируется с `COPY_SRC`, когда его отдаёт драйвер
(`caps.usages`), и её текстура копируется в scratch ровно так же, как это уже делалось
для offscreen-родителя (`ensure_scratch_layer` + `copy_texture_to_texture`), после чего
blend-пасс читает scratch как backdrop и пишет обратно в `frame_view`. Сэмплировать
поверхность по-прежнему нельзя — копировать можно. Headless-текстура кадра несёт
`COPY_SRC` изначально; в `RenderPassMode::Band` (полосный рендер скролл-композитора)
доступен только `TextureView` без текстуры, поэтому там остаётся прежний fallback.

**2. Формула `BLEND_SHADER` брала Cd там, где спека берёт Cs.** Было
`Co = αs·B(Cd,Cs) + αs·Cd·(1−αd) + Cd·(1−αs)`. Спека (CSS Compositing L1 §7–§8) —
сначала смешивание с backdrop-ом `Cs' = (1−αd)·Cs + αd·B(Cd,Cs)`, затем source-over
`Co = αs·Cs' + (1−αs)·αd·Cd`. Прежняя запись теряла множитель `αd` на blended-члене и
подставляла `Cd` на месте `Cs`, поэтому при **прозрачном** backdrop-е (`αd = 0`)
multiply/difference давали `Co = αs·B(0,Cs) = 0` — чёрный вместо собственного цвета
элемента. Это и есть остаток TEST-148: квадрат внутри `isolation: isolate` блендится
против пустой группы. При `αd = 1` (композит в непрозрачный кадр) обе формы совпадают
тождественно — вот почему дефект жил незамеченным на не-изолированных блэндах и почему
TEST-49 не сдвинулся ни на сотую (2.74% → 2.74%).

Заодно результат стал премультиплированным (`αs`/`αd` внесены в `co`) — та же
конвенция, в которой offscreen-слои копят контент и которую ждёт composite-пайплайн
(`One`/`OneMinusSrcAlpha`). Прежняя форма возвращала straight-цвет, что расходилось с
конвенцией слоя при `αd < 1`.

**Результат.** TEST-56 **14.12% → 0.00%**, TEST-148 **5.44% → 0.00%** — обе записи
убраны из `KNOWN_DEBTORS` (пиксель-в-пиксель с Edge; страницы состоят из сплошных
боксов без текста, поэтому нулю есть где взяться). Полный прогон 152 теста
(чанками `--only`, live-окно): регрессий нет, единственное ухудшение против
`results/latest.json` — TEST-61 +6.01 п.п., предсуществующее и уже разобранное в
[BUG-103](BUG-103-OPEN.md) (view-transitions, ни `mix-blend-mode`, ни `isolation` на
странице нет). Остальные сдвиги — улучшения от чужих влитых фиксов (BUG-128 и др.).

Does **not** close BUG-277: не-blend долги базлайна (border-radius AA, filter, image-set,
SVG-AA, mask-image) не тронуты. Крупнейшие оставшиеся — TEST-59 21.98%, TEST-62,
TEST-101/104 ~20%, TEST-26 13.50%, TEST-39 12.65%.

## Срез 4 (2026-08-05, P3) — SDF скруглённого прямоугольника: 7 тестов в PASS

Крупнейший не-blend долг базлайна оказался не «AA-дрейфом», а сломанной
геометрией: **wgpu рисовал `FillRoundedRect` как внутренний прямоугольник плюс
четыре угловые дуги**, теряя краевые полосы шириной r вдоль каждой стороны.
На TEST-101 это видно буквально — синий контейнер 300×300 с `border-radius: 60px`
состоял из столбца x∈[60,240] и двух угловых четвертькругов снизу.

**1. `sdf_rrect` считала краевые полосы внешними.** Функция строит
`q = |p| − half + (rx, ry)` — смещение от центра угловой эллипсы, — но в двух
ветках возвращала `q` без обратного вычитания радиуса:

```wgsl
if q.x <= 0.0 { return q.y; }   // точка в нижней/верхней полосе → q.y > 0 → «снаружи»
if q.y <= 0.0 { return q.x; }   // точка в левом/правом столбце  → q.x > 0 → «снаружи»
```

Верное расстояние здесь — `q.x − rx` (= `|p.x| − half.x`), то есть обычный
box-SDF. Заменено: вся неугловая область (`q.x ≤ 0` **или** `q.y ≤ 0`, а также
вырожденный радиус) считается точным box-SDF-ом
`length(max(d,0)) + min(max(d.x,d.y),0)`, где `d = |p| − half`; эллиптический
член остался только там, где точка внутри угловой полосы по ОБЕИМ осям.
Для круглых углов ветки склеиваются непрерывно на касательных
(`(q.x/r − 1)·r = q.x − r = d.x`), поэтому AA-кайма не рвётся.

Почему дефект дожил до сегодня: ветка «обе оси в углу» была верна, а «внутренний
прямоугольник» (`q.x ≤ 0 && q.y ≤ 0`) возвращал отрицательное значение и тоже
заливался — то есть фигура терялась ровно на полосах шириной r, и на мелких
радиусах (2–8 px) читалась как AA-шум по краю.

**2. Радиусы клэмпились по-осевым `min(r, half)` прямо в шейдере.** CSS
Backgrounds L3 §5.5 требует уменьшать все четыре угла ОДНИМ коэффициентом
(минимум по всем четырём рёбрам). Для «пилюли» `border-radius: 999px` на
300×140 правильный ответ — стадион с круглыми торцами r=70, а по-осевой min
давал `rx=150, ry=70`, то есть сплошной эллипс во всю коробку. Клэмп перенесён
на CPU-сторону в `push_rrect_quad` через общий `CornerRadii::clamped_to_box`
(тот же, которым пользуется `cpu_raster`), из шейдера убран — заодно перестал
резать легальные «широкие» углы вида `border-radius: 100px 0 0 0`.

Дисплей-лист и CPU-путь не тронуты (правка целиком внутри wgpu-исполнителя),
CPU-снимки не перегенерировались.

## Срез 5 (2026-08-05, P3) — скруглённый клип детей: TEST-101 закрыт

Второй дефект, предсказанный срезом 4, подтвердился как есть: `PushClipRoundedRect`
в `renderer.rs` игнорировал `radii` и толкал в `clip_stack` один прямоугольник,
потому что scissor умеет только box. Дети обрезались по bbox: круглый контейнер
(`border-radius: 50%`) оставлял ребёнка квадратом, у пилюли были прямые торцы.

**Механизм фикса — тот же, что уже несут маски и фильтры,** новых понятий не
вводится: push открывает offscreen-уровень (`current_level += 1`, как
`PushOpacity`/`PushFilter`), парный `PopClip` закрывает его новым проходом
`RenderPlanItem::RRectClipComposite` — квад по клип-ректу, сэмплирующий текстуру
уровня и домножающий premultiplied-цвет на покрытие `sdf_rrect`. bbox по-прежнему
идёт в scissor (дешёвое отсечение до пасса), SDF снимает только углы.

Детали, которые пришлось учесть:

- **AA-кромка та же, что у заливки** (`1 − smoothstep(−0.5, 0.5, d)`), иначе край
  ребёнка не сел бы на край контейнера — расхождение читалось бы как ореол.
- **Радиусы проходят тот же `CornerRadii::clamped_to_box`** (CSS Backgrounds L3
  §5.5), что и `push_rrect_quad`: иначе пилюля обрезала бы детей эллипсом, а
  собственный фон рисовала стадионом.
- **Уровень открывается только при axis-aligned трансформе** (`axis_aligned_scale`:
  нет поворота/скоса; масштаб превращает круглые радиусы в эллиптические). Под
  поворотом контур в экранных координатах — уже не rounded-rect, там остаётся
  прежний bbox-фолбэк, а не заведомо неверная маска.
- **Пустой/за-экранный уровень выбрасывается из плана** (`LevelBounds`, как в
  `PopOpacity`) — скруглённый клип без нарисованных детей не стоит ни пасса.
- **`sdf_rrect` вынесена в общую WGSL-константу `SDF_RRECT_WGSL`** и подклеивается
  к обоим шейдерам (заливка + клип). Вторая копия формулы — ровно тот путь,
  которым краевой дефект среза 4 вернулся бы на одном из двух путей.
- Пары стеков: `clip_level_stack` двигается ровно теми же командами, что
  `clip_stack`, за вычетом `PushScrollLayer`/`PopScrollLayer` (у них своя пара).

Дисплей-лист и CPU-путь не тронуты (правка целиком внутри wgpu-исполнителя); на
CPU скруглённый клип живёт с [BUG-249](BUG-249-FIXED.md), CPU-снимки не менялись.

## Срез 6 (2026-08-05, P3) — маски и конечная фигура радиального градиента

Крупнейшие оставшиеся долги — TEST-104 (32.28 %) и TEST-26 (13.30 %) — числились
за «sub-pixel snapping маски» (запись `KNOWN_DEBTORS`, DS-9 2026-07-23). Диагноз
был неверен: под ним лежали **три независимых дефекта wgpu-исполнителя**,
дисплей-лист снова не тронут.

**1. Квады маски не прогонялись через накопленный `PushTransform`.** Каждый
обычный draw делает `push_*_quad(...)` и сразу
`apply_affine_to_*_verts(&mut verts[v_start..], m)` — маски этого шага не делали
вовсе. Их вершины (квад mask-композита в `PopMask`, квад градиента маски и квад
`PopMaskLayer`) оставались в нетрансформированных координатах, тогда как сам
контент рисуется трансформированным: шелл сдвигает страницу вниз на высоту
хрома (`toolbar::CHROME_H`) одним `PushTransform`.

Следствие ровно арифметическое. Контент элемента лежит в слое на
`y ∈ [top + CHROME_H, bottom + CHROME_H]`, квад композита покрывает
`y ∈ [top, bottom]`, а `uv_layer = pos / viewport` сэмплирует слой там же, где
пишет. Пересечение — `[top + CHROME_H, bottom]`: то, что попало в пересечение,
композитится **на верной позиции экрана**, а нижние `CHROME_H` px элемента не
композитятся никогда. Отсюда и «сдвиг снапинга», и то, почему число выросло
11.24 → 13.50 при удвоении хрома (36 → 72 px) — это не новый sub-pixel-эффект,
а прямая пропорция: обрезается ровно столько, сколько добавили хрома. Замер
до фикса: у всех маскированных ячеек TEST-104 нижняя граница на 68 px выше
эталонной (`#contentArea` начинается на y = 68), у немаскированной контрольной
ячейки — совпадает с эталоном до пикселя.

Сама маска при этом ещё и разъезжалась с элементом: временная текстура
градиента писалась по тем же нетрансформированным координатам, поэтому её
содержимое стояло на `CHROME_H` px выше, чем читалось.

**2. Радиальный градиент нормировался на полуширину бокса, а не на радиус.**
`radial_gradient_uv_params` возвращала `p1 = [max(cx, 1−cx), max(cy, 1−cy)]` —
полуоси коробки в UV, то есть farthest-**side**, — и `radius_x`/`radius_y`,
которые дисплей-лист уже посчитал по CSS Images L3 §3.5, отбрасывались
(`DrawRadialGradient` их несёт; `cpu_raster::rasterize_radial_gradient` берёт
именно их). Шейдер считает `t = length((uv − p0) / p1)`, поэтому `t = 1` ложилось
на вписанный эллипс вместо конечной фигуры: на `circle at 50% 50%` в квадрате
300×300 это радиус 150 px вместо farthest-corner 212 px — градиент сжимался
в √2 раза. Теперь `p1 = [radius_x / w, radius_y / h]`, то есть `t = 1` ровно на
конечной фигуре. Маске радиуса не передают, и она, как и `cpu_raster::render_mask`,
считает его сама (`hypot` до дальнего угла) — раньше это число уходило только
в `line_len` для `Px`/`Calc`-стопов, а на нормировку не влияло.

**3. UV масок делились на размер поверхности, а не на CSS-viewport.** Позиции
вершин — в CSS px, `surface_w/h` — в device px; совпадают они только при
`dpr = 1`, на котором всё и мерилось. Полноразмерные текстуры (временная
текстура градиента, scratch и слой маски у `PopMaskLayer`) пишутся через тот же
`u.viewport`-маппинг, поэтому CSS-позиция `p` читается по `uv = p / viewport`.
Скрытый дефект DPI-масштаба, графическим гейтом не покрытый; исправлен заодно,
потому что квады всё равно переписывались.

Заодно `sdf`-подобного дублирования не завелось: квад градиента маски строится
один раз на этапе планирования (`transformed_grad_quad`) и хранится в
`MaskGradientSpec` уже трансформированным — рендер-стадия матрицы не видит,
и вторая копия геометрии была бы ровно тем местом, где расхождение вернулось бы.
