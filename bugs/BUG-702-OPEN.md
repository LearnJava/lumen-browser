# BUG-702: `tbank.ru/auth/login/` вешает JS-движок бесконечным циклом (100% CPU, не завершается) — взаимодействие `react.js`+`platform.js`

**Статус:** OPEN (частично исправлено — см. [BUG-706](BUG-706-FIXED.md))
**Компонент:** js (движок; один подтверждённый и исправленный триггер — `MessagePort`/`MessageChannel` в `crates/js/src/dom.rs`, см. [BUG-706](BUG-706-FIXED.md); второй, ещё не исправленный триггер локализован до statement 235 модуля `41760` в `platform.js` — bootstrap-вызов Tramvai-приложения через `regeneratorRuntime`-скомпилированный `initialization()`; воспроизводится тривиальной regenerator-функцией на тех же `i`/`n` переменных, НЕ воспроизводится тем же кодом с нуля — причина не различена между «реальный баг в глобальном состоянии» и «артефакт агрессивной редукции», см. «Раунд-3» ниже)
**Найден:** живая проверка `https://www.tbank.ru/auth/login/` (запрос пользователя — открыть браузер, зайти в личный кабинет, заполнить поля входа), 2026-08-09

## Симптом

`lumen --dump-layout https://www.tbank.ru/auth/login/` никогда не завершается —
`timeout 120` даёт exit 124. CPU процесса растёт монотонно, память стабильна
~150-165МБ — настоящий бесконечный цикл, не ожидание сети.

Live-окно (`--mcp-live-port`): `navigate` возвращает `Ack`, `wait{document_ready}`
уходит в таймаут, `eval` затем навсегда падает `JS context not available` —
движковый поток шелла застрял внутри зависшего `rt.eval`, это следствие
зависания, не отдельный баг.

## Локализация (полная бисекция — 2026-08-09, отдельная сессия P3)

Страница входа подключает 4 внешних скрипта с `cdn.tbank.ru`; исходная
бисекция (первая сессия) сузила до пары:
`unic/sso-newauth/react.<hash>.js` (140КБ) + `unic/sso-newauth/platform.<hash>.js`
(493КБ) — каждый по отдельности мгновенен, вместе виснут, воспроизводится
полностью офлайн (без сети, локальным HTML с двумя `<script src>`).

**Автоматизированная бисекция** (Node.js + acorn AST-парсинг, delta-debugging
поверх границ модулей/операторов webpack-бандла, каждый шаг проверялся
реальным запуском `lumen.exe --dump-layout` с robust-timeout через
`taskkill /T /F`) прошла несколько раундов, сужая от «630КБ, два файла» до
54КБ **полностью офлайн-воспроизводимого репро** (`react.js` без изменений +
урезанный `platform.js`, который не делает ничего, кроме: (1) запуска
core-js Promise-polyfill-detection кода и (2) одного `require()` React
Scheduler-модуля). Финальная цепочка причинности, подтверждённая построчным
инструментированием (`console.log`-метки внутри реального минифицированного
кода на каждом top-level statement):

1. `platform.js` требует `44557` → core-js Promise-конструктор
   feature-detection (`36318`/`13970`/`43033`/`46759`/`29833` — стандартный
   core-js `es.promise.constructor`/`es.set-immediate` полифилл).
2. Позже `platform.js`/`react.js` требуют React-DOM через собственный
   (не webpack Module Federation, самописный, но по форме идентичный)
   shared-module resolver runtime (`i.I`/`n(...)`/`i.m[id]=...`).
3. Это в итоге требует `react.js`-модуль `41745` (react-dom) →
   `72824`/`20805` — **React's Scheduler package** (`scheduler.production.min.js`,
   опознан по сигнатуре `unstable_scheduleCallback`/`MessageChannel`).
4. Само требование модуля `20805` (не вызов `scheduleCallback`, просто
   evaluation модуля) зависает — доказано двумя независимыми тестами:
   стаб-замена React-core (`68866`) на тривиальную функцию НЕ убирает
   зависание; стаб-замена именно Scheduler-модуля (`20805`) на тривиальную
   функцию убирает зависание полностью.
5. Построчная инструментация модуля `20805` показала зависание ровно на
   `L.port1.onmessage=T` (statement 13 — MessageChannel-based scheduler
   bootstrap) — присваивание обработчика на MessagePort, а не сам
   `new MessageChannel()` (который в изоляции не виснет) и не вызов `T()`
   (который при первом присваивании тривиален, `_` ещё `null`).
6. Найден и подтверждён Rust-уровневый механизм: `MessagePort.postMessage`/
   `.start()` в `crates/js/src/dom.rs` планировали доставку через
   `queueMicrotask` вместо задачи (нарушение HTML §9.2.3) — под V8's
   auto-draining микрозадач это ломает именно тот паттерн, который использует
   React Scheduler (self-rescheduling `MessageChannel`-потребитель,
   специально выбранный вместо Promise ради настоящей macrotask-границы),
   ЕСЛИ параллельно работает второй независимый producer (здесь — core-js's
   собственный `setImmediate`-фолбэк, который тоже создаёт `MessageChannel`).
   Заведено и исправлено как **[BUG-706](BUG-706-FIXED.md)**.

## Что уже исправлено

[BUG-706](BUG-706-FIXED.md): `MessagePort.postMessage`/`.start()` теперь
планируют доставку через `setTimeout(fn,0)` (тот же механизм, что уже
корректно использовал `window.postMessage`), а не `queueMicrotask`.
Верифицировано на 54КБ минимальном репро — больше не виснет.

## Что ещё НЕ исправлено (остаток)

**Полные, неурезанные бандлы tbank.ru (`react.js`+`platform.js` целиком) ВСЁ
ЕЩЁ виснут** с исправленным движком (подтверждено, `timeout 60` → exit 124).
Значит существует минимум ещё один независимый триггер где-то в оставшейся
части 493КБ `platform.js`.

## Раунд-2 бисекции — завершён, новый триггер строго локализован (P3, 2026-08-09, отдельная сессия)

Продолжение того же инструмента (Node+acorn ddmin, `spawn`+`taskkill /T /F`,
robust-timeout) на ИСПРАВЛЕННОМ (BUG-706) бинарнике, начиная с нуля (список
модулей прошлого раунда не сохранился). Два ускорения алгоритма, стоящие
переиспользования в будущих бисекциях:
- **Пропуск фазы "chunk alone"** при мелкой грануляции (chunks.length > 20):
  малый чанк почти никогда не воспроизводит зависание в изоляции без
  остального контекста бандла, а полный проход по всем n чанкам перед
  переходом к complement-фазе тратит ~половину тестов впустую. Пропуск
  этой фазы ускорил сходимость примерно вдвое.
- **Перемешивание порядка элементов перед разбиением на чанки** на каждой
  итерации (а не фиксированный порядок исходного файла) — не дало
  измеримого эффекта в этом прогоне (узкое место оказалось не в порядке,
  а в самой "chunk alone"-фазе), но дёшево и не вредит, оставлено.

**Результат module-level бисекции:** 501 модуль `platform.js` → 94 модуля
(1-minimal, ddmin сошёлся: `n >= circumstances.length`). Полный список 94
ключей модулей и техника — см. [[project_bug702_round2_localization]] в
памяти ассистента (списки ключей туда сохранены текстом, `.tmp/` не
коммитится). Один из 94 — модуль `41760` (286КБ, самый большой в файле) —
require-агрегатор с `MutationObserver`/`postMessage`/`setTimeout`-паттернами
на верхнем уровне; статический grep подтвердил, что это **единственный** из
94 модулей, где вообще встречаются React-хуки (`useSyncExternalStore` и
др.) — весь оставшийся триггер живёт внутри него.

**Statement-level бисекция внутри модуля `41760`:** 236 top-level
statements → 117 (1-minimal). Реальный полезный код в оставшихся statements
— библиотека клиентского роутинга фреймворка **Tramvai** (внутренний
SPA-фреймворк T-Bank/Авито; строка `window.__TRAMVAI_HTML_READY_PROMISE__`
в одном из statements подтверждает атрибуцию): фабрика роутера (~19.5КБ,
опции `trailingSlash`/`mergeSlashes`/`enableViewTransitions`/
`beforeResolve`/`beforeNavigate`/`afterNavigate`), event-emitter-класс
(~18КБ), route-guard логика (~15КБ), URL-валидатор (~11КБ),
history/view-transitions обёртка (~10КБ) — плюс **88 экземпляров**
`for(;;)switch(t.prev=t.next)` (Babel regenerator-runtime state-machine —
стандартный паттерн транспилированных `async function`, не сам по себе
баг, но означает, что искомый цикл почти наверняка живёт внутри одной из
~88 транспилированных асинхронных функций).

**Независимость от BUG-706/Scheduler — подтверждена экспериментально:**
удаление модуля React Scheduler (`20805` в `react.js`) из репро **не**
убирает зависание (`timeout 15` → всё ещё виснет). Это НЕ рецидив
исправленного триггера — самостоятельный, ранее неизвестный второй
дефект.

**`react.js` тоже бисектирован (впервые в этом расследовании)** — у него
свой, отдельный, гораздо более мелкий webpack module map (`(self.wsp=...)
.push([["react"],{...9 модулей...}])`, не найденный первым acorn-поиском,
настроенным на map >50 записей — потребовалась отдельная эвристика поиска
`.push([ArrayExpression, ObjectExpression])`). Из 9 модулей `react.js`
для воспроизведения нужны **только два**: `68866` (сам пакет `react`,
React 18.3.1 — `Component`/`createElement`/хуки-прокси на
`ReactCurrentDispatcher.current`) и `57203` (тривиальный ре-экспорт
`e.exports=t(68866)`). **`react-dom` (`41745`, 129КБ — самый большой модуль
файла) для зависания НЕ нужен вообще** — то есть настоящего рендера React
не происходит, `ReactDOM.render`/`createRoot` в цепочке причинности нет.
Это исключает как минимум одну гипотезу: `useSyncExternalStore`,
встречающийся в оставшемся коде `41760` (компонент-провайдер `Ru`,
использующий `(0, Su.useSyncExternalStore)` из отдельного пакета-шима
`use-sync-external-store`, не из чистого React), скорее всего **не**
исполняется по-настоящему (без `react-dom` этот компонент никогда не
рендерится) — его код остаётся в 1-minimal репро потому, что удаление
statement'а, где он объявлен, ломает что-то ДО реального цикла (вероятно
ReferenceError на использовании определяемого там символа), а не потому,
что сам компонент выполняется. **Значит настоящий цикл — в
top-level-исполняемом коде модуля `41760` (в момент `require()`, не внутри
функции/компонента, который никогда не вызывается), скорее всего внутри
одной из ~88 regenerator-транспилированных async-функций.**

**Минимальное подтверждённое репро на конец сессии:** `react.js` (94→2
модуля, 6.7КБ полезной нагрузки) + `platform.js` (501→94 модуля, один из
которых — `41760` сужен с 236 до 117 top-level statements, ~222КБ
полезной нагрузки) — `timeout 20` → exit 124, зависание подтверждено.

## Раунд-3 бисекции — statement 235 найдена как точное место зависания, дальше локализовано до regenerator-runtime (P3, 2026-08-09, третья сессия)

Бандлы перескачаны заново с `cdn.tbank.ru` (хэши сменились:
`react.ae1f0f0d516279a1.js`, `platform.92ea3fe00eb9d2b9.js`) — размеры
байт-в-байт совпали с раундом-2 (140185 / 493056), поэтому сохранённые
списки индексов (94 модуля `platform.js`, 117 statements внутри модуля
`41760`, 2 модуля `react.js`) применились без повторной ddmin-бисекции и
сразу воспроизвели зависание на пересобранном (текущий `main`,
BUG-706-фикс внутри) бинарнике.

**Техника «start/end маркер»** (новая, быстрее чем ddmin для этого шага):
вместо продолжения ddmin внутрь 117 statements, каждый top-level statement
модуля `41760` обёрнут в `console.log("S_START "+i); STMT;
console.log("S_END "+i);` — маркеры видны в выводе `lumen.exe` как
`[JS] ...` (стандартный вывод `console.log`, не буферизуется, успевает
попасть в лог до зависания). За один прогон это показало **statement 235
(последний из 117) стартует, но никогда не завершается** — все
предыдущие 116 стартуют И завершаются штатно. Гоча при первой попытке:
вставка `console.log(...)` СРАЗУ ПОСЛЕ statement без предваряющего `;`
даёт синтаксическую ошибку `Unexpected identifier 'console'`, если
statement — последний в функции и в исходнике у него нет trailing
`;` перед закрывающей `}` (типично для минифицированного кода) — чинится
префиксом `;` перед каждой инъекцией маркера.

**Statement 235 — сам bootstrap-вызов Tramvai-приложения:**
```js
!function(t){var e;try{e=new T(t)}catch(t){throw t.appCreationError=!0,t}
e.initialization("client").then((function(){return e}))
 .catch((function(t){throw t instanceof Error&&(t.appCreationError=!0),t}))}
({name:"newauth", modules:[...17 элементов...], bundles:{...}, providers:[...6...]})
```
Точечная замена содержимого этого ОДНОГО statement (при неизменных
остальных 116) показала:
- `new T({})` (конструктор Tramvai-приложения, пустой конфиг) — **НЕ
  виснет**, завершается штатно.
- `new T({}).initialization("client")` (без `.then/.catch`) — **виснет**.
  Значит проблема внутри `initialization`, не в конструкторе и не в
  цепочке промисов вокруг вызова.
- `di.get({token:C.Fp,optional:true})` и `di.get({token:O,optional:true})`
  (две DI-подстановки, вызываемые ВНУТРИ `initialization`), протестированы
  каждая **отдельно и синхронно** (без regenerator-обвязки) на новом `new
  T({})` — **обе завершаются штатно**. Значит DI-контейнер Tramvai сам по
  себе не виснет — гипотеза «зависание в DI resolution» из раунда-2
  **опровергнута**.
- `initialization` — это `regeneratorRuntime`-скомпилированная async-
  функция (Babel-паттерн `(0,n.Z)(i().mark(function t(...){return
  i().wrap(function(t){for(;;)switch(...){...}},t)}))`, где в скоупе
  модуля `n.Z` — классический `_asyncToGenerator`, `i()` — классический
  `regeneratorRuntime` объект с методами
  `wrap,isGeneratorFunction,mark,awrap,AsyncIterator,async,keys,values`
  — подтверждено дампом `typeof`/`toString()` этих переменных на месте).
- Синтетическая **тривиальная** regenerator-функция (`return
  regeneratorRuntime.abrupt("return",42)`, без единого `await`/DI/Tramvai-
  кода), собранная через ТЕ ЖЕ `n`/`i` переменные из скоупа модуля
  `41760` и запущенная ВМЕСТО statement 235 — **тоже виснет**. Значит
  дефект НЕ в Tramvai-коде вообще — воспроизводится чистым
  `regeneratorRuntime.mark`+`.wrap`+`_asyncToGenerator`-паттерном.

**Решающий контрольный эксперимент:** та же самая тривиальная
regenerator-функция, собранная с НУЛЯ — официальный npm-пакет
`regenerator-runtime` (файл `runtime.js`, тот же classic API) + написанный
вручную классический `_asyncToGenerator`/`asyncGeneratorStep` (побайтово
той же формы, что и в бандле) — в ПОЛНОСТЬЮ отдельном, чистом HTML без
единого байта из `react.js`/`platform.js` — **НЕ виснет**, отрабатывает
штатно (`foo().then(v=>...)` печатает `42`). Т.е. код самого
`regenerator-runtime` корректен и работает в Lumen изолированно.

**Вывод раунда-3:** зависание воспроизводится ТОЛЬКО когда `regenerator-
runtime`-машина запускается ЧЕРЕЗ переменные `i`/`n`, разделяемые (общий
scope) с предыдущими 116 statements модуля `41760` — то же самое, побайтово
идентичное API, взятое «с чистого листа», не виснет. Это означает одно из
двух (не различено в этой сессии):
1. **Реальный баг**: одно из предыдущих 116 statements (порт-агрегат
   множества исходно раздельных webpack-модулей, слитых в один по
   require-графу) оставляет `regeneratorRuntime`/`Promise`/`Symbol`/др.
   глобальные объекты в состоянии, которое ломает внутренний
   `while(true)`-диспетчер `regeneratorRuntime.invoke` конкретно под
   Lumin'ом (например, полифилл core-js, упомянутый в раунде-1
   [[project_bug702_messageport_task_vs_microtask]] — «core-js
   Promise-constructor feature-detection» — мог неверно определить
   природу Promise/Symbol в Lumen и подменить их некорректным
   полифиллом, который затем ломает reentrancy-guard `regeneratorRuntime`
   держит через `f`/`context` объект).
2. **Артефакт собственной редукции**: агрессивное удаление 119 из 236
   statements могло убрать код, от которого — в оригинале — зависело
   корректное поведение (например, инициализацию переменной, без которой
   `regeneratorRuntime`-диспетчер входит в непредусмотренный путь), и
   зависание, которое мы сейчас видим, специфично для НАШЕГО урезанного
   репро, а не для полного бандла (хотя полный неурезанный бандл тоже
   виснет — просто не факт, что по тому же самому механизму).

**Не различено, какая из двух гипотез верна — это первоочередная задача
следующей сессии.**

## Как продолжить (для следующей сессии)

1. Инфраструктура (acorn-бисектор, robust-timeout runner, patch_stmt.js
   для точечной замены одного statement) быстро восстанавливается с нуля
   — см. [[reference_js_bundle_hang_bisection_technique]] и
   [[feedback_spawn_sync_timeout_unreliable_on_windows]] в памяти.
   Точные списки индексов (94/117/2) — в
   [[project_bug702_round2_localization]], инструмент точечной замены
   statement 235 и результаты всех вариантов раунда-3 — в
   [[project_bug702_round3_regenerator_localization]] (новая память).
2. **Первоочередная задача**: различить гипотезы 1 и 2 выше. Практический
   путь — вместо statement 235 (полностью заменённого нашей тривиальной
   regenerator-функцией) начать УБИРАТЬ из оставшихся 116 «сетапных»
   statements по одному/группами (тот же ddmin, но теперь ЦЕЛЬ —
   «regenerator-репро всё ещё виснет с тривиальным телом на statement
   235»), пока не найдётся МИНИМАЛЬНОЕ подмножество из 116, необходимое
   для воспроизведения — тогда можно будет прочитать именно ЭТОТ код и
   понять, что именно он делает с глобальным состоянием (Promise, Symbol,
   core-js, `Object.prototype`) перед тем как звать `regeneratorRuntime`.
   Это должно быть быстрее раунда-2, потому что «детектор» зависания
   теперь тривиален (bare regenerator call), а не Tramvai DI/App логика.
3. Если гипотеза 1 подтвердится — это будет чистый инженерный баг уровня
   Lumen (вероятно в том, как Lumen инициализирует/предоставляет
   `Promise`/`Symbol`/`WeakMap` глобалы, которые core-js полифиллит
