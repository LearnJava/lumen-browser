# BUG-702: `tbank.ru/auth/login/` вешает JS-движок бесконечным циклом (100% CPU, не завершается) — взаимодействие `react.js`+`platform.js`

**Статус:** OPEN (частично исправлено — см. [BUG-706](BUG-706-FIXED.md))
**Компонент:** js (V8-движок; один подтверждённый и исправленный триггер — `MessagePort`/`MessageChannel` в `crates/js/src/dom.rs`; минимум один остающийся триггер не локализован глубже ~215 модулей `platform.js`)
**Найден:** живая проверка `https://www.tbank.ru/auth/login/` (запрос пользователя — открыть браузер, зайти в личный кабинет, заполнить поля входа), 2026-08-09

## Симптом

`lumen --dump-layout https://www.tbank.ru/auth/login/` никогда не завершается —
`timeout 120` даёт exit 124. CPU процесса растёт монотонно, память стабильна
~150-165МБ — настоящий бесконечный цикл, не ожидание сети.

Live-окно (`--mcp-live-port`): `navigate` возвращает `Ack`, `wait{document_ready}`
уходит в таймаут, `eval` затем навсегда падает `JS context not available` —
движковый поток шелла застрял внутри зависшего `rt.eval`, это следствие
зависания, не отдельный баг.

## Локализация (полная бисекция — 2026-08-09, отдельная сессия P3)

Страница входа подключает 4 внешних скрипта с `cdn.tbank.ru`; исходная
бисекция (первая сессия) сузила до пары:
`unic/sso-newauth/react.<hash>.js` (140КБ) + `unic/sso-newauth/platform.<hash>.js`
(493КБ) — каждый по отдельности мгновенен, вместе виснут, воспроизводится
полностью офлайн (без сети, локальным HTML с двумя `<script src>`).

**Автоматизированная бисекция** (Node.js + acorn AST-парсинг, delta-debugging
поверх границ модулей/операторов webpack-бандла, каждый шаг проверялся
реальным запуском `lumen.exe --dump-layout` с robust-timeout через
`taskkill /T /F`) прошла несколько раундов, сужая от «630КБ, два файла» до
54КБ **полностью офлайн-воспроизводимого репро** (`react.js` без изменений +
урезанный `platform.js`, который не делает ничего, кроме: (1) запуска
core-js Promise-polyfill-detection кода и (2) одного `require()` React
Scheduler-модуля). Финальная цепочка причинности, подтверждённая построчным
инструментированием (`console.log`-метки внутри реального минифицированного
кода на каждом top-level statement):

1. `platform.js` требует `44557` → core-js Promise-конструктор
   feature-detection (`36318`/`13970`/`43033`/`46759`/`29833` — стандартный
   core-js `es.promise.constructor`/`es.set-immediate` полифилл).
2. Позже `platform.js`/`react.js` требуют React-DOM через собственный
   (не webpack Module Federation, самописный, но по форме идентичный)
   shared-module resolver runtime (`i.I`/`n(...)`/`i.m[id]=...`).
3. Это в итоге требует `react.js`-модуль `41745` (react-dom) →
   `72824`/`20805` — **React's Scheduler package** (`scheduler.production.min.js`,
   опознан по сигнатуре `unstable_scheduleCallback`/`MessageChannel`).
4. Само требование модуля `20805` (не вызов `scheduleCallback`, просто
   evaluation модуля) зависает — доказано двумя независимыми тестами:
   стаб-замена React-core (`68866`) на тривиальную функцию НЕ убирает
   зависание; стаб-замена именно Scheduler-модуля (`20805`) на тривиальную
   функцию убирает зависание полностью.
5. Построчная инструментация модуля `20805` показала зависание ровно на
   `L.port1.onmessage=T` (statement 13 — MessageChannel-based scheduler
   bootstrap) — присваивание обработчика на MessagePort, а не сам
   `new MessageChannel()` (который в изоляции не виснет) и не вызов `T()`
   (который при первом присваивании тривиален, `_` ещё `null`).
6. Найден и подтверждён Rust-уровневый механизм: `MessagePort.postMessage`/
   `.start()` в `crates/js/src/dom.rs` планировали доставку через
   `queueMicrotask` вместо задачи (нарушение HTML §9.2.3) — под V8's
   auto-draining микрозадач это ломает именно тот паттерн, который использует
   React Scheduler (self-rescheduling `MessageChannel`-потребитель,
   специально выбранный вместо Promise ради настоящей macrotask-границы),
   ЕСЛИ параллельно работает второй независимый producer (здесь — core-js's
   собственный `setImmediate`-фолбэк, который тоже создаёт `MessageChannel`).
   Заведено и исправлено как **[BUG-706](BUG-706-FIXED.md)**.

## Что уже исправлено

[BUG-706](BUG-706-FIXED.md): `MessagePort.postMessage`/`.start()` теперь
планируют доставку через `setTimeout(fn,0)` (тот же механизм, что уже
корректно использовал `window.postMessage`), а не `queueMicrotask`.
Верифицировано на 54КБ минимальном репро — больше не виснет.

## Что ещё НЕ исправлено (остаток)

**Полные, неурезанные бандлы tbank.ru (`react.js`+`platform.js` целиком) ВСЁ
ЕЩЁ виснут** с исправленным движком (подтверждено, `timeout 60` → exit 124).
Значит существует минимум ещё один независимый триггер где-то в оставшейся
части 493КБ `platform.js` (настоящее приложение, а не только
Promise-полифилл-детекция + require-цепочка, которые составляли 54КБ
минимального репро).

Раунд-2 автоматизированной module-level бисекции (тот же инструмент, тот же
принцип, но с ИСПРАВЛЕННЫМ бинарником и полным `platform.js`) запущен и дал
прогресс: из 501 модулей `platform.js` сужено до ~215 (список модулей —
не сохранён постоянно, только в эфемерном `.tmp/`, который не коммитится;
при продолжении — перезапустить `bisect_round2.js`-подобный скрипт с нуля,
инфраструктура быстро восстанавливается, см. ниже) — остановлено по времени
сессии, не по технической причине. Дальнейшее сужение весьма вероятно
приведёт к структурно похожему дефекту (либо ещё один
`MessageChannel`/таймер-паттерн, либо иной класс реентерабельности,
специфичный для V8-интеграции Lumen).

## Как продолжить (для следующей сессии)

1. Скачать те же 2 бандла (`curl`, точные URL — см. `.tmp/tbank-*.log` в
   старых логах сессии, или заново живой проверкой tbank.ru):
   `cdn.tbank.ru/unic/sso-newauth/react.ae1f0f0d516279a1.js` +
   `.../platform.92ea3fe00eb9d2b9.js` (хэши могут устареть при редеплое
   сайта — тогда просто взять текущие).
2. Собрать harness: acorn (`npm install acorn acorn-walk` в scratch-папке
   вне репозитория, например `.tmp/`) для парсинга webpack module map
   объекта `{ID:function(t,e,r){...}, ...}` в `platform.js`, delta-debugging
   (ddmin) по индексам модулей — стабить кандидатов на `function(){}`,
   гонять `lumen.exe --dump-layout` с robust-timeout (`spawn`+`taskkill /T /F`,
   НЕ `spawnSync{timeout}` — ненадёжно убивает дочерний процесс на Windows,
   see BUG-706 fix session notes) до сходимости.
3. Ожидаемое время: ~30-40 минут автоматического прогона на раунд (по опыту
   первого и второго раунда).
4. Возможный общий корень с [BUG-703](BUG-703-OPEN.md) (зависшая гидратация
   на главной странице, другая пара react+platform-бандлов того же вендора)
   — не доказано, стоит проверить первым.

Найден вне P-ролей, живая проверка tbank.ru, 2026-08-09. Частично
исправлено (BUG-706) и продиагностировано P3, 2026-08-09.
