# BUG-286 — скролл: `content-visibility:auto` relevance-триггер стопорил UI-поток на ~1с

**Статус:** OPEN (DEBTOR) — митигация Задач 1+2 влита и подтверждена живым замером; остаток требует P1-масштаба архитектурной переделки (Задача 3), см. «Замер 2026-08-06» ниже
**Компонент:** shell (`crates/shell/src/main.rs`, `maybe_expand_cv_relevant`)
**Найден:** 2026-07-15, ручной тест колесом мыши на https://ria.ru (в ходе расследования BUG-284)

## Симптом

Первый скролл колесом на тяжёлой реальной странице «подвисает» примерно на
секунду, дальнейший скролл идёт гладко. `LUMEN_FRAME_LOG=1` на ria.ru поймал
это прямо посреди прокрутки:

```
[engine] relayout 1041.99ms
```

## Корень

`maybe_expand_cv_relevant` (`crates/shell/src/main.rs`, вызывается на каждом
кадре `RedrawRequested`, Step 1.6 «Update the rendering») — единственный из
scroll/relayout-триггеров, звавший **напрямую** синхронный `self.relayout()`
вместо `self.relayout_raf_dirty()`, которым уже пользуются rAF DOM-dirty flush
и zoom-дебаунс. Как только скроллом в расширенный viewport (`viewport +
CV_SLACK_FACTOR`) попадает пропущенный `content-visibility:auto`-узел, эта
функция раскрывает его (`cv_relevant.extend`) и синхронно гонит **полный**
relayout — пересчёт CSS-каскада (`compute_style`) для всех styled-узлов
документа на UI-потоке. На ria.ru (3093 правила, 1141 styled-узел, до фикса
BUG-284 — 2.4с/relayout, после — ~1.0–1.1с) это блокирует событийный цикл
ровно на то время, пока идёт `compute_style`.

Совпадает с «первым» скроллом чаще всего потому, что до первого скролл-тика
весь под-fold контент под `content-visibility:auto` остаётся «skipped» —
раскрывается он только когда впервые попадает в viewport+запас.

## Фикс (влит)

`maybe_expand_cv_relevant`: `self.relayout()` → `self.relayout_raf_dirty()`.
Под `LUMEN_ENGINE_THREAD=1` (не дефолт) это уводит relayout на движковый
поток (fire-and-forget, latest-wins — контент выкладывается на один из
следующих кадров вместо блокировки текущего). На дефолтной сборке (флаг
выключен) `relayout_raf_dirty()` падает обратно на тот же
incremental-затем-full путь — **поведение и стоимость на UI-потоке не
меняются**, зафиксирован только пропущенный кейс маршрутизации (согласованность
с остальными scroll/relayout-триггерами).

## Остаток (не устранён этой задачей)

Настоящий источник ~1с — сам каскад (`compute_style` на ~1141 узел), не
маршрутизация. `try_relayout_raf_incremental()` тоже не спасает много — он
всё равно пересчитывает полный каскад, пропускает только геометрию
неизменившихся поддеревьев. Полный план трёх независимых способов закрыть
это (ускорить `compute_style`, включить `LUMEN_ENGINE_THREAD` по умолчанию,
частичный пересчёт стилей поддерева) — [docs/tasks/p3-cascade-perf.md](../docs/tasks/p3-cascade-perf.md)
(точка входа для следующей сессии). `tracy` УЖЕ подключён к `lumen-layout`
(проверено 2026-07-15) — доступен `cargo run -p lumen-shell --features tracy`,
не нужно ничего доустанавливать в коде, только скачать GUI-приложение.

**БЛОКЕР для дальнейшей работы (найдено P3 2026-08-06, независимо
переоткрыто из этого же входа — см. подтверждение ниже):** живой скролл
на ria.ru (тот же сайт, что использует этот баг для репро) в тот момент не
доходил до состояния «~1с cascade-стопор» вообще — окно необратимо
зависало (0% CPU, ≥180с, любая automation-команда таймаутила) значительно
раньше/вместо этого, из-за отдельного бага
[BUG-307](BUG-307-FIXED.md) (WebSocket recv-мьютекс держался вечно на
простое). **BUG-307 исправлен в той же сессии 2026-08-06** — блокер снят,
см. «Замер 2026-08-06» ниже с фактическими числами после фикса.

## Замер 2026-08-06 (P3) — блокер снят, живой замер сделан

Собран свежий `dev-release`, живой прогон через MCP (`--mcp-live-port`) на
https://ria.ru: `navigate` → `wait document_ready` → 2с на докачку ресурсов
→ 20 тиков `scroll` (400px, раз в 100мс). Полный лог `[profile]`/`[frame]`/
`[engine]` — см. метод в [docs/tasks/p3-cascade-perf.md](../docs/tasks/p3-cascade-perf.md).

**Результат: полного UI-фриза больше нет.** RTT каждого `scroll`-вызова:

```
scroll[0]   2.7ms
scroll[1] 495.9ms   ← единственный стопор, первое раскрытие content-visibility
scroll[2]   3.3ms
scroll[3..19]  1.3–4.7ms
```

Соответствующий лог движка вокруг стопора:

```
[engine] relayout 511.07ms (off-thread) dl=1071 styled=1150
[frame] total 580.03ms  (scroll_y 400, dl 1071 cmds)
[frame] total   3.68ms  (scroll_y 800, dl 1071 cmds)
```

Т.е. `relayout` действительно ушёл на движковый поток (Задача 2, ADR-023,
дефолт с 2026-07-28) и стал вдвое короче (511мс против 1041.99мс в исходном
репро 2026-07-15, ещё до Задачи 1) — Задача 1 (кэш `active_media`/
`active_supports`) и Задача 2 (engine-thread по умолчанию) в сумме сократили
симптом с «многосекундный фриз всего окна» до **одного кадра ~580мс**,
после которого скролл снова держит 2-6мс без повторов на дальнейших 8000px
прокрутки (ria.ru использует `content-visibility:auto`, судя по логу, только
на одном/нескольких блоках у top-of-fold — остаток страницы не переоткрывает
дорогой пересчёт). Окно в этот момент не «не отвечает» на уровне ОС — это
одна отложенная кадровая пауза, не индефинит-хэнг.

**Вывод по Задаче 3:** протокол файла `p3-cascade-perf.md` прямо предписывал
не начинать архитектурную переделку (частичный пересчёт стилей поддерева)
без свежего замера — «профиль может показать, что после ускорения самого
`compute_style` частичный пересчёт вообще не нужен». Замер это подтверждает:
единичная пауза ~580мс на первом скролле тяжёлой страницы — не тот масштаб
проблемы, что оправдывает риск Задачи 3 (наивный частичный пересчёт может
дать неверный каскад на `:nth-child`/sibling-комбинаторах/`counter-reset`,
почему сам план называет её «самой рискованной» и советует делать только
если задача 1 не хватит). P3-скоуп на этом исчерпан: точечного бага нет,
дальнейшее — architectural trade-off (тратить P1-риск ради экономии
не-блокирующей паузы 500мс), решение по которому должен принимать
пользователь/P1, не P3. Классифицирую DEBTOR, KNOWN_DEBTOR-класса не
заводил (не graphic-test, а real-site perf).

## Ревизия P3 (2026-09-01)

Свежий живой замер тем же методом («Замер 2026-08-06») на ria.ru: маршрутизация
content-visibility по-прежнему верна, регрессии в её логике нет. Но замер
показал не одну паузу ~580мс, а **33** полных off-thread relayout'а
(850–2600мс каждый) за ~15–20с сессии при неизменном `dl`/`styled` — не
раскрытие content-visibility (то срабатывает один раз), а непрерывный
пересчёт, вызванный отдельным механизмом: активным `requestAnimationFrame`+
DOM-мутацией на странице (видеоплеер), для которого M4-инкрементальный путь
(`try_relayout_raf_incremental`) оказался мёртвым кодом на дефолтной сборке.
Заведён отдельно как [BUG-935](BUG-935-OPEN.md) — не тот же корень, что этот
баг (см. BUG-935 «Почему не тот же баг, что BUG-286»). Заодно поправлен
doc-комментарий `relayout_raf_dirty` (`relayout.rs`), описывавший порядок
вызовов неверно. BUG-286 остаётся DEBTOR в своём скоупе, дрейфа не найдено.

## Воспроизведение

Нужна реальная тяжёлая страница с `content-visibility:auto` под-fold
контентом и большим числом CSS-правил (например, `@media`-тяжёлый сайт вроде
ria.ru/lenta.ru — синтетические `samples/`/`graphic_tests/` страницы не
используют `content-visibility`, репродукции на них не будет):

```
cargo run --release -p lumen-shell -- https://ria.ru
# один тик колеса вниз после первого непустого кадра
LUMEN_FRAME_LOG=1 cargo run --release -p lumen-shell -- https://ria.ru
```
