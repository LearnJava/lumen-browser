# BUG-274 — wgpu-бэкенд: медленный cold-start / первый кадр ~18–24× femtovg (заявка про idle-CPU ОПРОВЕРГНУТА)

**Статус:** OPEN — **пере-скоуплен 2026-07-20 (P1)**: исходная заявка «idle CPU ~4× + скачок памяти
в простое» **опровергнута замером** (оба бэкенда в истинном простое жгут 0% CPU и не рисуют кадров —
event loop корректно паркуется, фикс BUG-271 действует и для wgpu-пути). Наблюдавшийся CPU/RSS был
собран во **время загрузки** страницы, а не в простое. Остаётся реальный дефект: **cold-start
wgpu — первый непустой кадр ~7–9.4 с против ~0.4 с у femtovg** (на этой же странице).
**Компонент:** paint (`WgpuBackend`/`Renderer`, `crates/engine/paint/src/backends/wgpu_backend.rs`,
`crates/engine/paint/src/renderer.rs`) / shell (streaming-пайплайн первого кадра, `crates/shell/src/main.rs`)
**Найден:** 2026-07-08, сравнительный замер `LUMEN_BACKEND=femtovg` vs `LUMEN_BACKEND=wgpu` по запросу пользователя («можно ли уже запустить браузер на wgpu и будет ли это быстрее»)

> **Историческая часть ниже (Симптом … Обновление 2026-07-13) сохранена как есть.** Корректная
> диагностика — в разделе «Диагностика 2026-07-20 (P1)» в конце файла.

## Симптом

На идентичной статичной странице (`graphic_tests/1000000-final.html`, 2002 DOM-узла, 1062
paint-команды) wgpu-бэкенд в простое ест заметно больше CPU, чем femtovg, и один раз резко
наращивает память вскоре после открытия окна — ещё до какого-либо взаимодействия.

## Данные (dev-release, `target/dev-release/lumen.exe`, один прогон на бэкенд)

### CPU в простое (10 с, страница статична, без ввода)

| Бэкенд | CPU-время за 10с | ≈% одного ядра |
|---|---|---|
| femtovg | 375 мс | 3.8% |
| wgpu | 1422 мс | 14.2% |

### CPU во время скролла (~4.2 с, 16×PageDown)

| Бэкенд | CPU-время |
|---|---|
| femtovg | 203 мс |
| wgpu | 62.5 мс |

(На скролле wgpu, наоборот, эффективнее — проблема именно в простое, не в самом рендере при движении.)

### Память — покадровые чек-поинты (PowerShell `Get-Process`, снято до/после каждого PageDown)

wgpu:
```
t=5s  (сразу после загрузки)      WorkingSet=763.6MB PrivateBytes=741.7MB
t=10s (idle settle, БЕЗ ввода)    WorkingSet=1034.9MB PrivateBytes=1015.7MB   ← скачок +274MB
после PGDN #1..#8, скролл назад   WorkingSet=1034.9MB PrivateBytes=1015.7MB   ← дальше плоско
```

femtovg (тот же протокол):
```
t=5s   WorkingSet=759.4MB PrivateBytes=562.2MB
t=10s  WorkingSet=759.4MB PrivateBytes=562.1MB   ← без изменений
после PGDN #1..#8, скролл назад   PrivateBytes=562.1MB   ← плоско всё время
```

`GPU Process Memory\Local Usage` (Get-Counter, снято после idle-окна): femtovg 559.1MB, wgpu 709.3MB.

## Важное уточнение (снимает гипотезу утечки)

Рост памяти wgpu происходит **разово, между t=5с и t=10с, до первого PageDown** — то есть не
связан со скроллом и не прогрессирует дальше при взаимодействии (8 шагов вперёд + 8 назад —
без изменений). Это не утечка, а единовременная стоимость чего-то, что происходит в первые
секунды после появления окна.

## Гипотезы (не проверены — нужен профиль)

1. **Idle CPU (4×).** У wgpu-пути, вероятно, нет аналога фикса BUG-271 (протухший
   `WaitUntil` / безусловный rAF-пинг `request_redraw`) — либо тот фикс общий для обоих
   бэкендов на уровне шелла, и источник горения именно в `WgpuBackend::render()`/его
   presentation-цикле (например, лишний re-submit кадра или poll GPU-адаптера каждую
   итерацию event loop).
2. **Разовый скачок памяти (+274 МБ WS / +450 МБ private суммарно от старта).** Похоже на
   отложенную инициализацию: компиляция шейдеров/pipeline-кэш wgpu, преаллокация GPU-буферов
   или атласа текстур, случающаяся не в момент создания бэкенда, а чуть позже (первые кадры
   после появления окна).

## Что НЕ проверено (следующие шаги для того, кто возьмёт баг)

- Есть ли у `WgpuBackend` поддержка `LUMEN_FRAME_LOG` (см. BUG-273) — если нет, добавить,
  чтобы разбить idle-CPU по типам работы за кадр.
- Профиль на других страницах (JS-тяжёлых, с анимациями) — на одностраничном статике эффект
  может отличаться от реальных сайтов.
- Влияние профиля сборки (`dev-release` без LTO vs `release`) на абсолютные цифры —
  относительное сравнение (4× CPU, +450MB) должно быть профиль-независимым, но не проверено.
- Не разделено, один это дефект или два разных (idle-CPU и memory-spike могут иметь разные
  причины) — объединены в один тикет, т.к. найдены в одном прогоне.

## Как воспроизвести

```powershell
$env:LUMEN_BACKEND="femtovg"; $env:LUMEN_MEM_REPORT="1"
target\dev-release\lumen.exe graphic_tests\1000000-final.html

$env:LUMEN_BACKEND="wgpu"; $env:LUMEN_MEM_REPORT="1"
target\dev-release\lumen.exe graphic_tests\1000000-final.html
```

Снять `Get-Process -Id <pid> | Select TotalProcessorTime,WorkingSet64,PrivateMemorySize64` до и
после 10-секундного простоя (без фокуса/ввода) — сравнить дельту CPU-времени и память на
чек-поинтах t=5s / t=10s.

## Контекст

Найдено не как таргетированный баг-хант, а как побочный результат исследования «стоит ли
переводить live-рендер шелла на wgpu вместо femtovg» — см. `docs/decisions/ADR-010`
(миграционный путь бэкендов) и `subsystems/paint.md`. До закрытия этого бага wgpu как
дефолтный live-путь брать не стоит — простой на статичной странице должен стоить ~0 CPU
(инвариант, закреплённый BUG-271), а на wgpu он нарушен.

## Обновление 2026-07-13 — P1-wgpu-vkgl: замер с новыми фичами

До этого коммита wgpu на Windows собирался только с фичей `dx12`; `backend_probe` (Vulkan→GL→DX12)
всегда откатывался на DX12 — кандидаты Vulkan и GL были недоступны на уровне wgpu-runtime.
С P1-wgpu-vkgl Windows-сборка включает `["dx12", "vulkan", "gles", "wgsl", "std"]`.

### Результаты probe на Intel Iris Plus (2026-07-13)

```
[probe] Vulkan: present=WHITE texture=ok  adapter="Intel(R) Iris(R) Plus Graphics" — отклонён
[probe] GL:     present=WHITE texture=n/a adapter="Intel(R) Iris(R) Plus Graphics" — отклонён
[probe] DX12:   present=ok    texture=ok  adapter="Intel(R) Iris(R) Plus Graphics" — ПРИНЯТ
[probe] бэкенд выбран за 2127 мс: DX12
```

Выводы:
- **Vulkan** — BUG-275 подтверждён (`present=WHITE`, DWM-заголовок исправен).
- **GL (GLES через wgpu/WGSL)** — тоже `present=WHITE`; это wgpu-over-GLES, не femtovg-over-GL —
  драйвер Intel Iris Plus не презентует wgpu-GLES-swapchain через DWM. `texture=n/a` означает
  отсутствие COPY_SRC у GLES-поверхности.
- **DX12** — единственный рабочий путь на этой машине.

Данные из exp-ветки о "wgpu-GL как лучшем" применимы к другой машине или другой конфигурации
GLES-бэкенда — на Intel Iris Plus он также white-screens.

### Замер idle CPU (dev-release, график. 1000000-final.html, t=5..15 с)

| Бэкенд | Дельта CPU за 10 с | % одного ядра | Примечание |
|---|---|---|---|
| femtovg (new) | ~219 мс | ~2.2% | базовая линия |
| wgpu/DX12 probe (new, Phase 2) | ~2391 мс | ~23.9% | probe 2.1 с overhead; blit per-frame |
| wgpu/DX12 (original BUG-274, pre-Phase2) | ~1422 мс | ~14.2% | |

Wgpu DX12 ухудшился vs исходного замера (~24% vs 14%). Гипотеза: scroll-compositor (Phase 2,
M3 blit path) делает GPU-blit каждый кадр даже в idle (`[frame] delta Identical` → `[frame] band blit`),
тогда как skip-identical-frame только предотвращает полный repaint, но не сам blit. Фикс = добавить
skip-blit когда `delta Identical` и нет dirty-regions (отдельная подзадача).

## Диагностика 2026-07-20 (P1) — заявка про idle-CPU опровергнута, реальный дефект = cold-start

Повторный контролируемый замер (dev-release `target/dev-release/lumen.exe`, DX12 probe→DX12,
Intel Iris Plus, `LUMEN_FRAME_LOG=2`). **Ключевая ошибка исходного протокола:** окно замера t=5..15 с
на этой странице **попадает в фазу загрузки**, а не в простой — на wgpu первый непустой кадр
наступает только на ~7–9.4 с (см. ниже), т.е. весь ранний CPU/RSS — это стоимость загрузки и
первых (очень дорогих) кадров, а не простоя.

### Истинный простой (замер после полного оседания страницы, t=16 с → t=26 с)

| Бэкенд | CPU t16 | CPU t26 | ΔCPU за 10 с простоя | кадров в окне простоя | WS t16→t26 |
|---|---|---|---|---|---|
| wgpu/DX12 | 4125 мс | 4125 мс | **0 мс (0%)** | **0** | 678.7→678.7 МБ (плоско) |
| femtovg | 1891 мс | 1891 мс | **0 мс (0%)** | **0** | 587.9→587.9 МБ (плоско) |

**Оба бэкенда в истинном простое жгут ноль CPU и не выпускают кадров** — `about_to_wait` уводит
event loop в `ControlFlow::Wait` (фикс BUG-271, общий для обоих путей, т.к. шелл рендерит через
`Box<dyn RenderBackend>` и не ветвится по типу бэкенда). Никакого фонового GPU-poll-потока,
жгущего CPU, нет (`TotalProcessorTime` учитывает все потоки процесса — дельта 0).

Вывод: **регрессии idle-CPU не существует.** «4×/14×/24%» из исходной и Phase-2 таблиц — это
CPU, накопленный за долгую загрузку wgpu (probe + очень дорогие первые кадры), поделённый на
10-секундное окно, которое ошибочно считалось «простоем».

### «Скачок памяти +274/+450 МБ» — одноразовая стоимость старта, а не простоя

Рост WorkingSet между t=5 и t=10 в исходном замере пришёлся на окно **до** первого кадра wgpu
(первый кадр ~7–9.4 с). Это одноразовая аллокация wgpu на старте (pipeline/шейдеры, атлас текстур,
GPU-буферы), полностью согласуется с собственной пометкой бага «не утечка, разовая стоимость
инициализации». В истинном простое (t16→t26) WS плоский.

### Реальный дефект: cold-start / латентность первого кадра ~18–24× femtovg

`[bench] first non-empty frame` на идентичной `1000000-final.html`:

| Бэкенд | Первый непустой кадр | Probe |
|---|---|---|
| femtovg | **399 мс** | — |
| wgpu/DX12 | **7075–9448 мс** | 1679 мс (Vulkan 718 + GL 524 + DX12 435) |

Разбор wgpu-таймлайна:
- **Probe ~1.7 с** — одноразовый перебор Vulkan→GL→DX12 (первые два `present=WHITE`, отклоняются).
- **~5.3 с между концом probe и первым кадром.** Femtovg на том же streaming-пайплайне рисует
  инкрементальные кадры уже на 399 мс; wgpu первый непустой кадр даёт лишь после
  `Streaming завершён, финальный pipeline (off-thread)` — т.е. wgpu-путь **не рисует ранние
  streaming-кадры**, которые femtovg рисует.
- **Сами первые кадры очень дороги** (`LUMEN_FRAME_LOG`): `[frame:wgpu] total` 100–210 мс,
  доминирует `encode` (75–96 мс) + `bdrop`/`mask`/`filt` (backdrop-filter/маски/фильтры) — часть
  этого пересекается с BUG-273 (перф фильтр-слоёв).

### Замечание про skip-identical и «band blit каждый кадр» (гипотеза Phase-2)

Гипотеза «scroll-compositor блитит каждый кадр даже в idle» **не подтвердилась**: в истинном
простое кадров нет вообще, а на загрузке 0 из кадров идут по skip-identical-пути
(`[frame:wgpu] page-compose unstable-key: gen N`) — `content_generation` инкрементится на каждую
пришедшую картинку, поэтому хэш кадра меняется и skip-identical (правильно) не срабатывает во
время загрузки. Это ожидаемо для прогрессивной загрузки, а не дефект блита. Строки `[frame] band
blit` / `[frame] delta Identical` — это **измерительная** классификация в шелле (только под
`LUMEN_FRAME_LOG`), она не выполняет GPU-блит.

### Что остаётся сделать (следующему, кто возьмёт баг)

- **Рисовать ранние streaming-кадры на wgpu-пути** так же, как femtovg (это главный вклад в
  разрыв 0.4 с vs 7 с). Найти, почему первый непустой wgpu-кадр откладывается до конца streaming.
- Снизить стоимость первого кадра: pipeline/шейдеры компилируются лениво на первом draw
  (`encode` 75–96 мс); прогреть кэш пайплайнов заранее.
- ~~Probe 1.7 с — кэшировать выбранный API между запусками~~ — **сделано срезом 2026-07-24 (P3)**,
  см. ниже.
- Пересечение с BUG-273 (перф backdrop/mask/filter-слоёв) — часть `encode` там же.

Idle-CPU и memory-spike-in-idle из заголовка **закрыты как не-баг** (артефакт протокола замера).

## Срез 2026-07-24 (P3) — кэш результата пробы бэкенда

Закрывает один из четырёх пунктов «что остаётся сделать» — саму пробу (Vulkan→GL→DX12, до ~1.7 с
на этой машине, где первые два всегда `White` и отклоняются), не общий разрыв cold-start (тот
остаётся открытым, см. два первых пункта выше — streaming-кадры и warm pipeline-кэш).

**Фикс:** `crates/engine/paint/src/backend_probe.rs` — кандидат, принятый прошлой пробой,
персистится в `<exe_dir>/data/paint/backend_probe.txt` (`write_cached_backend`, best-effort,
портативное хранилище — тот же принцип, что `shell::adblock::browser_data_dir`, но без
зависимости paint→shell, свой маленький резолвер `<exe_dir>/data`). При следующем запуске
`pick_backend` переставляет закэшированного кандидата в начало очереди пробы
(`reorder_by_cache`) — на типичной машине (то же GPU/драйвер) проба идёт по одному кандидату
вместо трёх (~1.7 с → ~0.4–0.5 с для DX12-случая с этой машины). Кэш не влияет на корректность:
кандидат всё равно проходит полную валидацию (readback + `PrintWindow`-захват через DWM) — если
GPU/драйвер сменился и закэшированный кандидат теперь отклонён, проба прозрачно скатывается на
оставшиеся два в исходном порядке (self-healing). 6 юнит-тестов (`reorder_by_cache_*`,
`cache_roundtrip_writes_and_reads_back`) — только под фичей `backend-wgpu` (не default-фича
crate'а `lumen-paint`, `cargo test -p lumen-paint --features backend-wgpu`).

## Срез 2026-07-28 (P3) — видео-репродукция, точная цифра по стадиям, проверенная (и отвергнутая) архитектурная гипотеза

**Живая репродукция.** Записан gdigrab-скрин старта на `graphic_tests/1000000-final.html`
(dev-release, живая сборка после мержа CC-14): заголовок окна становится
«Lumen 0.5.0 (Не отвечает)» буквально через ~2 с после запуска, окно залито сплошной синей
заливкой (DWM-плейсхолдер для зависшего окна) — держится ~9 с, `[bench] first non-empty
frame: 9889ms`. Подтверждает исходную заявку бага буквально, не только по цифрам.

**Точная разбивка по стадиям** (новая инструментация — два `eprintln!` под
`frame_log_enabled()` в `crates/engine/paint/src/renderer.rs::new_async`, окружают
adapter/device request и `init_pipelines` отдельно от уже существующего лога пробы):

| Бэкенд | probe | adapter+device | init_pipelines (16 pipeline'ов) | first non-empty frame |
|---|---|---|---|---|
| Vulkan (принят пробой) | ~1000-1200 мс | ~270-410 мс | ~260-400 мс | ~2-6.7 с (сайт-зависимо) |
| DX12 (`WGPU_BACKEND=dx12`, без пробы) | - | ~270-470 мс | ~3000-7000 мс | ~3.6-8.6 с |

Узкое место — компиляция 16 пайплайнов (`Renderer::init_pipelines`) именно на DX12, не сама
проба (уже закрыта срезом выше) и не GPU-адаптер/девайс (одинаково быстро на обоих API). DX12
(via naga→HLSL→FXC/DXC) в 10-20x медленнее Vulkan (SPIR-V) на ОДНОМ И ТОМ ЖЕ железе (Intel Iris
Plus) для одних и тех же шейдеров. Число нестабильно между запусками (3.0-7.0 с) — похоже на
переменный вклад драйверного on-disk PSO-кэша (Intel), не изученный детально в этом срезе.

**Проверенная и отвергнутая архитектурная гипотеза: вынести создание wgpu-бэкенда (проба +
adapter + device + surface + pipelines) на фоновый поток**, чтобы winit не блокировал pump
оконных сообщений во время прогрева GPU (главная теория, почему Windows помечает окно
«не отвечает» — весь `resumed()` выполняется синхронно на потоке, обслуживающем message loop).
Реализовано (новый `LoadEvent::RendererReady`/`RendererWgpuFailed`/`RendererInitFailed`,
`backend_factory::create_wgpu_only`/`create_femtovg_only`, `resumed()` спавнит поток вместо
синхронного вызова) и эмпирически проверено на живом запуске — результат отрицательный:
`instance.create_surface(window)` (внутри `Renderer::new_async`, до adapter request) молча
проваливается для ВСЕХ трёх кандидатов (DX12/Vulkan/GL) при вызове с фонового потока —
«no GPU adapter under any candidate backend» вместо реального DX12-успеха, который тот же
код даёт на главном потоке. Вывод: на этом стеке Windows/winit surface/adapter-negotiation
жёстко привязана к потоку, создавшему окно — аналогично уже задокументированному
femtovg/GL-ограничению (`backend_factory::create_threaded_femtovg`'s doc, «window handle
доступен только на главном потоке»), но теперь подтверждено и для wgpu-пути, где раньше
предполагалось обратное (wgpu — Send, в отличие от GL-контекста). Изменение полностью
отменено (`git checkout` на main.rs/backend_factory.rs) — оставлена только инструментация
таймингов в renderer.rs (безопасна, гейтится `LUMEN_FRAME_LOG`, поведение не меняет).

**Правильное направление для следующего среза (не сделано в этом):** раз adapter/surface
должны остаться на главном потоке, а `init_pipelines` не трогает surface/window (только
`device`/`queue`/`format`/`font_bytes`) — можно вынести на фон именно и только компиляцию
пайплайнов, реконструировав `Renderer` из (surface+device+queue, оставшихся на главном потоке)
+ (скомпилированные pipeline'ы, пришедшие с фона). Альтернатива без threading вообще: ленивая
компиляция редко используемых пайплайнов (blur/backdrop/mask*/filter/blend/composite/
cross_fade/mipgen — ~11 из 16) по первому реальному использованию вместо eager при старте;
common-case страницы (fill/rrect/text/image/gradient — ~5 из 16) прогреваются быстро, тяжёлые
эффекты платят cold-start в момент первого появления на экране, а не все разом при запуске. Ни
то ни другое не реализовано — оценка рисков и итоговый выбор архитектуры за тем, кто продолжит.

**Побочная находка на реальном сайте (lenta.ru, по запросу пользователя по ходу того же среза):
узкое место cold-start на реальных сайтах — не бэкенд, а серия синхронных relayout'ов на
каждый догруженный `@font-face`.** Замер `LUMEN_FRAME_LOG=1` на `https://lenta.ru` (9
кастомных web-шрифтов):

| Конфигурация | first non-empty frame |
|---|---|
| Vulkan (дефолт, без флагов) | ~6.7 с |
| DX12 (`WGPU_BACKEND=dx12`) | ~8.6 с |
| femtovg (`LUMEN_BACKEND=femtovg`, нет GPU pipeline cold-start вообще) | ~7.0 с |
| Vulkan + `LUMEN_ENGINE_THREAD=1` | ~3.6 с |

femtovg (без единого GPU-пайплайна) была НЕ БЫСТРЕЕ Vulkan — то есть на этой странице backend
choice не главный фактор. Лог показывает 6-9 relayout'ов по ~300-700 мс каждый, идущих подряд
ДО первого кадра (`LoadEvent::FontLoaded` → `relayout_chrome()` → синхронный полный relayout
~1800-узлового display list на каждый пришедший файл шрифта, сериализуется на UI-потоке т.к.
`LUMEN_ENGINE_THREAD` дефолт off, ADR-016). С `LUMEN_ENGINE_THREAD=1` (весь ADR-016 M0-M4.1
ЗАКРЫТ 2026-07-15, флаг документирован как «байт-идентичен при off» на каждом срезе)
относительный вклад пропал из синхронного пути — first-frame упал почти вдвое. Это отдельный
от cold-start-пробы механизм зависания (тот же класс, что BUG-284's relayout storms, но триггер
— `@font-face`, не начальный DOM) и не заведён отдельным номером — решение о разделении/переносе
за пользователем. `LUMEN_ENGINE_THREAD` — кандидат на default-flip (по образцу ADR-017/CC-14),
но это отдельное, более крупное решение вне скоупа BUG-274, требующее полного гейта
(graphic_tests + scroll-перф регрессия) — не сделано в этом срезе.

**Апдейт 2026-07-28 (тот же день, ветка `p3-engine-thread-default`):** флип сделан по решению
пользователя — [ADR-023](../docs/decisions/ADR-023-engine-thread-default.md), движковый поток
включён по умолчанию, откат `LUMEN_NO_ENGINE_THREAD=1`. Приёмка по счётчику (не по wall-clock,
`docs/perf-method.md`): синхронных relayout до первого кадра на lenta.ru **9 → 1–3**. Сам
BUG-274 этим НЕ закрывается: cold-start пайплайнов DX12 (3–7 с в `init_pipelines`) — независимый
остаток, ленивая/фоновая компиляция пайплайнов по-прежнему не сделана. Прокрутка тоже не
чинится флипом — заведён отдельный [BUG-405](BUG-405-OPEN.md).
