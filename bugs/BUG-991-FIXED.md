# BUG-991 — `health.log` перезаписывался каждым запуском процесса: журнал предыдущих сессий терялся

**Статус:** FIXED 2026-09-05
**Заведён:** 2026-09-04 (наблюдение за живым прогоном корпуса)
**Область:** `crates/shell/src/health_log.rs` (открытие файла журнала)
**Владелец:** P3

## Симптом

Журнал здоровья сессии (PERF-6) пишется в `health.log` в рабочем каталоге и
открывается на **перезапись**, а не на дозапись. Каждый новый процесс `lumen.exe`
стирает журнал предыдущего.

## Что говорит измерение

Прогон 100 сайтов 2026-09-04 перезапускал окно **девять раз**. По завершении в
`health.log` осталась ровно одна запись `session_start` и диапазон времени
12:45:27–13:27:26 UTC = 15:45:27–16:27:26 локального — это в точности последний
процесс (PID 18600, старт 15:45:27, наблюдался сэмплером).

Итог: из 100 сайтов журнал покрывает примерно 60. Данные первых сорока стёрты
восемью перезаписями.

## Почему это дорого

На этом файле строятся выводы о прогоне. В отчёте по прогону 2026-09-04 число
«8 белых экранов» получено именно отсюда — и это **нижняя граница по неполной
выборке**, а не число по корпусу. Пока файл перезаписывается, любой агрегат по
`health.log` из многосессионного прогона занижен на неизвестную величину и
выглядит при этом как полный.

## Что нужно

Открывать журнал на дозапись, либо давать имя с меткой процесса
(`health.<pid>.log`), либо и то и другое. `scripts/health_report.py` должен
уметь собрать серию файлов одного прогона.

Смежное: гоняющий скрипт мог бы копировать журнал перед убийством окна — но это
обход, а не исправление, и он не спасёт того, кто запускает браузер руками.

## Сырые данные

`health.log` в корне репозитория на момент 2026-09-04 16:27,
`.tmp/observe/OBSERVATION-2026-09-04.md`.

## Фикс (2026-09-05, P3)

Сделано и то, и другое, как предлагала карточка бага:

- `crates/shell/src/health_log.rs`: журнал теперь именуется по pid процесса
  (`log_path()` → `health.<pid>.log`, вычисляется один раз через `OnceLock`) и
  открывается через `OpenOptions::append(true)` вместо `truncate(true)` — как
  в `init()` (создание файла + запись `session_start`), так и в `append()`
  (каждая последующая запись). Один процесс никогда не трогает файл другого,
  поэтому многосессионный прогон, перезапустивший окно N раз, оставляет N
  файлов серии вместо одного, содержащего только последний процесс.
  `session_start` дополнительно несёт поле `pid` для агрегатора.
- `scripts/health_report.py`: новая `discover_logs(pattern)` — без явного
  аргумента находит и упорядочивает по mtime всю серию `health.*.log` (плюс
  устаревшее одиночное `health.log`, если такое ещё лежит) в рабочем
  каталоге; явный аргумент — путь к одному файлу или glob-маска. `main()`
  склеивает найденные файлы в один поток перед разбором. Покрыто
  `_selftest_discover_logs()` внутри `--selftest`.
- `scripts/perf_audit.py`: `LiveBrowser._spawn()` считает `health_log_path`
  из pid только что запущенного дочернего процесса (`self.proc.pid`) вместо
  единого фиксированного `health.log` — отслеживание новых событий с позиции
  `health_log_pos` (уже сбрасывалась в 0 при каждом `_spawn()`) теперь
  указывает на верный файл после рестарта, а не на файл предыдущего процесса.

Регресс-тест `log_path_is_stamped_with_this_process_id`
(`crates/shell/src/health_log.rs`) фиксирует, что путь стабилен в пределах
процесса и содержит его pid. Живая проверка: два последовательных запуска
`lumen.exe --health-log --dump-source about:blank` дали два файла
`health.<pid1>.log`/`health.<pid2>.log`, оба с непустой записью
`session_start`, ни один не был затёрт другим.

5/5, `cargo clippy -p lumen-shell --all-targets -- -D warnings` чисто,
`python scripts/health_report.py --selftest` OK.
