# BUG-442 — на V8 отсутствующий атрибут читается как `null`, а весь шим сравнивает с `undefined`: `hasAttribute()` всегда `true`, `<details>/<dialog>.open` всегда `true`, `input.checked` всегда `true`, Popover API работает по инвертированному состоянию

**Статус:** OPEN
**Компонент:** js (`crates/js/src/v8_runtime.rs:1306` — натив `_lumen_get_attr`
возвращает `Option<String>`, и биндинги V8 отображают `None → null`; шим
`crates/js/src/dom.rs` в 15 местах проверяет наличие атрибута выражением
`_lumen_get_attr(...) !== undefined`, написанным под rquickjs, где `None →
undefined` — это расхождение прямо задокументировано в шапке `WEB_API_SHIM`,
`dom.rs:3295`)
**Найден:** P1, BUG-381 (2026-07-29), юнит-проба на `V8JsRuntime::install_dom`

## Симптом

Проба на дефолтном движке (V8), документ `body > input#field` с единственным
атрибутом `id`:

```
_lumen_get_attr(field, 'inert')   = null        ← rquickjs здесь даёт undefined
el.hasAttribute('data-nope')      = true        ← атрибута нет
_lumen_get_attr_names(field)      = ["id"]      ← нативный список верен
```

То есть нативы читают DOM правильно, ломается только проверка «атрибут
присутствует»: `null !== undefined` истинно всегда.

## Причина

`WEB_API_SHIM` писался под rquickjs, где `Option<T>` отображается в
`undefined` (это отмечено в его же doc-комментарии). Поэтому шим завёл два
разных стиля чтения атрибута:

* значение — через `_lumen_u2n(_lumen_get_attr(...))`, нормализующий и
  `undefined`, и `null` в `null` → **работает на обоих движках**;
* присутствие — голым `_lumen_get_attr(...) !== undefined` → **на V8 всегда
  истинно**.

Биндинги V8 (`v8_runtime.rs`) отображают `None` в `null`, а не в `undefined`,
и второй стиль на них разваливается молча — исключения нет, есть неверный
булев ответ.

## Влияние

Пятнадцать мест в `dom.rs`, все на дефолтном движке:

| Место | Что ломается |
|---|---|
| `dom.rs:5613` `toggleAttribute` | ветка «атрибут есть» выбирается всегда → `toggleAttribute('x')` снимает атрибут, которого нет, и возвращает `false` |
| `dom.rs:5627` `get open()` | у **любого** `<details>`/`<dialog>` `el.open === true` |
| `dom.rs:5651` `close()` | ранний `return` не срабатывает никогда |
| `dom.rs:6199` `get checked()` | у **любого** чекбокса/радио `el.checked === true` |
| `dom.rs:13457`, `13481`, `13504` | обработка `toggle` у `<details>`, схлопывание `<details name>`-групп, стек модальных `<dialog>` |
| `dom.rs:13540`–`13622` | весь Popover API: `showPopover` считает открытым всё, `hidePopover` — тоже, light-dismiss отрабатывает по инвертированному состоянию |
| `hasAttribute` / `hasAttributeNS` (через ту же ветку) | `true` для любого имени |
| `_lumen_find_autofocus_in` (`dom.rs:13160`) | возвращал первого потомка контейнера вместо `[autofocus]` → `<dialog>.showModal()` фокусировал не тот узел. **Уже исправлено** в рамках BUG-381 |

Отдельно это ставит под сомнение всякий вывод вида «фича X работает», сделанный
по юнит-тестам `dom::tests` — они гоняются на `QuickJsRuntime`, где ветка
`!== undefined` верна, поэтому весь класс дефекта тестами не виден: зелёный
тест на rquickjs маскирует сломанную фичу на V8.

## Как чинить

Правильное место — граница биндингов, а не 15 мест шима: отдавать из
`_lumen_get_attr` (V8) `undefined` для отсутствующего атрибута, как это делает
rquickjs. Тогда оба стиля чтения снова сойдутся, а `_lumen_u2n`-обёртки
продолжат работать без изменений (они нормализуют `undefined → null`).

Порядок работы:

1. Проверить, как `reg!` в `v8_runtime.rs` конвертирует `Option<T>`, и решить,
   менять ли конверсию точечно для `_lumen_get_attr` или для всех нативов
   (второе шире и требует пересмотра тех мест, где шим сравнивает результат
   натива с `null` напрямую — их надо выписать грепом до правки).
2. Прогнать «присутствие атрибута» тестами **на V8**, не только на QuickJS:
   `hasAttribute` отсутствующего имени, `toggleAttribute` без `force`,
   `<details>.open` у закрытого элемента, `input.checked` у неотмеченного,
   `showPopover`/`hidePopover`.
3. Заодно перевести оставшиеся `!== undefined` в `dom.rs` на общий помощник
   `_lumen_has_attr` (добавлен в BUG-381, `dom.rs:3303`) — он engine-agnostic и
   не даст рецидива, если конверсию когда-нибудь поменяют обратно.
