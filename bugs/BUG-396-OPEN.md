# BUG-396 — GIF-декодер отклоняет спек-валидный кадр без предшествующего Graphic Control Extension («invalid code in LZW stream»)

**Статус:** OPEN
**Компонент:** image (`crates/engine/image/src/gif.rs:339-393` —
`decode_gif_animated`, зависимость `gif` крейт v0.14.2, `Cargo.lock`)
**Найден:** P2, WPT-VENDOR-gif (2026-07-28), прямая проба на реальном
вендоренном GIF-файле (`tests/wpt/gif/reset-no-gce.gif`) — категория сама
по себе не прогоняется (единственный тест `reftest`, неподдерживаемый тип
для минимального экзекьютора), проба через `cargo test`/`include_bytes!`
подставлена вместо `run_report.py`

## Симптом

`tests/wpt/gif/reset-no-gce.gif` — 3-кадровый GIF (2×2, non-looping,
глобальная палитра из 4 цветов: 0=чёрный, 1=красный, 2=зелёный, 3=синий).
Кадр 0 несёт GCE с disposal=2 ("restore to background") и
`transparent_index=0` (чёрный — эффекта нет, кадр полностью красный).
Кадр 1 несёт GCE с disposal=2 и `transparent_index=2` (зелёный — весь
кадр становится прозрачным). Кадр 2 **не имеет предшествующего GCE
вовсе** — именно это и тестирует upstream (комментарий в
`reset-no-gce-1.html`): "The third frame is all green, there is no gce
preceeding it, so there is no transparent index."

`decode_gif_animated` (metadata-проход, читает каждый кадр через
`reader.next_frame_info()`/`reader.read_into_buffer()`) успешно
декодирует кадр 0 (`[255,0,0,255]` ×4, корректно), но падает на кадре 1:

```
next_frame_info ERROR at idx 1: invalid code in LZW stream
```

Ошибка воспроизводится и с `ColorOutput::RGBA` (боевой режим Lumen), и
с дефолтным индексированным выводом — не связана с RGBA-компоузингом.

## Независимая проверка: файл валиден

Тот же файл, открытый Pillow (`PIL.Image`, независимый декодер) из
`tests/wpt/.venv`, декодируется без ошибок и даёт ровно ожидаемый
upstream-комментарием результат:

```
n_frames 3
0 disposal 2 transparency 0    [(255,0,0,255)]×4   — красный, непрозрачный
1 disposal 2 transparency None [(0,0,0,0)]×4        — полностью прозрачный (transparent_index=2 совпал с заливкой)
2 disposal 2 transparency None [(0,255,0,255)]×4    — зелёный, непрозрачный (нет GCE ⇒ нет transparent_index)
```

Файл байт-в-байт идентичен апстримному (сверено `xxd`-диффом после
`git sparse-checkout`) — повреждения при вендоринге нет. Значит дефект
не в тестовых данных, а в декодере, которым пользуется Lumen.

## Причина (предварительно)

Не в собственном коде Lumen — `decode_gif_animated`/`AnimatedGif`
(`gif.rs`) лишь вызывают публичный API крейта `gif` v0.14.2
(`DecodeOptions::read_info` → `next_frame_info`/`read_into_buffer`) в
задокументированном для этого крейта порядке; ошибка `invalid code in
LZW stream` возникает внутри самого крейта при попытке разобрать/
пропустить кадр 1. Похоже на баг LZW-декодера крейта `gif` при переходе
между кадрами с разными GCE-конфигурациями (кадр 0 → кадр 1 с другим
`transparent_index`) либо при отсутствии GCE у последующего кадра —
сценарий, который стандартные тестовые наборы (не WPT) редко покрывают.
Не диагностировано глубже (вне скоупа P2/вендоринга — фикс/апгрейд
зависимости принадлежит P1/P3).

## Как чинить

1. Минимальное воспроизведение уже выделено (см. проба выше, 3-байтовые
   LZW-данные кадра 1/2 — `94 a5 00`, `min_code_size=2`) — можно
   репортить апстриму `image-rs/gif` или искать существующий issue по
   тексту ошибки.
2. Проверить, чинит ли обновление версии крейта `gif` (текущий пин —
   `0.14.2`, `Cargo.lock`) — если да, поднять версию отдельной задачей
   с проверкой регрессий на остальных декодируемых GIF (существующие
   unit-тесты `gif.rs` + `graphic_tests`, если там есть анимированные
   GIF).
3. Если апстрим не чинит — рассмотреть fallback-декодер или
   pre-обработку (нормализация GCE перед каждым кадром) в
   `decode_gif_animated`.

Регрессия без WPT: `decode_gif_animated` на
`tests/wpt/gif/reset-no-gce.gif` должен вернуть 3 кадра с пикселями
`[красный]×4`, `[прозрачный]×4`, `[зелёный]×4` — сейчас падает
`DecodeError` на втором кадре.

## Связанные

* Категория `gif` — скоуп ⬜ (кандидат), единственный тест —
  reftest-пара (`reset-no-gce-1.html`/`reset-no-gce-ref.html`),
  неподдерживаемый тип для минимального `wptrunner`-экзекьютора
  (тот же класс гэпа, что `apng`/`acid`/`animation-worklet`/
  `accessibility`'s crashtests) — прогон дал бы `Unsupported test type
  reftest`, 0/0, без сигнала; находка получена прямой пробой декодера
  на реальном вендоренном файле вместо прогона, тот же приём, что
  `eyedropper`/`geolocation` (см. `tests/wpt/VENDOR.md`).
* Не связан с BUG-272 (Canvas 2D `arc`) или другими image-находками —
  первый вендоринг-баг конкретно в GIF-декодере.
