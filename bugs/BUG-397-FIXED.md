# BUG-397 — Global Privacy Control (GPC) полностью не реализован: ни `navigator.globalPrivacyControl`, ни `Sec-GPC`

**Статус:** FIXED 2026-08-11 (P3)
**Компонент:** js (`crates/js/src/surface_api.rs` — рядом с `navigator.doNotTrack`,
строки 116-121) + network (`crates/network/src/http/headers.rs::build_request_headers`,
все 7 `HttpProfile`)
**Найден:** P2, WPT-VENDOR-gpc (2026-07-28), прогон дал 0 сигнала —
находка получена прямым грепом по `crates/`, не прогоном

## Симптом

Категория `gpc` (`tests/wpt/gpc/`, 4 исполняемых файла) целиком
недостижима этим wptrunner-исполнителем: 3 файла используют кастомные
testdriver-методы `test_driver.get_global_privacy_control()`/
`set_global_privacy_control()` → `SKIP (Executor does not support
testdriver.js)`; `idlharness.any.js` падает на невендоренных
`/resources/WebIDLParser.js`+`idlharness.js` (404) → `TIMEOUT`. Прогон
сам по себе не даёт находки (тот же класс, что многие категории этого
backlog-а).

По правилу «пробуй даже без сигнала» — грепом по `crates/`:

```
grep -rli "globalPrivacyControl\|Sec-GPC\|sec_gpc" crates/ --include="*.rs"
```

— **ноль совпадений**. Ни `navigator.globalPrivacyControl` (JS-свойство,
Boolean, спека https://www.w3.org/TR/gpc/), ни HTTP-заголовок `Sec-GPC: 1`
не реализованы вовсе — ни в JS-шиме, ни в исходящих HTTP-запросах.

## Почему это находка, а не просто "вне скоупа"

Соседний, юридически более слабый сигнал `navigator.doNotTrack`
**реализован** (`surface_api.rs:116-121`, намеренно `null` —
Chrome-совместимое поведение). Заголовок `DNT: 1` **отправляется**
по умолчанию в HTTP-профиле Chrome/Edge (`headers.rs:143`,
`headers.rs:193` через тот же блок). GPC — юридически обязывающий
сигнал (California CCPA/CPRA, Colorado Privacy Act, Connecticut
Data Privacy Act прямо признают `Sec-GPC: 1` как валидный универсальный
opt-out-запрос), а Lumen позиционируется как «private, lightweight,
transparent browser» (`CLAUDE.md` — «What is this»), уже имеет
per-profile HTTP-фингерпринт-инфраструктуру (ADR-007,
`crates/network/src/http/headers.rs`) и отдельный `HttpProfile::Strict`
для privacy-режима — естественное место для сигнала уже существует и
используется для менее значимого DNT, но не для GPC.

Реальные браузеры расходятся: Chrome/Edge/Safari не поддерживают GPC
нативно (поэтому его отсутствие в `HttpProfile::Chrome`/`Edge`/`Safari`
— корректная имитация), но Firefox с расширениями, Brave и DuckDuckGo
Browser его отправляют, и в `HttpProfile::Lumen` (собственный
незамаскированный фингерпринт Lumen, `headers.rs:233-246`) и/или
`HttpProfile::Strict` (усиленный anti-fingerprint профиль,
`headers.rs:126` — общий блок с Chrome) отсутствие GPC — не имитация
чужого браузера, а неиспользованная возможность собственного
privacy-заявления.

## Что нужно сделать

1. `navigator.globalPrivacyControl` — read-only Boolean на
   `Navigator`/`WorkerNavigator` (спека: `true`, если пользователь
   включил сигнал; в реальных браузерах это либо статический `true`
   при поддержке, либо настраиваемый тумблер). Естественное место —
   рядом с `navigator.doNotTrack` в `surface_api.rs`.
2. `Sec-GPC: 1` — HTTP-заголовок на каждый исходящий запрос, когда
   сигнал включён. Естественное место — `headers.rs::build_request_headers`,
   в блоке `HttpProfile::Strict`/`HttpProfile::Lumen` (и опционально
   `HttpProfile::TorBrowser`, если реальный Tor Browser его тоже
   отправляет — сверить перед добавлением, чтобы не создать обратный
   fingerprint-разрыв).
3. Оба значения должны быть согласованы (JS-свойство `true` ⇔
   заголовок присутствует) — иначе сайт увидит противоречивый сигнал,
   что само по себе является fingerprinting-вектором.
4. Нужен ли тумблер в `about:settings` (Privacy tab, уже существует,
   `CAPABILITIES.md` строка `Настройки`) или включать по умолчанию —
   решение продукта, не техническое; зафиксировать в ADR при реализации.

## Связанные

* `navigator.doNotTrack` — `crates/js/src/surface_api.rs:19,116-121`
  (реализован, для сравнения).
* `DNT`/`Sec-Fetch-*`/UA per-profile фингерпринт —
  `crates/network/src/http/headers.rs` (ADR-007).
* Категория `gpc` сама по себе не даёт исполняемого сигнала —
  находка исключительно из прямого грепа по кодовой базе, тот же
  приём, что `geolocation-sensor` (но там проба дала отрицательный,
  то есть корректный, результат — здесь положительный, то есть пробел).

## Исправление (P3, 2026-08-11)

### Один источник истины вместо двух половин

Заявка перечисляет две половины сигнала (JS-свойство и заголовок) и
отдельным пунктом 3 требует их согласованности. Реализовывать их как две
независимые правки — значит завести расхождение как класс дефекта: любая
последующая правка одной стороны молча разводит их. Поэтому добавлен
предикат, из которого выводятся **обе** половины:

```rust
// crates/network/src/http/headers.rs
pub fn sends_global_privacy_control(profile: HttpProfile) -> bool {
    matches!(profile, HttpProfile::Lumen | HttpProfile::Strict)
}
```

* сеть: `build_request_headers` добавляет `Sec-GPC: 1` под этим предикатом
  (в двух местах — общая ветка Chrome/Edge/Strict и собственная ветка
  `Lumen`); H2-путь (`h2_fingerprint_headers`) выводится из того же
  блока и получает `sec-gpc` автоматически;
* JS: shell (`config.rs::install_navigator`) зовёт
  `lumen_js::set_global_privacy_control(sends_global_privacy_control(http_profile))`,
  и `surface_api.rs` ставит `navigator.globalPrivacyControl` только при
  включённом флаге.

Расхождение теперь невозможно не по договорённости, а по построению —
и зафиксировано тестом, перебирающим все 7 профилей и сверяющим факт
наличия заголовка с предикатом.

### Почему именно `Lumen` и `Strict`

Профили имитации (`Chrome`/`Edge`/`Safari`/`Firefox`) существуют ради
байт-точного совпадения с чужим браузером. Нативного GPC у настоящих
Chrome/Edge/Safari нет, у Firefox в обычном режиме он выключен — лишний
заголовок там был бы не приватностью, а **меткой**: сигнал, отличающий
Lumen от того, кем он представляется.

`Lumen` (собственный незамаскированный отпечаток) и `Strict` (усиленный
privacy-профиль) не имитируют никого — там сигнал и включён.

`TorBrowser` **намеренно оставлен выключенным**: Tor Browser в принципе
наследует firefox'овое «включён в приватном окне», но проверить это против
реальной сборки в рамках задачи не удалось, а неверная догадка ломает ровно
то байт-точное совпадение, ради которого профиль и заведён. Причина и
условие пересмотра записаны в doc-комментарии предиката, а не только здесь.

### Отсутствие, а не `false`

Когда сигнал выключен, свойства на `navigator` **нет вовсе**.
`'globalPrivacyControl' in navigator` — ровно та проверка, которую делает
fingerprinting-скрипт, и `false` отвечал бы «браузер умеет GPC, но
пользователь его не включил», то есть добавлял бы бит энтропии там, где
имитируемый браузер не даёт ничего (тот же класс, что
[BUG-379](BUG-379-FIXED.md)). Состояния «поддерживаю, но выключен» у Lumen
сегодня нет: сигнал выбирается выбором HTTP-профиля, а не пер-сайтовым
тумблером.

### Пункт 4 заявки (тумблер в `about:settings`) — решение

Отдельного тумблера не заводится, GPC привязан к `http_profile`. Причина:
любой независимый тумблер немедленно воспроизводит ту самую рассогласованность,
от которой предостерегает пункт 3 заявки (пользователь включает GPC на
профиле Chrome → заголовок расходится с имитируемым браузером). Решение
оформлено как [ADR-026](../docs/decisions/ADR-026-global-privacy-control-signal.md).

### Побочный дефект, не названный в заявке

`BrowserSession::set_fingerprint_profile` (driver, обе реализации —
`InProcessSession` и `WinitSession`) меняет HTTP-профиль **в рантайме**.
HTTP-клиент пересобирается из `context.fingerprint_profile()` на каждый
запрос, поэтому переключение на `Strict` немедленно начинало бы слать
`Sec-GPC: 1`, а JS-сторона продолжала бы докладывать профиль, с которым
процесс стартовал — то есть правка «в лоб» (только shell-старт) сама
создала бы расхождение на рантайм-пути. Добавлен
`session::sync_global_privacy_control`, зеркалящий решение сети на JS-флаг
(новое значение доезжает до страницы со следующим JS-контекстом, ровно как
навигаторный/экранный профиль).

## Проверка

**Юнит-тесты.** 4 новых в `lumen-network` (`cargo test -p lumen-network
--lib http::headers`, 17/17) — из них исчерпывающий
`test_sec_gpc_matches_the_predicate_on_every_profile` по всем 7 профилям
(именно он не даёт половинам разъехаться молча), порядок заголовков у
`Strict` (GPC встаёт в privacy-группу между `DNT` и `Sec-Fetch-*`) и
H2-регистр. 3 новых в `lumen-js` (`cargo test -p lumen-js --features
v8-backend surface_api`, 13/13) — `true` и нестираемость при включённом
сигнале, полное отсутствие при выключенном.

**Сквозная живая проба.** Собственные тесты модуля заглушают `navigator`
(`var navigator = { language: 'en-US' }`) и по построению не показали бы,
что свойство доезжает до реального `install_dom`, — и не трогают
`http_profile`-путь вовсе. Поэтому прогнана проба против настоящего
`lumen.exe`: локальный записывающий HTTP-сервер отдаёт страницу, браузер
идёт на неё через `--mcp-live-port`, и **на одном и том же запросе**
сверяются провод и `eval`.

| профиль | `Sec-GPC` на проводе | `'globalPrivacyControl' in navigator` | согласованы |
|---|---|---|---|
| `strict` | `1` | `true` (значение `true`) | да |
| `lumen`  | `1` | `true` (значение `true`) | да |
| `chrome` | нет | `false` (свойство отсутствует) | да |
| `firefox`| нет | `false` | да |
| `safari` | нет | `false` | да |
| `edge`   | нет | `false` | да |

`tor` в живой пробе недостижим (профиль автоматически заводит SOCKS5 на
`127.0.0.1:9050`, живого Tor-демона нет — страница не грузится) и покрыт
только юнит-тестом.

Две ловушки пробы, стоившие прогонов и записанные здесь, чтобы не
повторять: страница **без `<script>`** не получает JS-контекста вовсе и
`eval` отвечает `JS context not available` (это не BUG-298/299/300, а
отсутствие скрипта); и `JSON.stringify` **выбрасывает** член со значением
`undefined`, так что отсутствующий ключ в ответе — это и есть ответ
«свойства нет», а не сбой пробы.
